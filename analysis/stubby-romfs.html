Stubby ROMFS: 포인터 선택과 실제 복사

부트로더가 파일을 선택했다고 해서 항상 바이트를 복사하는 것은 아닙니다. 원본 ROMFS에 있는 kernel과 장치 트리를 이용해, 주소를 돌려주는 경로와 실제 복사 경로를 나눠 확인했습니다.

핵심 요약

  • 원본 mount·파일 조회·wrapper·복사 함수를 대체 함수 없이 실행했습니다. Unicorn 2.1.4의 Cortex-A7 모델에서 여섯 사례가 통과했습니다.
  • 같은 kernel 파일에 maxsize=17을 주어도 포인터 선택 경로는 전체 길이 2,993,056을 반환했습니다. 복사 경로는 17바이트만 기록했습니다.
  • 각 사례 뒤 메모리의 원본 payload 전체와 복사 바이트·목적지 앞뒤 검사 영역을 확인했습니다. 디스크 입력은 여섯 사례가 모두 끝난 뒤 재읽어 보존 여부를 검사했습니다.
  • 실행 주소와 호출 인자는 합성 조건입니다. 실제 SRAM 매핑, kernel 실행, 전체 부팅 또는 ROM 인증을 확인한 결과는 아닙니다.

이전 시험에서 더 내려간 경계

기존 Stubby 시험의 여섯 사례는 상위 적재 함수의 성공·실패와 진입 주소 전달을 확인했습니다. 그때는 파일 wrapper 0x9fc 전체를 대체해 읽기 결과를 양수·0·음수로 넣었습니다.

이번에는 원본 LINUX 레코드 안의 ROMFS를 그대로 읽게 했습니다. mount 0xedc가 읽기 callback을 설정합니다. wrapper의 주소 조회는 0xea4를 직접 호출하고, wrapper의 복사는 이 callback을 거칩니다. 상위 적재 함수와 DTB 보조 함수는 이번 시험에서 호출하지 않습니다. 두 시험은 범위가 달라 기존 여섯 사례를 대체하지 않습니다.

주소와 “원본”의 의미

작은 주소는 LINUX 레코드 시작에서 잰 offset입니다. 0x41000000은 CPU 재현에 주입한 base이며 물리 주소의 증거가 아닙니다. 명령과 ROMFS 바이트는 제공된 원본을 사용하지만, RAM 배치·초기 전역값·호출 인자는 재현기가 정합니다.

mount 이후 주소 선택과 복사로 나뉩니다

mount 후 ROMFS 전역 포인터는 0x41008000, 파일 읽기 callback은 Thumb 주소 0x41000e5d가 됩니다. wrapper는 source와 목적지 조건에 따라 주소 조회 0xea4 또는 이 callback으로 연결됩니다. 주소 조회와 읽기는 같은 lookup 0xd30을 사용합니다.

코드 구간은 9개입니다. wrapper 0x9fc–0xa52, mount 0xedc–0xf1e, PIC 참조 0x1080–0x1098, 주소 조회 0xea4–0xed4, lookup 0xd30–0xe52, big endian 읽기 0xd04–0xd1a, 이름 정렬 0xd1a–0xd30, 파일 읽기 0xe5c–0xe9c, 바이트 복사 0x122e–0x1244입니다. 끝 offset은 제외하며 각 구간의 SHA-256은 검증 JSON에 있습니다.

Cortex-A7에서 재현한 여섯 사례

여섯 사례는 각각 새로운 CPU 인스턴스에서 원본 mount를 호출한 뒤 파일 연산을 실행합니다. 표의 명령 수에는 mount의 39개 명령이 포함됩니다. 원본 파일이나 파일 시스템을 수정해 오류를 주입하지 않았습니다.

복사한 경우 목적지 쓰기는 0x123c에서 1바이트씩 순서대로 발생했습니다. DTB 전체의 SHA-256은 b7968478e48fd492678512ef0efaee63f0fb298ad5d3781bc9975994c0d3b70b이고, kernel 앞 17바이트의 SHA-256은 c80fe044c18fc5953a99290bfa3cb0f2c4c97602010aa3dd84a74c45ec14a40b입니다. 반환값은 raw r0 비트 패턴이며 0xffffffff는 부호 있게 읽으면 −1입니다.

maxsize는 모든 경로의 반환 길이 상한이 아닙니다

마지막 두 사례는 같은 kernel 이름, 같은 목적지 0x40008000, 같은 maxsize=17을 사용합니다. wrapper의 첫 인자만 0과 1로 바꿨습니다.

source 0의 주소 조회 경로는 0xec2에서 파일 전체 길이를 저장합니다. wrapper는 kernel 포인터를 갱신하고 0xa36에서 그 길이를 반환합니다. 이 경로에는 maxsize 비교가 없습니다. source 1의 복사 경로는 0xa46에서 원본 callback을 호출하고, 0xe7c–0xe84의 unsigned 비교로 파일 크기와 maxsize 중 작은 값을 선택합니다.

따라서 “wrapper가 성공하면 반환값은 항상 maxsize 이하”라는 가정은 이 입력에서 성립하지 않습니다. 포인터 선택 경로는 목적지에 쓰지 않았으므로, 이 관측을 곧바로 버퍼 초과 쓰기로 해석할 수는 없습니다.

source 1은 합성 호출 인자입니다

확인한 상위 loader 0x984는 source 0을 전달합니다. 이번 비교는 wrapper가 받은 인자에 따른 동작을 확인한 것이며, 실제 loader에서 source 1 경로에 도달함을 증명하지 않습니다. DTB 목적지 비교도 복사 경로를 선택하는 조건이므로 source 값만으로 모든 호출을 분류해서도 안 됩니다.

원본 보존, 관측 hook과 종료 조건

명령과 ROMFS가 들어 있는 원본 매핑 전체를 read+execute로 설정해 쓰기를 금지했습니다. 각 사례 뒤 원본 3,062,784바이트를 다시 비교하고, 여섯 사례가 끝난 뒤 디스크 입력을 재읽어 SHA-256과 내용을 검사했습니다.

  • 명령 hook: 원본 9개 구간만 실행하도록 검사하고 명령 수·분기 offset을 기록합니다.
  • 쓰기 hook: 해당 목적지 버퍼만 관찰합니다. 복사 횟수와 순서, 1바이트 크기, 기록 명령 0x123c를 검사합니다. 전역값과 앞쪽 검사 영역은 실행 후 확인합니다.
  • 잘못된 접근: 매핑되지 않았거나 보호된 메모리에 접근하면 실패합니다. 어떤 hook도 원본 함수의 반환값을 대신 제공하지 않습니다.
  • 종료: 호출마다 400,000개 명령 이내에 합성 반환 지점 0x70000f00에 도달해야 하며 SP와 r4–r11이 보존돼야 합니다. 선택된 이미지의 첫 명령은 실행하지 않습니다.

목적지 앞 16바이트와 복사 구간 뒤의 나머지 버퍼를 검사했습니다. kernel 버퍼는 4,096바이트, DTB 버퍼는 36,864바이트입니다. 예를 들어 DTB 전체 복사 뒤에는 4,170바이트, kernel 17바이트 복사 뒤에는 4,079바이트가 초기값을 유지해야 합니다. 다른 목적지 버퍼와 mount·callback·DTB·initrd 전역값도 검사합니다. JSON은 복사 바이트 일치와 전체 목적지 해시를 함께 기록합니다.

이전 계측 실패와 남은 과제

앞선 재현에서 모든 주소의 쓰기를 관찰한 구성은 0xa2c에서 매핑되지 않은 0x83800000을 읽으려다 멈췄습니다. callback의 PC 읽기와 레지스터 관측을 제거한 시도도 실패했습니다. 이후 쓰기 hook을 목적지로 한정하고 원본 매핑을 read+execute로 설정한 구성에서 통과했습니다. 두 설정을 함께 바꿨으므로 어느 변경이 원인이었는지는 분리하지 못했습니다. 펌웨어나 에뮬레이터 결함으로 단정하지 않습니다.

이번 도구는 원본 ROMFS의 선택된 파일을 읽는 하위 경계를 확인합니다. ROMFS checksum 검사, 상위 적재 함수와 DTB 보조 함수를 모두 연결한 실행, kernel 진입, M0·BOOT·Boot ROM의 인증, 수정 이미지 수락 여부는 확인하지 않았습니다. 실제 SRAM remap과 bank 선택 문제도 이 시험의 범위 밖입니다.

다음 단계는 상위 정상 적재 경로에 원본 wrapper를 연결하고, 남은 DTB helper 경계를 분리해 검증하는 일입니다. 기존 상위 여섯 사례의 합성 오류 반환 시험은 그대로 보존합니다. 펌웨어 빌드·플래시·실기 장치 접근은 하지 않았습니다.

재현 방법

사용자가 보유한 linux.bin 또는 압축을 푼 전체 decoded.bin을 입력합니다. 기존 Stubby 도구의 크기·전체 SHA 검증 로더를 재사용하고, 새 도구가 실행 구간 9개의 해시도 확인합니다. 원본 바이너리는 저장소에 포함하지 않습니다.

python -m pip install unicorn==2.1.4
python verify_stubby_romfs.py linux.bin --output romfs-linux.json
python verify_stubby_romfs.py decoded.bin --output romfs-decoded.json

기존 출력, 입력 파일 자체, 입력의 hardlink, dangling symlink는 덮어쓰지 않습니다. 출력은 배타적으로 새로 생성하며 검증이 실패하면 비제로 종료합니다. assert 검사를 생략하는 python -O 실행은 시작 단계에서 거부합니다.

검증한 LINUX SHA-256: fcb11ce850f22420ddd6a29d63ef9074ad6322bc021d0ba101e1354d1277b9c2. 전체 decoded 스트림 SHA-256: 7ff301d585ef7adcd620a15575faa39b4227cc5a27eaa8d754efe50f667a30f9. 추출 절차는 펌웨어 구조 보고서에 있습니다.
