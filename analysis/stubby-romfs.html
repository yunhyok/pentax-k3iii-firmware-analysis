Stubby가 ROMFS에서 커널을 고르고 DTB를 복사하는 방식

부트로더가 파일을 “읽었다”고 해서 늘 바이트를 옮기는 것은 아닙니다. Linux 쪽 부트로더 Stubby의 원본 코드를 실행해, 파일 위치만 알려 주는 경로와 실제로 복사하는 경로를 나눠 보았습니다.

  4. 길이 상한은 복사 경로에만 적용됩니다

  7. 재현 방법

핵심 요약

  • Stubby의 원본 ROMFS 함수(mount, 파일 찾기, 파일 wrapper, 복사)를 대체 함수 없이 PC 에뮬레이터에서 여섯 사례로 실행했습니다. 여섯 사례 모두 예상한 결과를 냈습니다.
  • 커널은 복사하지 않고 ROMFS 안의 위치만 전역 포인터에 적습니다. 장치 트리(DTB)는 실제로 복사하며 복사본은 원본과 바이트 단위로 같았습니다.
  • 길이 상한(maxsize)은 복사 경로에만 걸립니다. 같은 커널에 상한 17을 주어도 주소만 고르는 경로는 전체 길이 2,993,056을 돌려주었고 목적지에는 아무것도 쓰지 않았습니다.
  • 로더 시작점부터 이어 실행한 두 사례는 INITFS 헤더를 읽고 DTB의 initrd 범위를 고친 뒤 보드 레지스터 읽기에서 멈췄습니다.
  • 코드를 놓은 주소, 호출 인자, INITFS 위치는 시험용으로 정한 값입니다. 카메라에서 실행한 것이 아니며 커널 기동, 전체 부팅, ROM 인증은 확인하지 않았습니다.

  • 커널 위치 선택과 DTB 복사, 길이 상한의 적용 범위
  • 원본 바이트와 목적지 앞뒤 영역의 보존
  • 로더부터 INITFS 헤더 읽기와 initrd 속성 기록까지

  • Ricoh가 공개한 Stubby 소스의 파일 읽기 함수와 같은 구조
  • 보드 레지스터 값으로 CPU 전압 표를 고치는 공개 소스 구간

모델 시험용으로 정한 값

  • 코드 기준 주소 0x41000000, 스택, 전역 초깃값
  • 파일 연산의 호출 인자와 목적지, 돌아올 지점
  • INITFS를 놓은 주소, 진단 출력 함수의 대체

미확인 확인하지 않은 것

  • 실제 로더가 복사 전용 인자(source 1)로 이 함수를 부르는지
  • INITFS를 메모리에 올리는 실제 경로, 보드 레지스터 값
  • ROMFS 무결성 검사, ROM 인증, 수정 이미지 수락
  • 실제 주소 배치와 카메라 동작

배경: Stubby와 ROMFS

펌웨어 패키지의 LINUX 레코드 맨 앞에는 작은 부트로더 Stubby가 있고 그 뒤에 커널과 장치 트리가 들어 있습니다(펌웨어 구조). 이 파일들은 ROMFS라는 읽기 전용 파일 시스템 안에 묶여 있습니다. Stubby는 ROMFS에서 이름으로 파일을 찾아 커널과 장치 트리(DTB)를 준비하고 커널로 넘어갑니다.

쉽게 말하면

ROMFS가 이미 메모리에 올라와 있다면 커널을 다른 곳으로 옮길 필요가 없습니다. “커널은 여기 있다”고 주소만 적어 두면 됩니다. DTB는 부트로더가 내용을 고쳐 써야 하므로 쓸 수 있는 곳으로 복사합니다. 이 문서는 원본 코드가 실제로 그렇게 나눠 처리하는지 확인한 기록입니다.

앞 문서의 시험과 다른 점

Stubby 적재 조건 문서의 여섯 사례는 상위 적재 함수의 성공·실패와 진입 주소 전달을 보았습니다. 그때는 파일 wrapper 0x9fc 전체를 대체 함수로 바꿔 읽기 결과(양수·0·음수)를 넣어 주었습니다. 여기서는 그 wrapper와 아래 함수들을 원본 그대로 실행하고 LINUX 레코드 안의 ROMFS를 실제로 읽게 했습니다. 아래 여섯 사례는 하위 함수만 부릅니다. 로더 연속 실행 두 사례는 상위 로더부터 들어갑니다.

주소 읽는 법

0x9fc 같은 작은 값은 LINUX 레코드 시작에서 잰 오프셋입니다. 0x41000000은 에뮬레이터에 레코드를 놓은 기준 주소로, 시험용으로 정한 값이며 카메라의 실제 주소가 아닙니다. 명령과 ROMFS 바이트는 원본이고 RAM 배치·전역 초깃값·호출 인자는 재현 도구가 정합니다.

mount 뒤 파일 요청은 두 경로로 나뉩니다

파일 wrapper는 커널 요청을 “주소 조회”로, DTB 요청을 “실제 복사”로 보냅니다. 두 경로는 같은 파일 찾기 함수를 씁니다.

DTB 요청은 주소 조회를 먼저 거친 뒤 복사 경로로 넘어갑니다. bootloader 파일처럼 ROMFS에 없는 이름은 주소 조회에서 실패해 0xffffffff(부호 있게 읽으면 −1)를 돌려줍니다. mount가 등록한 callback은 Thumb 주소 0x41000e5d였습니다. 앞 문서에서 정체를 밝히지 못한 wrapper의 간접 호출(0xa46)이 이 시험 조건에서는 이 callback으로 갔습니다.

공개 소스와 비교

Ricoh가 공개한 Stubby 1.60.1의 src/load_image.c 32–61행 _filesystem_read도 같은 모양입니다. ROMFS이면 먼저 파일 주소를 얻습니다. 대상이 커널이면 포인터만 바꾼 뒤 길이를 돌려줍니다. 대상이 DTB이면 복사로 넘어갑니다. 같은 파일의 DTB 상한 MAX_DTB_SIZE(50 × 1024 = 51,200)와 bootloader 상한(1,048,576)은 이 문서의 호출 인자와 같습니다. 공개 소스와 이 이미지가 같은 빌드라는 증거는 아니므로 구조가 같다는 데까지만 씁니다.

원본 함수로 실행한 여섯 사례

여섯 사례 모두 예상한 결과를 냈습니다. 커널은 주소만 바뀌었습니다. DTB와 상한을 둔 복사는 정확히 요청한 만큼만 목적지에 쓰였습니다.

source 1은 시험용 인자입니다

확인한 상위 로더 0x984는 source 0을 넘깁니다. 이 비교는 wrapper가 받은 인자에 따라 어떻게 움직이는지 본 결과입니다. 실제 로더가 source 1 경로에 닿는다는 증거는 없습니다. DTB 목적지인지도 복사 경로를 고르는 조건이므로 source 값만으로 모든 호출을 나눌 수는 없습니다.

로더부터 이어 실행하면 INITFS 헤더와 DTB 속성까지 갑니다

원본 로더 0x984에서 시작한 두 사례는 커널 선택과 DTB 복사를 마치고 INITFS 헤더를 읽었습니다. INITFS를 놓아 준 사례는 DTB의 initrd 범위까지 고친 뒤 보드 레지스터 읽기에서 멈췄습니다.

로더 안의 try_source(0, 0, 0)가 mount를 불렀습니다. 이어 원본 load_files(0, 1, 0)가 wrapper에 넘긴 source는 모두 0이었습니다. 결과는 위 여섯 사례와 같습니다. bootloader 조회는 −1을 돌려주었습니다. 커널 조회는 포인터를 0x41009000으로 바꾸고 2,993,056을 돌려주었습니다. DTB는 0x42800000에 순서대로 복사되었습니다. 대체한 것은 진단 출력 함수 세 개뿐입니다. 그중 0xc84는 INITFS를 놓은 사례에서만 호출됐습니다.

끝 주소는 시작 주소에 헤더의 길이를 더한 값입니다. Linux 장치 트리 규약에서 linux,initrd-end는 범위에 포함되지 않는 끝 주소이므로 이 두 값은 14,451,829바이트 범위를 가리킵니다(Linux chosen 노드 문서). dtb.cfg 조회는 −1을 돌려주었습니다.

멈춘 보드 주소의 쓰임

공개 Stubby 소스 configs/config-sc2000-rtos.h 288–308행은 0x1800003c 값의 하위 5비트로 ASV(전압 등급) 값을 계산합니다. 그 값이 840~900mV 범위이면 DTB의 CPU operating-points 속성을 고칩니다. 이 이미지의 실제 입력값과 하드웨어 의미는 확인하지 못했습니다(Ricoh 소스 배포와 출처).

INITFS 위치, 바뀐 바이트, 감시 범위
  • INITFS 레코드: 압축 해제 스트림의 offset 0x1f5558c, 14,452,736바이트. 헤더 읽기 0xae4, 바이트 순서 변환 0xae8, 포인터 이동 0xaf0.
  • 속성 기록은 1바이트 쓰기 8회였습니다. 원본 DTB와 최종 값이 다른 바이트는 +0x153, +0x161, +0x162, +0x163 네 개입니다.
  • 원본 명령 허용 구간 19개와 실제로 실행한 구간의 해시를 기록했습니다. 데이터 접근은 메모리 영역별로 셌습니다. 쓰기는 스택·전역 영역·복사된 DTB에만 있었습니다. 원본 LINUX와 INITFS, 커널 목적지, DTB 앞뒤 영역의 최종 바이트도 확인했습니다.
  • 진단 대체 함수는 LR로 돌아가며 r0에 0을 두고 r1–r3·r12를 바꿉니다. 복귀 직후 SP와 r4–r11이 보존됐는지 검사했습니다. 0x894 안의 CP15 MPIDR 읽기는 건너뛰었습니다.
  • 명령 수는 원본 명령의 CODE callback 횟수입니다. 끝나지 않은 읽기 명령은 포함하고 진단 대체 함수 본문은 뺐습니다.
  • 두 실행은 SP가 0x7000efc8일 때 멈췄습니다. 초기 SP보다 56바이트 낮은 값은 멈춘 순간의 차이일 뿐이며 실행 중 최대 스택 사용량이 아닙니다.
  • 근거: 로더 실행 검증 JSON

한계와 남은 과제

  • INITFS는 시험에서 정한 주소에 미리 놓았습니다. 실제로 누가 INITFS를 그 주소에 올리는지, 보드 주소에서 어떤 값이 오는지, 커널이 initrd를 쓰는지는 남아 있습니다. BOOT가 INITFS를 같은 주소로 읽어 오라고 요청하는 경로는 bank 선택 문서의 INITFS 시험에서 따로 보았습니다.
  • ROMFS 체크섬, SRAM remap과 bank 선택, M0·BOOT·Boot ROM 인증과 수정 이미지 수락은 이 시험의 범위 밖입니다.
  • source 1 경로를 실제 호출자가 쓰는지 확인하지 않았습니다.
  • 펌웨어 빌드·플래시와 실물 장치 접근은 하지 않았습니다.
처음 시도에서 실패한 계측 구성

모든 주소의 쓰기를 감시한 구성은 0xa2c에서 매핑되지 않은 0x83800000을 읽으려다 멈췄습니다. callback의 PC 읽기와 레지스터 관측을 뺀 시도도 실패했습니다. 쓰기 감시를 목적지로 좁히고 원본 영역을 읽기·실행 전용으로 바꾼 구성에서 통과했습니다. 두 설정을 함께 바꿨기 때문에 어느 쪽이 원인이었는지는 가리지 못했습니다. 펌웨어나 에뮬레이터의 결함으로 단정하지 않습니다.

재현 방법

직접 추출한 linux.bin이나 압축을 푼 전체 decoded.bin을 넣습니다. 원본 바이너리는 저장소에 넣지 않았으며 추출 절차는 펌웨어 구조 보고서에 있습니다.

python -m pip install unicorn==2.1.4
python verify_stubby_romfs.py linux.bin --output romfs-linux.json
python verify_stubby_romfs.py decoded.bin --output romfs-decoded.json
python verify_stubby_loader.py decoded.bin --output stubby-loader.json
  • verify_stubby_romfs.py는 기존 Stubby 도구의 크기·SHA 확인 로더를 다시 쓰며 실행 구간 9개의 해시를 더 확인합니다.
  • 로더 연속 실행에는 LINUX와 INITFS가 모두 든 decoded.bin이 필요합니다. 원본과 INITFS, 명령 구간 19개, 다시 쓰는 공개 Python 모듈 두 개의 SHA-256을 확인합니다. 모듈은 줄 끝을 LF로 맞춰 해시를 검사한 뒤 불러옵니다.
  • 기존 출력 파일, 입력 파일 자체, 입력의 hardlink, 대상이 없는 symlink는 덮어쓰지 않습니다. 출력은 새로 만들며 검증이 실패하면 0이 아닌 값으로 끝납니다. assert를 끄는 python -O 실행은 거부합니다.
