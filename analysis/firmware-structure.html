펌웨어 구조와 하드웨어

펌웨어 업데이트 파일 한 개 안에 무엇이 들어 있는지, 그 내용으로 카메라의 칩과 소프트웨어 구성을 어디까지 알 수 있는지 정리했습니다. 다른 문서를 읽다가 레코드 이름이나 주소가 나오면 여기로 돌아와 찾아보면 됩니다.

이 문서에서

  3. 이름이 붙은 레코드 15개

  5. 원본 코드와 대조한 네 가지 동작

핵심 요약

  • 약 35MB인 펌웨어 파일의 압축을 풀면 약 79MB의 스트림이 나오고 그 안에 이름이 붙은 레코드 15개가 차례로 들어 있습니다. 직접 만든 추출기의 결과는 독립된 공개 디코더의 결과와 바이트 단위로 같습니다.
  • 용량의 대부분은 네 레코드가 차지합니다. 카메라 동작을 맡는 RTOS, Linux(부트로더·커널·장치 트리), Linux의 초기 파일 시스템, 화면 아이콘 묶음입니다. 한 펌웨어에 RTOS와 Linux가 함께 들어 있습니다.
  • Linux의 장치 트리는 이 펌웨어가 Socionext Milbeaut SC2000A 계열과 Cortex-A7을 대상으로 만들어졌음을 직접 보여 줍니다. Ricoh는 이 카메라의 영상 엔진을 PRIME V라고 부릅니다. 기판에 실장된 칩의 각인은 확인하지 않았습니다.
  • 재배포 조건을 확인한 소스 파일 세 개(셸 스크립트 둘, 직렬 포트 드라이버 하나)를 확보했습니다. 카메라 전체를 다시 빌드할 수 있는 비공개 소스는 없습니다.
  • 모든 내용은 파일을 읽고 PC에서 분석한 결과입니다. 카메라에서 실행해 본 것은 없습니다.

확인 파일 바이트를 읽어 대조

  • 파일과 레코드 15개의 크기·위치·SHA-256
  • 압축 해제 결과가 독립 디코더와 일치
  • 장치 트리 속성, 커널 버전과 내장 설정, 초기 파일 시스템의 파일 수
  • 셸 스크립트 두 개가 공개 소스와 바이트 단위로 일치

정적 분석 읽어서 판단

  • Linux 직렬 포트 함수 한 개와 공개 C 소스의 대응
  • RTOS의 적재 주소 추정, HDMI 명령 처리기와 초기화 일부
  • 초기 파일 시스템에 적힌 서비스 시작 순서

미확인 확인하지 못한 것

  • 실장된 칩의 각인, 실제 동작 클록, 가속기의 부품 번호
  • DSP·SRIC·CPU 등 일부 레코드와 스트림 끝부분의 내용
  • 카메라의 부팅 로그, HDMI 출력 등 실기 동작

배경: 업데이트 파일 한 개가 펌웨어 전체입니다

Ricoh Imaging은 K-3 Mark III의 펌웨어를 ZIP 파일로 배포합니다. 그 안의 fwdc233b.bin을 SD 카드에 넣고 카메라에서 업데이트를 실행하면 내장 저장소의 펌웨어가 바뀝니다. 이 연구는 이 파일 하나를 대상으로 합니다.

이 문서는 파일의 지도 역할을 합니다. 각 부분을 깊이 분석한 내용은 주제별 문서에 있습니다.

  • 부팅 초기 코드(M0, BOOT)와 저장소: 부팅과 저장소 안내
  • 카메라가 이 파일을 검사하고 기록하는 과정: 업데이트 과정 안내
  • RTOS의 명령과 촬영·AF·영상 처리: RTOS 명령 안내, 색 처리 안내
  • 파일을 고쳐 다시 포장하는 실험: 재구축 안내
용어

RTOS는 셔터·AF처럼 시간이 중요한 동작을 맡는 작은 운영체제입니다. SoC는 CPU와 영상 처리 회로를 한 칩에 넣은 부품입니다. 장치 트리는 Linux 커널에 하드웨어 구성을 알려 주는 데이터입니다.

파일의 겉 구조: 헤더, 압축 스트림, 꼬리

파일은 128바이트 헤더, 압축된 본문, 280바이트 꼬리로 되어 있습니다. 본문을 풀면 레코드 15개가 이어진 78,683,892바이트 스트림이 나옵니다.

정정

이전 개요 문서는 압축 스트림 뒤의 280바이트를 “용도를 확정하지 않은 영역”이라고 적었습니다. 그 뒤의 업데이트 검사 분석에서 이 280바이트가 버전 레코드 표 256바이트와 꼬리말 24바이트로 읽힌다는 것을 확인했으므로 위 표처럼 고쳤습니다. 버전 레코드의 나머지 필드는 여전히 해석하지 않았습니다. 압축을 푼 스트림 끝의 4,841,096바이트는 이와 다른 영역이며 용도를 모릅니다.

압축 형식과 해시
  • 블록은 2바이트 big endian 길이로 시작합니다. 최상위 비트가 1이면 무압축 블록이고 길이가 0이면 스트림의 끝입니다.
  • LZ 블록은 16비트 플래그 워드를 상위 비트부터 읽어 “다음이 1바이트 리터럴인지, 2바이트 복사 토큰인지”를 가립니다. 복사 길이는 3~10이고 10이면 뒤따르는 바이트로 늘어납니다. 복사 거리는 13비트입니다. 블록은 00 00으로 끝납니다.
  • 압축을 푼 스트림 SHA-256: 7ff301d585ef7adcd620a15575faa39b4227cc5a27eaa8d754efe50f667a30f9
  • 스트림 뒤 280바이트 SHA-256: e65b0144b960c708860bcc64eb75fcf96ae0c8767cc2c1937431416c8d17a152
  • ZIP SHA-256: 6175dae81f56d225b9863d656282ead9617ca82b75884532458675a2372d113d, 구성원 k3III_v220/fwdc233b.bin. REA로 확인한 ZIP 증거 ID는 evidence.json에 있습니다.
  • 비교에 쓴 디코더: Trimz/Ricoh3x의 pdec.py(고정한 커밋). 받은 소스의 SHA-256은 abc92c0090d2b870f2ec74782d67a2decb8c5a1eb8132f35756a2db81cfe8f50입니다.
  • 추출기는 서명이나 진위를 검사하지 않습니다. 한 번에 스트림 하나만 풉니다.

이름이 붙은 레코드 15개

레코드 헤더는 8바이트 이름(대문자, 남는 자리는 0), 16비트 종류(kind), 16비트 번호(index), 32비트 길이 순서입니다. 아래 “시작”은 압축을 푼 스트림에서 내용이 시작하는 위치입니다.

어떤 칩을 대상으로 만든 펌웨어인가

펌웨어 안의 장치 트리와 커널 설정은 Socionext Milbeaut SC2000A 계열과 Cortex-A7을 가리킵니다. 이것은 “Linux가 무엇을 대상으로 빌드되었는가”의 직접 증거입니다. 실장된 부품을 눈으로 확인하지는 않았습니다.

Socionext 보도자료 (2017-01-05)SC2000은 Milbeaut 영상 프로세서 8세대인 “M10V” 시리즈의 제품입니다. CPU는 “ARM Cortex A7 Quad 660MHz”이고 컴퓨터 비전에 맞춘 DSP를 갖췄다고 설명합니다.
Linux 커널 메일링 리스트의 SC2000 지원 패치 소개 (Socionext, 2019-02)“M10V”는 SC2000의 내부 이름이라고 밝힙니다. 구성으로 Cortex-A7 4코어, NEON, DSP, GPU, 최대 3GB DDR3, 전원 제어용 Cortex-M0를 듭니다.
Linux 업스트림 소스Kconfig에 “Milbeaut SC2000/M10V platform”이 있습니다. 장치 트리 소스의 루트 compatible은 socionext,sc2000a입니다. arm,cortex-a7 CPU 노드는 넷(reg 0xf00~0xf03)이고 직렬 포트는 0x1e700010에 있습니다.
Ricoh Imaging 제품 설명K-3 Mark III는 “PRIME V imaging engine”과 “second-generation accelerator unit”을 쓴다고 설명합니다. K-3 II의 영상 엔진은 PRIME III입니다.
akinas의 K-3 Mark III 펌웨어 분석개인 연구자의 독립 분석도 메인 SoC를 Socionext SC2000으로 지목합니다.

펌웨어의 장치 트리에는 CPU 노드 번호(cpu@3, reg 0xf03)와 직렬 포트 주소가 적혀 있습니다. 이 두 값은 업스트림 SC2000A 장치 트리의 네 번째 CPU, 직렬 포트 주소와 그대로 들어맞습니다. 제조사 접두어만 milbeaut,와 socionext,로 다릅니다.

이 식별의 한계

  • PRIME V는 Ricoh의 제품 명칭이고 SC2000A는 장치 트리에 적힌 플랫폼 이름입니다. 이 문서는 두 이름을 같은 부품이라고 단정하지 않습니다.
  • Ricoh가 공개한 커널에는 R03010 보드와 GR III 보드의 설정 파일이 함께 있습니다. 플랫폼을 공유한다는 근거이지만 두 카메라의 펌웨어나 기판이 같다거나 K-3 II의 모든 하위 시스템이 교체되었다고 판단할 근거로는 부족합니다.
  • 실장 패키지의 각인, 카메라의 실제 동작 클록, 별도 가속기의 부품 번호는 확인하지 않았습니다.
  • 패키지의 M0 레코드와 DSP 레코드가 공개 설명에 나오는 “전원 제어용 Cortex-M0”와 DSP를 위한 코드일 가능성이 있습니다. 그러나 펌웨어에서 확인한 것은 레코드 이름과 M0 코드가 Thumb 명령이라는 점까지이므로, 이 대응은 공개 설명에서 나온 추정입니다.

원본 코드와 대조한 네 가지 동작

Linux의 셸 스크립트는 원문을 그대로 꺼낼 수 있고 컴파일된 함수는 기계어를 읽어 동작을 추적할 수 있습니다. 그 예로 Linux 쪽 둘, RTOS 쪽 둘을 확인했습니다.

Linux: 직렬 포트 함수 한 개가 공개 C 소스와 맞습니다

커널 Image 안에는 함수 이름과 주소를 담은 압축 심볼 표(kallsyms)가 있습니다. 여기서 심볼 43,829개를 복원해 usio_tx_empty의 위치를 찾았습니다.

Linux: 카메라 서비스의 시작 순서

INITFS에서 꺼낸 etc/rc.local에는 서비스를 시작하는 순서가 적혀 있습니다.

  1. 무선 드라이버드라이버를 올림
  2. 카메라 제어 데몬준비 표식을 기다림
  3. USB·시스템 관리데몬 시작
  4. 네트워크·BLE일반 모드에서 시작
  5. 웹 API저장장치를 마운트한 뒤
  6. MTP 서비스MTP 장치를 만든 뒤

usr/bin/ble_init.sh에는 위 직렬 포트 드라이버의 장치 이름인 /dev/ttyUSI1이 나옵니다. 이것은 파일에 적힌 순서이며 실제 카메라의 부팅 로그는 수집하지 않았습니다.

RTOS: 적재 주소 추정과 HDMI 명령 처리기

RTOS가 메모리의 어느 주소에 놓이는지는 세 가지 단서를 따로 맞춰 0x52500000으로 추정했습니다. 벡터 기준 레지스터에 기록하는 값, 예외 처리기 포인터, SHELLCMD 표의 명령 주소입니다.

명령 표에서 App_ChangeHdmi의 주소는 0x52508000입니다. RTOS 오프셋 0x8000에서 시작하는 56바이트 전체를 디스어셈블했습니다.

  • 추가 인수가 있으면 첫 인수를 10진수로 해석하는 경로를 거칩니다.
  • 그 값의 하위 8비트를 설정 갱신 함수로 넘기고 처리기는 0을 반환합니다.
  • 하위 함수는 값을 비교한 결과에 따라 레코드 21개의 +0x970 필드에 그 바이트를 기록합니다.

실제 HDMI 모드와 출력 신호가 바뀌는지는 확인하지 않았습니다.

RTOS: 초기화 경로의 일부

리셋 벡터에서 이어지는 주 코어 초기화 경로의 일부는 0x65A80바이트를 복사하고 메모리 구간을 0으로 채웁니다. 이어서 보조 코어가 확인하는 표식을 기록하고 ARM의 SEV 명령(다른 코어를 깨우는 신호)을 냅니다. 이와 별도로 명령 4개짜리 함수 0x52500508은 0x1D001000에 32비트 값 3을 기록합니다.

이 레지스터 기록 함수와 HDMI 처리기는 angr로 C 형태의 의사코드를 만들어 ARM 명령과 대조했습니다. HDMI 함수의 스택 프레임과 간접 반환은 도구가 부정확하게 표현했기 때문에, 그 부분은 명령어를 기준으로 읽었습니다.

한계

  • 여기 적은 것은 패키지에 들어 있는 내용과 컴파일된 코드에 관한 정적 근거입니다. 실행 중에 실제로 쓰이는지, 카메라에서 어떻게 동작하는지는 시험하지 않았습니다.
  • 레코드 15개 가운데 DRAMPARA, DSP, SRIC, CPU, FDRVPARA는 내용을 해석하지 않았습니다. 스트림 끝의 4,841,096바이트도 마찬가지입니다.
  • 추출기는 서명이나 진위를 검사하지 않습니다. 파일이 Ricoh가 배포한 것과 같은지는 SHA-256으로만 확인했습니다.
  • 칩의 식별은 장치 트리와 공개 자료를 맞춘 것이며 기판을 분해해 확인한 것이 아닙니다.
  • 카메라 플래싱, 실기 실행, 전체 펌웨어 재빌드는 하지 않았습니다.

재현 방법

기본 절차는 Python 3 표준 라이브러리만 씁니다. 첫 명령의 출력 폴더는 아직 없는 새 경로여야 합니다. 펌웨어 파일을 읽을 수 있는 위치에서 실행합니다.

python inspect_firmware.py fwdc233b.bin --output-dir .private/my-decode
python verify_findings.py .private/my-decode/decoded.bin
  1. 추출 첫 명령은 압축을 푼 decoded.bin과, 블록마다 원본과 출력의 위치를 적은 inventory.json을 저장합니다.
  2. 검증 둘째 명령은 이 버전의 decoded.bin SHA-256을 먼저 확인합니다. 그 뒤 장치 트리, 커널 설정, 초기 파일 시스템, 공개 셸 원문, 직렬 포트 함수와 HDMI 처리기의 범위를 검증합니다.
  3. 도구 자체 점검 입력 파일 없이 도구만 점검하려면 두 스크립트에 각각 --self-test를 붙입니다.

디컴파일까지 재현하기

자동 디컴파일을 재현하려면 별도의 Python 환경에 angr==10.0.5를 설치합니다. 아래 명령은 원본 RTOS의 해시와 함수 범위를 확인한 뒤 디컴파일러의 C 형태 출력을 표준 출력으로 보냅니다. 디컴파일 경고는 표준 오류에 나옵니다.

python decompile_sample.py .private/my-decode/decoded.bin hdmi
python decompile_sample.py .private/my-decode/decoded.bin register-write

사용한 도구

  • 압축 해제와 레코드 나누기: 이 저장소의 inspect_firmware.py. 결과를 공개 디코더와 비교했습니다.
  • 커널 심볼 복원: vmlinux-to-elf
  • 함수 분석: angr 디컴파일러와 디스어셈블러
  • 배포 ZIP과 구성원의 해시 확인: REA. Windows의 REA 펌웨어 스캐너는 Linux용 Binwalk 공급자가 필요해 실행되지 않았으므로, 위 세 작업은 각각 다른 도구로 했습니다.

약관과 공개 범위

Ricoh의 펌웨어 배포 페이지에 실린 사용 약관 3·4·6항에는 복제, 역분석, 양도를 제한하는 내용이 있습니다. 이 저장소가 공개하는 것은 재배포 조건을 확인한 OSS 파일, 직접 작성한 분석 도구, 측정 결과입니다. 원본 BIN, 추출한 독점 코드, RTOS 디컴파일 출력은 로컬에만 보관합니다. 그래서 재현하려면 펌웨어 파일을 직접 구해야 합니다.
