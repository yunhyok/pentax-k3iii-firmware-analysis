PafMotor 상태 바이트를 쓰는 코드

PafMotor 안의 바이트 하나(+0x43)가 PWM 값과 적응형 문턱의 선택에 쓰입니다. 이 바이트에 누가 어떤 조건에서 무슨 값을 쓰는지 원본 명령을 읽어 정리했습니다.

이 문서에서

  1. 배경: 상태 바이트가 하는 일
  2. 상태 바이트를 둘러싼 객체와 입력
  3. 상태를 쓰는 세 함수와 조건
  4. 피드백 값의 출처와 상태 다시 읽기
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • PafMotor 코드 구간에서 상태 바이트 +0x43에 직접 쓰는 명령 22개를 찾았습니다. 쓰는 값은 0부터 5까지입니다.
  • 두 함수가 피드백 값(또는 호출 인자)을 문턱과 견주고 이전 상태를 보며 1, 2, 3, 5로 차례로 옮겨 갑니다. 다른 하나는 Joint의 요청 코드에 따라 0이나 4를 씁니다.
  • 나중에 적응형 함수가 이 바이트를 다시 읽어 2배·4배 문턱을 고릅니다. 두 읽기 사이에 드라이버 리셋 호출이 있어 두 시점의 값이 같은지는 확인하지 않았습니다.
  • 이 문서는 정적 분석입니다. 원본 코드를 실행하지 않았고 레지스터 값이나 서비스 반환도 넣지 않았습니다. 상태의 원래 이름과 물리적 뜻은 모릅니다.

정적 분석 코드를 읽어 판단

  • 직접 바이트 저장 22개의 위치와 값 (Capstone으로 대조)
  • 두 상태 선택 함수와 Joint 요청 분기의 조건
  • 피드백 값의 출처와 적응형 함수의 재읽기
  • 28개 구간 해시, 명령 위치 35개, 분기표 2개

미확인 확인하지 않은 것

  • 원본 코드 실행, 레지스터 읽기, 서비스 반환값
  • 다른 함수나 계산한 주소로 이 바이트를 쓰는 코드
  • 상태 0~5의 원래 이름과 물리적 역할
  • 리셋 전 보관한 값과 적응형 함수가 다시 읽은 값이 같은지

배경: 상태 바이트가 하는 일

PafMotor는 Joint 쪽 하위 제어 객체입니다(AF 드라이버와 PWM 연결). 이 객체의 바이트 +0x43은 두 곳에서 쓰입니다. PWM 요청의 호출점 B가 두 정수를 고를 때와, 적응형 함수가 2배·4배 문턱을 고를 때입니다. 그래서 이 값을 누가 만드는지가 다음 질문이 됩니다.

쉽게 말하면

신호등의 현재 색처럼 “지금 어느 단계인지”를 적어 두는 칸입니다. 측정값이 문턱보다 크면 처음 단계로, 작아지면 다음 단계로 옮겨 적습니다. 이 문서는 그 규칙을 코드에서 읽어 낸 것입니다. 각 단계가 실제로 무엇을 뜻하는지는 아직 모릅니다.

이 문서에서 v는 상태 선택 함수의 진입 r2이거나, r1=0 경로에서 피드백 함수가 돌려준 값입니다. T는 PafMotor+0x5a의 unsigned 반워드이며 문턱 역할을 합니다.

피드백 값과 Joint 요청이 상태 바이트에 쓰입니다. 래퍼와 적응형 함수가 이를 읽습니다. 모두 같은 PafMotor 객체입니다.

피드백 값의 출처와 상태 다시 읽기

상태 선택에 쓰는 피드백 값은 ReloadTimer의 레지스터에서 오는 경로로 보입니다. 상태는 래퍼가 한 번 읽어 보관합니다. 적응형 함수는 리셋 뒤에 다시 읽습니다.

  1. Motor 전달0x52f0b490
    함수 진입 r1=0
  2. 드라이버 피드백0x53178310
    반환의 하위 16비트
  3. ReloadTimer (키 0xd1)드라이버 +0x38
    vtable +0x6c → 0x5326d5e4
  4. 레지스터 읽기0x5326d5e8
    주소 0x1e000024

AfMotorDriver +0x38에 키 0xd1의 ReloadTimer가 결합돼 있으면 ROM vtable +0x6c가 0x5326d5e4를 가리킵니다. 이 경우 0x5326d5e8의 LDR 주소는 0x1e000024로 계산됩니다. 등록이 성공하는지와 레지스터의 실제 값은 관찰하지 않았습니다. ReloadTimer 결합의 실행 근거는 AF 서비스 객체와 레지스터 경계에 있습니다.

래퍼 0x52f0be18은 앞서 읽은 상태값을 보관하고 0x52f0be38에서 드라이버 리셋 경로를 부릅니다. Motor +0x2c가 0이고 보관한 값이 2나 3이면 적응형 함수로 갑니다. 적응형 함수는 0x52f0bd78에서 같은 상태 바이트를 다시 읽습니다.

문턱과 비교하는 수치는 별도 서비스 0x53106370의 unsigned 반환값입니다. 그 값이 무엇인지는 AF 적응형 문턱의 입력에서 추적했습니다. PWM 요청의 실행 검사는 적응형 함수 호출 앞에서 멈췄습니다(PWM 실행 범위).

주의

래퍼가 보관한 값과 적응형 함수가 다시 읽은 값 사이에는 드라이버 리셋 호출이 있습니다. 두 시점의 값이 같은지는 확인하지 않았고 같다고 가정하지도 않았습니다.

한계와 남은 과제

  • 검색 범위: 저장 검색은 [0x52f0b380, 0x52f0de00) 구간의 명시적 STRB [receiver,#0x43]만 봤습니다. 다른 함수, 계산한 주소, 간접·광역 저장은 목록에 없을 수 있습니다.
  • 실행하지 않음: 원본 ARM 명령을 실행하지 않았습니다. 장치 레지스터를 읽거나 서비스 반환값을 넣은 실험도 없습니다. 객체 별칭과 분기 조건은 원본 명령을 사람이 따라가 해석했습니다.
  • 뜻: 상태 0~5의 원래 이름, 문턱 T와 피드백 값의 단위는 모릅니다.

재현 방법

검사기는 원본 RTOS 또는 decoded.bin의 해시를 확인합니다. 그다음 Capstone으로 28개 구간, 직접 바이트 저장 22개, 명령 위치 35개, 분기표 2개를 대조합니다. 전체 기록이 원래 연구에서 동결한 결과의 형 해시와 직렬화 해시에 모두 맞아야 JSON을 씁니다.

Capstone 런타임은 5.0.7입니다. 검증 환경의 Python 배포 패키지는 capstone 5.0.9였습니다. --compare는 LF와 CRLF를 모두 받고 출력은 새 파일 경로여야 합니다.

python -B verify_af_state_producers.py path/to/rtos.bin --output new-state-checks.json --compare analysis/af-state-producer-checks.json
python -B verify_af_state_producers.py path/to/decoded.bin --output new-decoded-checks.json --compare analysis/af-state-producer-checks.json
