두 시각 조회 함수가 출력 버퍼에 쓰는 값

커널에는 “지금 몇 시인가”를 돌려주는 함수가 둘 있습니다. 두 함수가 64비트 카운터와 하위 시간을 어떤 모양으로 내놓는지, 값을 쓰기 전에 무엇을 검사하는지 확인했습니다.

이 문서에서

  1. 배경: 시각은 굵은 값과 잔 값으로 나뉩니다
  2. 주 시각은 상위 32비트를 앞에 놓습니다
  3. 값을 쓰기 전에 실행 문맥을 검사합니다
  4. 디스패치 표에는 있지만 부르는 쪽은 찾지 못했습니다
  5. 함수마다 6개, 모두 12개 사례
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 두 함수는 출력이 둘입니다. 주 시각(64비트, 워드 두 개)과 하위 시간(32비트 정수)을 서로 다른 포인터에 저장합니다.
  • 주 시각은 상위 32비트를 앞에, 하위 32비트를 뒤에 둡니다. 이 8바이트를 흔한 little-endian 64비트 정수로 읽으면 두 워드가 뒤바뀝니다.
  • 한 함수는 카운터에 64비트 보정값을 더한 값을, 다른 함수는 카운터만 내놓습니다. 하위 시간은 둘 다 하위 시간 변환의 결과입니다.
  • 값을 쓰기 전에 실행 문맥을 검사하고, 조건이 맞지 않으면 아무것도 쓰지 않고 다른 코드로 넘어갑니다.
  • 함수마다 6개씩 12개 사례를 원본 기계어로 실행했습니다. 이 함수들을 실제로 부르는 쪽과 시간 단위는 찾지 못했습니다.

확인 원본 코드 실행으로 확인

  • 출력 값, 저장 위치, 기록 순서
  • 32비트 자리올림과 64비트 순환
  • 문맥 검사의 통과와 실패 갈래
  • 하위 시간 출력이 변환 식과 일치

정적 분석 코드를 읽어서 판단

  • 디스패치 표에 두 함수의 주소가 들어 있음

모델 시험 조건으로 정한 것

  • 카운터, 보정값, task 상태, 타이머 레지스터는 직접 넣은 값
  • lock과 인터럽트 차단·복원은 대체 함수
  • 에뮬레이터의 MPIDR 값에 따라 CPU 0으로만 실행

미확인 확인하지 않은 것

  • 이 함수들을 부르는 코드와 요청 번호
  • 검사에 실패한 뒤 넘어가는 코드의 동작
  • 시간 단위와 실제 카운터 범위
  • 출력이 쓰이는 곳과 촬영 동작에 미치는 영향

배경: 시각은 굵은 값과 잔 값으로 나뉩니다

커널의 시계는 두 층입니다. 굵은 층은 틱마다 오르는 64비트 카운터이고, 잔 층은 틱과 틱 사이를 하드웨어 타이머에서 읽어 환산한 하위 시간입니다. 이 문서의 두 함수는 두 층을 한 번에 읽어 호출자에게 건넵니다.

하위 시간 변환 함수를 부르는 곳을 찾다가 이 두 함수에 닿았습니다. 그래서 타이머 사슬에서는 곁가지에 해당합니다. 예약과 콜백의 본줄기는 커널 호출, 기한 큐 삽입, 지연 콜백으로 이어집니다.

주 시각
64비트 카운터에서 나온 값. 32비트 워드 두 개로 저장됩니다.
보정값
카운터에 더하는 또 하나의 64비트 값. 근거 파일에서는 OFFSET64라고 적습니다. 예약 시각에 더하는 32비트 주기 값과는 다른 변수입니다.
하위 시간
하드웨어 타이머의 카운터 차이를 환산한 32비트 정수.

주 시각은 상위 32비트를 앞에 놓습니다

두 함수 모두 첫째 인수가 가리키는 곳의 +0에 상위 워드, +4에 하위 워드를 쓰고, 둘째 인수가 가리키는 곳에 하위 시간을 씁니다.

두 함수는 들어올 때 받은 첫째 인수(r0)를 주 시각 출력 포인터로, 둘째 인수(r1)를 하위 시간 출력 포인터로 보관합니다. 먼저 하위 시간 변환 함수를 불러 그 반환값을 둘째 포인터에 저장하고, 그다음 주 시각의 두 워드를 씁니다. 정상 경로의 반환값은 0입니다.

쉽게 말하면

카운터가 4,294,967,295일 때 카운터만 읽는 함수는 +0에 0, +4에 4,294,967,295를 씁니다. little-endian 방식에서는 64비트 정수의 하위 워드가 앞에 오므로, 이 8바이트를 그런 정수로 읽으면 전혀 다른 큰 수가 됩니다. 출력은 “워드 두 개짜리 구조체”로 다뤄야 합니다.

NOW64는 틱마다 오르는 카운터이고, OFFSET64는 타이머 초기화가 카운터와 함께 0으로 만드는 또 하나의 64비트 변수입니다. 이 값을 0이 아닌 값으로 바꾸는 코드는 이 문서에서 다루지 않았습니다.

참고: 공개 T-Kernel 소스와 견주면

공개 T-Kernel 2.0의 시스템 시각 구조체 SYSTIM은 상위 32비트 hi가 앞, 하위 32비트 lo가 뒤입니다. 그 소스에는 시각 구조체와 나노초 단위의 잔 값을 함께 돌려주는 td_get_tim과 td_get_otm이 있습니다. 앞의 것은 동작 시간에 보정값을 더한 시각을, 뒤의 것은 동작 시간만 돌려줍니다. 이 문서의 두 함수와 같은 모양이지만, 이름과 단위를 이 펌웨어에서 확인한 것은 아닙니다.

값을 쓰기 전에 실행 문맥을 검사합니다

두 함수는 인터럽트를 막고 lock을 잡은 뒤, 현재 CPU의 task 상태를 봅니다. 세 조건 가운데 하나가 맞아야 값을 읽는 경로로 갑니다.

세 갈래 모두 사례로 실행했습니다. task가 없는 경우, task의 바이트에 다른 비트가 켜진 경우, CPU별 값이 1인 경우는 출력까지 진행했습니다. task가 있고 바이트 검사 값이 0이며 CPU별 값이 0인 경우는 출력 전에 다른 코드로 넘어갔고, 그때 출력 버퍼는 그대로였습니다.

주의

넘어간 뒤의 코드가 되돌아오는지, 멈추는지, 잡아 둔 lock과 인터럽트 상태를 어떻게 처리하는지는 이 결과로 판단하지 않습니다. 시험은 그 주소에서 멈췄습니다. 디컴파일된 C에는 이 조건 분기가 빠져 있어서, 분석은 원본 ARM 명령을 기준으로 했습니다.

디스패치 표에는 있지만 부르는 쪽은 찾지 못했습니다

두 함수의 주소는 시스템 호출의 디스패치 표에 들어 있습니다. 그러나 그 칸을 가리키는 함수 번호를 실제로 싣고 호출하는 코드는 확인하지 못했습니다.

하위 시간은 재적재 값 6,749에 카운터 차이를 차례로 0, 4,294, 4,295, 6,749, 1로 두고 원본 변환 함수를 함께 실행한 값입니다. 차이 4,295에서 4가 나오는 것은 하위 시간 문서에서 본 32비트 넘침 그대로입니다.

출력 값 말고도 다음을 검사했습니다.

  • 두 번 겹쳐 받은 인터럽트 차단 값이 받은 순서의 반대로 복원되는지
  • lock과 unlock에 넘기는 인수
  • 출력의 기록 순서, 출력 버퍼 앞뒤 메모리의 보존
  • 타이머 레지스터 영역과 커널 변수 영역이 바뀌지 않는지
시험 조건

따로 잘라 낸 RTOS 파일과 통합 decoded 파일에서 결과가 같았습니다. Unicorn이 돌려준 MPIDR 값이 CPU 0을 고르는 조건이었고, 다른 CPU 번호는 시험하지 않았습니다. 두 출력 버퍼는 서로 겹치지 않게 두었습니다. 버퍼가 겹칠 때나 여러 곳에서 동시에 읽을 때의 일관성은 확인하지 않았습니다. lock과 인터럽트 차단·복원은 대체 함수여서 실제 효력은 재현하지 않았습니다.

새로 보관한 디컴파일 C는 2개입니다. 이 문서의 ARM 명령 113 words는 하위 시간 문서에서 이미 보관한 범위와 겹칩니다. 새로 한 것은 두 조회 함수의 선택 경로 실행이고, 원본 명령 113개를 더 찾았다는 뜻이 아닙니다.

한계와 남은 과제

  • 부르는 쪽을 모릅니다. 이 함수들의 출력을 실제로 쓰는 코드와 호출 규약은 연결하지 못했습니다.
  • 시간 단위와 카운터의 실제 범위를 모릅니다. 현재 판단은 타이머 설정과 64비트 카운터에 정리했습니다.
  • 이 출력 구조만으로 결함을 말할 수 없습니다. 실제 시각 값이 거꾸로 가는지, 카메라 동작에 문제가 있는지는 이 결과로 판단하지 않습니다.
  • 검사 실패 뒤의 코드는 보지 않았습니다. 시험은 넘어가는 주소에서 멈췄습니다.
  • 카메라 입출력과 펌웨어 빌드·기록은 하지 않았습니다.

재현 방법

입력은 따로 잘라 낸 RTOS 파일이나 통합 decoded 파일입니다. SHA-256과 적재 주소는 UI 타이머 문서의 재현 방법과 같습니다. Python 패키지 unicorn이 필요합니다.

python verify_update_clock_readers.py rtos.bin --output clock-readers.json

원본 C, ARM 목록, 바이너리는 공개하지 않습니다.
