AF와 렌즈 제어

AF와 렌즈 제어 안내

자동 초점은 초점 오차를 계산하고 그만큼 렌즈를 움직이는 일입니다. 이 주제는 K-3 Mark III 펌웨어가 렌즈의 능력을 확인하고 구동 방식을 고른 뒤, 요청을 만들어 드라이버와 PWM 쪽으로 내려보내는 경로를 따라갑니다.

핵심 요약

  • 렌즈가 알려 준 능력 바이트의 bit 6이 두 제어 코드 가운데 하나를 고릅니다. 1이면 InMotor 쪽이 렌즈에 보낼 요청을 만들어 큐에 넣습니다. 0이면 Joint 쪽이 PafMotor·드라이버·PWM으로 이어지는 하위 제어를 씁니다.
  • 두 경로 모두 원본 기계어를 PC 에뮬레이터에서 구간별로 실행해 확인했습니다. 실행은 렌즈 통신 함수나 첫 레지스터 접근 앞에서 멈춥니다. 상태 바이트와 적응형 문턱 입력은 코드를 읽어 정리한 정적 분석입니다.
  • InMotor 쪽의 “완료” 통지는 렌즈 쪽 전달을 건너뛴 경우에도 돌아왔습니다. 소프트웨어의 완료와 렌즈의 실제 이동은 다른 사실입니다.
  • 실제 렌즈 통신, 모터의 움직임, 초점 정확도는 하나도 확인하지 않았습니다. 요청 값과 PWM 값의 물리 단위, 시간 표본의 단위도 모릅니다.

동그라미 숫자는 아래 읽는 순서의 문서 번호입니다. 상자 제목을 누르면 그 문서로 갑니다. 위에서 아래로 갈수록 하드웨어에 가까워집니다. 맨 아래 점선 상자부터는 아직 아무것도 확인하지 못한 영역입니다.

“확인”은 그 문서가 다루는 코드 구간을 실행해 결과를 봤다는 뜻입니다. 구간과 구간 사이의 연결은 문서마다 실행으로 이은 것과 코드를 읽어 이은 것이 섞여 있습니다. 각 문서의 검증 범위 상자에서 구분해 두었습니다.

배경 지식

이 주제의 문서를 읽는 데 필요한 개념을 짧게 정리합니다. 더 자세한 설명은 세 기종 AF 기초 비교에 있습니다.

바디 모터와 렌즈 안 모터

K 마운트 렌즈의 초점은 바디의 모터가 돌릴 수도, 렌즈 안의 모터가 움직일 수도 있습니다. 리코이미징은 바디 모터로 하는 자동 초점을 “Body AF”라고 부릅니다. 렌즈 안 모터는 SDM(초음파), DC, PLM(펄스·스테핑)으로 구분합니다(리코이미징 초점 구동 표기). 바디 모터의 회전은 마운트의 AF 커플러로 렌즈에 전해집니다. 리코이미징의 K-3 Mark III 지원 문서는 모터가 있는 렌즈 가운데 AF 커플러가 없는 렌즈를 KAF3로 분류합니다. 그런 렌즈는 소프트웨어를 바꿔도 바디 모터로 움직일 수 없습니다.

능력 바이트와 두 제어 객체

렌즈가 바디에 알려 주는 정보 가운데 한 바이트(능력 바이트)의 bit 6이 제어 객체를 고릅니다. 1이면 AfInMotorLensControl, 0이면 AfJointLensControl입니다. 이름은 “렌즈 안 모터”와 “연결부”를 떠올리게 하지만 각 객체가 실제로 어느 모터를 움직이는지는 확인하지 않았습니다. 제조사가 이 비트를 무엇이라 부르는지도 모릅니다.

요청, 큐, 완료 통지

InMotor 쪽은 렌즈에 보낼 명령을 바로 보내지 않습니다. 요청 기록을 만들어 대기 줄(큐)에 넣으면 다른 task가 꺼내 처리한 뒤 완료 통지를 돌려줍니다. 완료 통지는 처리 코드가 끝까지 돌았다는 뜻이며 렌즈가 다 움직였다는 뜻이 아닙니다.

PWM

PWM은 전원을 빠르게 켜고 끄며 켜져 있는 시간의 비율로 평균 출력을 조절하는 방식입니다. 모터 구동 칩은 이 비율을 바꿔 모터에 걸리는 평균 전압을 맞춥니다(TI DRV8235 데이터시트 7.3.6.1). Joint 쪽 드라이버가 Pwm 객체 두 개를 붙잡고 있다는 사실은 바디 쪽 구동 하드웨어를 짐작하게 합니다. 그 채널이 바디 AF 모터에 연결된다는 증거는 아직 없습니다.

원본 코드 실행과 대역

“확인”은 펌웨어의 원본 ARM 기계어를 PC의 CPU 에뮬레이터(Unicorn)에서 실행해 결과를 본 것입니다. 렌즈 응답, 객체 상태, 운영체제의 큐·이벤트 함수는 연구자가 정한 합성 입력과 대역(stub)입니다. 카메라에서 실행한 실험은 하나도 없습니다. 결과는 그 조건에서만 성립합니다.

지금까지 알아낸 것과 아직 모르는 것

구동 방식 선택부터 요청 작성, 큐, Joint 쪽 하위 제어, 드라이버와 PWM 레코드까지는 소프트웨어 안에서 이어졌습니다. 그 아래의 통신, 레지스터, 모터와 숫자의 물리 단위는 비어 있습니다.

읽는 순서

위에서 아래로, 렌즈에 가까운 판단부터 하드웨어에 가까운 값 순서로 읽으면 이해하기 쉽습니다. 9번부터는 앞 문서에서 쓰인 값이 어디서 오는지를 거슬러 올라갑니다.

  • 1 · 기초

    세 기종 AF 기초 비교

    AF는 어떤 단계로 진행되며 세 기종에서 각각 어디까지 확인했나?

    다섯 단계로 나눠 확인 범위를 비교합니다. 바디 모터와 렌즈 안 모터, 마운트 구분도 여기 있습니다.

  • 2 · 선택과 요청

    렌즈 구동 선택·명령·응답

    펌웨어는 어디에서 구동 방식을 정하고 렌즈에 보낼 요청을 어떻게 만드나?

    능력 바이트의 bit 6이 제어 객체를 고릅니다. InMotor 쪽이 0x8900·0x8902 2바이트 요청을 만듭니다.

  • 3 · 큐와 완료

    AF 요청 큐와 완료 통지

    만든 요청은 누가 꺼내 처리하며 완료 통지는 무엇을 뜻하나?

    AccessoryArbitrate task가 요청을 실행합니다. 완료 통지는 렌즈 쪽 전달을 건너뛰어도 옵니다.

  • 4 · Joint

    Joint 요청과 하위 제어

    bit 6이 0일 때 Joint 객체는 요청을 받아 무엇을 하나?

    이벤트 0x80에서 내부 모드 1·2를 고릅니다. 하위 서비스나 레지스터 읽기 직전까지 실행했습니다.

  • 5 · 서비스 객체

    AF 서비스 객체와 레지스터 경계

    PafMotor의 리셋 호출은 어떤 하드웨어 객체를 쓰나?

    채널 0은 ReloadTimer(키 0xd1), 채널 1은 Udc(키 0x123)에 연결되며 첫 레지스터 접근 앞에서 멈춥니다.

  • 6 · 모드 1

    Joint 모드 1의 요청과 피드백 계산

    요청 코드와 렌즈 상태가 어떻게 구동 인자와 피드백 숫자가 되나?

    요청 0~9의 분기표와 요청 3의 피드백 누적·조회 계산을 원본 코드로 대조했습니다.

  • 7 · 드라이버

    AF 드라이버와 PWM 연결

    드라이버는 어떤 PWM 객체를 붙잡고 돌아오는 이벤트를 어떻게 처리하나?

    키 0xe0·0xe1의 PWM 두 개를 붙잡습니다. 이벤트에 따라 플래그를 쓰거나 Joint로 넘깁니다.

  • 8 · PWM 값

    AF PWM 요청과 정수 변환

    PafMotor가 넘긴 정수는 어떤 계산을 거쳐 PWM 레코드에 들어가나?

    843/1000 배율과 16비트 제한을 거쳐 12바이트 레코드 한 개나 두 개가 됩니다. 93회 실행으로 확인했습니다.

  • 9 · 상태

    PafMotor 상태 바이트의 쓰기 경로

    PWM 값 선택에 쓰이는 상태 바이트는 누가 어떤 조건에서 쓰나?

    직접 저장 22개가 0~5를 씁니다. 피드백 값과 문턱, 이전 상태로 단계가 옮겨 갑니다(정적 분석).

  • 10 · 시간 표본

    AF 적응형 문턱의 입력

    적응형 함수가 2배·4배 문턱과 비교하는 값은 무엇인가?

    ElapsedTimer가 계산한 두 카운터 표본의 차이를 27로 나눈 몫입니다. 카운터의 단위는 모릅니다(정적 분석).

  • 11 · 기준값

    PafPulse 기준값의 쓰기 경로

    피드백 계산이 읽는 PafPulse의 기준값은 어디서 갱신되나?

    네 쓰기 지점 가운데 두 경로를 실행했습니다. 요청 3의 계산이 같은 객체의 새 값을 읽는 것을 확인했습니다.

  • 12 · 입력값

    PafMotor와 PafPulse의 입력값 경로

    PafMotor와 PafPulse의 남은 입력 필드는 어디서 오나?

    디버그 요청과 설정 레코드 복사, LensInfo 계산을 대조했습니다. Motor +0x56·+0x68의 출처는 아직 모릅니다.

한계와 다음에 확인할 것

  • 하드웨어 아래: 렌즈와의 패킷 교환, PWM·타이머 레지스터 접근, 인터럽트는 실행하지 않았습니다. 모든 실행은 그 바로 앞에서 멈춥니다.
  • 단위: 0x8900 값, PWM 반워드, 적응형 문턱의 시간 표본이 각각 몇 펄스·몇 초인지 모릅니다. D9 ReloadTimer의 클럭과 분주 설정을 추적하는 것이 다음 과제입니다(연구 체크포인트).
  • 연결의 빈칸: 초점 오차 계산 결과가 구동 요청 값으로 바뀌는 경로와 PafMotor 두 필드의 입력은 찾지 못했습니다.
  • 구동 방식 변경: 이 연구는 구형 렌즈의 구동 방식 변경 같은 앞으로의 작업에 대비한 기초 조사입니다. 렌즈 기계 구조, 타이밍, 위치 한계, 보정은 따로 검증해야 합니다.
