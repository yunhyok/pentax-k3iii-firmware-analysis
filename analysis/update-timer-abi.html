펌웨어 업데이트 과정 · 타이머 사슬 2/7

타이머 시스템 호출이 닿는 커널 함수와 예약 시각 계산

UI 타이머의 시작, 정지, 상태 조회는 시스템 호출로 커널에 넘어갑니다. 그 호출이 어느 커널 함수에 닿는지, 커널이 “언제 울릴지”를 어떤 식으로 계산하는지 확인했습니다.

이 문서에서

  1. 배경: UI 코드는 커널 함수를 번호로 부릅니다
  2. 세 호출은 펌웨어 안의 표를 거쳐 커널 함수 세 개에 닿습니다
  3. 예약 시각은 현재 카운터에 지연과 주기 값을 더한 값입니다
  4. 공개 T-Kernel과 번호는 다르고 구조는 닮았습니다
  5. 17개 사례의 구성
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 알람 시작, 정지, 상태 조회 호출의 함수 번호를 펌웨어 안의 디스패치 표에서 직접 찾아 커널 함수 세 개에 연결했습니다. 외부 문서의 번호표에 기대지 않았습니다.
  • 시작 경로는 예약 시각 = 현재 카운터 + 요청 지연 + 주기 값을 64비트로 계산합니다. 상태 조회는 예약 시각에서 현재 카운터와 주기 값을 빼고 음수면 0으로 바꿔 하위 32비트를 돌려줍니다.
  • 이 계산과 표 조회를 원본 기계어로 17개 사례 실행했고 결과는 모두 식과 같았습니다.
  • 펌웨어의 식별 문자열은 SMP T-Kernel 1.00.01을 가리킵니다. 공개된 T-Kernel 2.0 소스와 계산 구조는 닮았지만 함수 번호가 다릅니다. 그래서 공개 소스의 시간 단위 정의를 그대로 옮기지 않았습니다.

확인 원본 코드 실행으로 확인

  • 함수 번호 세 개의 표 조회와 분기 대상
  • 예약 시각의 두 번의 64비트 덧셈
  • 남은 시간의 뺄셈, 음수 처리, 상태 값

정적 분석 코드를 읽어서 판단

  • 예외 벡터에서 SVC 6 처리 코드까지의 연결
  • 호출 직전 함수가 싣는 함수 번호
  • 표의 기준 주소와 항목 값

모델 시험 조건으로 정한 것

  • 현재 카운터, 주기 값, 알람 객체는 직접 넣은 값
  • 큐 삽입 함수는 대체 함수
  • 함수 전체가 아니라 고른 명령 구간만 실행

미확인 확인하지 않은 것

  • 시간 단위
  • 실제 SVC 예외 진입과 권한 검사
  • 경계값이 실제로 생기는지 여부

배경: UI 코드는 커널 함수를 번호로 부릅니다

UI 타이머는 시간을 직접 재지 않습니다. 커널의 알람 기능에 “얼마 뒤에 알려 달라”고 맡기고 필요하면 멈추거나 상태를 묻습니다. 이 세 가지 요청은 시스템 호출입니다.

ARM에서 시스템 호출은 svc 명령으로 시작합니다. 이 명령은 예외를 일으켜 CPU를 커널 쪽 코드로 보냅니다. 어떤 기능을 원하는지는 함수 번호로 알리고 커널은 번호로 디스패치 표를 찾아 해당 함수로 갑니다. 이 문서는 그 표를 따라가 커널 함수 세 개를 찾고 그 가운데 시작과 상태 조회의 시각 계산을 확인합니다.

64비트 카운터
커널이 유지하는 현재 시각 값. 타이머 인터럽트가 올 때마다 커집니다. 타이머 설정과 64비트 카운터에서 다룹니다.
주기 값
카운터가 한 번에 커지는 양. 내장 설정 TTimPeriod에서 읽은 32비트 값입니다.
예약 시각(기한)
알람이 울려야 하는 카운터 값. 이 사슬의 다른 문서에서는 “기한”이라고 부릅니다.

세 호출은 펌웨어 안의 표를 거쳐 커널 함수 세 개에 닿습니다

함수 번호의 상위 16비트를 부호 있는 수로 읽어 표의 위치를 정합니다. 세 번호는 표에서 이웃한 세 칸을 가리키고 그 칸에 커널 함수의 주소가 들어 있습니다.

인덱스는 함수 번호의 상위 16비트에서 65,536을 뺀 값입니다. 표 항목의 위치는 기준 주소에 인덱스의 네 배를 더해 얻습니다. 세 사례 모두 계산한 위치에 든 값이 분기 대상과 같았고 넘겨준 인수 두 개는 바뀌지 않았습니다.

ARM의 예외 벡터 표에서 세 번째 칸(오프셋 8)은 SVC 예외의 자리입니다. 이 펌웨어의 그 칸은 SVC 분배 코드로 가는 분기이고 SVC 6은 디스패치 코드로 이어집니다. 여기까지는 코드를 읽어 확인했습니다. 실행 시험은 권한 검사와 예외 진입을 건너뛰고 디스패치 코드의 뒷부분부터 시작했습니다.

예약 시각은 현재 카운터에 지연과 주기 값을 더한 값입니다

지연이 0이 아닐 때 알람 시작은 64비트 덧셈 두 번으로 예약 시각을 만듭니다. 상태 조회는 같은 값을 거꾸로 빼서 남은 시간을 구합니다.

예약 시각

알람 시작 함수 안의 한 구간은 현재 카운터(64비트)에 요청 지연(32비트)을 더하고 다시 주기 값(32비트)을 더합니다. 결과가 64비트를 넘으면 넘친 부분은 버려집니다. 이어서 기록 함수가 알람 객체 안의 타이머 노드에 예약 시각, 만료 때 부를 함수, 그 인수를 적고 큐 삽입 함수로 넘어갑니다.

시험 조건

이 시험에서 큐 삽입 함수는 불렸다는 사실만 기록하는 대체 함수였습니다. 삽입 자체는 기한 큐 삽입에서 원본 기계어로 따로 실행했습니다. 주기 값이 어디서 오는지는 타이머 설정과 64비트 카운터에 있습니다.

남은 시간과 상태 값

상태 조회 함수는 출력 구조체에 워드 세 개를 씁니다. 첫 워드는 알람 객체의 첫 워드를 그대로 옮긴 값입니다. 둘째는 남은 시간, 셋째는 상태 값입니다.

  • 남은 시간: 상태 값의 맨 아래 비트가 켜져 있을 때만 계산합니다. 예약 시각에서 현재 카운터와 주기 값을 뺀 64비트 결과를 부호 있는 수로 보아, 음수면 0으로 바꾸고 그렇지 않으면 하위 32비트만 남깁니다. 비트가 꺼져 있으면 0입니다.
  • 상태 값: 알람 객체의 상태 값에서 비트 1과 비트 2를 끈 값(flags & ~6)입니다. 맨 아래 비트만 뽑아내는 연산이 아니므로, 다른 비트가 켜져 있으면 1이 아닌 값이 나옵니다.

공개 T-Kernel과 번호는 다르고 구조는 닮았습니다

함수 번호 세 개는 공개 T-Kernel 2.0의 알람 호출 번호와 다릅니다. 반면 계산 방식과 출력 구조체의 순서는 공개 소스의 알람 코드와 같은 모양입니다.

펌웨어 안의 식별 문자열은 SMP T-Kernel 1.00.01을 가리킵니다. T-Kernel은 TRON Forum이 규격과 소스를 공개한 실시간 운영체제입니다. 공개된 것은 단일 프로세서용 2.0 소스이고 이 펌웨어가 쓰는 SMP 판의 소스는 확인하지 못했습니다. SMP 판 규격 PDF는 서버 오류로 받지 못해 근거로 쓰지 않았습니다.

주의

닮았다는 것은 이 문서에서 두 코드를 견주어 본 결과입니다. 같은 소스에서 나왔는지는 확인하지 않았습니다. 공개 T-Kernel 2.0은 지연 값의 자료형 RELTIM을 밀리초로 정의합니다. 하지만 함수 번호가 다른 이 펌웨어에 그 정의를 그대로 적용하지 않았습니다. 시간 단위는 미확인으로 둡니다.

상태 조회90x525d0bfc–0x525d0c54음수 처리, 하위 32비트, 상태 값의 비트

따로 잘라 낸 RTOS 파일과 통합 decoded 파일에서 결과가 같았습니다. 각 실행은 표에 적은 명령 구간 안에서만 진행하도록 제한했습니다. 상태 조회 사례에서는 알람 객체가 바뀌지 않았는지, 출력 구조체 앞뒤의 메모리가 그대로인지도 확인했습니다.

공개하지 않고 보관한 자료는 디컴파일 C 2개, 보조 구간 7개, ARM 명령 453 words입니다. 상태 조회의 디컴파일 결과에는 잘못 복원된 자기 반복 goto가 있어서 판정은 원본 ARM 명령과 실행 결과로 했습니다.

한계와 남은 과제

  • 시간 단위를 정하지 않았습니다. 이 문서가 확인한 것은 정수 계산입니다. 카운터 한 눈금이 얼마의 시간인지는 타이머 설정과 64비트 카운터에서 단서와 함께 정리했습니다.
  • 함수 전체를 실행하지 않았습니다. 각 사례는 함수 중간의 구간에서 시작합니다. 그 구간에 들어오기 전의 검사와 지연이 0일 때의 경로는 재현하지 않았습니다.
  • 실제 SVC 예외, 인터럽트, 스케줄러, 시계는 실행하지 않았습니다. 벡터에서 디스패치 코드까지의 연결은 코드를 읽은 결과입니다.
  • 경계값은 시험이 만든 입력입니다. 32비트 자리올림, 64비트 순환, 음수 처리, 추가 상태 비트가 실제 커널 상태에서 생긴다는 증거는 아닙니다.
  • 알람 정지 함수는 주소만 확인했습니다. 내부 동작은 이 문서의 범위가 아닙니다.
  • 카메라, 운영체제, 저장 매체 입출력과 펌웨어 빌드·기록은 하지 않았습니다.

재현 방법

입력은 따로 잘라 낸 RTOS 파일이나 통합 decoded 파일입니다. SHA-256과 적재 주소는 UI 타이머 문서의 재현 방법과 같습니다. Python 패키지 unicorn이 필요합니다.

python verify_update_timer_abi.py rtos.bin --output timer-abi.json

원본 C, ARM 목록, 바이너리, 문자열 본문은 공개하지 않습니다.
