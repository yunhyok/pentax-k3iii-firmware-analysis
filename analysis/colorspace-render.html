UI와 화면 자원 · 색공간 화면 3

색공간 행의 아이콘·체크 표시와 sRGB 글자 크기 측정

색공간 선택 화면의 한 행이 무엇을 어디에 그리는지 원본 코드로 따라가 봤습니다. 이 문서는 아이콘과 체크 표시를 그리는 단계와 글자를 그리기 전에 크기를 재는 단계를 다룹니다.

이 문서에서

  1. 배경: 행 하나는 세 개의 그림 조각으로 이뤄집니다
  2. 현재값과 스타일이 행 아이콘을 고릅니다
  3. 글꼴 캐시를 준비하는 과정은 네 지점에서 멈춰 봤습니다
  4. sRGB의 네 글자가 76×40 배치 크기로 이어졌습니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 원본 행 코드가 현재값과 스타일에 맞는 아이콘을 골라 시험 표면에 복사했습니다. 다섯 가지 조건 모두 표면 전체와 쓰기 순서가 독립 계산과 같았습니다.
  • 체크 표시는 행의 콜백을 따로 불렀을 때 기록됐고 행 아이콘과 합쳐 1,532개 픽셀을 썼습니다.
  • sRGB 행은 원본 Latin 글꼴 두 파일을 준비한 뒤 네 글자를 재서 배치 크기 76×40을 냈습니다. 이 값은 글자를 놓을 자리의 크기이며 글자 픽셀은 다음 문서에서 그립니다.
  • 모두 PC 에뮬레이터에서 원본 ARM 코드를 실행한 결과입니다. 표면·메뉴 상태·파일 읽기는 시험이 넣어 준 값이고 카메라 LCD 출력과 실제 팔레트·버튼 입력은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 행 생성, 목록 채우기, 아이콘 ID 선택과 ICONBIN 복사
  • 체크 표시 콜백과 체크 아이콘 복사
  • 글꼴 캐시 준비의 네 정지 지점
  • sRGB 네 글자의 측정과 설정 63바이트 복사

모델 시험 조건으로 정한 것

  • 256×144 RAM 표면, 사각형과 클립, 메뉴 현재값·스타일
  • ICONBIN 준비 상태, 언어 바이트 0
  • 글꼴 파일 읽기·메모리 할당은 호출 모형이 응답
  • CPU는 Unicorn 2.1.4의 Cortex-A15 모델

미확인 확인하지 않은 것

  • 화면 전체의 이벤트 순서와 실제 목록 생성 경로
  • LCD의 채널 해석, 실제 파일시스템·잠금·할당기
  • 언어 바이트 0 밖의 문자열, K-3 II·Q7에서의 동작

배경: 행 하나는 세 개의 그림 조각으로 이뤄집니다

색공간 선택 화면에는 sRGB와 AdobeRGB 두 행이 있습니다. 행마다 왼쪽에 체크 표시, 가운데에 행 아이콘, 오른쪽에 이름 글자가 놓입니다. 펌웨어는 이 세 조각을 각각 별도의 화면 부품(위젯)으로 만듭니다. 체크와 아이콘은 IconView, 글자는 StringView라는 부품입니다.

그림이 그려지는 곳은 표면입니다. 표면은 RAM 안의 픽셀 배열이며 이 시험에서는 가로 256, 세로 144픽셀에 픽셀 하나가 4바이트 워드입니다. 아이콘은 ICONBIN 레코드의 그림을 그대로 복사합니다. 글자는 먼저 크기를 재고 그 크기로 자리를 잡은 뒤 픽셀을 찍습니다. 이 문서는 크기를 재는 데까지 다룹니다.

원본 실행은 세 단계로 나눠 했습니다. 단계마다 시험 조건을 새로 준비했고 화면 전체의 이벤트 순서는 재현하지 않았습니다.

  1. 행과 아이콘타입 19 행을 만들고 ID를 설정합니다. IconView가 ICONBIN 그림을 표면에 복사합니다.
  2. 글꼴 준비StringView가 언어 0의 문자열을 찾고 Latin 글꼴을 캐시에 올립니다.
  3. sRGB 크기 측정네 글자를 재서 76×40을 얻고 그리기 설정 63바이트를 복사합니다.

현재값과 스타일이 행 아이콘을 고릅니다

현재값과 스타일 바이트에 따라 아이콘 ID가 바뀌었고 다섯 조건 모두 표면 전체와 쓰기 순서가 독립 계산과 같았습니다.

타입 19 행의 생성자는 체크용 IconView, 행 아이콘, StringView를 행 객체 안에 차례로 둡니다. 원본 목록 채우기 함수는 색공간 메뉴의 디스크립터 72번을 읽고 행에 아이콘과 문자열 ID를 넘깁니다. 체크 표시를 켤지는 설정 레코드의 현재값과 비교해 정합니다. 화면에서 지금 고르고 있는 행(포커스)은 방향 입력·포커스 재현에서 다룹니다.

읽은 픽셀보다 쓴 픽셀이 적은 것은 복사 함수가 상위 바이트가 건너뛰기 키와 같은 픽셀을 쓰지 않기 때문입니다. 마지막 조건은 행 아이콘 1,600+1,444에 체크 아이콘 800+88을 더한 값입니다. 하네스가 행의 원본 +0x6c 콜백을 따로 부르자 체크 ID 0x231이 기록됐습니다.

아이콘마다 그린 뒤 256×144 표면 전체와 순서 있는 쓰기 목록을 독립 바이트 계산과 대조했습니다. 사각형, ICONBIN 슬롯과 초기화 상태는 호스트가 공급했습니다. ICONBIN 형식과 복사 규칙은 ICONBIN 형식과 복사 규칙에 있습니다.

두 행의 StringView는 언어 바이트 0을 받아 원본 문자열 표의 슬롯 1을 골랐습니다. ID 0x1f6은 sRGB, ID 0x1f7은 AdobeRGB를 가리킵니다. 둘 다 NUL로 끝나는 UTF-16LE 문자열입니다. 원본 표의 21개 슬롯 전체에서 두 이름은 정적으로 대조했고 실행은 언어 바이트 0으로 한정했습니다. 색공간 값과 메뉴 리소스의 연결은 색공간 선택 화면 문서에 있습니다.

글꼴 캐시를 준비하는 과정은 네 지점에서 멈춰 봤습니다

글꼴 캐시가 비어 있으면 원본 코드는 RT·LE 두 Latin 글꼴 파일을 요청합니다. 이어서 두 렌더러와 작업 공간을 만들고 RT 글꼴을 읽어 성공(0)을 돌려줍니다.

글꼴 시험은 모두 sRGB 행의 원본 StringView 진입점에서 시작합니다. 언어 슬롯 1은 글꼴 선택자 0을 고릅니다. 성공 사례에서는 파일 이름·크기·복사 주소를 검사하는 호출 모형이 decoded 파일의 RT_Latin.bin 53,880바이트와 LE_Latin.bin 20,784바이트를 복사해 넘겼습니다. 실제 파일시스템, 잠금, 할당기, 실패 뒤 재시도는 실행하지 않았습니다.

sRGB의 네 글자가 76×40 배치 크기로 이어졌습니다

원본 측정 경로는 s·R·G·B를 하나씩 재고 너비 76과 높이 40을 StringView 설정에 복사합니다. 이 크기는 글자를 놓을 자리이며 글자가 실제로 찍힌 범위와는 다른 값입니다.

  1. 작업 공간 할당5,960바이트를 요청하고 NUL 포함 UTF-16 다섯 단위를 받습니다.
  2. LE 준비s,R,G,B,NUL로 매핑 레코드 다섯 개를 만듭니다.
  3. 문자 측정네 번의 측정 호출이 각각 0을 돌려줍니다.
  4. 크기 계산결과 [0, 76, 40, 15000, 15000]
  5. 설정 복사63바이트를 StringView+0x188에 복사합니다.
측정 단계별 원본 관측값
원본 코드관측값
0x528c38a4 · 작업 공간 할당원본 크기 계산 경로가 5,960바이트를 요청합니다. 준비 함수는 NUL을 포함한 UTF-16 단위 다섯 개를 받습니다.
0x5338aa64 · LE 준비s,R,G,B,NUL을 읽고 LE 매핑 레코드 다섯 개를 만듭니다. 이 레코드의 RT 글리프 ID는 확인하지 않았습니다.
0x5338da60 · 문자 측정내부 측정 호출 네 번이 차례로 s,R,G,B를 받아 각각 0을 돌려줍니다. 요청 경계의 halfword 네 개는 [0, 2, 75, 37]입니다.
0x528c3930 · 크기 계산20바이트 결과는 [0, 76, 40, 15000, 15000]입니다. 너비는 Xmax+1이고 높이는 별도의 줄 높이 계산에서 나왔습니다. 마지막 두 값의 뜻은 확인하지 않았습니다.
0x52beec08 · StringView 복사임시 그리기 설정 63바이트가 StringView+0x188에 그대로 복사됩니다. 너비는 +0x194, 높이는 +0x198에서 읽었습니다.

측정 결과가 메모리의 초기값에 기대지 않는지도 봤습니다. 같은 측정을 할당 영역을 00, A5, 5A로 채운 세 조건에서 실행했고 채움값과 조건 이름만 맞춰 놓자 세 결과가 모두 같았습니다.

  • RT 준비까지만 실행한 두 대조는 IMAGE1 할당 12개를 A5와 5A로 채웠습니다. 실행 추적과 파일 호출·읽기 기록이 0으로 시작한 글꼴 시험과 같았습니다.
  • 전체 측정 세 대조는 같은 12개에 작업 공간 하나를 더해 13곳을 채웠습니다. 정규화한 필드는 조건 이름과 채움값 13개, 모두 14개입니다.
  • 세 측정 모두 같은 63바이트를 복사했고 앞 단계의 아이콘·체크 1,532개 쓰기와 표면 SHA-256도 같았습니다.
주의

기존 문맥 등 나머지 메모리는 하네스의 초기 상태를 유지했습니다. 이 대조만으로 힙 전체가 초기값과 무관하다거나 모든 라이브러리 읽기의 초기화 순서가 맞다고 말할 수는 없습니다.

LE 임시 레코드 쓰기와 설정 해시
  • 새로 매핑한 LE 임시 레코드 0x547cd248에는 쓰기 세 번만 허용했고 최종 4바이트는 00 00 00 01입니다. 이 영역을 쓰기 전에 읽는 일이 있으면 잡는 훅을 두었습니다. 게스트 읽기는 관찰되지 않았습니다.
  • 복사한 그리기 설정의 SHA-256은 f8341380dc7a5523cb0d150da83a1aecf8ea871b75c4e7874fe1d26db2ed1a9f입니다.
  • 측정 구간 16곳의 SHA-256은 colorspace-render.json의 measurement_ranges에 있습니다.

한계와 남은 과제

  • 아이콘, 체크, StringView를 같은 재생 안에서도 따로 불렀습니다. 화면 전체의 이벤트와 호출 순서는 재현하지 않았습니다.
  • 현재값·스타일·사각형·ICONBIN 준비 상태·표면은 시험 입력입니다. 카메라 LCD가 4바이트 워드의 채널을 어떻게 해석하는지는 시험하지 않았습니다.
  • 글꼴 파일 읽기와 할당은 호출 모형이 대신했습니다. 문자열 실행은 언어 바이트 0으로 한정했습니다.
  • 설정 저장, 메뉴 입력, K-3 II·Q7으로 옮겼을 때의 동작은 확인하지 않았습니다. 세 기종 비교는 세 기종 UI 이식 검증 조건에 있습니다.

같은 StringView의 별도 그리기 슬롯 0x52bedb40에서 시작하는 글자 래스터와 전송은 sRGB 글자의 래스터와 픽셀 전송에 기록했습니다. 그 문서는 같은 글꼴의 부분 커버리지 표본 705개를 합성 표면에 쓰는 구간까지 확인합니다. 두 문서의 시험은 각자의 실행 범위를 지킵니다.

재현 방법

입력은 K-3 III 펌웨어 2.20의 decoded 파일(78,683,892바이트)입니다. 명령은 입력과 도우미 소스의 SHA-256을 확인한 뒤 실행하며 출력 파일은 새 경로여야 합니다. 실행한 A32 명령을 입력과 비교하고 메모리 쓰기 범위, 표면 경계, 입력과 재배치 영역이 바뀌지 않았는지 검사합니다.

python -B tools/verify_colorspace_render.py decoded.bin --output colorspace-render-replay.json
python -B -m unittest discover -s tests -p test_verify_colorspace_render.py

같은 환경에서는 새 JSON의 SHA-256을 공개 결과와 비교할 수 있습니다. 결과에는 사례별 실행 주소와 코드 구간의 SHA-256이 들어 있습니다.
