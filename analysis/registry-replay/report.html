펌웨어 재구축 · 시작 과정 재현

원본 할당기가 내준 이름 배열을 0으로 채우고 조회까지 이어 보기

RTOS는 task 같은 객체를 이름으로 찾기 위해 registry 배열을 둡니다. 이 배열을 할당하고 비우고 조회하는 원본 코드를 한 에뮬레이터 안에서 이어 실행해, 포인터가 실제로 전달되는지 확인했습니다.

이 문서에서

  1. 배경: 이름 registry와 0으로 채우기
  2. 배열 할당에서 이름 조회까지 이어진 경로
  3. 두 가지 초기 RAM에서 같은 결과
  4. 합성 RAM과 연구자가 넣은 입력
  5. lock 명령 실행과 빈 이름 대조
  6. 전체 기록을 확인한 뒤에만 요약을 저장
  7. 한계와 남은 과제
  8. 재현 방법
  9. 근거 파일과 참고 자료

핵심 요약

  • 원본 할당기가 task 이름 registry 배열(300칸, 1,200바이트)을 내주었습니다. 원본 코드가 그 자리를 0으로 채운 뒤 포인터를 registry에 저장했습니다. 포인터는 연구자가 넣어 준 값이 아닙니다.
  • 같은 에뮬레이터에서 원본 InitTask 이름 조회가 hash 300개를 읽은 뒤 일치하는 항목 없이 끝났습니다(조회 −1, wrapper 0).
  • 초기 RAM을 00과 A5 두 가지로 바꿔 실행했습니다. 0으로 채우기 전 내용은 달랐지만 채운 뒤 1,200바이트와 조회 결과는 같았습니다.
  • 단일 vCPU의 합성 RAM에서 얻은 결과입니다. 단계 사이는 연구자가 고른 진입점입니다. 다른 registry 유형과 도메인 초기화는 생략했습니다. 물리 lock, 캐시 일관성, 전체 부팅, task 생성 성공은 보여 주지 않습니다.

확인 원본 코드 실행으로 확인

  • 원본 calloc이 반환한 포인터를 원본 store가 registry에 저장
  • 1,200바이트를 4바이트씩 300번 0으로 기록
  • 원본 조회가 hash 300개를 읽고 일치 없음으로 끝남
  • 원본 LDREX/STREX 실행, STREX 결과 10개 모두 0

모델 연구자가 정한 조건

  • heap 전체의 초기 바이트(00 또는 A5)와 호출 스택
  • 단계별 진입점과 일부 진입 인자(개수 300, registry 주소, descriptor)
  • 아직 쓰이지 않은 채 읽어도 되는 RMW 관리 바이트 56개

미확인 확인하지 않은 것

  • 도메인 초기화와 다른 11개 registry 유형
  • creator의 lock·context 검사, task 슬롯 사용
  • 물리 lock, 다중 코어, 캐시 일관성, 카메라 동작

배경: 이름 registry와 0으로 채우기

RTOS는 객체를 이름으로 찾을 수 있게 유형별 registry를 둡니다(task 유형 0을 포함해 12개 유형). task 유형의 registry에는 개수와 배열 포인터가 있습니다. 배열의 각 칸에는 4바이트 hash 값이 들어갑니다. 조회 함수는 찾는 키를 칸마다 비교합니다. 값이 같을 때만 task 이름 레코드까지 내려가 이름을 비교합니다.

배열은 calloc으로 받습니다. 받은 자리에는 켜질 때 남은 값이 섞여 있을 수 있어서 원본 코드가 300칸을 모두 0으로 덮어씁니다. 남은 값이 우연히 키와 같으면 조회가 이름 비교로 내려가 버립니다. 그래서 펌웨어를 다시 만들 때도 할당 직후 0 채우기가 빠지면 안 됩니다.

LDREX/STREX란

할당기는 여러 코어가 동시에 쓰지 못하게 lock을 겁니다. ARM에서는 LDREX로 값을 읽고 STREX로 조건부로 씁니다. STREX는 쓰기에 성공하면 0, 다른 쓰기가 끼어들어 실패하면 1을 돌려줍니다(Arm 동기화 명령 해설). 이 재현에서는 이 명령을 고치거나 결과를 대신 넣지 않고 그대로 실행했습니다.

배열 할당에서 이름 조회까지 이어진 경로

원본 calloc이 반환한 포인터 하나가 0 채우기, registry 저장, 조회까지 연구자의 개입 없이 전달됐습니다.

  1. 준비설정·페이지·arena·task 표를 구간별 별도 진입으로 만듦
  2. calloc 300 × 4내부 할당기가 0x56508808 반환
  3. 0 채우기4바이트씩 300회, 1,200바이트 전부
  4. 포인터 저장원본 store가 registry에 기록
  5. 이름 조회별도 진입, hash 300개 읽고 −1
  6. 정지그 뒤 task 생성은 실행하지 않음

개수 저장과 조회는 연구자가 고른 진입점에서 시작했습니다. 그 밖의 연결은 원본 명령이 직접 이었습니다. calloc의 반환값은 호스트를 거치지 않고 원본 store가 registry에 썼습니다. 조회 구간에는 원본 descriptor만 넘겼습니다. task 표 포인터와 이름 주소는 원본 인자 구성 코드가 스스로 읽고 계산했습니다.

합성 RAM과 연구자가 넣은 입력

원본 이미지에서 가져온 것은 RTOS 코드와 초기 .data뿐입니다. 나머지 RAM과 호출 스택은 연구자가 정했습니다.

논리 heap [0x56492c80, 0x57c52c80)의 초기 바이트는 실험마다 모두 00이거나 모두 A5입니다. 실제 물리 메모리의 내용이라고 가정하지 않았습니다. 페이지 정렬 때문에 생긴 heap 바깥 여백에 guest가 접근하면 거부합니다.

아직 아무도 쓰지 않은 heap 바이트를 읽어도 되는 곳은 RMW 관리 바이트 56개뿐입니다. 할당 경로 재현에서 쓴 48바이트에, 이번 할당에서 처음 읽힌 0x56493278의 8바이트를 더했습니다. 이 8바이트를 읽은 원본 RMW 명령은 네 곳이었습니다. 실행이 끝났을 때는 56바이트 모두 원본 코드가 덮어썼습니다.

lock 명령 실행과 빈 이름 대조

LDREX/STREX는 원본 그대로 실행했고 결과를 강제하지 않았습니다. 빈 이름을 넣으면 원본 wrapper는 배열을 보지 않고 0을 돌려줍니다.

exclusive 명령을 허용한 대상은 할당기 lock 0x54c40e60과 원본 .data에서 −1로 시작하는 counter 0x545011a0 두 곳입니다. 허용한 원본 PC와 RAM 주소를 함께 검사했습니다. 조건마다 관찰한 STREX 결과 10개는 모두 0(성공)이었습니다. DMB·DSB·SEV와 CPSR 마스크 조작도 에뮬레이터 안의 처리입니다. MPIDR·CP15·SVC·MMIO는 실행하지 않았습니다.

core0 분기는 MPIDR 직전에 멈춘 뒤 따로 골랐습니다. 도메인 초기화, 다른 11개 registry 유형의 개수·포인터, creator의 lock·context 검사와 실제 task 슬롯 사용은 생략했습니다. 정적 설정 max_domain_id=100과, 도메인 초기화가 성공했을 때의 레코드 수 101은 구분해야 합니다. 이 재현에서 도메인 초기화를 실행하지는 않았습니다.

빈 이름 대조에는 원본 설정 문자열 안의 NUL 바이트 0x533e3353을 썼습니다. 원본 wrapper는 그 한 바이트만 이름으로 읽었습니다. 개수·배열 포인터·hash는 읽지 않은 채 0을 반환했습니다. 함께 넘긴 task 이름 기반 주소는 실제 원본 task 표에서 계산한 값이며 역참조되지 않았습니다. 실제로 이름이 빈 task descriptor를 찾았다는 뜻은 아닙니다.

전체 기록을 확인한 뒤에만 요약을 저장

공개 CLI는 7,200,103바이트짜리 전체 관측 기록을 메모리에서 다시 만들어 승인된 해시와 같을 때만 요약 JSON을 씁니다.

전체 기록에는 모든 guest 쓰기, 제한된 범위의 읽기, 명령 기록이 들어 있습니다. 전체 trace는 파일로 내보내지 않습니다. 소스 manifest에는 주소·크기·해시만 있고 펌웨어 바이트나 disassembly는 없습니다. 공개 요약에서는 큰 목록을 개수와 해시로 줄였습니다.

  • 쓰기 목록은 스택을 포함한 모든 guest store입니다.
  • 읽기 목록은 아직 쓰이지 않은 RMW 바이트의 읽기와 이름 조회·빈 이름 대조의 읽기만 담습니다. 모든 guest read가 아닙니다.
  • 명령 기록에는 조건이 거짓이라 실행되지 않은 조건부 명령도 들어갈 수 있습니다.

설정부터 task 표 초기화까지의 스택 밖 guest store 3,907개는 할당 경로 재현의 해당 조건 기록과 같았습니다. 초기 heap의 쓰이지 않은 부분까지 같다는 뜻은 아닙니다(이전 기록과의 대조).

원본 분석 스크립트의 해시는 과거 증거의 출처를 나타냅니다. 공개 helper는 그 스크립트의 줄바꿈만 LF로 바꾼 파일이라 해시가 따로 있습니다. 두 해시는 각각 검사합니다(출처와 인코딩 규칙).

한계와 남은 과제

  • 단일 vCPU, 합성 RAM의 결과입니다. 원본 LDREX/STREX는 실행했지만 물리적인 exclusive 동작과 캐시 일관성은 증명하지 않습니다.
  • 설정·플랫폼·페이지·arena·task 초기화는 구간별 별도 진입입니다. 전체 부팅이 아닙니다.
  • table0 개수와 조회 구간은 따로 들어갔습니다. 그보다 먼저 일어나는 도메인 할당과 다른 11개 registry의 개수·포인터 조건은 생략했습니다.
  • InitTask 조회는 일치 없음으로 끝났습니다. task 슬롯을 쓰거나 creator가 성공한 일은 없습니다.
  • 검증 범위는 task 유형 0의 hash 배열과 이름 조회입니다. 카메라 설치용 펌웨어가 아닙니다. 기기 쓰기·빌드·플래시는 하지 않았습니다.

배열이 놓인 페이지를 할당기가 어떻게 고르는지는 설정에서 첫 task 스택까지에서 다룹니다. 이 재현에서 처음 읽힌 8바이트 관리 칸의 최종값은 RMW 8바이트 모형 검증에서 따로 증명했습니다.

재현 방법

Python 3.12에서 Unicorn 2.1.4와 Capstone 5.0.7로 검증했습니다. 의존성 파일과 .gitattributes의 LF 규칙을 유지해야 합니다. 입력은 사용자가 준비한 정확한 decoded 이미지입니다. CLI가 크기 78,683,892바이트와 SHA-256을 검사해 다른 입력은 실행 전에 거부합니다.

python -m pip install -r requirements.txt
python replay.py /path/to/decoded.bin --output result-new.json
python test_replay.py --work-dir /path/to/work --output tests-new.json
python test_replay.py --work-dir /path/to/work --decoded /path/to/decoded.bin --output tests-with-input-new.json

명령은 이 패키지 폴더에서 실행하는 예입니다. 스크립트에 절대 경로를 주면 다른 폴더에서도 됩니다. --work-dir는 이미 있는 작업 폴더, 각 --output은 새 파일이어야 합니다. 펌웨어 입력 없이도 패키지·타입·입출력 검사는 됩니다. --decoded를 주면 위치를 옮긴 원본 재현과 전체 관측 변조 검사까지 합니다.

공개 테스트는 실행마다 독립된 임시 폴더를 만들어 그 안에서만 fixture를 다룹니다. 입력 크기·해시, 최적화 모드, 출력 별칭, helper와 manifest 변조, 필드 타입을 검사합니다. 공개 JSON에서 생략한 개별 guest 쓰기를 바꿔도 전체 관측 검증이 실패하는지 확인했습니다. 다른 경로로 옮긴 재현 두 번을 포함해 25개 검사를 통과했습니다(테스트 결과).

기본 패키지에는 원본 펌웨어와 7MB trace가 없습니다.
