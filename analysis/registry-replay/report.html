K-3 III · 원본 코드의 합성 RAM 재현 · 2026-11-13

원본 할당자가 만든 포인터로
1200바이트 초기화와 이름 조회를 연결했습니다

합성 RAM을 사용하는 단일 vCPU에서 원본 allocator가 0x56508808을 반환했습니다. 원본 코드가 이 주소부터 1200바이트를 0으로 채우고 같은 포인터를 registry에 저장했습니다. 이어서 원본 InitTask 조회가 hash 300개를 읽고 일치 항목 없이 끝났습니다. 원본 실행의 검증 요약

이 재현에서는 합성 ordinary RAM에 대한 원본 LDREX/STREX를 실행합니다. 성공 상태를 대신 넣거나 명령을 고치지 않았습니다. 이 결과는 단일 vCPU emulator의 동작이며 카메라의 물리 lock·캐시 일관성·전체 부팅을 입증하지 않습니다.

1. 실제 포인터가 이어진 경로

실선은 해당 구간 안의 원본 실행 연결, 점선은 호스트가 선택한 독립 진입입니다. 점선을 실제 bootstrap 호출의 연속 실행으로 해석하지 않습니다.

0x525d5bec에 count 300과 원본 전역 registry base를 인자로 넣으면 원본 명령이 element 크기 4를 설정합니다. 0x525d5bf0 → 0x525d99d4의 반환값은 호스트를 거치지 않고 0x525d5bf4에서 저장됩니다. 조회 구간 0x525bb354에는 원본 descriptor만 넘겼습니다. task 테이블 포인터와 이름 주소는 원본 인자 구성 코드가 읽고 계산합니다. 명령·데이터 주소와 해시

3. 합성 입력과 exclusive 실행의 범위

RTOS 코드와 초기 .data는 고정 해시의 원본 이미지에서 가져왔습니다. 나머지 global RAM과 호출 스택은 호스트 모형입니다. 논리 heap [0x56492c80, 0x57c52c80)의 초기 바이트는 각 실험에서 모두 00 또는 A5이며 실제 물리 메모리의 내용이라고 가정하지 않았습니다.

guest가 아직 쓰지 않은 heap 바이트를 읽을 수 있는 범위는 RMW 메타데이터 56바이트뿐입니다. 기존 48바이트에 이번 할당에서 처음 읽힌 0x56493278의 8바이트 pair가 추가됐습니다. 이번 할당 구간에서 추가 pair를 읽은 원본 RMW 명령은 네 곳이었고 마지막에는 모든 제어 바이트를 원본 코드가 덮었음을 확인했습니다. 페이지 정렬 때문에 매핑된 heap 바깥 여백의 guest 접근도 거부합니다. 모든 제공 상태·진입 인자·중단 PC

exclusive 허용 대상은 allocator lock 0x54c40e60과 원본 .data에서 −1로 시작하는 counter 0x545011a0입니다. 허용한 원본 PC와 RAM 주소를 함께 검사했습니다. 상태를 강제로 성공으로 만들지 않았으며 각 대조군에서 관찰한 STREX 결과 10개는 모두 0이었습니다. DMB·DSB·SEV와 CPSR 마스크 조작 역시 emulator 안의 처리입니다. MPIDR·CP15·SVC·MMIO는 실행하지 않았습니다.

core0 분기는 MPIDR 직전에 멈춘 후 별도로 선택했습니다. 도메인 초기화, 다른 11개 registry 유형의 count·포인터, creator의 lock·context 검사와 실제 task 슬롯 소비는 생략했습니다. 정적 설정 max_domain_id=100과 성공한 도메인 초기화의 레코드 수 101을 구분하며 이번에 그 도메인 초기화를 실행한 것은 아닙니다.

4. 대조군과 기존 증거의 대조

빈 이름 대조군에는 원본 설정 문자열의 NUL 0x533e3353을 사용했습니다. 원본 wrapper는 그 한 바이트만 이름으로 읽고 count·배열 포인터·hash를 읽지 않은 채 0을 반환했습니다. 인자로 넘긴 task 이름 기반 주소는 실제 native task 테이블에서 계산한 값이며 역참조되지 않았습니다. 실제 빈 이름 task descriptor를 발견했다는 뜻은 아닙니다.

공개 테스트는 매 실행마다 독립된 임시 폴더를 만들고 그 안에서만 fixture를 관리합니다. 입력 크기·해시·최적화 모드·출력 별칭·helper와 manifest 변조·필드 타입을 검사합니다. 공개 JSON에서 생략되는 개별 guest 쓰기를 바꿔도 전체 관측 검증이 실패하는지 확인했습니다. 다른 경로로 옮긴 재현 두 번을 포함해 25개 검사를 통과했습니다. 테스트 결과

설정부터 task 테이블 초기화까지의 non-stack guest store 3907개는 각 대조군에 대응하는 승인된 27번 기록과 일치했습니다. 초기 heap의 쓰이지 않은 부분까지 같다는 의미는 아닙니다. 기존 prefix와 대조

5. 전체 기록을 확인한 뒤 요약합니다

공개 CLI는 7,200,103바이트 전체 관측 JSON을 메모리에서 재구성합니다. 모든 guest 쓰기와 제한된 범위의 읽기 기록, 코드 훅까지 포함한 원본 스키마의 해시가 승인된 값과 같을 때만 공개 요약 JSON을 저장합니다. 전체 trace는 파일로 내보내지 않습니다. 소스 manifest에는 주소·크기·해시만 있으며 firmware 바이트나 disassembly는 포함하지 않습니다.

원본 스크립트 해시는 과거 증거의 출처를 나타냅니다. 공개 helper는 그 분석 스크립트의 줄바꿈만 LF로 통일한 파일이므로 별도 해시로 검사합니다. 이 출처 구분 때문에 관측값 검사를 생략하지 않습니다. 출처와 인코딩 규칙

6. 직접 재현하기

Python 3.12에서 Unicorn 2.1.4와 Capstone 5.0.7로 검증했습니다. 의존성 파일과 .gitattributes의 LF 규칙을 유지하십시오. 입력은 사용자가 준비한 정확한 decoded 이미지이며 CLI가 크기 78,683,892바이트와 SHA-256을 검사합니다. 다른 입력은 실행 전에 거부합니다.

python -m pip install -r requirements.txt
python replay.py /path/to/decoded.bin --output result-new.json
python test_replay.py --work-dir /path/to/work --output tests-new.json
python test_replay.py --work-dir /path/to/work --decoded /path/to/decoded.bin --output tests-with-input-new.json

명령은 이 패키지 폴더에서 실행하는 예입니다. 스크립트에 절대 경로를 주면 다른 폴더에서도 실행할 수 있습니다. --work-dir는 존재하는 작업 폴더, 각 --output은 새 파일이어야 합니다. firmware 입력 없이도 기본 패키지·타입·입출력 검사를 할 수 있고 --decoded를 주면 재배치된 원본 재현과 전체 관측 변조 검사까지 수행합니다.

기본 패키지는 원본 firmware와 7MB trace를 배포하지 않습니다. 검증 범위는 task 유형 0의 hash 배열과 이름 조회입니다. 도메인 초기화·다른 11개 유형·creator의 앞선 lock/context 경로를 실제로 이어 실행한 것은 아닙니다. MPIDR는 읽기 전에 멈추며 물리 lock·다중 코어·전체 부팅·카메라 동작은 미검증입니다.
