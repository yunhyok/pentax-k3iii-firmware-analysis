기한 큐에 예약을 끼워 넣는 순서와 세 가지 입력 경로

타이머 처리 함수는 큐의 맨 앞만 보고 멈출지 정합니다. 그래서 예약을 큐의 어디에 넣느냐가 중요합니다. 삽입 함수의 비교 규칙과, 기한을 만들어 그 함수에 넘기는 세 경로를 확인했습니다.

이 문서에서

  1. 배경: 큐의 순서가 예약의 처리 순서를 정합니다
  2. 같은 기한이면 먼저 들어온 예약 뒤에 놓입니다
  3. 기한을 만드는 경로는 셋입니다
  4. 18개 사례와 옮겨 쓸 때 지켜야 할 조건
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 삽입 함수는 큐를 앞에서부터 훑으며 새 기한에서 노드의 기한을 뺀 값을 부호 있는 64비트 수로 봅니다. 0 이상이면 지나가고 음수가 되는 첫 노드 앞에 넣습니다.
  • 기한이 같으면 차이가 0이라 지나갑니다. 그래서 같은 기한의 예약은 먼저 들어온 것이 앞에 남습니다.
  • 기한을 만드는 경로는 셋입니다. 부호 있는 지연, 부호 없는 지연, 절대 기한입니다. 부호 있는 지연에서 −1은 “큐에 넣지 않음”을 뜻하는 특수한 값입니다.
  • 네 함수를 대체 함수 없이 원본 기계어로 18개 사례 실행했습니다.
  • 이 비교는 임의의 64비트 값 전체에 대해 일관된 순서를 보장하지 않습니다. 실제 호출자가 어떤 범위의 값을 넘기는지는 확인하지 못했습니다.

확인 원본 코드 실행으로 확인

  • 삽입 위치 10개 사례와 비교 분기
  • 세 경로의 기한 계산과 −1 특수 경로
  • 목록의 앞뒤 연결, 노드 내용의 보존
  • 보존해야 하는 레지스터와 스택 포인터의 복원

모델 시험 조건으로 정한 것

  • 큐는 연결이 올바른 합성 목록
  • 새 노드는 어디에도 연결되지 않은 상태
  • 현재 카운터와 주기 값은 직접 넣은 수
  • −2와 가장 작은 음수 지연은 직접 넣은 입력

미확인 확인하지 않은 것

  • 실제 호출자가 넘기는 지연과 기한의 범위
  • 이미 큐에 있는 노드를 다시 넣는 경우
  • 연결이 잘못된 목록, 동시에 수정하는 경우
  • 시간 단위

배경: 큐의 순서가 예약의 처리 순서를 정합니다

타이머 처리 함수는 큐의 맨 앞 노드가 아직 미래이면 뒤는 보지 않고 멈춥니다. 큐가 기한 순서로 늘어서 있다는 전제에서만 옳은 동작입니다. 그 순서를 만드는 곳이 이 문서의 삽입 함수입니다.

알람 시작 호출을 검증할 때는 이 삽입 함수를 대체 함수로 두었습니다. 여기서는 삽입 함수와, 기한을 계산해 삽입 함수로 넘어가는 세 함수를 원본 그대로 실행합니다. 알람 시작이 쓰는 것은 셋 가운데 절대 기한 경로입니다.

기한 큐
머리 노드 하나에서 시작해 다시 머리로 돌아오는 원형 양방향 연결 목록.
노드
+0 다음 노드, +4 이전 노드, +8 기한(64비트), +0x10 콜백, +0x14 콜백에 넘길 인수.
부호 확장
32비트 수를 64비트로 넓힐 때 맨 윗자리 비트를 위쪽에 복사하는 것. 음수가 음수로 유지됩니다.

같은 기한이면 먼저 들어온 예약 뒤에 놓입니다

비교식은 signed64((새 기한 − 노드의 기한) mod 264) ≥ 0입니다. 참이면 다음 노드로 가고 거짓이면 그 노드 앞에 넣습니다. 끝까지 가면 머리 앞, 곧 목록의 맨 뒤에 넣습니다.

노드를 끼워 넣는 데는 포인터 기록 네 번이 쓰입니다. 새 노드의 앞뒤 포인터 두 개, 그리고 양쪽 이웃의 포인터 하나씩입니다. 삽입 함수 자신은 새 노드의 기한, 콜백, 인수를 바꾸지 않습니다.

마지막 두 사례가 이 비교의 한계를 보여 줍니다. 기한 0인 노드가 있는 큐에 263을 넣으면, 숫자로는 더 크지만 차이가 음수로 읽혀 앞에 들어갑니다. 두 기한의 거리가 64비트 범위의 절반보다 작을 때만 “더 이른 것이 앞”이라는 뜻이 유지됩니다.

주의

이 비교식은 순환하는 차이의 부호를 쓰므로, 임의의 64비트 값 전체에 대해 일관된 정렬 순서를 보장하지 않습니다. 절반 범위 경계의 사례는 그 비교 한 번의 결과만 확인한 것입니다. 실제 호출자가 넘기는 기한의 범위와 “큐는 늘 정렬되어 있다”는 전제는 따로 검증해야 합니다.

삽입 함수의 구간은 0x525b7e00–0x525b7e64이고 큐 머리는 0x5457ec00입니다. 시험은 분기 순간의 음수 플래그와 넘침 플래그를 읽어 “부호 있는 차이가 0 이상”과 일치하는지 검사했습니다.

기한을 만드는 경로는 셋입니다

두 경로는 지연을 받아 현재 카운터와 주기 값을 더해 기한을 만들고 한 경로는 이미 계산된 기한을 그대로 받습니다. 세 경로 모두 마지막에 같은 삽입 함수로 넘어갑니다.

두 지연 경로는 현재 카운터와 주기 값을 같은 전역 변수에서 읽습니다. 부호 있는 경로는 상위 워드에 지연의 부호를 복사해 더하고 부호 없는 경로의 상위 워드에는 자리올림만 반영됩니다. 그래서 같은 32비트 값이라도 맨 윗자리 비트가 켜져 있으면 두 경로의 결과가 달라집니다.

−1 특수 경로

부호 있는 경로는 먼저 콜백과 인수를 노드에 적습니다. 그다음 지연이 −1이면 노드의 다음·이전 포인터를 자기 주소로 바꾸고 원래 있던 기한은 건드리지 않은 채 돌아갑니다. 큐에는 아무 변화가 없습니다.

이 경로는 이미 큐에 연결된 노드를 안전하게 빼내는 기능이 아닙니다. 시험은 새 노드가 어디에도 연결되지 않은 조건에서만 실행했습니다. −2와 가장 작은 음수도 넣어 부호 확장 계산을 확인했지만 실제 호출자가 그런 값을 허용한다는 뜻은 아닙니다.

절대 기한 경로

절대 기한 경로는 콜백과 인수를 레지스터가 아니라 스택(들어올 때의 SP와 SP+4)에서 읽습니다. 노드에 기한, 콜백, 인수를 적고 삽입 함수로 넘어갑니다. 알람 시작이 계산한 예약 시각이 이 경로로 들어옵니다. 그 계산은 커널 호출과 예약 시각에 있습니다.

참고: 공개 T-Kernel 소스와 견주면

공개 T-Kernel 2.0의 타이머 코드에도 같은 구성의 함수 셋이 있습니다. timer_insert는 부호 있는 대기 시간을 받고 값이 TMO_FEVR(−1, 무한 대기)이면 큐에 넣지 않고 노드의 연결만 초기화합니다. 주석은 그 까닭을 “나중에 삭제 함수가 불려도 괜찮게 하려는 것”이라고 적습니다. timer_insert_reltim은 부호 없는 상대 시간을, timer_insert_abs는 절대 시각을 받습니다. 큐에 넣는 enqueue_tmeb는 새 시각이 노드의 시각보다 작아지는 첫 자리 앞에 넣습니다. 이 펌웨어에서 본 동작과 같은 모양입니다. 다만 같은 소스인지는 확인하지 않았습니다.

따로 잘라 낸 RTOS 파일과 통합 decoded 파일에서 결과가 같았습니다. 사례마다 목록의 양방향 연결이 맞는지, 새 노드의 기한·콜백·인수가 보존되는지, 보존해야 하는 레지스터와 스택 포인터가 돌아오는지, 노드 앞뒤 메모리가 그대로인지 검사했습니다. 이 18개 사례에는 대체 함수가 없습니다.

이 코드를 옮겨 쓸 때 지켜야 할 것

  • 같은 기한의 노드는 들어온 순서를 유지할 것 (차이 0에서 지나감)
  • 부호 있는 지연과 부호 없는 지연을 구분할 것
  • 부호 있는 지연의 −1을 “삽입하지 않음”으로 처리할 것
  • 32비트와 64비트 덧셈의 순환을 그대로 둘 것

동시에, 호출자가 “목록은 올바르고 새 노드는 어디에도 연결되어 있지 않다”는 전제를 어디서 보장하는지도 확인해야 합니다. 삽입 함수 안에서 입력을 검사하는 코드는 확인되지 않았습니다.

새로 보관한 자료는 디컴파일 C 4개와 ARM 명령 69 words입니다. 이 가운데 절대 기한 함수의 8 words는 커널 호출 문서에서 이미 보관한 범위와 겹칩니다. 디컴파일된 C는 부호 있는 함수의 자기 연결 기록을 조건 없이 하는 것처럼 보여 주거나 꼬리 호출을 빠뜨립니다. C는 고치지 않고 ARM 명령을 기준으로 판단했습니다.

한계와 남은 과제

  • 올바른 입력만 넣었습니다. 연결이 잘못된 목록, 이미 큐에 있는 노드의 재삽입, 여러 곳에서 동시에 수정하는 경우의 안전성은 검증하지 않았습니다.
  • 비교는 국소적입니다. 기한들이 64비트 범위의 절반 이상 떨어져 있으면 순서가 직관과 달라집니다. 실제 호출자가 그런 값을 넘기지 않는다는 보장은 찾지 못했습니다.
  • 호출자를 다 잇지 못했습니다. 절대 기한 경로는 알람 시작과 이어져 있지만 두 지연 경로를 부르는 쪽과 그쪽의 입력 검사는 이 문서에서 다루지 않았습니다.
  • 콜백은 실행하지 않았습니다. 이 시험은 노드를 큐에 넣는 데까지입니다. 꺼내서 부르는 쪽은 타이머 등록과 지연 콜백에 있습니다.
  • 실제 운영체제, 인터럽트, 하드웨어 동작과 시간 단위는 확인하지 않았습니다. 펌웨어 빌드·기록도 하지 않았습니다.

재현 방법

입력은 따로 잘라 낸 RTOS 파일이나 통합 decoded 파일입니다. SHA-256과 적재 주소는 UI 타이머 문서의 재현 방법과 같습니다. Python 패키지 unicorn이 필요합니다.

python verify_update_timer_insertion.py rtos.bin --output timer-insertion.json

원본 C, ARM 목록, 바이너리는 공개하지 않습니다.
