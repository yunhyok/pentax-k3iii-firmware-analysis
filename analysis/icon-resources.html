UI와 화면 자원 · 아이콘 자원

ICONBIN 아이콘의 저장 형식과 화면으로 복사되는 경로

K-3 Mark III의 메뉴 아이콘은 펌웨어 패키지의 ICONBIN 레코드에 들어 있습니다. 화면을 고치거나 다른 기종으로 옮기려면, 아이콘 하나가 어디에 어떤 모양으로 저장되고 어떤 함수가 화면용 버퍼에 옮기는지부터 알아야 합니다.

이 문서에서

  1. 배경: 아이콘이 화면에 나오려면 필요한 것
  2. 아이콘 목록은 RTOS에, 픽셀은 ICONBIN에 있습니다
  3. GUI가 아이콘 번호에서 픽셀 복사까지 가는 길
  4. 아이콘 하나를 바꿨다가 되돌리는 시험
  5. 검사 61건의 구성
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • ICONBIN은 패키지에서 가장 큰 레코드(26,219,192바이트)입니다. 아이콘 1,665개의 32비트 픽셀이 빈틈없이 이어져 있습니다. 어느 구간이 어느 아이콘인지 알려 주는 목록은 ICONBIN이 아니라 RTOS 레코드 안에 있습니다.
  • 화면 요소(IconView)가 아이콘 번호를 받으면 그리기 단계에서 목록을 찾아 픽셀을 복사합니다. 회전이 없을 때 쓰는 복사 함수는 32비트 값을 그대로 옮기고 상위 바이트가 정해진 키 값과 같은 픽셀만 건너뜁니다.
  • 아이콘 하나(ID 5)에 작은 + 표식을 그린 후보를 PC에서 만들었습니다. 원래 픽셀을 다시 넣으면 ICONBIN 전체의 해시가 원본과 같아졌습니다. 후보를 넣고 다시 포장한 패키지는 구조 검사와 체크섬 검사를 통과했습니다.
  • 후보 패키지를 카메라에 넣어 보지는 않았습니다. 색 채널의 순서, 화면 합성, LCD 표시, 어느 메뉴가 ID 5를 쓰는지는 확인하지 않았습니다.

확인 바이트 대조·원본 코드 실행

  • 포인터 배열 1,666칸과 descriptor, 픽셀 구간이 빈틈·겹침 없이 맞물림
  • 회전 없는 복사 함수 25건(대체 함수 없이 실행)
  • IconView의 번호 저장 5건, 그리기용 사본 3건
  • 후보 패키지의 헤더·체크섬 함수 8건

정적 분석 코드를 읽어 판단

  • IconView 그리기에서 아이콘 그리기 분배 함수로 이어지는 호출
  • descriptor 각 필드를 읽는 명령의 위치

모델 시험 조건으로 정한 것

  • 합성 픽셀과 합성 목적지 버퍼, 좌표와 pitch
  • 다시 그리기 요청은 호출 횟수만 셈
  • CPU는 Unicorn의 Cortex-A15 모델

미확인 확인하지 않은 것

  • 어느 메뉴 동작이 ID 5를 고르는지
  • 색 채널 순서, 감마, 알파 합성, LCD 표시
  • 하드웨어 디코더와 업데이트 수용, 카메라 동작
  • descriptor의 +1·+6 필드의 뜻

배경: 아이콘이 화면에 나오려면 필요한 것

펌웨어 패키지를 풀면 이름이 붙은 레코드 15개가 나옵니다(펌웨어 구조와 하드웨어). 그중 ICONBIN은 UI 아이콘의 픽셀 데이터이고 패키지 안에서는 종류 4·번호 4인 레코드입니다. 풀린 데이터 78,683,892바이트 가운데 약 3분의 1을 차지합니다.

아이콘 하나를 화면에 그리려면 세 가지가 맞물려야 합니다. 이 문서는 세 가지를 차례로 확인합니다.

  1. 저장 형식: 번호로 아이콘의 크기와 위치를 찾는 목록, 그리고 픽셀 자체.
  2. GUI 호출 경로: 화면 요소가 받은 번호가 픽셀 복사 함수까지 이어지는 길.
  3. 복사 규칙: 픽셀을 어떤 단위로, 어떤 조건에서 옮기는지.

읽기 전에 알아 둘 말

32비트 픽셀
픽셀 하나를 4바이트 값 하나로 저장하는 방식입니다. 이 문서에서는 4바이트 중 맨 위 1바이트를 ‘상위 바이트’, 나머지를 ‘하위 3바이트’라고 부릅니다.
stride(pitch)
메모리에서 한 줄의 시작부터 다음 줄의 시작까지의 거리입니다. 그림의 폭과 같을 수도 있고 더 클 수도 있습니다. 펌웨어의 복사 함수는 원본 줄 간격으로 ‘4 × 아이콘 폭’을, 목적지 줄 간격으로 ‘4 × pitch’를 씁니다. 일반적인 설명은 Microsoft Learn의 Image Stride에 있습니다.
알파
픽셀의 투명한 정도를 나타내는 값을 가리키는 일반 용어입니다(PNG 규격의 설명). ICONBIN의 상위 바이트가 이런 뜻으로 쓰이는지는 확인하지 못했습니다. 확인한 복사 함수는 값을 섞지 않고 ‘키와 같으면 건너뛰기’만 합니다.
descriptor
아이콘 하나의 사용 여부, 폭, 높이, 픽셀 위치를 적은 12바이트 기록입니다.
IconView
아이콘 하나를 보여 주는 GUI 객체입니다. 메뉴의 행마다 하나씩 들어 있습니다(색공간 화면의 예).

아이콘 목록은 RTOS에, 픽셀은 ICONBIN에 있습니다

아이콘 번호로 포인터 배열의 한 칸을 고르면 12바이트 descriptor가 나오고 그 안의 offset이 ICONBIN 속 픽셀의 시작 위치를 알려 줍니다. 활성 아이콘 1,665개의 픽셀 구간은 ICONBIN 26,219,192바이트를 빈틈이나 겹침 없이 정확히 나눕니다.

주의

ICONBIN 안에는 descriptor가 없습니다. 그래서 아이콘의 크기를 바꾸려면 ICONBIN, RTOS에 있는 descriptor, 그 뒤에 오는 모든 아이콘의 offset을 함께 검토해야 합니다. 이 문서의 후보는 크기와 descriptor를 그대로 두고 픽셀 값만 바꿨습니다.

GUI가 아이콘 번호에서 픽셀 복사까지 가는 길

IconView는 받은 번호를 저장해 두었다가, 그릴 때 사본을 만들고 아이콘 그리기 함수를 부릅니다. 회전이 없으면 복사 함수 하나가 32비트 값을 그대로 목적지 버퍼에 씁니다.

  • 번호 저장: IconView의 +0x17c에 16비트 번호를 씁니다. 값이 이전과 다를 때만 다시 그리기 요청 함수(0x52c0205c)를 부릅니다.
  • 그리기용 사본: 번호와 위치 사각형을 그리기용 필드로 복사합니다.
  • 그리기 호출: IconView 안에 든 그리기 객체가 가상 함수 표로 그리기 함수에 연결되고 설정 객체의 +0x24가 전달됩니다. 여기까지는 명령을 읽어 확인했습니다.

실제 메뉴 동작이 ID 5를 고르는 지점은 찾지 못했습니다. 아이콘의 모양만 보고 메뉴 이름을 붙이지도 않았습니다.

복사 함수가 하는 일

copyWidth  = min(requestedWidth, descriptor.width)
copyHeight = min(requestedHeight, descriptor.height)
srcStart   = source + 4 * (offsetY * descriptor.width + offsetX)
dstStart   = destination + 4 * ((y + offsetY) * pitch + x + offsetX)
copy u32 pixel only when (pixel >> 24) != drawObject.byte7
  • 픽셀을 32비트 값으로 읽고 같은 값을 그대로 씁니다. 원본의 줄 간격은 4 × width, 목적지의 줄 간격은 4 × pitch입니다.
  • 픽셀의 상위 바이트가 그리기 객체의 바이트 +7(키)과 같으면 그 픽셀은 쓰지 않습니다.
  • 이 함수에는 팔레트 조회, 압축 해제, 알파 값에 따른 혼합이 없습니다.

실제 ID 5의 픽셀 1,600개를 키 0으로 복사한 시험에서 목적지에 쓴 픽셀은 1,444개였습니다. 나머지 156개는 상위 바이트가 0이어서 건너뛴 것입니다.

주의

다른 GUI 경로나 이 뒤의 디스플레이 처리까지 같은 방식이라고 단정하지 않습니다. 또 원본 함수는 offset을 더한 뒤 폭을 다시 줄이지 않습니다. 직접 만든 계산 모델은 원본과 목적지 사각형이 모두 범위 안에 있을 때만 받아들이는데 이것은 도구의 정책입니다. 펌웨어가 같은 검사를 한다는 뜻이 아닙니다.

아이콘 하나를 바꿨다가 되돌리는 시험

ID 5의 오른쪽 아래에 7 × 7 크기의 + 표식을 그려 픽셀 44개를 바꿨습니다. 크기, descriptor, 다른 아이콘은 건드리지 않았고 원래 픽셀을 다시 넣으면 ICONBIN 전체가 원본과 같아졌습니다.

미리보기의 제한

도구가 만드는 미리보기는 하위 3바이트가 서로 같고 상위 바이트가 0 또는 255인 아이콘만 보여 줍니다. 세 바이트가 같으면 어느 바이트가 빨강·초록·파랑인지 몰라도 같은 회색으로 보이기 때문입니다. 그 대신 LCD에서의 색의 뜻, 감마, 알파 합성은 재현하지 않습니다. 추출 도구는 이미 있는 출력 폴더를 거부하고 원본 입력은 읽기만 합니다. 원본 픽셀과 미리보기는 공개하지 않고 로컬에 보관합니다.

후보 패키지는 모든 블록을 압축하지 않은 블록(stored block)으로 다시 담아서 원본보다 훨씬 큽니다. 원본 ARM 검사 8건은 두 패키지 각각에 대해 헤더와 바깥 체크섬 통과 1건, 헤더 필드를 고쳤을 때의 거부 2건, 안쪽 체크섬 통과 1건입니다. 패키지를 바꾸지 않고 다시 포장하면 원래의 압축 데이터를 재사용하므로 원본과 바이트 단위로 같습니다. 제조사의 압축기를 복원했다는 뜻은 아닙니다.

주의

파일 로더의 메모리 할당 한계, 하드웨어 디코더, 업데이트 프로그램 전체, 카메라 동작은 검증하지 않았습니다. 이 후보는 PC에서 만든 자료이며 카메라에 설치할 수 있다고 확인된 펌웨어가 아닙니다. 재포장 방식은 압축 블록을 보존한 재패키징에서 더 다룹니다.

디컴파일 결과와 원본 명령의 차이

디컴파일 결과 6개와 보조 구간 8개를 로컬에 보관했습니다. 원본 ARM word 573개, 분기 96개, 데이터 구간 16개, 포인터 word 1,728개를 대조했습니다. angr가 만든 C에는 원본과 다른 곳이 두 군데 있었습니다. 분석과 계산 모델은 원본 명령과 실행 결과를 따랐고 C는 고치지 않고 보관했습니다.

  • 복사 함수의 C는 조건부 저장 STRNE를 무조건 저장으로 표현합니다. 그대로 믿으면 건너뛰기 규칙이 사라집니다.
  • 번호 저장 함수의 C는 다시 그리기 요청으로 가는 꼬리 호출을 빠뜨립니다.
입력 검사 28건의 목록
  • 받아들임: 2 × 2 합성 descriptor
  • 포인터: 이미지 앞쪽을 가리킴, 이미지 뒤쪽을 가리킴, 4바이트 정렬이 아님, descriptor가 중간에 잘림
  • descriptor 값: 지원하지 않는 사용 여부 값, 예약 바이트가 0이 아님, 폭 0, 높이 0, 예약 16비트가 0이 아님, offset 넘침, 폭이 범위를 넘김, 높이가 범위를 넘김, 비활성인데 크기가 있음
  • 표와 길이: 표가 잘림, ICONBIN 길이가 4의 배수가 아님, 칸 수 0, 칸 수 초과
  • 추출·교체: 픽셀 구간이 잘림, 교체할 픽셀의 크기가 다름
  • 구간 검사: 구간 겹침, 끝에 남는 빈틈
  • 미리보기·표식: 색이 있는 아이콘 거부, 중간값 상위 바이트 거부, 표식이 투명 경계를 넘음
  • 복사 모델: 원본 범위를 벗어난 잘라 내기, 목적지 넘침
  • 입력 파일: SHA-256이 다른 파일

한계와 남은 과제

  • 어느 화면의 아이콘인지: ID 5를 고르는 메뉴 동작을 찾지 못했습니다.
  • 색의 뜻: 하위 3바이트의 채널 순서, 감마, 화면 합성에서의 알파 처리를 모릅니다. 미리보기는 회색 아이콘에만 통합니다.
  • 다른 그리기 경로: 회전이 없는 복사 함수 하나만 실행했습니다. 분배 함수의 나머지 분기와 그 뒤의 디스플레이 처리는 보지 않았습니다.
  • 실행 환경: GUI의 이벤트 처리, 디스플레이 장치, 카메라 플래시 기록은 실행하지 않았습니다. Cortex-A15 모델로 에뮬레이션해도 카메라 하드웨어와 똑같다는 보장은 없습니다.
  • 패키지: 후보 패키지를 하드웨어 디코더와 업데이트 프로그램이 받아들이는지 모릅니다.

K-3 II·Q7로 옮기려면 남는 조건

이 문서의 결과는 K-3 Mark III의 아이콘 자원을 고칠 때 쓸 근거입니다. 다른 기종으로 옮기려면 descriptor, 픽셀 표현, GUI 객체 구조, 이벤트 번호, 화면 출력을 대상 펌웨어에서 각각 따로 연결해야 합니다. 리코의 K-3 Mark III·K-3 II 메뉴 대응표는 메뉴의 뜻과 배치를 비교하는 데 쓸 수 있지만 바이너리가 호환된다는 근거는 아닙니다. 세 기종의 같은 화면을 어떻게 맞출지는 UI 이식 설계에 정리했습니다.
