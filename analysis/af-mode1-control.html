Joint 모드 1의 리셋, 요청 분기, 피드백 계산

Joint 모드 1에서 PafMotor는 요청 번호와 렌즈 상태를 보고 서비스에 넘길 값을 만듭니다. 리셋 뒤 호출, 요청 번호별 분기, 피드백 숫자 계산을 각각 원본 코드로 실행해 확인했습니다.

  4. 요청 번호마다 첫 값과 극성이 정해집니다

핵심 요약

  • 리셋은 채널 0의 ReloadTimer 메서드 세 개를 차례로 부릅니다. 세 메서드 모두 첫 레지스터 읽기 직전까지 인자를 확인했습니다. 채널 1 쪽 리셋은 서비스 칸이 비어 있어도 그냥 돌아왔습니다.
  • 요청 번호 0~9는 분기표로 갈립니다. 번호마다 PafPulse의 어느 값을 첫 값으로 쓰는지, 방향 표시(극성)를 어떻게 정하는지를 19건으로 확인했습니다.
  • 요청 3은 피드백 값을 누적한 뒤 표에서 값을 골라 PafMotor에 씁니다. 하드웨어 읽기는 실행하지 않았습니다. 읽기 결과 자리에 시험 수치를 넣어 그 뒤의 계산만 실행했습니다.
  • 세 구간은 서로 이어지지 않은 별도 실행입니다. 객체 상태와 요청·피드백 수치는 합성 입력입니다. 장치 피드백과 물리 단위는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 리셋 뒤 ReloadTimer 메서드 세 개의 인자 (5건)
  • 요청 0~9와 범위 밖 번호의 분기, 극성 계산 (19건)
  • 채널 1 수치 인터페이스의 부호 처리 (4건)
  • 요청 3의 누적·버킷 조회 14건, 로컬 호출 조건 9건

정적 분석 코드를 읽어 판단

  • 첫 ReloadTimer 메서드의 읽기 이후 두 분기
  • +0x68 비영 분기의 두 저장 위치

모델 시험 조건으로 정한 것

  • 렌즈·PafPulse 상태, 요청 값, 피드백 수치 f
  • 일부 factory 포인터, 할당 주소, Udc 카운터
  • 리셋·보조 호출·장치 읽기의 반환은 합성하지 않고 건너뜀

미확인 확인하지 않은 것

  • 실제 장치 피드백과 레지스터 응답
  • 모터의 물리적 구분, 시간·거리·각도 단위
  • Pulse +0xa88과 PafMotor 보정 필드의 생산자

배경: 모드 1에서 PafMotor가 하는 일

Joint 하위 제어 문서에서 client 1이 Joint 모드 1을 고르는 것을, AF 서비스 객체 문서에서 그 서비스의 채널 0·1이 ReloadTimer와 Udc에 연결되는 것을 확인했습니다. 이 문서는 그 사이에서 PafMotor가 무엇을 계산하는지 봅니다.

모드 1의 하위 객체가 PafMotor입니다. PafMotor는 PafPulse와 짝을 이룹니다. Joint가 넘긴 요청 번호(Joint+0x74), 방향 후보(Joint+0x5c), 표본 값(Joint+0x68)을 받아 서비스에 넘길 값을 만듭니다.

쉽게 말하면

요청 번호는 메뉴 번호처럼 처리 방식을 고릅니다. 번호에 따라 기준 값을 고르고 방향 표시를 붙여 서비스로 넘깁니다. 요청 3은 피드백 값을 받아 누적하고 그 크기에 맞는 값을 표에서 찾아 둡니다. 숫자가 실제로 무엇을 뜻하는지는 아직 모릅니다.

세 구간을 따로 실행했습니다

각 구간은 앞 단계의 반환값을 합성하지 않고 다음 진입점에서 새로 시작했습니다. 그래서 구간 사이의 연결은 실행으로 확인한 것이 아닙니다.

원본 명령은 해시를 확인한 RTOS에서 읽었습니다. 각 진입에 필요한 메모리와 레지스터는 검증 스크립트가 준비했습니다. 레지스터 페이지는 매핑하지 않았고 앞 단계의 리셋·보조 호출·장치 읽기의 반환값도 합성하지 않았습니다.

리셋은 ReloadTimer 메서드 세 개를 부릅니다

채널 0 리셋은 PafMotor +8의 서비스를 거쳐 D1의 ROM vtable 슬롯 세 개를 부릅니다. 세 메서드 모두 같은 레지스터 블록을 읽기 직전까지 실행했습니다.

0x52f0bb0c에서 서비스를 채널 인수 0으로 호출하면 0x531784c8이 기본 키 0xd1의 ReloadTimer를 씁니다. 두 번째와 세 번째 행은 원본 호출 프레임을 준비한 뒤 각각 따로 진입한 대조입니다.

리셋 뒤 ReloadTimer 메서드
vtable 슬롯 → 원본 대상확인한 인자정지 지점
+0x7c → 0x5326d6b0r1=0xffff, r2=10x5326d6c8, 0x1e000020의 첫 32비트 읽기 직전
+0x54 → 0x5326d740원본 descriptor로 객체 +0x30을 0으로 쓰고, 제어값 0xc80과 reload 후보 0xffff, 0을 준비0x5326d8b4, 같은 읽기 직전
+0x58 → 0x5326d570r1=0x1e000020, ip=0x1e000028, r2=00x5326d57c, 첫 읽기 직전

첫 호출 앞에서 확인한 descriptor 19바이트는 01000000 000001?? ffff0000 00000000 000003입니다. +7(??)은 스택을 A5와 5A로 채운 두 대조에서 각각 채운 값을 그대로 유지했습니다. D1이 없으면 0x5317850c의 빈 포인터 역참조 직전에 멈췄습니다.

채널 인수 1로 0x52f0bb18에서 따로 호출한 대조는 두 서비스 칸이 비어 있어도 스택 가드 확인 뒤 돌아왔습니다. 바깥 코드가 PafMotor +0x20/+0x21/+0x32를 0으로 썼습니다. 이 인수 1은 AF 서비스 객체 문서의 Udc 리셋에 쓰인 객체의 채널 바이트와 별개입니다.

첫 ReloadTimer 메서드의 읽기 이후 (정적 분석)

원본 0x5326d6c8에서 읽을 레지스터의 bit 12가 켜진 분기는 이 인자에서 0x1e00002c에 값을 씁니다. bit 12가 꺼진 분기는 쓰기를 건너뛰고 거짓 조건을 assertion 서비스로 넘깁니다. 이 서비스가 반환하는 경우에만 이어지는 원본 코드가 0을 반환합니다. 호출자는 그 반환값을 검사하지 않고 다음 메서드로 넘어갑니다.

근거: 5개 대조와 원본 범위 · 리셋 뒤 메서드 재현기

요청 번호마다 첫 값과 극성이 정해집니다

요청 번호 0~9는 분기표로 갈려 PafPulse의 서로 다른 값을 첫 값으로 씁니다. 방향 표시는 렌즈 바이트와 입력 word 두 가지로 정해집니다.

원본 0x52ef877c가 client 1에서 Joint 모드 1을 고른 뒤 0x52f08474가 Joint+0x74의 32비트 요청값을 읽습니다. 0x52f0d8b0은 이 값을 부호 없이 비교해 0~9의 점프 테이블을 씁니다. Joint+0x5c의 32비트 값은 극성 계산 후보가 되고 Joint+0x68의 halfword는 Pulse +0x2e에 기록됩니다.

1, 2(Pulse[+0x2e] + Pulse[+0xec]) mod 65536. 요청 1에서 Pulse +0x15가 0이 아니면 합산 전에 별도 함수로 들어갑니다.

요청 3은 피드백을 누적해 표에서 값을 고릅니다

요청 3은 피드백 수치를 PafMotor +0x52에 누적합니다. 그 값으로 ROM 표의 버킷을 골라 +0x5a/+0x5c에 씁니다.

요청 3의 D1 메서드는 0x5326d5e8에서 0x1e000024를 32비트로 읽습니다. 실행은 이 읽기 직전에 멈췄습니다. 다음 단계는 0x52f0c7d8에서 수치 f를 r0에 넣어 시작했습니다. 원본 호출자 0x53178344가 읽기 결과의 하위 16비트를 취하므로 입력 폭도 16비트로 맞췄습니다.

A = u16(Paf[+0x52] + Paf[+0x58] − s16(f))
Paf[+0x52] = A
x = u16((A의 bit 15가 켜져 있으면 0, 아니면 A) + p)
버킷 = (x == 0) ? 0 : floor((x − 1) / 100)      ※ Paf+0x43 = 0, Paf+0x68 = 0일 때

0x52f0c7dc의 SXTH가 f를 부호 확장합니다. bit 15가 켜져도 메모리의 A는 그대로 남고 조회에 쓰는 임시값만 0이 됩니다. ROM 0x538f25e0부터의 표는 버킷 28까지 씁니다. +0x43이 0이 아니면 조회를 건너뛰고 2*p의 하위 16비트를 채널 1로 먼저 넘깁니다.

입력 2,900과 2,901은 표에서 같은 값 300을 읽었고 +0x56의 4를 더해 304가 됐습니다. 주소 기록을 보면 2,900은 버킷 28을 읽었고 2,901은 범위를 벗어나 기본값 읽기로 갔습니다. 두 읽기가 같은 ROM 위치를 가리킵니다.

정정

이전 요청 분기 기록은 “범위 밖의 몫이나 Paf+0x68이 0이 아닌 분기는 기본값으로 간다”고 적었습니다. 당시 실행한 요청 대조는 +0x68=0이었습니다. 원본 명령을 다시 확인한 결과는 아래와 같습니다.

  • 요청 9가 214 초과 경로로 들어가거나 요청 0xff를 처리할 때, 0x52f0c8cc가 읽은 비영 +0x68은 그대로 +0x5a에 저장됩니다. +0x5c는 ROM 기본값입니다. 원본 0x52f0c918부터 따라가면 0x52f0c8c0과 0x52f0c8c4의 두 저장이 보입니다.
  • 요청 3의 조회 경로는 +0x5a = u16(선택값 + Paf[+0x56])입니다. +0x68이 0이 아니면 그 값이 선택값이고 +0x5c는 ROM 기본값을 받습니다. 0x52f0c99c 경로 대조에서 +0x68=1, +0x56=4일 때 결과는 5와 300이었습니다.

로컬 호출자가 요청 3을 부르는 조건

별도 0x52f0c9f0 진입에서 아래 두 식을 확인했습니다. 결과는 Pulse +0xf8에 저장됩니다.

difference = u16(Pulse[+0xa88] − f)
remainder  = s16(Pulse[+0x2e] − difference)

이 분기는 Paf+0x1a=0, Paf+0x43이 0 또는 4, remainder>0일 때 0x52f0ca44에서 요청 3을 부릅니다. 9건 가운데 잔여값 1·32,767과 기준값 wrap 사례, 상태 4 사례가 요청 3으로 갔습니다. 잔여값 0·−1·−32,768, +0x1a=1, 상태 1은 요청 3을 부르지 않았습니다. 다른 호출 지점도 있으므로 이 조건은 이 로컬 분기에만 해당합니다.

근거: 14개 누적·조회와 9개 로컬 호출 대조 · 피드백 수치 재현기

한계와 남은 과제

  • 구간 사이의 연결 세 구간은 각각 따로 진입했습니다. 리셋이 실제로 돌아온 뒤 분기표로 이어지는 실행은 하지 않았습니다.
  • 장치 피드백 f는 레지스터 읽기 결과 자리에 넣은 시험 수치입니다. 실제 장치가 어떤 값을 돌려주는지는 모릅니다.
  • 남은 생산자 Pulse +0xa88의 비영 기준값과 PafMotor 보정 필드(+0x56, +0x68)를 누가 쓰는지는 기준값 쓰기 경로 문서와 PafMotor 필드 문서에서 이어서 추적합니다.
  • 물리 의미 부팅 중 객체 수명, 모터의 물리적 구분, 시간·거리·각도 단위는 확인하지 않았습니다. 카메라에서 실행한 결과가 아닙니다.

재현 방법

세 스크립트가 같은 RTOS 또는 decoded 파일을 받아 각 구간을 실행합니다.

  • Unicorn 2.1.4에서 Cortex-A7 기본 실행과, 호출자 저장 레지스터·NZCV를 바꾼 Cortex-A7·A15 대조가 일치했습니다.
  • RTOS와 decoded 입력이 스크립트마다 바이트 단위로 같은 JSON을 만들었습니다. 실행 뒤 원본 매핑 전체의 SHA-256도 다시 확인했습니다.
  • 원본 생성자와 레지스트리·바인더를 썼습니다. 일부 factory 포인터와 할당 주소, Udc 카운터, 렌즈·Pulse 상태, 요청·피드백 수치는 스크립트가 넣었습니다.
