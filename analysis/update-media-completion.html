업데이트 파일의 저장 매체 객체와 완료 통지

업데이트 파일 경로의 드라이브 문자 C와 R이 펌웨어 안에서 어떤 저장 장치 객체로 이어지는지 확인했습니다. 업데이트 작업이 끝났다는 통지가 화면 쪽으로 넘어가는 길도 함께 따라갔습니다.

이 문서에서

  1. 배경: 파일 경로에서 저장 장치 객체까지
  2. C는 SdDriver, R은 Emmc 객체에 연결됩니다
  3. SD 객체의 크기 필드는 CSD에서 계산한 sector 수입니다
  4. R 볼륨의 시작·크기 값은 별도 객체 EmmcPartition에서 옵니다
  5. 완료 통지는 모델 상태를 바꾸고 UI 작업을 등록합니다
  6. 검증 범위와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 업데이트 파일 경로의 C는 SdDriver, R은 Emmc 클래스의 객체로 이어집니다. 객체를 만드는 코드와 클래스 이름 문자열로 확인했습니다. 펌웨어 속 클래스 이름일 뿐이며 카드가 꽂혀 있는지나 초기화에 성공했는지를 뜻하지는 않습니다.
  • SD 쪽 객체에 저장되는 크기 값은 카드의 CSD 레지스터에서 계산한 512바이트 sector 수입니다. 합성 CSD 45개로 원본 계산 코드를 실행했고 계산식은 SD 규격의 용량식과 같은 꼴입니다.
  • R 볼륨의 두 숫자는 Emmc 객체가 아니라 별도 객체 EmmcPartition에 든 상수에서 옵니다.
  • 완료 통지는 메시지 하나로 나갑니다. 받는 쪽 코드는 FwUpdateModel의 상태 값을 3으로 바꾸고 UI 작업 큐에 작업 하나를 넣습니다. 보내는 쪽과 받는 쪽을 따로 실행했고 둘 사이의 실제 전달은 확인하지 못했습니다.
  • 상태 값 3을 저장소 기록 성공이나 인증 통과로 읽을 근거는 없습니다.

확인 원본 코드 실행으로 확인

  • 매체 객체·CSD 계산·volume record 57사례
  • 완료 통지의 송신·수신·작업 큐 15사례
  • RTOS 단독 입력과 통합 이미지 입력에서 같은 결과

정적 분석 코드를 읽어 판단

  • 객체를 만들어 provider에 넣는 생성 함수 두 개
  • Emmc 초기화·활성화 함수에 크기 필드 쓰기가 없음
  • FwUpdateModel 생성자와 클래스 이름

모델 시험 조건으로 정한 것

  • CSD 16바이트와 카드 읽기 성공 여부는 합성 값
  • 8칸짜리 작업 큐, 초기화가 끝난 singleton 상태
  • 전송·OS 이벤트·lock·assertion은 대체 함수
  • CPU는 Unicorn의 Cortex-A15 모델

미확인 확인하지 않은 것

  • 송신에서 수신까지의 실제 전달과 스케줄링
  • Emmc 크기 필드를 0이 아닌 값으로 바꾸는 코드
  • 실제 카드 용량, mount 성공, 초기화 시점
  • assertion 본체와 큐가 가득 찼을 때의 실제 처리

배경: 파일 경로에서 저장 장치 객체까지

업데이트 프로그램은 파일 이름을 C:\FWDC%ldB.BIN과 R:\FWDC%ldB.BIN 두 형식으로 만듭니다. 경로의 첫 문자로 볼륨을 찾고 볼륨은 저장 장치를 다루는 객체 하나를 가리킵니다. 여기까지는 파일 경로·volume·종료 처리에서 확인했습니다. 이 문서는 그 객체의 정체와, 객체 안의 크기 값이 어디에서 오는지를 다룹니다.

문서 뒷부분은 업데이트 실행이 끝난 뒤의 일입니다. 종료 함수는 실행 결과가 0이 아닐 때 완료 통지 함수를 부릅니다. 이 통지가 화면을 담당하는 UI 쪽에 어떤 모습으로 도착하는지 따라갑니다.

이 문서에서 쓰는 용어

vtable·RTTIC++ 컴파일러가 남기는 가상 함수 표와 클래스 이름 정보입니다. 이름은 8SdDriver처럼 글자 수와 이름을 이어 붙인 문자열로 남습니다(Itanium C++ ABI).

C는 SdDriver, R은 Emmc 객체에 연결됩니다

드라이브 문자와 클래스의 연결은 객체를 만들어 provider에 넣는 코드에서 직접 확인했습니다.

앞 문서는 C가 provider 번호 0, R이 번호 2에 연결된다는 데까지 확인했습니다. 이번에는 그 번호 자리에 포인터를 써 넣는 생성 함수를 따라갔습니다. 번호 0에는 SdDriver 객체가, 번호 2에는 Emmc 객체가 들어갑니다. 클래스 이름은 생성자가 설치하는 vtable과 거기에 연결된 RTTI 이름 문자열에서 읽었습니다.

두 경로의 매체 객체
경로provider 번호클래스종류 값 (+0x14)크기 필드 (+0x18) 초깃값
C0SdDriver00
R2Emmc30

확인 두 생성자를 실행해 종류 값, 크기 필드, vptr를 관측했습니다. 정적 분석 provider 번호 자리에 포인터를 저장하는 코드는 읽어서 판단했습니다.

두 클래스는 같은 부모 생성자를 부릅니다. 부모 생성자는 넘겨받은 값의 하위 1바이트를 +0x14에 쓰고 +0x18을 0으로 만듭니다. SdDriver는 0을, Emmc는 3을 넘깁니다. 그래서 +0x18에 0이 아닌 값이 들어가려면 생성자와 다른 코드가 나중에 써야 합니다.

  • SD 쪽: 그 코드를 찾았습니다. 다음 절에서 설명합니다.
  • Emmc 쪽: 찾지 못했습니다. Emmc의 초기화 함수와 활성화 함수 두 개에는 +0x18에 직접 쓰는 명령이 없었습니다. 살펴본 두 함수에 없다는 뜻이며 펌웨어 전체에서 이 값이 바뀌지 않는다는 결론은 아닙니다.

R만 번호 2를 쓰는 것은 아닙니다. 앞 문서의 등록 표에 따르면 문자 A, B, E, F, G, H, R 일곱 개가 모두 provider 번호 2에 연결됩니다.

이름이 뜻하지 않는 것

SdDriver와 Emmc는 펌웨어 코드에 남은 클래스 이름입니다. 객체를 만드는 생성 함수는 코드만 읽었고 실행하지 않았습니다. 그래서 카메라에 카드가 꽂혀 있는지, 객체 생성과 초기화가 성공하는지, 볼륨이 mount되는지는 이 결과로 알 수 없습니다.

SD 객체의 크기 필드는 CSD에서 계산한 sector 수입니다

SD 활성화 함수는 조건이 맞을 때만 CSD 16바이트를 가져와 sector 수를 계산하고 그 값을 객체의 +0x18에 넣습니다.

  1. 조건 검사gate 통과, 아직 준비 전, 카드 있음, 읽기 성공(최대 3회 시도)
  2. CSD 복사전역 버퍼의 16바이트를 객체 +0x28로 복사
  3. sector 수 계산CSD 형식에 따라 두 가지 식 중 하나
  4. 저장결과를 +0x18에 쓰고 준비 표시 +0x79를 1로

조건을 하나씩 바꿔 가며 활성화 함수를 실행했습니다. 조건이 맞지 않은 네 경우에는 미리 넣어 둔 +0x18 값이 그대로 남았습니다.

카드에서 CSD를 읽어 오는 동작은 실행하지 않았습니다. 읽기 함수는 성공·실패만 돌려주는 대체 함수이고 CSD 바이트는 미리 전역 버퍼에 넣어 둔 합성 값입니다.

이 값을 512바이트 sector 수로 읽는 근거

  • 같은 전역 버퍼를 출력하는 진단 코드가 이 16바이트를 CSD Register라고 부르고 CSD_STRUCTURE 항목을 표시합니다.
  • 성공했을 때 남기는 로그가 계산값을 total sectors라고 부릅니다.
  • 두 매체 클래스 모두 vtable+0x4c의 getter가 512를 돌려줍니다.
  • 계산식이 512로 나눈 꼴이고 SD 규격의 용량식과 맞습니다(아래).

이 근거는 값의 단위를 정해 줄 뿐입니다. 실제 카드의 용량을 잰 결과가 아닙니다.

CSD 필드와 계산식

펌웨어는 16바이트의 첫 바이트를 최상위로 보고 필드를 꺼냅니다. 꺼내는 위치는 SD 규격의 CSD 비트 배치와 같습니다.

펌웨어가 읽는 CSD 필드 (b는 16바이트 배열)
규격의 필드 이름규격의 비트 위치펌웨어가 꺼내는 식아래 식의 기호
CSD_STRUCTURE127–126b[0] >> 6s
READ_BL_LEN83–80b[5] & 15r
C_SIZE (CSD 1.0, 12비트)73–62((b[6] & 3) << 10) | (b[7] << 2) | (b[8] >> 6)C
C_SIZE_MULT (CSD 1.0)49–47((b[9] & 3) << 1) | (b[10] >> 7)m
C_SIZE (CSD 2.0, 22비트)69–48((b[7] & 63) << 16) | (b[8] << 8) | b[9]C

크기 필드 C는 함수 0x532824fc가 꺼내고 sector 수는 함수 0x53282554가 계산합니다. 아래 식의 u32는 결과를 32비트로 자릅니다.

s=1:
C = ((b[7] & 63) << 16) | (b[8] << 8) | b[9]
count = u32((C + 1) << 10)

s=0:
C = ((b[6] & 3) << 10) | (b[7] << 2) | (b[8] >> 6)
r = b[5] & 15
m = ((b[9] & 3) << 1) | (b[10] >> 7)
count = u32((C + 1) * (LSL32(2, u32(r-1)) >> 9) * LSL32(2, m+1))

s=2 또는 3: count = 0

LSL32는 ARM의 레지스터 값만큼 왼쪽으로 미는 명령입니다. 미는 양은 하위 8비트만 쓰고 32 이상이면 결과가 0입니다. 그래서 s=0 식은 r이 9 이상일 때 (C+1)×2m+2×2r÷512와 같고 r이 8 이하이면 0이 됩니다.

합성 CSD 45개 가운데 대표 사례 확인
형식넣은 값계산된 sector 수

s=1C = 0x100fe67,369,984

s=1C = 0x3fffff (최댓값)0 (32비트를 넘침)

45개는 형식 값 네 가지(4개), s=0에서 C·r·m의 경계 조합(20개), s=1에서 C 다섯 값(5개), 난수 16바이트(16개)입니다. 최댓값에서 0이 되는 사례는 계산 코드의 동작을 본 것입니다. 실제 카드가 그런 값을 내놓는다는 뜻이 아닙니다.

SD 규격과 맞춰 보기

SD Association의 Physical Layer Simplified Specification은 CSD 2.0의 용량을 (C_SIZE+1)×512KByte로 정의합니다. 512바이트로 나누면 (C_SIZE+1)×1024이고 펌웨어의 s=1 식과 같습니다.

  • 원래 조사에서는 규격 PDF 전문을 열지 못했습니다(내려받기 형식 문제와 HTTP 403 응답). 검색 색인에 나온 발췌(6.00판 인쇄 쪽 172의 C_SIZE·READ_BL_LEN 설명)만 확인했습니다.
  • 이번 검수에서도 규격 PDF는 약관 동의 뒤에만 받을 수 있어 열지 않았습니다. 대신 누구나 읽을 수 있는 Linux 커널의 CSD 해석 코드(mmc_decode_csd)와 대조했습니다. 위 표의 비트 위치, CSD 2.0의 (1 + C_SIZE) << 10, CSD 1.0의 (1 + C_SIZE) << (C_SIZE_MULT + 2)와 블록 길이 보정이 펌웨어의 식과 같은 꼴입니다.
참고: 파일시스템 선택과의 관계

파일시스템 종류를 고르는 코드는 매체 객체의 종류 값이 4이면 Virtual을 고릅니다. 그 밖에는 크기 필드가 0x0403ffff보다 크면 ExFat을, 아니면 Fat을 고릅니다(파일 인터페이스와 버퍼 수명). 이번 결과로 C 경로에서 이 비교에 쓰이는 값의 출처를 연결했습니다. 위 표의 0x100fe와 0x100ff는 이 경계 바로 아래와 위에 놓이도록 고른 값입니다.

경계를 넘는 가장 작은 값 67,371,008 sector는 512바이트 기준으로 약 32.1GiB입니다. SD Association은 32GB를 넘는 SDXC 카드의 파일시스템을 exFAT로 안내하므로 방향은 맞습니다. 다만 Linux 커널 주석이 SDXC의 최소 C_SIZE로 적은 0xFFFF(67,108,864 sector)보다 262,144 sector 큽니다. 이 차이의 이유는 확인하지 못했습니다. 초기화와 mount가 언제 실행되고 성공하는지도 따로 확인해야 합니다.

활성화 함수와 진단 코드의 주소
  • SD 활성화 함수: 0x53281cf8–0x53281f18. 전역 0x54583af0의 16바이트를 this+0x28로 복사합니다. 같은 자리에서 전역 0x54583ae0의 16바이트도 this+0x38로 복사합니다(뜻은 조사하지 않았습니다).
  • 계산 함수 0x53282554의 결과를 0x53281e04에서 this+0x18에 저장하고 +0x79를 1로 만듭니다.
  • 성공 로그에 값을 넘기는 자리: 0x53281e20, 0x53281e4c.
  • 진단 코드 구간: 0x5260f57c–0x5260f610. 문자열 CSD Register, CSD_STRUCTURE를 씁니다.
  • 크기 필드 추출 0x532824fc–0x53282554, sector 수 계산 0x53282554–0x532825d8.
  • 시험에서 실행한 분기: this+0x24 = 0, +0x7a = 0, +0x10 = 0x1b2, 기본 callback. mutex를 쓰는 경로, 다른 mode, 재정의된 callback은 실행하지 않았습니다.
  • 원래 조사의 규격 확인 기록(출처 주소, 인쇄 쪽, 열람 실패 사유)은 update-volume-descriptor-evidence.json의 external_corroboration에 있습니다.

R 볼륨의 시작·크기 값은 별도 객체 EmmcPartition에서 옵니다

Emmc 객체의 필드를 쓰는 것처럼 보이던 코드는 다른 객체의 생성자였습니다. R의 volume record는 그 객체에 든 상수 두 개를 받습니다.

함수 0x53297fac는 +0x14와 +0x18 근처에 값을 씁니다. 처음에는 Emmc 객체를 고치는 코드로 보였습니다. 그러나 이 함수가 설치하는 vtable의 RTTI 이름은 EmmcPartition입니다. Emmc 객체는 작업 조회와 dynamic cast로 찾아 이 객체의 +4에 포인터로만 보관합니다. 따라서 이 생성자의 쓰기를 Emmc 객체의 갱신으로 세면 안 됩니다.

volume record에 들어가는 값 확인
volume record 필드매체 객체 종류 3 (R)다른 종류 (검사한 C 조건)
+0x0cEmmcPartition+0x24 → 0x3480000
+0x10EmmcPartition+0x44 → 0x38c000매체 객체+0x18
+0x14 / +0x160 / 0매체 객체+0x1c / +0x1e

볼륨 설정 함수 두 개가 매체 객체의 종류 값(부호 있는 1바이트)을 검사해 이 분기를 고릅니다. 종류가 3이면 EmmcPartition 객체에서 문자 R에 해당하는 값을 꺼내 record에 씁니다. 원본 코드로 실행한 두 사례에서 매체 객체 자체의 내용은 바뀌지 않았습니다.

이 절의 근거만으로는 두 상수의 단위를 정할 수 없습니다. 두 값을 실제로 쓰는 코드를 따라간 R 파티션과 sector I/O에서 +0x0c는 시작 sector 오프셋, +0x10은 총 sector 수로 확인했습니다.

참고

여기서 말하는 volume record는 파일시스템 볼륨의 항목입니다. 쓰기 bank와 BOOT 선택에서 다루는 FwPartition의 bank record와는 다른 구조입니다.

EmmcPartition과 record 쓰기 주소
  • EmmcPartition 생성자: 0x53297fac. vptr 0x53cb16e8, RTTI 이름 문자열 0x53cb16cc. 두 상수를 +0x24와 +0x44에 쓰는 명령은 0x532980a0, 0x532980d0에 있습니다.
  • 문자별 getter: 0x53298148, 0x532981ec. R에서 위 상수를 돌려줍니다.
  • 볼륨 설정 함수: 0x52f51028, 0x52f5107c. 종류 3이면 factory+0x1c의 EmmcPartition을 씁니다.
  • record에 쓰는 명령: 0x52f527c4(+0x0c), 0x52f528d0(+0x10)와 뒤따르는 +0x14, +0x16 쓰기.
  • 시험 값: C 조건에서 매체 객체의 +0x18, +0x1c, +0x1e에 넣어 둔 값이 record의 +0x10, +0x14, +0x16으로 그대로 복사됐습니다. +0x0c는 0이었습니다.

완료 통지는 모델 상태를 바꾸고 UI 작업을 등록합니다

완료 함수는 메시지 ID 하나를 골라 공통 송신 함수로 보냅니다. 받는 쪽은 그 ID를 보고 모델 상태를 3으로 바꾼 뒤 UI 작업을 등록합니다. 두 쪽을 잇는 전달은 확인하지 못했습니다.

보내는 쪽

  • 완료 함수는 메시지 ID 0x2640820b와 인수 0을 골라 공통 송신 함수에 넘깁니다.
  • 공통 송신 함수는 받은 두 값을 7 word짜리 봉투(envelope)의 첫 두 칸에 적고 나머지 다섯 칸을 0으로 채웁니다. 그런 다음 통지 객체 +4에 있는 pipe를 거쳐 전송 함수로 넘깁니다.
  • 반환값: 공유 소유자 포인터가 null인 시험 조건에서 송신 함수는 전송 함수의 반환값(0, 1, 0xffffffff)을 그대로 돌려줬습니다. 완료 함수는 이 반환값으로 분기하지 않습니다. 반환값이 무엇이든 이벤트 경계에 0x20을 넘기고 마지막 통지 호출로 넘어갑니다.

받는 쪽

  • 수신 router는 메시지 ID의 최상위 바이트(group)가 0x26인 분기를 고릅니다. 이어 판별 함수 두 개를 거칩니다. 다른 종류의 메시지인지 묻는 판별은 통과하지 못하고 update 메시지인지 묻는 판별을 통과해 수신부로 갑니다.
  • 모델 객체는 getter가 돌려주는 전역 객체입니다. 생성자가 설치하는 vtable과 RTTI 이름으로 FwUpdateModel임을 확인했습니다.
  • 수신부는 모델의 +8에 3을 쓰고 작업 ID 0x128과 인수 0, 0을 UI 작업 큐에 등록합니다.
수신부가 기록한 상태 값 확인 (메시지는 모델)

이웃한 세 메시지는 내용이 0인 합성 메시지로 시험했습니다. 값 2, 4, 5의 이름이나 뜻은 정하지 않았습니다. 이 값들을 UI가 어떻게 다루는지는 완료 후 UI 작업에 있습니다.

주의

송신부와 수신부는 각각 원본 코드로 실행했습니다. 그러나 둘 사이의 구독, 전달, 스케줄링은 시험에서 연결하지 않았습니다. 상태 값 3을 실제 업데이트 성공이나 인증 통과로 해석하지 않습니다.

UI 작업 큐에 넣는 조건과 큐가 가득 찬 경우

큐 등록 함수는 16비트 개수(count)와 용량(capacity)을 읽습니다. count < capacity − 1일 때만 12바이트 항목에 작업 ID와 두 인수를 저장합니다. 그 뒤 count를 1 늘리고 쓰기 위치를 (위치 + 1) & mask로 옮기고 unlock과 wake를 부릅니다.

한계와 남은 과제

  • 대체한 호출: 매체 객체 시험에서 부모 클래스의 기반 생성자, 작업 조회, dynamic cast, 카드 읽기와 설정, 작은 메모리 복사는 대체 함수입니다. 완료 통지 시험은 초기화가 끝난 singleton과 직접 만든 큐를 쓰고 실제 전송·OS 이벤트·업데이트 실행기는 대체했습니다.
  • 실행한 분기: SD 활성화 함수는 고른 조건의 분기만 실행했습니다. 생성 함수와 Emmc 초기화·활성화 함수는 읽기만 했습니다.
  • Emmc 크기 필드: 0이 아닌 값을 넣는 코드를 찾지 못했습니다.
  • 송신과 수신의 연결: 실제 큐 등록, 전달, 스케줄링을 실행하지 않았습니다.
  • 디컴파일 C의 한계: 자동으로 복원한 C에는 꼬리 호출이 빠지거나 구조체·인덱스 추정이 틀린 곳이 있을 수 있습니다. C 출력은 고치지 않았고 원본 ARM 명령과 실행 결과를 결론의 기준으로 삼았습니다.
  • 하지 않은 것: 실제 저장 매체, 카메라, 펌웨어 빌드, 플래시 기록은 다루지 않았습니다.
