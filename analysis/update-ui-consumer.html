완료 통지 뒤 UI 작업이 처리되는 과정

완료 통지를 받은 코드는 UI 작업 큐에 작업 하나를 넣습니다. 그 작업이 큐에서 나와 어느 객체로 가고, 그 객체가 무엇을 하는지 따라갔습니다.

이 문서에서

  1. 배경: 작업 큐와 상태별 처리 객체
  2. 큐에서 꺼낸 작업은 현재 상태의 객체로 전달됩니다
  3. 모델 값에 따라 요청을 만들고 handle을 저장합니다
  4. 검증 범위와 남은 과제
  5. 재현 방법
  6. 근거 파일과 참고 자료

핵심 요약

  • 큐에서 꺼낸 작업은 받는 객체가 정해져 있지 않습니다. 항목을 처리할 때마다 현재 UI 상태에 맞는 객체를 찾아 전달합니다. 상태 ID가 특정 값일 때 UserFwUpdateController로 이어지는 경로를 연결했습니다.
  • 이 객체는 FwUpdateModel의 상태 값을 읽습니다. 값이 3이면 이전 요청을 취소하고 서비스에 새 요청을 등록한 뒤, 돌려받은 handle을 저장합니다.
  • 나중에 callback이 오면 받은 handle이 저장한 값과 같은지 봅니다. 같고 플래그 두 개가 조건에 맞을 때만 후속 작업을 큐에 넣는 함수로 갑니다.
  • 원본 코드 28사례를 실행했습니다. UI가 실제로 그 상태에 들어가는 과정, 서비스가 callback을 전달하는 과정, 후속 작업의 소비와 재부팅은 확인하지 못했습니다.

확인 원본 코드 실행으로 확인

  • 큐에서 꺼내기, 위치 순환, 항목별 상태 재조회
  • 모델 값에 따른 분기와 handle 저장
  • 항목 callback과 서비스 callback의 조건
  • RTOS 단독 입력과 통합 이미지 입력에서 같은 결과

정적 분석 코드를 읽어 판단

  • 객체가 없을 때의 할당과 생성자 호출
  • 후속 작업 함수가 큐에 넣는 값(작업 5, 인수 4)
  • vtable·RTTI로 읽은 클래스 이름

모델 시험 조건으로 정한 것

  • 큐 항목과 상태 ID를 직접 넣음, 객체는 이미 만들어진 상태
  • OS 대기·lock·이벤트, 화면 갱신, 요청·취소는 대체 함수
  • 개수와 위치가 어긋난 큐 같은 합성 상태
  • CPU는 Unicorn의 Cortex-A15 모델

미확인 확인하지 않은 것

  • 완료 메시지의 실제 전달, UI가 그 상태로 들어가는 호출자
  • 요청 인수 1000의 단위, 서비스의 callback 전달
  • 작업 5의 소비, 상태 전환, 재부팅
  • 디코딩된 버퍼의 최종 회수

배경: 작업 큐와 상태별 처리 객체

앞 문서에서 완료 통지의 수신부가 두 가지 일을 하는 것을 확인했습니다. FwUpdateModel의 상태 값(+8)을 3으로 바꾸고, UI 작업 큐에 작업 ID 0x128을 넣습니다. 이 문서는 그 뒤를 잇습니다.

화면 쪽 코드는 상태 ID에 따라 작업을 처리할 객체를 고릅니다. 큐는 “누가 처리할지”를 저장하지 않고 “지금 어떤 상태인지”만 기억합니다. 그래서 같은 작업 번호라도 상태에 따라 다른 객체가 받을 수 있습니다. 업데이트 완료가 화면에 어떻게 반영되는지 알려면 이 연결을 따라가야 합니다.

큐에서 꺼낸 작업은 현재 상태의 객체로 전달됩니다

작업 0x128은 받는 곳이 고정된 작업이 아닙니다. 상태 ID가 0x0100000f일 때 UserFwUpdateController의 상태 처리 함수에 도착합니다.

큐에서 꺼내는 동작

  • 큐 소비 함수는 읽기 위치와 쓰기 위치가 다르면 12바이트 항목 하나를 스택으로 복사합니다.
  • 읽기 위치를 1 늘려 mask를 적용하고, 16비트 개수(count)를 1 줄인 다음 unlock하고 항목을 전달합니다.
  • 큐에 있던 원래 항목은 지우지 않습니다.
  • 되풀이할지는 count가 아니라 두 위치가 같은지로 정합니다.

첫 두 줄은 OS 호출의 반환값과 비운 뒤의 판정 함수 결과만 다르게 넣은 사례입니다. 다섯 사례 모두 끝난 뒤 count는 0이었고 원래 항목은 그대로 남았습니다. 읽기 위치 7과 6에서 시작한 사례는 위치가 8칸 끝에서 0으로 돌아갑니다.

합성 상태에서만 본 현상

count를 0으로 두고 두 위치만 다르게 넣었더니, 항목 하나를 처리한 뒤 count가 65,535가 됐습니다. 서로 맞지 않는 값을 일부러 넣었을 때의 산술 결과입니다. 실제 UI에서 그런 상태가 생긴다는 증거가 아닙니다.

상태 ID로 처리 객체를 찾는 과정

  • 상태 ID가 기록되는 곳 — 일반 상태 설정 함수는 넘겨받은 ID를 controller의 +4와 큐의 +4에 쓰고, 전역 영역 0x5458f264의 0x48바이트를 지웁니다. ID 0, 0x0100000f, 0xffffffff 세 값으로 실행해 확인했습니다.
  • 객체를 찾는 곳 — 조회 함수는 정규화한 상태 ID가 0x0100000f이면 registry의 +0x54에 든 객체를 돌려줍니다. 그 자리가 비어 있으면 0x1b0바이트를 할당하고 생성자를 부르는 코드가 있습니다. 시험은 객체가 이미 있는 경우만 실행했습니다.
  • 항목마다 다시 찾음 — 전달 함수는 항목을 처리할 때마다 상태 객체를 다시 조회합니다. 합성 callback이 registry의 객체 포인터를 바꾼 사례에서 다음 항목은 새 객체로 갔습니다.

실제 업데이트 화면이 이 상태 ID로 들어가는 호출자는 아직 연결하지 못했습니다. 위 결과를 특정 화면 전환을 카메라에서 재현한 것으로 읽으면 안 됩니다.

모델 값에 따라 요청을 만들고 handle을 저장합니다

상태 처리 함수는 모델 값이 3일 때만 서비스에 새 요청을 등록합니다. 값 4와 5에서는 객체 안의 플래그만 바꿉니다.

값 3: 이전 요청 취소와 새 요청 등록

  1. 이전 handle 정리 객체 +0x1a8에 저장된 handle이 0이 아니면 서비스의 취소 함수에 넘기고, 저장값을 0으로 만듭니다.
  2. 새 요청 등록 서비스의 등록 함수를 인수 (서비스, 1000, 객체 +0x188)로 부릅니다. +0x188은 callback을 받을 자리입니다.
  3. handle 저장 등록 함수의 반환값을 그대로 +0x1a8에 저장합니다. 0이 돌아와도 저장합니다.

인수 1000의 단위와 서비스가 실제로 하는 일은 이 문서에서 확인하지 않았습니다. 서비스 내부의 슬롯과 handle 번호는 UI 타이머와 콜백에서 다룹니다.

callback: handle과 플래그 확인

callback은 객체의 +0x188 자리로 들어옵니다. thunk가 포인터에서 0x188을 빼 객체의 시작으로 되돌린 뒤 callback 함수로 넘어갑니다.

후속 작업 함수

후속 작업 함수는 큐를 얻은 뒤 앞 문서의 큐 등록 함수로 넘어갑니다. 넘기는 값은 작업 5, 인수 4, callback 없음입니다. 이 연결은 코드를 읽어 확인했고, 시험에서는 함수에 들어왔다는 사실만 기록하는 대체 함수로 바꿨습니다. 작업 5가 어디에서 소비되는지, 실제 상태 전환과 재부팅이 일어나는지, 디코딩된 버퍼가 언제 회수되는지는 아직 조사하지 못했습니다.

한계와 남은 과제

  • 대체한 호출 — OS의 대기·lock·이벤트, observer, 화면 갱신, 설정 처리, 요청·취소, 큐를 비운 뒤의 판정 함수는 모두 대체 함수입니다. 대체 함수가 실패 값을 돌려준 사례를 실제 OS의 동작으로 읽으면 안 됩니다.
  • 실행한 분기 — 상태 ID 조회 함수는 전체 구간을 보존했지만, 실행한 것은 객체가 이미 있는 0x0100000f 경로뿐입니다.
  • 디컴파일 C의 한계 — 자동으로 복원한 C에는 큐의 읽기 위치 계산과 callback의 꼬리 호출에 오류와 누락이 있습니다. C 출력은 고치지 않았고, 원본의 덧셈·AND·16비트 저장 명령과 실행 결과를 해석의 기준으로 삼았습니다.
  • 남은 과제 — 실제 메시지 전달, UI 상태 진입, 서비스의 시간 단위와 callback 전달, 작업 5의 소비, 재부팅, bank 전환, 인증.
  • 하지 않은 것 — 카메라, OS, 저장소 입출력, 펌웨어 빌드, 플래시 기록.

재현 방법

도구는 RTOS만 잘라 낸 rtos.bin이나 추출기가 만든 통합 이미지 decoded.bin을 입력으로 받습니다. 입력의 SHA-256이 아래 값과 다르면 실행하지 않습니다.

RTOS SHA-256
342d2f35405e8daf1797dfe431d2e4aa70f4b52a2c242a29df48206672f1dfb4
통합 이미지 SHA-256
7ff301d585ef7adcd620a15575faa39b4227cc5a27eaa8d754efe50f667a30f9
Python 패키지
unicorn==2.1.4
python verify_update_ui_consumer.py rtos.bin --output ui-consumer.json

출력 파일이 이미 있으면 멈춥니다. Python을 -O로 실행해 assert를 끄면 실행을 거부합니다.

  • update-ui-consumer-checks.json — 28사례의 입력과 결과, 대체 함수 목록, 실행된 명령 주소
