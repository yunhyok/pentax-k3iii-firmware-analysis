PENTAX K-3 MARK III · CONDITIONAL UI DISPATCH · 2026-11-08

완료 통지 이후 UI 작업과 handle 처리

작업 0x128은 현재 UI 상태에 따라 다른 객체로 전달된다. 상태 ID가 0x0100000f일 때 UserFwUpdateController로 이어지는 경로를 연결했다. 모델 값 3은 새 서비스 요청을 만들며 이후 callback은 handle과 플래그를 검사한다. 실제 타이머 동작과 재부팅은 아직 확인하지 않았다.

연구 개요 · 완료 메시지·작업 등록 · 큐·상태 선택 · handle·callback · 검증 범위

큐에서 현재 상태의 처리기로

큐 소비 함수 0x528e901c는 read index(+0x20)와 write index(+0x22)가 다르면 12바이트 record를 스택으로 복사한다. read index를 증가시켜 mask(+0x24)를 적용하고 16비트 count(+0x1c)를 줄인 뒤 unlock과 dispatch를 호출한다. 큐의 원래 record는 지우지 않는다. 반복 조건은 count가 아닌 두 index의 비교다. 큐 명령·호출 근거

0x526dbf0c의 정규화된 상태 ID 0x0100000f 분기는 registry+0x54의 객체를 반환한다. NULL이면 0x1b0바이트 할당과 생성자 0x5274e8cc 호출이 있다. 생성자·vtable·RTTI는 이 객체를 UserFwUpdateController로 식별한다. 수치 검사는 객체가 이미 있는 분기만 실행했다. 실제 업데이트 UI가 이 상태로 진입하는 호출자는 아직 연결하지 않았다.

일반 상태 setter 0x526d9604는 공급된 ID를 controller+4와 queue+4에 기록하고 0x5458f264의 0x48바이트를 지운다. dispatcher는 매 record마다 상태 객체를 다시 조회한다. 합성 callback이 registry의 객체 포인터를 바꾼 사례에서는 다음 record가 새 객체를 사용했다. 이 결과를 특정 UI 전환의 실기 재현으로 해석하지 않는다.

작업 ID 0x1bc는 상태 처리만 생략한다. record+8의 callback 포인터가 있으면 해당 vslot 0에 작업 ID와 record+4 인수를 전달한다. 상태 handler와 이 callback의 반환값은 사용하지 않으며 dispatcher는 1을 반환한다. 작업 0x128의 User controller 경로는 0x526d8ccc → 0x5274f0ec → 0x5274f010이다. 중간 observer와 화면 효과는 시험에서 대체했다.

이전 handle인 controller+0x1a8이 비제로이면 서비스 함수 0x528eb490에 넘기고 저장값을 0으로 만든다. 이어 0x528eb758(service, 1000, this+0x188)의 반환값을 그대로 새 handle로 저장하며 반환값 0도 저장한다. 인수 1000의 단위와 서비스 실행 결과는 확인하지 않았다. 이 handle을 펌웨어 input·decoded 버퍼의 포인터나 해제 상태로 보지 않는다. handle 저장·가상 호출 근거

secondary vslot+8의 thunk 0x5274e8c4는 this에서 0x188을 빼고 0x5274e88c로 이동한다. 받은 handle이 저장값과 일치해야 저장 handle을 0으로 만들고 byte+0x1ad를 1로 쓴다. 이어 +0x1ac가 비제로이고 +0x1ae가 0일 때만 0x5274e860으로 간다. 원본 callback의 이 조건은 실행했지만 실제 서비스가 callback을 전달하는 과정은 실행하지 않았다.

후속 생산자 0x5274e860는 기존 enqueue에 work 5, 인수 4, callback NULL을 넘긴다. 이 연결은 정적 근거이며 수치 검사에서는 생산자 진입을 기록하는 stub으로 대체했다. work 5 소비·실제 상태 전환·재부팅과 decoded 버퍼의 최종 회수는 다음 조사 범위다.

28사례의 범위와 의사코드 한계

원본 ARM 28사례는 RTOS 직접 입력과 통합 decoded 입력에서 동일하게 통과했다. 상태 ID 기록 3, cached resolver 1, 모델·handle 분기 8, record callback 4, 큐 drain·wrap·OS 반환 5, record별 재조회 1, 불일치 count 1, 서비스 callback 조건 5사례다. C 출력 10개와 지원 범위 12개, ARM 3,077 words를 로컬에 보존했다. 공개 28사례 결과

count 0과 서로 다른 index를 주입한 사례에서는 한 record를 처리한 뒤 count가 65535가 됐다. 이는 불일치한 합성 상태의 산술 결과이며 실제 UI에서 그 상태가 발생한다는 증거는 아니다. OS wait·lock·event, observer·refresh·설정 처리, 요청·취소와 drain 후 predicate는 모두 stub이다. 원본 resolver 전체를 보존했어도 모든 상태 분기를 실행한 것은 아니다.

자동 복원 C의 큐 index 계산과 callback tail call에는 오류·누락이 있다. C 출력은 수정하지 않고 원본 ADD·AND·STRH와 실행 결과를 해석 기준으로 삼았다. 실제 메시지 전달·UI 상태 진입·서비스 시간 단위·callback 전달·재부팅·bank 전환·인증은 미확정이다. 카메라·OS·저장소 I/O와 빌드·플래시는 수행하지 않았다.
