펌웨어 업데이트 과정 · 타이머 사슬 3/7

TTimPeriod 설정값이 64비트 카운터를 올리는 과정

예약 시각 계산에는 “주기 값”이 한 번씩 더해집니다. 이 값이 어디서 오는지 찾아, 펌웨어에 들어 있는 설정 한 줄에서 커널의 시각 카운터와 하드웨어 타이머 설정까지 이었습니다.

이 문서에서

  1. 배경: 커널은 틱을 세어 시간을 잽니다
  2. 주기 값은 내장 설정의 TTimPeriod에서 옵니다
  3. 틱마다 64비트 카운터에 주기 값을 더합니다
  4. 보드 초기화는 타이머 레지스터에 값 다섯 개를 씁니다
  5. 20개 사례의 구성
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 주기 값은 펌웨어에 내장된 설정의 TTimPeriod 항목에서 옵니다. 내장 값은 1이고, 타이머 초기화는 1부터 50까지만 받아들입니다.
  • 같은 값이 세 곳에 쓰입니다. 틱마다 64비트 카운터에 더해지고, 예약 시각에 한 번 얹히고, 남은 시간에서 한 번 빠집니다.
  • 보드 초기화 함수는 타이머 채널의 레지스터에 값 다섯 개를 정해진 순서로 씁니다. 그 가운데 재적재 값은 6,749입니다.
  • 설정 읽기, 범위 검사, 64비트 덧셈, 레지스터 기록을 원본 기계어로 20개 사례 실행했습니다.
  • 카운터 한 눈금이 얼마의 시간인지, 타이머가 어떤 주파수로 도는지는 확정하지 못했습니다. 공개 자료와 맞추어 보면 1밀리초로 읽히지만 가설로 남겨 둡니다.

확인 원본 코드 실행으로 확인

  • 원본 파서가 내장 설정에서 값 1을 읽음
  • 1~50 밖의 값과 빠진 값을 거부
  • 카운터에 주기 값을 더하는 64비트 덧셈
  • 레지스터 기록 다섯 번의 주소, 값, 순서

정적 분석 코드를 읽어서 판단

  • 설정 표의 주소를 전역 변수에 넣는 초기화 코드
  • 보드 함수가 descriptor에 적는 함수 주소
  • 덧셈 명령이 타이머 처리 함수 안에 있다는 점

모델 시험 조건으로 정한 것

  • 설정 표를 가리키는 전역 포인터는 직접 설정
  • 범위 시험의 설정 문자열은 직접 작성
  • 레지스터 주소는 일반 메모리로 대신함
  • 인터럽트 차단·복원 함수는 대체 함수

미확인 확인하지 않은 것

  • 시간 단위와 타이머 입력 주파수
  • 초기화 전체가 끝까지 성공하는지
  • 실제 인터럽트가 이 덧셈을 실행하는 주기
  • 부팅 뒤 설정이 다른 값으로 바뀌는지

배경: 커널은 틱을 세어 시간을 잽니다

이 커널은 시간을 연속으로 재지 않습니다. 하드웨어 타이머가 일정한 간격으로 인터럽트를 걸면, 그때마다 카운터를 정해진 양만큼 올립니다. 이 한 번을 틱이라고 하고, 한 번에 올리는 양이 주기 값입니다. 예약한 알람은 카운터가 기한에 닿은 틱에서 처리됩니다.

커널 호출과 예약 시각에서는 예약 시각에 “현재 카운터”와 “주기 값”이 들어간다는 것까지 확인했습니다. 이 문서는 그 두 값을 만드는 쪽을 다룹니다. 하드웨어 카운터를 직접 읽는 부분은 하위 시간의 32비트 산술로, 인터럽트 처리 함수의 등록은 타이머 등록과 지연 콜백으로 이어집니다.

TTimPeriod
펌웨어의 설정 표에 들어 있는 항목 이름. 공개 T-Kernel 소스에서는 같은 이름의 항목이 타이머 인터럽트 간격(밀리초)입니다.
64비트 카운터
커널의 현재 시각 값. 이 문서와 근거 파일에서는 NOW64라고도 적습니다.
재적재 타이머
값을 하나씩 줄여 가다가 0을 지나면 인터럽트를 걸고, 미리 정한 재적재 값부터 다시 세는 하드웨어 타이머.
MMIO
메모리 주소에 값을 쓰는 방식으로 하드웨어 레지스터를 다루는 것.

주기 값은 내장 설정의 TTimPeriod에서 옵니다

타이머 초기화는 설정 표에서 TTimPeriod를 읽어 전역 변수에 넣고, 값이 1~50이 아니면 오류를 돌려줍니다. 내장 설정에 적힌 값은 1입니다.

설정을 읽는 과정

설정 초기화 코드는 펌웨어에 들어 있는 설정 표의 주소를 전역 변수에 넣습니다. 이 표 안에 TTimPeriod, 탭 문자, 1, 줄바꿈으로 이루어진 한 줄이 있습니다. 시험에서는 전역 변수를 직접 그 주소로 맞춘 다음, 원본 파서를 그대로 실행해 값 1을 읽어 냈습니다.

실행한 것은 원본 코드입니다. 설정 읽기 함수, 숫자 읽기, 키 찾기, 토큰 나누기, 숫자 변환, 그리고 문자열 길이와 비교 보조 함수까지 대체 함수 없이 돌렸습니다. 다만 고른 입력만 넣었으므로, 파서의 문법 전체나 모든 잘못된 입력을 검증한 것은 아닙니다.

범위 검사

타이머 초기화는 값을 한 개만 받을 수 있는 출력 칸에 설정을 읽습니다. 읽은 개수가 0 이하이거나 u32(값 − 1) > 49이면 0xfffb0000을 반환합니다. 부호 없는 비교라서 0과 음수도 함께 걸러집니다. 통과하면 64비트 값 두 개를 0으로 만들고 기한 큐의 머리를 빈 상태로 초기화합니다.

시험 조건

통과 사례는 초기화가 다음 함수를 부르기 직전에서 멈추게 했습니다. 그 뒤의 지연 실행 큐 초기화, 하드웨어 설정, 처리 함수 등록은 이 시험에 들어 있지 않습니다. “통과”가 초기화 전체의 성공을 뜻하지는 않습니다. 실제 부팅에서 설정 초기화 코드가 불리는지, 그 뒤에 설정이 바뀌는지도 실행으로 확인하지 않았습니다.

파서의 반환값

  • 없는 키와 빈 키는 0xffd60000을 반환하고 출력을 건드리지 않습니다.
  • 키는 있는데 값이 없으면 개수 0을 반환합니다.
  • 값이 두 개인 설정(TTimPeriod 1 50)을 출력 칸 하나로 읽으면, 첫 값만 저장하고 반환 개수는 2입니다. 저장한 개수가 아니라 읽은 개수를 돌려준다는 뜻입니다.
참고: 공개 T-Kernel 소스와 견주면

공개 T-Kernel 2.0의 timer_initialize도 TTimPeriod를 읽고, 범위를 벗어나면 오류를 돌려주고, 시각 변수 두 개를 0으로 만든 뒤 타이머 큐를 초기화합니다. 그 소스의 오류 코드 표기로 0xfffb0000은 E_SYS(시스템 오류), 0xffd60000은 E_NOEXS(대상 없음)와 같은 값입니다. 구조가 닮았다는 관찰이며, 이 펌웨어가 같은 소스를 쓴다고 확인한 것은 아닙니다.

틱마다 64비트 카운터에 주기 값을 더합니다

카운터를 올리는 명령은 NOW64 = (NOW64 + u32(주기 값)) mod 264입니다. 이 카운터가 예약 시각과 남은 시간 계산에 쓰이는 바로 그 값입니다.

마지막 사례의 주기 값은 실제 설정에서 나올 수 있다는 뜻이 아닙니다. 덧셈 명령이 32비트 값을 부호 없이 넓혀 더한다는 점을 보려고 넣은 값입니다.

덧셈 명령은 타이머 처리 함수의 구간 안에 있습니다. 그 함수를 실제 인터럽트로 실행한 시험은 없고, 이 문서의 사례는 덧셈 명령 몇 개만 따로 실행했습니다. 처리 함수가 등록되는 과정과 기한 비교는 타이머 등록과 지연 콜백에 있습니다.

제어 레지스터의 이전 값이 0일 때와 모든 비트가 1일 때 두 번 실행했고, 기록 다섯 번은 두 경우 모두 같았습니다. 이전 값을 읽어 섞지 않고 정해진 상수를 쓴다는 뜻입니다.

오른쪽 열의 이름은 리코가 공개한 K-3 Mark III용 Linux 커널 소스의 Milbeaut 타이머 드라이버에서 가져왔습니다. 이 드라이버는 채널마다 제어, 카운터, 재적재 레지스터 두 개를 상대 위치 0, 4, 8, 12에 두고, 클럭 선택 칸을 비트 10부터로 정의합니다. 관측한 주소 배치와 맞습니다.

주의

이름 풀이는 보조 근거입니다. Linux 쪽 장치 트리가 쓰는 채널은 0x1e000050과 0x1e000060이고, RTOS가 쓰는 0x1e0000d0 채널은 거기에 없습니다. 타이머에 들어가는 클럭도 분주 설정을 거칩니다. 드라이버가 쓰는 클럭 선택 값은 0뿐이어서 값 1의 뜻은 이 자료에 없습니다. 그래서 이 자료만으로는 RTOS 타이머의 주파수나 시간 단위를 정할 수 없습니다.

시험 조건

초기화 함수를 따로 불러, 레지스터 주소를 에뮬레이터의 일반 메모리에 대응시킨 결과입니다. 실제 주변장치에서 값을 되읽을 때의 동작, 스스로 바뀌는 상태 비트, 카운터가 줄어드는 과정, 인터럽트는 재현하지 않았습니다. 이 함수의 주소가 보드 descriptor에 저장된다는 점은 코드를 읽어 확인했지만, 부팅 과정에서 그 descriptor가 선택되는 흐름은 실행하지 않았습니다.

따로 잘라 낸 RTOS 파일과 통합 decoded 파일에서 결과가 같았습니다. 이 20개 사례는 UI 타이머의 39개, 커널 호출의 17개와 별개입니다.

공개하지 않고 보관한 자료는 디컴파일 C 8개, 보조 구간 5개, ARM 명령 414 words입니다. 디컴파일된 C에는 잘못 복원된 변수와 분기가 있어서, 고치지 않고 원본 ARM 명령과 실행 결과로 판단했습니다. CPU는 Unicorn의 Cortex-A15 모델입니다.

한계와 남은 과제

시간 단위에 대해 지금 말할 수 있는 것

구분내용상태
펌웨어에서 확인한 값내장 TTimPeriod는 1, 허용 범위는 1~50, 타이머의 재적재 값은 6,749. 하위 시간 변환은 카운터 차이에 1,000,000을 곱하고 6,749로 나눈 몫을 냅니다. 재적재 한 주기를 1,000,000 눈금으로 보는 환산입니다.확인
공개 자료공개 T-Kernel 2.0 소스에서 TTimPeriod는 밀리초 단위의 타이머 간격이고, 참조 보드 구현의 허용 주기는 최대 50밀리초입니다. 틱 사이의 시간을 돌려주는 함수는 나노초를 씁니다.확인
두 가지를 맞추어 본 해석틱 하나가 1밀리초이고 하위 시간이 나노초라고 읽으면 위 값들이 서로 맞습니다. 이 경우 완료 화면이 넘긴 지연 1000은 1초 남짓입니다.미확인

해석을 확정하지 못한 까닭은 세 가지입니다. RTOS가 쓰는 타이머 채널의 입력 주파수를 확인하지 못했습니다. 이 펌웨어의 함수 번호가 공개 T-Kernel 2.0과 달라, 같은 정의를 쓴다고 단정할 수 없습니다. 실제 카메라에서 시간을 잰 적이 없습니다.

그 밖의 한계

  • 타이머 초기화는 앞부분만 실행했습니다. 처리 함수 등록과 인터럽트 설정은 타이머 등록과 지연 콜백에서 정적 분석으로 이었습니다.
  • 설정 초기화 코드와 보드 연결 함수가 실제 부팅에서 불리는 흐름, 부팅 뒤 설정이 바뀔 가능성은 확인하지 않았습니다.
  • 이 문서 범위 밖: 0이 아닌 bank 값을 만드는 코드, 리소스 레코드의 +4 위치를 쓰는 코드, 인증 경로. 카메라 입출력과 펌웨어 빌드·기록은 하지 않았습니다.

재현 방법

입력은 따로 잘라 낸 RTOS 파일이나 통합 decoded 파일입니다. SHA-256과 적재 주소는 UI 타이머 문서의 재현 방법과 같습니다. Python 패키지 unicorn이 필요합니다.

python verify_update_timer_clock.py rtos.bin --output timer-clock.json

스크립트는 새 출력 파일만 만들고 이미 있는 파일은 덮어쓰지 않습니다. 원본 C, ARM 목록, 바이너리, 내장 설정 표는 공개하지 않습니다.
