부팅과 저장소 · bank 기록자 후보 점검

부트 헤더를 읽는 함수의 +4 저장은 어디에 쓰이는가

파티션 표의 bank 값을 누가 바꾸는지 찾는 과정에서, 표 근처 주소를 다루면서 “+4” 위치에 값을 쓰는 함수 하나가 후보로 남았습니다. 이 함수가 실제로 쓰는 곳을 확인해 후보에서 제외할 수 있는지 판단했습니다.

이 문서에서

  1. 배경: bank 값과 “+4 저장” 후보
  2. 헤더는 입력이고 출력은 멀리 떨어진 전역 버퍼입니다
  3. 출력 128바이트를 채우는 규칙
  4. 검증: 원본 ARM 코드 9사례
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 후보 함수를 직접 부르는 곳을 한 군데 찾았습니다. 그 호출에서 함수의 출력은 RTOS의 별도 전역 버퍼이고 파티션 표와 겹치지 않습니다.
  • 함수는 부트 헤더를 읽기만 합니다. 헤더의 한 값이 0인지에 따라, 헤더에서 옮겨 온 값 또는 기본값으로 128바이트 출력을 채웁니다.
  • 원본 ARM 코드를 에뮬레이터에서 9가지 조건으로 실행했습니다. 모든 사례에서 기록은 출력 버퍼에만 일어났고 파티션 표의 내용은 그대로였습니다.
  • 따라서 이 함수의 “+4 저장”을 파티션 표 레코드의 bank 기록으로 볼 근거가 없습니다. 0이 아닌 bank 값을 만드는 코드는 여전히 찾지 못했습니다.

확인 원본 코드 실행으로 확인

  • 구성 함수 5사례, 실제 호출부 앞부분 4사례
  • 기록 주소가 출력 32워드(호출부 사례는 정보 구조 +8 포함)뿐임
  • 헤더와 파티션 표 영역의 내용 보존

정적 분석 읽어서 판단

  • 호출부가 넘기는 인수와 출력 주소
  • 호출부 전체의 흐름과 진단 문자열
  • 이 함수를 가리키는 다른 직접 분기·주소 참조 검색

모델 시험 조건으로 정한 것

  • 헤더, 기본값 표, 장치 정보, 컨트롤러 레지스터 자리에 채운 값
  • CPU는 Unicorn의 ARM 모델(Cortex-A15)

미확인 확인하지 못한 것

  • 계산된 간접 호출이나 다른 CPU에서의 호출
  • 0이 아닌 bank 값과 슬롯 2 레코드 +4 값을 만드는 코드
  • 실제 장치에서의 값과 호출 뒤의 컨트롤러 처리

배경: bank 값과 “+4 저장” 후보

카메라의 내장 저장소에는 펌웨어 구성 요소가 어디에 들어 있는지 적은 파티션 표가 있습니다. 표의 각 레코드는 같은 리소스의 사본 위치를 여러 벌 가질 수 있고 그중 어느 것을 쓸지를 bank 값이 정합니다. BOOT 단계는 각 레코드의 +4 위치에 있는 값을 bank로 읽습니다(선택값의 위치와 의미).

수정한 펌웨어를 안전하게 다루려면 이 +4 값을 0이 아닌 값으로 바꾸는 코드가 있는지 알아야 합니다. 그래서 RTOS에서 파티션 표 주변 주소나 표 크기를 다루는 코드를 찾아, +4에 쓰는 곳을 하나씩 가려냈습니다(+4 기록자 구분). 다른 후보들은 조정 데이터 버퍼처럼 표와 무관한 객체에 쓰는 것으로 정리되었고 함수 0x53323ce4는 호출자를 확인하지 못해 남았습니다.

이 함수가 후보로 남은 이유

이 함수는 파티션 표(0x50b70100) 바로 앞의 주소 0x50b70020을 만들어 읽고 세 번째 인수(r2)가 가리키는 곳의 +4에 값을 씁니다. 함수 안쪽만으로는 r2가 실제로 어디를 가리키는지 알 수 없었습니다. r2가 파티션 표를 가리킨다면 bank 기록자일 수 있었습니다.

이 문서의 주소는 RTOS를 추정 적재 주소 0x52500000에 놓았을 때의 값입니다.

헤더는 입력이고 출력은 멀리 떨어진 전역 버퍼입니다

찾아낸 호출에서 r2는 0x54c40f3c로 고정되어 있습니다. 헤더 입력, 출력 버퍼, 파티션 표는 서로 겹치지 않는 세 영역입니다.

찾아낸 호출부

호출부를 찾기 전까지 확인한 것은 0x53323d24가 0x50b70028을 읽는다는 사실과 인수 r2 쪽으로 저장한다는 사실뿐이었습니다. 직접 호출 0x525e019c는 다음처럼 인수를 준비합니다.

r0, r1
전역 정보 구조 0x54c40ee0의 +0과 +4에서 읽은 값
r2
고정 주소 0x54c40f3c

호출부가 속한 함수 0x525e012c 안의 진단 문자열에는 mwnf_get_device_information()이라는 이름이 나옵니다. 장치 정보를 얻는 초기화의 일부로 보이지만 실제 장치 식별값이나 실행 성공은 확인하지 않았습니다.

호출 직전에 호출부는 0x1910080c를 읽습니다. 상위 두 비트가 0x40000000이면 전역 정보 구조의 +8에 0을, 다른 값이면 1을 저장합니다. 시험에서는 이 주소를 RAM으로 바꿔 놓았습니다. 구성 함수까지 실행한 뒤 복귀 주소 0x525e01a0에서 멈췄으므로, 그 뒤의 컨트롤러 처리와 초기화 결과는 검증하지 않았습니다.

다른 호출자가 있는지 찾아본 범위

  • RTOS 이미지 전체에서 4바이트 경계에 놓인 ARM 직접 분기 가운데 이 함수를 가리키는 후보를 찾았고 위 호출 하나가 나왔습니다.
  • 함수 주소가 워드로 저장된 곳과, 인접한 MOVW/MOVT 명령 쌍으로 주소를 만드는 곳도 찾았으나 추가 참조는 나오지 않았습니다.
  • 계산된 간접 호출, 다른 CPU, 따로 적재되는 코드까지 배제하는 검색은 아닙니다. 결론은 확인한 호출과 그 출력 주소에 한정합니다.

출력 128바이트를 채우는 규칙

출력의 앞 9워드는 항상 기본값 표에서 복사됩니다. “+4 저장”은 그 복사의 둘째 워드입니다. 나머지는 헤더의 +8 값에 따라 달라집니다.

검증: 원본 ARM 코드 9사례

9사례 모두에서 +4 저장은 0x54c40f40에 일어났고 파티션 표 영역은 한 바이트도 바뀌지 않았습니다.

시험 조건

RTOS 이미지의 원본 바이트를 Unicorn의 ARM 모델(Cortex-A15)에 올렸습니다. 헤더, 기본값 표, 장치 정보, 컨트롤러 레지스터 자리는 모두 직접 만든 값을 채운 RAM입니다. 파티션 표 영역은 0xa5로 채워 두고 실행 뒤에 그대로인지 봤습니다. 함수 안의 호출을 대체한 것은 없습니다. 실제 저장 매체 입출력은 일어나지 않습니다.

사례마다 다음을 검사했습니다.

  • 출력 앞 9워드가 기본값 표와 같습니다.
  • 스택을 뺀 기록 주소의 집합이 출력 32워드와 정확히 같습니다. 호출부 사례에서는 정보 구조 +8 하나가 더해집니다.
  • 모든 기록이 4바이트 단위입니다.
  • 파티션 표 영역(0x50b70100부터)이 실행 전과 같습니다.
  • 실행 위치가 두 함수의 범위를 벗어나지 않습니다.

RTOS 레코드만 넣었을 때와 압축을 푼 전체 스트림을 넣었을 때 결과가 같았습니다. 에뮬레이터의 결과를 실제 장치에서 실행한 결과로 해석하지 않습니다.

디컴파일 의사코드와 보존한 자료

두 함수는 angr 10.0.5의 C 형태 의사코드와 ARM 명령 전체를 로컬에 보관했습니다. 호출부 전체의 의사코드와 명령은 정적 근거이며 CPU 실행은 위에 적은 앞부분에 한정합니다. 원본 펌웨어, 의사코드, 명령 목록, 문자열 본문은 공개 자료에 넣지 않았습니다.

한계와 남은 과제

  • 제외한 것은 “출력 주소가 고정된 이 호출”입니다. 가능한 모든 호출자나 다른 이름으로 같은 메모리를 가리키는 경우까지 다 따지지는 않았습니다.
  • 0이 아닌 FwPartition bank 값을 만드는 코드와, 슬롯 2 레코드 +4의 실제 값을 만드는 코드는 여전히 미확정입니다.
  • 원본 기본값 표의 내용과 각 필드의 하드웨어 의미는 복구하지 않았고 시험에도 쓰지 않았습니다.
  • 실제 저장 매체 입출력, 펌웨어 빌드, 플래시는 하지 않았습니다.

재현 방법

검증 도구는 따로 잘라 낸 RTOS 레코드(rtos.bin)나 추출기가 만든 decoded.bin을 받습니다. 입력의 SHA-256을 확인하고 결과 파일이 이미 있으면 멈추며 Python의 assert가 꺼져 있으면 실행을 거부합니다. Python 패키지 unicorn이 필요합니다.

python verify_header_alias_consumer.py rtos.bin --output header-alias.json

추출 방법은 펌웨어 구조와 하드웨어의 재현 절차에 있습니다.
