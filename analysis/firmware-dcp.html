펌웨어 값으로 만드는 Lightroom 색 프로파일

이 저장소는 펌웨어 2.20의 색 값으로 만든 Custom Image 16종의 카메라 프로파일(DCP)과 그 바탕이 된 색 표를 공개합니다. 이 문서는 프로파일의 각 태그를 펌웨어 값에서 어떻게 얻는지 설명합니다. DNG 기준 처리 경로로 계산했을 때 카메라 JPEG와 얼마나 가까운지, 그리고 Lightroom 자체처럼 확인하지 않은 것이 무엇인지도 함께 적었습니다.

핵심 요약

  • 펌웨어 2.20의 색 값으로 만든 Custom Image 16종의 DCP가 저장소의 profiles/k3iii/에 있습니다. 추출한 색 표도 k3iii-color-tables.json으로 공개합니다. 각 프로파일은 그 모드의 출고 설정으로 만들었습니다. Bright는 대비 +1, Flat은 대비 −4입니다.
  • tools/make_k3iii_profile.py는 펌웨어 없이 공개된 색 표만으로 같은 프로파일을 만듭니다. 펌웨어 에뮬레이터로 만든 16개 파일과 바이트 단위로 같습니다.
  • ForwardMatrix에는 모든 Custom Image가 공유하는 센서 공통 행렬만 넣습니다. 모드 행렬, 채널별 곡선, 카메라 색역 끝의 자르기는 ProfileLookTable이 맡습니다. 이전 설계는 채도를 올리는 모드에서 채도 높은 파란색을 검정으로 그렸습니다.
  • 16개 프로파일은 각자의 색 모델을 색역 안쪽 무작위 색에서 평균 ΔE00 0.02~0.11로 따라갑니다. LookTable 계산은 Adobe DNG SDK의 해당 루틴과 대조했고 평균 차이는 8비트 코드 0.017~0.062였습니다.
  • 카메라 JPEG와 비교하면 평탄한 블록의 평균 ΔE00이 Natural 표본에서 0.90, Bright 표본에서 0.91이었습니다. Bright 값은 RAW에 기록된 대비 +1로 다시 계산한 것입니다. 색이나 톤을 맞추려고 조정한 값은 없습니다.
  • Lightroom은 실행하지 않았습니다. 모든 수치는 PC에서 DNG SDK의 기준 처리 방식으로 계산했습니다. 카메라 JPEG와 비교한 것은 두 모드, 두 장면(둘 다 ISO 100, 이전 펌웨어로 촬영)뿐입니다. 나머지 14개 프로파일은 카메라 출력과 비교하지 않았습니다.

확인 실행하거나 계산해 확인

  • 펌웨어의 색 조정 루틴 전체를 19개 모드에서 에뮬레이터로 실행해 색 행렬·감마 곡선·YC 변환·채도 억제 값을 얻음
  • 펌웨어 없는 색 엔진이 에뮬레이터와 10,087개 경우에서 모두 일치하고 두 경로로 만든 16개 DCP가 바이트 단위로 같음
  • 16개 프로파일 대 색 모델, Adobe SDK 루틴 대조, 카메라 JPEG 두 장과의 색차를 PC에서 계산

정적 분석 코드를 읽어 판단

  • DNG 태그를 준비하는 루틴의 BaselineExposure 계산식(공개 표본 한 장의 태그 값과 수치로 대조)
  • 펌웨어의 DNG 색 행렬 표 두 개와 행마다 나누는 채널 이득
  • 출고 설정 표(0x53c174e0)의 행과 Custom Image의 대응. 행 순서와 세 가지 정황으로 정했고 대응시키는 코드는 찾지 못함

모델 연구자가 정한 것

  • ForwardMatrix와 LookTable의 역할 나누기, LookTable을 계산하는 방법
  • 레지스터의 의미(공개 SDK 헤더 기준), 운영체제 기능의 대역, 지정한 필드 밖 입력은 0
  • ColorMatrix의 행 배율은 공개 표본 한 대에서 얻은 값

미확인 하지 않은 것

  • Lightroom·Camera Raw에서의 실제 결과
  • 다른 ISO와 조명, JPEG와 비교하지 않은 14개 프로파일, 키·하이라이트 대비·섀도 대비 설정
  • 다축 색 보정 블록의 식, 화이트밸런스 단계, 그림자 보정 때문으로 보이는 밝기 차이

배경: 카메라 조정값을 프로파일로 옮기기

RAW 파일에는 센서가 받은 빛의 양만 들어 있습니다. Lightroom은 DCP(DNG Camera Profile)라는 작은 파일에 적힌 규칙으로 이 값을 색으로 바꿉니다. 현상 화면의 “프로파일”에서 고르는 항목이 DCP입니다. 프로파일은 정해진 순서로 적용되는 태그의 묶음입니다.

  1. ForwardMatrix화이트밸런스를 맞춘 센서 RGB → XYZ D50
  2. 노출BaselineExposure + 프로파일의 BaselineExposureOffset
  3. ProfileLookTable색상·채도·명도 격자로 색을 옮김
  4. ProfileToneCurve선형 값 기준의 톤 곡선
  5. 출력 색공간sRGB, Adobe RGB 등

순서는 Adobe DNG SDK 1.7.1의 dng_render.cpp를 따랐습니다. 이 문서에서 쓰지 않는 HueSatMap 단계는 뺐습니다. 태그의 정의와 DNG 규격의 쪽 번호는 DCP 구조와 생성 도구에 있습니다.

이 사이트의 이전 시도는 바깥에서 값을 맞추는 방식이었습니다. 공개 DNG 파일에 든 색 행렬을 그대로 복사했고 톤 곡선은 색상표 차트의 무채색 패치에 맞췄습니다. 그렇게 만든 시험 DCP는 실제 Lightroom에서 Adobe의 Camera Matching 프로파일보다 카메라 JPEG에서 멀었습니다(Lightroom 색 프로파일 안내). 펌웨어의 색 행렬이 어떤 RGB를 받아 어떤 RGB를 내는지 몰라서 프로파일로 옮기지 못했습니다.

지금은 값이 카메라 자신의 조정 코드에서 나옵니다. 펌웨어 2.20의 조정 루틴을 에뮬레이터에서 실행해 색 처리 하드웨어에 들어갈 레지스터 값을 얻었습니다. 색 행렬이 화이트밸런스 뒤의 센서 RGB를 선형 sRGB로 바꾼다는 점도 계산으로 확인했습니다. 이 경로의 근거는 펌웨어 색 처리 경로에 정리되어 있습니다. 같은 계산을 펌웨어 없이 하는 색 엔진(tools/k3iii_color_engine.py)도 있습니다. 이 엔진은 공개된 색 표만 읽습니다.

쉽게 말하면

카메라는 JPEG를 만들 때 행렬 하나, 곡선 하나, 몇 가지 보정을 차례로 적용합니다. Lightroom 프로파일에도 행렬과 곡선을 넣는 칸이 있습니다. 행렬 칸에는 모든 모드에 공통인 부분만 넣습니다. 곡선은 그대로 옮깁니다. 모드마다 다른 색 변환, Lightroom이 곡선을 카메라와 다르게 적용해서 생기는 차이, 나머지 보정은 색 격자 표(LookTable)에 미리 계산해 넣었습니다.

ForwardMatrix에는 공통 행렬만 넣습니다

ForwardMatrix는 모든 Custom Image가 공유하는 센서 공통 행렬에서 만듭니다. 그래서 16개 프로파일의 ForwardMatrix가 모두 같습니다.

DNG 규격의 ForwardMatrix는 화이트밸런스를 맞춘 카메라 RGB를 XYZ D50으로 바꾸는 행렬입니다. 카메라의 색 행렬 CC0은 같은 입력을 받아 선형 sRGB를 냅니다. 이 색 행렬에는 모든 Custom Image가 공유하는 공통 행렬이 들어 있습니다. 공통 행렬은 화이트밸런스 뒤의 센서 RGB를 선형 sRGB로 바꿉니다. 색 행렬 가운데 공통 행렬 밖의 부분을 이 문서는 모드 행렬이라고 부릅니다. ForwardMatrix는 공통 행렬에 DNG SDK의 dng_color_space.cpp에 있는 sRGB→XYZ D50 행렬을 곱한 것입니다.

색 행렬의 출력이 선형 sRGB라는 근거는 AdobeRGB 설정입니다. 이 설정에서만 곱해지는 행렬 A가 표준 “선형 sRGB → 선형 Adobe RGB (1998)” 행렬과 0.000277 안에서 같았습니다. AdobeRGB로 만드는 프로파일도 ForwardMatrix는 같습니다. 행렬 A와 Adobe RGB 출력은 LookTable의 목표 색을 계산할 때 들어갑니다.

색 행렬 전체를 넣지 않는 이유

이전 설계는 색 행렬 전체(CC0)를 ForwardMatrix에 넣었습니다. 채도를 올리는 모드에서는 이 행렬이 채도 높은 색을 크게 밀어냅니다. 그런 색은 처리 경로의 작업 공간인 선형 ProPhoto RGB 밖으로 나가고 LookTable에 닿기 전에 잘립니다. 이전 설계는 카메라 색역 밖의 색을 자르지 않고 이어서 계산했습니다. 그 결과 채도 높은 파란색의 휘도가 음수가 되었고 프로파일은 이 색을 검정으로 그렸습니다. Bright, Landscape, Vibrant, Radiant, HARUBENI, KATEN, Portrait에서 모델과의 ΔE00이 최대 40~56이었습니다.

이 문제는 프로파일 16개를 각자의 색 모델과 비교하는 tools/check_profile_accuracy.py로 찾았습니다. 이전 판에 적은 평균 0.05는 Natural에서만 잰 값이었습니다. Natural에서는 이 문제가 생기지 않습니다. 지금은 공통 행렬만 ForwardMatrix에 넣습니다. 모드 행렬이 채도를 올리는 일과 카메라가 색역 끝에서 자르는 일은 LookTable 안에서 계산합니다.

  • 무채색 보존: 공통 행렬의 각 행 합은 정확히 1.0입니다(표의 값 8192). 그래서 세 채널이 같은 카메라 색은 D50 백색으로 갑니다. DNG가 ForwardMatrix에 요구하는 조건입니다.
  • 두 광원에 같은 행렬: 카메라는 화이트밸런스와 광원에 관계없이 행렬 하나를 씁니다. 화이트밸런스는 행렬 앞에서 채널 이득으로 적용됩니다. 그래서 ForwardMatrix1과 ForwardMatrix2에 같은 행렬을 넣었습니다.
  • Monochrome: 이 모드의 색 행렬은 세 행이 같아 역행렬이 없습니다. 이전 설계에서는 이 모드만 공통 행렬을 썼습니다. 지금은 모든 모드가 같은 규칙을 따릅니다.

ColorMatrix1·2는 Lightroom이 화이트밸런스를 계산할 때 쓰는 별도의 행렬입니다. 펌웨어는 DNG를 쓸 때 표 두 개의 각 행을 채널 이득으로 나눕니다. 공개 표본 #4678의 DNG 값은 표의 행에 R 0.68926, G 1.0, B 0.31733을 곱한 값이었고 도구는 이 배율을 기본값으로 씁니다. 이 이득은 기기마다 다른 보정값으로 보이지만 추적하지 않았습니다. 자기 카메라로 찍은 DNG가 있으면 --color-matrix-from으로 그 값을 복사합니다.

톤 곡선과 노출 기준

톤 곡선은 출고 설정으로 계산한 감마 곡선을 sRGB 함수로 복호한 것입니다. +0.5 EV는 펌웨어의 BaselineExposure 식에 든 1/√2를 되돌립니다.

감마 곡선을 선형 톤 곡선으로

펌웨어는 모드와 설정마다 256점 16비트 곡선(최댓값 16384)을 계산합니다. 하드웨어 표는 그 상위 10비트입니다. AdobeRGB를 고르면 펌웨어 곡선은 그대로이고 하드웨어 표만 달라집니다. 그 표는 “sRGB 표를 sRGB 함수로 복호한 뒤 감마 2.2(563/256)로 부호화한 것”과 10비트 한 단계의 0.947 안에서 같았습니다. 펌웨어 자신이 곡선의 출력을 sRGB 부호화 값으로 다룬다고 볼 근거입니다.

ProfileToneCurve는 선형 값을 받아 선형 값을 내는 곡선입니다. 그래서 감마 곡선의 출력을 sRGB 함수로 복호해 257점으로 적었습니다. 곡선은 그 모드의 출고 설정으로 계산합니다(설정이 곡선을 바꾸는 방식). 설정이 모두 0이면 Reversal Film을 뺀 모든 모드가 Natural과 같은 곡선을 씁니다. 출고 설정이 0이 아닌 모드는 곡선도 다릅니다. Bright와 Landscape는 대비 +1, Flat은 대비 −4로 계산한 곡선입니다.

+0.5 EV가 필요한 이유

펌웨어에서 DNG 태그를 준비하는 루틴은 BaselineExposure를 아래 식으로 계산합니다. 값은 분모 65536으로 저장합니다.

BaselineExposure = log2( 1448 / ( c · (maxval / (white − black)) · (G / 8192) / d ) )
  c = 2048 (특정 플래그가 켜지면 1024),  maxval = 2^bits − 1
  G = 노출 이득 (기준 8192),  d = 1 (다른 플래그가 켜지지 않으면)

1448은 1024·√2에 가깝습니다. 기준 이득에서 1448/2048은 1/√2이므로 BaselineExposure에는 −0.5 EV가 들어 있습니다. Lightroom이 이 값을 적용한 선형 값에 √2를 곱하면 카메라 감마 단계의 입력과 같아집니다. 프로파일의 BaselineExposureOffset +0.5 EV가 그 √2입니다. 이렇게 하면 톤 곡선은 기준 이득(0x2000)의 곡선 하나로 충분합니다.

총 노출이 음수일 때

노출 이득이 기준보다 크면 BaselineExposure와 +0.5 EV를 더한 총 노출이 음수가 됩니다. DNG SDK는 음수 노출을 LookTable 앞에서 적용하지 않습니다. 톤 곡선에 접어 넣어 LookTable 뒤에 적용합니다(dng_function_exposure_tone: 0.25 아래는 단순 배율, 그 위는 백색을 백색으로 두는 2차식). 그러면 LookTable은 아직 어두워지지 않은 값을 보게 됩니다.

#4678(총 노출 −0.337 EV)에서 이 영향이 보였습니다. 채도 30 이상의 평탄 블록에서 프로파일은 평균 ΔE00 1.007, 펌웨어 모델은 0.418이었습니다. 총 노출이 −0.006 EV인 Imaging Resource 표본에서는 프로파일과 모델이 거의 같았습니다.

LookTable이 맡는 것

LookTable은 공통 행렬 밖의 모든 것을 담습니다. 모드 행렬, 감마 곡선의 채널별 적용, 카메라 색역 끝의 자르기, YC 변환, 채도 억제입니다.

카메라는 색 행렬 출력의 음수 값을 0으로 자릅니다. 그 뒤 각 채널에 같은 곡선을 따로 적용합니다. 그다음 YC로 바꾸고 밝은 영역에서 색차 성분을 줄입니다. 채도 억제 이득은 가장 어두운 약 5% 구간에서 0부터 1로 오르고 전체의 약 75%까지 1을 유지합니다. 그 위에서는 84% 부근에서 약 0.84, 백색에서 약 0.27로 내려갑니다. 모든 모드가 같습니다.

Adobe의 기준 구현은 톤 곡선을 ProPhoto RGB에서 적용합니다. 가장 큰 채널과 가장 작은 채널에 곡선을 적용하고 가운데 채널은 둘 사이의 상대 위치를 유지하도록 보간합니다. 색상이 덜 틀어지도록 만든 방식입니다. 무채색에서는 두 경로가 같지만 채도가 높을수록 결과가 갈라집니다.

표를 계산하는 방법

  1. 격자 색 정하기 노출 뒤의 선형 ProPhoto 공간에서 색상 90 × 채도 30 × 명도 30 격자를 놓습니다. 명도 축은 sRGB 방식으로 부호화합니다(인코딩 1).
  2. 카메라 결과 계산 격자 색 p를 공통 행렬로 되돌려 화이트밸런스 뒤의 센서 RGB를 얻습니다. 여기에 그 모드의 색 행렬 전체를 곱합니다. 카메라와 같이 음수 출력을 0으로 자르고 감마, YC 변환, 채도 억제를 거쳐 JPEG 색을 얻습니다. 그 색을 출력 색공간에서 선형 ProPhoto로 옮겨 목표로 삼습니다.
  3. Adobe 곡선 역산 Adobe의 RGB 톤 단계를 거쳐 목표가 되는 색 q를 역함수로 찾습니다.
  4. 변화량 저장 그 격자 칸의 값은 p에서 q로 가는 색상 이동(도), 채도 배율, 명도 배율입니다.
  • 카메라 색역 끝: 표는 카메라 모델을 그대로 계산합니다. 색 행렬의 음수 출력을 0으로 자르는 단계도 카메라와 같습니다. 모드 행렬이 LookTable 안에 있으므로 채도를 올리는 단계와 그 뒤의 자르기가 표 안에서 함께 계산됩니다.
  • 명도 0 줄: 명도 0은 표의 값과 관계없이 검정입니다. 가장 어두운 색이 “변화 없음” 쪽으로 보간되지 않도록 첫째 줄의 값을 그대로 복사했습니다.
  • 채도 0 칸: 색상 이동과 채도 배율은 첫째 칸의 값을 이어 씁니다. 명도 배율은 DNG 규칙대로 1입니다.
  • Monochrome: 모든 칸의 채도 배율을 0으로 두어 모든 색을 회색으로 만듭니다.

표의 크기는 --table로 바꿀 수 있고 기본은 90×30×30입니다. 값은 4바이트 실수 3개씩이라 프로파일 하나가 약 950 KB이고 16개를 합치면 약 15 MB입니다. 아래 검증의 수치는 모두 이 기본 크기에서 얻었습니다.

  • 남은 차이: 무채색 평탄 블록에서 모델이 카메라 JPEG보다 L* 0.2~0.5 어둡습니다(8비트 한 단계 안팎). Natural 표본은 모델 −0.47, 프로파일 −0.16이고 Bright 표본은 둘 다 −0.19입니다. 두 장 모두 그림자 보정이 Auto로 촬영되었는데 에뮬레이션의 톤 조정 표는 항등입니다. 원인은 확정하지 못했습니다.
  • 프로파일과 모델의 차이: #4678의 채도 30 이상 블록에서만 크게 벌어집니다(1.007 대 0.418). 총 노출이 음수일 때 생기는 일입니다(톤 곡선과 노출 기준).
이전 실측값과 나란히 놓지 않는 이유

이 사이트의 이전 측정은 실제 Lightroom 출력의 픽셀 중앙값이었습니다. 값은 K-3 Mark III 행렬 시험 프로파일 2.028, Camera Bright 1.421, Adobe Standard 1.944입니다(K-3 III·Q7 참조 프로파일 비교). 이 문서의 값은 DNG 기준 경로와 블록 평균으로 계산했습니다. 측정 방법이 달라서 순위를 매기는 데 쓸 수 없습니다.

만드는 방법과 Lightroom에 넣기

공개된 DCP 16개를 그대로 받아 쓸 수 있습니다. 설정을 바꾼 프로파일은 펌웨어 없이 명령 한 줄로 만듭니다.

공개된 파일 받기

16개 프로파일은 저장소의 profiles/k3iii/k3iii-firmware-<mode>.dcp에 있습니다. 예를 들면 k3iii-firmware-natural.dcp, k3iii-firmware-bright.dcp입니다. 모드별 설명과 색 견본은 K-3 Mark III 색 프로파일 모음에 있습니다. 공개된 파일은 모두 출고 설정과 sRGB로 만들었습니다. Lightroom에 보이는 이름은 “K-3 III Firmware Natural”처럼 모드 이름입니다.

펌웨어 없이 만들기

tools/make_k3iii_profile.py는 공개된 색 표 k3iii-color-tables.json과 색 엔진만 씁니다. 필요한 패키지는 numpy뿐입니다.

python tools/make_k3iii_profile.py --mode natural --output Natural.dcp
python tools/make_k3iii_profile.py --all --output-dir my-profiles
python tools/make_k3iii_profile.py --from-raw IMGP0001.PEF --output IMGP0001.dcp

지정하지 않은 설정은 그 모드의 출고 값을 따릅니다. --neutral을 주면 지정하지 않은 설정이 0이 됩니다. --from-raw는 PEF나 DNG에 기록된 Custom Image, 설정, 색공간을 읽어 그 사진에 맞는 프로파일을 만듭니다. --all은 k3iii-firmware-<mode>.dcp 이름으로 16개 파일을 씁니다. --color-space adobergb이면 이름 끝에 -adobergb가 붙습니다. 같은 이름의 파일이 이미 있으면 덮어쓰지 않고 멈춥니다.

펌웨어로 만들기

tools/build_firmware_dcp.py는 펌웨어의 색 조정 코드를 에뮬레이터에서 실행해 같은 프로파일을 만듭니다. 두 도구로 만든 16개 파일은 바이트 단위로 같습니다. 펌웨어 2.20은 Ricoh의 K-3 Mark III 지원 페이지에서 받습니다(k3III_v220.zip 안의 fwdc233b.bin). 필요한 패키지는 unicorn==2.1.4와 numpy입니다.

python inspect_firmware.py fwdc233b.bin --output-dir .private/my-decode
python tools/build_firmware_dcp.py .private/my-decode/decoded.bin --mode natural --output Natural.dcp
python tools/build_firmware_dcp.py .private/my-decode/decoded.bin --all --output-dir my-profiles

표준 출력에는 프로파일마다 레지스터 해시와 파일 해시가 JSON으로 나옵니다.

Lightroom에 넣기

Adobe 도움말은 Lightroom Classic의 가져오기 경로를 이렇게 적습니다. 현상(Develop) 모듈의 프로파일 브라우저에서 + 메뉴의 “프로파일 가져오기(Import Profiles)”를 고릅니다. Adobe의 프로파일 설치 FAQ는 카메라 프로파일 폴더를 Windows C:\ProgramData\Adobe\CameraRaw\CameraProfiles, macOS ~/Library/Application Support/Adobe/CameraRaw/CameraProfiles로 적고 있습니다. 폴더에 직접 복사했다면 Lightroom을 다시 시작해야 목록에 나타납니다.

K-3 Mark III의 RAW를 열고 프로파일 브라우저에서 촬영 때의 Custom Image와 같은 이름을 고릅니다. 예를 들면 “K-3 III Firmware Natural”입니다. 카메라를 AdobeRGB로 설정했다면 --color-space adobergb로 만든 프로파일을 씁니다. 촬영 때 설정을 출고 값에서 바꿨다면 --from-raw로 그 사진에 맞는 프로파일을 만듭니다. 조색, 그림자 보정, 디지털 필터, 렌즈 보정 같은 카메라 기능은 프로파일에 들어 있지 않습니다.

주의

이 절차와 폴더는 Adobe 문서에서 옮긴 것이고 이 연구에서 실행해 보지 않았습니다. 공개한 16개 프로파일이 Lightroom에서 어떻게 보이는지도 확인하지 않았습니다. 파일 형식 작성기 tools/profile_bridge.py로 만든 이전 시험 DCP는 Lightroom Classic이 받아들였습니다(DCP 구조와 생성 도구). BaselineExposureOffset과 DefaultBlackRender 태그를 넣은 파일은 Lightroom에 넣어 보지 않았습니다.

직접 확인하는 방법

펌웨어 2.20의 카메라로 RAW+JPEG를 찍으면 자기 사진으로 같은 비교를 할 수 있습니다. 아래 명령은 RAW와 카메라 JPEG를 받아 모델과 프로파일의 색차를 계산합니다. --jpeg를 빼면 RAW 안의 미리보기를 씁니다. 모드는 메이커노트에서 읽고 읽지 못하면 --mode로 정합니다. 설정은 메이커노트 태그 0x0247에서 읽고 --contrast 같은 옵션으로 바꿀 수 있습니다. 직접 만든 DCP는 --profile로 넘깁니다. 이 도구는 펌웨어 이미지가 필요하고 추가로 rawpy와 opencv-python-headless가 필요합니다.

python tools/compare_camera_jpeg.py IMGP0001.PEF --jpeg IMGP0001.JPG --decoded .private/my-decode/decoded.bin

이 도구도 DNG 기준 경로로 계산합니다. Lightroom에서의 결과를 알려면 Lightroom에서 내보낸 파일을 카메라 JPEG와 따로 비교해야 합니다.

한계와 남은 과제

  • 표본 두 장: 두 장면 모두 ISO 100이고 카메라 펌웨어 1.01과 1.10으로 찍혔습니다. 분석한 펌웨어는 2.20입니다. 높은 ISO와 다른 조명은 없습니다. 비교한 것은 Natural(설정 모두 0)과 Bright(대비 +1)뿐입니다. 나머지 14개 프로파일은 카메라 JPEG와 비교하지 않았습니다. 일부 모드의 출고 설정에 들어 있는 키, 하이라이트 대비, 섀도 대비도 카메라 출력과 비교하지 않았습니다.
  • Lightroom 미실행: 프로파일은 DNG SDK 기준 경로(Python 모델, SDK 루틴과 대조)로만 평가했습니다. 실제 Lightroom은 처리 버전(Process Version)과 노출 처리 등 자기 방식을 씁니다. Lightroom에서 얼마나 가까운지는 Lightroom에서 재야 합니다.
  • 출고 설정 표의 대응: 표의 행을 Custom Image에 대응시키는 코드는 찾지 못했습니다. 이 표는 분석 범위 밖의 메뉴 쪽 코드가 읽습니다. 대응은 행 순서와 세 가지 정황으로 정했습니다.
  • 프로파일 밖의 기능: 조색, 그림자·하이라이트 보정, 선명도(Clarity), 디지털 필터, HDR, 렌즈 보정, 노이즈 감소, 샤프닝은 프로파일에 없습니다. 프로파일은 고정된 색 변환 하나입니다.
  • 프로파일이 없는 모드: Auto Select는 장면에 따라 모드가 바뀌고 Cross Processing과 Gold는 채널마다 다른 곡선을 씁니다.
  • 음수 총 노출: 노출 이득이 기준보다 크면 기준 경로가 LookTable을 어둡게 하기 전에 적용합니다. 채도 높은 색의 차이가 커집니다(#4678에서 1.007 대 0.418).
  • PEF의 BaselineExposure: PEF 파일에는 Lightroom이 기종별로 정한 BaselineExposure를 씁니다. 그 값이 카메라가 DNG에 적는 값과 같은지 확인하지 않았습니다.
  • 모델에 없는 단계: 다축 색 보정 블록은 효과가 보이지 않았고 식도 공개되지 않아 넣지 않았습니다. 화이트밸런스 이득과 색 행렬 앞의 처리(검정 레벨, 디모자이크)는 추적하지 않았고 비교에는 RAW의 촬영 시 값을 썼습니다.
  • 밝기 차이: 무채색 영역에서 모델이 카메라 JPEG보다 L* 0.2~0.5 어두운 원인을 찾지 못했습니다. 그림자 보정 Auto가 후보입니다.
  • ColorMatrix 행 배율: 공개 표본 한 대에서 얻었습니다. 기기마다 다를 수 있으므로 자기 DNG가 있으면 --color-matrix-from을 권합니다.
  • 에뮬레이션 조건: 운영체제 기능은 대역으로 바꿨고 지정한 필드 밖의 입력은 0입니다. 샤프닝 단계와 Make 뒤의 두 단계는 실행하지 않았습니다.

재현 방법

아래 세 명령은 펌웨어 없이 실행합니다. 공개된 DCP와 문서가 생성기 출력과 같은지, 각 프로파일이 색 모델을 얼마나 따라가는지, 색 엔진의 기록 해시가 맞는지 확인합니다.

python tools/build_profile_pages.py --check
python tools/check_profile_accuracy.py --compare analysis/k3iii-profile-accuracy.json
python tools/check_color_engine.py --compare analysis/k3iii-color-engine-checks.json
python -m unittest tests.test_color_engine tests.test_firmware_color_model -v

python tools/check_firmware_color.py .private/my-decode/decoded.bin --compare analysis/firmware-color-pipeline.json
