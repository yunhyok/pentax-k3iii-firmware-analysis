펌웨어 값으로 만드는 Lightroom 색 프로파일

이 저장소의 도구는 사용자가 가진 펌웨어 2.20에서 Custom Image 16종의 카메라 프로파일(DCP)을 만듭니다. 이 문서는 프로파일의 각 태그를 펌웨어 값에서 어떻게 얻는지 설명합니다. DNG 기준 처리 경로로 계산했을 때 카메라 JPEG와 얼마나 가까운지, 그리고 Lightroom 자체처럼 확인하지 않은 것이 무엇인지도 함께 적었습니다.

이 문서에서

  1. 배경: 카메라 조정값을 프로파일로 옮기기
  2. 프로파일의 각 태그가 어디서 오는가
  3. ForwardMatrix는 카메라의 색 행렬입니다
  4. 톤 곡선과 노출 기준
  5. LookTable이 맡는 것
  6. 검증: 모델, Adobe SDK, 카메라 JPEG와 비교
  7. 만드는 방법과 Lightroom에 넣기
  8. 한계와 남은 과제
  9. 재현 방법
  10. 근거 파일과 참고 자료

핵심 요약

  • tools/build_firmware_dcp.py는 카메라의 색 조정 코드를 PC 에뮬레이터에서 실행합니다. 그 결과로 Natural부터 FUYUNO까지 Custom Image 16종의 DCP를 만듭니다. 저장소에는 생성 도구만 있고 프로파일과 펌웨어 값은 없습니다.
  • 태그 네 개가 펌웨어 값에서 나옵니다. ForwardMatrix는 색 행렬에서, ProfileToneCurve는 감마 곡선에서 옵니다. ProfileLookTable은 두 태그로 옮기지 못한 나머지를 담습니다. BaselineExposureOffset +0.5 EV는 펌웨어의 BaselineExposure 계산식에서 나왔습니다.
  • 무작위 색으로 비교하면 프로파일과 펌웨어 색 모델의 평균 색차(ΔE00)는 LookTable이 있을 때 0.05, 없을 때 1.65입니다. LookTable 계산은 Adobe DNG SDK의 해당 루틴을 컴파일해 대조했고 차이는 8비트 한 단계의 0.41 이하였습니다.
  • 카메라가 저장한 JPEG와 비교하면 평탄한 블록의 평균 ΔE00이 Natural 표본에서 0.90, Bright 표본에서 1.38이었습니다. 색이나 톤을 맞추려고 조정한 값은 하나도 없습니다. 이 수치는 PC에서 DNG SDK의 기준 처리 방식으로 계산한 것입니다.
  • Lightroom은 실행하지 않았습니다. 카메라 JPEG와 비교한 것은 두 모드, 두 장면(둘 다 ISO 100, 이전 펌웨어로 촬영)뿐입니다. 나머지 14개 모드와 다른 조명은 비교하지 않았습니다.

확인 실행하거나 계산해 확인

  • 펌웨어의 색 조정 루틴 전체를 19개 모드에서 에뮬레이터로 실행해 색 행렬·감마 곡선·YC 변환·채도 억제 값을 얻음
  • 색 행렬의 출력이 선형 sRGB이고 감마 곡선의 출력이 sRGB 부호화 값임을 계산으로 대조
  • 프로파일 대 펌웨어 모델, Adobe SDK 루틴 대조, 카메라 JPEG 두 장과의 색차를 PC에서 계산

정적 분석 코드를 읽어 판단

  • DNG 태그를 준비하는 루틴의 BaselineExposure 계산식(공개 표본 한 장의 태그 값과 수치로 대조)
  • 펌웨어의 DNG 색 행렬 표 두 개와 행마다 나누는 채널 이득

모델 연구자가 정한 것

  • LookTable을 만드는 방법과 카메라 색역 밖의 매끈한 연장
  • 레지스터의 의미(공개 SDK 헤더 기준), 운영체제 기능의 대역, 지정한 필드 밖 입력은 0
  • ColorMatrix의 행 배율은 공개 표본 한 대에서 얻은 값

미확인 하지 않은 것

  • Lightroom·Camera Raw에서의 실제 결과
  • 다른 ISO와 조명, JPEG와 비교하지 않은 14개 모드, 슬라이더를 바꾼 프로파일
  • 다축 색 보정 블록의 식, 화이트밸런스 단계, 그림자 보정 때문으로 보이는 밝기 차이

배경: 카메라 조정값을 프로파일로 옮기기

RAW 파일에는 센서가 받은 빛의 양만 들어 있습니다. Lightroom은 DCP(DNG Camera Profile)라는 작은 파일에 적힌 규칙으로 이 값을 색으로 바꿉니다. 현상 화면의 “프로파일”에서 고르는 항목이 DCP입니다. 프로파일은 정해진 순서로 적용되는 태그의 묶음입니다.

  1. ForwardMatrix화이트밸런스를 맞춘 센서 RGB → XYZ D50
  2. 노출BaselineExposure + 프로파일의 BaselineExposureOffset
  3. ProfileLookTable색상·채도·명도 격자로 색을 옮김
  4. ProfileToneCurve선형 값 기준의 톤 곡선
  5. 출력 색공간sRGB, Adobe RGB 등

순서는 Adobe DNG SDK 1.7.1의 dng_render.cpp를 따랐습니다. 이 문서에서 쓰지 않는 HueSatMap 단계는 뺐습니다. 태그의 정의와 DNG 규격의 쪽 번호는 DCP 구조와 생성 도구에 있습니다.

이 사이트의 이전 시도는 바깥에서 값을 맞추는 방식이었습니다. 공개 DNG 파일에 든 색 행렬을 그대로 복사했고 톤 곡선은 색상표 차트의 무채색 패치에 맞췄습니다. 그렇게 만든 시험 DCP는 실제 Lightroom에서 Adobe의 Camera Matching 프로파일보다 카메라 JPEG에서 멀었습니다(Lightroom 색 프로파일 안내). 펌웨어의 색 행렬이 어떤 RGB를 받아 어떤 RGB를 내는지 몰라서 프로파일로 옮기지 못했습니다.

지금은 값이 카메라 자신의 조정 코드에서 나옵니다. 펌웨어 2.20의 조정 루틴을 에뮬레이터에서 실행해 색 처리 하드웨어에 들어갈 레지스터 값을 얻었습니다. 색 행렬이 화이트밸런스 뒤의 센서 RGB를 선형 sRGB로 바꾼다는 점도 계산으로 확인했습니다. 이 경로의 근거는 firmware-color-pipeline.html에 정리되어 있습니다.

쉽게 말하면

카메라는 JPEG를 만들 때 행렬 하나, 곡선 하나, 몇 가지 보정을 차례로 적용합니다. Lightroom 프로파일에도 행렬과 곡선을 넣는 칸이 있습니다. 행렬과 곡선은 그대로 옮길 수 있습니다. 다만 Lightroom은 곡선을 카메라와 다른 방식으로 적용합니다. 그 차이와 나머지 보정을 색 격자 표(LookTable)에 미리 계산해 넣었습니다.

프로파일의 각 태그가 어디서 오는가

행렬과 곡선은 펌웨어가 계산한 값을 단위만 바꿔 옮깁니다. 둘로 담지 못한 차이는 LookTable이 맡습니다.

ForwardMatrix는 카메라의 색 행렬입니다

카메라의 색 행렬은 화이트밸런스 뒤의 센서 RGB를 선형 sRGB로 바꿉니다. 여기에 sRGB→XYZ D50 행렬을 곱하면 ForwardMatrix가 됩니다.

DNG 규격의 ForwardMatrix는 화이트밸런스를 맞춘 카메라 RGB를 XYZ D50으로 바꾸는 행렬입니다. 카메라의 CC0 행렬은 같은 입력을 받아 선형 sRGB를 냅니다. 그래서 CC0 값을 실수로 바꾸고(256이 1.0) DNG SDK의 dng_color_space.cpp에 있는 sRGB→XYZ D50 행렬을 곱했습니다.

CC0의 출력이 선형 sRGB라는 근거는 AdobeRGB 설정입니다. 이 설정에서만 곱해지는 행렬 A가 표준 “선형 sRGB → 선형 Adobe RGB (1998)” 행렬과 0.000277 안에서 같았습니다. AdobeRGB로 만드는 프로파일은 A가 포함된 행렬에 SDK의 Adobe RGB→XYZ D50 행렬을 곱합니다.

  • 무채색 보존: 19개 모드 모두 CC0의 각 행 합이 정확히 256입니다. 그래서 세 채널이 같은 카메라 색은 D50 백색으로 갑니다. DNG가 ForwardMatrix에 요구하는 조건입니다.
  • 두 광원에 같은 행렬: 카메라는 화이트밸런스와 광원에 관계없이 행렬 하나를 씁니다. 화이트밸런스는 행렬 앞에서 채널 이득으로 적용됩니다. 그래서 ForwardMatrix1과 ForwardMatrix2에 같은 행렬을 넣었습니다.
  • Monochrome: 이 모드의 행렬은 세 행이 같아 역행렬이 없습니다. ForwardMatrix에는 모든 모드가 공유하는 공통 행렬을 넣고 채도를 없애는 일은 LookTable이 맡습니다.

ColorMatrix1·2는 Lightroom이 화이트밸런스를 계산할 때 쓰는 별도의 행렬입니다. 펌웨어는 DNG를 쓸 때 표 두 개의 각 행을 채널 이득으로 나눕니다. 공개 표본 #4678의 DNG 값은 표의 행에 R 0.68926, G 1.0, B 0.31733을 곱한 값이었고 도구는 이 배율을 기본값으로 씁니다. 이 이득은 기기마다 다른 보정값으로 보이지만 추적하지 않았습니다. 자기 카메라로 찍은 DNG가 있으면 --color-matrix-from으로 그 값을 복사합니다.

톤 곡선과 노출 기준

톤 곡선은 감마 곡선을 sRGB 함수로 복호한 것입니다. +0.5 EV는 펌웨어의 BaselineExposure 식에 든 1/√2를 되돌립니다.

감마 곡선을 선형 톤 곡선으로

펌웨어는 모드마다 256점 16비트 곡선(최댓값 16384)을 계산합니다. 하드웨어 표는 그 상위 10비트입니다. AdobeRGB를 고르면 펌웨어 곡선은 그대로이고 하드웨어 표만 달라집니다. 그 표는 “sRGB 표를 sRGB 함수로 복호한 뒤 감마 2.2(563/256)로 부호화한 것”과 10비트 한 단계의 0.947 안에서 같았습니다. 펌웨어 자신이 곡선의 출력을 sRGB 부호화 값으로 다룬다고 볼 근거입니다.

ProfileToneCurve는 선형 값을 받아 선형 값을 내는 곡선입니다. 그래서 감마 곡선의 출력을 sRGB 함수로 복호해 257점으로 적었습니다. 기준 노출에서 중간 회색의 기준점은 입력 12.5%이고 출력의 약 0.47(sRGB 코드 약 119/255)로 갑니다.

+0.5 EV가 필요한 이유

펌웨어에서 DNG 태그를 준비하는 루틴은 BaselineExposure를 아래 식으로 계산합니다. 값은 분모 65536으로 저장합니다.

BaselineExposure = log2( 1448 / ( c · (maxval / (white − black)) · (G / 8192) / d ) )
  c = 2048 (특정 플래그가 켜지면 1024),  maxval = 2^bits − 1
  G = 노출 이득 (기준 8192),  d = 1 (다른 플래그가 켜지지 않으면)

1448은 1024·√2에 가깝습니다. 기준 이득에서 1448/2048은 1/√2이므로 BaselineExposure에는 −0.5 EV가 들어 있습니다. Lightroom이 이 값을 적용한 선형 값에 √2를 곱하면 카메라 감마 단계의 입력과 같아집니다. 프로파일의 BaselineExposureOffset +0.5 EV가 그 √2입니다. 이렇게 하면 톤 곡선은 기준 이득(0x2000)의 곡선 하나로 충분합니다.

총 노출이 음수일 때

노출 이득이 기준보다 크면 BaselineExposure와 +0.5 EV를 더한 총 노출이 음수가 됩니다. DNG SDK는 음수 노출을 LookTable 앞에서 적용하지 않습니다. 톤 곡선에 접어 넣어 LookTable 뒤에 적용합니다(dng_function_exposure_tone: 0.25 아래는 단순 배율, 그 위는 백색을 백색으로 두는 2차식). 그러면 LookTable은 아직 어두워지지 않은 값을 보게 됩니다.

#4678(총 노출 −0.337 EV)에서 이 영향이 보였습니다. 채도 30 이상의 평탄 블록에서 프로파일은 평균 ΔE00 1.00, 펌웨어 모델은 0.42였습니다. 총 노출이 −0.006 EV인 Imaging Resource 표본에서는 프로파일과 모델이 거의 같았습니다.

LookTable이 맡는 것

카메라와 Adobe는 같은 곡선을 서로 다른 방식으로 적용합니다. LookTable은 격자 색마다 두 경로가 같은 색에서 끝나도록 미리 색을 옮겨 둡니다.

카메라는 출력 RGB의 각 채널에 같은 곡선을 따로 적용합니다. 그 뒤 YC로 바꾸고 밝은 영역에서 색차 성분을 줄입니다. 채도 억제 이득은 가장 어두운 약 5% 구간에서 0부터 1로 오르고 전체의 약 75%까지 1을 유지합니다. 그 위에서는 84% 부근에서 약 0.84, 백색에서 약 0.27로 내려갑니다. 모든 모드가 같습니다.

Adobe의 기준 구현은 톤 곡선을 ProPhoto RGB에서 적용합니다. 가장 큰 채널과 가장 작은 채널에 곡선을 적용하고 가운데 채널은 둘 사이의 상대 위치를 유지하도록 보간합니다. 색상이 덜 틀어지도록 만든 방식입니다. 무채색에서는 두 경로가 같지만 채도가 높을수록 결과가 갈라집니다.

표를 계산하는 방법

  1. 격자 색 정하기 노출 뒤의 선형 ProPhoto 공간에서 색상 90 × 채도 30 × 명도 30 격자를 놓습니다. 명도 축은 sRGB 방식으로 부호화합니다(인코딩 1).
  2. 카메라 결과 계산 격자 색 p를 카메라의 색 행렬 출력으로 바꾸고 감마, YC 변환, 채도 억제를 거쳐 JPEG 색을 얻습니다. 그 색을 다시 선형 ProPhoto로 옮겨 목표로 삼습니다.
  3. Adobe 곡선 역산 Adobe의 RGB 톤 단계를 거쳐 목표가 되는 색 q를 역함수로 찾습니다.
  4. 변화량 저장 그 격자 칸의 값은 p에서 q로 가는 색상 이동(도), 채도 배율, 명도 배율입니다.
  • 카메라 색역 밖: 카메라는 감마 단계 앞에서 음수 값을 0으로 자릅니다. 그대로 표를 만들면 색역 경계에서 값이 꺾여 보간이 거칠어집니다. 그래서 같은 단계를 0 아래로 매끈하게 연장해 계산했습니다(곡선은 원점 대칭, 아래쪽 자르기 없음). 카메라가 자르지 않는 색에서는 결과가 같습니다. 최종 출력 색공간으로 바꿀 때 Lightroom 쪽에서 잘립니다.
  • 명도 0 줄: 명도 0은 표의 값과 관계없이 검정입니다. 가장 어두운 색이 “변화 없음” 쪽으로 보간되지 않도록 첫째 줄의 값을 그대로 복사했습니다.
  • 채도 0 칸: 색상 이동과 채도 배율은 첫째 칸의 값을 이어 씁니다. 명도 배율은 DNG 규칙대로 1입니다.
  • Monochrome: 모든 칸의 채도 배율을 0으로 두어 모든 색을 회색으로 만듭니다.

표의 크기는 --table로 바꿀 수 있고 기본은 90×30×30입니다. 값은 4바이트 실수 3개씩이라 프로파일 하나가 약 950 KB입니다. 아래 검증의 수치는 모두 이 기본 크기에서 얻었습니다.

검증: 모델, Adobe SDK, 카메라 JPEG와 비교

프로파일은 펌웨어 모델을 평균 ΔE00 0.05 안에서 따라갑니다. DNG 기준 경로로 계산한 카메라 JPEG와의 차이는 평탄 블록 평균 0.90(Natural)과 1.38(Bright)입니다.

SDK로 확인하지 않은 부분

검사기는 libjxl·XMP가 필요한 SDK 소스를 빼고 컴파일합니다. 그래서 SDK 전체를 빌드한 것이 아닙니다. 프로파일 파일 읽기, 색 행렬 처리, 노출 처리는 SDK 코드로 확인하지 않았습니다. Lightroom도 실행하지 않았습니다. 대조 도구의 C++ 부분(tools/dng_sdk_harness.cpp)에는 Adobe 코드가 들어 있지 않습니다.

만드는 방법과 Lightroom에 넣기

펌웨어 파일을 풀고 명령 한 줄을 실행하면 16개 프로파일이 약 6초 만에 만들어집니다.

명령

펌웨어 2.20은 Ricoh의 K-3 Mark III 지원 페이지에서 받습니다(k3III_v220.zip 안의 fwdc233b.bin). 필요한 패키지는 unicorn==2.1.4와 numpy입니다.

python inspect_firmware.py fwdc233b.bin --output-dir .private/my-decode
python tools/build_firmware_dcp.py .private/my-decode/decoded.bin --mode natural --output Natural.dcp
python tools/build_firmware_dcp.py .private/my-decode/decoded.bin --all --output-dir my-profiles

--all은 “PENTAX K-3 Mark III Firmware Natural.dcp” 같은 이름으로 16개 파일을 씁니다. 같은 이름의 파일이 이미 있으면 덮어쓰지 않고 멈춥니다. 표준 출력에는 프로파일마다 레지스터 해시와 파일 해시가 JSON으로 나옵니다.

Lightroom에 넣기

Adobe 도움말은 Lightroom Classic의 가져오기 경로를 이렇게 적습니다. 현상(Develop) 모듈의 프로파일 브라우저에서 + 메뉴의 “프로파일 가져오기(Import Profiles)”를 고릅니다. Adobe의 프로파일 설치 FAQ는 카메라 프로파일 폴더를 Windows C:\ProgramData\Adobe\CameraRaw\CameraProfiles, macOS ~/Library/Application Support/Adobe/CameraRaw/CameraProfiles로 적고 있습니다. 폴더에 직접 복사했다면 Lightroom을 다시 시작해야 목록에 나타납니다.

K-3 Mark III의 RAW를 열고 프로파일 브라우저에서 촬영 때의 Custom Image와 같은 이름을 고릅니다. 예를 들면 “K-3 III Firmware Natural”입니다. 카메라를 AdobeRGB로 설정했다면 --color-space adobergb로 만든 프로파일을 씁니다. 그림자 보정, 디지털 필터, 렌즈 보정 같은 카메라 기능은 프로파일에 들어 있지 않습니다.

주의

이 절차와 폴더는 Adobe 문서에서 옮긴 것이고 이 연구에서 실행해 보지 않았습니다. 이 도구가 만든 프로파일이 Lightroom에서 어떻게 보이는지도 확인하지 않았습니다. 파일 형식 작성기 tools/profile_bridge.py로 만든 이전 시험 DCP는 Lightroom Classic이 받아들였습니다(DCP 구조와 생성 도구). 이번에 더한 BaselineExposureOffset과 DefaultBlackRender 태그를 넣은 파일은 Lightroom에 넣어 보지 않았습니다.

직접 확인하는 방법

펌웨어 2.20의 카메라로 RAW+JPEG를 찍으면 자기 사진으로 같은 비교를 할 수 있습니다. 아래 명령은 RAW와 카메라 JPEG를 받아 모델과 프로파일의 색차를 계산합니다. --jpeg를 빼면 RAW 안의 미리보기를 씁니다. 모드는 메이커노트에서 읽고 읽지 못하면 --mode로 정합니다. 직접 만든 DCP는 --profile로 넘깁니다. 추가로 rawpy와 opencv-python-headless가 필요합니다.

python tools/compare_camera_jpeg.py IMGP0001.PEF --jpeg IMGP0001.JPG --decoded .private/my-decode/decoded.bin

이 도구도 DNG 기준 경로로 계산합니다. Lightroom에서의 결과를 알려면 Lightroom에서 내보낸 파일을 카메라 JPEG와 따로 비교해야 합니다.

한계와 남은 과제

  • 표본 두 장: 두 장면 모두 ISO 100이고 카메라 펌웨어 1.01과 1.10으로 찍혔습니다. 분석한 펌웨어는 2.20입니다. 높은 ISO와 다른 조명은 없습니다. 지원 모드 16개 가운데 14개는 카메라 JPEG와 비교하지 않았습니다. 슬라이더를 바꾼 프로파일도 비교하지 않았습니다.
  • Lightroom 미실행: 프로파일은 DNG SDK 기준 경로(Python 모델, SDK 루틴과 대조)로만 평가했습니다. 실제 Lightroom은 처리 버전(Process Version)과 노출 처리 등 자기 방식을 씁니다. Lightroom에서 얼마나 가까운지는 Lightroom에서 재야 합니다.
  • 프로파일 밖의 기능: 그림자·하이라이트 보정, 선명도(Clarity), 디지털 필터, HDR, 렌즈 보정, 노이즈 감소, 샤프닝은 프로파일에 없습니다. 프로파일은 고정된 색 변환 하나입니다.
  • 음수 총 노출: 노출 이득이 기준보다 크면 기준 경로가 LookTable을 어둡게 하기 전에 적용합니다. 채도 높은 색의 차이가 커집니다(#4678에서 1.00 대 0.42).
  • PEF의 BaselineExposure: PEF 파일에는 Lightroom이 기종별로 정한 BaselineExposure를 씁니다. 그 값이 카메라가 DNG에 적는 값과 같은지 확인하지 않았습니다.
  • 모델에 없는 단계: 다축 색 보정 블록은 효과가 보이지 않았고 식도 공개되지 않아 넣지 않았습니다. 화이트밸런스 이득과 색 행렬 앞의 처리(검정 레벨, 디모자이크)는 추적하지 않았고 비교에는 RAW의 촬영 시 값을 썼습니다.
  • 밝기 차이: 무채색 영역에서 카메라 JPEG가 8비트 한두 단계 밝은 원인을 찾지 못했습니다. 그림자 보정 Auto가 후보입니다.
  • ColorMatrix 행 배율: 공개 표본 한 대에서 얻었습니다. 기기마다 다를 수 있으므로 자기 DNG가 있으면 --color-matrix-from을 권합니다.
  • 에뮬레이션 조건: 운영체제 기능은 대역으로 바꿨고 지정한 필드 밖의 입력은 0입니다. 샤프닝 단계와 Make 뒤의 두 단계는 실행하지 않았습니다.

재현 방법

검증 도구는 추출기가 만든 decoded.bin을 받습니다. RTOS 레코드의 SHA-256이 맞을 때만 실행합니다.

python tools/check_firmware_color.py .private/my-decode/decoded.bin --compare analysis/firmware-color-pipeline.json
python tools/compare_camera_jpeg.py IMGP0001.PEF --jpeg IMGP0001.JPG --decoded .private/my-decode/decoded.bin
python tools/check_dcp_against_sdk.py --sdk-source dng_sdk_1_7_1/dng_sdk/source --work-dir <비어 있는 기존 폴더> My-Natural.dcp
python -m unittest tests.test_firmware_color_model -v
  • 첫 줄은 레지스터 해시와 구조 정보를 firmware-color-pipeline.json과 대조합니다.
  • SDK 대조에는 g++와 numpy가 필요합니다. DNG SDK는 저장소에 없으므로 Adobe에서 따로 받습니다. 빌드와 실행에 약 13초가 걸렸습니다.
  • 단위 테스트 11개 가운데 하나는 환경 변수 PENTAX_K3III_DECODED가 decoded.bin을 가리킬 때만 펌웨어를 실행합니다.
