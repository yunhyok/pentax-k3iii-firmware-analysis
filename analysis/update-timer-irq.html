타이머 처리 함수의 등록과 기한이 지난 콜백의 실행

타이머 인터럽트가 들어오면 커널은 기한이 지난 예약을 큐에서 꺼내 콜백을 부릅니다. 그 처리 함수가 어떻게 등록되는지, 알람의 콜백이 어떤 단계를 거쳐 실행되는지 따라갔습니다.

이 문서에서

  1. 배경: 예약은 타이머 인터럽트에서 처리됩니다
  2. CPU 0의 초기화가 descriptor를 만들고 처리 함수를 등록합니다
  3. 기한 비교는 부호 있는 64비트 차이로 합니다
  4. 알람의 콜백은 CPU별 지연 실행 큐를 거쳐 실행됩니다
  5. 20개 사례의 구성
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • CPU 0의 초기화 경로가 메모리에 보드 descriptor를 만듭니다. 타이머 초기화는 거기 적힌 하드웨어 초기화 함수를 부르고, 타이머 처리 함수를 인터럽트 처리 함수 표에 등록합니다.
  • 처리 함수는 기한 큐의 맨 앞 노드부터 봅니다. 기한에서 현재 카운터를 뺀 값을 부호 있는 64비트 수로 보아 0 이하면 노드를 떼어 콜백을 부르고, 1 이상이면 거기서 멈춥니다.
  • 알람의 콜백은 응용 함수를 바로 부르지 않습니다. 노드를 CPU별 지연 실행 큐로 옮겨 두고, 표시와 비우기 단계를 거친 뒤에 응용 콜백에 닿습니다.
  • descriptor 만들기, 기한 처리, 지연 실행 경로를 원본 기계어로 20개 사례 실행했습니다.
  • 실제 인터럽트 진입, CPU 사이의 신호, 스케줄러는 실행하지 않았습니다. 등록 경로가 이어져 있다는 것과 인터럽트가 실제로 전달된다는 것은 다른 이야기입니다.

확인 원본 코드 실행으로 확인

  • descriptor에 적히는 값과 그 사본
  • 기한 비교와 노드 분리 순서 (12개 사례)
  • 알람 전달, 표시, 비우기, 알람 실행 함수 (4개 사례)
  • 지연 실행 큐 초기화와 표시 비트 변환

정적 분석 코드를 읽어서 판단

  • CPU 번호 검사에서 초기화 경로로 가는 분기
  • 타이머 초기화의 간접 호출과 처리 함수 등록
  • 처리 함수의 나머지 부분과 CPU 선택 코드

모델 시험 조건으로 정한 것

  • 큐, 노드, 알람 객체는 시험이 만든 값
  • 응용 콜백, lock, 인터럽트 차단·복원은 대체 함수
  • CPU 번호와 단계 사이의 순서는 시험이 지정

미확인 확인하지 않은 것

  • 실제 인터럽트 진입과 복귀
  • 다른 CPU로의 신호 전달
  • 임의의 CPU 마스크에서 큐 번호가 범위 안인지
  • 여러 CPU가 동시에 접근할 때의 안전성

배경: 예약은 타이머 인터럽트에서 처리됩니다

알람 시작 호출은 예약 시각을 계산해 기한 큐에 넣는 데서 끝납니다. 그 예약이 실제로 “울리는” 곳은 타이머 인터럽트의 처리 함수입니다. 이 함수는 틱마다 64비트 카운터를 올리고, 기한이 된 노드를 큐에서 꺼내 콜백을 부릅니다.

이 문서는 두 가지를 다룹니다. 하나는 그 처리 함수가 부팅 때 어떻게 등록되는가입니다. 다른 하나는 꺼낸 노드의 콜백이 UI 쪽 함수에 닿기까지의 경로입니다. 이 커널은 CPU 코어 여러 개에서 도는 판이어서, 알람의 콜백은 어느 CPU에서 실행할지 정한 다음 그 CPU의 대기 큐를 거칩니다.

보드 descriptor
보드마다 다른 타이머 함수의 주소와 설정값을 모아 둔 0x30바이트 구조체. 메모리(RAM)에 만들어집니다.
기한 큐
예약 노드가 기한 순서로 늘어선 연결 목록. 노드에는 기한, 콜백, 인수가 들어 있습니다.
지연 실행 큐
바로 실행하지 않고 미뤄 둔 콜백을 CPU마다 따로 모아 두는 큐. 네 개가 있습니다.
MPIDR
지금 실행 중인 CPU 코어를 구분하는 ARM 레지스터. 이 코드는 하위 2비트를 CPU 번호로 씁니다.

CPU 0의 초기화가 descriptor를 만들고 처리 함수를 등록합니다

descriptor는 펌웨어 안의 고정된 표가 아니라 부팅 중에 메모리에 채워지는 값입니다. 타이머 초기화는 그 값을 읽어 하드웨어를 설정하고 처리 함수를 등록합니다.

  1. CPU 번호 검사 초기화 함수가 MPIDR을 읽어 CPU 번호가 0이면 descriptor를 만드는 경로로 갑니다.
  2. descriptor 채우기 0x30바이트를 0으로 지운 뒤 보드 연결 함수에 넘깁니다. 이 함수가 첫 칸에 하드웨어 초기화 함수를, 이어지는 칸에 다른 보드 함수의 주소와 설정값을 적습니다. 일부 값은 다른 전역 변수로 복사됩니다.
  3. 하드웨어 초기화 타이머 초기화는 descriptor의 첫 포인터가 0이 아니면 그 함수를 부릅니다. 앞 단계가 실행되고 그 뒤에 덮어쓰지 않았다면, 불리는 함수는 레지스터에 값 다섯 개를 쓰는 함수입니다.
  4. 처리 함수 등록 descriptor에서 복사해 둔 번호를 색인으로, 처리 함수 표에 wrapper의 주소를 적습니다. wrapper는 타이머 처리 함수를 부릅니다.

“미래 노드가 맨 앞” 사례는 큐가 기한 순서로 정렬되어 있지 않으면 지난 예약이 처리되지 않는다는 것을 보여 줍니다. 정렬을 지키는 쪽은 기한 큐 삽입입니다. 다만 삽입 함수를 따로 검증한 결과도 임의의 64비트 기한에 대해 순서가 항상 일관된다거나, 삽입을 부르는 쪽이 유효한 범위만 넘긴다는 것까지 보장하지는 않습니다.

시험 조건

큐는 앞뒤 연결이 올바른 합성 목록입니다. 콜백이 현재 카운터를 바꾸는 동작은 시험이 만든 것이고, 실제로 그런 콜백을 찾았다는 뜻이 아닙니다. 처리 함수 전체가 아니라 큐를 도는 구간만 실행했으며, 그 앞의 카운터 증가와 스케줄러 관련 부분은 건너뛰었습니다.

알람의 콜백은 CPU별 지연 실행 큐를 거쳐 실행됩니다

기한 큐에서 불리는 알람의 콜백은 “전달 함수”입니다. 이 함수는 노드를 CPU 하나의 지연 실행 큐로 옮기기만 하고, 응용 콜백은 나중에 그 큐를 비우는 단계에서 불립니다.

어느 CPU의 큐로 갈지 정하기

알람을 시작할 때 노드에 적힌 콜백은 전달 함수 0x525cdfa0이고 인수는 알람 객체입니다. 전달 함수는 알람 객체의 속성에 따라 CPU 번호를 고릅니다.

  • 객체 +4의 0x20000 비트가 켜져 있으면 객체 +0x34의 마스크로 고릅니다. 마스크가 0이면 0번, 아니면 가장 낮은 자리에 켜진 비트의 번호입니다.
  • 그 비트가 꺼져 있으면 MPIDR의 하위 2비트, 곧 지금 실행 중인 CPU의 번호를 씁니다.

고른 번호의 큐는 0x54c405e8 + 12 × 번호에 있습니다. 전달 함수는 노드를 이 큐 끝에 연결하고, 노드의 콜백을 알람 실행 함수 0x525cde48로, 인수를 알람 객체로 바꿔 적습니다. 그리고 큐의 상태 바이트에서 비트 0을 켭니다.

네 사례 모두 객체 상태는 0x81에서 출발했고, 응용 콜백은 한 번씩 불렸으며, 끝난 뒤 기한 큐와 지연 실행 큐는 비어 있었습니다. 응용 콜백이 불리는 순간에는 노드가 이미 큐에서 떨어져 있었습니다.

시험 조건

기한 큐 처리 → 전달 함수 → 표시 → 고른 CPU의 비우기 → 응용 콜백 순서는 시험이 차례로 직접 불렀습니다. 처리 함수가 반환 마스크를 보고 다른 CPU에 신호를 보내거나 현재 CPU에서 비우기로 넘어가는 코드는 읽기만 했습니다. 비우기 함수는 CPU 번호를 읽는 앞부분을 건너뛰고 시험이 번호를 넣었습니다. 응용 콜백, lock, 인터럽트 차단·복원은 대체 함수입니다. UI 쪽 콜백이 이어지는 경로는 UI 타이머와 콜백에 있습니다.

참고: 공개 T-Kernel 소스와 견주면

공개 T-Kernel 2.0의 timer_handler도 카운터에 주기를 더한 뒤 큐의 맨 앞부터 보며, 기한이 현재보다 크면 멈추고, 그렇지 않으면 노드를 떼고 콜백이 있을 때만 부릅니다. 알람의 콜백 call_almhdr는 “동작 중” 비트를 끄고 등록된 함수를 확장 정보와 함께 부릅니다. 여기까지는 이 펌웨어에서 본 것과 같은 모양입니다. CPU별 지연 실행 큐는 단일 프로세서용인 공개 소스에 없는 부분입니다.

따로 잘라 낸 RTOS 파일과 통합 decoded 파일에서 결과가 같았습니다. 이 20개에는 TTimPeriod 문서의 20개 사례와 하위 시간 문서의 6,754회 실행이 들어 있지 않습니다.

공개하지 않고 보관한 자료는 디컴파일 C 7개, 보조 구간 7개, ARM 명령 582 words입니다. 디컴파일 결과가 포인터와 CPU 상태를 정확히 복원하지 못한 곳은 원본 ARM 명령으로 판단했습니다. CPU는 Unicorn의 Cortex-A15 모델입니다.

한계와 남은 과제

  • 인터럽트는 한 번도 일어나지 않았습니다. 처리 함수의 등록은 코드를 읽어 이었고, 실제 인터럽트 진입과 복귀는 실행하지 않았습니다.
  • descriptor가 나중에 덮어써지지 않는다는 것은 전제입니다. 부팅 전체를 실행하지 않았으므로 완전히 배제하지 못했습니다.
  • CPU 사이의 전달은 재현하지 않았습니다. 다른 CPU에 신호를 보내는 코드와 스케줄러는 읽기만 했습니다. 현재 CPU 번호로 큐를 고르는 경로도 실행하지 않았습니다.
  • 떼어 낸 노드 자신의 연결은 초기화되지 않습니다. 연결이 잘못되었거나 고리가 생긴 목록, 여러 CPU가 동시에 큐를 바꾸는 경우의 안전성은 확인하지 않았습니다.
  • 객체 +0x38 필드의 뜻은 모릅니다. “콜백 앞뒤로 같은지 비교한다”는 것만 확인했습니다.
  • 이 문서 범위 밖: 시간 단위와 주파수, 0이 아닌 bank 값을 만드는 코드, 리소스 레코드의 +4 위치를 쓰는 코드, 인증과 재시작, 카메라에서의 동작. 카메라 입출력과 펌웨어 빌드·기록은 하지 않았습니다.

재현 방법

입력은 따로 잘라 낸 RTOS 파일이나 통합 decoded 파일입니다. SHA-256과 적재 주소는 UI 타이머 문서의 재현 방법과 같습니다. Python 패키지 unicorn이 필요합니다.

python verify_update_timer_irq.py rtos.bin --output timer-irq.json

원본 C, ARM 목록, 바이너리, 내장 표는 공개하지 않습니다.
