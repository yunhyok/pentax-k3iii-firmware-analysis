펌웨어 재구축 · 초기 메모리 증명

RMW 48바이트를 분류하고 할당 끝 칸 4바이트를 증명하기

할당기 재현에서 초기 메모리를 읽어도 되도록 허용한 바이트가 어디에 쓰이는지 정리했습니다. 그 가운데 한 워드는 최종값이 초기 내용과 무관하다는 것을 수식 모형으로 보였습니다.

핵심 요약

  • 기존 실행 기록에서 쓰이기 전에 읽히는 48바이트를 세 구간, 여섯 개의 8바이트 레코드로 나누었습니다. 각 바이트를 처음 읽은 명령과 그 뒤의 쓰기를 정리했습니다.
  • 그중 할당 끝 칸의 첫 4바이트는 원본 명령 7개를 옮긴 수동 모형에서, 전제 아래 최종값이 초기 32비트와 관계없이 정해짐을 Z3로 증명했습니다.
  • 재현에는 decoded 이미지와 별도로 받아야 하는 과거 실행 기록(accepted31)이 둘 다 필요합니다. 원본 CPU 명령은 새로 실행하지 않습니다.
  • 나머지 44바이트는 이 증명 밖입니다. 중간 바이트 값은 초기값에 따라 달라집니다. 실제 초기 기록자는 아직 모르며 기존 56바이트 허용 목록도 그대로입니다.

확인 기록·파일 대조로 확인

  • 과거 분석 결과 전체를 다시 구성해 고정 해시와 일치
  • 48바이트 모두 첫 읽기 전에 guest 쓰기가 없고 끝에는 모두 기록됨
  • 모형 블록(명령 7개, 28바이트)의 해시

모델 모형과 전제

  • 할당 끝 칸 4바이트의 수동 모형과 네 가지 전제
  • 과거 실행의 초기 RAM 00·A5와 연구자가 고른 진입점
  • 레코드 역할 이름은 분석상 해석

미확인 확인하지 않은 것

  • 나머지 44바이트의 초기값 의존성
  • 48바이트의 실제 초기 기록자
  • MMIO, 동시 접근, fault, 전체 부팅

배경: 왜 48바이트를 따로 보는가

할당기는 빈 페이지 목록을 만들 때 관리 칸 몇 곳을 RMW로 고칩니다. 아직 아무도 쓰지 않은 칸을 읽으므로 켜질 때 남은 값이 결과에 섞일 수 있습니다. 할당 경로 재현은 이런 칸 48바이트에 연구자가 정한 값을 넣고 실행했습니다. registry 재현은 8바이트를 더해 56바이트를 허용했습니다.

더해진 8바이트는 RMW 8바이트 모형 검증에서 최종값을 증명했습니다. 이 문서는 남은 48바이트가 각각 무슨 칸인지부터 정리한 뒤 그중 한 워드를 증명합니다. 다시 만든 펌웨어에서 초기화를 줄이려면 칸마다 이런 근거가 필요합니다.

48바이트는 세 구간, 여섯 레코드

48바이트는 관리 칸 1·2번, 0xbc~0xbe번, 0x2f50번의 여섯 레코드입니다. 두 초기 패턴 모두 첫 읽기 전에는 guest 쓰기가 없었고 실행 끝에는 모두 원본 코드가 썼습니다.

주소 범위는 시작을 포함하고 끝을 뺍니다. 기준 주소는 0x56492c80, 레코드 간격은 8바이트입니다. 모든 레코드에서 첫 읽기 전의 guest 쓰기는 없었습니다. 최종 두 워드는 과거 실행 기록의 마지막 저장값입니다.

초기 RAM 00과 A5 각각에서 guest store 4,473개를 조사했습니다. 관련 메모리 사건의 (단계, PC)가 명령 기록에 정확히 한 번 나올 때만 순서를 이었습니다. 바이트별로 다시 계산한 "이미 쓰인 바이트" 집합은 기록된 미생산 바이트 수와 맞았습니다. 각 바이트의 첫 읽기·첫 기록과 이후 쓰기 순서는 projection.cases에 있습니다.

해석할 때 주의

연구자가 넣은 00·A5 패턴과 선택한 실행 구간을 실제 하드웨어의 초기 상태와 같다고 볼 수 없습니다. 읽기 기록은 모든 guest read를 담지 않습니다. 조건이 거짓인 명령도 명령 기록에 나타날 수 있어서 실제 쓰기는 별도의 메모리 사건으로 확인했습니다.

할당 끝 칸 4바이트의 최종값

대상 워드의 최종값은 (요청 페이지 수 << 2) | 3입니다. 전제 아래 초기 32비트와 관계없습니다.

대상은 [0x56493260, 0x56493264)입니다. 원본 [0x525d8774, 0x525d8790)의 A32 명령 7개(28바이트)에 대응하는 의사코드와 수동 모형을 검증했습니다. 의사코드는 분석자가 쓴 것으로 제조사 소스나 빌드 대상이 아닙니다.

byte   = (old_word & 0xff) | 3
staged = (old_word & 0xffffff00) | byte
final  = (staged & 3) | ((requested_pages & 0x3fffffff) << 2)
       = (requested_pages << 2, 32-bit) | 3

전제

  • signed 페이지 수가 2보다 커서 tail 경로에 들어옵니다.
  • LR에는 원본 0x525d8740이 만든 값, 곧 요청 페이지 수의 하위 30비트가 들어 있습니다.
  • 대상은 고정된 주소의 쓰기 가능한 일반 RAM 워드이고 little-endian입니다.
  • 명령이 순서대로 정상 완료되며 동시 쓰기·비동기 관찰·fault가 없습니다.

주소 계산과 레지스터·제어 흐름 전체는 전제로 두었고 모형에서 실행하지 않았습니다. 이 증명은 대상 4바이트만 다루며 바로 뒤 워드는 포함하지 않습니다.

전체 기록을 검사한 뒤 공개 필드만 추림

CLI는 과거 분석 결과 전체를 메모리에서 다시 만든 뒤 고정 해시와 맞을 때만 공개할 필드를 골라냅니다.

검증 CLI는 사용자가 따로 준비한 decoded 이미지와 accepted31 JSON을 읽습니다. 일반 파일인지, 크기와 SHA-256이 맞는지 확인하며 정해진 크기보다 1바이트까지만 더 읽습니다. RTOS 구간과 모형 블록의 해시를 확인한 뒤 원본 분석 결과의 모든 필드를 메모리에서 다시 구성합니다.

  1. 타입 구분 dict·list·str·int·bool을 구분하고 float·null은 허용하지 않습니다.
  2. 정규화와 비교 전체 기록을 키 정렬·공백 없는 UTF-8 JSON으로 만들어 고정 SHA-256과 비교합니다. bool을 정수로 바꾸거나 공개하지 않는 원본 역어셈블리 필드를 바꿔도 실패합니다.
  3. 공개 필드 추리기 비교를 통과해야 공개 필드를 고르는 함수가 실행됩니다.

이 검사는 기존 결과 전체가 그대로인지 확인할 뿐, 실제 초기화 경로의 증거를 더하지는 않습니다. 명령 바이트, 48개 원본 명령의 역어셈블리 목록, accepted31 전체는 배포하지 않습니다. 원본 명령 정보는 재구성과 비교 중 메모리에서만 씁니다.

공개 JSON의 historical35는 과거 결과와 그 환경의 출처입니다. current_execution은 지금 CLI·helper의 해시와 실제 실행 환경입니다. 둘을 같은 실행 기록으로 다루지 않습니다(입력·구간·고정 해시).

재현 방법

Python 3.12.3에서 확인했습니다. 실제 재구성에는 capstone 5.0.9와 z3-solver 5.3.1.0을 썼습니다. 실행 중 모듈 표시는 각각 5.0.7과 5.3.1입니다. 다른 버전에서 디코딩 표기나 solver 반례가 바뀌면 전체 비교가 실패할 수 있습니다. 기존 결과와 맞지 않는 실행을 성공으로 처리하지 않습니다.

# 펌웨어 없이 하는 기본 검사 (작업 폴더는 이미 있어야 하고 출력은 새 파일)
python -S test_verify.py --work-dir /existing/temp-parent --output /path/to/new-guards.json

# 따로 받은 두 입력으로 재검증 (원본 CPU 실행 없음)
python -m pip install -r requirements-proof.txt
python verify.py /path/to/decoded.bin /path/to/accepted31.json --output /path/to/new-result.json
python test_verify.py --work-dir /existing/temp-parent --decoded /path/to/decoded.bin --accepted31 /path/to/accepted31.json --output /path/to/new-proof-tests.json

명령은 이 패키지 폴더에서 실행하는 예입니다. 다른 위치에서는 스크립트의 절대 경로를 씁니다. decoded는 업데이트 파일 자체가 아닙니다. accepted31은 따로 받아야 하므로 decoded만으로는 이 재검증을 끝낼 수 없습니다. 정확한 해시는 source.json에 있습니다.

한계와 남은 과제

  • 이전 8바이트 증명은 다른 레코드(0xbf번)의 두 워드 ((count << 2) | 1, 0)을 다뤘습니다. 이 문서의 증명은 할당 끝 칸의 첫 워드와 flag 값 3을 다룹니다. 두 결과를 합쳐도 초기화 완료나 허용 목록 축소의 근거가 되지 않습니다.
  • registry 재현의 실행 기록에서 관측한 CP15 정지점은 0x525b5a54입니다. 그 뒤 단계는 연구자가 따로 고른 진입점이며 그 정지점에서 부팅을 이어 간 결과가 아닙니다. 이 패키지는 원본 CPU 명령을 새로 실행하지 않고 CP15·MPIDR 값을 대신 넣지도 않습니다.
  • 실제 초기 기록자, 나머지 44바이트의 초기값 의존성, MMIO·동시 접근·fault·전체 부팅 동작은 미확인입니다. 카메라 실행, 빌드, 플래시는 하지 않았습니다.
참고

바로 뒤 워드 [0x56493264, 0x56493268)는 별도 검토 기록에서 같은 종류의 전제 아래 최종값 0으로 확인됐습니다. 그 기록 기준으로 48바이트 중 조건부로 증명한 범위는 8바이트, 남은 범위는 40바이트입니다. 근거 파일은 비공개로 보관되어 이 패키지로는 재현할 수 없습니다(독립 검토 기록 요약).
