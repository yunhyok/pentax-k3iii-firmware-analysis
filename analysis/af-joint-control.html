K-3 III Joint 이벤트 0x80의 요청과 하위 제어

명령 6이 만든 요청에서 Joint 하위 제어의 첫 서비스 또는 MMIO 경계까지 원본 ARM을 실행했습니다.

이 문서에서

  1. 객체 선택과 Joint 내부의 분기는 서로 다른 값을 읽습니다
  2. 하위 함수가 준비하는 값과 종료 지점
  3. 재현과 다음 경계

객체 선택과 Joint 내부의 분기는 서로 다른 값을 읽습니다

  1. facade 명령 60x52ef89f4 → 0x52ef8c98. 능력 바이트 C+0x5272의 bit 6에 따라 Joint와 InMotor 중 하나를 고릅니다.
  2. 요청 저장과 이벤트0x52ef82b8는 호출자의 client 값이 0x5478442c와 같을 때 요청 필드를 선택된 객체에 쓰고 그 객체의 이벤트에 0x80을 넘깁니다.
  3. Joint가 요청을 읽음0x52f08828의 반복문이 합성 대기에서 받은 0x80으로 0x52f0853c → 0x52f083f0을 실행합니다. J+0x64의 word를 [J+0xd0]+0x19c4에 저장합니다.
  4. Joint 내부 모드0x52ef877c가 전역 client와 J+0x60을 읽습니다. 이 분기는 능력 바이트를 다시 읽지 않습니다.

같은 입력을 facade에 주었을 때 bit 6이 0이면 Joint의 요청과 이벤트가 바뀌었고, 1이면 별도 InMotor 객체의 요청과 이벤트가 바뀌었습니다. InMotor 대조군은 facade 반환에서 종료했습니다. Joint 요청 생산자부터 직접 시작한 별도 쌍에서는 bit 6만 바꿔도 내부 모드 2와 하위 결과가 같았습니다. client가 다르면 생산자가 0을 반환하고 이벤트를 만들지 않았으며, Joint 루프도 두 번째 대기까지 처리기에 들어가지 않았습니다.

고정 상태에서는 반환이 항상 1 또는 2입니다. 첫 호출이 1을 반환하면 바로 모드 1로 가고, 그렇지 않으면 두 번째 호출에서 2를 확인합니다. 0x52f0843c는 모드 2의 세 하위 호출이 반환한 뒤 합류하는 공통 이벤트 경로이기도 합니다. 전역이 두 읽기 사이에 바뀌는 상황은 실행하지 않았습니다.

하위 함수가 준비하는 값과 종료 지점

아래에서 p=[J+0x68], q=[J+0x6c], p2=[J+0x7c], q2=[J+0x7e]는 각각 halfword입니다. 숫자의 물리 단위는 확인하지 않았습니다.

Joint 내부 경로와 원본 실행 경계
경로원본에서 관찰한 값실행을 멈춘 곳
모드 1 · 0x52f0d83c[J+0xdc], [J+0x74], [J+0x5c], J+0x58을 넘깁니다. 호출 전에 p를 [J+0xe0]+0x2e에 저장합니다. 하위 함수는 두 번째 인자를 자체 +0x38에 쓰고 여러 상태 필드를 초기화합니다.기본 합성 상태는 0x531784b8의 channel 0 가상 서비스 분기 직전입니다. singleton이 초기화되지 않은 조건은 0x533aaeb4, 하위 객체 +0x43이 0이 아닌 조건은 0x53178788에서 먼저 멈췄습니다.
모드 2 · J+0x82 ≠ 00x52f09164가 하위 +0x58/+0x5a/+0x5c/+0x5e에 p/max(q,600)/p2/max(q2,600)을 기록합니다. +0x83도 켜진 대조군에서 이 경로가 우선했고, 공통 함수는 +0x7c에 4를 썼습니다.원본 서비스가 합성 채널 7을 사용해 주소 0x1e0020f4를 계산한 뒤 0x5334a3ac의 첫 읽기 직전에 멈췄습니다.
모드 2 · J+0x82 = 0, J+0x83 ≠ 00x52f09198가 같은 필드에 p/max(q,600)/0/max(q,600)을 기록합니다. 공통 함수는 +0x7c에 6을 썼습니다. 599·600·601 대조에서 하한 비교가 확인됐습니다.
모드 2 · 두 바이트가 00x52f0aa44가 q와 q2에 하위 +0xa0 기준을 적용합니다. J+0x78의 float bit pattern, p2, J+0x80, J+0x5c의 0/비0을 하위 상태에 저장합니다. 이 fixture는 하위 +0xd3의 초기값을 0으로 둔 경로입니다.합성 채널 7의 주소 0x1e0020ec에서 0x5334a3fc의 첫 읽기 직전에 멈췄습니다.

두 바이트가 0인 경로는 0x52f0943c에서 2p를 60,000 기준 몫과 나머지로 나누고 후속 조정을 합니다. p=29,999 / 30,000 / 30,001에서 하위 +0x36/+0x38은 각각 0/59,998, 0/60,000, 1/1이었습니다. p=30,000에서는 처음 몫 1이 나머지 0보다 커서 몫을 0으로 낮추고 나머지에 60,000을 더합니다. 이 계산의 단위와 모터 운동에 대한 의미는 확인하지 않았습니다.

정적으로는 모드 1 하위 호출이 반환한 뒤의 상태 처리와 wrapper의 조건부 0x52ef88dc tailcall도 보입니다. 이번에는 그보다 앞선 서비스에서 멈췄습니다. 반환값을 합성해 뒤의 완료 경로까지 이어 붙이지 않았습니다.

재현과 다음 경계

HQ는 원본 명령 700개와 35개 명령 구간을 별도로 대조하고, 공개 재현기를 원본 입력으로 다시 실행했습니다. 아래 결과는 합성 상태에서의 원본 명령 실행이며 카메라 동작 검증과 구분합니다.

26개 사례를 Unicorn 2.1.4 Cortex-A7에서 실행했습니다. OS 이벤트 설정·대기·지우기만 대체했습니다. 이 세 함수의 반환 때 r1–r3/r12를 덮고 NZCV를 반전한 Cortex-A7·A15 대조군에서도 사례 기록이 같았습니다. RTOS 직접 입력과 decoded 입력의 JSON은 바이트 단위로 일치했고, 실행 뒤 적재된 원본 RTOS 전체의 SHA-256도 유지됐습니다. 합성 메모리에 MMIO 페이지를 매핑하지 않았습니다.

python verify_af_joint.py /path/to/original-rtos.bin --output fresh-joint-checks.json
python verify_af_joint.py /path/to/original-decoded.bin --output fresh-decoded-joint-checks.json

다음으로 확인할 지점은 모드 1에서 0x531784b8이 참조하는 서비스 객체 +0x38과 그 vtable 슬롯 +0x40의 실제 생성자 연결입니다. 이를 추적해야 어떤 하위 서비스가 선택되는지 판단할 수 있습니다. 여기서 확인한 주소 계산과 인자는 실제 렌즈 연결, SDM·바디 모터의 대응, 물리 단위, 모터 이동이나 완료를 입증하지 않습니다.
