AF와 렌즈 제어 · Joint 쪽 하위 제어

Joint 제어 객체가 요청을 받아 모드를 고르고 값을 넘기기까지

능력 바이트의 bit 6이 0이면 AF 구동 명령은 Joint 제어 객체로 갑니다. 그 객체가 요청을 어떻게 받고, 안에서 어떤 값으로 다시 갈라지며, 하위 객체에 무엇을 넘기는지 따라갔습니다.

이 문서에서

  1. 배경: Joint 제어 객체와 이 묶음의 용어
  2. Joint 안의 모드 분기는 능력 바이트를 다시 읽지 않습니다
  3. 모드마다 하위 객체에 넘기는 값
  4. 한계와 남은 과제
  5. 검사 26건과 재현 방법
  6. 근거 파일과 참고 자료

핵심 요약

  • 능력 바이트의 bit 6이 0이면 facade가 명령 6의 요청을 Joint 제어 객체에 저장하고 이벤트 0x80을 보냅니다. Joint의 이벤트 루프가 이 이벤트를 받아 처리기를 실행하는 것까지 원본 코드 26건 실행으로 확인했습니다.
  • Joint 안에서 모드 1과 모드 2가 다시 갈립니다. 이 분기는 능력 바이트를 다시 읽지 않고 client 번호와 Joint의 상태 값만 봅니다.
  • 모드 2는 하위 객체에 값 네 개를 기록하며 일부 값에 600의 하한을 둡니다. 다른 경로는 값을 60,000 기준의 몫과 나머지로 나눕니다. 이 숫자들의 물리 단위는 모릅니다.
  • 모든 사례는 첫 하드웨어 레지스터 읽기나 다음 서비스 호출 직전에 멈췄습니다. 객체 상태와 이벤트 전달은 합성 조건입니다. 렌즈 통신과 모터 동작은 실행하지 않았습니다.

확인 원본 코드 실행으로 확인

  • facade 명령 6 → 요청 저장 → 이벤트 0x80 → Joint 처리기
  • client 번호와 상태 값에 따른 모드 1·2 선택 (9건)
  • 모드 2의 세 경로가 하위 객체에 쓰는 값, 600 하한, 60,000 분할
  • InMotor 쪽 대조군은 facade 반환까지

정적 분석 코드를 읽어 판단

  • 모드 1 하위 호출이 돌아온 뒤의 상태 처리
  • wrapper의 조건부 tailcall

모델 시험 조건으로 정한 것

  • Joint와 하위 객체의 상태 값, client 번호, 요청 값
  • OS 이벤트 설정·대기·지우기 세 함수는 stub
  • CPU는 Unicorn 2.1.4의 Cortex-A7 모델 (A15 대조)

미확인 확인하지 않은 것

  • 레지스터 읽기 이후의 동작, 렌즈 연결, 모터 이동과 완료
  • 값의 물리 단위, SDM·바디 모터와의 대응
  • 모드 1 하위 호출이 반환한 뒤의 실행

배경: Joint 제어 객체와 이 묶음의 용어

렌즈 구동 선택 문서에서 AF 구동 명령을 받는 창구(facade)가 능력 바이트의 bit 6으로 두 제어 객체 가운데 하나를 고른다는 것을 확인했습니다. 1이면 InMotor 제어 객체, 0이면 Joint 제어 객체입니다. 그 문서는 InMotor 쪽을 따라갔고 Joint 쪽 처리기의 내부는 남겨 두었습니다.

이 문서는 그 남은 쪽의 첫 구간입니다. Joint가 요청을 받고 하위 객체에 값을 넘기는 지점까지 갑니다. 하위 객체가 쓰는 서비스는 AF 서비스 객체 문서에서, 모드 1의 계산은 모드 1 문서에서 이어집니다. 주제 전체의 지도는 AF와 렌즈 제어 안내에 있습니다.

쉽게 말하면

창구 직원(facade)이 신청서를 Joint 담당자의 서류함에 넣고 벨(이벤트 0x80)을 누릅니다. 담당자는 벨을 듣고 서류를 꺼낸 뒤, 신청한 부서(client 번호)와 자기 업무 상태를 보고 처리 방식(모드 1·2)을 정합니다. 이 문서는 담당자가 아래 부서로 서류를 넘기기 직전까지 지켜본 기록입니다.

주의

Joint·InMotor는 펌웨어의 클래스 이름입니다. 이름이 “연결부”, “렌즈 안 모터”를 떠올리게 하지만 각 객체가 실제로 어느 모터를 움직이는지는 확인하지 않았습니다.

아래에서 J는 Joint 제어 객체입니다. p=[J+0x68], q=[J+0x6c], p2=[J+0x7c], q2=[J+0x7e]는 각각 halfword입니다. client 번호와 사례 값은 10진수, 주소와 오프셋은 16진수입니다.

Joint 안의 모드 분기는 능력 바이트를 다시 읽지 않습니다

bit 6은 어느 제어 객체가 요청을 받을지만 정합니다. Joint 안에서 모드 1·2를 고르는 것은 client 번호와 Joint의 상태 값입니다.

  1. facade 명령 6 facade가 능력 바이트의 bit 6에 따라 Joint와 InMotor 가운데 하나를 고릅니다.
  2. 요청 저장과 이벤트 요청 생산 함수는 호출자의 client 값이 전역 값과 같을 때만 요청 필드를 고른 객체에 쓰고 그 객체에 이벤트 0x80을 보냅니다.
  3. Joint가 요청을 읽음 Joint 이벤트 루프가 합성 대기에서 받은 0x80으로 처리기를 실행합니다. 처리기는 J+0x64의 word를 [J+0xd0]+0x19c4에 저장합니다.
  4. Joint 내부 모드 모드 결정 함수가 전역 client와 J+0x60을 읽습니다. 능력 바이트는 다시 읽지 않습니다.

고정된 상태에서는 반환이 항상 1 또는 2입니다. 첫 호출이 1을 돌려주면 바로 모드 1로 가고 아니면 두 번째 호출에서 2인지 확인합니다. 두 읽기 사이에 전역이 바뀌는 상황은 실행하지 않았습니다. 0x52f0843c는 모드 2의 세 하위 호출이 돌아온 뒤 합류하는 공통 이벤트 경로이기도 합니다.

대조 실험의 결과는 세 가지입니다. 같은 입력을 facade에 주었을 때 bit 6이 0이면 Joint의 요청과 이벤트가, 1이면 InMotor 객체의 요청과 이벤트가 바뀌었습니다. 요청 생산 함수부터 시작한 별도 쌍에서는 bit 6만 바꿔도 Joint 내부 모드 2와 하위 결과가 같았습니다. client가 다르면 생산 함수가 0을 반환하고 이벤트를 만들지 않았습니다. Joint 루프도 두 번째 대기까지 처리기에 들어가지 않았습니다.

한계와 남은 과제

  • 하위 서비스의 정체 모드 1이 0x531784b8에서 부르는 서비스 객체와 그 vtable 슬롯의 실제 생성자 연결은 AF 서비스 객체 문서에서 이어서 추적했습니다.
  • 물리 의미 계산된 레지스터 주소와 인자는 실제 렌즈 연결, SDM·바디 모터와의 대응, 물리 단위, 모터의 이동이나 완료를 입증하지 않습니다.
  • 실행하지 않은 것 레지스터 읽기, 모드 1 하위 호출의 반환 이후, InMotor 이벤트 루프, 두 읽기 사이에 전역이 바뀌는 경우는 실행하지 않았습니다.
  • 카메라 모든 결과는 합성 상태에서 원본 명령을 실행한 것이며 카메라 동작을 검증한 것이 아닙니다.
