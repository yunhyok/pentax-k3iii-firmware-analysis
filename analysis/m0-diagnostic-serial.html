부팅과 저장소 · M0 초기화 세부

M0의 진단용 직렬 출력: 속도 설정에서 문자 출력까지

부팅 초기 코드는 진단 문구를 직렬 포트로 내보냅니다. 초기 설정 가운데 어디까지가 이 직렬 출력을 위한 것인지 가려내면, 정체를 모르는 레지스터 기록의 범위가 그만큼 줄어듭니다.

이 문서에서

  1. 배경: 부팅 초기의 직렬 콘솔
  2. 직렬 설정: 상태 비트 하나로 속도와 클록 값을 고릅니다
  3. 문자 출력: 등록된 callback 아래로는 이어지지만 포맷터와의 연결은 미확정입니다
  4. 공개 USIO 드라이버와 나란히 놓으면 배치와 계산이 같습니다
  5. 검증: 원본 함수를 8가지 조건으로 실행
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • M0의 초기 설정은 pin 제어 후보 레지스터의 비트 하나를 켠 뒤 곧바로 직렬 포트 설정 함수를 부릅니다. 이 함수는 상태 비트 하나에 따라 목표 속도(115200 또는 1200)와 계산에 쓸 클록 값을 고르고, 나눗셈으로 얻은 분주값을 레지스터에 씁니다.
  • 문자를 내보내는 함수는 줄바꿈(LF) 앞에 CR을 넣고, 상태 비트를 기다렸다가 한 문자씩 데이터 레지스터에 씁니다.
  • 레지스터의 오프셋·비트 위치와 “클록 ÷ 속도 − 1” 계산은 Ricoh가 공개한 Linux의 USIO 직렬 드라이버와 같습니다. 같은 드라이버는 Linux 업스트림에도 있습니다.
  • 원본 함수를 에뮬레이터에서 8가지 조건으로 실행해 분기와 기록 순서를 확인했습니다. 실제 통신 속도, 출력 핀, 전압 파형은 확인하지 않았습니다. SRAM remap에 관한 새 근거도 아닙니다.

확인 원본 코드 실행으로 확인

  • 설정 준비·적용·활성화 함수의 분기와 레지스터 기록 순서(5사례)
  • 분주값 계산 결과 네 가지
  • 문자 출력 함수의 대기·기록 순서, CR 삽입(3사례)

  • 출력 callback의 등록, callback 아래의 호출 사슬
  • 공개 USIO 드라이버 소스와의 대조

모델 시험 조건으로 정한 것

배경: 부팅 초기의 직렬 콘솔

기기를 개발할 때는 화면이 켜지기 전 단계의 상태를 보려고 직렬 포트(UART)로 글자를 내보냅니다. M0 코드에도 보드 버전 같은 진단 문구를 출력하는 호출이 있습니다. 직렬 포트를 쓰려면 먼저 통신 속도를 맞춰야 합니다. 속도는 입력 클록을 정수로 나눠 만들고, 그 나눗수를 분주값이라고 합니다.

이 문서가 다루는 코드는 M0 보드 설정과 같은 reset 초기화에 속합니다. 그 문서에서 본 0x4dffb208의 비트 5(pin 제어 후보)를 켜는 초기 helper가 바로 뒤에 직렬 설정을 부릅니다. 이 연결을 확인하면 초기 레지스터 기록의 일부를 “직렬 출력 준비”로 분류할 수 있습니다.

USIO란

이 SoC 계열의 직렬 통신 장치를 Linux 드라이버에서 부르는 이름입니다. Ricoh가 배포한 K-3 Mark III용 Linux 커널 소스에 drivers/tty/serial/usio.c가 들어 있고, 이 저장소에도 사본이 있습니다. 같은 장치의 드라이버가 Linux 업스트림에는 milbeaut_usio.c라는 이름으로 있습니다.

주소는 M0 레코드를 정적 분석 기준 주소 0x3ffe0300에 놓았을 때의 값입니다. M0라는 이름과 CPU 코어의 관계는 M0 보드 설정의 배경에 적었습니다.

직렬 설정: 상태 비트 하나로 속도와 클록 값을 고릅니다

설정 코드는 분자(클록 값)를 분주 바이트와 목표 속도로 차례로 나누고 1을 뺀 값을 분주값 레지스터에 씁니다.

  1. 초기 helper0x3ffe0838 · pin 제어 후보에 OR 0x20
  2. 설정 준비0x3ffe7698 · 상태 비트로 목표 속도 선택
  3. 설정 적용0x3fff42e0 · 분주값 계산과 제어 레지스터 기록
  4. 출력 활성화 후보0x3fff4550 · 상태 저장과 제어 비트 설정

초기 helper는 0x4dffb208에 OR 0x20을 적용한 뒤 설정 준비 함수를 부릅니다. 설정 준비 함수는 설정값을 마련해 설정 적용 함수로 넘기고, 이어서 활성화 함수를 부릅니다. 두 호출 사이에 결과를 검사하는 분기는 없습니다. 호출 순서는 확인했지만 pin 제어 후보와 실제 전기적 출력의 연결은 확인하지 않았습니다.

코드의 계산을 식으로 쓰면 다음과 같습니다. 나눗셈은 모두 정수 나눗셈이고, 양수 입력에서 순서대로 수행하는 경로를 나타냅니다.

Q = ((N / (low8(clock_divider) + 1)) / config[0]) - 1

몫은 분자를 (D + 1)로 나눈 뒤 목표 속도로 다시 나눈 정수입니다. 둘째 줄을 예로 들면 100,000,000 ÷ 256 = 390,625이고 390,625 ÷ 115,200 = 3입니다. 넷째 줄은 32,768 ÷ 256 = 128, 128 ÷ 1,200 = 0입니다.

분주 바이트 0과 255는 양 끝을 시험하려고 넣은 값입니다. 마지막 줄처럼 나눗셈 결과가 0이 되는 조합이 실제 하드웨어에서 나오는지는 알 수 없습니다.

수치를 읽을 때 주의

115200과 1200은 목표 통신 속도 후보로 해석할 수 있지만 실제 속도를 측정한 것은 아닙니다. 100000000과 32768도 코드에 적힌 분자일 뿐이며, 이 기판의 실제 입력 클록을 확인한 값이 아닙니다. 또 상태 비트를 두 함수가 따로 읽으므로, 두 번의 읽기 사이에 하드웨어 값이 그대로라는 보장은 이 분석에 없습니다.

출력 활성화 후보 함수

0x3fff4550은 넘겨받은 두 인수를 상태 영역에 저장하고 0x4de00001의 비트 0을 켭니다. 두 번째 인수가 0이 아니면 비트 4도 켭니다. 공개 USIO 드라이버는 같은 오프셋의 같은 비트를 각각 송신 활성화(TXE)와 수신 인터럽트 허용(RIE)이라고 부릅니다. 이 해석은 레지스터 대응이 성립한다는 조건에서만 맞습니다. 초기 설정 경로에서는 두 번째 인수가 0이라 비트 0만 켭니다.

문자 출력: 등록된 callback 아래로는 이어지지만 포맷터와의 연결은 미확정입니다

출력 callback이 등록된다는 사실과 callback이 문자 기록 함수까지 내려간다는 사실은 각각 확인했습니다. 포맷터가 그 callback을 실제로 부르는 지점은 찾지 못했습니다.

줄 출력 함수와 길이 반환

줄 출력 함수 0x3ffe7710은 LF를 만나면 그 앞에 CR을 먼저 내보냅니다. 한 단계 위의 0x3ffe0860은 아래 함수의 반환값과 상관없이 요청받은 길이를 그대로 돌려줍니다. 따라서 이 반환값만으로는 실제 카메라에서 직렬 전송이 성공했는지 판단할 수 없습니다.

문자 한 개를 기록하는 함수

마지막 함수 0x3fff4800의 동작은 다음과 같습니다.

  1. 상태 대기 0x4de00003의 비트 1이 켜질 때까지 기다립니다.
  2. 기록 0x4de00004에 16비트 값을 씁니다. 값은 (읽은 16비트 & 0xfe00) | r0의 하위 16비트입니다.
  3. 다시 대기 같은 상태 비트가 켜질 때까지 다시 기다립니다.

인수 r0의 높은 비트가 켜져 있으면 기존 상위 7비트에도 OR 결과가 반영됩니다. 다만 위의 줄 출력 함수는 문자를 바이트 단위로 읽어 넘깁니다. 레지스터 배치는 공개 소스의 SSR·DR과 같지만, 읽고 쓰는 레지스터의 실제 하드웨어 동작은 따로 확인해야 합니다.

주의

이 함수에는 timeout이 없습니다. 시험에서는 RAM에 둔 상태 비트를 정해 둔 순서로 바꿔 주었습니다. 분기와 접근 순서를 확인한 것이며, 실제 송신 완료나 전압 파형을 재현한 것이 아닙니다. 상태 비트가 끝내 켜지지 않는 경우는 실행하지 않았습니다.

공개 USIO 드라이버와 나란히 놓으면 배치와 계산이 같습니다

M0 코드가 쓰는 오프셋 네 개와 비트 세 개, 그리고 분주값 계산의 꼴이 공개 드라이버와 같습니다. 이 일치가 “직렬 포트 설정”이라는 해석을 뒷받침합니다.

Ricoh의 K3mkIII_220.tar.gz 안에 있는 Linux 소스의 drivers/tty/serial/usio.c와 대조했습니다. M0 쪽은 0x4de00000을 기준으로 본 오프셋입니다.

M0 코드는 분자를 분주 바이트로 한 번 더 나눈다는 점이 다릅니다. 그 결과를 드라이버의 uartclk 자리에 놓으면 나머지 계산은 같은 꼴입니다.

이 비교로 말할 수 있는 것과 없는 것

  • 공개 소스에서 M0 쪽의 정확한 base 주소와 입력 클록을 확인한 것은 아닙니다. 레지스터 배치가 호환된다는 비교와 물리 주소가 대응한다는 주장은 구분합니다.
  • 이 경로는 0x4dffb208을 SRAM remap 레지스터로 볼 근거를 보태지 않습니다. 오히려 pinctrl 소스 비교와 직렬 설정이 바로 이어진다는 사실은 pin 기능 설정이라는 해석을 뒷받침하는 단서입니다.
  • 실제 pin 다중화 표, CLK_CRRRS의 비트 정의, 0x2000fffc와 0x0100fffc의 물리적 관계는 여전히 필요합니다.

시험 조건

M0 레코드의 원본 바이트를 Unicorn의 Cortex-M0 모델에 올렸습니다. 레지스터 주소에는 독립된 일반 RAM을 두었고, 카메라나 PC의 장치에는 접근하지 않았습니다. 상태 비트와 분주 바이트, 데이터 레지스터의 초기값, 상태 비트가 켜지는 순서는 시험용으로 정한 값입니다. 설정 사례는 원본의 나눗셈 함수와 메모리 채우기 함수까지 그대로 실행합니다.

설정 사례마다 레지스터 영역에 16회 기록이 일어났습니다. 모든 사례에서 r4–r11과 스택 포인터가 보존되었고, 실행 위치가 정해 둔 함수 범위를 벗어나지 않았습니다. M0 레코드만 넣었을 때와 압축을 푼 전체 스트림을 넣었을 때 결과가 같았습니다.

디컴파일 의사코드

설정 적용·활성화·문자 기록 함수 세 개는 angr 10.0.5의 C 형태 의사코드를 로컬에 보관했습니다. 판단 기준은 원본 Thumb 명령, literal, 분기와 호출 대상이며, 의사코드를 빌드할 수 있는 복원 소스로 다루지 않았습니다. 활성화 함수의 의사코드에 “지원하지 않는 명령”으로 남은 것은 원본의 DSB입니다. 문자 기록 함수의 의사코드가 상수를 반환하는 것처럼 보이는 것은 r0에 남은 값이며, 전송 결과를 돌려주는 것으로 해석하지 않았습니다.

독립 검토의 추가 실행

독립 검토에서는 상태 비트 24가 두 번의 읽기 사이에 0에서 1로, 1에서 0으로 바뀌는 입력을 넣었습니다. 목표 속도와 분자가 서로 다른 쪽에서 선택되었습니다. 코드가 두 값을 따로 고른다는 점을 보인 것이며, 실제 하드웨어에서 부팅 중에 이 비트가 바뀐다는 주장은 아닙니다. 이 2사례는 공개 도구의 8사례에 들어 있지 않습니다.

한계와 남은 과제

  • 양수 나눗셈 경로만 실행했습니다. 목표 속도가 0이거나 음수인 경우, 설정 구조의 선택 필드(+0x1c), 기본값이 아닌 형식 플래그는 실행하지 않았습니다.
  • printf에서 write callback으로 가는 실행 중의 호출은 증명하지 못했습니다. callback 등록과 그 아래의 출력 사슬은 따로 확인한 두 조각입니다.
  • 레지스터는 일반 RAM이었습니다. 주변장치의 동작, 시간 단위, 실제 통신 속도, 콘솔 핀, SRAM alias, 인증의 의미는 다루지 않았습니다.
  • 이 결과는 직렬 초기화의 일부를 가려낸 것이며, 수정 펌웨어가 받아들여진다는 근거가 아닙니다. 0이 아닌 bank의 실제 생산자, 리소스 레코드 +4의 값을 정하는 정책, 선행 Boot ROM의 인증과 SRAM remap은 미확정입니다(현재까지 검증한 bank 선택 조건).
  • 펌웨어 빌드와 플래시는 하지 않았습니다.

재현 방법

검증 도구는 따로 잘라 낸 M0 레코드(m0.bin)나 추출기가 만든 decoded.bin을 받습니다. 입력의 SHA-256을 확인한 뒤 실행하며, 결과 파일이 이미 있으면 멈춥니다. Python 패키지 unicorn이 필요합니다.

python verify_m0_diagnostic_serial.py m0.bin --output m0-serial-direct.json
python verify_m0_diagnostic_serial.py decoded.bin --output m0-serial-decoded.json
