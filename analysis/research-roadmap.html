시작하기 · 선행 연구

수정 펌웨어와 UI 이식을 위한 선행 연구

목표는 내용을 수정·추가·삭제한 펌웨어를 카메라에서 정상 동작시키는 것과 K-3 Mark III의 UI를 K-3 II나 Q7에 이식하는 것입니다. 일부 수치 함수는 C로 다시 컴파일해 원래 위치에 넣고 재패키징한 뒤 PC에서 비교까지 마쳤습니다. 전체 소스 재구축, 카메라 적용·부팅·복구, 대상 기종 UI 이식은 미검증입니다.

이 문서에서

  1. 목표와 현재 단계
  2. 지금까지 확인한 UI 자원 접근
  3. 업데이트와 공개 소스의 경계
  4. 다음 조사 항목과 완료 기준
  5. K-3 II·Q7 이식 비교의 출발점
  6. 근거 파일과 참고 자료

핵심 요약

  • 이 문서는 수정·이식의 검증 단계를 정리한 로드맵입니다. 제한된 구현의 PC 검증과 실제 장치에서 확인해야 할 조건을 나눠 적습니다. 색 프로파일과 AF를 포함한 네 목표의 현재 상태는 세 기종 연구 본부에 있습니다.
  • 확보한 의사코드는 원래 소스 프로젝트가 아닙니다. 타입·이름·링커 배치·라이브러리·자원 생성 도구를 복원하지 않았으므로, 지금 코드를 컴파일한다고 원본과 동등한 펌웨어가 되지는 않습니다.
  • 전체 분석과 재구축은 장기 목표로 유지합니다. 각 변경의 검증에 들어가려면 대상의 의존 범위·이미지 재구성 규칙·부팅과 복구 조건·검증 방법을 먼저 설명할 수 있어야 합니다.

확인 원본 코드·바이트로 확인

  • 아이콘 자원 접근 함수 5개의 구간과 연결
  • 무변경 재포장의 바이트 일치(round trip)
  • 수치 함수의 재컴파일·배치와 선택된 상위 호출의 PC 대조

정적 분석 코드·공개 자료를 읽어 판단

  • 업데이트 파일명 생성자와 모델 값 경로
  • 공개 Stubby OSS의 보드 설정

미확인 확인하지 않은 것

  • 실제 업데이트 수용·서명 정책·부팅·복구
  • 전체 자원·메뉴 연결과 실제 입력 인터페이스
  • 대상 기종의 이식 코드·LCD·입력·설정 유지

목표와 현재 단계

세 가지 구현 경로(전체 소스 재구축, 특정 모듈 재구현, 기존 이미지의 제한적 변경)는 필요한 근거와 검증 범위가 서로 다릅니다. 어느 경로를 택할지는 선행 분석 결과로 판단합니다.

지금까지 확인한 UI 자원 접근

아이콘 자원이 어디에 준비되고 어떻게 그려지는지는 확인했습니다. 다만 ICONBIN만 옮긴다고 UI가 작동하지는 않습니다.

패키지의 ICONBIN 자원은 26,219,192바이트입니다. 별도 RES 레코드에 폰트 경로가 있습니다. 크기와 이름만으로 자원 포맷이나 호환성을 판단하지는 않았습니다. 아이콘 그리기 경로는 리소스 슬롯 5의 준비 상태를 확인한 뒤 기준 주소를 얻습니다. 이 슬롯은 초기화 원본에 대응하며 이름 포인터가 IconBinaryData를 가리킵니다.

준비 확인 함수는 레코드가 가리키는 값이 0xa55a5aa5인지 봅니다. 이는 관찰한 자원 준비 표식일 뿐, 업데이트 패키지의 암호학적 서명 검증이 아닙니다. 이 구조에서는 자원 적재, 설명자 표, 그리기 코드, 메뉴 상태, 입력 이벤트의 인터페이스를 함께 비교해야 합니다.

업데이트와 공개 소스의 경계

파일명 생성자와 별도의 기종·버전·체크섬 판정 경로를 분석했습니다. 개별 검사를 통과한다고 최종 이미지가 받아들여지고 부팅된다는 뜻은 아닙니다.

판정 경로의 세부는 업데이트 검사와 ICONBIN에, 업데이트 전체 흐름은 업데이트 과정 안내에 있습니다.

파일명 생성자 0x52ff32ac는 런타임 값을 받아 C:\FWDC%ldB.BIN과 R:\FWDC%ldB.BIN 경로를 만듭니다. 숫자는 모델 값을 읽는 객체의 +0x18에서 옵니다. 이것은 파일명 생산자를 확인한 결과일 뿐, 업데이트 수용 판단과 이은 결과가 아닙니다.

공식 OSS 패키지의 Stubby 1.60.1도 확인했습니다. README 109~117행은 MLB01 보드의 RTOS-main 이미지 조합을 설명하며 별도 입력 MILB_SDK.bin을 요구합니다. 설정 파일 config-sc2000-rtos.h의 RTOS 주소는 0x60000000으로, 이번 분석의 RTOS 적재 주소 0x52500000과 다릅니다. 공개 보드 설정을 카메라의 실제 빌드 설정으로 취급하지 않습니다.

주의

이 설정 파일에서 RSA 서명 옵션은 주석 처리된 상태입니다. 옵션의 존재·상태만으로 카메라가 수정된 업데이트를 받아들인다는 결론은 나오지 않습니다. 입력 패키지의 32비트 합계가 0이라는 관찰도 검증 규칙 전체를 설명하지 않습니다. RTOS 업데이트 수신부, 패키지 검증기, 실제 부트로더를 각각 연결해야 합니다.

패키지를 변경 없이 다시 포장하면 바이트까지 같다는 것(round trip)과, 함수 하나를 바꿔 다시 포장하는 과정은 재구축 주제에서 다뤘습니다. 함수 배치·재패키징 · 압축 블록 보존 재패키징

다음 조사 항목과 완료 기준

완료한 개별 실험의 범위를 넓히고 실기 단계로 넘어가기 위한 항목입니다. 원본 보존과 독립 복구는 실기 검증의 선행 조건으로 유지합니다.

선행 조사 항목
우선조사 항목완료 기준
1업데이트 파일명에서 실제 검증기로파일 열기 → 헤더·기종·버전 검사 → 무결성·서명 판단 → 기록 요청의 조건부 호출 그래프
1원본을 보존하는 패키지 재구성변경 없는 round trip의 바이트 일치. 불명 영역과 실패 조건 설명(대체로 확인)
1부팅·복구 의존 관계실제 부트 단계·파티션·실패 시 복구 진입 확인. 공개 보드 예제와 기기 경로 구분
2ICONBIN 로더와 자원 포맷payload → RAM 슬롯 연결, 경계 검사, 압축·픽셀 포맷·팔레트·투명도를 설명하고 로컬 디코드로 확인
2메뉴와 입력 이벤트 (ScreenManager·TouchPanel·FontManager 문자열)화면 상태 → 메뉴 동작 → 공통 속성의 연결, 버튼·다이얼·터치 이벤트 어댑터 목록
2재빌드에 필요한 ABI·도구컴파일러 ABI·예외 처리·라이브러리·링커 배치·자원 생성 입력의 확보 여부를 모듈별 판정
3기종별 UI 비교각 기종 펌웨어를 분석해 ISA·OS·그리기 API·메모리·입력·자원 포맷 차이표 작성

실제 정상 동작의 판정에는 부팅뿐 아니라 메뉴 입력, 촬영·저장·재생, AF·노출, 전원 전환과 원본 복구 확인이 필요합니다. 실기 단계에서 쓸 검증 기준이며 지금까지 수행한 시험이 아닙니다.

K-3 II·Q7 이식 비교의 출발점

세 기종은 화면 사양부터 다릅니다. 도트 수는 표시 자원·레이아웃·입력 매핑을 따로 검토해야 하는 근거입니다. framebuffer 해상도나 메모리 포맷으로 환산하지 않았습니다.

세 기종의 후면 화면 사양
기종화면 크기도트 수(약)터치
K-3 Mark III3.2형162만정전식 터치
K-3 II3.2형103.7만없음
Q73.0형46만없음

기종 간 비교 연구에서 원본 ARM·MIPS 실행과 기종별 텍스트 그리기·메뉴 상태를 비교했습니다. K-3 III의 32비트 표면과 Q7의 인덱스 팔레트는 서로 다른 계약을 사용합니다. 화면 구성·메뉴 상태·입력을 대상 인터페이스에 맞게 구현하고 각각 검증해야 합니다. 화면 한 부분의 PC 재현은 전체 UI 런타임 이식이나 LCD 동작을 입증하지 않습니다. 기종 간 글자 전송 비교 · UI 이식 계약 · K-3 III 표면 생산자
