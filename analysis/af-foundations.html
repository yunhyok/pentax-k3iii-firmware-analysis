AF와 렌즈 제어 안내: 계산부터 렌즈 이동 완료까지

자동 초점(AF)은 초점이 얼마나 어긋났는지 계산하고, 그만큼 렌즈를 움직이고, 다 움직였는지 확인하는 일입니다. 이 주제는 그 과정이 펌웨어 안에서 어떻게 이어지는지를 K-3 Mark III, K-3 II, Q7 세 기종에서 추적합니다.

핵심 요약

  • AF 경로를 다섯 단계(초점 신호, 초점 오차 계산, 구동 요청, 렌즈·모터로 전달, 이동과 완료 확인)로 나누고, 세 기종에서 단계마다 어디까지 확인했는지 정리했습니다.
  • K-3 Mark III에서는 렌즈가 알려 준 능력 값의 한 비트가 두 제어 코드 중 하나를 고르고, 그 한쪽이 2바이트짜리 구동 요청을 만들어 큐에 넣는 데까지 확인했습니다. 원본 기계어를 PC 에뮬레이터에서 실행한 검사 1,267건과 요청 큐 검사 18건이 근거입니다.
  • 세 기종 모두 소프트웨어의 완료 통지와 렌즈의 실제 이동은 별개입니다. K-3 Mark III는 렌즈 쪽 전달을 건너뛴 경우에도 완료 통지가 돌아왔습니다.
  • 이 연구는 앞으로 있을 수 있는 변경(구형 렌즈의 구동 방식 변경, 새 AF 알고리즘)에 대비한 기초 조사입니다. 실제 렌즈를 움직인 적도, 수정한 코드를 카메라에 넣은 적도 없습니다.

한눈에 보기

세 기종 모두 가운데 단계(구동 요청과 전달)는 원본 코드를 실행해 확인했습니다. 앞쪽의 센서 신호 처리와 뒤쪽의 실제 렌즈 이동은 아직 확인하지 못했습니다.

세 기종의 펌웨어는 주소 체계와 내부 구조가 서로 다르고, Q7은 CPU 계열(MIPS)도 다릅니다. 그래서 같은 단계 이름 아래에 놓았을 뿐, 한 기종의 결과를 다른 기종의 증거로 쓰지 않습니다. 기종별 세부 비교는 세 기종 비교 절에 있습니다.

배경 지식

이 주제의 문서를 읽는 데 필요한 개념을 짧게 정리합니다. 제조사 사양은 리코이미징의 공식 자료에서 확인했습니다.

AF 한 번이 진행되는 다섯 단계

  1. 초점 신호를 얻습니다. 위상차 방식은 전용 AF 센서가 상 두 개를 읽습니다. 콘트라스트 방식은 촬영용 영상 센서의 화면을 씁니다.
  2. 초점 오차를 계산합니다. 위상차 방식은 두 상을 견줘 어긋난 양을 구하고, 이를 초점이 벗어난 정도(디포커스)로 바꿉니다.
  3. 구동 요청을 만듭니다. 렌즈가 지원하는 구동 방식에 맞는 제어 코드를 고르고, 움직일 방향과 양을 요청 값으로 만듭니다.
  4. 렌즈나 모터에 전달합니다. 바디 모터 방식은 바디가 모터를 돌려 마운트의 AF 커플러로 힘을 전합니다. 렌즈 안 모터 방식은 마운트 접점으로 렌즈에 명령을 보냅니다.
  5. 이동과 완료를 확인합니다. 명령이 받아들여졌는지, 렌즈가 멈췄는지, 초점이 맞았는지는 서로 다른 확인입니다.

위상차 AF: 한 번의 측정으로 방향과 양을 압니다

K-3 Mark III와 K-3 II는 뷰파인더로 찍을 때 위상차 AF를 씁니다. 촬영 렌즈를 지난 빛의 일부가 보조 거울을 거쳐 AF 모듈로 갑니다. AF 모듈 안의 분리 렌즈는 촬영 렌즈의 서로 다른 쪽을 지난 빛으로 상을 두 개 만들고, 줄 모양의 센서 한 쌍이 그 두 상을 읽습니다. 리코이미징의 K-3 Mark III 소개 자료는 AF 모듈의 구성품으로 콘덴서 렌즈, 색수차 보정 렌즈, 분리 렌즈, 적외선 차단 필터, AF 센서를 듭니다.

두 상이 어긋난 방향은 초점이 앞뒤 어느 쪽으로 벗어났는지를, 어긋난 양은 얼마나 벗어났는지를 알려 줍니다. 카메라는 두 신호를 서로 견주는 상관 연산으로 어긋난 양을 구하고, 이를 디포커스 양으로 바꿉니다. 그래서 렌즈를 이리저리 움직여 보지 않고도 한 번에 목표 위치로 보낼 수 있습니다. K-3 Mark III 펌웨어에서 이 단계에 쓰이는 SAD·SSD 함수와 디포커스 변환은 디스패처·셔터·AF 상관 연산 문서에서 다룹니다.

콘트라스트 AF: 선명도가 가장 높은 곳을 찾습니다

Q7의 공식 사양은 AF 방식을 콘트라스트 검출 AF로 적습니다. 콘트라스트 AF는 촬영에 쓰는 영상 센서의 화면에서 선명도를 재는 방식입니다. 화면 한 장만으로는 어느 방향으로 얼마나 벗어났는지 알 수 없어서, 렌즈를 움직이며 선명도가 오르는지 내리는지를 봅니다. Q7 문서에는 렌즈에 보내는 “검색” 명령과 렌즈의 “이동 중” 상태가 나옵니다.

이 주제에서 쓰는 말

능력 값 (capability)
렌즈가 바디에 알려 주는 정보 가운데, 어떤 구동 코드를 쓸지 정하는 데 쓰이는 값입니다. K-3 Mark III와 K-3 II에서는 한 바이트의 bit 6이 분기를 가릅니다. 제조사가 이 비트를 뭐라고 부르는지는 알지 못합니다.
요청과 큐
렌즈에 보낼 명령은 바로 전송되지 않습니다. 요청 기록으로 만들어 대기 줄(큐)에 넣으면 다른 작업(task)이 꺼내서 처리합니다.
완료 통지
요청을 처리한 코드가 요청을 낸 쪽에 “끝났다”고 알리는 호출입니다. 렌즈가 실제로 움직였는지와는 다른 사실입니다.
합성 입력, stub
실물 렌즈 대신 연구자가 정해 넣은 값이 합성 입력입니다. 실행하지 않고 기록만 하도록 바꿔 둔 함수가 stub입니다. 이 주제의 모든 실행 결과는 이 조건에서만 성립합니다.

구동 능력 통신 객체의 능력 바이트(C+0x5272) bit 6으로 InMotor·Joint 제어 객체 가운데 하나를 고릅니다. 이 비트가 SDM만을 가리킨다는 결론은 아직 없습니다. 명령 0x8205의 응답을 렌즈 객체의 +6에 저장합니다. bit 6 판정 뒤 렌즈 명령을 보내는 쪽과 바디 드라이버를 준비하는 쪽으로 갈립니다. AF 사용 가능 판정 함수는 통신 상태 bit 3과 기능 그룹 2의 연산 4를 모두 확인합니다. 검색 명령의 전송 검사는 따로 있습니다. 기능 맵을 읽었다는 표시(map-read-OK)가 1일 때 연산 허용 여부만 보고, 통신 비트는 다시 확인하지 않습니다.
명령 인자 명령 0x8900을 만드는 함수가 값의 하위 14비트와 방향 플래그를 묶어 2바이트로 만듭니다. 값의 실제 거리 단위와 방향의 극성은 확정하지 못했습니다. 별도의 생산 함수와 소비 함수가 펄스 상태를 구동 요청으로 바꿉니다. 렌즈 쪽 계산에는 명령 0x8211의 2바이트 응답도 씁니다. 검색·정지·위치 구동 메시지는 각각 6·8·7입니다. mode 3 검색은 별도의 VD 동기화 처리를 거칩니다.
완료의 의미 객체 선택과 명령 작성, 요청 큐, 물리 전송을 서로 다른 단계로 나눠 조사합니다. 작성된 바이트나 완료 통지만으로 이동이 끝났다고 판단하지 않습니다. 구동 준비와 계산 상태의 전달을 확인했습니다. 실제 이동량, 모터 정지, 초점 판정은 따로 검증해야 합니다. 큐의 응답과 라이브 뷰의 이동(motion) 상태를 서로 다른 경로에서 처리합니다. 요청 조건에 따라 소프트웨어 완료 알림을 바로 보내는 분기도 있습니다.
재현 근거 선택 587건 + 명령 408건 + 능력 값 기록 272건 = 1,267건. RTOS 추출본과 전체 디코딩 이미지에서 각각 실행해 일치했습니다. 요청 큐 검사 18건은 따로 셉니다. 능력 조회 8건 + 바디 제어 14건 + 렌즈 제어 3건, 그리고 먼저 수행한 구동 선택 사례. 다시 실행해 일치했습니다. 기능 탐색·캐시·속도·응답·완료 합계 32건. 원본 MIPS 코드를 VEX로 실행했고 다시 실행해 통과했습니다.

표의 결과는 합성 메모리에서 원본 코드를 실행해 얻었습니다. 실물 렌즈의 응답은 측정하지 않았습니다. 검사별 입력과 한계는 af-foundations.json에 있습니다.

비교할 때 지킨 원칙

  • 기종 사이에 필드의 비트 위치나 명령 번호가 비슷해도 같은 ABI라고 가정하지 않습니다. 펌웨어 버전, 주소 체계, 호출 인자, 객체 수명이 함께 맞아야 합니다.
  • 능력 값을 바꿔도 없는 기계 연결부가 생기지 않고, 맞지 않는 광학계가 맞게 되지도 않습니다.
  • 큐가 요청을 받았다는 것, 전송 응답이 왔다는 것, 모터가 멈췄다는 것, 광학적으로 초점이 맞았다는 것은 서로 다른 관측입니다.
  • 나중에 초점 추정 알고리즘을 바꾸더라도 렌즈의 한계값, 방향, 취소, 늦게 온 응답, 시간 초과 처리는 그대로 지켜야 합니다.

구형 렌즈의 구동 방식을 바꾸는 연구에 필요한 것

이 주제는 나중에 구동 방식이나 AF 알고리즘을 바꾸게 될 경우를 위한 준비입니다. 지금은 계산, 렌즈의 구동 능력, 명령 전달, 실제 이동을 나눠 각 단계 사이의 조건을 확인합니다.

특정 렌즈를 정하거나 모터를 움직이지 않아도 이 기초 조사는 계속할 수 있습니다. 다만 아래 세 가지 공식 자료를 보면 “능력 비트 하나만 바꾸면 된다”고 볼 수 없습니다.

  • 두 방식을 모두 지원하는 렌즈가 실제로 있습니다. 리코이미징은 구형 smc PENTAX-DA★ 16–50mm F2.8 ED AL [IF] SDM이 SDM 지원 바디에서는 렌즈 안의 SDM으로, 지원하지 않는 바디에서는 바디 모터로 AF를 한다고 설명합니다. 두 방식을 견줄 수 있는 사례입니다. 그렇다고 모든 SDM 렌즈에 기계 연결부가 있다는 뜻은 아닙니다. (공식 렌즈 설명)
  • SDM·DC·PLM은 렌즈 안의 모터 방식이고 Body AF는 바디 모터 방식입니다. 구동 정책을 바꾸려면 렌즈의 실제 연결 구조, 바디의 지원 여부, 구동 단위, 정지 조건을 확인해야 합니다. 능력 비트 하나를 바꾸는 것만으로 이 조건이 채워지지는 않습니다. (공식 초점 구동 정의)
  • Q7에는 K-3 계열의 바디 구동을 그대로 옮길 수 없습니다. Q7 공식 호환표에서 K 마운트용 Adapter Q의 초점 방식은 수동입니다. Q7 연구는 Q 렌즈의 명령, 능력, 이동 상태를 따로 확인합니다. (Q7 공식 렌즈 호환표)

읽는 순서

AF가 진행되는 순서대로 읽으면 이해하기 쉽습니다. 다른 두 기종의 문서는 같은 질문을 각 기종에서 확인한 기록입니다.

  • 1 · 계산

    디스패처·셔터·AF 상관 연산

    초점 오차는 어떤 연산으로 구하는가?

    상관 연산의 SAD·SSD 함수를 실행해 기준식과 일치시켰습니다. 디포커스 변환까지의 호출 순서는 정적 분석입니다.

  • 2 · 구동 요청

    렌즈 구동 선택·명령·응답

    어느 제어 코드를 쓸지 어디서 정하고, 렌즈에 보낼 값은 어떻게 만드는가?

    능력 바이트의 bit 6이 InMotor·Joint 객체를 고르고, InMotor 쪽이 명령 0x8900의 2바이트를 만듭니다. 검사 1,267건.

  • 3 · 전달과 완료

    AF 요청 큐와 완료 통지

    만든 요청은 누가 꺼내 처리하고, 완료 통지는 무엇을 뜻하는가?

    요청은 32칸짜리 슬롯에 복사되어 큐로 넘어갑니다. 전달을 건너뛴 경우에도 완료 통지가 왔습니다. 검사 18건.

  • K-3 II

    K-3 II의 AF 안내

    K-3 II에서는 같은 분기가 어떻게 생겼는가?

    렌즈 응답의 bit 6에 따라 렌즈 명령과 바디 드라이버로 갈립니다. 카운터와 보정값에서 구동 요청까지 이어 확인했습니다.

    • 렌즈 능력과 구동 분기
    • AF 요청 계산과 구동 준비
    • AF 카운터와 보정값
  • Q7

    Q7의 AF·렌즈 안내

    콘트라스트 AF 기종에서는 명령과 완료를 어떻게 구분하는가?

    명령의 처리 결과, 캐시에 기반한 이동 완료, AF 시퀀스 종료가 서로 다른 판정임을 확인했습니다.

    • AF 명령과 완료 판정
    • Loader 입력 검증과 렌즈 정책
    • 저장 경계와 렌즈 준비 상태

세 기종의 목표와 진행 상태는 세 기종 연구 본부의 AF 항목에 한데 정리되어 있습니다.

한계와 다음에 확인할 것

이 주제에 포함되지 않은 것

렌즈별 패치, 렌즈 EEPROM 수정, 카메라에 설치하는 시험, 모터를 구동하는 시험은 하지 않았습니다. 실제 이동과 촬영 검증은 나중의 구현 단계에서 할 일로 남아 있습니다.

  • 초점 추정값이 명령 인자로 바뀌는 모든 경로에서 부호, 단위, 제한값을 기록합니다.
  • 렌즈 연결이 바뀐 경우, 전송이 실패한 경우, 응답이 늦은 경우, 취소한 뒤의 상태를 구분하고 기존 값이 보존되는지 확인합니다.
  • 큐의 응답, 모터 상태, 광학적 초점이라는 세 가지 완료 조건을 따로 재현합니다.
  • 나중에 알고리즘을 바꿀 때는 확인한 호출 규약과 렌즈 제한을 지키는 가장 작은 사례부터 검증합니다.
