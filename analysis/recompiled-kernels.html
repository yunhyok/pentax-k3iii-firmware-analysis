펌웨어 재구축 · 1단계

수치 함수 두 개를 C로 다시 만들어 원본과 대조하기

펌웨어를 고치려면 먼저 “원본과 똑같이 동작하는 코드를 직접 만들 수 있는가”를 확인해야 합니다. 가장 작은 단위인 계산 함수 두 개로 이 질문을 시험했습니다.

이 문서에서

  1. 배경: 왜 작은 함수부터 다시 만드는가
  2. 검증 방법: 원본과 새 코드를 같은 조건에서 실행
  3. 결과: 237개 입력 모두 일치
  4. 펌웨어에 넣기 전에 남은 확인
  5. 재현 방법
  6. 근거 파일과 참고 자료

핵심 요약

  • 원본 기계어를 참고해 C 함수 두 개를 새로 작성했습니다. AF에서 두 신호의 차이를 재는 SAD·SSD 함수와, 색 변환 행렬을 곱하는 Q13 3×3 행렬 곱 함수입니다.
  • 이 C 코드를 ARM 기계어로 컴파일한 뒤, PC의 CPU 에뮬레이터에서 원본 기계어와 같은 입력 237개를 넣어 실행했습니다. 출력 바이트가 모두 같았고 Python으로 쓴 기준식과도 일치했습니다.
  • 확인한 것은 함수 하나를 따로 떼어 실행한 결과입니다. 펌웨어에 넣거나 카메라에서 실행하지는 않았습니다. 실행 시간과 일부 CPU 플래그는 비교하지 않았습니다.

확인 원본 코드 실행으로 확인

  • SAD·SSD 131개, Q13 행렬 곱 106개 입력에서 출력 바이트 일치
  • 두 코드 모두 지정된 출력과 스택 작업 영역에만 기록
  • 호출 규약이 보존하라고 정한 레지스터(r4–r11, d8–d15, SP) 보존

모델 시험 조건으로 정한 것

  • 입력은 직접 만든 합성 값(경계값과 난수)
  • 쓰지 않는 첫 인수에는 매핑하지 않은 주소를 넣음
  • CPU는 Unicorn의 Cortex-A7 모델

미확인 확인하지 않은 것

  • 개수가 0이거나 음수일 때 원본의 동작
  • 실행 시간, 모든 CPU 플래그의 동일성
  • 펌웨어 통합, 카메라에서의 AF·색 출력

배경: 왜 작은 함수부터 다시 만드는가

제조사의 원본 소스 코드는 공개되어 있지 않습니다. 펌웨어를 고치는 방법은 두 가지입니다. 기계어 몇 바이트를 직접 바꾸거나, 함수를 C로 새로 작성해 컴파일한 결과로 원본 함수를 대체하는 것입니다. 두 번째 방법이 유지하기 쉽지만 새 코드가 원본과 정확히 같은 결과를 낸다는 것을 먼저 증명해야 합니다.

그래서 다른 함수를 부르지 않고 계산만 하는 작은 함수(leaf 함수) 두 개를 골랐습니다. 입력과 출력이 분명해서 원본과 새 코드를 나란히 실행해 비교하기 쉽습니다.

대상 함수 두 개
함수하는 일펌웨어에서 쓰이는 곳
SAD·SSD16비트 값 배열 두 개를 받아 원소별 차이의 절댓값 합(SAD)과 제곱 합(SSD)을 구합니다. 두 신호가 얼마나 닮았는지 재는 기본 연산입니다.AF의 상관 연산 (디스패처·셔터·AF)
Q13 3×3 행렬 곱3×3 행렬 두 개를 곱합니다. 값은 Q13 고정소수점이라서 곱한 뒤 반올림하고 13비트만큼 내립니다.색공간 변환 행렬 준비 (색 처리 알고리즘)

검증 방법: 원본과 새 코드를 같은 조건에서 실행

새 코드와 원본 코드를 서로 다른 주소에 올려 놓고 같은 입력으로 각각 실행한 뒤 출력 바이트를 비교했습니다.

실행할 때마다 확인한 조건

출력값만 보지 않았습니다. 함수가 주변 상태를 망가뜨리지 않는지도 매번 검사했습니다.

  • 출력: Python 기준식의 결과와 바이트 단위로 같아야 합니다. 정해진 출력 위치에 빠짐없이 쓰였는지도 확인했습니다.
  • 쓰기 범위: 출력 버퍼와 스택 작업 영역 밖에는 쓰지 않아야 합니다.
  • 읽기 범위: 넘겨준 버퍼, 스택, 그리고 원본 SAD·SSD가 쓰는 128바이트 마스크 표만 읽어야 합니다.
  • 실행 범위: 함수 구간 안에서만 실행되고 정해 둔 복귀 주소로 돌아와야 합니다.
  • 보존 레지스터: ARM 호출 규약(AAPCS32)이 보존하라고 정한 r4–r11, d8–d15, SP와 호출자의 스택 인수, CPSR 제어 비트가 그대로여야 합니다.
비교 기준에서 뺀 것

실행 시간과 계산 과정에서 바뀌는 조건 플래그 전체는 비교하지 않았습니다. 쓰지 않는 첫 인수(r0)에는 일부러 매핑하지 않은 주소를 넣어, 두 코드 모두 이 인수를 건드리지 않는다는 점을 확인했습니다.

결과: 237개 입력 모두 일치

함수별 측정값
함수원본 주소 → 시험 주소코드 크기 (원본 → 새 코드)일치한 입력스택 사용 깊이
SAD·SSD0x52c73190 → 0x62000000216 → 84바이트131개12 → 16바이트

코드 크기는 함수 구간의 기계어 크기입니다. 원본 SAD·SSD가 따로 참조하는 128바이트 마스크 표는 포함하지 않았습니다. 스택 사용 깊이는 함수에 들어올 때의 스택 포인터 아래로 가장 멀리 쓴 위치입니다.

크기가 줄어든 이유

원본 SAD·SSD는 여러 값을 한 번에 처리하는 NEON 명령을 씁니다. 새 코드는 값을 하나씩 처리하는 단순한 반복문이라 더 작습니다. 결과는 같지만 속도는 다를 수 있으며 속도는 이번에 측정하지 않았습니다.

SAD·SSD 함수

입력은 부호 없는 16비트 배열 두 개(r1, r2)와 양수인 원소 개수(r3)입니다. 결과는 스택으로 넘긴 포인터 두 곳에 32비트 값으로 저장됩니다.

  • 시험한 길이: 1~17개, 그리고 8개 단위 경계 앞뒤(23·24·25, 31·32·33, … 1023·1024·1025). 길이마다 값이 모두 같은 경우, 차이가 최대인 경우, 번갈아 바뀌는 경우, 난수를 넣었습니다.
  • 32비트를 넘는 경우: 모든 차이가 65,535일 때 길이 65,537의 SAD는 0xffffffff입니다. 길이 65,538에서는 32비트를 넘어 65534가 됩니다. 원본과 새 코드 모두 넘친 값을 그대로 잘라 냅니다.
  • 패딩: 원본은 마지막 NEON 벡터를 읽을 때 배열 끝을 조금 넘겨 읽을 수 있습니다. 그래서 원본에는 0이 아닌 패딩 값을 붙여 주고 새 코드에는 유효한 원소만 주었습니다. 결과는 같았습니다.

Q13 3×3 행렬 곱 함수

입력은 행 우선으로 놓인 부호 있는 16비트 행렬 두 개(r2, r3)이고 출력 행렬은 r1이 가리킵니다. 원소마다 세 곱의 합에 4,096(Q13에서 0.5)을 더한 32비트 값을 오른쪽으로 13비트 논리 시프트하고 하위 16비트를 저장합니다.

  • 시험한 입력: 단위 행렬, 영 행렬, 양수·음수 반올림 경계, 합이 32비트를 넘는 경우, 결과가 16비트를 넘는 경우, 난수 96개.
  • 범위를 넘을 때: 결과가 16비트 범위를 넘으면 최댓값으로 고정(포화)하지 않고 하위 16비트만 남깁니다. 원본과 새 코드가 같게 동작합니다.
해석의 한계

출력이 같다는 사실만으로는 계산 중간의 시프트 방식이나 누산 폭까지 같다고 말할 수 없습니다. 그 부분의 해석은 원본 명령 분석에 근거합니다.

펌웨어에 넣기 전에 남은 확인

이 결과는 “함수 하나를 떼어 놓았을 때 같다”는 것까지입니다. 실제 펌웨어에 넣으려면 호출하는 쪽의 조건을 더 확인해야 합니다.

  • 실제 호출마다 버퍼의 수명·정렬·겹침, 길이의 범위, 스택 여유가 맞는지
  • 이 함수를 주소로 간접 호출하는 곳이 더 있는지
  • NEON을 쓰는 원본과 값을 하나씩 처리하는 새 코드의 실행 시간 차이가 AF의 처리 시간 예산 안에 드는지
  • 실행 주소 배치와 분기 연결, 이미지 검증과 부팅, 실기에서의 AF·색 출력

Q13 행렬 곱 함수를 원래 자리에 넣고 다시 포장하는 과정은 재컴파일 함수 배치·재패키징에서 이어집니다. 통합 전에 확인할 항목 전체는 수정·이식 선행 연구에 정리했습니다.

재현 방법

검증기는 추출기가 만든 decoded.bin 또는 따로 잘라 낸 rtos.bin을 입력으로 받습니다. 입력 RTOS의 SHA-256이 아래 값과 같을 때만 실행합니다.

RTOS SHA-256

RTOS 적재 기준 주소
0x52500000
Python 패키지
unicorn==2.1.4, pyelftools==0.33
컴파일러
Zig 0.15.2 (x86_64 Windows 배포본). 공식 배포 색인의 ZIP SHA-256 3a0ed1e8799a2f8ce2a6e6290a9ff22e6906f8227865911fb7ddedc3cc14cb0c과 일치할 때만 사용
python tools/verify_recompiled_kernels.py .private/my-decode/decoded.bin "<Zig 폴더>/zig.exe"

검증기는 컴파일러 실행 파일의 해시를 확인한 뒤 아래 옵션으로 컴파일합니다. 만들어진 ARM A32 리틀엔디언 ELF 객체에서 두 함수만 꺼내 씁니다. 함수 코드에는 재배치 항목이나 외부 심볼 참조가 없었습니다.

zig cc -target arm-freestanding-eabi -mcpu=cortex_a7 -marm -std=c11 \
  -ffreestanding -fno-builtin -fno-stack-protector \
  -fno-unwind-tables -fno-asynchronous-unwind-tables -ffunction-sections \
  -Oz -Wall -Wextra -Werror \
  -c source/reconstructed/numeric_kernels.c -o .private/hq-compile/numeric_kernels.o

ELF 객체, 함수별 바이너리, 빌드 캐시는 .private/hq-compile/에 남고 공개하지 않습니다. 공개 결과에는 해시와 합성 사례만 들어 있습니다.

근거 파일과 참고 자료

  • source/reconstructed/numeric_kernels.c — 새로 작성한 C 소스
  • recompiled-kernels.json — 사례 237개의 입력 해시·출력, 구간, 컴파일러 정보
  • tools/verify_recompiled_kernels.py — 빌드와 격리 실행, 검사 코드
  • numerical-checks.json — 앞서 원본 함수만 실행해 얻은 수치 검증
  • deep-evidence.json — 원본 주소, 호출 위치, 구간 해시
