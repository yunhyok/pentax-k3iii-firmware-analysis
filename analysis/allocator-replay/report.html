펌웨어 재구축 · 시작 과정 재현

설정에서 첫 task의 스택까지, 원본 할당 경로를 다시 실행하기

펌웨어를 다시 만들어 부팅시키려면 RTOS가 시작할 때 메모리를 어떻게 나눠 주는지부터 알아야 합니다. 원본 할당기 코드를 PC 에뮬레이터에서 실행해 설정값이 첫 task의 스택 버퍼가 되기까지를 따라갔습니다.

이 문서에서

  1. 배경: 할당기와 task 스택, 그리고 초기 메모리
  2. 할당 경로: 설정값이 스택 포인터가 되기까지
  3. 일곱 실행 조건과 멈춘 위치
  4. 초기 메모리와 무관함을 증명한 다섯 경로
  5. 이 재현이 이어받은 이전 분석
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 원본 RTOS의 할당 코드를 구간별로 실행해 설정 읽기 → 페이지 영역 준비 → task 표 300개 할당 → 첫 task 스택 확보까지 이었습니다.
  • 일곱 실행 조건 가운데 네 조건에서 원본 할당기가 첫 task의 스택(24,576바이트 요청)을 확보했습니다. 초기 메모리를 네 가지로 바꿔도 반환 포인터와 최종 관리 정보는 같았습니다.
  • 할당기가 아직 아무도 쓰지 않은 메모리를 읽고 고쳐 쓰는 다섯 경로는 수식 모형으로 옮겼습니다. Z3로 검사한 결과 최종 필드는 초기값과 관계없이 같았습니다.
  • 연속 부팅을 재현한 결과는 아닙니다. 단계마다 진입점을 연구자가 골랐고 초기 메모리도 연구자가 정했습니다. 실행은 프로세서 번호를 읽는 명령 직전에서 멈췄으며 task 생성 완료나 카메라 부팅을 뜻하지 않습니다.

확인 원본 코드 실행으로 확인

  • 원본 설정 생산자가 task 설정 300 / 16,384 / 3을 만듦
  • task 표 요청 384,000바이트를 원본 할당기가 188페이지로 확보
  • 네 조건에서 첫 스택 포인터와 최종 관리 정보가 같음
  • 스택 할당 전후로 task 표와 free queue가 바뀌지 않음

모델 연구자가 정한 조건

  • 단계별 진입점, 호스트 호출 스택, .data 복사본, 0으로 채운 BSS
  • 초기 메모리 대조 바이트 48개(마지막 네 조건은 72개)와 그 값
  • RMW 다섯 경로의 증명은 분석자가 옮긴 32비트 수식 모형에서 얻음

미확인 확인하지 않은 것

  • lock 획득·task 레코드 사용·creator 반환·스케줄러 상태
  • 실제 카메라 RAM의 초기 내용과 물리 메모리 배치
  • OS pool의 handle과 ID2 등록, 0이 아닌 bank 값의 생산자

배경: 할당기와 task 스택, 그리고 초기 메모리

카메라의 RTOS는 켜질 때 넓은 RAM 영역을 2,048바이트짜리 페이지로 나눈 뒤 필요한 곳에 몇 페이지씩 내줍니다. 이 일을 하는 코드가 메모리 할당기(allocator)입니다. 페이지를 묶어 관리하는 단위를 이 문서에서는 arena라고 부릅니다.

가장 먼저 받아 가는 것 가운데 하나가 task 표입니다. task마다 상태를 적어 둘 레코드가 필요합니다. 실행할 때 쓸 스택 버퍼도 따로 받아야 합니다. 설정값이 300개라면 300개 레코드가 들어갈 자리부터 확보합니다.

쉽게 말하면

할당기는 빈 페이지 목록을 RAM 안의 작은 관리 칸(8바이트씩)에 적어 둡니다. 처음 목록을 만들 때 이 칸을 RMW로 고칩니다. 읽은 값의 일부 비트를 남긴 채 다시 쓰는 방식이라, 켜질 때 RAM에 남아 있던 쓰레기 값이 결과에 섞일 위험이 있습니다. 펌웨어를 다시 만들 때 이 부분이 초기값에 기대고 있으면 실행할 때마다 결과가 달라질 수 있습니다.

그래서 두 가지를 확인했습니다. 원본 코드가 실제로 어떤 값을 만들어 내는지, 그리고 그 값이 초기 RAM 내용과 무관한지입니다.

할당 경로: 설정값이 스택 포인터가 되기까지

설정 300개 → task 표 188페이지 → 첫 스택 13페이지 순서로 같은 에뮬레이터 RAM 안에서 이어졌습니다. 단계 사이는 연구자가 고른 진입점으로 연결했습니다.

RAM 상태는 처음부터 끝까지 한 에뮬레이터 안에 남겨 두었습니다. 다만 단계마다 함수 입구를 연구자가 골라 실행했으므로 전체 부팅을 이어서 실행한 결과로 볼 수는 없습니다. 프로세서 번호(MPIDR)를 읽는 명령은 한 번도 실행하지 않았습니다. core0 쪽 분기는 연구자가 따로 골라 들어갔습니다.

마지막 정지 지점은 creator 본문 안쪽보다 먼저 만나는 lock 함수의 MPIDR 읽기입니다. 이때 R0에 든 값은 lock 주소이며 task ID나 creator의 반환값이 아닙니다.

관리 칸은 페이지 번호로 찾습니다. 기록을 분석해 보면 할당기는 블록의 처음과 끝 칸에 길이와 상태를 적습니다. 이 칸들이 초기값을 읽는 RMW 대상입니다(역할 이름은 분석상 해석). 연구자가 넣은 대조 바이트는 실행이 끝났을 때 모두 원본 코드가 덮어썼습니다.

일곱 실행 조건과 멈춘 위치

앞의 세 조건은 스택 할당 도중의 세 경계에서 일부러 멈춥니다. 뒤의 네 조건은 초기 메모리 값을 바꿔 가며 MPIDR 직전까지 갑니다. 네 조건의 결과 포인터와 관리 정보는 같았습니다.

조건마다 새 에뮬레이터에서 시작합니다. 초기값 패턴은 연구자가 넣은 대조 바이트를 모두 그 값으로 채웠다는 말입니다. 실제 RAM의 초기 내용이라고 주장하지 않습니다.

숫자 읽는 법

읽기는 동적 RAM 범위에서 일어난 사건 수입니다. 쓰기 목록은 호스트 호출 스택에 쓴 것을 빼되 0x525bb2c0의 스택 포인터 저장만 예외로 넣었습니다. 전체 명령 수나 모든 쓰기 수가 아닙니다. 명령 기록에는 ARM 조건이 거짓이라 효과가 없던 명령도 들어 있습니다.

초기 메모리와 무관함을 증명한 다섯 경로

관리 칸을 고치는 원본 연산을 32비트 수식으로 옮겨 Z3에 반례를 물었습니다. 다섯 고정 경로 모두에서 반례가 없었습니다(unsat).

에뮬레이터 실험은 초기값을 네 가지로만 바꿔 봤습니다. 모든 초기값을 다 넣어 볼 수는 없습니다. 그래서 원본의 마스크와 필드 쓰기를 수식으로 옮긴 뒤 Z3 solver에게 "초기값에 따라 최종 필드가 달라지는 경우"를 찾게 했습니다. 답이 unsat이면 그런 경우는 없습니다.

전제

  • 원본 명령을 분석자가 검토해 32비트 식으로 옮겼습니다. 바이너리 전체를 자동으로 형식 검증한 것이 아닙니다.
  • 인수는 표의 고정값이며 0 sentinel(목록 끝 표시)이 미리 있어야 합니다. 이 두 조건은 원본 실행에서 각 진입마다 따로 확인했습니다.
  • 명령이 순서대로 끝까지 실행되며 동시에 다른 코어나 인터럽트가 같은 칸을 보거나 쓰지 않는다고 가정합니다.
증명하지 않은 것

최종 필드만 증명했습니다. 중간의 바이트 쓰기에는 초기값의 일부가 잠시 남고 그 값은 초기값마다 다릅니다. 물리 메모리, 전체 부팅, core·task별 상태, OS handle과 ID2 등록은 이 증명 범위 밖입니다.

이 재현이 이어받은 이전 분석

이 패키지가 실행하는 것은 일곱 조건과 다섯 증명뿐입니다. 아래 분석 단위들은 맥락이며 하나하나 다시 실행하지 않습니다.

준비 단계에서 설정, 페이지, arena, task 표를 만드는 과정은 다시 재현합니다. 이전 단위의 해시와 요약은 history.json에 있습니다.

한계와 남은 과제

  • 호스트 호출 스택 [0x10000000, 0x10010000), 원본 .data의 호스트 복사본, reset BSS [0x54565b00, 0x54c52c14)를 0으로 둔 모형을 썼습니다. 실제 부팅을 마친 상태와 같다고 볼 수 없습니다.
  • 동적 영역에서 읽는 바이트는 먼저 일어난 원본 쓰기나 명시한 RMW 대조 범위에 속해야 합니다. 그 밖의 쓰이지 않은 바이트를 읽으려 하면 그 자리에서 실행을 멈춥니다.
  • 최종 RAM 해시 범위 [0x56492c80, 0x57c52c80)에는 원본 할당기가 확보한 스택 버퍼가 들어갑니다. 호스트 호출 스택, 초기 데이터, BSS, 페이지 정렬 여백은 뺐습니다.
  • 관리 정보와 주소는 소프트웨어 관측입니다. 물리 DRAM 매핑, MMU, SRAM remap은 입증하지 않았습니다.
  • MPIDR·CP15·SVC 명령은 실행하지 않았고 값을 대신 넣지도 않았습니다. 성공 handle, task 포인터, 스택 포인터를 연구자가 공급한 일도 없습니다.
  • lock 획득, task 레코드 사용, creator 반환, 실행 가능한 스케줄러 상태, OS pool의 양의 handle·ID2 등록은 미확인입니다. 0이 아닌 bank 생산자와 리소스 레코드 +4 정책도 풀지 못했습니다.
  • 빌드, 플래시, 기기 접근은 하지 않았습니다.

할당기가 같은 페이지를 이름 registry 배열에 내주는 경우는 이름 registry 할당과 조회에서 다룹니다. 관리 칸 RMW의 나머지 증명은 RMW 8바이트와 RMW 48바이트 분류에서 다룹니다.

재현 방법

폴더 전체를 함께 옮겨 실행합니다. 입력은 사용자가 준비한 정확히 78,683,892바이트짜리 decoded 이미지입니다. 업데이트 파일을 그대로 넣는 방식은 아닙니다. CLI는 아무것도 내려받지 않고 이미지도 고치지 않습니다. 출력 파일은 새 경로여야 하고 상위 폴더가 있어야 합니다.

python replay.py "path/to/decoded.bin" --output "new-result.json"
python test_replay.py --work-dir "." --output "new-tests.json" --decoded "path/to/decoded.bin"

--decoded를 빼면 펌웨어 없이 입력·helper·출력 경계만 검사합니다. 실제 재현 테스트에는 verified.json도 필요합니다. 임시 fixture는 지정한 작업 폴더 안에서 만들고 지웁니다.

검증한 환경
Windows의 Python 3, Unicorn 2.1.4, Capstone 5.0.9, z3-solver 5.3.1.0(solver 문자열 5.3.1). 정확한 의존성 버전. 다른 OS에서는 실행을 확인하지 않았습니다.
검사 결과
입력 크기·해시 오류, -O 실행, helper 변조, 출력 별칭, 기존 출력과 hardlink, dangling symlink를 포함한 14개 검사 통과. 공백이 든 다른 폴더로 옮겨 두 번 실행한 결과가 공개 요약과 같았습니다. 검사 결과 · 검사 코드

전체 기록에는 도구 버전 문자열도 들어갑니다. 원본 이미지가 맞아도 도구 버전이 다르면 전체 해시 검사가 실패하고 JSON을 만들지 않습니다. 이 오류만으로 펌웨어가 잘못됐다고 판단하면 안 됩니다. .gitattributes가 Windows checkout에서도 helper의 LF 바이트를 지킵니다.

  1. 보호 검사 출력 별칭과 기존 경로를 거부한 뒤 두 helper의 바이트를 고정 SHA-256과 대조합니다.
  2. 입력 확인 decoded 크기·전체 해시, RTOS/BOOT/M0 해시, 지정한 코드·데이터 구간 해시를 봅니다. BOOT/M0는 출처 확인용이고 실행 대상은 RTOS입니다.
  3. 실행 검사한 helper 바이트를 그대로 실행합니다(파일을 다시 열지 않음). 원본 조건 7개와 증명 5개를 돌립니다.
  4. 대조 전체 JSON을 메모리에서 직렬화해 수용된 기록의 크기·SHA-256과 비교합니다.
  5. 저장 일치할 때만 공개 요약을 새 파일로 쓴 뒤 입력이 바뀌지 않았는지 다시 확인합니다.

근거 파일과 참고 자료

  • verified.json — 공개 검증 결과(일곱 조건, 다섯 증명, 한계)
