제공된 decoded 이미지의 원본 명령으로 task 테이블을 만들었습니다. 네 대조 조건에서는 첫 task의 stack 버퍼도 확보했고, lock helper가 processor ID를 읽기 직전인 0x525b7a24에서 멈췄습니다. task 생성 완료나 카메라 부팅 성공을 뜻하지 않습니다.

1. 같은 RAM을 유지하되 진입점은 구분했습니다

호스트가 합성 호출 스택과 원본 .data 복사본을 준비하고 reset 시 BSS를 0으로 보는 모형을 사용합니다. 이후 설정·페이지·arena·task 초기화 명령이 만든 상태를 같은 emulator RAM에 보존합니다. 함수에 독립 진입하는 구간이 있으므로 전체 부팅을 연속 실행한 결과는 아닙니다.

실선: 같은 실행 조건 안에서 유지한 RAM 상태   점선: 호스트가 선택한 별도 진입점. 선은 카메라의 정상 호출 순서를 보증하지 않습니다.

  1. 원본 설정 생산자0x525d6eb4가 설정 포인터를 만들고 반환합니다.다음 구간은 호스트의 독립 진입입니다.
  2. core prologue → processor 읽기 전 중단0x525b5a50 → 0x525b5a54. MPIDR은 실행하지 않습니다.같은 native frame을 유지한 채 조건부 core0 분기 0x525b5a6c에 별도 진입합니다. 실제 core ID를 확인하거나 대체한 것이 아닙니다.
  3. stack 예약량과 논리 RAM 범위원본 분기가 예약량 0x40000을 만들고, 별도 platform 진입 0x525d9e94를 통해 범위 [0x56492c80, 0x57c52c80)를 얻습니다.페이지 초기화 0x525d8a34와 arena 초기화 0x525d9a64는 각각 독립 진입합니다.
  4. 원본 페이지·arena 상태페이지 크기는 0x800, 시작 페이지 수는 0x2f50입니다. 원시 메모리의 RMW 조건은 아래 다섯 고정 경로 검증과 연결합니다.pool 테이블을 먼저 할당하지 않고 task 초기화 0x525b8830에 독립 진입합니다.
  5. task 테이블: 같은 frame에서 요청·할당·초기화설정값 300 / 0x4000 / 3 → 요청 0x5dc00 → arena 0x54582f80 → 포인터 0x564aa808. 300개 레코드에서 지정된 일곱 필드를 검사하고 per-core word 12개에 대한 원본 쓰기를 확인합니다.같은 RAM을 유지하고 ROM descriptor 주소 0x533e33f8를 인수로 creator 0x525bb150에 별도 진입합니다.
  6. 첫 task stack: 같은 creator frame에서 계속요청 0x6000, 명시적 flags 0 → arena 0x54582f48 → 원본 반환 포인터 0x56508808. 0x525bb2c0이 creator frame +0xc에 저장합니다.

    lock helper 0x525b7a24의 MPIDR 읽기 직전에 중단합니다. creator 본문의 0x525bb310보다 먼저 만나는 경계입니다.

최종 중단 시 R0의 0x54c3fd04는 lock 주소입니다. task ID나 creator 반환값이 아닙니다. task 테이블의 전체 할당 범위와 free queue는 creator 진입 전후에 동일했고 해당 영역·테이블 포인터·lock/counter 범위에 겹치는 creator 쓰기도 없었습니다. 검사 구현

2. 세 경계 조건과 네 대조군

각 행은 새 emulator에서 시작합니다. 초기 task-table 준비 단계에는 원시 대조 바이트 48개를 사용했습니다. 마지막 네 행에만 stack RMW용 24바이트를 더해 총 72바이트를 사용합니다. 이 값들은 호스트가 준 대조 조건이며 실제 RAM의 초기 내용으로 주장하지 않습니다.

읽기는 동적 RAM 범위의 사건 수입니다. 쓰기 목록은 호스트 호출 스택의 일반 쓰기를 제외하고 0x525bb2c0의 stack 포인터 저장만 예외로 포함합니다. 따라서 전체 명령 수나 모든 guest 쓰기 수로 읽으면 안 됩니다. 코드 훅에는 ARM 조건이 거짓인 명령도 들어갑니다.

세 번째 조건은 주소 0x564932c8에 원본 쓰기나 호스트 대조값이 없음을 확인하고 읽기 전에 멈춥니다. 마지막 네 조건은 node 0xc9 / 0xca / 0xcb에 추가 대조값을 둡니다. 원본이 선택한 free index는 0xbd, 요청은 0xd페이지입니다. 최종 메타데이터·접근 주소·코드 훅·stack 포인터는 네 조건에서 같습니다. 중간 쓰기 값과 그 해시는 서로 다릅니다.

원본 전체 기록과 요약의 비교표(JSON)에는 생략한 목록마다 기록 수와 SHA-256을 남겼습니다. task_nodes 300개는 일곱 필드 검사 기록입니다. 레코드 전체 필드가 초기화됐다는 뜻은 아닙니다.

3. 표본 네 개와 별도로 검증한 RMW 조건

원본 마스크와 필드 쓰기를 검토해 32비트 식으로 옮겼습니다. 임의 초기값에 따라 최종 필드가 달라지는 반례를 Z3에 질의했습니다. 아래 다섯 고정 경로에서 모두 unsat을 얻었습니다. 원본 실행은 각 free-list 진입의 인수와 0 sentinel을 별도로 확인합니다.

4. 이전 분석에서 이어진 질문과 중요한 정정

5. 이동 가능한 재현 패키지

폴더 전체를 함께 옮긴 뒤 아래처럼 실행합니다. 입력은 정확히 78,683,892바이트인 decoded 이미지입니다. 원본 업데이트 파일을 그대로 넘기는 인터페이스는 아닙니다. CLI는 다운로드하거나 이미지 내용을 수정하지 않습니다. 출력 파일은 새 경로여야 하고 상위 폴더가 있어야 합니다.

python replay.py "path/to/decoded.bin" --output "new-result.json"
python test_replay.py --work-dir "." --output "new-tests.json" --decoded "path/to/decoded.bin"

--decoded를 생략한 테스트는 펌웨어 없이 입력·helper·출력 경계만 검사합니다. 양성 재현 테스트에는 이 패키지의 verified.json도 필요합니다. 임시 fixture는 지정한 작업 폴더 안에서 만들고 정리합니다.

검증한 환경은 Windows의 Python 3, Unicorn 2.1.4, Capstone 5.0.9, z3-solver 5.3.1.0(solver 문자열 5.3.1)입니다. 정확한 의존성 버전을 기록했으며 이번 작업에서는 새로 설치하지 않았습니다. 다른 OS에서는 아직 실행을 확인하지 않았습니다.

전체 witness에는 도구 버전 문자열도 들어갑니다. 원본 이미지가 맞더라도 버전·출력 차이가 있으면 전체 해시 검사가 실패하며 JSON을 만들지 않습니다. 이 오류만으로 펌웨어가 잘못됐다고 판단하면 안 됩니다. .gitattributes는 Windows checkout에서도 helper의 LF 바이트를 보존하도록 포함했습니다.

입력부터 공개 요약까지

  1. 출력 alias와 기존 경로를 거부하고 두 helper의 바이트를 모두 읽어 고정 SHA-256과 대조합니다.
  2. decoded 크기·전체 해시, RTOS/BOOT/M0 해시, 명시한 코드·데이터 구간 해시를 확인합니다. BOOT/M0는 출처 확인용이며 실행 대상은 RTOS입니다.
  3. 검사한 helper 바이트 자체를 compile/exec합니다. 파일을 다시 열어 다른 내용을 실행하지 않습니다. Python 의존성은 설치된 신뢰 환경에서 일반 import합니다.
  4. 원본 조건 7개와 증명 5개를 실행합니다. 전체 JSON을 기존 방식으로 메모리에서 직렬화해 수용된 witness의 크기·SHA-256과 대조합니다.
  5. 일치할 때만 공개 요약을 새 파일로 기록합니다. 원본 입력의 변경 여부도 재확인합니다.

전체 witness 직렬화는 json.dumps(indent=2)의 기본 ASCII 처리와 마지막 LF 한 개를 사용합니다. 생략 목록의 해시는 별도로 키 정렬·공백 없는 JSON 직렬화를 사용합니다. 두 해시 규칙을 혼용하지 않습니다.

공백이 있는 다른 폴더로 옮겨 두 번 실행한 결과가 배포 후보 요약과 일치했습니다. 입력 크기·동일 크기의 잘못된 해시, -O, 두 helper의 실행 sentinel 변조, 직접 입력 alias, 기존 출력과 그 hardlink, dangling symlink를 포함해 14개 검사를 통과했습니다. 검사 결과 · 검사 코드

6. 확인 범위와 미확정 사항

  • 호스트 호출 스택 [0x10000000, 0x10010000), 원본 .data의 host 복사, reset BSS [0x54565b00, 0x54c52c14)의 0 모형을 사용합니다. 실제 부팅 완료 상태와 같다고 볼 수 없습니다.
  • 동적 영역에서 읽는 byte는 앞선 원본 쓰기 또는 명시한 RMW 대조 범위에 속해야 합니다. 나머지 미생산 byte를 읽는 순간은 통과시키지 않습니다.
  • 최종 RAM 해시 범위 [0x56492c80, 0x57c52c80)에는 원본 allocator가 확보한 stack 버퍼가 포함됩니다. 호스트 호출 스택·초기 데이터·BSS·페이지 정렬 여백은 제외합니다.
  • 메타데이터와 주소는 소프트웨어 관측입니다. 물리 DRAM 매핑·MMU·하드웨어 SRAM remap을 입증하지 않습니다.
  • MPIDR·CP15·SVC는 실행하거나 값을 대체하지 않았습니다. 성공 handle·task 포인터·할당된 stack 포인터를 공급하지 않았습니다.
  • lock 획득, task 레코드 소비, creator 반환, runnable scheduler 상태, OS pool의 양의 handle·ID2 등록은 미확정입니다. 비제로 bank 생산자와 리소스 레코드 +4 정책도 해결하지 못했습니다.
  • 이번 범위는 공개 재현 패키지 준비입니다. 하드웨어 경계를 넘는 새 분석, 빌드·플래시·기기 접근은 수행하지 않았습니다.
