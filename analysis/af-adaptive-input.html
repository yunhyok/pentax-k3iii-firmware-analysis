AF 적응형 문턱에 들어가는 시간 표본

PafMotor의 적응형 함수는 어떤 수치를 문턱과 비교해 PWM 값을 2배나 4배로 키울지 정합니다. 그 수치가 어디에서 오고 어떤 계산을 거치는지 원본 명령에서 확인했습니다.

이 문서에서

  1. 배경: 경과 시간과 적응형 문턱
  2. 이전 표본과 새 표본
  3. 차이 계산과 문턱
  4. 카운터의 정체는 아직 확정되지 않았습니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 비교하는 수치는 ElapsedTimer라는 객체가 계산합니다. PafMotor에 저장해 둔 이전 카운터 표본과 새로 읽은 표본의 차이를 27로 나눈 몫입니다.
  • 적응형 함수는 이 몫을 PafMotor 상태에 따라 2000·4000 또는 4000·8000과 비교해 배율을 고릅니다. 차이로 환산하면 54,027부터 2000을 넘습니다.
  • 나눗셈은 곱셈과 시프트로 구현되어 있습니다. 이것이 32비트 입력 전체에서 정확한 나눗셈과 같다는 것을 정수 산술로 확인했습니다.
  • 이 문서는 정적 분석입니다. 원본 코드, 서비스, 레지스터는 실행하지 않았습니다. 카운터가 어떤 클럭으로 세는지 몰라서 27이나 2000이 몇 초인지는 말할 수 없습니다.

정적 분석 코드를 읽어 판단

  • ElapsedTimer의 생성, 결합, 차이·환산 함수
  • PafMotor에 이전 표본을 저장하는 다섯 곳
  • 30개 구간 해시, 명령 위치 31개, 포인터 워드 9개와 이름
  • 환산식의 정수 산술 대조 21건 (PC에서 식만 계산)

미확인 확인하지 않은 것

  • 원본 코드 실행, 레지스터에서 읽히는 실제 카운터 값
  • 카운터의 클럭, 계수 방향, 물리 시간 단위
  • 적응형 호출 전에 초기화가 언제 실행되는지
  • 래퍼가 보관한 상태와 다시 읽은 상태가 같은지

배경: 경과 시간과 적응형 문턱

AF PWM 요청의 호출점 B는 PafMotor 상태가 2나 3일 때 적응형 함수 0x52f0bd6c를 부릅니다. 이 함수는 어떤 수치가 문턱을 넘으면 PWM 값을 2배나 4배로 키웁니다. 문턱 값은 PafMotor 상태 바이트를 다시 읽어 고릅니다.

쉽게 말하면

초시계의 숫자를 두 번 읽어 그 차이를 보는 것과 같습니다. 이전에 읽어 둔 숫자와 지금 숫자를 빼서 일정한 수로 나눕니다. 그 값이 기준보다 크면 힘을 더 줍니다. 다만 이 초시계가 1초에 몇 번 세는지 모르기 때문에 그 기준이 실제로 몇 초인지는 아직 알 수 없습니다.

이름이 ElapsedTimer(경과 시간 측정기)인 객체가 차이를 계산하므로 시간과 관련된 값으로 보입니다. 그러나 이름은 단위를 증명하지 않습니다. 이 문서는 값이 지나가는 길과 계산식까지만 다룹니다.

이전 표본과 새 표본

이전 표본은 PafMotor +0x80에 저장해 둔 값입니다. 새 표본은 ElapsedTimer가 결합한 객체의 가상 함수에서 읽습니다. 두 값의 차이를 환산한 몫이 문턱과 비교됩니다.

  1. 이전 표본 0x531062d4의 반환을 PafMotor+0x80에 저장합니다.
  2. 새 표본 0x53106370이 ElapsedTimer+4에 결합된 객체의 가상 함수 슬롯 +0x6c를 부릅니다.
  3. 차이와 환산 0x53106304가 두 32비트 표본과 경계값을 받아 mode 0에서 27로 나눈 몫을 돌려줍니다.
  4. 배율 선택 0x52f0bdb4 뒤에서 Motor 상태에 따른 문턱과 unsigned로 비교합니다.

PafMotor에 저장되는 표본

Motor +0x80은 0x52f0b8fc, 0x52f0b974, 0x52f0ba10에서 이 카운터의 표본을 받습니다. 0x52f0bf48과 0x52f0bf54는 두 번 읽은 값을 +0x84와 +0x88에 저장합니다. +0x84는 별도 mode 1 호출의 이전 표본입니다.

상태 선택에 쓰는 피드백(D1)은 다른 값입니다. 드라이버 +0x38이 결합돼 있다는 전제에서 0x1e000024를 읽은 하위 16비트입니다. D1을 보고 카운터를 다시 표본하는 곳도 있지만 두 반환 경로는 구분됩니다(D1 피드백과 상태 재읽기).

차이 계산과 문턱

차이 D는 이전 값에서 현재 값을 뺀 unsigned 32비트 값입니다. 이전 값이 현재 값 이하이면 경계값을 더합니다. mode 0에서는 D를 27로 나눈 몫이 문턱과 비교됩니다.

D = u32(old − now + (bound if old ≤ now else 0))
mode 0: D // 27     mode 1: D // 108
mode 2: D // 216    mode 3: D // 27000

0x5310630c와 0x53106310의 두 RSB 명령이 모두 이전 값에서 현재 값을 뺍니다. 이전 값이 현재 값 이하이면 Timer +8을 더합니다. 그래서 같은 값끼리 빼도 경계값이 더해집니다.

곱셈으로 구현한 나눗셈

0x53106328..0x5310636f의 UMULL과 시프트를 묶으면 처음 세 mode의 몫은 floor(D×(2³²+A)/(2³²×k))입니다. 여기서 A=0x2f684bdb이고 k는 32·128·256입니다.

  • 27×(2³²+A)−32×2³²=25입니다. u32 입력 전체에서 오차가 각 나눗수의 역수보다 작습니다. 그래서 결과는 27·108·216으로 정확히 나눈 몫과 같습니다.
  • mode 3의 두 번째 곱셈 상수 B=0x10624dd3은 1000×B−2³⁸=56을 만족합니다. mode 0 몫의 범위에서 이 내림은 정확한 1000 나눗셈과 같습니다. 결과는 원래 D를 27000으로 나눈 몫입니다.

두 등식은 직접 다시 계산해 확인했습니다. 21건의 산술 대조는 이 식을 PC에서 계산한 것이며 원본 명령을 실행한 결과가 아닙니다.

카운터의 정체는 아직 확정되지 않았습니다

키 0xd9로 찾는 객체가 무엇인지, 그 객체가 어떤 클럭으로 세는지 알아야 27이나 2000을 시간으로 바꿀 수 있습니다. 지금은 후보까지만 좁혔습니다.

키 0xd9의 객체를 읽는 실제 레지스트리 칸은 0x54784f6c입니다. 같은 키를 쓰는 공급자 등록 0x531fc9f0의 칸은 0x54785cf8입니다. 두 주소가 다르므로 공급자 등록만으로는 결합 객체나 실제 getter를 정할 수 없습니다. 객체 칸의 생산자, +0x6c 구현, 카운터 클럭을 확인해야 물리 시간 단위를 판정할 수 있습니다.

별도의 정적 조사는 객체 등록에 성공한 조건에서 이 칸에 D9 ReloadTimer가 들어간다고 확인했습니다. 그 vslot +0x6c가 0x5326d5e8에서 0x1e0000a4를 읽는 경로입니다. IRQ 키와 객체 키, 등록 실패 가능성은 따로 구분합니다. 실제 순서, 계수 방향, 클럭, 단위는 여전히 미확인입니다(D9 객체 근거와 남은 시간 단위 검증).

한계와 남은 과제

  • 실행하지 않음: 원본 ARM, 서비스, 레지스터는 실행하지 않았습니다. 산술 대조는 PC에서 식만 계산했습니다.
  • 시간 단위: 카운터의 클럭과 분주 설정을 모르므로 27, 2000, 54,027 같은 숫자를 초나 밀리초로 바꾸지 않습니다.
  • 초기화 시점: ElapsedTimer의 카운터 결합과 경계값 설정이 적응형 호출보다 먼저 실행되는지 확인하지 않았습니다.
  • 상태 값: 래퍼가 보관한 상태와 적응형 함수가 다시 읽은 상태가 같은지 확인하지 않았습니다.

재현 방법
