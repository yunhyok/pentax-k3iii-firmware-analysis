Lightroom 색 프로파일 · K-3 II #1376

Lightroom 톤과 내보낸 RGB의 관계

같은 RAW와 현상값에서 두 톤 프로파일을 비교했습니다. 파란 채널의 밝기 순서가 뒤집혔고, Adobe RGB로 내보낸 뒤 ProPhoto 좌표로 되돌려도 이 역전은 남았습니다.

이 문서에서

  1. 같은 버전에서도 두 패치의 파란 채널 순서가 뒤집혔습니다
  2. Adobe RGB에서도 같은 채널의 역전이 남았습니다
  3. Adobe SDK의 참조 구현에서 톤은 선형 작업 RGB에 적용됩니다
  4. 같은 채널 역전만으로는 내부 작업 색공간을 알 수 없습니다
  5. 재현 방법

같은 버전에서도 두 패치의 파란 채널 순서가 뒤집혔습니다

같은 #1376 RAW에 Identity, Explicit ACR3, 곡선을 생략한 행렬 DCP, 기존 합성 톤 DCP를 적용했습니다. Lightroom Classic 16.0에서 내보낸 네 ProPhoto RGB TIFF는 6016×4000 RGB16 무압축입니다. As Shot 5200 K/+2와 노출 0.00을 유지했고, 프로파일 이름·다이제스트를 제외한 기록된 현상값이 같았습니다. 15.6과 16.0의 Identity 및 Explicit ACR3는 기존 24개 200×200 차트 영역에서 역할별 RGB16 코드가 모두 일치했습니다. 같은 엔진 대조 기록

프로파일 곡선을 내보낸 RGB의 최솟값과 최댓값에 그대로 적용한다면, 입력 끝값의 크기 순서는 유지돼야 합니다. 비교에는 각 100×100 패치의 하위 중앙 순위값을 썼습니다. 각 픽셀에서 RGB 채널 순서가 양쪽 출력에서 모두 유지된 패치입니다.

Adobe RGB에서도 같은 채널의 역전이 남았습니다

새 TIFF를 읽기 전에 두 ProPhoto 출력에서 예측한 Adobe RGB 선형 RGB가 모두 0.01~0.99 안쪽인 픽셀을 고정했습니다. 960,000개 중 932,946개가 남았습니다. 두 Adobe RGB 파일에서 각 ProPhoto 대조군의 CRS 속성 115개와 중첩 설정 6개가 정확히 일치했습니다. 19개 정합 지점의 최대 이동은 Identity 0.111픽셀, Explicit ACR3 0.124픽셀이었습니다.

두 번째 패치 쌍의 역전은 마스크를 적용하기 전 ProPhoto에서 137코드였습니다. #15 중앙 10,000개 중 6,669개를 남긴 후에는 두 출력 공간에서 모두 역전이 사라졌습니다. 첫 번째 패치 쌍은 두 패치의 중앙 픽셀을 모두 유지했습니다.

실제 Adobe RGB와 원래 ProPhoto의 D50 PCS 색차 중앙값은 Identity 0.02580, Explicit ACR3 0.02128이었습니다. 실제 Adobe RGB와 LittleCMS 상대색도 -c0 예측의 최대 차이는 각각 22코드와 24코드였습니다. 직접 ICC 행렬/TRC 예측과 -c0은 채널당 최대 1코드 차이였고 -c1과 -c0은 최대 1,838코드 차이였습니다. 실제 출력 경로에는 작은 차이가 남았지만, 이 두 경로에서 같은 채널 역전의 방향은 유지됐습니다.

최초 검사는 설치 ICC와 내장 ICC의 파일 해시가 달라 중단됐습니다. 두 ICC는 생성 시각 6바이트와 저작권 연도 4바이트만 달랐습니다. 행렬과 TRC를 비롯한 나머지 바이트가 같았고, 두 ICC로 따로 예측한 전체 ROI의 LittleCMS RGB16 코드도 각각 -c0, -c1에서 모두 일치했습니다. 두 해시와 차이 위치를 명시해 재검사했고 마스크와 판정 기준은 유지했습니다. 정합·ICC·픽셀 차이 전체 기록

Adobe SDK의 참조 구현에서 톤은 선형 작업 RGB에 적용됩니다

같은 입력 좌표에서 E가 단조이고 공통이라면, 이상적인 끝값 연산에서 Identity가 제공하는 값에 B를 적용한 결과는 합성 곡선 B∘E와 같습니다. 원본의 BaselineExposure는 −33165/65536 EV입니다. SDK의 유효 노출에는 Stage3Gain도 들어가므로 UI 노출 0만으로는 실제 E를 알 수 없습니다.

고정한 세 EV 예시에서 유한 LUT와 순차 적용의 최대 스칼라 차이는 0.00000264였습니다. Python 계산은 float32 원본과 표본을 사용하고 보간은 float64로 했습니다. SDK의 ACR3 평가와 LUT 보간에는 real32 연산이 사용되므로 이 예시는 SDK 산술의 비트 재현이나 모든 노출에서의 상한으로 해석할 수 없습니다.

같은 채널 역전만으로는 내부 작업 색공간을 알 수 없습니다

합성 예시에서 중성축을 보존하는 3×3 행렬 H와 증가 곡선 x²를 사용했습니다. 내보낸 두 RGB의 첫 채널 0.200과 0.201은 H⁻¹로 옮겨 톤을 적용한 뒤 H로 돌아오면 약 0.080347과 0.040451로 역전합니다. 이때 두 픽셀에서 가운데 채널의 상대 위치는 정확히 보존됩니다. 실제 #7 오렌지의 ACR3−Identity 가운데 채널 비율 차이 중앙값도 원래 ProPhoto −0.00001175, Adobe RGB 역변환 +0.00002083으로 작았습니다.

따라서 테스트한 출력 좌표의 공통 단조 스칼라 모델은 데이터와 맞지 않습니다. 작업 좌표 차이와 채널 문맥에 따른 변환이 모두 가능한 상태이며, 실제 Lightroom의 비공개 처리 순서나 특정 행렬은 식별하지 못했습니다. 다음 JPEG 대조에서는 채널 관계를 다루는 프로파일을 고정한 뒤, 프로파일을 만들 때 쓰지 않은 장면에서 별도로 평가해야 합니다.

재현 방법

원본 DNG는 CC0 표본 #1376입니다. pentax-k3ii-1376.dng라는 이름으로 Lightroom에 가져옵니다. 곡선 생략 행렬 DCP와 Identity 및 Explicit ACR3 대조 DCP의 생성 절차는 기존 톤 보고서에 있습니다. 합성 톤 DCP는 이전 실험의 파일을 사용합니다. 입력용 DCP 디렉터리에 아래 네 이름으로 둡니다. 원본 RAW 출처 · 대조 DCP 준비 · 합성 톤 DCP 및 현상 설정

각 역할의 파일과 카메라 프로파일
역할프로파일TIFF 출력

각 TIFF 디렉터리의 파일명은 pentax-k3ii-1376.tif입니다. 16.0에서는 As Shot 5200 K/+2, EV 0.00, PV15.4로 맞추고 전체 크기 SDR, RGB16 무압축, 크기 조정 및 출력 선명하게 하기 해제, 전체 메타데이터로 내보냅니다. SHA로 고정한 Adobe DNG SDK 1.7.1 Build 2768 ZIP, 설치 Adobe RGB (1998) ICC, LittleCMS 2.12의 시험용 tificc 실행 파일도 필요합니다. 파일 해시는 JSON에 있습니다. 재현에 사용한 환경은 Python 3.12.3, NumPy 1.26.4, SciPy 1.13.1, OpenCV 4.13.0, Pillow 10.4.0, scikit-image 0.24.0, tifffile 2023.4.12였습니다.

python -B tools/check_lightroom_tone_coordinates.py \
  --raw pentax-k3ii-1376.dng --dcps dcps --tiffs tiffs \
  --sdk dng-sdk.zip --adobe-icc AdobeRGB1998.icc \
  --tificc tificc.exe --output replay.json

기본 모드는 보관한 TIFF 8개의 파일 해시와 재계산한 수치 전체를 대조합니다. 보관 TIFF는 배포하지 않습니다. --fresh-exports를 붙이면 16.0 TIFF 6개로 다시 측정합니다. ProPhoto 4개는 고정 좌표와 마스크를 유지하도록 전체 디코딩 픽셀이 보관 값과 같아야 합니다. TIFF 컨테이너는 달라도 되며, Adobe RGB 두 파일은 같은 ICC와 115+6 현상값 등 고정 조건 안에서 픽셀이 달라도 됩니다. 이 모드는 실제 입력 해시를 기록하고 15.6 대조를 재측정하지 않습니다. 다른 엔진이나 작업 설정으로 범위를 넓히면 별도 실험이 필요합니다. 재현 도구 · 동결한 결과·계획·입력 해시
