Lightroom 색 프로파일 · 예측이 어긋난 이유

Lightroom 톤 곡선과 내보낸 RGB의 관계

합성 톤 DCP의 실제 출력이 PC 예측과 달랐던 이유를 찾으려고, 톤 곡선만 바꾼 Lightroom 출력의 RGB 값을 직접 비교했습니다.

이 문서에서

  1. 배경: 곡선은 값의 순서를 바꾸지 않습니다
  2. 같은 버전에서도 두 패치의 파란 채널 순서가 뒤집혔습니다
  3. Adobe RGB에서도 같은 채널의 역전이 남았습니다
  4. Adobe SDK의 참조 구현에서 톤은 선형 작업 RGB에 적용됩니다
  5. 같은 채널 역전만으로는 내부 작업 색공간을 알 수 없습니다
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 같은 K-3 II RAW #1376을 같은 Lightroom Classic 16.0에서 톤 곡선만 다른 DCP 네 개로 내보내 RGB 코드를 비교했습니다. 15.6과 16.0의 출력은 차트 영역에서 코드가 모두 같았습니다.
  • 곡선이 내보낸 RGB에 그대로 적용된다면 값의 크기 순서는 바뀌지 않아야 합니다. 그런데 두 패치의 파란 채널 순서가 뒤집혔습니다. 11번 패치 B 최솟값과 10번 패치 B 최댓값의 차이가 Identity에서 +119, ACR3 곡선에서 −44 코드였습니다.
  • Adobe RGB로 내보낸 뒤 ProPhoto 좌표로 되돌려도 역전은 남았습니다(+121.784 → −39.806). ProPhoto 출력 인코딩에서만 생기는 현상은 아닙니다.
  • 내보낸 RGB 좌표에 공통 단조 곡선 하나를 적용하는 모델은 데이터와 맞지 않습니다. Lightroom의 비공개 작업 색공간이나 처리 순서는 이 측정으로 식별하지 못했습니다. RAW 한 장, 차트 24칸의 결과입니다.

확인 실제 출력에서 잰 값

  • Lightroom 16.0 TIFF 6개(ProPhoto 4, Adobe RGB 2)와 보관한 15.6 TIFF 2개의 RGB16 코드
  • CRS 속성 115개와 중첩 설정 6개 일치, 19개 지점의 위치 맞춤
  • 설치 ICC와 내장 ICC의 바이트 차이와 LittleCMS 예측 일치

정적 분석 소스를 읽어 정리

  • Adobe DNG SDK 1.7.1 Build 2768 참조 렌더러의 SDR 처리 순서
  • ProfileToneCurve가 선형 작업 RGB의 끝값에 적용되는 방식

모델 연구자가 정한 것

  • Identity 출력에 SDK ACR3를 적용한 예측
  • Adobe RGB 색역 안쪽 픽셀 마스크(측정 전 고정)
  • 중성축을 보존하는 3×3 행렬 H를 쓴 합성 반례

미확인 남은 것

  • Lightroom 내부 작업 색공간과 비공개 처리 순서
  • 다른 장면·엔진·작업 설정에서의 결과

배경: 곡선은 값의 순서를 바꾸지 않습니다

톤 곡선은 증가 함수입니다. 입력 a가 b보다 작으면 곡선을 지난 뒤에도 a 쪽이 작습니다. DNG SDK의 참조 렌더러는 픽셀의 가장 낮은 채널과 가장 높은 채널에 이 곡선을 적용합니다. 그러니 같은 채널끼리 비교하면 곡선을 바꿔도 패치 사이의 크기 순서가 유지돼야 합니다.

이 문서는 그 성질을 시험합니다. 톤 곡선이 없는 것과 같은 Identity DCP의 출력을 입력으로 보고 다른 곡선을 넣은 DCP의 출력과 순서를 비교했습니다. 순서가 뒤집히면 "내보낸 RGB에 곡선 하나를 적용했다"는 설명이 틀린 것입니다.

두 축의 눈금은 다릅니다. 그림은 크기 순서만 보여 줍니다.

같은 버전에서도 두 패치의 파란 채널 순서가 뒤집혔습니다

같은 엔진, 같은 현상값에서 곡선만 바꿨는데도 채널 순서가 바뀌었습니다.

같은 #1376 RAW에 DCP 네 개를 적용했습니다. Identity, Explicit ACR3, 곡선을 생략한 행렬 DCP, 합성 톤 DCP입니다. Lightroom Classic 16.0에서 6016×4000 RGB16 무압축 ProPhoto RGB TIFF로 내보냈습니다. As Shot 5200 K/+2와 노출 0.00을 유지했습니다. 프로파일 이름·지문을 빼면 기록된 현상값이 같았습니다.

15.6과 16.0의 Identity·Explicit ACR3 출력은 기존 200×200 차트 영역 24곳에서 역할별 RGB16 코드가 모두 같았습니다. 이 비교에서 두 버전의 차이는 따로 고려하지 않아도 됩니다.

Adobe RGB에서도 같은 채널의 역전이 남았습니다

출력 색공간을 바꿔 내보내고 다시 ProPhoto로 되돌려도 첫 번째 패치 쌍의 역전은 그대로였습니다.

  1. 같은 RAW와 프로파일Identity와 Explicit ACR3에 같은 현상값
  2. 실제 TIFF 두 쌍Lightroom 16.0에서 ProPhoto RGB와 Adobe RGB로 각각 내보냄
  3. 공통 좌표로 환산Adobe RGB를 내장 ICC로 해석해 ProPhoto 선형 RGB·코드 척도로

새 TIFF를 읽기 전에 픽셀 마스크를 고정했습니다. 두 ProPhoto 출력에서 예측한 Adobe RGB 선형 값이 모두 0.01~0.99 안쪽인 픽셀만 남겼습니다. 960,000개 중 932,946개가 남았습니다. 두 Adobe RGB 파일은 대응하는 ProPhoto 출력과 CRS 속성 115개, 중첩 설정 6개가 정확히 같았습니다. 19개 정합 지점의 최대 이동은 Identity 0.111픽셀, Explicit ACR3 0.124픽셀이었습니다.

ICC 해시 불일치로 첫 검사가 멈춘 경위

첫 검사는 설치 ICC와 내장 ICC의 파일 해시가 달라 색차를 재기 전에 중단됐습니다. 두 ICC(각 560바이트)는 생성 시각 6바이트와 저작권 연도 4바이트만 달랐습니다. 행렬과 TRC를 포함한 나머지 바이트는 같았습니다. 두 ICC로 따로 예측한 전체 ROI의 LittleCMS RGB16 코드도 -c0, -c1 모두에서 같았습니다. 두 해시와 차이 위치를 명시해 다시 검사했습니다. 마스크와 판정 기준은 바꾸지 않았습니다.

Adobe SDK의 참조 구현에서 톤은 선형 작업 RGB에 적용됩니다

공개 SDK에서는 톤 곡선이 출력 변환보다 앞서 선형 ProPhoto 작업 공간에서 적용됩니다.

  1. 선형 작업 RGB카메라 RGB → PCS → 선형 ProPhoto RGB. 조건에 따라 색상·채도, 노출 램프, LookTable
  2. 끝값에 톤 적용공통 노출 톤 E와 프로파일 곡선 F를 합성한 LUT. 최솟값·최댓값 변환, 가운데 채널 보간
  3. 출력 변환조건에 따라 RGBTables, 출력 행렬과 클램프, 감마, 소스 마스크 합성

같은 입력 좌표에서 E가 단조이고 공통이라면, 이상적인 끝값 연산에서 Identity 출력에 B를 적용한 결과는 합성 곡선 B∘E와 같습니다. 원본의 BaselineExposure는 −33165/65536 EV입니다. SDK의 유효 노출에는 Stage3Gain도 들어가므로 UI 노출 0만으로는 실제 E를 알 수 없습니다.

고정한 세 EV 예시에서 유한 LUT와 순차 적용의 최대 스칼라 차이는 0.00000264였습니다. Python 계산은 float32 원본과 표본에 float64 보간을 썼습니다. SDK의 ACR3 평가와 LUT 보간은 real32 연산이라, 이 예시를 SDK 산술의 비트 재현이나 모든 노출에서의 상한으로 볼 수는 없습니다.

같은 채널 역전만으로는 내부 작업 색공간을 알 수 없습니다

역전은 "다른 좌표에서 곡선을 적용했다"로도 설명되지만 그것이 실제 원인이라고 정할 수는 없습니다.

합성 예시로 가능성을 보였습니다. 중성축을 보존하는 3×3 행렬 H와 증가 곡선 x²를 씁니다. 내보낸 두 RGB의 첫 채널 0.200과 0.201을 H⁻¹로 옮겨 톤을 적용하고 H로 돌아오면 약 0.080347과 0.040451이 되어 순서가 뒤집힙니다. 이때도 두 픽셀에서 가운데 채널의 상대 위치는 정확히 보존됩니다.

실제 7번 오렌지 패치에서도 ACR3−Identity 가운데 채널 비율 차이의 중앙값은 작았습니다. 원래 ProPhoto에서 −0.00001175, Adobe RGB 역변환에서 +0.00002083입니다.

테스트한 출력 좌표에서 공통 단조 스칼라 곡선 하나로 설명하는 모델은 데이터와 맞지 않습니다. 작업 좌표가 다르거나 채널 문맥에 따라 변환이 달라지는 경우가 모두 남아 있습니다. 실제 Lightroom의 비공개 처리 순서나 특정 행렬은 식별하지 못했습니다.

재현 방법

원본 DNG는 CC0 표본 #1376입니다. pentax-k3ii-1376.dng라는 이름으로 Lightroom에 가져옵니다. 곡선 생략 행렬 DCP와 Identity·Explicit ACR3 대조 DCP의 생성 절차는 톤 곡선 비교 문서에 있습니다. 합성 톤 DCP는 해당 실험의 파일을 씁니다. 입력용 DCP 폴더에 아래 네 이름으로 둡니다(원본 RAW 출처, 대조 DCP 준비, 합성 톤 DCP 및 현상 설정).

각 TIFF 폴더의 파일명은 pentax-k3ii-1376.tif입니다. 16.0에서는 As Shot 5200 K/+2, EV 0.00, PV15.4로 맞춥니다. 내보내기는 전체 크기 SDR, RGB16 무압축, 크기 조정·출력 선명하게 하기 해제, 전체 메타데이터입니다.

그 밖에 SHA로 고정한 Adobe DNG SDK 1.7.1 Build 2768 ZIP, 설치 Adobe RGB (1998) ICC, LittleCMS 2.12의 시험용 tificc 실행 파일이 필요합니다. 파일 해시는 JSON에 있습니다. 재현 환경은 Python 3.12.3, NumPy 1.26.4, SciPy 1.13.1, OpenCV 4.13.0, Pillow 10.4.0, scikit-image 0.24.0, tifffile 2023.4.12였습니다.

python -B tools/check_lightroom_tone_coordinates.py \
  --raw pentax-k3ii-1376.dng --dcps dcps --tiffs tiffs \
  --sdk dng-sdk.zip --adobe-icc AdobeRGB1998.icc \
  --tificc tificc.exe --output replay.json
  • 기본 모드는 보관한 TIFF 8개의 파일 해시와 다시 계산한 수치 전체를 대조합니다. 보관 TIFF는 배포하지 않습니다.
  • --fresh-exports를 붙이면 16.0 TIFF 6개로 다시 잽니다. ProPhoto 4개는 고정 좌표와 마스크를 지키도록 디코딩 픽셀 전체가 보관 값과 같아야 합니다. TIFF 컨테이너는 달라도 됩니다.
  • Adobe RGB 두 파일은 같은 ICC와 115+6 현상값 같은 고정 조건 안에서 픽셀이 달라도 됩니다.
  • 이 모드는 실제 입력 해시를 기록하고 15.6 대조는 다시 재지 않습니다. 다른 엔진이나 작업 설정으로 범위를 넓히려면 별도 실험이 필요합니다.
