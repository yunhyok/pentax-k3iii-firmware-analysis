현재 확인한 범위

R2y 제어 바이트 8개의 생산자와 원본 비트 조건을 확인했다. WBLV 문자열의 실제 레지스터 참조와 bypass·픽셀 순서는 미확정이다. 새 생산자 분석 · WBLV 후보 검증 · 수정 펌웨어·UI 이식 선행 연구

PENTAX K-3 Mark III v2.20의 WB 선택 결과를 B2r gain 레지스터까지 연결했다. 색공간 메시지 0x145의 수신부와 common 버퍼 반영 경로도 확인했다. ISP에서는 입력 스트림의 클리핑 설정과 R2y의 상한 후보 필드를 찾고 B2r·R2y의 조건부 버퍼 연결을 검증했다. 이전에 확인한 JPEG 압축기와 컬러모드 행렬·곡선 전달 경로를 함께 정리한다. 실제 픽셀을 처리하는 ISP 내부 산술, 카메라 출력과 Lightroom의 색 일치는 아직 검증하지 않았다.

분석 대상은 fwdc233b.bin에서 추출한 ARM RTOS다. 적재 기준 주소는 0x52500000, RTOS SHA-256은 342d2f35405e8daf1797dfe431d2e4aa70f4b52a2c242a29df48206672f1dfb4다. 함수명 일부는 분석용 이름이다. 호출 관계의 간접 연결은 기록한 생성자·vtable·객체 초기화가 유지된다는 조건 아래 성립한다. 검증 주소와 바이트 해시

하위 JPEG 압축기

상위 JPEG 매크로는 작업을 큐에 제출한다. JpegCodecPipeService의 생성자 0x5304c74c는 vtable을 설치한다. 이 vtable의 어댑터 0x5304d538은 실행 함수 0x5304cd4c로 연결된다. 이후 0x5304c7e8이 하위 드라이버의 0x5320b18c를 호출한다. 이 경로는 서비스 객체 초기화와 메시지 전달이 성공한 경우를 설명한다. 호출·vtable 근거

하위 드라이버는 JPEG 블록의 MMIO 기준 주소 0x298c0000을 사용한다. Y 주소는 +0x430, CbCr 주소는 +0x434, 압축 결과를 담는 code 주소는 +0x440에 설정한다. 시작 함수 0x5320bd68은 +0x4의 bit 0을 세운다. 버퍼 주소가 확인되었다고 해서 모든 입력 모드의 크로마 서브샘플링과 메모리 배치까지 확정되는 것은 아니다. 드라이버 근거

양자화 표의 품질 배율

0x5320ac78은 두 개의 64항 표에 품질 배율을 적용한다. 함수 인수 Q를 10으로 나눈 값을 q로 사용하며 계산 중간마다 float32 반올림을 거친다. q가 50 이하이면 배율은 trunc(1000 × 50 / q), 그보다 크면 trunc(1000 × (100 − q) / 50)에 해당한다. 각 항목 t는 정수 연산 (t × 배율 + 500) / 1000으로 바꾸고 1~255로 제한한다. 간결한 수식의 연산 결합 순서만 바꾸어도 float32 경계값이 달라질 수 있으므로 공개 검증기는 원래 명령의 순서를 따른다.

결과는 RAM의 0x547bd374와 0x547bd3b4에 보관하고 4항씩 묶어 MMIO 0x298c0100과 0x298c0140에 기록한다. 합성 표 4쌍과 Q=1~1000을 사용해 원래 ARM 함수 및 하위 레지스터 함수를 실행했다. 4,000개 조건에서 표 항목 512,000개와 MMIO 워드 128,000개가 독립 계산식과 일치했다. MMIO는 에뮬레이터의 일반 RAM으로 대체했으며 카메라나 압축 엔진은 실행하지 않았다. 실행 검증기 · 검증 결과

이 시험은 양자화 표 생성과 전달을 검증한다. DCT, 실제 영상의 양자화 결과, 엔트로피 코딩은 시험 범위 밖이다. Q=0과 범위를 벗어난 인수도 시험하지 않았다. 카메라의 JPEG 품질 메뉴와 이 Q 값 사이의 전체 매핑은 별도 확인이 필요하다.

압축 크기와 완료 처리

0x5304ca20의 정책 경로는 Q=950으로 예비 압축한 뒤 실제 크기와 목표 크기로 품질을 추정하고 본 압축을 요청한다. 결과가 0이거나 용량을 넘으면 품질을 낮춰 재시도하는 분기가 있다. 기준 크기를 얻는 런타임 가상 호출은 미해결이며 이 정책 전체를 수치 재현하지는 않았다.

ImageInterruptService의 입력 0xd5는 JPEG 처리기 0x53201640으로 분기한다. 이 번호를 물리 CPU IRQ 번호로 확정하지 않았다. 처리기는 MMIO의 +0x480과 +0x2c에서 상태를 읽고 확인 응답을 기록한 뒤 관찰자 source 0x63 또는 0x64에 통지한다. source 0x64, 상태 bit 31, 드라이버 mode 0 조건에서는 +0x20의 압축 길이를 읽어 이벤트 0x00e00001로 전달한다.

파이프 콜백은 그 길이를 pipe+0x44에 저장하고 이벤트 마스크 0x1(bit 0)을 깨운다. 압축 헬퍼는 길이를 출력 descriptor의 +0xc로 복사한다. 마지막 0x00c00003 콜백은 상위 JPEG 매크로의 이벤트 마스크 0x2(bit 1)를 설정한다. 다른 오류·디코드 분기도 있으므로 모든 인터럽트를 압축 성공으로 해석하지 않았다. 조건부 콜백·상태 근거

컬러모드에서 하드웨어 설정으로

Develop의 반복 처리 0x52e5c088은 준비, 설정, 시작·대기, 종료 처리를 호출한다. 초기화 함수 0x52e5739c는 B2b·B2r·R2y 서비스를 매크로의 +0x9820, +0x9824, +0x9828에 연결한다. 시작 명령은 R2y, B2r, B2b 순서로 제출된다. 이것은 CPU가 시작을 요청하는 순서다. 센서 픽셀이 하드웨어 블록을 통과하는 순서로 해석하지 않았다. Develop·서비스 근거

R2y 매개변수 준비 함수 0x52e597c0은 설정 포인터를 P의 +0x94에 기록하고 갱신 플래그 7개를 세운다. 변환 함수 0x5307fdec은 설정의 +0x120에서 시작하는 0x5d24바이트를 드라이버 설정의 +0x644로 복사한다. 이 영역에는 이전 분석에서 계산한 Custom Image 행렬과 곡선이 들어 있다. 갱신 플래그와 선행 처리의 성공 조건을 통과하면 0x53253eac이 0x532512cc를 호출해 해당 설정을 적용한다.

하드웨어 생성자와 등록 테이블을 따라가면 R2y 레지스터 기준 주소는 0x28418000, 0x28518000, 0x28618000이다. 데이터 영역은 각각 0x294a0000, 0x295a0000, 0x296a0000으로 설정된다. 0x532512cc는 행렬 필드 +0x20..+0x30에서 signed 12-bit 계수를 꺼낸다. 첫 두 계수는 레지스터 기준 주소의 +0xa0에 각각 bits 0..11과 16..27로 기록된다. 초기화·필드 복사·레지스터 근거

이 연결로 모드별 행렬이 하드웨어 설정에 도달하는 지점까지 확인했다. 레지스터 기록 함수 자체는 픽셀별 행렬 곱을 계산하지 않는다. 내부 누산기의 비트 수, 행렬의 픽셀 연산 배율, 포화 시점과 출력 비트 깊이는 별도 근거가 필요하다.

감마·톤 테이블의 전달 위치

톤 포장 함수 0x5313775c는 16비트 항목 1024개를 설정의 +0x1568에 넣으며 하위 적용 함수는 이를 데이터 영역의 +0x0000으로 복사한다. 감마 포장 함수 0x53135c60이 만든 네 개의 0x800바이트 버퍼는 +0x8800, +0x9000, +0x9800, +0xa000으로 전달된다. 네 개의 0x200바이트 버퍼는 +0xaa00, +0xac00, +0xae00, +0xb000으로 전달된다. 이는 테이블의 저장·전달 위치를 확정한 결과이며 하드웨어 보간식까지 복원한 결과는 아니다. 설정 복사 근거

합성 설정 8개로 전체 적용 함수 0x532512cc와 실제 레지스터 함수, NEON memcpy를 실행했다. 원래 wrapper 생성자도 사용했다. 9개 행렬 필드, 4개 톤 필드, 감마 플래그 묶음, 18개 테이블 복사를 조건별로 대조해 지정 필드 외 비트의 보존도 확인해 총 312개 검사가 통과했다. 첫 번째 하드웨어 인스턴스의 레지스터와 데이터 영역을 일반 RAM으로 모델링한 시험이다. 센서 입력과 ISP의 픽셀 출력을 에뮬레이션하지 않았다. ISP 설정 검증기 · 검증 결과

색공간과 화이트밸런스

색공간 파서 0x52aed898은 sRGB와 AdobeRGB 문자열을 각각 선택값 0과 1로 변환한다. 0x52954be0 → 0x52954afc를 거쳐 UserData의 +0x35b에 저장하고 변경 알림에서 메시지 0x145를 보낸다. 이번에는 해당 메시지의 수신부에서 common+0x26b5로 기록하는 연결까지 확인했다. RAW 모델의 1/2를 common의 0/1로 바꾸는 경로는 이 큐 경로와 별도다. 색공간 설정 근거

메시지 0x145의 수신과 반영

송신 함수 0x52edd820은 opcode 1, 속성 ID 0x145, 한 바이트 payload와 해제 플래그 0을 큐에 제출한다. 송신이 성공한 경우 이벤트 마스크 0x1(bit 0)을 기다린다. 큐 객체 생성자 0x52ed0844의 vtable 0x538ef480+0xc는 실행 함수 0x52ede7cc를 가리킨다. opcode 1은 0x52ede66c로 연결된다.

속성별 멤버 함수 표는 RAM 0x545241cc에 있다. ID 0x145의 항목 0x54524bf4에는 {0x52ecf4a8, 0}이 들어 있다. 이 항목의 초기 ROM 위치는 0x53d0c934이며 시작 코드의 복사 매핑과 대조했다. 디스패처의 간접 호출 0x52ede6e8은 이 항목을 통해 실제 색공간 처리기 0x52ecf4a8에 도달한다. 같은 숫자를 쓰는 두 함수를 추정으로 연결한 결과가 아니다. 초기화·분기·멤버 함수 표 · 메시지 의미와 조건

처리기는 서비스의 +0x518 포인터와 payload를 0x52eef4c0에 넘긴다. 이 함수가 부르는 0x52eef408은 common의 +0x26b5를 갱신한다. 기존 값과 다르고 변경 추적 객체가 있을 때 변경 목록에 ID 0x145와 이벤트 0x28101f01도 기록한다. 후속 commit 0x52edfa40의 성공 분기는 두 common 버퍼 포인터를 교환하고 새 current의 0x4ed0바이트를 다른 버퍼로 복사한다. 변경 알림 0x52ede4d8 → 0x5330b1b0은 설정 요청을 수신한 뒤의 별도 통지 경로다.

전체 속성 처리기와 멤버 함수 디스패치의 일부 구간을 각각 실행했다. 두 시험 모두 실제 setter·commit·NEON memcpy를 호출하며 함수 대역은 쓰지 않았다. 기존 값 0·1·255와 payload 0~255를 조합한 총 1,536사례에서 버퍼, 변경 목록과 포인터 교환이 예상과 일치했다. 메뉴 의미가 확인된 값은 0·1뿐이다. 나머지는 바이트 전달 시험이며 카메라에서 지원하는 색공간 값이 아니다. 큐·잠금·스케줄러·변경 알림 수신자는 실행하지 않았다. 재현 검증기 · 실행 결과

common+0x26b5 == 1이면 P52가 1이 된다. 이 플래그는 모드 행렬에 추가 행렬을 곱하고 YCbCr 계수 조정과 감마 준비에도 영향을 준다. 따라서 색공간 선택을 행렬 하나의 교체로만 재현할 수는 없다. 각 행렬의 물리적인 입력·출력 좌표계는 아직 확정하지 않았다. 설정 분기 근거 · 이전 수치 분석

감마 변환 0x53136f4c는 입력 곡선 256항에 대해 y = min((flag ? L[x] : x) >> 4, 1023)을 계산한다. 인접 출력 차이는 0~240으로 제한한 뒤 8바이트 레코드를 고르는 인덱스로 사용한다. 마지막 항목에는 차이 0의 레코드를 넣는다. L은 펌웨어 lookup이며 표준 감마 지수로 단정하지 않았다. flag가 켜졌을 때 함수 내부에는 x의 lookup 범위를 확인하는 검사가 없다. 이번 시험 범위는 x=0~16384다. 전체 함수 시험에는 두 flag 조건의 해당 입력을 모두 포함했다. 전체 함수 시험 151개와 WB 부분 구간 시험 34개가 통과했다. 색공간·WB 검증기 · 185개 검증 결과

WB 결과에서 B2r gain 레지스터까지

화이트밸런스 서비스 0x5314db1c는 선택 객체의 16비트 값 4개를 >>5 하여 common+0x30c10..0x30c16에 기록한다. 별도 항등 분기는 256을 직접 저장한다. GM/BA 미세 조정은 채널 0과 3에 lookup 곱과 13비트 이동을 적용한다. 네 채널을 R/Gr/Gb/B로 이름 붙일 근거는 아직 부족하다.

후속 함수 0x5314b914는 quartet을 다시 읽어 공통 배율을 계산한다. 각 곱셈은 32비트 결과에서 bits 13..28을 추출한 뒤 상한 2047을 적용하고 common+0x30c18..0x30c1e에 저장한다. 단순히 수학적인 곱을 8192로 나눈 것과는 다르다. 원래 명령의 32비트 곱셈과 16비트 추출을 보존해야 한다. 배율은 quartet의 최솟값, 보정 표의 최솟값과 common 제어값에 의존하며 다른 분기는 제어값부터 재계산한다. 이 2047 제한은 gain 계수의 제한이다. 대체 WB 분기는 첫 재배율 뒤 원본 common+0x30c10/0x30c16만 덮어쓸 수 있다. 실제 소비되는 파생 quartet과 최종 원본 quartet을 항상 동일시해서는 안 된다. 배율·분기·정수 연산 근거

Develop 입력의 +0x48은 common+0x30c10을 가리킨다. 준비 함수 0x52e594f0은 그 포인터의 +8/+a/+c/+e, 즉 파생 quartet을 읽어 각각 <<5 한 값을 gain 객체에 저장한다. B2r 매개변수 +0x24에서 드라이버 설정 +0x70으로 이 객체 포인터가 전달된다. 갱신 플래그를 통과하면 하위 적용 함수 0x531bc180이 객체 값을 다시 >>5 하여 레지스터 함수에 넘긴다.

버퍼 연결로 확인한 처리 관계

Develop의 메시지 0x200005는 B2r 반복 처리 0x52e5b4cc, 0x200006은 R2y 반복 처리 0x52e5b148로 연결된다. 각각 인덱스 0~3을 순회하며 0x52e5ac24와 0x52e5acf8을 통해 버퍼 모드 1을 선택한다. 서로 다른 메시지이므로 이 사실만으로 두 작업의 큐 실행 순서를 확정하지는 않는다.

버퍼 모드 1에서 B2r의 출력 descriptor와 R2y의 입력 descriptor는 같은 입력 P, 같은 반복 인덱스와 같은 형식일 때 세 주소를 공유한다. R2y의 하위 read-unit으로 전달하는 변환에는 R2y 매개변수의 +1==0 조건도 있다. 두 준비 함수 0x52e5a500, 0x52e5a62c는 P+0x60/+0x64/+0x68에 같은 표 기반 오프셋을 더한다. 형식 0의 배수는 1, 형식 8의 배수는 2다. 일반 반복 준비 0x52e5a99c는 버퍼 모드 0을 넘기며 이때 세 주소는 0으로 설정된다. 따라서 이 DRAM 연결을 모든 현상 분기에 일반화하지 않는다. 조건부 버퍼 관계

입력 스트림의 M2PCLIP을 찾았다. 레지스터 덤프 0x532427e4가 read-unit 기준 주소 +0x1c를 이 이름으로 출력한다. 설정 함수 0x532249e8은 레코드의 +6에서 읽은 u16을 상위 16비트에, +8에서 읽은 s16을 하위 16비트에 기록한다. SetupInputDram의 0x53022bc8은 이 필드에 각각 0xffff와 0을 설정한다. 형식 분기는 다른 형식·shift 설정을 바꾼다.

B2b 입력 DRAM 경로의 0x53211140은 해당 read 설정 함수를 호출한다. 기록한 factory 초기화가 실행됐다는 조건에서 Read0/1의 M2PCLIP 주소는 0x2886881c/0x2886891c + pipe×0x100000이며 pipe는 0~2다. 이 factory의 가상 초기화 호출 지점은 아직 연결하지 못했다. read-unit의 주소와 드라이버 연결은 클리핑 근거에 기록했다. 이는 입력 스트림의 clip 설정이며 앞서 찾은 행렬 계수 포화와 구분된다. 필드의 부호 해석과 실제 clamp 연산식을 실측하지 않았으므로 0xffff를 센서 white level 또는 실제 유효 16비트라고 해석하지 않는다.

R2y 생성자 0x53254790과 B2r 생성자 0x531bd0a4는 레지스터 기준 주소 인수를 객체 +4에 저장하고 각각 채널 vtable을 설치한다. 문자열 주변 메타데이터와 클래스의 관계를 더 확인한 결과다. 이 사실만으로 WBLV 필드명과 특정 MMIO 오프셋을 연결하지 않는다. 진단 코드가 제거됐거나 문자열이 미사용이라는 결론도 유보했다.

Lightroom 이전에 남는 구체 조건

프로파일을 만들 때는 계수뿐 아니라 그 계수가 받는 좌표와 적용 위치도 필요하다. 예를 들어 임의의 정규화 입력 x=0.75, gain=2, 상한=1을 가정하면, gain 다음 clip의 결과는 1이지만 clip 다음 gain은 1.5다. 이 값은 순서에 따른 차이를 설명하는 수학 예시이며 펌웨어에서 측정한 픽셀 값이 아니다. 같은 레지스터 설정이 확인되더라도 처리 순서가 다르면 옮길 변환도 달라진다.

Lightroom으로 옮기기 위한 조건

펌웨어의 컬러모드 행렬과 곡선을 DCP에 그대로 넣는 방식은 아직 성립하지 않는다. 입력 색좌표, 화이트밸런스 적용 상태, 고정소수점 배율과 클리핑 위치가 일치해야 같은 연산이 된다. 현재 복원한 자료는 모드별 변환을 재현할 때 사용할 연산 모델과 피연산자 목록이다. 카메라 JPEG와의 색 일치를 검증한 Lightroom 프로파일은 아직 만들지 않았다.

DNG의 ColorMatrix는 XYZ에서 기준 카메라 색공간으로, ForwardMatrix는 화이트밸런스를 적용한 카메라 색에서 XYZ D50으로 변환한다. 펌웨어에서 발견한 3×3 행렬에는 ColorMatrix라는 이름이 붙어 있다. 이 이름만으로 두 행렬을 같은 것으로 볼 수 없다. Adobe의 LookTable 역시 정해진 색공간과 적용 순서를 사용한다. 변환 방향과 좌표계를 먼저 맞춰야 한다. Adobe DNG 규격 1.7.1.0, pp.33, 52–53, 57, 63–64

정적인 색 변환은 LookTable이나 RGB LUT의 후보가 된다. 영상 통계에 따라 달라지는 톤 보정, 공간적인 노이즈 감소와 샤프닝, 디모자이킹까지 하나의 전역 LUT로 재현할 수는 없다. 이런 처리는 별도 구현 또는 일치 범위의 제한이 필요하다. 화이트밸런스와 감마를 양쪽 파이프라인에서 중복 적용하지 않도록 입력 상태도 기록해야 한다.

RAW·JPEG 예제가 제공된 뒤의 검증

같은 RAW에서 모드별 카메라 JPEG를 만들고 가능한 설정을 고정한다. 촬영 때의 WB와 노출, 렌즈, 카메라 펌웨어, 출력 색공간, JPEG 품질, 노이즈 감소, 샤프닝과 자동 톤 설정을 함께 기록한다. 비교에 쓰는 모드가 해당 렌즈와 촬영 조건에서 실제로 선택되는지도 확인한다.

색상표만으로 평가를 끝내지 않는다. 회색 계조, 피부색, 잎과 강한 원색, 하이라이트가 포함된 장면을 준비하고 특성이 알려진 조명 조건을 나누어 비교한다. 프로파일을 맞출 때 사용하지 않은 이미지로 다시 검사한다. 평가 항목은 패치별 색차와 중성축 오차, 계조의 단조성, 노출 변화에 따른 오차, 채널별 클리핑 비율이다. 허용 오차는 사용 목적에 맞춰 정하고 측정 결과와 함께 공개한다.

JPEG 압축과 크로마 처리 때문에 파일 바이트의 완전한 일치를 색 재현의 합격 조건으로 삼기는 어렵다. 디코딩한 이미지에서 동일한 색관리와 출력 크기를 적용하고 패치 내부의 색과 경계 부근의 공간 오차를 구분해 평가한다. 현재 단계에서는 실제 RAW·JPEG 쌍, 카메라 하드웨어 출력, Lightroom 적용 결과를 시험하지 않았다.

검증과 보관

이번 M2P·R2y 추가 의사코드는 로컬 .private/m2p-semantics/와 .private/r2y-order-semantics/에 있다. 분석 문서 5개와 로컬 노트 21개를 HTML로 교체하고, 기존 주소·해시·재현 명령과 내부 링크를 검수했다. GitHub 진입용 README와 윤문·이전 배포 검증의 원본 기록은 Markdown으로 보존한다.

이번 보고서의 주소·분기·vtable 및 설정 필드는 원본 ARM 목록과 대조했다. 공개한 deep-evidence.json과 검증기는 해당 기록의 바이트 일치와 연결 조건을 검사한다. 바이트 검증이 모든 함수 의미나 실제 카메라 실행을 입증하는 것은 아니다.

추가 angr 의사코드와 전체 조사 구간의 ARM 목록은 로컬 .private/wb-gain-hardware/, .private/colorspace-message/, .private/isp-clipping-order/, .private/isp-buffer-order/에 보관한다. 이전 JPEG·ISP·WB 조사 자료와 원본 계수·테이블도 로컬에 유지한다. 공개 저장소에는 분석 문서, 주소·해시·조건부 연결과 재현용 검증 코드를 담는다. 디컴파일된 C는 원래 소스코드가 아니며 타입·부동소수점·간접 호출 해석에서 ARM 목록과 차이가 날 수 있다.

검증 재현 명령

python verify_deep_analysis.py path/to/decoded.bin
python verify_jpeg_quantization.py path/to/decoded.bin --output jpeg-checks.json
python verify_isp_configuration.py path/to/decoded.bin --output isp-checks.json
python verify_colorspace_wb.py path/to/decoded.bin --output colorspace-wb-checks.json
python verify_wb_gain_hardware.py path/to/decoded.bin --output wb-gain-checks.json
python verify_colorspace_message.py path/to/decoded.bin --output message-checks.json
python verify_isp_clipping.py path/to/decoded.bin --output clip-checks.json
python verify_isp_buffers.py path/to/decoded.bin --output buffer-checks.json
python verify_isp_semantics.py --self-test
python verify_isp_semantics.py path/to/decoded.bin --output semantics-checks.json
python decompile_sample.py path/to/decoded.bin 0x531bc180

verify_deep_analysis.py와 verify_isp_semantics.py는 Python 표준 라이브러리를 사용한다. JPEG·ISP 수치 검증은 Unicorn 2.1.4, 개별 함수 디컴파일은 angr 10.0.5를 사용했다. 입력 펌웨어의 준비 방법은 저장소 안내에 있다.

이전 단계의 분담 조사 뒤 별도 검토자가 WB·ISP·버퍼의 원본 범위 129개와 ARM 10,443워드를 대조하고 해당 수치 시험을 다시 실행했다. 구체적인 수정 권고는 없었다. 색공간 메시지 작업은 담당자의 자기 검토를 독립 검토로 세지 않았으며, 통합 담당자가 원본 setter·commit과 초기화 표를 확인하고 공개 검증기를 다시 실행했다. 새 표 분기 검증에는 정상 4건과 잘못된 인덱스·명령 위치를 거부하는 5건의 검사도 적용했다.

문장 검토와 남은 검증

기존 본문은 humanize-korean light 경로로 검토했다. 언어 검토 등급 B, 자체 점검 6/6이며 수치·인용·유보 표현 보존 검사를 통과했다. 변경률은 최종 검사에서 0.3% 미만이다. 이 등급은 펌웨어 분석의 신뢰도 점수가 아니다. 이번 추가 절은 standard 경로에서 진단·윤문·보존 검사를 별도로 수행했고, 변경률 0.48%, 등급 B, 자체 점검 6/6이며 보존 게이트를 통과했다. “필요한 것은 …다”를 “…도 필요하다”로 다듬고 연결어미 뒤 쉼표를 줄였다. 긴 조건절을 나누고 “사용하며, 계산”을 “사용하며 계산”으로 다듬었다.

실제 카메라·센서·DMA·ISP 픽셀 출력과 Lightroom 렌더링은 실행하지 않았다. 특히 M2PCLIP의 비교식과 R2y 상한 후보의 의미, 내부 연산 순서는 레지스터 규격 또는 관측 가능한 출력이 있어야 확정할 수 있다.
