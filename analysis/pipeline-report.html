배경: RAW가 JPEG가 되는 과정과 이 문서가 확인한 범위

디지털카메라는 센서가 내놓은 RAW 데이터를 여러 단계로 가공해 JPEG를 만듭니다. 일반적인 순서는 블랙 레벨 보정, 화이트밸런스, 디모자이크, 노이즈 감소, 색 변환, 톤·감마 적용, 압축입니다(Karaimer·Brown 2016, 그림 1). 구체적인 구현은 카메라마다 다릅니다.

K-3 Mark III에서 조사한 경로를 보면 펌웨어는 픽셀을 직접 계산하지 않습니다. 영상 처리 회로(ISP)와 JPEG 압축 회로의 레지스터에 설정값을 기록하고 시작 신호를 보내고 완료를 기다립니다. 그래서 펌웨어를 읽으면 어떤 값을 어디에 쓰는지는 알 수 있습니다. 회로가 그 값으로 픽셀을 어떻게 계산하는지는 알 수 없습니다. 이 문서의 결론은 모두 이 구분을 따릅니다.

1단계 센서 데이터 입력: M2PCLIP 레지스터에 기록되는 값

입력 데이터를 읽는 장치에 M2PCLIP이라는 레지스터가 있고 확인한 설정 경로는 모두 상위 16비트에 0xffff, 하위 16비트에 0을 기록합니다. 이 두 값이 픽셀을 어떻게 잘라 내는지는 알 수 없습니다.

ISP는 메모리에 있는 영상 데이터를 읽기 장치(ProReadUnit)로 읽어 들입니다. 읽기 장치에는 offset, shift, clip 설정이 있고 펌웨어에는 그 이름으로 M2POFS, M2PBSFT, M2PCLIP이 나옵니다. 그중 M2PCLIP은 펌웨어의 레지스터 덤프 함수가 직접 이 이름으로 값을 출력하므로 이름과 위치를 함께 확인할 수 있었습니다.

2단계 화이트밸런스: 계산 결과가 B2r gain 레지스터에 도달

화이트밸런스 서비스가 고른 gain 네 개는 재배율과 상한 2047 처리를 거친 뒤, B2r 블록의 11비트 레지스터 필드 네 개에 기록됩니다.

쉽게 말하면

화이트밸런스는 조명 색에 맞춰 채널마다 다른 배율(gain)을 곱해 흰색이 흰색으로 보이게 하는 처리입니다. 펌웨어는 이 배율 네 개를 계산해 하드웨어에 넘깁니다. 실제 곱셈은 하드웨어가 합니다.

  1. 선택 결과 저장16비트 값 4개를 5비트 내려 common에 저장
  2. 미세 조정GM·BA 설정을 채널 0과 3에 반영
  3. 재배율공통 배율을 곱하고 2047로 제한 → 파생 gain
  4. Develop 준비파생 gain을 5비트 올려 gain 객체에 저장
  5. B2r 기록다시 5비트 내려 11비트 필드에 기록
화이트밸런스 값이 지나가는 위치
위치하는 일
화이트밸런스 서비스 0x5314db1c선택 객체의 16비트 값 4개를 >>5 하여 common+0x30c10..0x30c16에 기록합니다. 별도의 항등 분기는 256을 직접 저장합니다.
GM/BA 미세 조정채널 0과 3에 조회표 값의 곱을 적용하고 13비트 이동합니다.
재배율 함수 0x5314b914네 값을 다시 읽어 공통 배율을 계산합니다. 곱셈마다 32비트 결과의 bits 13..28을 꺼내고 상한 2047을 적용해 common+0x30c18..0x30c1e에 저장합니다. 이 문서에서는 이 값을 파생 gain이라고 부릅니다.

매개변수 전달B2r 매개변수 +0x24에서 드라이버 설정 +0x70으로 gain 객체의 포인터가 넘어갑니다.
적용 함수 0x531bc180갱신 플래그를 통과하면 객체 값을 다시 >>5 하여 레지스터 함수에 넘깁니다. 채널 인덱스 0·3·1·2 순서로 기록합니다.
gain 레지스터B2r 기준 주소 0x28412000, 0x28512000, 0x28612000의 +0x4c와 +0x50에 있는 11비트 필드입니다. 기록 함수는 0x531bd360, 0x531bd380, 0x531bd3a0, 0x531bd3c0입니다.

초기화한 B2r 객체와 갱신 플래그가 유지되면 화이트밸런스 결과가 하드웨어의 gain 설정으로 전달됩니다. 이 조건부 연결까지 확인했습니다.

이 값을 다룰 때 지켜야 할 점

  • 재배율은 단순한 나눗셈이 아닙니다. 수학적인 곱을 8192로 나눈 값과 다릅니다. 원래 명령의 32비트 곱셈과 16비트 추출을 그대로 따라야 같은 결과가 나옵니다.
  • 배율은 여러 값에 의존합니다. 네 값의 최솟값, 보정 표의 최솟값, common의 제어값이 들어갑니다. 다른 분기는 제어값부터 다시 계산합니다.
  • 2047은 gain 계수의 제한입니다. 픽셀 값을 자르는 포화와 다릅니다.
  • 하드웨어가 쓰는 값은 파생 gain입니다. 대체 화이트밸런스 분기는 첫 재배율 뒤에 원본 값(common+0x30c10, +0x30c16)만 덮어쓸 수 있습니다. 마지막에 저장된 원본 값과 실제로 소비되는 파생 gain이 항상 같다고 보면 안 됩니다.
  • 네 채널의 색 이름은 모릅니다. R/Gr/Gb/B로 이름 붙일 근거가 아직 부족합니다. 실제 픽셀에 곱하는 배율과 디모자이크 전후 위치도 이 기록만으로는 정할 수 없습니다.
시험 조건

260사례에서 원본 함수의 출력이 기준식과 일치했습니다. 재배율 함수 전체 128사례(제어값을 그대로 쓰는 분기 64, 다시 계산하는 분기 64), Develop 준비 함수의 일부 구간 64사례, B2r 적용 함수 전체 68사례입니다. gain뿐 아니라 같은 객체의 offset 필드와 상한 후보 필드의 기록도 대조했습니다. 입력과 객체는 합성 값이고 하드웨어 주소는 일반 메모리입니다.

4단계 색 행렬·감마·톤: Custom Image 설정이 R2y에 도달

컬러모드에서 계산한 색 행렬과 감마·톤 표는 0x5d24바이트짜리 설정 묶음에 담겨 R2y 블록의 레지스터와 표 영역으로 복사됩니다. 복사 위치와 비트 폭은 확인했습니다. 회로가 이 값으로 픽셀을 계산하는 방식은 모릅니다.

RAW 현상 모듈 Develop의 반복 처리 0x52e5c088은 준비, 설정, 시작·대기, 종료 처리를 차례로 호출합니다. 초기화 함수 0x52e5739c가 B2b·B2r·R2y 서비스를 매크로의 +0x9820, +0x9824, +0x9828에 연결해 둡니다. 시작 명령은 R2y, B2r, B2b 순서로 제출됩니다. 이것은 CPU가 시작을 요청하는 순서일 뿐이며 픽셀이 블록을 지나가는 순서로 해석하지 않습니다.

  1. 설정 포인터 등록 R2y 매개변수 준비 함수 0x52e597c0이 설정 포인터를 매개변수의 +0x94에 기록하고 갱신 플래그 7개를 세웁니다.
  2. 설정 묶음 복사 변환 함수 0x5307fdec이 설정의 +0x120부터 0x5d24바이트를 드라이버 설정의 +0x644로 복사합니다. 이 문서에서는 이 묶음을 C라고 부릅니다. 색 처리 알고리즘에서 계산한 Custom Image 행렬과 곡선이 여기에 들어 있습니다.

적용 함수 0x532512cc는 C의 +0x20..+0x30에서 부호 있는 12비트 계수 9개를 꺼냅니다. 첫 두 계수는 R의 +0xa0에 각각 bits 0..11과 bits 16..27로 기록됩니다. 나머지도 같은 방식으로 이어집니다.

톤 포장 함수 0x5313775c는 16비트 항목 1024개를 C의 +0x1568에 넣고 적용 함수가 이를 표 영역의 +0x0000으로 복사합니다. 감마 포장 함수 0x53135c60이 만든 0x800바이트 버퍼 네 개는 +0x8800, +0x9000, +0x9800, +0xa000으로, 0x200바이트 버퍼 네 개는 +0xaa00, +0xac00, +0xae00, +0xb000으로 전달됩니다. 표가 저장되고 전달되는 위치를 확정한 것이며 회로가 표를 보간하는 식까지 복원한 것은 아닙니다.

색공간에 따라 달라지는 감마 변환

감마 변환 함수 0x53136f4c는 256항 입력 곡선을 하드웨어에 보낼 형식으로 바꿉니다. 플래그가 켜지면 값을 펌웨어의 조회표 L에 한 번 더 통과시킵니다. 앞 절의 색공간 플래그 P52가 이 감마 재대응을 켜는 조건에 들어갑니다.

y[i] = min((flag ? L[x[i]] : x[i]) >> 4, 1023)
d[i] = clamp(y[i+1] − y[i], 0, 240)      → 8바이트 레코드를 고르는 인덱스
마지막 항목에는 차이 0의 레코드를 넣음
  • L은 펌웨어 안의 조회표입니다. 표준 감마 지수로 단정하지 않았습니다.
  • 플래그가 켜졌을 때 함수 안에는 x가 조회표 범위를 넘는지 확인하는 검사가 없습니다. 시험한 범위는 x=0~16384입니다.

이 비트를 bypass로 볼 수 있는가

아직 그렇게 볼 근거가 없습니다. R+0x10 bit 0이 bypass인지, 클럭 제어인지, 처리 활성화인지 알 수 없습니다.

  • 0x5313399c는 Edge descriptor의 byte 0이 정확히 1일 때 계수와 표를 준비합니다. 다른 상태와 캐시 조건도 관여합니다. 이 바이트가 CPU 쪽 준비 작업을 켜는 조건이라는 근거는 생겼습니다.
  • 그러나 패커의 &1 연산과 같은 조건은 아닙니다. 예를 들어 값 3은 하위 비트가 1이지만 ==1을 만족하지 않습니다.
  • 일반 자원 선택 분기에서 Edge는 객체의 u16+0x204 값이 2, 3, 그 밖의 값인지에 따라 서로 다른 getter를 씁니다. 이 getter는 project index와 별도의 6칸 sub-index를 참조합니다.
  • ColorReference에는 내부 Custom Image enum 10에서만 쓰는 별도의 자원 선택이 있습니다. 다른 런타임 분기도 있습니다.

따라서 여덟 바이트를 사용자 컬러모드 하나에 대응하는 고정된 값 묶음으로 볼 수 없습니다. 이 결과는 각 기능의 설정이 하위 제어 비트 하나로 모이는 경로를 설명할 뿐이며 하드웨어의 bypass나 픽셀 처리 순서를 정하지 않습니다.

이와 별도로 C의 첫 바이트에서 하위 2비트를 꺼내 0x53251310 → 0x53256ccc로 전달하고 R+0x80의 bits 0..1에 기록하는 경로도 있습니다. 이 값을 bypass·클럭·필터 활성화로 해석하거나, 감마·톤·행렬의 순서를 바꾸는 모드라고 판단할 근거는 없습니다.

5단계 JPEG 압축: 양자화 표와 완료 통지

JPEG 압축은 전용 하드웨어가 맡습니다. 펌웨어는 양자화 표와 버퍼 주소를 기록하고 시작 비트를 세운 뒤, 완료 인터럽트로 압축 길이를 받습니다. 양자화 표 계산은 4,000조건에서 원본 코드와 기준식이 일치했습니다.

요청 경로

상위 JPEG 매크로는 작업을 큐에 제출합니다. JpegCodecPipeService의 생성자 0x5304c74c가 vtable을 설치하고 이 vtable의 어댑터 0x5304d538이 실행 함수 0x5304cd4c로 이어집니다. 이후 0x5304c7e8이 하위 드라이버의 0x5320b18c를 호출합니다. 이 경로는 서비스 객체의 초기화와 메시지 전달이 성공한 경우를 설명합니다.

하위 드라이버는 JPEG 블록의 MMIO 기준 주소 0x298c0000을 씁니다. Y 주소는 +0x430, CbCr 주소는 +0x434, 압축 결과를 담는 code 주소는 +0x440에 설정합니다. 시작 함수 0x5320bd68은 +0x4의 bit 0을 세웁니다. 버퍼 주소를 확인했다고 해서 모든 입력 모드의 크로마 서브샘플링과 메모리 배치까지 확정되는 것은 아닙니다.

양자화 표의 품질 배율

쉽게 말하면

JPEG는 영상을 8×8 블록으로 나눠 주파수 성분(DCT 계수)으로 바꾼 다음, 각 성분을 양자화 표의 값으로 나누고 반올림합니다(ITU-T T.81 A.3.4). 표의 값이 클수록 정보를 많이 버려 파일이 작아집니다. 품질 설정은 이 표에 곱하는 배율을 바꿉니다.

0x5320ac78은 64항짜리 기본 표 두 개에 품질 배율을 적용합니다. 함수 인수 Q를 10으로 나눈 값을 q로 씁니다.

q ≤ 50 :  배율 = trunc(1000 × 50 / q)
q > 50 :  배율 = trunc(1000 × (100 − q) / 50)
항목   = (t × 배율 + 500) / 1000   → 1~255로 제한
  • 계산 중간마다 float32 반올림을 거칩니다. 식의 결합 순서만 바꿔도 float32 경계에서 값이 달라질 수 있어, 검증기는 원래 명령의 순서를 따릅니다.
  • 결과는 RAM의 0x547bd374와 0x547bd3b4에 보관하고 4항씩 묶어 MMIO 0x298c0100과 0x298c0140에 기록합니다.
  • 8비트 양자화 표의 값 범위가 1~255인 것은 JPEG 규격(T.81 표 B.4)과 같습니다.
참고

이 식은 널리 쓰이는 IJG libjpeg의 품질 배율과 꼴이 같습니다. libjpeg는 품질 50 미만에서 5000/Q, 그 이상에서 200−2Q를 백분율 배율로 쓰고 항목을 (t×배율+50)/100으로 구합니다(jcparam.c). 펌웨어는 같은 식을 열 배 세밀한 단위로 계산합니다. 펌웨어의 기본 표 두 개가 어떤 표인지는 공개 자료에 싣지 않았습니다.

시험 조건

합성 표 4쌍과 Q=1~1000으로 원본 ARM 함수와 하위 레지스터 함수를 실행했습니다. 4,000조건에서 표 항목 512,000개와 MMIO 워드 128,000개가 따로 만든 계산식과 일치했습니다. MMIO는 에뮬레이터의 일반 메모리로 대신했고 카메라나 압축 엔진은 실행하지 않았습니다.

이 시험은 양자화 표의 생성과 전달만 확인합니다. DCT, 실제 영상의 양자화 결과, 엔트로피 부호화는 시험 범위 밖입니다. Q=0과 범위를 벗어난 인수도 시험하지 않았습니다. 카메라의 JPEG 품질 메뉴와 이 Q 값 사이의 대응은 따로 확인해야 합니다.

압축 크기 정책과 완료 통지

0x5304ca20의 정책 경로는 Q=950으로 예비 압축을 한 뒤, 실제 크기와 목표 크기로 품질을 추정해 본 압축을 요청합니다. 결과가 0이거나 용량을 넘으면 품질을 낮춰 다시 시도하는 분기가 있습니다. 기준 크기를 얻는 런타임 가상 호출은 풀지 못했고 이 정책 전체를 수치로 재현하지는 않았습니다.

  1. 인터럽트 분기 ImageInterruptService의 입력 0xd5가 JPEG 처리기 0x53201640으로 분기합니다. 이 번호를 물리적인 CPU IRQ 번호로 확정하지 않았습니다.
  2. 상태 읽기 처리기는 MMIO의 +0x480과 +0x2c에서 상태를 읽고 확인 응답을 기록한 뒤, 관찰자 source 0x63 또는 0x64에 통지합니다.
  3. 압축 길이 전달 source 0x64, 상태 bit 31, 드라이버 mode 0의 조건에서 +0x20의 압축 길이를 읽어 이벤트 0x00e00001로 전달합니다.
  4. 파이프 콜백 길이를 pipe+0x44에 저장하고 이벤트 마스크 0x1(bit 0)을 깨웁니다. 압축 헬퍼는 길이를 출력 descriptor의 +0xc로 복사합니다.
  5. 매크로 완료 마지막 0x00c00003 콜백이 상위 JPEG 매크로의 이벤트 마스크 0x2(bit 1)를 설정합니다.

오류 분기와 디코드 분기도 따로 있으므로 모든 인터럽트를 압축 성공으로 해석하지 않았습니다.

M2PCLIP의 비교 방식을 정할 수 없는 이유

M2PCLIP의 실제 픽셀 비교식은 확인하지 못했습니다. 이 문서에서 말하는 상위·하위는 레지스터 안의 16비트 위치를 뜻하며 수치의 상한·하한으로 확정한 이름이 아닙니다.

  • 값이 한 가지뿐입니다. 찾은 설정 위치가 모두 0xffff와 0을 쓰므로, 값을 비교해 방향이나 부호를 가려낼 수 없습니다.
  • 읽는 방식의 차이는 증거가 되지 않습니다. 설정 함수는 상위 값을 LDRH(부호 없음)로, 하위 값을 LDRSH(부호 있음)로 읽습니다. 그러나 두 기록 함수는 결과의 하위 16비트만 남깁니다. CPU의 부호 확장 정보가 레지스터에 남지 않으므로 하드웨어가 부호 비교를 한다는 증거가 못 됩니다.
  • 픽셀을 도는 코드가 없습니다. 채널 설정·시작·상태 함수를 더 읽었지만 descriptor의 값을 레지스터에 쓰고 제어 비트를 다룰 뿐입니다. 픽셀 배열을 돌며 샘플과 임계값을 비교하는 반복문은 없었습니다. 조사한 범위의 결과이며 펌웨어 어디에도 CPU 참조 구현이 없다는 증명은 아닙니다.
  • 공개 자료에도 없습니다. 제조사의 SC2000 제품 자료는 하드웨어 영상 기능을 나열하지만 확인한 2쪽 문서에 M2PCLIP 비교식이나 R2y 레지스터 정의는 없습니다(Socionext SC2000 제품 자료, AD04-00113-3E, 2017년 5월).

앞의 450개 설정 검사는 레지스터에 값이 올바로 채워지는지 본 결과입니다. 픽셀 비교를 시험한 것으로 세지 않습니다.

R2y의 세 번째 필드와 WBLV 문자열

R2y의 gain·offset 객체에서 +0x18부터 읽는 세 번째 필드는 여전히 상한 후보입니다. 이 필드를 읽는 getter 0x530dd638의 직접 호출은 B2r의 네 곳과 R2y의 세 곳이고 모두 앞에서 본 레지스터 기록 경로에 속합니다. 이 값을 받아 CPU에서 픽셀을 자르는 코드는 검색 범위에서 찾지 못했습니다.

진단 문자열에는 R2Y_Core.OFG.WBLV_0/1과 B2r의 WBLVRB/GR라는 표기가 있습니다. 이 문자열이 R2y의 +0x30/+0x34 레지스터를 가리킨다면 필드의 이름을 알 수 있습니다. 그러나 문자열과 레지스터 읽기를 잇는 포인터나 덤프 경로를 찾지 못했습니다. 그래서 WBLV라는 약어를 임의로 풀지 않았고 세 번째 필드를 white level이나 clip threshold로 이름 붙이지 않았습니다. 이름과 레지스터 읽기가 함께 확인된 M2PCLIP보다 증거가 약합니다.

정적인 색 변환은 LookTable이나 RGB LUT의 후보가 됩니다. 영상 통계에 따라 달라지는 톤 보정, 공간적인 노이즈 감소와 샤프닝, 디모자이크까지 전역 LUT 하나로 재현할 수는 없습니다. 이런 처리는 따로 구현하거나 일치 범위를 제한해야 합니다. 화이트밸런스와 감마를 양쪽 파이프라인에서 중복 적용하지 않도록 입력 상태도 기록해야 합니다.

같은 RAW의 카메라 출력으로 검증하는 방법

  1. 출력 쌍 만들기 같은 RAW에서 모드별 카메라 JPEG를 만들고 가능한 설정을 고정합니다. 촬영 때의 화이트밸런스와 노출, 렌즈, 카메라 펌웨어, 출력 색공간, JPEG 품질, 노이즈 감소, 샤프닝, 자동 톤 설정을 함께 기록합니다. 비교할 모드가 그 렌즈와 촬영 조건에서 실제로 선택되는지도 확인합니다.
  2. 장면 고르기 색상표만으로 평가를 끝내지 않습니다. 회색 계조, 피부색, 잎과 강한 원색, 하이라이트가 있는 장면을 준비하고 특성이 알려진 조명 조건을 나눠 비교합니다. 프로파일을 맞출 때 쓰지 않은 이미지로 다시 검사합니다.
  3. 평가하기 패치별 색차, 중성축 오차, 계조의 단조성, 노출 변화에 따른 오차, 채널별 클리핑 비율을 봅니다. 허용 오차는 사용 목적에 맞춰 정하고 측정 결과와 함께 공개합니다.
  4. 압축의 영향 분리하기 JPEG 압축과 크로마 처리 때문에 파일 바이트가 완전히 같기를 합격 조건으로 삼기는 어렵습니다. 디코딩한 이미지에 같은 색 관리와 출력 크기를 적용하고 패치 안쪽의 색과 경계 부근의 공간 오차를 나눠 평가합니다.
현재 상태

이 문서의 추적에서는 RAW·JPEG 쌍, 카메라의 하드웨어 출력, Lightroom 적용 결과를 시험하지 않았습니다. 그 뒤에 한 실제 Lightroom 실험은 Lightroom 색 프로파일 주제에 있습니다. 카메라 JPEG와 색을 맞춘 모드별 프로파일은 아직 없습니다. Adobe 형식의 적용 위치와 기존 프로파일 구조는 컬러모드 자원과 Lightroom에 정리했습니다.

  • 이 문서의 주소, 분기, vtable, 설정 필드는 원본 ARM 목록과 대조했습니다. deep-evidence.json과 검증기는 그 기록의 바이트 일치와 연결 조건을 검사합니다. 바이트 검증이 모든 함수의 의미나 실제 카메라에서의 실행을 입증하지는 않습니다.
  • deep-evidence.json은 저장소의 여러 주제가 함께 쓰는 파일입니다. 지금은 분석 구간 1,232개, 분기 위치 7,389곳, 데이터 워드 492개, 조건부 연결 104개를 담고 있습니다.
  • 디컴파일한 C는 원래 소스 코드가 아닙니다. 타입, 부동소수점, 간접 호출의 해석에서 ARM 목록과 차이가 날 수 있습니다.
  • 에뮬레이터의 CPU 모델은 시험마다 다릅니다. WB → B2r 시험과 R2y 제어 바이트 시험은 Cortex-A15 모델, JPEG·R2y 설정·색공간 0x145·입력 클리핑 시험은 Cortex-A7 모델을 썼습니다.

  • 이 문서의 추적은 2026년 11월 7일 기준 기록에서 출발했습니다. JPEG와 Custom Image 설정 경로를 먼저 확인했고 이어서 화이트밸런스·색공간·ISP 클리핑, R2y 제어 바이트와 WBLV, M2PCLIP 의미의 순서로 조사했습니다.
  • 화이트밸런스·색공간·ISP 단계에서 의사코드 130개와 ARM 목록을 저장했습니다. M2PCLIP 의미 조사에서 M2P 8개, R2y 2개 함수의 의사코드와 전체 ARM 목록을 더했습니다. 제어 바이트 조사에서는 생산자·준비 함수 10개, WBLV 주변 생성자 2개, UI·업데이트 접근 함수 5개의 의사코드를 더했습니다. 당시 통합 목록의 고유 디컴파일 진입점은 389개였습니다.
  • M2PCLIP 의미 조사를 마친 시점의 deep-evidence.json은 분석 구간 807개, 분기 위치 6,119곳, 데이터 워드 236개, 조건부 연결 50개였습니다. 그 뒤 다른 주제의 근거가 더해져 위에 적은 현재 값이 됐습니다.
  • 별도 검토자가 화이트밸런스·ISP·버퍼의 원본 범위 129개와 ARM 10,443워드를 대조하고 해당 수치 시험을 다시 실행했습니다. 구체적인 수정 권고는 없었습니다.
  • 색공간 메시지 작업은 담당자의 자기 검토를 독립 검토로 세지 않았습니다. 통합 담당자가 원본 갱신 함수·commit과 초기화 표를 확인하고 공개 검증기를 다시 실행했습니다. 표 분기 검증에는 정상 4건과, 잘못된 인덱스·명령 위치를 거부하는 5건의 검사도 적용했습니다.

한계와 남은 과제

실제 카메라, 센서, DMA, ISP의 픽셀 출력은 실행하지 않았습니다. 아래 항목은 레지스터 규격이나 관측할 수 있는 출력이 있어야 확정할 수 있습니다.

  • ISP 내부의 픽셀 계산 — offset과 gain을 어떤 순서로 적용하는지, 클리핑이 행렬·감마 앞인지 뒤인지, 하드웨어가 LUT를 어떻게 보간하는지 모릅니다.
  • M2PCLIP의 의미 — 상위·하위 값의 방향, 부호, 포함 여부, offset·shift와의 순서, 0xffff가 임계값인지 표식인지 모릅니다.
  • R2y 세 번째 필드와 제어 비트 — 상한 후보가 실제 클리핑 임계값인지, R+0x10 bit 0과 R+0x80의 2비트가 무엇을 켜고 끄는지 모릅니다. WBLV 문자열이 가리키는 레지스터도 찾지 못했습니다.
  • 화이트밸런스 — 네 채널의 색 이름, gain의 실제 픽셀 배율, black level과의 관계, 디모자이크 전후 위치가 남아 있습니다.
  • JPEG — DCT와 엔트로피 부호화는 하드웨어 내부입니다. 형식 값 1·2가 어떤 크로마 서브샘플링인지, 품질 메뉴와 Q의 대응, 크기 정책의 수치 재현, 인터럽트 입력 0xd5의 물리 번호가 남아 있습니다.
  • 블록 사이의 연결 — Develop의 출력이 JPEG의 Y·CbCr 입력 버퍼로 이어지는 전체 계보, 큐와 DMA의 실제 순서를 확인하지 못했습니다.
  • 실행 조건 — 객체 초기화 순서, 런타임 vtable, 큐·잠금·스케줄러는 실행하지 않았습니다. 모든 간접 연결은 기록한 초기화가 유지된다는 조건에서 성립합니다.
  • 색 일치 — 카메라 출력과 Lightroom의 색 일치는 검증하지 않았습니다.

수정 펌웨어와 UI 이식에 앞서 확인할 항목은 수정·이식 선행 연구에 따로 정리했습니다.
