펌웨어 재구축 · 2단계

재컴파일한 색 행렬 함수를 원래 자리에 넣고 패키지 다시 만들기

앞 단계에서 함수를 따로 떼어 원본과 같다는 것을 확인했습니다. 이번에는 그 함수를 원본 펌웨어의 원래 자리에 넣고, 펌웨어 파일 전체를 다시 포장해도 같은 결과가 나오는지 시험했습니다.

이 문서에서

  1. 배경: 함수를 원래 자리에 넣는다는 것
  2. 원래 주소에 넣고 끝 명령은 보존
  3. 펌웨어 패키지를 다시 포장
  4. 원래 주소와 실제 호출자에서 확인
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • C로 다시 만든 Q13 3×3 행렬 곱 함수를 원본 RTOS 안의 원래 주소에 그대로 올려놓고 펌웨어 패키지를 다시 포장해 로컬 후보 파일 하나를 만들었습니다.
  • 이 후보를 다시 풀어, 같은 주소의 함수와 이 함수를 부르는 실제 색 행렬 준비 경로를 PC 에뮬레이터에서 실행했습니다. 출력과 보존 레지스터가 원본과 같았고 원본 펌웨어의 헤더·체크섬 검사도 통과했습니다.
  • 확인한 범위는 행렬 함수 하나와 색공간 처리가 켜진 두 호출 분기입니다. 카메라에서 실행하거나 업데이트로 적용하지는 않았습니다. 이번 후보는 압축을 풀어 저장하는 방식이라 원본보다 두 배 넘게 큽니다(줄이는 방법은 다음 문서).

확인 원본 코드 실행·바이트 대조로 확인

  • 원래 주소에서 직접 호출 106개 입력이 기준식과 일치
  • 색 행렬 준비 호출자 2개 분기에서 출력·보존 레지스터 일치
  • 원본·후보 모두 원본 펌웨어의 헤더·체크섬 검사 8건 통과
  • 패키지 변경 범위가 교체 레코드와 체크섬으로 한정됨

모델 시험 조건으로 정한 것

  • 색공간 처리를 켠 합성 설정과 합성 행렬 입력
  • CPU는 Unicorn의 Cortex-A7 모델
  • 후보는 압축 없이 전부 저장(stored)한 임시 형식

미확인 확인하지 않은 것

  • 색공간이 꺼진 분기, 입력·출력이 겹치는 경우, 실행 시간
  • 커진 패키지를 카메라의 RAM·하드웨어 디코더가 받는지
  • 실제 업데이트 수용과 부팅, 카메라에서의 색 출력

배경: 함수를 원래 자리에 넣는다는 것

앞 문서에서는 새로 만든 함수를 빈 주소에 따로 올려놓고 원본과 비교했습니다. 이것만으로는 “함수 자체가 같다”는 것까지만 알 수 있습니다. 펌웨어를 실제로 고치려면 한 걸음 더 나가야 합니다. 새 코드를 원본 함수가 있던 바로 그 주소에 넣고 펌웨어 파일을 다시 포장한 다음, 그 주소를 부르는 다른 코드가 변함없이 동작하는지까지 확인해야 합니다.

대상은 색 변환에 쓰이는 Q13 3×3 행렬 곱 함수 하나입니다. 이 함수를 원래 주소에 넣고 펌웨어 패키지를 다시 만든 뒤, 원본과 후보를 나란히 실행해 비교했습니다.

쉽게 말하면

펌웨어 파일은 여러 부품을 압축해 담은 상자입니다. 부품 하나(RTOS)의 작은 함수만 새것으로 바꾸고 상자를 다시 봉한 뒤, 상자를 열어 그 함수가 제자리에 있고 이웃 부품이 멀쩡한지 확인한 셈입니다. 다만 다시 봉할 때 이번에는 압축을 하지 않아 상자가 커졌습니다.

펌웨어 파일 fwdc233b.bin은 15개의 이름 붙은 레코드를 압축해 담고 있습니다. 바꾼 것은 그중 RTOS 레코드 하나뿐이고 그 안에서도 함수 한 개의 구간만 교체했습니다.

원래 주소에 넣고 끝 명령은 보존

함수 구간 116바이트 가운데 앞 112바이트를 새 코드로 덮고 마지막 복귀 명령 4바이트는 원본 그대로 두었습니다. 새 코드는 그 직전에서 복귀하므로 보존한 끝 명령은 실행되지 않습니다.

새 코드는 다른 함수를 부르지 않고 코드 안에서 데이터를 참조하거나 재배치가 필요한 부분도 없습니다. ARM 명령 28개를 확인했고 코드 안의 직접 분기 3개는 모두 함수 내부(새 코드 구간)를 가리켰습니다. 주소·해시는 아래 접이식에 있습니다.

참고

체크섬은 파일 전체 바이트를 32비트로 더한 값입니다. 내용이 바뀌면 다시 계산해 맞춰야 합니다. 이 검사는 내용이 온전한지 보는 것일 뿐, 암호학적 서명이 아닙니다.

원래 주소와 실제 호출자에서 확인

함수를 직접 부르는 경우와, 색 행렬을 준비하는 실제 상위 함수가 이 함수를 거치는 경우를 모두 원본·후보에서 실행해 비교했습니다. 결과와 보존 상태가 같았습니다.

직접 호출

원본과 다시 푼 후보에서 각각 106개 입력을 넣어 함수를 직접 실행했습니다. 부호 있는 16비트 입력, 반올림·정수 범위 경계, 난수에서 출력이 기준식과 같았습니다. 두 실행 모두 함수 밖으로 나가지 않고 복귀했으며 보존 레지스터·스택 포인터와 출력 쓰기 범위를 확인했습니다. 진입 시점의 스택 포인터 아래로 가장 깊이 쓴 위치는 원본 28바이트, 후보 32바이트였습니다.

색 행렬 준비 경로

색공간(ColorSpace) 처리를 켠 합성 설정으로 원본 호출자 0x5312ce30 전체를 이미지마다 10회 실행했습니다. 수동 RGB 5회와 필터 5회가 직접 분기 세 곳을 거쳐 이미지당 행렬 함수를 20번 불렀습니다. 호출자와 하위 호출의 복귀 시점마다 보존 레지스터(r4–r11, d8–d15)와 스택 포인터가 그대로였습니다. 각 행렬 호출은 두 입력과 자기 스택 영역만 읽고 18바이트 출력과 자기 영역에만 썼습니다. 호출자 기준 가장 깊은 스택 쓰기는 원본 228바이트에서 후보 232바이트로 늘었습니다. 최종 출력은 두 이미지가 같았습니다.

계산 중 바뀌는 플래그 하나는 차이가 남

따로 만든 합성 행렬 하나에서는 출력 18바이트가 모두 0으로 같았지만 복귀할 때 CPU의 포화 플래그(CPSR.Q)가 원본은 0, 후보는 1로 달랐습니다. 원본은 반올림 상수 4,096을 누산한 뒤에 더하고 새 C 코드는 누산 전에 더해, 계산 중간의 부호 오버플로가 달라지기 때문입니다.

주의

이 플래그 차이가 뒤에 영향을 주는지 별도로 시험했습니다. 원본의 상위 호출 지점 네 곳에서 시작해, 하위 행렬 함수가 돌아올 때 Q만 0 또는 1로 바꿔 넣고 다음 처리 호출 직전까지 실행했습니다. 색공간을 켠 80쌍(160회)에서 실행 경로·쓰기·결과가 모두 같았습니다. 다만 ARM 호출 규약(AAPCS32)은 공개 함수 복귀 시 Q 값을 정하지 않으며 이 시험만으로 다른 분기나 간접 호출에서 Q를 쓰는지까지는 알 수 없습니다.

원본 펌웨어의 헤더·체크섬 검사

원본 펌웨어 안에 들어 있는 헤더 검사와 체크섬 검사 코드를 에뮬레이터에서 직접 실행했습니다. 원본과 후보 모두 정상 입력을 받아들였고 프로젝트 값이나 매직 값을 바꾼 입력은 거절했습니다. 호스트에서 돌린 반례 검사에서는 바깥 합이 틀린 후보, 바깥 합만 다시 맞춘 내부 체크섬 오류, 체크섬을 다시 맞춘 뒤에도 보존 영역을 바꾼 후보를 각각 거절했습니다.

한계와 남은 과제

  • 확인한 것은 행렬 함수 하나와 색공간이 켜진 두 호출 분기뿐입니다. 색공간이 꺼진 분기, 출력이 입력과 겹치는 경우, 실제 실행 시간은 별도 확인이 필요합니다.
  • 이번 후보는 압축을 풀어 전부 저장한 임시 형식이라 원본보다 두 배 넘게 큽니다. 원본 크기에 가깝게 줄이는 방법은 압축 블록을 보존한 재패키징에서 다룹니다.
  • 커진 패키지를 카메라의 RAM과 하드웨어 디코더가 받아들이는지, 실제 업데이트·부팅·저장 경로가 이 후보를 수용하는지는 확인하지 않았습니다. 통합 전 확인 항목 전체는 수정·이식 선행 연구에 있습니다.

재현 방법

검증기는 바이트가 동일한 공식 2.20 원본 패키지 fwdc233b.bin과, 해시가 확인된 Zig 컴파일러를 입력으로 받습니다. 같은 Python 패키지(unicorn==2.1.4, pyelftools==0.33, capstone==5.0.7)를 사용합니다.

python -B tools/verify_recompiled_integration.py fwdc233b.bin "<Zig 폴더>/zig.exe"

실행하면 빌드 결과와 후보를 .private/hq-integration/ 아래 새 작업 폴더에 남깁니다. 검사 중의 후보 파일 이름은 matrix-offline.repacked.unverified.bin입니다. 모든 검사와 기록이 끝나면 matrix-offline.repacked.bin으로 바꿉니다. 공개 결과에는 해시와 합성 사례만 들어 있습니다.
