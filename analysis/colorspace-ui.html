색공간 UI의 선택·확정·리소스 경로

sRGB·AdobeRGB 메뉴의 현재값과 보류 선택을 구분하고 확정·취소가 설정 메모리와 하위 요청에 영향을 주는 조건을 확인했다.

색공간 화면으로 들어가는 경로

촬영 색공간 메뉴의 route 0x0200009f가 SelectMenuController의 descriptor 72번을 고른다. route 처리기 0x5278bb44는 jump table 0x5278bc5c의 대상 0x5278d4c0으로 분기하고 controller의 +0x1d4에 72를 쓴다. 이 숫자는 10진수이며 나머지 주소와 offset은 16진수다. descriptor 주소는 0x536439e0 + 72 × 0x5c = 0x536453c0이다. route·descriptor·타입 정보 근거

controller의 vtable은 0x5364ad68이다. RTTI가 가리키는 20SelectMenuController 문자열을 함께 확인했다. vtable의 open 진입 0x5278ed80은 route 선택 후 표시 갱신으로 이어지고 event 진입 0x5278ef84은 확정·취소·이동 이벤트를 분기한다. 생성자와 open 진입 범위는 정적으로 보존했으며 이번 실행 검사는 route 처리기와 메뉴 구성 함수에서 시작한다.

현재값·보류 선택·확정의 구분

0x5278e05c(controller, 1)은 각 옵션을 현재 캐시값과 비교한다. 일치하면 0x5278e150의 조건부 STRBNE가 controller +1d6을 갱신한다. 마지막에는 이 index를 리스트에 넘긴다. 리스트의 +1ce는 현재 선택 중인 index이며 확정 함수는 이 값을 읽는다. 메뉴 구성 mode 0은 mode 1과 달리 기존 controller index를 사용하는 분기가 있어, 두 모드를 혼동하지 않았다. 메뉴 구성·getter 근거

확정 event e7은 5278db30 → 5278dac0 → 527826f4로 이어진다. 선택 행의 byte +17a가 0이 아니면 setter와 close를 모두 생략한다. 그 밖에는 descriptor의 apply를 호출한 뒤 close 526d8b28로 간다. 취소 event e9는 취소 hook을 확인한 뒤 close로 간다. 색공간 행의 hook은 0이므로 setter를 호출하지 않는다. 이 event 번호의 물리적 버튼·터치 입력 대응은 아직 확인하지 않았다. 확정·취소·행 차단 사례

옵션 index 0·1은 536a6250의 두 바이트를 거쳐 값 0·1이 된다. 기존 파서 52aed898 분석은 이 값을 sRGB·AdobeRGB에 대응시킨다. K-3 II와 Q7에서도 enum이나 event 번호가 같다고 가정하지 않는다. 기존 색공간 요청 분석 · 기종 간 이식 조건

설정 기록과 observer의 조건

apply는 52954be0 → 52954afc를 호출한다. 현재 record는 UserData+4가 가리키는 index byte로 선택하며 실제 색공간 값은 해당 메모리 record의 +35b에 있다. 캐시는 UserData+3b7이다. 이 record 선택을 업데이트용 활성 bank와 동일시하지 않는다. 비휘발성 저장장치에 기록됐다는 증거도 이번 검사에는 없다. setter의 주소 계산·비교·기록 명령

write_record = (record.byte35b != new_value)
            || (UserData.byte3b7 != new_value)

따라서 두 값이 이미 같아도 확정은 setter에 진입한다. 실제 record 기록과 observer 생성만 생략한다. record와 캐시가 불일치하면 record에 같은 값을 다시 쓰는 경우도 있다. 합성 불일치 4조건에서 OR 비교와 주변 record 바이트 보존을 확인했다. 이 불일치가 실제 카메라에서 발생하는 조건은 아직 추적하지 않았다. 기록 횟수·불일치 경계 검사

생성된 observer 5290e520은 record의 값을 캐시와 비교해 다를 때 캐시를 갱신한다. 이어 record byte +2c가 0이 아니면 돌아오고 0이면 52eaacf4 → 52edd820으로 색공간 속성 요청을 전달한다. 즉 캐시 갱신과 하위 요청의 조건은 서로 다르다. 이번에는 callback 수집·전달을 동기 stub으로 대체하고 observer 본체를 원본 ARM으로 실행했다. 실제 callback 컨테이너 수명과 스케줄링은 미검증이다. observer 조건부 store·return

요청 0x145의 하위 수신부와 52ecf4a8 연결은 앞선 분석에서 별도로 검증했다. 이번 UI 검사는 52edd820 진입에서 인자를 포착하므로 메뉴부터 ISP까지 한 번에 실행한 결과로 합산하지 않는다. 기존 1,536사례의 실행 범위

검사 범위와 후속 조건

원본 ARM의 합성 실행 16사례를 통과했다. 확정·취소 조합 8개, record·캐시 불일치 4개, observer gate 1개, 선택 행 차단 2개, 다른 style 값의 리소스 선택 1개다. 확정·취소 조합에서는 같은 객체에 메뉴 구성을 다시 수행해 선택 상태를 재구성했다. 창 소멸·재생성이나 전체 재개방을 검사한 것은 아니다. 16사례·stub·범위 해시

초기 8사례와 추가 경계 6개를 독립 검토했고 이후 조정자가 검사를 16사례로 정리했다. 검토에서 발견한 두 작은 문제는 수정했다. route 검사 전에 descriptor를 ffff로 초기화해 실제 기록을 확인하고 결과의 재개방 표현을 동일 객체의 선택 상태 재구성으로 바꿨다. 새 genuine C 14개와 보조 ARM 범위 12개는 로컬에 저장했다. 공개 자료에는 해시·주소·관계만 포함한다. 독립 검토·원본 산출물 근거

디컴파일러 결과에는 구체적인 한계가 있다. 메뉴 구성 C는 5278e150의 조건부 store를 무조건 대입처럼 표현하고 확정 함수 C는 5278db78의 close tail call을 누락한다. genuine C를 손으로 수정하지 않고 보존했으며 조건과 호출은 원본 ARM과 실행 결과를 기준으로 판단했다.

python verify_colorspace_ui.py rtos.bin --output colorspace-ui-checks.json

재현 도구는 입력 RTOS 또는 전체 decoded 파일의 SHA-256을 확인한다. 기존 출력은 덮어쓰지 않고 assert를 비활성화하는 실행은 거부한다. GUI 배치, focus 직접 설정, heap, callback 전달과 속성 제출의 대체 지점은 결과 JSON에 기록했다. 카메라·렌즈·주변장치 I/O와 비휘발성 기록은 수행하지 않았다.

이식에 필요한 다음 조건은 실제 입력에서 focus 변경까지의 연결, 글꼴·문자열 리소스 해석, 창 생성과 종료 시 객체 수명, 설정 저장·복원이다. 그 뒤 K-3 II와 Q7 각각에서 의미가 대응하는 이벤트·위젯·설정 API를 찾아야 한다. 현재 자료는 기능 단위 대응을 정하는 근거이며 K-3 III의 함수 주소나 객체를 다른 기종에 그대로 복사할 수 있다는 증거는 아니다.

정적 분석과 합성 CPU 실행 결과다. 실제 카메라 입력·완성 화면·저장·전원 재시작·빌드·플래시는 검증하지 않았다. HTML 구조와 링크만 검사했으며 화면 렌더링 검사는 수행하지 않았다.
