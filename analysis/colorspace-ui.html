UI와 화면 자원 · 색공간 화면 1

색공간 선택 화면에서 확정과 취소가 하는 일

메뉴에서 sRGB와 AdobeRGB 중 하나를 고르는 화면이 펌웨어 안에서 어떻게 움직이는지 알아봤습니다. 화면을 다른 기종으로 옮기려면 ‘고르는 중인 값’과 ‘저장된 값’이 언제 갈라지고 언제 합쳐지는지를 먼저 알아야 합니다.

  3. 고르는 중인 값은 확정할 때만 설정으로 넘어갑니다
  4. 확정한 값이 실제로 기록되는 조건
  5. 16가지 사례를 어떻게 실행했는가
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 이 화면에서 색공간 값은 세 군데에 있습니다. 설정 레코드, 그 사본인 현재값 캐시, 그리고 화면에서 고르는 중인 보류 선택입니다. 화면을 채울 때는 캐시를 읽고, 포커스를 옮길 때는 보류 선택만 바뀝니다.
  • 확정하면 보류 선택이 설정 함수로 넘어갑니다. 값이 이미 같으면 설정 함수에 들어가기는 하지만 기록은 생략합니다. 취소는 설정 함수를 부르지 않고 화면을 닫습니다.
  • 기록이 일어나면 관찰자 함수(observer)가 캐시를 레코드 값으로 맞춥니다. 그 뒤 조건이 맞으면 색공간 속성 요청을 아래 단계로 보냅니다.
  • 원본 ARM 코드를 PC 에뮬레이터에서 16가지 합성 상황으로 실행해 확인했습니다. 화면 객체와 포커스는 시험용으로 만들어 넣었고, 그리기 호출은 인수만 기록했습니다. 실제 버튼, 완성된 화면, 전원을 껐다 켠 뒤의 값은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 색공간 메뉴 항목이 descriptor 72번을 고르는 것
  • 확정·취소 8조합의 설정 함수 호출, 기록 횟수, 닫기 요청
  • 레코드와 캐시가 어긋난 4조건, 요청을 막는 바이트, 확정을 막는 행 바이트
  • 행마다 넘기는 아이콘 ID와 문자열 ID

정적 분석 코드를 읽어 판단

  • controller의 가상 함수 표와 타입 이름
  • 생성자와 화면 열기 진입 구간
  • 메뉴 구성의 mode 0 분기

모델 시험 조건으로 정한 것

  • 메뉴·목록·행 객체와 설정 메모리는 합성 객체
  • 보류 선택은 목록 필드에 직접 써 넣음
  • 레이아웃·그리기·힙·콜백 전달은 대체 함수

배경: 색공간 메뉴와 이 문서의 범위

K-3 Mark III의 정지화상 메뉴 5번(Image Capture Settings)에는 Color Space 항목이 있습니다. 선택지는 sRGB와 AdobeRGB 둘이고 기본값은 sRGB입니다(공식 사용설명서 24쪽·48쪽). 선택지가 둘뿐이고 K-3 II와 Q7에도 같은 설정이 있어서, UI 이식 설계의 첫 단위로 이 화면을 골랐습니다.

이 문서는 화면이 구성된 뒤부터 값이 설정 메모리에 닿을 때까지를 다룹니다. 포커스를 위아래로 옮기는 입력은 방향 입력과 포커스에서, 아이콘이 화면 버퍼로 복사되는 과정은 ICONBIN 아이콘 자원에서 다룹니다.

이 문서에 나오는 이름

route
메뉴 항목을 가리키는 32비트 번호입니다. 색공간 항목은 0x0200009f입니다.
descriptor
선택 화면 하나의 동작을 정의한 표의 한 줄(92바이트)입니다. 선택지 개수를 알려 주는 함수, 행을 준비하는 함수, 값을 반영하는 함수의 주소가 들어 있습니다.
controller
여러 선택 화면이 함께 쓰는 객체입니다. 펌웨어에 남은 타입 이름은 SelectMenuController입니다. 어느 descriptor를 쓸지 번호로 기억합니다.
list와 행
list는 선택지 행을 담는 목록 객체이고, 지금 포커스가 놓인 행 번호를 가집니다. 행마다 아이콘 표시부와 글자 표시부가 있습니다.
UserData
사용자 설정을 담는 메모리 객체입니다. 설정 레코드와 현재값 캐시가 여기에 있습니다.
setter·observer
setter는 설정값을 기록하는 함수, observer는 기록 뒤에 불려 뒷정리를 하는 함수입니다.

메뉴 항목에서 화면 구성까지

색공간 메뉴 항목은 공용 controller에 descriptor 72번을 지정합니다. 이 descriptor에 든 함수 다섯 개가 화면의 내용과 동작을 정합니다.

  1. 메뉴 항목route 0x0200009f
    시험에서는 직접 넣어 준 값
  2. route 처리기분기 표에서 색공간 칸을 골라 실행
  3. 번호 기록controller에 descriptor 번호 72(10진수)를 기록
  4. 메뉴 구성descriptor의 함수를 불러 행 두 개를 준비

descriptor는 주소 0x536439e0에서 시작하는 표의 한 줄이고 한 줄은 0x5c(92)바이트입니다. 72번 줄의 주소는 0x536439e0 + 72 × 0x5c = 0x536453c0입니다. 이 문서에서 72만 10진수이고 나머지 주소와 offset은 16진수입니다.

표의 각 함수 주소 옆에는 보정값 word가 하나씩 붙어 있고 이 줄에서는 모두 0입니다. C++의 멤버 함수 포인터가 함수 주소와 보정값의 쌍으로 표현되는 것과 같은 모양입니다(Itanium C++ ABI의 설명). 보정값이 0이라 이 줄에서는 함수를 직접 부르는 것으로 해석했습니다. 표의 형식 자체는 보정값에 따라 가상 호출도 할 수 있으므로, 다른 메뉴까지 직접 호출이라고 일반화하지 않았습니다.

행이 고르는 아이콘과 문자열

행 준비 함수는 선택지마다 아이콘 ID와 문자열 ID를 하나씩 정해 행 그리기 함수에 넘깁니다. 아이콘 ID는 스타일 값에 따라 두 벌이 있습니다.

행 그리기 함수는 행의 +0x180에 있는 아이콘 표시부(IconView)에 아이콘 ID를, +0x18c의 글자 표시부에 문자열 ID를 설정합니다. IconView가 이 ID로 아이콘 픽셀을 찾는 과정은 ICONBIN 아이콘 자원에 있습니다.

주의

시험에서는 행 그리기 함수를 ‘ID만 기록하는 대체 함수’로 바꿨습니다. 그래서 확인한 것은 어떤 ID가 넘어가는지까지입니다. 스타일 값의 공식 의미, 언어별 실제 문자열, 글꼴, 완성된 화면은 확인하지 않았습니다. descriptor에 있는 제목 후보 ID 0x1f3과 머리글 함수가 넘기는 0x1f5는 서로 다른 ID이며, 둘을 같은 화면 제목으로 합치지 않았습니다.

고르는 중인 값은 확정할 때만 설정으로 넘어갑니다

화면을 채울 때는 캐시의 현재값을 읽습니다. 고르는 동안에는 목록의 포커스 번호만 바뀌고, 확정 이벤트가 와야 그 번호가 설정 함수로 넘어갑니다. 취소는 아무것도 기록하지 않습니다.

시험 조건

보류 선택은 방향 이벤트로 옮긴 것이 아니라 list+0x1ce에 값을 직접 써 넣은 것입니다. 이벤트 번호 0xe7·0xe9도 시험이 넣어 준 값이며, 어떤 버튼이나 터치가 이 번호를 만드는지는 확인하지 않았습니다. 방향 이벤트가 실제로 포커스를 옮기는 과정은 다음 문서에서 따로 실행했습니다.

확정한 값이 실제로 기록되는 조건

setter는 새 값이 레코드나 캐시 중 어느 하나와라도 다르면 레코드에 기록합니다. 둘 다 이미 같으면 기록과 observer 생성을 생략합니다. 하위 요청을 보낼지는 observer가 다른 조건으로 따로 정합니다.

기록 여부를 식으로 쓰면 아래와 같습니다.

write_record = (record.byte35b != new_value)
            || (UserData.byte3b7 != new_value)

그래서 같은 값을 다시 확정해도 setter에는 들어갑니다. 레코드 기록과 observer 생성만 빠집니다. 반대로 레코드와 캐시가 서로 어긋나 있으면, 레코드에 이미 있는 값과 같은 값을 다시 쓰는 경우도 생깁니다.

네 조건 모두 화면을 채울 때의 포커스는 캐시 값을 따랐습니다. 기록 전후로 레코드 앞쪽 0x400바이트를 비교해 +0x35b 한 바이트만 바뀐 것을 확인했습니다.

시험 조건

레코드와 캐시가 어긋난 상태는 시험이 만들어 넣은 것입니다. 실제 카메라에서 이런 불일치가 언제 생기는지는 추적하지 않았습니다.

observer가 하는 두 가지 일은 조건이 다릅니다

  • 캐시 맞추기 — 레코드의 값을 캐시와 비교해 다를 때만 캐시를 갱신합니다.
  • 하위 요청 — 레코드의 바이트 +0x2c가 0일 때만 색공간 속성 요청 함수로 넘어갑니다. 0이 아니면 캐시만 맞추고 돌아갑니다.

+0x2c를 1로 둔 사례에서 레코드와 캐시는 각각 한 번씩 기록됐고 속성 요청은 없었습니다. 이 바이트가 카메라에서 무엇을 뜻하는지는 확인하지 않았습니다.

주의

여기서 ‘레코드’는 UserData의 +4가 가리키는 번호 바이트로 고르는 메모리 안의 레코드입니다. 펌웨어 업데이트에서 말하는 활성 bank와 같은 것으로 보지 않습니다. 이 시험에는 값이 비휘발성 저장 장치에 기록됐다는 증거도 없습니다.

구간의 끝 주소는 포함하지 않습니다. 함수 14개의 디컴파일 결과와 보조 구간 12개의 ARM 목록은 공개하지 않고 로컬에 보관합니다. 공개 자료에는 구간별 SHA-256, 주소, 호출 관계만 있습니다(colorspace-ui-evidence.json).

디컴파일 결과를 그대로 믿지 않은 이유

디컴파일러(angr 10.0.5)가 만든 C 코드에는 원본 명령과 다른 곳이 두 군데 있었습니다. 판단은 원본 ARM 명령과 실행 결과를 기준으로 했고, 디컴파일된 C는 손대지 않고 보관했습니다.

  • 메뉴 구성 함수의 C는 0x5278e150의 조건부 저장을 무조건 대입처럼 표현합니다.
  • 확정 함수의 C는 0x5278db78의 닫기 꼬리 호출을 빠뜨립니다.
조사 경과: 독립 검토에서 고친 것

처음 만든 8개 사례와 추가 경계 6개를 다른 검토자가 독립적으로 다시 실행했습니다. 그 뒤 사례를 16개로 정리했고, 늘어난 사례는 조정자가 따로 다시 실행했습니다. 검토에서 나온 작은 문제 두 가지를 고쳤습니다.

  • route 검사 전에 descriptor 번호를 0xffff로 초기화해, 72가 실제로 기록되는지 확인하도록 했습니다.
  • 결과의 ‘다시 열기’라는 표현을 ‘같은 객체의 선택 상태 재구성’으로 바꿨습니다.

검토 범위는 디컴파일 파일 14개와 ARM word 5,194개였고, 중요도가 높은 지적은 없었습니다.

한계와 남은 과제

  • 입력 — 이벤트 0xe7·0xe9와 실제 버튼·터치의 대응을 확인하지 않았습니다.
  • 화면 — 레이아웃, 표시 여부, 아이콘·글자 그리기는 대체 함수였습니다. 글리프와 픽셀 배치는 재현하지 않았습니다.
  • 창의 수명 — 생성자와 화면 열기 진입은 정적으로만 봤습니다. 창을 없애고 다시 만드는 과정은 실행하지 않았습니다.
  • 아래 단계 — 시험은 속성 요청 함수 입구에서 멈춥니다. 메뉴에서 ISP까지를 한 번에 실행한 결과가 아닙니다.
  • 저장 — 카메라·렌즈·주변 장치 입출력과 비휘발성 기록은 하지 않았습니다.

화면을 옮기려면 실제 입력에서 포커스 변경까지의 연결, 글꼴·문자열 자원의 해석, 창을 만들고 닫을 때의 객체 수명, 설정의 저장과 복원을 더 확인해야 합니다. 그 다음에 K-3 II와 Q7에서 뜻이 대응하는 이벤트·위젯·설정 함수를 각각 찾아야 합니다. 이 문서의 자료는 기능 단위의 대응을 정하는 근거입니다. K-3 Mark III의 함수 주소나 객체를 다른 기종에 그대로 복사할 수 있다는 증거가 아닙니다.

검증기는 RTOS 이미지 또는 추출기가 만든 decoded.bin 전체를 입력으로 받고, SHA-256이 아래 값과 같을 때만 실행합니다. Python 패키지 unicorn이 필요합니다.
