펌웨어 업데이트 과정 · bank 선택

RTOS가 쓰는 bank와 BOOT가 읽는 bank의 선택 조건

업데이트가 이미지를 저장소에 쓰는 코드와, 다음 부팅 때 이미지를 읽는 코드는 저장 위치를 서로 다른 값으로 고릅니다. 두 값이 어긋나면 어떻게 되는지 같은 표 하나를 두 코드에 넘겨 시험했습니다.

이 문서에서

  1. 배경: bank와 선택값
  2. 한 표를 함께 써도 두 선택값은 저절로 맞춰지지 않습니다
  3. 원본 PARTPARA가 만든 INITFS 위치는 BOOT의 읽기 요청까지 그대로 갑니다
  4. 수정한 이미지가 부팅까지 가려면 거쳐야 하는 단계
  5. 두 선택값을 만드는 코드는 아직 찾지 못했습니다
  6. 검증 범위와 한계
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 파티션 표에는 리소스마다 저장 위치 설명자가 bank 0과 bank 1 두 벌 있습니다. RTOS의 쓰기 함수는 FwPartition 객체 안의 1바이트로, BOOT는 표의 레코드에 든 값으로 bank를 고릅니다. 두 값은 서로 다른 곳에 있습니다.
  • 같은 합성 표를 RTOS 쓰기 코드와 BOOT 적재 코드에 차례로 넘겨 12사례를 실행했습니다. 두 값이 같으면 BOOT가 새 payload를 읽었습니다. 다르면 쓰기가 성공했어도 BOOT는 다른 bank에 있던 기존 바이트를 읽었습니다.
  • 쓰기 함수와 그 앞의 배치 준비 함수는 BOOT가 보는 값을 바꾸지 않았습니다. 쓰기가 성공한 뒤 표에서 바뀐 것은 고른 설명자의 길이와 블록 수뿐입니다.
  • 실제 카메라의 표에 어떤 값이 들어 있는지는 모릅니다. 생성자는 RTOS 쪽 값을 0으로 만듭니다. 0이 아닌 값을 만드는 코드는 찾지 못했습니다. 실제 표가 bank 0을 가리킨다면 따로 전환하지 않아도 두 값은 맞습니다.
  • 별도 INITFS 시험에서는 원본 PARTPARA가 정한 INITFS 위치가 저장소 모델을 거쳐 BOOT의 읽기 요청에 그대로 들어갔습니다. 실제 저장 장치 기록, 재시작, 인증은 실행하지 않았으므로 수정한 이미지가 받아들여지거나 부팅된다는 증거가 아닙니다.

확인 원본 코드 실행으로 확인

  • RTOS 생성자·배치 준비·쓰기 함수와 BOOT 적재 조각 12사례
  • 쓰기 성공 때 바뀌는 표 바이트는 길이와 블록 수뿐
  • BOOT는 레코드 +4의 하위 16비트만 사용
  • 통합 이미지 입력과 RTOS·BOOT 분리 입력에서 같은 결과

정적 분석 코드를 읽어 판단

  • BOOT 진입 경로가 mode 값 2를 다루는 방식
  • 실제 부팅에서 표 사본을 선택하고 다시 읽는 경로
  • Log·SystemControl 등 후보에서 제외한 코드

모델 시험 조건으로 정한 것

  • 같은 RAM 표를 두 단계에 그대로 넘김(저장·재읽기·reset 생략)
  • 레코드 +4의 값, bank 1 강제 설정, mode 2 주입
  • 저장 매체는 시작 블록별 바이트 사전
  • CPU는 Unicorn의 Cortex-A15 모델

미확인 확인하지 않은 것

  • 실제 표의 초깃값과 레코드 +4를 만드는 코드
  • RTOS 쪽 값을 0이 아니게 만드는 코드
  • 표와 헤더의 영속 기록, 다음 부팅의 재읽기
  • Boot ROM 인증과 실제 부팅

배경: bank와 선택값

기기 펌웨어는 이미지를 두 벌 저장할 자리를 두는 경우가 많습니다. 새 이미지를 쓰는 동안 문제가 생겨도 다른 한 벌로 부팅할 수 있게 하려는 설계입니다. Android의 A/B 업데이트 문서는 이 두 벌을 슬롯이라 부르며 부트로더가 다음에 부팅할 슬롯을 표시 값으로 고른다고 설명합니다. 이런 구조에서는 “어느 쪽에 썼는가”와 “어느 쪽으로 부팅하는가”가 맞아야 새 이미지가 실행됩니다.

K-3 Mark III의 파티션 표에도 리소스마다 저장 위치 설명자가 두 벌 있습니다. 분석 기록은 이것을 bank라고 부릅니다. 이 카메라가 Android와 같은 전환 정책을 쓴다는 뜻은 아닙니다. bank를 언제 어떻게 바꾸는지는 아직 찾지 못했습니다. 이 문서는 그보다 좁은 질문을 다룹니다. 쓰는 코드와 읽는 코드가 각각 무엇을 보고 bank를 고르는가입니다.

파티션 표의 구조

  • 표 전체는 0x10e00바이트입니다. 0x870바이트짜리 레코드 32개로 이루어집니다. 레코드 하나가 리소스 하나에 대응합니다.
  • 레코드 안에는 bank 설명자가 0x434바이트 간격으로 놓입니다. 설명자는 적재 주소(+8), 진입 주소(+0x0c), 시작 블록(+0x10), 바이트 길이(+0x14), 블록 수(+0x18)를 담습니다.
  • 레코드의 공통 필드는 +0과 +4 두 개입니다. +0은 용량 필드입니다. BOOT는 이 값이 0이면 리소스가 없다고 보고 지나갑니다. 이 문서에서는 이 쓰임을 존재 표시라고 부릅니다. +4는 bank 선택값입니다.
  • RTOS 이미지는 리소스 1번입니다. 부팅 때는 BOOT 단계가 이 레코드를 보고 RTOS를 RAM으로 읽어 옵니다.

이름이 비슷한 네 가지 선택값

펌웨어에는 “둘 중 하나를 고르는 값”이 네 군데 있습니다. 서로 뜻이 다르며 항상 같은 값을 갖는다는 근거도 없습니다. 이 문서가 다루는 것은 앞의 둘입니다.

선택값 네 가지 (부팅·저장소 문서의 정리)

한 표를 함께 써도 두 선택값은 저절로 맞춰지지 않습니다

쓰기 함수는 객체 안의 1바이트만 봅니다. BOOT는 레코드 +4만 봅니다. 쓰기 경로의 어떤 코드도 레코드 +4를 고치지 않았습니다.

시험한 방법

  1. RTOS 쓰기객체 +0x10으로 설명자 선택, payload 쓰기, 길이와 블록 수 갱신
  2. 합성 표 넘기기같은 RAM 표를 그대로 넘김. 저장·재읽기·reset은 생략
  3. BOOT 선택과 읽기레코드 +4의 하위 16비트로 설명자 선택, 블록 읽기
  4. 결과 비교새 payload가 RAM에 도착했는지, 진입 주소가 저장됐는지
시험 조건

실제 업데이트에서는 1단계와 3단계 사이에 표를 저장 장치에 기록합니다. 그다음 카메라를 재시작하면 부팅 단계가 표를 다시 읽습니다. 시험은 이 과정을 건너뛰고 메모리의 표를 그대로 다음 단계에 넘겼습니다. 저장 매체는 “시작 블록 번호 → 바이트”를 담는 사전으로 흉내 냈습니다. payload는 513바이트(2블록)입니다. bank 0과 bank 1의 설명자는 시작 블록과 적재 주소가 서로 다르게 만들었습니다.

쓰는 쪽에서 확인한 것

  • FwPartition 생성자는 객체의 +0x10을 0으로 만듭니다. 쓰기 함수는 이 바이트에 0x434를 곱해 설명자를 고릅니다.
  • 쓰기 함수는 먼저 용량을 검사합니다. 시작 블록에 필요한 블록 수를 더한 값이 다음 번호 리소스의 시작 블록을 넘으면 쓰지 않고 0을 돌려줍니다.
  • 하위 쓰기가 0이 아닌 값을 돌려주면 고른 설명자의 +0x14(길이)와 +0x18(블록 수)을 고칩니다. 표에서 바뀐 바이트는 이 두 칸뿐이었습니다. 쓰기가 실패하거나 용량 검사에서 거절되면 이 두 값도 그대로 남았습니다.
  • 쓰기 앞에 실행되는 배치 준비 함수는 용량·주소·크기 필드를 채웁니다. 이 함수도 레코드 +4는 건드리지 않았습니다.

읽는 쪽에서 확인한 것

  • BOOT의 RTOS 적재 분기는 리소스 1번 레코드의 +0이 0이면 아무것도 읽지 않고 지나갑니다.
  • 0이 아니면 +4를 읽어 하위 16비트만 남긴 뒤 그 값에 0x434를 곱해 설명자를 고릅니다. 상위 16비트를 바꿔도 고르는 bank는 같았습니다.
  • 읽을 블록 수는 설명자의 +0x18입니다. 이 값이 0이면 +0x14의 길이를 512로 나눠 올림한 값을 씁니다.
  • 읽기가 성공하면 설명자의 진입 주소(+0x0c)를 두 곳에 저장합니다. 읽기가 실패하면 저장하지 않고 실패 분기로 갑니다.

새 payload가 읽히려면 모두 맞아야 하는 조건

넷째 조건은 “두 bank 번호가 같아야 한다”와 조금 다릅니다. BOOT가 고른 설명자가 새 바이트의 저장 위치를 가리켜야 합니다. 시험 표는 두 bank의 시작 블록을 다르게 두었기 때문에 번호가 같아야만 이 조건이 맞았습니다. 서로 다른 bank가 같은 시작 블록을 가리키면 번호가 달라도 새 payload를 읽습니다. 이 경우는 공개 도구 밖의 로컬 검토 사례로 확인했습니다.

결과를 읽을 때 주의할 점
  • 11번은 값을 만드는 코드를 찾았다는 뜻이 아닙니다. 생성자가 0으로 만든 값을 시험 코드가 1로 덮어쓴 것입니다.
  • 9번은 조각만 본 것입니다. BOOT의 실제 진입 경로는 0x0100fffc를 처음 읽었을 때 값이 2이면 리소스 적재 호출 자체를 건너뜁니다. 그 밖의 경우에는 mode 값을 다시 읽어 전역 상태에 저장한 뒤 적재 코드를 부릅니다. 조각에 2를 직접 넣은 결과를 실제 재부팅 경로에서 그 분기에 도달한다는 증거로 쓰지 않습니다(BOOT 진입 조건).
  • 6·7·8번의 “그대로 남는다”는 시험 설정입니다. 실패를 주입했을 때 매체와 목적지 바이트를 보존하도록 만든 것은 시험 쪽 정책입니다. 실제 저장 매체에 일부만 기록된 상태나 전원이 끊긴 경우는 다루지 않았습니다.
  • 실제 표의 값은 관측하지 않았습니다. 실제 표가 bank 0을 가리킨다면 1번과 같은 상황이므로 두 값은 맞습니다. 그 표를 얻지 못했기 때문에 현재 카메라의 상태로 단정하지 않습니다.

  • 시험 표: bank 0은 시작 블록 100, bank 1은 시작 블록 200. 쓰기 전의 블록 수 2, 길이 1,024. payload 513바이트를 쓰면 길이 513, 블록 수 2가 됩니다.
  • 대체한 함수: 블록 수 올림 0x532974a8, 블록 크기 getter 0x532971dc(512), 진단 출력 0x530fced4, 하위 쓰기 0x52ff5708, BOOT 블록 읽기 0x50b03f04. BOOT가 블록 수 0에서 길이를 올림하는 계산은 원본 명령으로 실행됐습니다.
  • 쓰기 함수의 용량 검사는 32비트 덧셈과 8비트 리소스 번호를 씁니다. 시험은 작은 값과 리소스 1번만 썼으므로 일반적인 범위에서 안전한지는 확인하지 않았습니다.
  • 구간 해시와 명령별 해시는 update-bank-selection-evidence.json, 사례별 인수와 표 변경 기록은 update-bank-selection-checks.json에 있습니다.

원본 PARTPARA가 만든 INITFS 위치는 BOOT의 읽기 요청까지 그대로 갑니다

원본 RTOS가 PARTPARA로 만든 INITFS 설명자(시작 LBA, 블록 수, 목적지)가 저장소 모델을 거쳐 원본 BOOT의 읽기 인수로 그대로 쓰였습니다.

위의 12사례는 같은 RAM 표를 그대로 넘겨 선택값의 영향만 비교했습니다. 이 시험은 압축을 푼 원본에서 PARTPARA와 INITFS를 읽습니다. 원본 RTOS가 만든 표를 저장소 모델에 기록했다가 BOOT 조각에서 다시 읽게 했습니다. Cortex-A7 ARM 모델에서 원본 코드 조각 여섯 개를 실행하며 원본 명령 콜백 3,001회와 표 쓰기 194회를 기록했습니다.

시험 조건

객체 연결, 단계별 진입, BOOT의 선택값과 표 LBA는 재현 조건입니다. 표 기록과 BOOT의 표 재적재는 시작 LBA를 키로 바이트를 보관하는 모델이 처리했습니다. kind 4의 외부 패키지 처리, 실제 표 사본 선택과 eMMC 전송, 물리 주소 배치와 인증은 이 시험에서 확인하지 못했습니다.

Stubby ROMFS 문서의 로더 시험은 같은 원본 INITFS를 0x43000000에 미리 놓고 헤더 읽기와 DTB 속성 기록을 확인했습니다. 이 시험은 BOOT가 그 주소로 읽기를 요청하는 데까지, Stubby 시험은 그 주소의 바이트를 쓰는 데까지 다룹니다. 두 시험 사이에서 실제로 바이트가 그 주소에 놓이는 과정은 확인하지 않았습니다.

INITFS 시험의 함수, 대체 호출, 근거
  • 원본 kind 분기 0x52ff2a24가 layout 함수를 호출합니다. 이 함수는 PARTPARA의 516바이트 payload에서 항목 32개를 읽습니다. index 6의 목적지는 0x52ff200c에서 읽어 0x52ff2020에서 0x50b733a8에 씁니다.
  • INITFS의 index 6, 원본 길이, 원본 바이트를 둔 주소는 재현 도구가 indexed writer 0x52ff586c에 넘겼습니다. 이 함수는 다음 리소스의 시작 LBA와 범위를 비교했습니다. 하위 쓰기가 1을 돌려준 뒤에는 길이와 블록 수를 차례로 기록했습니다.
  • 대체한 호출: 진단 0x530fced4, 하위 쓰기 0x53297a84, BOOT 읽기 0x50b03f04. 여섯 번의 대체 호출에서 LR 복귀, r0 반환값, r1–r3·r12 변경, SP와 r4–r11 보존을 확인했습니다. 대체 호출이 규칙대로 돌아왔는지만 본 검사입니다.
  • BOOT의 INITFS 읽기 호출은 0x50b01090에 있습니다. 최종 PC 0x50b01094는 INITFS 읽기 모델에서 돌아온 지점입니다. 그 주소에서 하는 원본 상태 비교는 실행하지 않았습니다.

두 선택값을 만드는 코드는 아직 찾지 못했습니다

레코드 +4를 “덮어쓰는” 경로는 확인했습니다. 그러나 그 값을 “만들어 내는” 코드는 찾지 못했습니다. 후보로 보였던 코드 몇 개는 다른 객체를 다루는 것으로 판명됐습니다.

M0가 받아 온 선택값을 BOOT까지 그대로 옮기는 경로는 리소스 선택값과 헤더 기록 조건에서 따로 시험했습니다.

살펴본 경로와 판단
경로확인한 것판단
BOOT의 초기 표 읽기, RTOS의 sys_fwtable 전체 표 재읽기매체의 바이트를 RAM의 표에 기록합니다. 레코드 +4도 함께 덮입니다(전체 표 읽기 · 주소 근거).밖에서 온 값을 옮기는 경로입니다. 그 값을 어떤 함수가 만들어 매체에 저장했는지는 별개의 문제입니다.

SRAM remap의 공개 소스 후보M8M 설정이나 전용 device tree 노드를 요구하는 코드입니다. SC2000A의 실제 설정으로 대입할 근거가 없습니다(기종·DT 조건 · M0 원본 근거).reset에서 본 0x4dffb208과 0x4dfff0xx 기록을 remap이나 인증 해제라고 이름 붙이지 않습니다.

다음에 볼 곳은 두 가지입니다.

  • bank 쪽: 매체에 놓일 표를 만드는 경로와, 계산으로 얻는 FwPartition 포인터를 쓰는 코드입니다. 이미 제외한 Log 상태, mutex, 다른 헤더의 같은 오프셋을 다시 bank 기록 코드로 세지 않습니다.
  • 부팅 쪽: 보드 선택 함수 0x3ffe3594가 고르는 본체, 해당 레지스터의 공식 정의, 선행 ROM의 설정입니다.

패키지 체크섬을 통과한다는 사실에서 Boot ROM 인증이 없다는 결론을 끌어내지 않습니다.

검증 범위와 한계

12사례는 통합 이미지 하나를 넣었을 때와 RTOS·BOOT를 따로 넣었을 때 같은 결과를 냈습니다.

  • 실행한 코드: RTOS의 생성자, 배치 준비 함수, 쓰기 함수 전체와 BOOT의 조각 0x50b00c70–0x50b00cf4입니다. 12사례에서 원본 코드로 들어간 횟수는 모두 37번입니다.
  • 디컴파일 C: 이전 분석에서 만든 C 출력 3개를 그대로 다시 쓰고 원본과 해시를 대조했습니다. 새로 복구한 함수로 세지 않았습니다. 두 선택 경로를 설명하는 의사코드도 따로 써서 로컬에 보관합니다. 분석자가 쓴 설명이며 원본 소스가 아닙니다.
  • 로컬 검토 2사례: 서로 다른 bank가 같은 시작 블록을 가리킬 때 새 payload를 읽는 것을 확인했습니다. 하위 쓰기가 2를 돌려주면 상위 함수도 2를 그대로 돌려줬습니다. 쓰기 성공을 1로 바꿔 돌려준다고 해석하면 안 됩니다. 이 2사례는 공개 도구의 12사례에 들어 있지 않습니다.
  • 공개 범위: 공개 자료에는 분석, 해시, 직접 만든 합성 시험만 있습니다.

한계

  • 12사례는 같은 RAM 표를 넘겼습니다. INITFS 시험은 저장소 모델에 표를 기록했다가 복원했습니다. 실제 저장 장치와 reset은 실행 범위 밖입니다.
  • BOOT의 초기화, 다른 리소스, 실제 mode 전환, 진입 주소로 들어가는 실행, 주변 장치, 인증은 시험 밖입니다.
  • 합성 매체는 시작 블록 번호별로 바이트를 저장합니다. 시작 블록이 다른 두 구간이 일부만 겹치는 경우는 흉내 내지 못합니다.
  • M0가 쓰는 주소와 BOOT가 읽는 주소를 합성 RAM에서 임의로 같은 메모리로 묶지 않았습니다.
  • 동시에 선택값이 바뀌는 경우는 다루지 않았습니다.
  • 펌웨어 빌드와 플래시 기록은 하지 않았습니다. 실제 카메라의 업데이트, 부팅, 복구 성공은 확인하지 못했습니다.

INITFS 시험에는 PARTPARA와 INITFS를 포함한 전체 decoded.bin이 필요합니다. 원본 입력과 레코드, 명령 구간 16개의 해시를 확인합니다. 재사용하는 bank 검증기는 줄 끝을 LF로 통일해 고정 해시와 비교한 다음, 검사한 바이트를 실행합니다.

--boot는 RTOS를 따로 넣을 때만 씁니다. 출력 경로에 기존 파일, hardlink, 대상이 없는 symlink가 있으면 멈춥니다. Python을 -O로 실행해 assert를 끄면 실행을 거부합니다.
