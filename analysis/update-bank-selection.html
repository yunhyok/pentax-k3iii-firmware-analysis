수정 이미지의 bank 선택과 부팅 수용 조건

RTOS가 payload를 쓰는 bank와 BOOT가 읽을 bank는 서로 다른 필드에서 나온다. 같은 합성 파티션 표를 두 원본 경로에 전달해 쓰기 성공 뒤에도 새 payload가 선택되지 않는 조건을 확인했다. 실제 비제로 bank 생산자와 공통 레코드 +4의 값 생성 정책은 아직 찾지 못했다.

연구 개요M0·BOOT·저장소같은 표의 쓰기·읽기수정 이미지 수용 조건남은 조사검증 범위

한 표를 공유해도 선택값은 자동으로 맞춰지지 않는다

원본 생성자 0x52ff52d4는 FwPartition의 byte +0x10을 0으로 만든다. 쓰기 함수 0x52ff586c는 이 byte로 bank 설명자를 고른다. BOOT의 RTOS 적재 분기 0x50b00c88은 리소스 index 1의 공통 레코드 +4를 읽고 하위 16비트로 bank를 고른다. 레코드 간격은 0x870, bank 간격은 0x434다. 원본 범위·주소·해시.

쓰기 성공 후 바뀐 표의 바이트는 선택한 설명자의 +0x14(길이)와 +0x18(블록 수)뿐이었다. 실패·용량 거부에서는 이 두 값도 보존됐다. 앞단 layout 함수 0x52ff1ea8는 용량·주소·크기 필드를 준비하지만 공통 +4를 맞추지는 않는다. 합성 매체는 시작 블록별로 바이트를 저장한다. 시작 블록이 다른 구간의 부분 중첩이나 실제 전송 실패 때의 부분 기록은 이 시험 범위 밖이다. 12사례의 인수·표 변경·읽기 결과.

따라서 이번 fixture에서 새 payload를 읽으려면 쓰기가 성공하고 존재 조건을 통과하며 BOOT가 새 바이트를 기록한 위치를 선택하고 읽기가 성공해야 한다. 서로 다른 bank가 같은 저장 위치를 가리키는 경우까지 배제한 결론은 아니다. 실제 정상 표가 bank 0을 가리킨다면 별도의 비제로 전환 없이도 선택값은 맞을 수 있다. 그 런타임 표를 확보하지 못했으므로 현재 카메라의 상태로 단정하지 않는다.

숫자 mode 2를 주입한 한 사례는 선택한 BOOT 조각의 읽기 생략만 확인했다. BOOT 진입 경로는 0x0100fffc를 처음 읽었을 때 값이 2면 리소스 적재 호출을 생략한다. 그 외에는 모드 값을 다시 읽어 전역 상태에 저장한 뒤 로더를 호출한다. 조각에 mode 2를 직접 넣은 결과를 실제 재부팅 경로의 도달 증거로 사용하지 않는다. BOOT 진입 조건.

수정 이미지 수용 과정과 남은 검증

다음 표는 앞선 검증을 단계별로 묶은 것이다. 일부는 원본 ARM 전체 함수, 일부는 선택한 조각과 대체 호출로 검증했다. 각 행의 성공을 전체 업데이트의 성공으로 합산하지 않는다.

비제로 bank와 record+4의 실제 생산자는 어디까지 좁혔는가

공통 record +4를 덮는 경로 자체는 확인했다. 초기 BOOT 표 읽기와 RTOS sys_fwtable의 전체 표 재읽기가 매체 바이트를 RAM에 기록한다. 그러나 이는 외부 값의 전달이며 어떤 함수가 그 값을 생성해 저장했는지는 별도 문제다. 이번 쓰기·layout 경로에서도 해당 필드는 유지됐다. 전체 표 읽기 · 주소 근거.

Log의 FwPartition alias는 index 20–25 설명자를 읽어 별도 캐시를 만들며 Log의 +4 store는 heap 상태의 사용 바이트 수였다. SystemControl은 보관한 FwPartition으로 잠금·해제를 요청하고 mutex의 카운터를 갱신한다. 이들을 bank 기록자로 분류하지 않았다. Log clear는 설명자 크기 필드를 지울 수 있으므로 “Log 전체가 표를 보존한다”는 결론도 내리지 않는다. 객체별 alias 분석.

SRAM remap의 공개 소스 후보도 적용 조건을 확인했다. M8M 설정이나 전용 DT 노드를 요구하는 코드를 SC2000A의 실제 설정으로 대입할 근거가 없다. reset에서 관찰한 0x4dffb208과 0x4dfff0xx 기록을 remap 또는 인증 해제로 명명하지 않았다. 다음 정적 조사 대상은 보드 선택 함수 0x3ffe3594의 선택된 본체, 해당 레지스터의 공식 정의, 선행 ROM 설정이다. 기종·DT 조건 · M0 원본 근거.

bank 쪽의 다음 연결점은 매체 표를 만드는 경로와 계산된 FwPartition alias다. 이미 배제한 Log 상태·mutex·다른 헤더의 같은 오프셋을 다시 bank 기록자로 세지 않는다. 패키지 체크섬 통과로 Boot ROM 인증 부재를 추론하지 않는다.

저장 자료와 검증 범위

원본 RTOS 생성자·layout·indexed writer와 BOOT의 0x50b00c70–0x50b00cf4 조각을 실행했다. 기존 genuine C 3개를 재사용하고 원본과 해시를 대조했다. 새 함수 복구 수로 세지 않았다. 두 선택 경로를 설명하는 의사코드도 별도로 작성해 로컬에 저장했다. 이 의사코드는 분석자가 작성한 설명이며 원본 소스가 아니다. 공개 자료에는 분석·해시·작성한 합성 시험만 포함한다. 범위와 대체 호출 · 검사 결과 · 재현 도구.

12사례는 단일 decoded 입력과 분리한 RTOS·BOOT 입력에서 같은 결과를 냈다. 실제 표 commit·reload·reset은 실행하지 않고 같은 RAM 표와 합성 바이트 저장소를 인계했다. BOOT 초기화·다른 리소스·실제 모드 전환·진입점 실행·주변장치·인증은 시험 밖이다. 전송 실패 때 바이트를 보존하는 것은 fixture의 정책이며 장치 동작을 뜻하지 않는다.

별도 로컬 검토 2사례에서는 다른 bank가 같은 시작 블록을 가리키면 새 payload를 읽을 수 있음을 확인했다. 또한 하위 쓰기 반환값 2는 상위에서도 2로 유지됐다. 쓰기 성공을 boolean 1로 정규화한다고 해석하지 않는다. 이 2사례는 공개 도구의 12사례에 포함하지 않았다.

python verify_update_bank_selection.py decoded.bin --output bank-decoded.json
python verify_update_bank_selection.py rtos.bin --boot boot.bin --output bank-split.json

입력 SHA-256을 고정하고 기존 파일·hardlink·dangling symlink 출력 및 assert 비활성 실행을 거부한다. --boot는 분리 RTOS 입력에만 사용한다. M0와 BOOT의 두 주소를 합성 RAM에서 임의로 alias시키지 않았다. 펌웨어 빌드·플래시는 이 분석에서 수행하지 않았다.
