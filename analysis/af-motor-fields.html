PafMotor와 PafPulse의 필드를 누가 쓰고 읽는가

요청 3의 계산은 PafMotor의 두 보정 필드를 읽지만, 그 값을 0이 아닌 수로 채우는 코드는 아직 모릅니다. 두 객체의 필드에 손대는 코드를 하나씩 실행해 어느 필드가 어디서 바뀌는지 정리했습니다.

이 문서에서

  1. 배경: 왜 두 필드를 쫓는가
  2. 필드마다 손대는 코드가 다릅니다
  3. PafPulse +0x56은 설정 레코드에서 옵니다
  4. 원본 실행 10건의 결과
  5. 찾지 못한 입력 생산자
  6. 재현과 결과 비교
  7. 근거 파일과 참고 자료

핵심 요약

  • PafMotor 생성자는 +0x56과 +0x68을 0으로 초기화합니다. 이번에 실행한 10건 가운데 이 두 필드를 다시 쓴 코드는 없었고 비영값의 출처는 여전히 모릅니다.
  • 디버그 요청은 요청 word를 두 값으로 나눠 PafMotor +0x78/+0x7a에 씁니다. 해제 요청은 조건에 따라 두 값을 지우거나 그대로 둡니다.
  • 설정 레코드의 값이 PafIntegralConfig를 거쳐 PafPulse +0x56에 저장되고 별도의 LensInfo 계산이 그 값을 분모로 읽습니다. 이 사슬의 각 구간을 따로 실행해 확인했습니다.
  • 객체 할당, factory 슬롯, 요청 word, 설정 값은 시험 입력입니다. 서비스 호출과 핸들 생성 직전에서 멈췄고 렌즈별 보정 레코드와 물리 단위는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 생성자 4개와 바인더 앞부분 4개, 리셋 앞부분
  • 디버그 요청의 설정·해제 (3건)
  • 설정 복사·accessor, PafPulse +0x56 저장, LensInfo 비율 (5건)
  • LensInfo 플래그 대조 12쌍 (24회 실행)

정적 분석 코드를 읽어 판단

  • PafPulse 저장 앞의 분기와 호출
  • Debug +0x2c 비영 분기
  • 설정 소스 +0x98을 쓰는 후보

모델 시험 조건으로 정한 것

  • 객체 할당, factory 슬롯, 바인더 진입 상태
  • PafMotor +0x56/+0x68의 시험값, 요청 word
  • 설정 소스 halfword, 렌즈·파라미터 메모리

미확인 확인하지 않은 것

  • PafMotor +0x56/+0x68의 비영값 생산자
  • 설정 소스 값을 처음 얻는 경로와 레코드 수명
  • 렌즈별 보정 레코드, 물리 단위, 바디·렌즈 모터 배정

배경: 왜 두 필드를 쫓는가

모드 1 문서의 요청 3 계산에서 PafMotor +0x68이 0이 아니면 표 조회를 건너뛰고 +0x56은 조회 결과에 더해졌습니다. 두 필드는 결과를 바꾸는 보정값입니다. 기준값 쓰기 경로 문서에서는 생성자 말고 두 필드를 쓰는 코드를 찾지 못했습니다.

이 문서는 같은 PafMotor 객체를 가리키는 다른 코드와, 이름이 같은 PafPulse +0x56으로 들어오는 값을 함께 살폈습니다. 오프셋이 같아도 객체가 다르면 다른 필드라는 점을 원본 포인터로 구분했습니다.

쉽게 말하면

장부의 두 칸이 계산 결과를 바꾸는데 누가 그 칸을 채우는지 모르는 상황입니다. 그래서 장부를 펼치는 사람을 한 명씩 불러 어느 칸을 고치는지 지켜봤습니다. 지금까지 부른 사람 가운데 두 칸을 고친 사람은 없었습니다.

필드마다 손대는 코드가 다릅니다

PafMotor의 많은 필드는 리셋 앞부분과 디버그 요청이 쓰지만 +0x56/+0x68은 생성자만 씁니다. PafPulse +0x56은 설정 값에서 오는 별개의 필드입니다.

세 경로는 각각 따로 진입했습니다. 객체 할당과 factory 슬롯, 일부 바인더 진입 상태는 재현기가 준비했습니다. 포인터 대입과 아래 표의 쓰기·산술은 모두 원본 ARM이 실행한 것입니다. 원본 생성자가 쓴 vtable 포인터와 ROM RTTI 이름으로 객체를 대조했습니다.

세 경로의 객체 연결과 정지 지점
경로무엇을 하는가정지 지점
PafMotor 생성과 초기화AfMotorFactory +0xc가 PafMotor를 가리킵니다. 생성자 0x52f0b4b0이 두 필드를 0으로 씁니다. 초기화 앞부분은 미리 넣은 두 시험값을 그대로 둡니다.0x52f0b6c0 서비스 호출 직전
PafControlDebug 요청Debug +0x1c가 같은 PafMotor를 가리킵니다. 요청 bit 0이 0, bit 1이 1이면 word를 bits 31:16과 15:4로 나눠 Motor +0x78/+0x7a에 씁니다.핸들 생성 호출 직전
PafPulse 쓰기와 별도 계산AfMotorFactory +0x10이 Pulse를 가리킵니다. 원본 0x52f0e3f4가 Pulse +0x56을 쓰고, 따로 시작한 LensInfo 계산이 그 새 값을 분모로 읽습니다.저장 뒤 카나리 비교 전
포인터 저장 주소

PafControlDebug의 포인터 저장은 0x52cb4610, PafLensInfo의 두 저장은 0x52f06194(+0x18)와 0x52f061c0(+0x1c)입니다. 원본 구간 SHA-256과 재생 기록에 74개 원본 구간이 있습니다.

PafPulse +0x56은 설정 레코드에서 옵니다

설정 소스의 halfword가 PafIntegralConfig +0xec로 복사되고 호출자가 그 값을 인자로 넘기면 최솟값 선택과 렌즈 조정을 거쳐 Pulse +0x56에 저장됩니다.

  1. 설정 소스상위 객체 +0x48의 레코드 +0x98 (시험 값)
  2. 설정 복사PafIntegralConfig +0xec에 u16 저장
  3. accessorPafSensorAccessor가 +0xec를 읽어 스택 인자로
  4. 최솟값과 렌즈 조정상한 후보와 비교, 렌즈 조건이면 v−(v>>5)
  5. Pulse +0x56 저장LensInfo가 분모로 읽음

원본 호출 0x52cb19f4와 0x52cb3240은 PafControl +0x34의 Pulse가 대상입니다. 두 호출은 먼저 0x52caad00을 불러 PafSensorAccessor +0x10이 가리키는 PafIntegralConfig의 +0xec u16을 스택 인자로 넘깁니다. 0x52caa2c0의 바인더와 0x52ca4524부터 이어지는 factory 할당 루프를 대조했습니다.

PafIntegralConfig 생성자 0x52cea934는 +0xec을 0으로 초기화합니다. 별도 설정 복사 경로는 호출 0x52cf1874에서 상위 객체 +0x48의 포인터를 받습니다. 그 뒤 0x52ceac04에서 소스 +0x98의 u16을 읽어 0x52ceac10에서 PafIntegralConfig +0xec에 씁니다. 재현에서는 소스 halfword와 객체 포인터를 넣은 뒤 복사와 accessor를 따로 실행했습니다. 실제 accessor 반환값은 Pulse 계산의 진입 인자로 넘겼습니다.

원본 분기에서 0x52f0e200의 반환이 0이면 0x52f0e3d0이 스택 인자와 [Pulse+0xc]+0x34의 u16 가운데 작은 값을 고릅니다. 이어 0x52f0e2f4는 렌즈 객체 +0x198c의 word에서 상위 10비트와 하위 6비트를 지운 값이 0x000dafc0이고 같은 객체의 +0x167 바이트가 0xf0일 때만 v−(v >> 5)로 줄입니다. 0x52f0e3f4가 결과를 Pulse +0x56에 저장합니다.

LensInfo가 Pulse +0x56을 읽는 방법

재현은 최솟값 선택 직전에서 시작해 원본 조정 함수와 저장 명령을 실행했습니다. 그 앞의 분기와 호출은 코드로만 읽었습니다. 별도 LensInfo 진입 0x52f0671c은 Motor +0x1a를 읽고 0x52f06734는 Pulse +0x56을 분모로 읽습니다.

차이 = Pulse[+0x40] − 요청          ※ Motor+0x1a ≠ 0이면 요청의 하위 16비트를 부호 확장해서 뺌
비율 = (분모 == 0) ? 0 : min(65535, (u16(차이) << 8) / 분모)     분모 = Pulse[+0x56]

플래그가 0이면 0x52f0674c에서, 0이 아니면 0x52f06740의 부호 확장 뒤 0x52f06750에서 뺄셈을 합니다. 공통 UXTH 명령 0x52f06754가 남기는 하위 16비트는 두 경우가 같습니다. 같은 요청에서 플래그만 바꾼 12쌍은 서로 다른 로드 명령을 거쳤지만 비율은 모든 쌍에서 같았습니다.

Cortex-A7 기본과 진입 레지스터·NZCV를 바꾼 Cortex-A7·A15 대조에서 결과가 같았습니다. 서비스 반환값을 대입한 훅은 없었습니다. 명령 주소와 원본 바이트, 지정 객체의 읽기·쓰기 범위를 검사했고 실행 전후 RTOS 매핑의 SHA-256이 일치했습니다.

찾지 못한 입력 생산자

PafMotor 두 필드와 설정 소스 +0x98의 값을 처음 만드는 코드가 남은 과제입니다.

  • PafMotor +0x56/+0x68 이 시험은 두 필드의 비영값을 미리 넣었습니다. 요청 3에서 두 필드를 읽는 코드의 앞 단계를 찾으려면, factory +0xc에서 나온 Motor 포인터로 실제 데이터를 넘기는 외부 호출을 찾아야 합니다.
  • 설정 소스 0x52cf0254가 상위 객체 +0x48이 가리키는 레코드의 +0x98에 값을 쓰는 후보입니다. 두 호출에서 같은 객체가 전달되는지는 확인하지 못했습니다.
  • 물리 의미 렌즈별 저장 보정 레코드, 물리 단위, 바디 모터와 렌즈 모터의 배정은 모릅니다. 초기화 뒤의 서비스와 핸들 생성, 카메라와 렌즈 동작은 실행 범위 밖입니다.

재현과 결과 비교

저장소 루트에서 Python과 Unicorn 2.1.4로 실행하며 공개 JSON과 바이트 단위로 같은지 비교할 수 있습니다.

python -B verify_af_motor_fields.py decoded.bin --output af-motor-decoded.json --compare analysis/af-motor-field-checks.json
python -B verify_af_motor_fields.py rtos.bin --output af-motor-rtos.json --compare analysis/af-motor-field-checks.json
python -B -m unittest discover -s tests -p test_af_motor_fields.py

재현기는 원본 decoded 또는 RTOS의 길이와 SHA-256을 검사합니다. -O 없이 실행하고 출력에는 새 파일을 지정합니다. 두 입력의 결과는 바이트 단위로 일치했습니다. 재현기는 원본 10건 전체와 플래그 대조 전체의 SHA-256을 각각 확인한 뒤 공개 JSON을 만듭니다.
