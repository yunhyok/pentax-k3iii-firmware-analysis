LINUX 내부 Stubby의 적재 조건과 인증 경계

기존의 No security 배너 참조에서 실제 파일 적재와 진입 주소 선택까지 추적했다. 이 Stubby 구간에는 파일 길이와 DTB 속성에 따른 성공·실패 분기가 있다. 이 결과는 해당 구성요소의 조건부 동작을 설명하며 선행 M0·BOOT·Boot ROM의 인증 여부를 결정하지 않는다.

LINUX payload 안의 주소로 연결했다

이 보고서의 작은 코드 주소는 LINUX payload 시작에 대한 상대 오프셋이다. 실제 카메라의 실행 base는 확인하지 않았다. ARM 호출부 0xcec는 Thumb 0x984로 들어가며 이 함수가 반환하면 0xcf0에서 0x9c8을 호출한다. 코드 범위·명령·해시.

0x984는 하위 반환값이 2이면 후보 탐색을 중단하고 실패 반복문으로 간다. 0이면 출력 함수를 거쳐 반환하며 그 밖의 값은 partition index를 늘려 재시도한다. 이 호출부의 boot source는 0으로 고정되어 있고 0x930은 그 경우 partition 0만 허용한다. 이 경로의 ROMFS 후보 주소는 0x41008000이다. 이 반복문을 SD·eMMC 전체 탐색으로 설명하지 않는다. Stubby 내부 후보 index를 RTOS FwPartition의 bank byte나 eMMC 물리 partition 번호와 같은 값으로 볼 근거도 없다.

반환값은 signed 비교로 판단한다

조건원본 동작근거 위치
bootloader 읽기 결과 > 0다른 kernel·DTB 읽기 없이 적재 함수가 0 반환0xaa4–0xaa6 → 0xbf0

initrd-start 또는 initrd-end 속성포인터가 비제로이고 반환 길이가 정확히 4여야 진행0xb32–0xb5c

파일 wrapper 0x9fc는 ROMFS 주소를 얻었을 때 요청 대상이 kernel 전역과 같으면 해당 전역을 얻은 주소로 바꾼다. 이 기록은 상위 함수가 길이를 검사하기 전에 일어난다. 따라서 전역의 값이 바뀌었다는 사실만으로 적재가 성공했다고 판단할 수 없다. DTB 대상은 copy 경로로 넘어가며 0xa46의 간접 호출은 별도 경계다. pointer·비교·간접 호출 근거.

kernel 경로는 0x43000068의 길이 값을 byte reverse하고 initramfs 주소에 0x80을 더한다. 이 길이가 0일 때만 0x25ca의 DTB 갱신 helper를 호출한다. initrd-start와 initrd-end에는 각각 시작 주소와 시작 주소+길이를 big endian으로 기록한다. 뒤의 0x1800003c 읽기에 따른 다른 DTB 조정 분기는 이번 공개 CPU 검사에서 실행하지 않았다.

0x9c8은 선택된 kernel 전역을 읽고 0x1d010000에 1을 기록한 뒤 r0=0, r1=0xffffffff, r2=DTB 주소로 분기한다. 검사는 이 분기 대상의 첫 명령을 실행하기 전에 정지한다. 이 흐름을 실제 Linux 부팅 성공과 동일시하지 않는다.

서명 옵션과 전체 부팅 인증은 별개다

Ricoh 배포본 안의 stubby-1.60.1.tar.gz에서 확인한 load_image.c 151–212행은 CONFIG_RSA_SIGNATURE 조건 안에서 서명 읽기·해시 계산·검증을 수행한다. 실패 시 데이터 삭제와 1 반환은 다시 CONFIG_RSA_SIGNATURE_ENFORCING 조건에 걸린다. 따라서 공개 소스에서도 서명 지원과 강제 거부는 서로 다른 조건이다. Ricoh 배포본 · 소스 member·행 범위·해시.

이번에 확인한 적재 함수의 코드 흐름은 해당 RSA 조건부 구간을 제외한 소스 구조와 맞으며 기존 No security 배너 참조와도 일관된다. 이것은 선택한 Stubby 함수에 대한 해석이다. 원본 빌드 옵션 전체를 복원한 것은 아니며 파일 시스템·DTB helper 내부의 추가 검사나 다른 부팅 단계의 암호 연산 부재를 입증하지 않는다.

실제 파일 시스템 copy callback의 생산자와 구현, 현재 카메라에서 이 구성요소에 도달하는 전체 부팅 경로, BOOT 이전 ROM의 인증은 미확정이다. 이 결과로 수정된 패키지가 카메라에서 수락된다고 결론내릴 수 없다.

검증과 로컬 의사코드

적재 함수와 부팅 후보 탐색 함수의 genuine C 2개를 로컬에 저장했다. 원시 C의 복원되지 않은 인자나 임시 변수는 원본 ARM·Thumb 명령으로 보완해 해석했다. literal pool을 실행 코드에서 분리했고 공개 자료에는 분석 설명·범위·해시와 직접 작성한 검사만 남겼다.

공개 CPU 검사는 6사례다. bootloader 성공, kernel 길이 0, DTB 길이 0, initrd-start 누락, initrd-end 길이 오류, kernel·DTB 정상 경로를 실행한다. 파일 wrapper 0x9fc, ROMFS mount, DTB helper·출력은 명시한 대체 함수가 처리한다. wrapper까지 포함한 실행은 재현 환경에서 실패했으므로 해당 함수의 전역 갱신과 간접 호출은 정적 근거로만 제시했다. 통과한 검사는 원본 적재 함수와 상위 반환·진입 주소 전달 경로의 조건부 동작을 확인하며 하위 파일 읽기나 포인터 생산자를 검증하지 않는다. 사례와 대체 함수 · 재현 도구.

독립 검토에서는 kernel 길이 0xffffffff가 signed 실패로 처리되는 경우와 결합된 initramfs 길이 0x1234인 경우를 추가 확인했다. 이 2사례는 공개 도구의 6사례와 별도로 기록했다. 모든 MMIO는 합성 RAM이며 실제 파일 시스템·장치·kernel을 실행하지 않았다.
