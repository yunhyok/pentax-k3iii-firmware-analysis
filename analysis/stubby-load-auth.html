Linux 부트로더 Stubby가 커널을 올리는 조건과 서명 검사의 범위

카메라 안의 Linux는 작은 부트로더가 커널과 장치 트리를 메모리에 올려 시작합니다. 이 부트로더가 무엇을 검사하고 무엇을 검사하지 않는지 확인하면, 수정한 이미지를 막는 장치가 이 단계에 있는지 판단할 수 있습니다.

이 문서에서

  1. 배경: Stubby와 이 문서의 좌표
  2. 호출 경로: 후보 탐색에서 진입 주소 전달까지
  3. 적재 조건: 읽은 길이와 initrd 속성으로 판단합니다
  4. 서명 검사: 공개 소스의 옵션과 이 이미지의 동작
  5. 검증: 원본 ARM·Thumb 코드 6사례
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • Stubby의 적재 함수는 파일을 읽은 길이와 장치 트리의 initrd 속성 두 가지로 성공과 실패를 가릅니다. 읽은 길이가 0 이하이거나 속성이 없거나 길이가 4가 아니면 실패를 돌려줍니다.
  • 성공하면 레지스터 세 개에 정해진 값을 넣고 선택된 주소로 분기합니다. 원본 코드를 에뮬레이터에서 6가지 조건으로 실행해 이 분기들을 확인했습니다. 실행은 커널의 첫 명령 직전에 멈춥니다.
  • Ricoh가 공개한 Stubby 소스에는 서명 검사 코드가 있지만 빌드 옵션으로 켜야 들어갑니다. 이 이미지에서 확인한 적재 함수의 흐름은 서명 구간을 뺀 소스 구조와 맞습니다.
  • 이 결과는 Stubby 한 구성 요소에 관한 것입니다. 앞 단계(M0, BOOT, Boot ROM)의 인증 여부는 알 수 없고, 수정한 패키지가 카메라에서 받아들여진다는 결론도 낼 수 없습니다.

확인 원본 코드 실행으로 확인

  • 적재 함수의 성공·실패 분기 6사례
  • 상위 탐색 함수가 실패 반복문으로 가는 경로
  • 진입 직전의 레지스터 값과 레지스터 기록 한 건

정적 분석 읽어서 판단

  • 이 문서의 6사례에서는 파일 wrapper의 전역 갱신과 간접 호출을 정적으로 해석. 후속 시험에서 원본 하위 경로를 별도 실행
  • 공개 소스의 서명 조건부 구간과의 구조 비교
  • 0이 아닌 initramfs 길이에서의 DTB 처리 순서

모델 시험 조건으로 정한 것

  • 파일 읽기 결과(양수·0·음수)와 DTB 속성 조회 결과
  • ROMFS mount, DTB 보조 함수, 출력 함수의 대체
  • 코드를 주소 0에 올린 배치, Unicorn의 Cortex-A15 모델

미확인 확인하지 못한 것

  • 이 문서의 상위 경로와 원본 파일 읽기·복사 callback을 모두 연결한 실행
  • 카메라가 이 코드에 도달하는 전체 부팅 경로, 실행 주소
  • M0·BOOT·Boot ROM의 인증, 수정 이미지의 수락

배경: Stubby와 이 문서의 좌표

후속 원본 ROMFS 검증

Stubby ROMFS: 포인터 선택과 실제 복사에서는 mount·wrapper·lookup·복사를 대체 함수 없이 Cortex-A7에서 6사례로 실행했습니다. 이 문서의 상위 호출자 시험과 기존 JSON은 당시의 6개 stub 사례로 보존합니다. 두 시험을 합쳐 전체 부팅이 검증됐다고 해석하지 않습니다.

펌웨어 패키지의 LINUX 레코드에는 세 가지가 들어 있습니다. 맨 앞의 부트 코드, 압축된 Linux 커널, 장치 트리(DTB)입니다(펌웨어 구조). 맨 앞의 부트 코드가 Stubby입니다. Ricoh는 오픈소스 묶음에 stubby-1.60.1이라는 이름으로 이 부트로더의 소스를 배포합니다.

부트로더가 하는 일은 단순합니다. 커널과 DTB를 정해진 메모리 위치에 올리고, 초기 파일 시스템(initrd)의 위치를 DTB에 적어 준 뒤, 커널의 첫 주소로 분기합니다.

조사한 이유는 Stubby가 시작할 때 출력하는 문구에 “(No security)”가 들어 있기 때문입니다(업데이트 검사와 ICONBIN). 문구만으로는 부족하므로, 실제로 파일을 올리고 진입 주소를 고르는 코드까지 따라가 조건을 확인했습니다.

주소 읽는 법

이 문서의 작은 코드 주소(0x984, 0xa68 등)는 LINUX 레코드 시작에서 잰 오프셋입니다. 실제 카메라에서 이 코드가 놓이는 주소는 확인하지 않았습니다. 0x40008000처럼 큰 값은 코드가 직접 쓰는 메모리 주소입니다.

호출 경로: 후보 탐색에서 진입 주소 전달까지

시작 호출부는 탐색 함수를 부르고, 탐색 함수가 돌아오면 진입 주소 전달 함수를 부릅니다. 탐색이 실패하면 돌아오지 않고 실패 반복문에 머뭅니다.

ARM 코드인 시작 호출부 0xcec는 Thumb 함수 0x984로 들어갑니다. 이 함수가 돌아오면 0xcf0에서 0x9c8을 부릅니다.

탐색 함수 0x984가 하위 결과를 처리하는 방식
후보 시도 함수 0x930의 결과탐색 함수의 동작
0출력 함수를 거쳐 호출부로 돌아갑니다. 이어서 진입 주소 전달이 실행됩니다.

이 호출부에서 boot source는 0으로 고정되어 있습니다. 0x930은 그 경우 partition 0만 받아들이고, partition 1을 요청받으면 2를 돌려줍니다. 그래서 적재가 한 번 실패하면 두 번째 시도에서 탐색이 끝납니다. 이 경로가 ROMFS를 찾는 후보 주소는 0x41008000 하나입니다.

혼동하기 쉬운 점

이 반복문은 SD 카드와 eMMC를 두루 찾는 탐색이 아닙니다. 또 Stubby의 후보 index를 RTOS의 FwPartition bank 값이나 eMMC의 물리 partition 번호와 같은 것으로 볼 근거가 없습니다. bank에 관한 내용은 쓰기 bank와 BOOT 선택에서 따로 다룹니다.

적재 조건: 읽은 길이와 initrd 속성으로 판단합니다

적재 함수는 파일 읽기 결과를 부호 있는 정수로 비교합니다. 0과 음수는 모두 실패입니다. 그 뒤 DTB에서 initrd 속성 두 개를 찾아 길이가 정확히 4인지 봅니다.

파일 wrapper가 전역 포인터를 먼저 바꿉니다

파일을 읽는 wrapper 0x9fc는 ROMFS에서 파일의 주소를 얻습니다. 요청받은 목적지가 커널 전역 포인터의 값과 같으면, 그 전역을 방금 얻은 주소로 바꿉니다. 이 기록은 상위 함수가 길이를 검사하기 전에 일어납니다. 따라서 전역 값이 바뀌었다는 사실만으로는 적재가 성공했다고 판단할 수 없습니다. DTB를 읽을 때는 복사 경로로 넘어가며, 그 안의 간접 호출(0xa46)이 실제로 무엇을 부르는지는 확인하지 못했습니다.

initramfs 위치를 DTB에 적는 방식

커널을 읽은 경로는 0x43000068에 있는 길이 값의 바이트 순서를 뒤집어 읽고, initramfs 주소에 0x80을 더합니다. 이 길이가 0일 때만 DTB 갱신 함수 0x25ca를 부릅니다. initrd-start 속성에는 시작 주소를, initrd-end 속성에는 시작 주소에 길이를 더한 값을 big endian으로 씁니다. 그 뒤에 0x1800003c를 읽어 갈라지는 또 다른 DTB 조정 분기가 있는데, 공개 CPU 검사에서는 실행하지 않았습니다.

참고: ROMFS 헤더와의 관계

ROMFS 형식은 32비트 값을 big endian으로 적고, 파일 헤더의 +8에 파일 크기를 두며, 16바이트 단위로 정렬합니다. “+0x68의 값을 뒤집어 길이로 쓰고 +0x80부터를 내용으로 본다”는 위 동작은 이 형식에서 첫 파일의 헤더가 +0x60에 있을 때의 배치와 같은 꼴입니다. 패키지의 INITFS 레코드도 +0x80에서 gzip 데이터가 시작합니다(펌웨어 구조). 다만 0x43000000에 INITFS 레코드가 놓인다는 것은 확인하지 않았으므로 형식상의 일치로만 적습니다.

서명 검사: 공개 소스의 옵션과 이 이미지의 동작

공개 소스에서 서명 검사는 빌드 옵션 두 개에 걸려 있고, 이 이미지의 적재 함수는 그 구간이 빠진 구조와 맞습니다. 그렇다고 부팅 전체에 인증이 없다는 뜻은 아닙니다.

Ricoh 배포본 안의 stubby-1.60.1.tar.gz에 있는 소스와 대조했습니다.

쉽게 말하면

공개 소스에는 “서명 기능을 넣을지”와 “서명이 틀리면 거부할지”가 따로 스위치로 나뉘어 있습니다. 이 이미지에서 본 적재 함수는 두 스위치가 모두 꺼진 소스와 같은 모양입니다.

이 비교로 말할 수 없는 것

  • 원본 빌드 옵션 전체를 복원한 것이 아닙니다. 공개 소스와 이 이미지가 같은 빌드라는 가정도 하지 않았습니다.
  • 파일 시스템 함수와 DTB 보조 함수 안에 추가 검사가 있을 수 있습니다. 특히 wrapper의 간접 호출은 추적하지 못했습니다.
  • 다른 부팅 단계에 암호 연산이 없다는 증거가 아닙니다. 현재 카메라가 이 구성 요소에 도달하는 전체 경로, BOOT 이전 ROM의 인증은 미확정입니다.
  • 따라서 수정한 패키지가 카메라에서 받아들여진다고 결론 낼 수 없습니다.

검증: 원본 ARM·Thumb 코드 6사례

파일 읽기 결과와 DTB 속성 조회 결과를 바꿔 가며 여섯 번 실행했고, 각 사례가 예상한 문구와 반환 경로를 따랐습니다.

시험 조건

LINUX 레코드의 원본 바이트를 Unicorn의 ARM 모델(Cortex-A15)에 주소 0부터 올리고 0xcec에서 실행을 시작했습니다. 탐색·후보 시도·적재·진입 주소 전달 함수는 원본 그대로 실행됩니다. 아래 함수들은 호출되는 순간 가로채 정해 둔 값을 돌려주는 대체 함수로 바꿨습니다. 메모리와 레지스터 주소는 모두 일반 RAM입니다. 실제 파일 시스템, 장치, 커널은 실행하지 않았습니다.

진입 지점에 도달한 두 사례에서는 r0 = 0, r1 = 0xffffffff, r2 = 0x42800000이었고 0x1d010000에 1을 쓰는 기록이 한 번 있었습니다. 실패한 네 사례에서는 이 기록이 없었습니다. 정상 사례에서 initrd-start와 initrd-end 속성 자리에는 0x43000080이 big endian으로 기록되었습니다(시험의 initramfs 길이는 0). LINUX 레코드만 넣었을 때와 압축을 푼 전체 스트림을 넣었을 때 결과가 같았습니다.

초기 wrapper 실행의 한계와 후속 검증

파일 wrapper 0x9fc까지 원본으로 실행한 초기 시도는 재현 환경에서 0xa2c에 이르러 예상하지 못한 레지스터 상태로 멈췄습니다. 이 문서의 6사례는 wrapper를 대체한 상태로 보존하며, 적재 함수와 상위 반환·진입 주소 전달 경로의 조건부 동작을 확인합니다. 이후 원본 ROMFS와 하위 함수들을 함께 사용하는 별도 6사례에서 전역 포인터 선택과 실제 복사를 재현했습니다. 재현 배치와 계측 조건이 달라 초기 실패의 원인은 여전히 확정하지 않았으며, 펌웨어나 에뮬레이터의 결함으로 단정하지 않습니다.

디컴파일 의사코드

적재 함수와 부팅 후보 탐색 함수는 angr 10.0.5의 C 형태 의사코드를 로컬에 보관했습니다. 의사코드가 복원하지 못한 인수와 임시 변수는 원본 ARM·Thumb 명령으로 보완해 해석했습니다. literal pool은 실행 코드에서 분리했습니다.

독립 검토의 추가 실행

독립 검토에서는 두 경우를 더 확인했습니다. 커널 읽기 결과가 0xffffffff(부호 있는 −1)이면 실패로 처리됩니다. 결합된 initramfs 길이가 0x1234이면 DTB 갱신 함수 0x25ca를 건너뛰고 끝 주소로 0x430012b4를 씁니다. 이 2사례는 공개 도구의 6사례와 따로 기록했습니다.

한계와 남은 과제

  • 좌표는 LINUX 레코드 기준 오프셋입니다. 실행 주소, 카메라가 이 코드에 도달하는지, 패키지·M0·BOOT·ROM의 인증, 수정 이미지의 수락은 증명하지 않았습니다.
  • 파일 시스템의 주소 조회·복사는 후속 시험에서 선택된 입력으로 재현했습니다. 상위 적재 경로와의 전체 연결 및 DTB 보조 함수 내부는 남은 경계입니다. 전체에 검사가 없다고 주장하지 않습니다.
  • 0x1800003c 값에 따른 DTB 조정 분기는 CPU 검사에서 다루지 않았습니다.
  • 시험은 저장 매체를 읽지 않고, 특권 모드의 시작 코드와 선택된 이미지를 실행하지 않습니다.
  • 펌웨어 빌드와 플래시는 하지 않았습니다.

재현 방법

검증 도구는 따로 잘라 낸 LINUX 레코드(linux.bin)나 추출기가 만든 decoded.bin을 받습니다. 입력의 크기와 SHA-256을 확인한 뒤 실행하며, 결과 파일이 이미 있으면 멈춥니다. Python 패키지 unicorn이 필요합니다.

python verify_stubby_load_auth.py linux.bin --output stubby-linux.json
python verify_stubby_load_auth.py decoded.bin --output stubby-decoded.json

추출 방법은 펌웨어 구조와 하드웨어의 재현 절차에 있습니다.
