재압축 후보의 파일 길이가 전달되는 경로와 allocator의 설정 용량을 확인했다. 실제 가용 공간과 업데이트 수용 여부는 별도 검증이 필요하다.

파일 크기부터 입력 버퍼까지

종류 값 2의 선택자 52fef240은 filename getter 52ff3474의 주소 54796104를 사용한다. 파일 정보 조회 52ff7d10 → 52ff7c38은 resourceManager+38 객체의 vtable slot +54를 호출한다. 성공하면 FileInfo의 +18 word를 읽고 이 값이 0이 아니면 경로와 크기를 updateState의 +40 / +44에 저장한다. 구체적인 파일 시스템 객체와 실제 조회의 구현은 아직 연결하지 않았다. 크기 생산자·저장 근거

52fee900은 resourceManager, 경로, 길이를 52ff7160에 넘기고 반환 포인터를 state+48에 저장한다. mutex를 얻은 뒤 52ff70a0이 52ff7014를 최대 3회 호출한다. unsigned 길이가 0x80000보다 크면 manager+30의 allocator를, 그 이하면 +34를 고른다. 원본과 두 후보는 모두 +30 경로이며 요청 길이를 그대로 전달하고 정렬 인자는 0x40이다. 이 선택 지점에 별도의 더 큰 상한 비교는 없지만 하위 할당 성공까지 뜻하지는 않는다. 크기 경계·인자 전달 검사

할당 뒤 52ff6dd4는 파일 객체의 open slot+20, read slot+28, close slot+24를 호출한다. open 실패는 close를 생략하고 open 성공 후 read 실패는 close한 뒤 할당 버퍼의 해제를 요청한다. read helper가 실패하면 같은 allocator의 slot+c로 해제를 요청하고 재시도한다. read 결과가 성공인 경로에서는 close의 반환값을 최종 성공 여부에 반영하지 않는다. 세 번 모두 실패하면 assertion/log 경계 530feb20에 false를 전달한다. 검사에서는 이 경계를 반환하는 stub으로 대체했으므로 실제 실패 후 카메라가 계속 실행한다고 단정할 수 없다. 실패·해제·재시도 조건

로더 검사 27사례는 크기·allocator 분기 11개, 할당/open/read 실패와 재시도 9개, mutex 거부 1개, close 반환 1개, 종류 2의 파일 정보→상태 저장 5개다. 모든 할당·해제와 파일 I/O를 합성 callback으로 대체했으며 큰 요청을 실제 메모리에 할당하거나 후보 파일을 읽은 검사가 아니다. 상태 저장 검사는 이전 필드를 sentinel로 채운 뒤 실제 기록을 확인했다. 로더 재현 도구 · 27사례·대체 지점

같은 pool로 연결되는 생산자

파일 입력에 쓰는 allocator ID 0x0e는 VariableMemoryPool 객체 0x547ba638, 이름 IMAGE1이다. 초기화 함수는 base 0x6e500000, 크기 0x31b00000 (833,617,920바이트), 기본 정렬 64바이트를 전달한다. decoded 출력의 validator도 같은 ID를 조회한다. 이 설정은 두 후보 크기보다 크지만 실제 생성 성공·사용량·단편화·연속 할당 성공은 확인하지 않았다.

근거: 주소·범위 해시·조건부 연결, 원본 ARM 35사례, 재검증 결과. 분석 원본 RTOS SHA-256: 342d2f35405e8daf1797dfe431d2e4aa70f4b52a2c242a29df48206672f1dfb4.

용량은 설정값이며 가용 메모리 값이 아니다

530f0504는 OS create descriptor에 [0, 0x20, size−0x10, base, 0, 0, 0]을 만든다. 따라서 전달 크기는 0x31affff0 = 833,617,904바이트다. 성공 시 object+14는 OS handle, +18은 이름, +1c는 size−16, +20은 기본 정렬, +24는 base가 된다. 설정 범위의 산술적 끝은 0xa0000000이다. 이 주소가 물리 DRAM에 어떻게 대응하는지는 이 조사로 정하지 않았다.

create 525b6a58와 allocate 525b7214는 각각 service word 80450100, 80470400을 로드하고 SVC 6으로 넘어간다. 그 내부 OS 구현·현재 pool 내용은 실행하지 않았다. 530efc80의 이름은 GetFreeSpace이며 OS report 경계 525b74c0가 0을 반환하면 report+8/+c 두 word를 출력한다. 각 word를 총 free/최대 연속 크기로 독립 식별하거나 실제 값을 얻지는 않았다. query 주소·해시

원본 allocator의 크기·포인터 계산

530efb8c에서 A=0이면 object+20을 사용한다. 요청 크기 N에 대한 OS 요청은 32비트 산술로 (((N+A−1) & −A) + A + 0x20) mod 2^32이다. 이번 정상 크기와 A=64에서는 roundUp64(N)+96이다. OS 결과가 nonzero이면 NULL을 반환한다. 성공 stub에서 받은 raw 포인터는 (raw+0x18+A+7)&−A로 정렬하고 [aligned−8]=raw+0x18을 기록한다. debug metadata 호출은 별도 경계다. allocate 주소·해시

재현 검사와 한계

allocator 재현 도구는 pinned RTOS 또는 decoded.bin SHA를 확인한다. 35사례는 create signed-return/등록 6, allocate 크기/성공실패 20, 기본 정렬·포인터·caller fallback 8, validator ctor의 동일 registry alias 1이다. original ARM ctor/create/registry/allocate 및 일부 초기화 fragment를 실행한다. 초기화 fragment는 530f5890부터 r5=64와 합성 stack을 주입한다. full startup이나 실제 대형 버퍼 할당은 실행하지 않는다. CPU 모델은 Unicorn Cortex-A15이며 카메라 일치성 주장이 없다.

명시적 stub은 OS create 525b6a58, OS allocate 525b7214, debug metadata 530ef42c, ctor assertion 530fdfc4이다. assertion이 실패할 때의 실제 fatal policy는 모사하지 않았다. OS stub은 작은 synthetic 포인터만 제공하며 실제 장치나 파일을 읽지 않는다.

genuine angr C 6개는 수정하지 않은 자동 출력이다. create C의 name-null conditional load 처리와 allocate C의 포인터형·stack-canary 표현에는 왜곡이 있으므로 원본 ARM과 실행 검사를 수학·조건의 근거로 쓴다. 원본 word와 범위 hash는 모두 보존했다. FixedMemoryPool 530f13b8 경로는 ID 0 등록 후보이므로 ID 14 생산자로 사용하지 않았다.

실행 가능성 판단에 남은 조건

로더 27사례와 pool 35사례는 서로 다른 경계를 검사한 합계 62사례다. 재현 도구는 모두 입력 SHA-256을 확인하고 기존 결과 파일 덮어쓰기와 assert 비활성화를 거부한다. 본 조사에서 새 genuine C 14개를 로컬에 보존했다. 공개 자료에는 원본 코드 대신 주소·해시·해석·검사 결과를 남겼다.

두 요청의 합이 설정 영역보다 작다는 사실만으로 현재 메모리 여유를 판단할 수는 없다. 실제 pool 생성, 다른 사용자의 점유, 연속 공간, 입력과 출력의 공존 수명, 파일 시스템과 하드웨어 디코더, 후속 검증·기록·부팅을 계속 연결해야 한다. 실제 장치에서 파일 읽기·할당·설치·실행·복구를 수행하지 않았다.

정적 주소·해시와 합성 CPU 실행 결과다. 원본 및 후보의 실제 카메라 수용을 주장하지 않는다. HTML 링크와 390px·1280px 화면 배치를 확인했다. 좁은 화면의 표는 내부에서 가로로 스크롤한다.
