업데이트 파일을 읽는 입력 로더와 메모리 할당

카메라는 업데이트 파일을 통째로 메모리에 올리고, 그것을 풀어 낸 데이터도 메모리에 둡니다. 수정한 파일이 원본보다 커지면 이 단계에서 막히는지 알아보려고, 파일 크기가 전달되는 경로와 메모리를 요청하는 계산을 조사했습니다.

핵심 요약

  • 로더는 파일 정보 조회에서 얻은 파일 크기 그대로 입력 버퍼를 요청합니다. 크기가 524,288바이트를 넘으면 큰 메모리 풀을 고르며, 이 선택 지점에는 그보다 큰 상한을 두는 비교가 없습니다.
  • 큰 풀은 이름이 IMAGE1인 가변 크기 메모리 풀입니다. 설정된 크기는 833,617,920바이트이고, 풀린 출력 버퍼도 같은 풀에서 요청합니다.
  • 풀이 운영체제에 요청하는 크기는 64바이트 단위로 올림한 크기 + 96바이트입니다. 원본 파일의 입력과 출력 요청을 더하면 113,790,848바이트로, 설정 크기의 약 14%입니다.
  • 읽기에 실패하면 버퍼를 해제하고 세 번까지 다시 시도합니다. 세 번 모두 실패한 뒤 카메라가 어떻게 되는지는 확인하지 못했습니다.
  • 설정 크기는 지금 비어 있는 메모리가 아닙니다. 실제 풀 생성, 다른 사용자의 점유, 연속 공간은 확인하지 않았으므로, 수정 파일을 카메라가 받아들인다고 말할 수 없습니다.

확인 원본 코드 실행으로 확인

  • 로더의 크기 분기, 재시도, 상태 저장 27건
  • 풀 생성·등록, 요청 크기와 포인터 계산 35건
  • RTOS 단독 입력과 통합 이미지 입력에서 같은 결과

정적 분석 코드를 읽어 판단

  • 풀 초기화 함수 전체와 IMAGE1 객체의 생성 위치
  • 클래스 이름 VariableMemoryPool(RTTI 문자열)
  • 빈 공간 조회 함수 GetFreeSpace의 구조

모델 시험 조건으로 정한 것

  • 할당·해제, 파일 열기·읽기·닫기, 잠금은 대체 함수
  • 운영체제 호출(풀 생성·할당)은 값만 돌려주는 대체 함수
  • CPU는 Unicorn의 Cortex-A15 모델
  • 큰 버퍼를 실제로 잡거나 파일을 읽지 않음

미확인 확인하지 않은 것

  • 실제 풀 생성 성공, 현재 여유, 최대 연속 공간
  • 풀 주소 범위가 실제 DRAM에 대응하는 방식
  • 세 번 실패한 뒤의 실제 처리
  • 수정 파일의 수용 여부와 업데이트 성공

배경: 왜 메모리 요청을 따져 보는가

펌웨어를 고쳐 다시 포장하면 파일 크기가 달라집니다. 압축 블록을 보존한 재패키징에서 만든 후보 두 개가 그 예입니다. 바뀐 블록만 압축 없이 저장한 선택 후보는 원본보다 조금 크고, 모든 블록을 압축 없이 저장한 전부 저장 후보는 원본의 두 배가 넘습니다. 카메라가 이런 파일을 읽을 메모리를 요청할 수 있는지가 이 문서의 질문입니다.

파일 크기에서 입력 버퍼까지

파일 크기는 파일 정보 조회 결과에서 나와 상태 객체에 저장되고, 로더는 그 값을 바꾸지 않고 메모리 풀에 요청합니다.

크기는 어디서 오는가

종류 2를 고르는 함수 0x52fef240은 파일 이름이 든 버퍼 0x54796104를 파일 정보 조회 함수에 넘깁니다. 조회 함수는 파일 시스템 객체의 가상 함수를 불러 파일 정보 구조체(FileInfo)를 채우고, 그 구조체의 +0x18에 있는 32비트 값을 크기로 읽습니다. 크기가 0이 아니면 경로와 크기를 상태 객체에 저장합니다. 파일 시스템 객체의 실제 정체는 파일 인터페이스와 버퍼 수명에서, 파일 이름이 만들어지는 과정은 파일 경로·volume·종료 처리에서 다룹니다.

시험 조건

로더 27건은 크기·풀 분기 11건, 할당·열기·읽기 실패와 재시도 9건, 잠금 거부 1건, 닫기 반환 1건, 파일 정보에서 상태 저장까지 5건입니다. 크기 분기에는 0, 1, 524,287, 524,288, 524,289, 원본과 두 후보의 크기, 2,147,483,647, 2,147,483,648, 4,294,967,295를 넣었습니다. 아주 큰 값은 인수 전달과 분기만 확인한 것이고 유효한 파일 크기라는 뜻이 아닙니다. 상태 저장 시험은 이전 필드를 표식 값으로 채운 뒤 실제로 덮어쓰였는지 확인했습니다.

입력과 출력이 같은 IMAGE1 풀에서 나옵니다

압축된 입력 버퍼와 풀린 출력 버퍼는 둘 다 등록 ID 14번인 IMAGE1 풀에 요청됩니다. 이 풀은 주소 0x6e500000에서 시작하는 833,617,920바이트 영역으로 설정되어 있습니다.

IMAGE1은 클래스 VariableMemoryPool의 객체 0x547ba638입니다. 초기화 함수가 기준 주소, 크기, 기본 정렬 64바이트를 넘겨 풀을 만듭니다. 풀린 출력을 담을 버퍼는 검증 객체가 같은 ID로 찾은 풀에서 요청하며, 요청 크기는 파일 footer에 적힌 출력 길이입니다(헤더와 footer에서 확인하는 값).

“확인”은 해당 함수나 조각을 에뮬레이터에서 실행해 저장 값과 인수를 관찰했다는 뜻입니다. 운영체제 호출은 대체 함수였습니다. 풀 생성 6건에는 양수 1, 4,660, 2,147,483,647과 0, 4,294,967,295, 2,147,483,648을 돌려주는 경우를 넣어 양수일 때만 등록되는 것을 확인했습니다.

등록 경로의 주소와 해시
  • 초기화 진입: 0x52ef427c가 관리 객체 함수 0x530f53ac를, 0x52ef4280이 초기화 함수 0x530f5430을 부릅니다.
  • 객체 생성: 보호 분기의 0x530f5a3c–0x530f5a44가 객체 0x547ba638을 생성자에 넘깁니다. RTTI 포인터 0x53a6b07c가 가리키는 0x53a6b018에 NUL로 끝나는 ASCII 문자열이 있습니다.
  • 설정 전달: 0x530f5890–0x530f58c8. 이름 문자열 IMAGE1은 0x53a6ad50에 있습니다.
  • 등록: 0x530f0560에서 운영체제 경계를 부르고, 0x530f0564·0x530f0568의 양수 조건을 지나 0x530f059c가 등록 함수 0x530ef274를 부릅니다.
  • 입력 쪽: 0x52ff5c14–0x52ff5c1c가 ID 14의 풀을 자원 관리 객체 +0x30에 저장하고, 0x52ff7054가 가상 함수 +8을 부릅니다. 표의 해당 칸은 0x53a6b040입니다.
  • 출력 쪽: 검증 객체 생성자의 0x52ff4a48이 ID 14를 넣고 0x52ff4a68에서 등록부를 조회해 0x52ff4a6c에서 저장합니다. 할당 호출은 0x52ff4fe0입니다.
  • ID 0번에는 다른 클래스의 생성 함수 0x530f13b8(FixedMemoryPool)이 0x530f55c0에서 호출됩니다. ID 14의 출처로 쓰지 않았습니다.

요청 크기 계산과 네 버퍼의 수치

할당 함수는 요청 크기를 정렬 단위로 올림한 뒤 정렬 값과 32바이트를 더해 운영체제에 요청합니다. 정렬이 64일 때는 “64의 배수로 올림 + 96바이트”입니다.

버퍼코드가 요청한 바이트풀이 운영체제에 넘긴 바이트풀린 출력 요청과의 합

입력과 출력이 실제로 같은 시점에 함께 잡혀 있는지는 파일 인터페이스와 버퍼 수명에서 확인했습니다.

계산식

요청 크기를 N, 정렬을 A라고 하면 할당 함수 0x530efb8c의 계산은 아래와 같습니다. 모든 계산은 32비트 범위에서 이루어집니다.

A가 0이면 A = 풀 객체의 기본 정렬(+0x20, IMAGE1은 64)
운영체제 요청 크기 = (((N + A − 1) & −A) + A + 0x20) mod 2^32
A = 64일 때       = roundUp64(N) + 96

운영체제가 돌려준 주소를 raw라고 하면
호출자에게 주는 주소 aligned = (raw + 0x18 + A + 7) & −A
aligned − 8 위치에 raw + 0x18을 기록

운영체제 호출이 0이 아닌 값을 돌려주면 할당 함수는 NULL을 돌려줍니다. 디버그 정보를 기록하는 호출은 따로 있으며 시험에서는 대체했습니다.

시험 조건

풀 35건은 생성·등록 6건, 요청 크기와 성공·실패 20건, 기본 정렬·주소 계산·태그 대체 8건, 검증 객체가 같은 풀을 찾는지 1건입니다. 요청 크기 시험에는 0, 1, 63, 64, 65, 524,288, 원본과 두 후보의 크기, 4,294,967,295(0xffffffff)를 넣었습니다. 이 최댓값은 32비트 산술을 확인한 것이며 유효한 파일 크기 판정이 아닙니다. 풀 초기화는 함수 전체가 아니라 0x530f5890부터의 조각을 정렬 값 64와 합성 스택으로 실행했습니다.

설정 크기는 가용 메모리가 아닙니다

833,617,920바이트는 풀을 만들 때 넘기는 설정값입니다. 풀이 실제로 만들어졌는지, 지금 얼마나 비어 있는지는 운영체제 안쪽의 일이며 실행해 보지 않았습니다.

생성 함수는 운영체제에 넘길 설명 구조체에 [0, 0x20, 크기−0x10, 기준 주소, 0, 0, 0]을 넣습니다. 그래서 운영체제에 전달되는 크기는 설정값보다 16바이트 작은 0x31affff0, 곧 833,617,904바이트입니다. 생성에 성공하면 풀 객체에 아래 값이 기록됩니다.

생성 성공 뒤 풀 객체의 필드
위치내용
+0x14운영체제가 준 풀 번호(handle)

설정 범위를 산술로 계산한 끝 주소는 0xa0000000입니다. 이 주소 범위가 물리 DRAM에 어떻게 대응하는지는 정하지 않았습니다.

운영체제 경계

풀 생성 함수 0x525b6a58과 할당 함수 0x525b7214는 각각 서비스 번호 0x80450100, 0x80470400을 싣고 SVC 6 명령으로 커널에 들어갑니다. 커널 안쪽의 구현과 현재 풀의 내용은 실행하지 않았습니다.

이름이 GetFreeSpace인 함수 0x530efc80은 운영체제의 조회 경계 0x525b74c0이 0을 돌려주면 조회 결과의 +8, +0xc 두 단어를 내놓습니다. 두 단어가 각각 빈 공간의 합계와 최대 연속 크기인지 따로 식별하지 않았고, 실제 값을 얻지도 않았습니다.

참고: 공개된 T-Kernel 자료와의 비교

이 RTOS의 식별 문자열은 SMP T-Kernel을 가리킵니다(커널 호출과 예약 시각). TRON Forum이 공개한 T-Kernel 2.0 소스에서 가변 크기 메모리 풀의 상태 구조체 T_RMPL은 +8에 빈 영역의 합계, +0xc에 최대 연속 빈 영역을 둡니다. GetFreeSpace가 읽는 두 위치와 같습니다. 다만 이 펌웨어의 서비스 번호는 그 소스의 번호(0x804b0100, 0x804d0400)와 다릅니다. 커널 안쪽을 확인한 것이 아니므로 두 단어의 뜻을 이 비교만으로 확정하지 않았습니다.

이 수치로 판단할 수 없는 것

두 요청의 합이 설정 크기보다 작다는 사실만으로는 메모리가 충분하다고 말할 수 없습니다. 두 버퍼가 함께 잡혀 있는 기간, 같은 풀을 쓰는 다른 코드, 운영체제 안쪽의 관리 비용, 지금 비어 있는 크기, 최대 연속 공간은 따로 확인해야 합니다. 후보 파일을 카메라가 받아들이거나 업데이트가 성공한다고 단정하지 않습니다.

한계와 남은 과제

  • 로더 27건과 풀 35건, 합계 62건은 서로 다른 경계를 검사한 것입니다. 전체 시작 과정이나 실제 대형 버퍼 할당은 실행하지 않았습니다.
  • 대체한 함수는 운영체제의 풀 생성 0x525b6a58, 할당 0x525b7214, 디버그 정보 기록 0x530ef42c, 생성자의 assert 0x530fdfc4, 그리고 로더 쪽의 잠금·기록·파일 호출입니다. assert가 실패했을 때의 실제 처리(정지 여부)는 흉내 내지 않았습니다. 대체 할당 함수는 요청 크기와 관계없이 작은 합성 주소만 돌려줍니다.
  • CPU 모델은 Unicorn의 Cortex-A15입니다. 카메라의 CPU와 같다고 주장하지 않습니다.
  • 디컴파일한 C는 로더 쪽 8개, 풀 쪽 6개로 모두 14개이며 자동 출력 그대로 보관했습니다. 풀 생성 C에는 이름이 없을 때의 조건부 읽기가, 할당 C에는 포인터 형식과 스택 보호 표현이 틀리게 복원된 곳이 있습니다. 계산식과 조건은 원본 ARM 명령과 실행 결과를 근거로 삼았습니다.
  • 남은 연결은 실제 풀 생성과 점유 상태, 입력·출력이 함께 있는 기간, 파일 시스템과 변환 장치, 그 뒤의 검증·기록·부팅입니다. 실제 장치에서 파일 읽기·할당·설치·실행·복구를 수행하지 않았습니다.
