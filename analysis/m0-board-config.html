부팅과 저장소 · M0 초기화 세부

M0 보드 설정 코드는 레지스터에 무엇을 쓰는가

카메라가 켜진 직후 실행되는 M0 코드에는 기판 종류에 따라 골라 쓰는 설정 코드가 있습니다. 이 코드가 입력을 검사하는지, 메모리 주소를 바꾸는 설정을 담고 있는지 확인하려고 여섯 갈래를 모두 읽었습니다.

  1. 배경: M0 단계와 보드 설정

  3. 같은 레지스터에 기록 요청이 여러 번 갑니다
  4. 공개 소스에서 찾은 레지스터 이름
  5. 검증: 본체 두 개를 에뮬레이터에서 끝까지 실행

  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 보드 선택값에 따라 호출되는 설정 본체는 여섯 개입니다. 여섯 개 모두 같은 순서의 주소에 미리 정해진 상수를 쓰고 정해진 횟수만큼 도는 반복문 두 개를 거쳐 돌아옵니다.
  • 이 본체들은 입력 데이터를 읽어 판단하지 않습니다. 바깥 함수를 부르지 않고 코드에 붙은 상수 외에는 메모리를 읽지 않습니다. 따라서 이 안에 데이터를 검사하는 소프트웨어 인증 계산은 없습니다.
  • 본체 두 개는 PC의 CPU 에뮬레이터에서 처음부터 끝까지 실행해 확인했고 나머지 네 개는 명령을 읽어 비교했습니다.
  • 기록한 값이 실제 칩에서 어떤 효과를 내는지는 모릅니다. 그래서 이 결과만으로 SRAM remap이나 하드웨어 인증과 무관하다고 말할 수 없습니다.

확인 원본 코드 실행·바이트 대조

  • 기본 본체와 선택값 0 본체를 에뮬레이터에서 끝까지 실행(4회)
  • 실행마다 기록 125회, 고유 주소 123곳, 반복문 두 개 각 20,000회
  • 코드에 붙은 상수 영역 밖의 데이터 읽기 0회
  • 여섯 본체의 코드·상수 영역 범위와 해시

정적 분석 읽어서 판단

  • 나머지 네 본체(선택값 3·6·9·12)의 명령과 상수 흐름
  • 초기 helper → 보드 본체 → 적재 helper의 기록 순서
  • 공개 Linux 소스의 레지스터 이름과 주소 대조

모델 시험 조건으로 정한 것

  • 레지스터 자리에 일반 RAM을 두고 초기값을 0x00 또는 0xff로 채움
  • CPU는 Unicorn의 Cortex-M0 모델

미확인 확인하지 못한 것

  • 실제 카메라의 보드 선택값
  • 레지스터의 쓰기 가능 비트, 되읽은 값, 부수 효과
  • SRAM remap의 위치, 선행 ROM의 인증

배경: M0 단계와 보드 설정

펌웨어 패키지에는 M0라는 이름의 레코드(92,164바이트)가 있습니다. 전원이 들어온 뒤 이른 단계에 실행되는 코드로 해석하며 클록·메모리·저장소를 준비하고 다음 단계의 진입 주소를 마련합니다. 이 문서의 주소는 정적 분석 기준 주소 0x3ffe0300에 M0 레코드를 놓았을 때의 값입니다. 전체 흐름은 M0 reset·SRAM remap·bank에서 다룹니다.

참고: M0라는 이름

펌웨어에서는 레코드 이름 M0를 확인했습니다. 이 코드는 Thumb 명령으로 되어 있습니다. 검증 도구도 이 코드를 Cortex-M0 모델에서 실행합니다. Socionext 개발자가 Linux 커널 메일링 리스트에 올린 SC2000 소개에는 Cortex-A7 4코어와 함께 “전원 제어용 Cortex-M0”가 나옵니다. M0 레코드가 그 코어에서 도는 코드라는 판단은 이 공개 설명에서 나온 추정입니다. 카메라에서 확인하지는 않았습니다.

M0의 reset 초기화는 기판에 연결된 입력에서 보드 선택값을 만들고 그 값에 맞는 설정 코드를 부릅니다. 이 문서는 그 설정 코드의 내용을 다룹니다.

조사한 이유는 두 가지입니다.

  • SRAM remap을 찾기 위해서입니다. M0는 다음 단계에 넘길 부팅 모드 값을 0x2000fffc에 씁니다. 뒤 단계인 BOOT 코드는 모드 값을 0x0100fffc에서 읽습니다. 두 주소가 같은 메모리라면 주소를 다시 배치하는 설정(remap)이 어딘가에 있어야 합니다. 보드 설정은 레지스터를 많이 기록하므로 후보였습니다.
  • 인증 검사가 숨어 있는지 보기 위해서입니다. 수정한 펌웨어가 받아들여질지 판단하려면 부팅 초기에 이미지를 검사하는 코드가 어디에 있는지 알아야 합니다.
읽는 데 필요한 용어

MMIO 레지스터는 메모리 주소처럼 보이지만 값을 쓰면 하드웨어 설정이 바뀌는 자리입니다. literal pool은 함수 뒤에 붙여 둔 상수 묶음입니다. Thumb은 이 코드가 쓰는 2바이트 명령 형식입니다.

선택값에 따라 여섯 본체 중 하나를 실행합니다

여섯 본체는 기록하는 주소와 순서가 같고 기록하는 값 일부만 다릅니다. 본체 안에는 입력에 따라 갈라지는 분기가 없습니다.

reset 초기화 함수 0x3ffe08b4는 보드 선택값을 읽고 선택기 0x3ffe3594를 부릅니다. 선택기는 값이 12 이하이면 분기 표에서 갈 곳을 찾고 12보다 크면 기본 본체로 갑니다. 분기 표의 13칸 가운데 0·3·6·9·12 다섯 칸만 전용 본체로 이어지고 나머지 여덟 칸은 기본 본체로 이어집니다. 선택값이 만들어지는 과정은 reset 초기화 문서에 있습니다.

같은 레지스터에 기록 요청이 여러 번 갑니다

앞 단계가 일부 비트만 켜 둔 레지스터를 보드 본체가 상수로 덮어쓰고 그중 하나는 뒤 단계에서 다른 값으로 다시 기록됩니다. 한 시점의 기록만 보고 최종 값을 말할 수 없습니다.

0x4dffb208: OR로 켠 비트를 상수로 덮어씁니다

reset 초기화는 초기 helper 0x3ffe0838을 먼저 부르고 그 뒤에 선택기를 부릅니다. 초기 helper는 0x4dffb208을 읽어 0x20을 OR 한 값을 다시 씁니다. 읽은 값의 다른 비트는 그대로 둡니다. 그런데 뒤에 실행되는 보드 본체는 같은 주소에 상수 0x20을 그대로 씁니다. 그러므로 초기 helper의 OR 연산만 보고 “다른 비트가 유지된다”고 설명할 수 없습니다. 실제 레지스터가 쓴 값을 전부 저장하는지는 별개의 문제이며 확인하지 않았습니다.

0x4d021090: 0x3f 다음에 0xf3f가 옵니다

보드 본체는 0x4d021090에 0x3f를 씁니다. 다음 단계의 이미지를 읽어 들이는 작업이 부르는 helper 0x3ffe4db4는 조건이 맞으면 같은 주소에 0xf3f를 씁니다. 그 직전에 세 값을 준비합니다.

공개 소스에서 찾은 레지스터 이름

Ricoh가 공개한 Linux 소스에는 주소가 0x30000000만큼 다른 같은 꼴의 레지스터가 있습니다. 이름을 붙일 단서는 되지만 같은 물리 레지스터라는 실측은 아닙니다.

Ricoh는 K-3 Mark III 2.20용 오픈소스 묶음에 Linux 커널 소스를 배포합니다. 이 소스는 A7 코어에서 도는 Linux가 보는 주소를 씁니다. M0가 기록하는 주소와 나란히 놓으면 다음과 같습니다.

CLK_CRRRS

공개 소스가 CLK_CRRRS라는 이름으로 읽고 복원하는 주소는 0x1d021090입니다. M0의 0x4d021090과 0x30000000 차이가 납니다. 주변장치 주소가 일정한 간격으로 대응한다는 단서일 뿐이고 두 주소가 같은 물리 레지스터임을 측정한 결과는 아닙니다. 소스의 이름은 각 비트의 기능이나 선행 ROM의 인증 정책을 설명하지도 않습니다.

CM0 pinctrl

같은 배포본의 sc2000.dtsi에는 주석으로 막아 둔 디버그용 CM0 pinctrl 노드가 있고 base를 0x1dffb000으로 적습니다. 대응하는 드라이버는 EPCR=0x200과 레지스터당 pin 16개를 정의합니다. GPIO로 쓸 때는 해당 비트를 지우고 그 밖의 기능으로 쓸 때는 비트를 켭니다. 주소 대응이 성립한다면 M0가 켜는 +0x208의 bit 5는 드라이버의 pin index 37(16 × 2 + 5)에 해당합니다.

이 해석에는 조건이 붙습니다. 활성화된 장치 트리 노드, 실제 패키지의 pin 번호, 선택된 주변장치 기능은 확인하지 않았습니다. 다만 이 비트를 켠 바로 뒤에 직렬 포트 설정이 이어진다는 점은 pin 기능 설정이라는 해석과 맞습니다. 그 내용은 M0 진단 직렬 출력에 있습니다.

SRAM remap에 관해 남은 것

  • SRAM 후보 두 주소의 차이는 0x1f000000입니다. 주변장치의 0x30000000 대응을 SRAM에 그대로 적용하지 않았습니다.
  • 여섯 본체에는 0x2000fffc, 0x0100fffc, 0x4dfff0xx에 직접 접근하는 명령이 없습니다.
  • 그렇다고 본체의 상수 기록이 내부 버스나 인증 하드웨어에 영향을 주지 않는다고 말할 수는 없습니다.
  • 다음에 볼 곳은 CLK_CRRRS의 비트 정의, M0와 A7의 버스 매핑 문서, 별도 설정 함수 0x3ffe04a4, 그리고 M0보다 먼저 실행되는 ROM입니다.

검증: 본체 두 개를 에뮬레이터에서 끝까지 실행

기본 본체와 선택값 0 본체를 네 번 실행했고 기록 횟수·순서·읽기 범위가 명령을 읽어 얻은 결론과 같았습니다.

시험 조건

M0 레코드의 원본 바이트를 Unicorn의 Cortex-M0 모델에 올렸습니다. 본체가 기록하는 네 주소 범위에는 서로 독립된 일반 RAM을 두었습니다. 초기값을 모두 0x00으로 채운 경우와 모두 0xff로 채운 경우(32비트로 읽으면 0xffffffff)를 각각 실행했습니다. 바깥 함수를 대체한 것은 없습니다. SRAM 후보 두 주소는 서로 연결하지 않았습니다.

실행마다 다음을 함께 검사했습니다.

  • 실행 위치가 본체의 코드 범위를 벗어나지 않고 정해 둔 복귀 주소로 돌아옵니다.
  • 기록은 모두 4바이트이고 네 주소 범위 안에만 일어납니다.
  • 0x4dffb208에는 0x20, 0x4d021090에는 0x3f가 한 번씩 기록됩니다.
  • RAM 초기값이 달라도 기록 순서와 값이 같습니다. 이 결과로 보아 본체는 기존 값을 읽지 않습니다.
  • r4–r11과 스택 포인터가 실행 전과 같습니다.

같은 도구에 M0 레코드만 넣었을 때와 압축을 푼 전체 스트림(decoded.bin)을 넣었을 때 결과가 같았습니다.

디컴파일 의사코드

기본 본체와 선택값 0 본체는 angr 10.0.5로 C 형태의 의사코드를 만들어 로컬에 보관했습니다. 손으로 고치지 않은 디컴파일러 출력이며 원본 Thumb 명령·제어 흐름 범위와 대조했습니다. literal pool은 실행 명령 수에 넣지 않았습니다. 의사코드는 즉시값 0x3fff0000을 변수 주소처럼 표현하고 남은 r0 값을 포인터 반환처럼 표현합니다. 이는 디컴파일러의 표현 방식이므로 결론은 원본 명령을 기준으로 삼았습니다.

독립 검토의 추가 실행

독립 검토에서는 선택값 3 본체와 선택값 12 본체도 실행했습니다. RAM 초기값은 각각 0x5a와 0xa5였고 같은 기록 횟수와 선택한 기록값을 확인했습니다. 이 2사례는 로컬 검토 기록이며 공개 도구의 4사례에는 들어 있지 않습니다.

한계와 남은 과제

  • 확인한 범위는 선택기 아래 여섯 본체와, 순서를 설명하는 데 필요한 주변 코드 몇 구간입니다. M0 전체나 선행 ROM에 인증이 없다고 주장하지 않습니다.
  • 에뮬레이터의 레지스터는 일반 RAM입니다. 실제 레지스터의 의미, 물리적 대기 시간, 보드 선택기 입력, reset 전체, 인증 하드웨어는 실행하지 않았습니다.
  • 주소는 하드웨어 기능의 이름이 아닙니다. 공개 소스와의 주소 대응만으로 remap, SRAM alias, 코어 해제 방식, 인증 우회를 증명할 수 없습니다.
  • 0이 아닌 bank 값을 만드는 코드와 리소스 레코드 +4의 값을 정하는 정책은 이 분석으로 풀리지 않았습니다. 현재까지의 조건은 쓰기 bank와 BOOT 선택에 있습니다.
  • 펌웨어 빌드, 플래시, 실제 카메라 조작은 하지 않았습니다.

재현 방법

검증 도구는 추출기가 만든 decoded.bin이나 따로 잘라 낸 M0 레코드(m0.bin)를 받습니다. 입력의 SHA-256이 분석한 원본과 같을 때만 실행합니다. Python 패키지 unicorn이 필요합니다. 결과 파일이 이미 있으면 덮어쓰지 않고 멈추므로 새 경로를 지정합니다.

python verify_m0_board_config.py decoded.bin --output m0-board-decoded.json
python verify_m0_board_config.py m0.bin --output m0-board-direct.json

추출 방법은 펌웨어 구조와 하드웨어의 재현 절차에 있습니다.
