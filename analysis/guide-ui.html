UI와 화면 자원 안내

카메라 메뉴는 버튼 입력을 받아 고르는 값을 바꾸고 바뀐 화면을 아이콘과 글자 픽셀로 다시 그립니다. 이 주제는 세 기종에 모두 있는 색공간(sRGB·AdobeRGB) 선택 화면 하나를 골라, 그 과정을 펌웨어 원본 코드로 어디까지 따라갈 수 있는지 기록합니다.

  1. 한눈에 보기: 메뉴 화면 하나가 그려지는 길

핵심 요약

  • K-3 Mark III에서는 방향 입력 → 포커스 이동 → 확정·취소와 설정 기록을 원본 ARM 코드를 PC 에뮬레이터에서 실행해 확인했습니다. 화면 객체와 이벤트는 시험이 만들어 넣었습니다.
  • 그리기 쪽은 색공간 행의 아이콘 복사, sRGB 글자의 측정과 래스터, 32비트 전송, 일곱 좌표의 클리핑을 원본 코드로 실행했습니다. 픽셀은 256×144 합성 RAM 표면에 썼습니다. 결과는 표면 전체를 독립 계산과 대조했습니다.
  • 전송에 쓰인 viewport와 표면이 펌웨어 안에서 어디서 오는지는 코드를 읽어 이었습니다. 맨 위 부모의 클립과 실제 표면을 만드는 코드는 찾지 못했습니다.
  • 다시 그리기 요청에서 행 그리기까지의 연결, 실제 화면 전체의 합성, 색 채널 순서, LCD 출력은 확인하지 못했습니다. 카메라에서 실행한 실험은 없습니다.
  • Q7 쪽은 갱신 한 번 안에서 마커와 두 글자 줄을 8비트 팔레트 번호 버퍼에 그리는 과정까지 원본 코드로 이었습니다. 기종마다 픽셀 형식과 렌더러가 다릅니다.

한눈에 보기: 메뉴 화면 하나가 그려지는 길

위에서 아래로 읽습니다. 왼쪽은 단계, 오른쪽은 그 단계를 다루는 문서입니다. 확인된 지식은 합성 RAM 표면에서 끝나고 LCD는 미확인입니다.

합성 표면 위에서 원본 코드로 확인한 것

K-3 Mark III의 그리기 결과는 모두 시험이 만든 256×144 워드 RAM 표면 위의 결과입니다. 원본 코드가 쓴 바이트를 독립 계산과 표면 전체 단위로 대조했습니다.

시험원본 코드가 한 일시험이 정한 것문서
행과 아이콘타입 19 행 생성, IconView가 ICONBIN 아이콘과 체크 표시를 복사(사례 5개)메뉴·현재값, 사각형, 표면⑤

Q7 갱신갱신 요청부터 버퍼 교체까지 실행, 마커·두 글자 줄 7,675바이트가 독립 계산과 일치등록표, 960×480 8비트 RAM, 큐·잠금·할당⑩

표면의 크기와 주소는 시험이 정한 값입니다. 카메라 화면의 화소 수로 읽으면 안 됩니다.

배경 지식

이 주제의 문서를 읽는 데 필요한 개념 여섯 가지입니다.

위젯, 포커스, 보류값

화면은 행·글자·아이콘 같은 위젯으로 이루어집니다. 포커스는 지금 고르고 있는 행입니다. 확정 전까지 고르는 값은 보류값으로 따로 둡니다. K-3 Mark III와 K-3 II는 확정할 때 기록합니다. Q7은 고르는 즉시 기록합니다.

다시 그리기 요청

값이 바뀌어도 펌웨어가 곧바로 픽셀을 칠하지는 않습니다. “다시 그려라”는 요청을 남기면 나중에 그리기 단계가 위젯 전체를 다시 씁니다. 그래서 상태를 바꾸는 코드와 픽셀을 쓰는 코드를 따로 확인해야 합니다. 그 사이의 연결도 별도 과제입니다.

글리프와 커버리지

글리프는 글자 하나의 모양입니다. K-3 Mark III의 글자 비트맵은 픽셀마다 글자가 얼마나 덮는지를 작은 값(커버리지)으로 담습니다. 0이면 배경을 그대로 둡니다. 부분 값이면 전경과 배경 색을 섞은 값을 씁니다.

클립과 viewport

클립은 그리기를 허용하는 사각형입니다. 자식 요소는 부모의 클립과 자기 영역이 겹친 부분(viewport) 안에만 그립니다(Microsoft Learn: Clipping).

표면, 프레임 버퍼, 스트라이드

표면은 그릴 메모리의 시작 주소, 픽셀 형식, 한 줄의 길이를 담은 설명입니다. 화면에 보이는 메모리는 프레임 버퍼입니다(Linux 커널의 frame buffer 문서). 한 줄의 바이트 수는 스트라이드라고 합니다(Microsoft Learn: Image Stride).

32비트 색 값과 8비트 팔레트 번호

K-3 Mark III의 아이콘과 글자 전송은 픽셀마다 32비트 값을 씁니다. Q7 메뉴 버퍼는 픽셀마다 팔레트 번호 1바이트를 씁니다. 실제 색은 표시할 때 팔레트에서 찾습니다(W3C PNG 규격의 indexed-colour와 같은 방식). 두 기종 모두 바이트가 LCD에서 어떤 색이 되는지는 확인하지 못했습니다.

“확인”은 원본 기계어를 PC 에뮬레이터에서 시험 입력으로 실행한 결과입니다. 수준의 뜻은 검증 수준 읽는 법에 있습니다.

지금까지 알아낸 것과 아직 모르는 것

입력·상태 쪽과 픽셀 쓰기 쪽을 각각 원본 코드로 확인했습니다. 둘 사이의 연결과 표면 이후의 출력은 비어 있습니다.

읽는 순서

입력과 상태에서 시작해 아이콘, 글자, 경계, 출처 순으로 읽으면 앞 문서의 결과가 뒤 문서의 전제가 됩니다. 비교 문서는 K-3 Mark III 쪽을 읽은 뒤에 보면 차이가 잘 보입니다.

가. 출발점

  • ①

    UI 이식 설계

    왜 색공간 화면을 골랐으며 세 기종은 같은 화면을 어떻게 다르게 처리하는가?

    K-3 Mark III·K-3 II는 확정할 때 기록하고 Q7은 고르는 즉시 기록합니다. 이식은 아직 시작하지 않았습니다.

나. 입력과 선택 상태

  • ②

    색공간 화면: 선택·확정·취소

    값을 고르고 확정하면 설정 메모리에 무슨 일이 일어나는가?

    고르는 동안에는 보류값만 바뀝니다. 확정할 때 설정 함수로 넘어갑니다. 16개 사례입니다.

  • ③

    색공간 화면: 방향 입력·포커스

    방향 입력은 포커스를 어떻게 옮기는가?

    네 이벤트 중 둘은 끝에서 순환하고 둘은 멈춥니다. 포커스 변경은 콜백으로 표시 갱신 입구까지 갑니다. 50개 사례입니다.

다. 아이콘과 글자를 픽셀로

  • ④

    ICONBIN 아이콘 자원

    아이콘은 어디에 어떤 모양으로 있으며 어떻게 화면 버퍼로 복사되는가?

    목록은 RTOS에, 32비트 픽셀은 ICONBIN에 있습니다. 회전 없는 복사는 키 값과 같은 픽셀만 건너뜁니다.

  • ⑤

    색공간 행의 아이콘과 글자 측정

    색공간 행은 어떤 아이콘과 문자열을 고르며 글자 크기는 어떻게 정해지는가?

    행·IconView의 아이콘 복사와 Latin 글꼴 준비를 원본 코드로 실행했습니다. sRGB의 배치 크기는 76×40입니다.

  • ⑥

    색공간 sRGB 글자의 래스터와 픽셀 전송

    글자 비트맵은 어떻게 표면의 32비트 값이 되는가?

    부분 커버리지 705개가 각각 한 워드를 썼습니다. 147,456바이트 표면 전체가 독립 계산과 같았습니다.

  • ⑦

    sRGB 글자 전송의 화면 경계

    글자가 표면 가장자리에 걸치면 무엇이 잘리는가?

    일곱 좌표 모두 교차 영역에만 썼습니다. 높이가 0인 경우에도 배경 워드 하나는 읽었습니다.

라. 사각형과 표면은 어디서 오는가

  • ⑧

    글자 viewport가 전송 함수에 닿는 경로

    전송에 쓰인 viewport 사각형은 펌웨어 안에서 어디서 계산되는가?

    부모·자식 클립의 교차가 텍스트 설정을 거쳐 전송 함수로 갑니다. 정적 분석이며 최상위 생산자는 미확인입니다.

  • ⑨

    StringView가 그릴 표면을 받는 경로

    글자를 찍을 메모리 정보는 누가 넘겨주는가?

    Canvas의 표면 포인터가 조건 네 개를 거쳐 StringView에 저장됩니다. 정적 분석입니다.

마. 다른 기종과 비교

  • ⑩

    Q7 화면 갱신 한 번에서 픽셀까지

    Q7에서는 갱신 요청부터 픽셀까지 한 번에 이어지는가?

    마커와 두 글자 줄이 같은 8비트 버퍼에 쓰였습니다. 버퍼 교체 뒤 명령 하나 앞에서 멈췄습니다.

  • ⑪

    K-3 III와 Q7의 sRGB 글자 그리기 비교

    같은 “sRGB” 글자를 두 기종은 어떻게 다르게 그리는가?

    K-3 III는 32비트 색 값을 계산하고 Q7은 팔레트 번호를 씁니다. 같은 값 1이 서로 다른 픽셀을 뜻합니다.

Q7 쪽 단계별 결과는 Q7 화면·글꼴 안내에, K-3 II 쪽은 K-3 II 색공간 메뉴와 표시에 있습니다.
