R 볼륨의 sector 주소 계산과 하위 입출력

R 볼륨에 설정된 두 숫자가 무엇을 뜻하는지 알아보려고, 그 값을 실제로 쓰는 읽기·쓰기 코드를 따라갔습니다. 파일시스템의 요청이 저장 장치 드라이버의 sector 번호로 바뀌는 과정입니다.

이 문서에서

  1. 배경: 볼륨 안의 번호와 장치의 번호
  2. 두 값은 시작 sector 오프셋과 총 sector 수입니다
  3. 읽기와 쓰기는 버퍼 정렬 조건이 다릅니다
  4. 따라간 경로에는 볼륨 끝을 넘는지 보는 비교가 없었습니다
  5. 검증 범위와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • R 볼륨의 두 상수는 시작 sector 오프셋과 총 sector 수입니다. 두 값을 쓰는 파일시스템 연결 함수와 Emmc 읽기·쓰기 함수를 따라가 확인했습니다.
  • 파일시스템이 볼륨 안의 상대 sector 번호로 요청하면, 연결 함수가 시작 오프셋을 더해 Emmc 드라이버에 넘깁니다. 이 경로에서 1 sector는 512바이트입니다.
  • 읽기와 쓰기는 버퍼 정렬 조건이 다릅니다. 읽기는 64바이트, 쓰기는 4바이트 단위로 정렬되지 않은 버퍼를 중간 버퍼로 나눠 처리합니다.
  • 따라간 경로 안에는 요청이 볼륨 끝을 넘는지 확인하는 비교가 없었습니다. 이 경로에서 본 사실이며, 시스템 전체에 범위 검사가 없다는 뜻은 아닙니다.
  • 모든 시험은 합성 버퍼로 했습니다. 실제 저장 장치 입출력, mount, 카메라는 실행하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 시작 오프셋 더하기와 총 sector 수 조회
  • 정렬에 따른 중간 버퍼 사용과 나눠 보내기
  • lock·준비 상태 검사, 최대 3회 시도
  • callback 두 개를 라이브러리 항목에 저장

정적 분석 코드를 읽어 판단

  • volume manager가 전역 변수에 저장되는 초기화 경로
  • vtable 칸과 읽기·쓰기 함수의 대응
  • 진단 문자열에 남은 함수 이름

모델 시험 조건으로 정한 것

  • 직접 만든 R record와 Emmc 객체(종류 3, 준비됨)
  • 한 번에 보내는 상한을 2 sector로 둔 설정
  • 저장 장치 입출력·lock·cache·라이브러리 조회는 대체 함수
  • 읽기 데이터는 합성 바이트, 쓰기는 해시만 기록

미확인 확인하지 않은 것

  • 이 sector 범위가 실제 저장 장치의 어디인지
  • 라이브러리가 callback을 부르는 시점, mount 성공
  • 상위 라이브러리와 하위 드라이버의 범위 검사
  • Virtual·ExFat 경로가 같은 값을 쓰는지

배경: 볼륨 안의 번호와 장치의 번호

앞 문서에서 R 볼륨의 volume record에 상수 두 개가 들어가는 것을 확인했습니다. +0x0c에 0x348000, +0x10에 0x38c000입니다. 그때는 숫자만 알았고 단위와 뜻은 몰랐습니다. 이번에는 두 값을 읽어서 쓰는 코드를 따라가 뜻을 정했습니다.

쉽게 말하면

큰 저장 장치의 한 구역을 볼륨 하나로 씁니다. 파일시스템은 그 구역 안에서 0번부터 번호를 매깁니다. 장치 드라이버는 장치 전체 기준의 번호를 받습니다. 그래서 둘 사이에 “구역이 시작하는 번호를 더하는” 단계가 필요합니다. 이 문서는 그 덧셈이 어디에서 일어나는지 찾은 기록입니다.

  • sector — 저장 장치를 읽고 쓰는 기본 단위입니다. 용량이 2GiB를 넘는 eMMC와 SDHC·SDXC 카드는 512바이트 sector 번호로 주소를 지정합니다. Linux 커널의 MMC 드라이버도 이 장치들의 용량을 512바이트 sector 수로 다룹니다.
  • Emmc — R 볼륨이 가리키는 매체 객체의 클래스 이름입니다. 읽기·쓰기 요청은 이 객체의 가상 함수로 전달됩니다.
  • FAT 연결 함수 — 파일시스템 라이브러리와 매체 객체 사이에 있는 펌웨어 쪽 함수입니다. 분석 기록에서는 FAT adapter, callback이라고 불렀습니다.
참고

여기서 다루는 volume record는 파일시스템 볼륨의 항목입니다. FwPartition의 bank record와 다른 구조이며, 이 문서의 값으로 RTOS의 bank 선택을 설명할 수는 없습니다. bank는 쓰기 bank와 BOOT 선택에서 다룹니다.

두 값은 시작 sector 오프셋과 총 sector 수입니다

+0x0c의 값은 요청한 상대 sector 번호에 더해지고, +0x10의 값은 “총 sector 수” 조회에 쓰입니다.

R 볼륨의 설정값과 512바이트 환산
항목sector 번호·개수10진수512바이트로 환산
시작 오프셋 (record +0x0c)0x3480003,440,6401,761,607,680바이트 (1,680MiB)
총 sector 수 (record +0x10)0x38c0003,719,1681,904,214,016바이트 (1,816MiB)
끝 (포함하지 않음)0x6d40007,159,8083,665,821,696바이트 (3,496MiB)

환산 값은 sector 수에 512를 곱한 계산입니다. 소프트웨어에 설정된 범위일 뿐입니다. 장치가 이 범위를 실제로 제공하는지, 어떤 파일시스템이 선택되는지, 저장 매체의 물리 주소와 어떻게 대응하는지는 이 결과로 판단할 수 없습니다.

읽기와 쓰기는 버퍼 정렬 조건이 다릅니다

요청은 연결 함수에서 Emmc 객체의 읽기·쓰기 함수로 넘어갑니다. 버퍼가 정렬되지 않았으면 중간 버퍼를 거쳐 여러 번에 나눠 보냅니다.

  1. 파일시스템 라이브러리callback을 부르는 시점은 확인하지 못함
  2. 입출력 callbackhandle을 찾고 개수가 0인지 검사
  3. 연결 함수상대 번호에 시작 오프셋을 더함
  4. Emmc 읽기·쓰기버퍼 정렬 검사, 필요하면 중간 버퍼로 나눔
  5. 하위 읽기·쓰기lock과 준비 상태 확인, 최대 3회 시도
  6. sector 입출력 경계시험에서는 인수만 기록하는 대체 함수
읽기와 쓰기의 차이 확인
방향중간 버퍼를 쓰는 조건한 번에 보내는 상한복사 순서하위 경로

512바이트 단위로 읽는 근거

  • 중간 버퍼로 복사하는 바이트 수는 “이번에 보낼 sector 수 × 512”입니다. 512는 Emmc 클래스의 블록 크기 getter(vtable+0x4c)가 돌려주는 값입니다.
  • 반면 sector 번호는 보낸 sector 수만큼만 늘어납니다. 번호에는 512를 곱하지 않습니다.
  • 하위 함수의 진단 문자열이 인수를 sector로 부릅니다.

이 근거는 기본 Emmc 클래스에 묶인 getter를 전제로 합니다. 블록 크기 getter를 재정의한 클래스는 실행하지 않았습니다.

합성 요청에서 본 나눠 보내기

상대 sector 9부터 요청했습니다. 드라이버에는 0x348009부터 전달됐습니다. 한 번에 보내는 상한은 시험에서 2 sector로 두었습니다.

따라간 경로에는 볼륨 끝을 넘는지 보는 비교가 없었습니다

callback에서 Emmc까지의 경로는 총 sector 수를 읽어 요청의 끝과 비교하지 않습니다. 이 경로에 한정한 관찰입니다.

  • 끝을 넘는 요청이 전달됐다는 사실은 이 경로의 관찰입니다. 상위 FAT 라이브러리와 하위 드라이버의 제약은 조사하지 않았습니다. 그래서 시스템 전체에 범위 검사가 없다거나 장치가 그 요청을 받아들인다는 뜻이 아닙니다.
  • 등록되지 않은 경로에서 총량은 대체 포인터가 가리키는 값이 됩니다. 조회 실패 때의 총량을 항상 0이라고 일반화할 수 없습니다.
  • Emmc 매체 객체의 +0x18을 0이 아닌 값으로 만드는 코드와, Virtual·ExFat 파일시스템이 같은 record를 쓰는지는 아직 확인하지 못했습니다.

  • 별도의 로컬 검토 3사례를 더 실행했습니다. 32바이트로만 정렬된 버퍼에서 읽기와 쓰기의 분기가 갈리는지, sector 덧셈이 32비트에서 순환하는지를 보았습니다. 이 3사례는 공개 도구의 25사례에 들어 있지 않습니다.
  • 분석 과정에서 만든 디컴파일 C 출력 10개와 원본 ARM 명령 957 word의 해시를 로컬에 보관합니다.

한계와 남은 과제

  • 시험 조건 — 직접 만든 R record와 기본 Emmc vptr를 썼습니다. 저장 장치 입출력, OS lock, cache, 라이브러리 조회, 등록 준비, 메모리 복사는 모두 명시적인 대체 함수입니다. 읽기는 합성 바이트를 채워 주고, 쓰기는 버퍼의 해시만 기록합니다.
  • 실행하지 않은 것 — 초기화, mount, 실제 파일 접근, 다른 mode와 재정의된 callback, 카메라, 펌웨어 빌드, 플래시 기록.
  • CPU 모델 — Unicorn의 Cortex-A15 모델로 산술과 메모리 흐름을 본 것입니다. 카메라의 CPU나 주변 장치를 재현한 것이 아닙니다.
  • 남은 과제 — R 볼륨의 실제 포맷과 mount 때 고르는 파일시스템, 물리 주소와의 대응, 상위 라이브러리와 하위 드라이버의 범위 검사.

재현 방법

도구는 RTOS만 잘라 낸 rtos.bin이나 추출기가 만든 통합 이미지 decoded.bin을 입력으로 받습니다. 입력의 SHA-256이 아래 값과 다르면 실행하지 않습니다.

RTOS SHA-256
342d2f35405e8daf1797dfe431d2e4aa70f4b52a2c242a29df48206672f1dfb4
통합 이미지 SHA-256
7ff301d585ef7adcd620a15575faa39b4227cc5a27eaa8d754efe50f667a30f9
Python 패키지
unicorn==2.1.4
python verify_update_partition_io.py rtos.bin --output partition-rtos.json
python verify_update_partition_io.py decoded.bin --output partition-decoded.json

Python을 -O로 실행해 assert를 끄면 실행을 거부합니다. 출력 경로에 기존 파일, hardlink, 대상이 없는 symlink가 있으면 입력을 읽기 전에 멈춥니다. 결과는 새 경로에만 만듭니다.
