Lightroom 색 프로파일 · K-3 III As Shot 중립값

K-3 III PEF에서 확인한 As Shot 중립값

K-3 III RAW(PEF)에는 Lightroom이 화이트밸런스 계산에 쓰는 표준 중립값 태그가 없습니다. Adobe 변환기가 어떤 값을 기록하는지 확인하고, 그 값으로 프로파일별 온도·틴트를 계산했습니다.

이 문서에서

  1. 배경: PEF에는 표준 중립값이 없습니다
  2. 두 DNG 변환에서 CFA 데이터가 일치했습니다
  3. 녹색 기준 역수 비율이 표준 중립값과 일치했습니다
  4. 같은 중립값에서 프로파일별 온도와 틴트를 계산했습니다
  5. 한계와 남은 과제
  6. 새 변환과 고정 입력 재현
  7. 근거 파일과 참고 자료

핵심 요약

  • K-3 III 스튜디오 PEF 한 장(촬영 펌웨어 1.10)의 복사본을 PC의 Adobe DNG Converter 18.7로 두 번 변환했습니다. 두 DNG의 센서 데이터는 같았고 둘 다 RGB 중립값 (0.431703, 1, 0.625917)을 기록했습니다.
  • 이 값은 PEF MakerNote의 WhitePoint(18976, 8192, 8192, 13088)를 녹색 기준 역수로 바꿔 소수 여섯 자리로 반올림한 값과 같습니다. 두 녹색 값이 같은 이 표본에서만 확인한 관계입니다.
  • 같은 중립값으로 Adobe DNG SDK 수식을 Python으로 재현했습니다. 매트릭스 4678은 5383.940 K/−7.231, Adobe Standard와 Camera Bright는 둘 다 5341.829 K/−6.123이 나왔습니다. 계산한 변화 −42.111 K/+1.107은 Lightroom 표기 변화 −50 K/+1과 7.889 K 차이가 납니다.
  • 한계: 계산 입력은 변환기 DNG이고 비교한 표기는 Lightroom 16.0에서 원본 PEF를 열어 얻었습니다. Lightroom의 실제 채널 이득과 반올림 규칙, PEF와 DNG가 똑같이 렌더링되는지는 확인하지 못했습니다.

확인 실제 실행과 파일 대조

  • Converter 18.7 변환 두 번, 두 DNG의 바이트 차이와 디코딩 CFA 해시
  • DNG의 AsShotNeutral·AnalogBalance와 MakerNote WhitePoint의 유리수 대조
  • Lightroom 16.0이 원본 PEF에서 표시한 As Shot 온도·틴트

모델 Python 수식 재현

  • SDK 1.7.1 Build 2768 수식으로 계산한 백색점과 온도·틴트
  • CameraWhite와 카메라→D50 행렬은 이 모델에서 계산한 값

미확인 알 수 없는 것

  • Lightroom의 채널 이득, UI 반올림 규칙, PEF·DNG 렌더 동등성
  • 두 녹색 값이 다른 사진에서의 관계
  • 변환기가 프로파일을 고르는 과정, 분석 펌웨어 2.20 RAW에서의 결과

배경: PEF에는 표준 중립값이 없습니다

DNG는 촬영 때 회색이 센서에 찍힌 비율을 AsShotNeutral 태그에 적습니다. Lightroom은 이 값을 프로파일의 ColorMatrix로 풀어 As Shot 온도·틴트를 정합니다(SDK 계산 경로). PENTAX 고유 RAW인 PEF에는 이 표준 태그가 없습니다. 대신 제조사 영역(MakerNote)에 WhitePoint라는 채널별 배율 네 개가 있습니다.

Lightroom이 PEF를 열 때 어떤 중립값을 쓰는지는 바깥에서 볼 수 없습니다. 그래서 Adobe DNG Converter로 PEF를 DNG로 바꿔, 변환기가 기록한 표준 중립값을 대신 확인했습니다.

쉽게 말하면

WhitePoint는 "R은 18976, G는 8192만큼 곱하라" 같은 배율입니다. 중립값은 그 반대로 "회색이 R:G:B = 0.43:1:0.63으로 찍혔다"는 비율입니다. 녹색을 1로 맞춘 뒤 역수를 취하면 한쪽에서 다른 쪽을 얻습니다.

두 DNG 변환에서 CFA 데이터가 일치했습니다

두 번 변환한 DNG는 날짜와 생성 ID 105바이트만 달랐고 디코딩한 센서 픽셀은 같았습니다.

설치된 Windows 명령줄 변환기로, 원본 해시와 같은 복사본 두 개를 각각 변환했습니다. 원본과 복사본 PEF의 해시는 변환 전후 그대로였습니다. 두 실행 모두 종료 코드 0이었고 GPU·WinML 초기화 진단 메시지는 로그에 남겼습니다.

녹색 기준 역수 비율이 표준 중립값과 일치했습니다

MakerNote WhitePoint를 녹색 기준 역수로 바꾸면 DNG의 AsShotNeutral과 소수 여섯 자리까지 같습니다.

원본 PEF에는 표준 AsShotNeutral 태그가 없었습니다. Pentax MakerNote 0x0201의 WhitePoint는 18976, 8192, 8192, 13088이며 변환 DNG에도 그대로 남았습니다. LibRaw의 PEF 파서는 이 값을 RGGB 순서의 As Shot WB로 읽습니다. 이 표본은 두 녹색 값이 같아서 녹색 기준 역수의 RGB 비율을 바로 대조할 수 있었습니다.

두 DNG의 AnalogBalance는 (1, 1, 1)이고 CameraCalibration1/2/3과 CameraCalibrationSignature는 없습니다. com.adobe는 별도의 ProfileCalibrationSignature 값입니다. 역수 비율이 맞는다는 관찰은 두 녹색 값이 같은 이 표본에 한정됩니다.

메타데이터는 ExifTool 13.59로 읽었습니다. Windows 런처와 설치된 Pentax 파서 모듈의 해시를 각각 기록했지만 전체 Perl 실행 환경이 온전한지는 확인 범위 밖입니다(표준 태그와 도구 해시). 해석 근거는 LibRaw 0.22.0 파서, 채널 순서, ExifTool 13.59 태그 정의입니다.

같은 중립값에서 프로파일별 온도와 틴트를 계산했습니다

Adobe Standard와 Camera Bright는 ColorMatrix가 같아 계산 결과도 같았습니다. 매트릭스 4678과의 차이는 −42.111 K였고 Lightroom 표기 차이는 −50 K였습니다.

변환기가 기록한 중립값을 세 프로파일에 넣어, 공개 Adobe DNG SDK 1.7.1 Build 2768의 수식을 Python으로 재현했습니다. 계산 순서는 SDK 계산 경로와 같습니다.

두 Adobe 프로파일은 ForwardMatrix가 달라, 카메라→D50 PCS 행렬의 최대 성분 차이가 0.619123입니다. 모델 CameraWhite는 매트릭스 기준과 최대 1.02×10⁻⁸ 차이였습니다. SDK의 저온 분기나 미수렴 대안은 쓰지 않았습니다. DNG에 내장된 ColorMatrix 두 개, 조명 태그 두 개, ForwardMatrix 두 개는 Adobe Standard의 해당 데이터와 바이트 단위로 같습니다. 변환기가 프로파일을 고르는 과정은 관측하지 않았습니다. 세 프로파일의 행렬·태그별 해시와 전체 결과는 세 프로파일 전체 결과에 있습니다.

주의

계산 입력은 Converter 18.7의 DNG이고 비교한 표기는 Lightroom 16.0에서 원본 PEF를 열어 얻었습니다. Lightroom의 실제 채널 이득, UI 반올림 규칙, PEF와 DNG의 렌더 동등성은 확인하지 못했습니다. 참조 프로파일 실험에서 As Shot 표기가 바뀌어 엄격한 WB 동일 조건이 실패한 결과도 그대로입니다(원본 PEF 현상 비교).

한계와 남은 과제

  • PEF 한 장, 촬영 펌웨어 1.10의 결과입니다. 분석 대상 펌웨어 2.20으로 찍은 RAW는 쓰지 않았습니다.
  • WhitePoint와 중립값의 역수 관계는 두 녹색 값이 같은 이 표본에서만 확인했습니다.
  • Lightroom이 PEF를 열 때 쓰는 중립값과 채널 이득은 직접 보지 못했습니다. 변환기 DNG는 대리 근거입니다.
  • 재현 계산기는 Converter나 Lightroom을 실행하지 않습니다.

새 변환과 고정 입력 재현

새 변환을 확인하려면 먼저 원본 PEF의 SHA-256이 기록과 같은지 봅니다. 그다음 독립 복사본을 새 폴더에서 변환합니다. -c는 무손실 압축, -p0은 별도 JPEG 미리보기 없음입니다. 실제 결과에는 256×171 RGB 썸네일이 들어 있습니다. 원본 내장·선형 DNG·손실 압축·크기 제한 옵션은 쓰지 않았습니다(Adobe CLI 옵션).

"Adobe DNG Converter.exe" -c -p0 -d <새 폴더> -o K3IIIhSLI0000100NR0.dng <PEF 복사본>

아래 계산기는 연구 당시의 첫 번째 DNG 파일을 입력으로 씁니다. 새로 변환한 파일은 CFA가 같아도 날짜와 UUID가 달라 전체 파일 해시가 바뀝니다. SDK ZIP과 DCP 세 개의 크기·해시도 확인하고 온도 표는 지정한 SDK ZIP에서 읽습니다. Adobe DCP·SDK·사진 원본은 배포하지 않습니다. 매트릭스 4678 DCP는 매트릭스 4678 레시피의 profile_recipes.k3iii.spec와 DCP 생성기 profile_bridge.py로 다시 만듭니다. SDK 사용 조건은 Adobe SDK 라이선스를 보십시오.

python -B tools/check_lightroom_pef_neutral.py --sdk dng-sdk.zip \
  --dng first-converted.dng --matrix pentax-k3iii-4678-matrix-test.dcp \
  --adobe-standard "PENTAX K-3 Mark III Adobe Standard.dcp" \
  --camera-bright "PENTAX K-3 Mark III Camera Bright.dcp" --output result.json

검증기는 기준 결과와 전체 구조·자료형을 비교합니다. 유한 실수의 허용 오차는 절대차 10⁻¹⁰입니다. 새 출력의 실제 SHA-256과 기준 SHA-256을 나란히 표시합니다. 기록에는 OpenBLAS Nehalem 커널로 계산한 대조도 있습니다. 실수 25개가 바뀌었고 최대 차이는 4.44×10⁻¹⁶이었습니다.
