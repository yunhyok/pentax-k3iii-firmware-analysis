원본 압축 블록을 그대로 두는 재패키징

앞 단계의 후보는 압축을 풀어 담아 원본보다 두 배 넘게 컸습니다. 바뀐 부분만 새로 넣고 나머지 압축 블록은 원본 그대로 재사용하면, 원본에 가까운 크기로 줄일 수 있습니다.

핵심 요약

  • 함수 하나만 바꾼 펌웨어 후보를 35,136,788바이트로 다시 만들었습니다. 원본보다 30,072바이트 클 뿐이고 압축을 전부 푼 앞 단계 후보(약 7,900만 바이트)보다 4,355만 바이트 작습니다.
  • 원본 압축 스트림의 블록 3,202개 중 3,198개는 원본 인코딩 바이트를 그대로 재사용하고 바뀐 내용에 영향을 받는 4개만 다시 저장했습니다. 압축을 푼 결과는 앞 단계의 후보와 바이트까지 같았습니다.
  • 독립 디코더로 다시 풀어 같은 결과가 나오는지, 원본 펌웨어의 헤더·체크섬 검사를 통과하는지 확인했습니다. 카메라의 RAM·하드웨어 디코더·업데이트·부팅은 확인하지 않았습니다.

확인 바이트 대조·원본 코드 실행으로 확인

  • 공개 도구의 후보가 선행 후보와 바이트 단위로 일치
  • 교체하지 않은 3,198개 블록이 원본 인코딩과 각각 일치
  • 독립 디코더로 푼 결과가 전부 저장 후보와 일치
  • 원본 ARM 헤더·체크섬 검사 8건 통과·거절 일치

모델 시험 조건으로 정한 것

  • 입력은 선행 단계의 전부 저장 후보 하나
  • 저장 블록은 관측한 0x6000바이트 단위로 인코딩
  • 합성 경계 테스트 8개(참조 거리·정렬·겹침 복사)

미확인 확인하지 않은 것

  • 카메라의 RAM·파일 크기 한계, 하드웨어 디코더
  • 실제 업데이트 실행, 저장장치 쓰기, 부팅
  • 원본 압축기 자체(재현한 것은 결과 일치일 뿐)

배경: 왜 압축 블록을 그대로 두는가

앞 단계에서는 바꾼 내용을 넣은 뒤 펌웨어를 전부 압축 없이 저장했습니다. 검증에는 충분했지만 파일이 두 배 넘게 커졌습니다. 카메라가 받아들일 수 있는 크기에 가깝게 하려면, 바뀐 부분만 새로 넣고 손대지 않은 부분은 원본이 쓰던 압축 그대로 재사용하는 편이 낫습니다.

원본 압축기를 복원하지는 못합니다. 대신 바뀐 바이트의 영향을 받지 않는 블록은 원본 인코딩을 그대로 복사하고 영향을 받는 블록만 압축 없이 다시 저장합니다.

어떤 블록을 그대로 쓰는가

압축의 복사 명령은 최대 8,191바이트 뒤까지 되돌아 참조합니다. 그래서 한 블록의 출력과, 그 앞 8,191바이트가 원본과 같으면, 원본 압축 바이트를 그대로 풀어도 같은 결과가 나옵니다.

쉽게 말하면

압축은 “조금 전에 나온 글자를 그대로 다시 써라”라는 식의 복사 명령으로 되어 있습니다. 복사가 최대 8,191글자 전까지만 거슬러 가므로, 그만큼 앞 범위와 현재 블록이 원본과 같다면 원본의 복사 명령을 그대로 재생해도 결과가 어긋나지 않습니다.

교체 블록을 고른 뒤 전체 길이가 홀수가 되면, 교체하지 않은 블록 중 변화량이 가장 작은 것을 하나 더 저장 블록으로 바꿔 길이를 맞춥니다. 4의 배수가 되지 않으면 저장 조각 하나를 둘로 나눕니다. 이번 후보에서는 길이 맞춤용 교체가 한 번 있었고 분할은 필요하지 않았습니다.

이번 후보에서 바꾼 네 블록

실제로 내용이 바뀐 블록은 함수 코드가 든 523번과 체크섬이 든 3201번입니다. 524번은 바뀐 바이트가 직전 참조 범위에 들어와서, 873번은 전체 길이를 맞추려고 함께 저장 블록으로 바꿨습니다.

블록 번호는 0부터 셉니다. 인코딩 크기는 블록 머리말을 포함합니다.

검증 결과와 적용 범위

공개 도구가 만든 후보가 선행 후보와 바이트까지 같고 두 가지 독립 방법으로 다시 풀어도 목표 내용과 일치했습니다.

  • 자체 재현: 공개 도구로 다시 만든 후보가 선행 실험의 선택 후보와 바이트 단위로 같았습니다. 교체하지 않은 3,198개 블록도 원본 인코딩과 각각 대조했습니다.
  • 독립 디코더: 다른 사람이 만든 디코더(Trimz/Ricoh3x, 특정 커밋으로 고정)로 후보를 풀었을 때 결과가 전부 저장 후보와 같았습니다. 같은 압축 형식을 쓰는 리코 GR 계열 도구를 K-3 III 바이트로 교차 확인한 것입니다.
  • 원본 ARM 검사: 원본 펌웨어의 헤더·체크섬 검사 코드를 에뮬레이터에서 실행해 원본과 후보 각각 네 번 돌렸습니다. 정상 입력은 받아들이고 프로젝트·매직 값을 바꾼 입력은 거절했습니다.
  • 합성 경계 테스트: 참조 거리 8191·8192의 경계, 겹치는 복사, 홀짝 정렬, 큰 블록 분할, 잘못된 길이·범위 거절, 출력 덮어쓰기 방지 등 8개 테스트를 통과했습니다.

주의

여기서 확인한 것은 호스트에서의 압축 해제와 원본 ARM의 헤더·체크섬 판정까지입니다. 카메라의 RAM 할당과 파일 크기 한계, 하드웨어 디코더, 실제 업데이트 실행, 저장장치 쓰기와 부팅은 별도 검증이 필요합니다.

한계와 남은 과제

  • 이 방법은 원본 압축기를 복원한 것이 아닙니다. 바뀌지 않은 블록의 원본 바이트를 그대로 복사하고 영향받는 블록만 압축 없이 저장하는 보수적 방식입니다.
  • 레코드 크기 변경, 추가·삭제, 소스 컴파일, 링커 재구성, 서명 생성은 지원하지 않습니다.
  • 카메라가 이 후보를 실제로 받아 동작하는지는 미확인입니다. 통합 전 확인 항목은 수정·이식 선행 연구에 있습니다.

재현 방법

해시가 일치하는 공식 2.20 원본과, 앞 단계의 전부 저장 후보를 입력합니다. 출력 폴더는 .private 아래에서 아직 없는 경로를 지정합니다.

python -B tools/repack_changed_blocks.py ORIGINAL.bin FULL_STORED.bin \
  --output-dir .private/selective-repack-local
python -B -m unittest discover -s tests -p test_repack_changed_blocks.py -v

공개 기록에는 구조와 해시만 들어 있습니다. 원본 압축 스트림과 추출한 독점 코드는 포함하지 않습니다.
