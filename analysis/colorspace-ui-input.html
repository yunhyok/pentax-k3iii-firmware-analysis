색공간 UI 입력과 focus callback

방향 이벤트가 리스트의 선택 index를 바꾸고, 등록된 callback을 통해 메뉴 표시 갱신을 요청하는 경로를 확인했다.

연구 개요 · 선택·확정·리소스 · 기종 간 이식 조건

route 0200009f의 descriptor72(십진수)를 기준으로, 방향 이벤트에서 실제 list+0x1ce 저장까지 연결했다. df/e0는 양 끝에서 순환하고 e3/e4는 해당 경계에서 멈춘다. 목록의 focus 변경은 옵션 확정·저장과 별도이며 실제 등록된 menu focus callback이 표시 갱신 경계로 이어지는 부분도 확인했다. 원본 ARM 검사 50개가 통과했다. [검사 기록, 주소·hash·관계 증거]

원본 RTOS base 52500000, SHA-256 342d2f35405e8daf1797dfe431d2e4aa70f4b52a2c242a29df48206672f1dfb4. 주소와 offset은 16진수다. descriptor72는 536439e0 + 72 × 5c = 536453c0이며 byte+3=1이다. M은 menu, L=M.ptr[1c8]은 list다. 물리 버튼이나 다이얼의 이름은 추정하지 않았다.

실제 focus writer와 서로 다른 row 상태

52c0e948은 현재 index의 앞이나 뒤를 검색하고 필요하면 반대쪽으로 돌아가며 item.byte[178] != 0인 항목을 이동 대상으로 센다. 52c0e25c도 대상의 이 byte를 검사한 뒤, 대상이 바뀌면 52c0e2cc STRH로 L+1ce에 저장한다. 후보가 부적격이면 저장 전에 돌아간다. [목록 이동, focus setter]

필드확인된 소비·생산 관계
item+178이동 검색과 focus setter가 사용하는 자격 byte. base item constructor는1로 초기화한다. 실제 색 공간 item의 이후 생산자·정책 전체는 미확정이다.
item+8ageneric visibility getter/setter가 읽고 쓰는 별도 byte. 이 값만0으로 바꾸고 item을 합성 pointer array에 남긴 검사에서는 이동이 계속됐다. 실제 숨김 처리에서 목록·기하가 어떻게 재구성되는지는 검사하지 않았다.
item+17a색 공간 confirm 경로5278db58..60이 확인하는 차단 byte. base constructor는0으로 초기화한다. 이 byte가1인 합성 row도+178이1이면 이동 대상이 됐다. focus 가능과 확정 가능을 같은 상태로 취급할 수 없다.

근거: base item constructor, visibility setter, 17a setter, confirm gate. synthetic flag 검사는 실제 UI의 hidden/disabled row 생성 조건을 입증한 것이 아니다.

Callback과 표시 갱신 경계

변경된 유효 target에 대한 52c0e25c의 순서는 다음과 같다. 기존 item의 vslot+70을 호출하되 기본 함수 52c0d6c4이면 생략한다. 이어 L+1ce를 기록한다. L.byte1d0이 nonzero이면 새 item의 vslot+6c를 호출하되 기본 함수 52c0d6c0이면 생략한다. 마지막으로 L.byte224가 nonzero이면 52c0e1c0을 통해 focus-change callback을 호출한다. supplied callback 검사에서 이전 callback은 이전 index, 이후 callback은 새 index를 읽었다. 실제 색 공간 row의 동적 item vptr까지 복원한 것은 아니다.

FocusChangeCallBack 문자열 53872c18과 View/ScrollList/ScrollListView.cpp 문자열 53628364가 focus notification 함수에서 사용된다. 이 함수는 L+220을 읽어 52c0e238 BX r3로 호출하며 r0=L+214 closure, r1=새 focus를 넘긴다. [notification 함수, 기본 no-op callback]

이 callback의 실제 menu 등록도 이어진다. 5278dcd0..5278dd54의 첫 등록 block은 menu pointer를 담은 closure, manager 5278b7b0, invoker 5278ecd0를 만든다. 52c0dfcc는 복사된 closure를 L+214, manager를+21c, invoker를+220에 저장하고+224를 활성화한다. 따라서 이후 실제 focus 변경은 5278ecd0 → 5278ec04를 호출한다. 색 공간 descriptor+38/+3c는 모두0이므로 row별 hook을 생략하고 byte0=1에 따라 5278ecc4 → 5278e4ac 표시 갱신 경계로 들어간다. [등록 block, installer, menu callback, 표시 갱신 함수]

두 수치 검사는 등록 block과 원래 closure manager·installer를 실행한 다음 실제 방향 이벤트로 실제 menu callback까지 진입했다. 5278e4ac는 그 검사에서 명시적 stub이다. 정적 ARM상 이 함수는 row+18 callback 52776a08 및 visibility setter로 이어지지만 그 아래의 실제 그리기를 실행했다고 주장하지 않는다.

Animation 경로의 확인 범위

목록 검색이 경계를 넘어 순환하면 52c0eac0에서 transition 인자를0으로 바꾼다. 즉시 경로는 focus setter와 scroll setter를 부른다. 순환하지 않는 이동에 transition 인자가1이면 52c0e838로 가서 L.byte1dc=2와 전환용 위치값을 기록한다. 이 함수도 52c0e900에서 focus setter를 먼저 호출하고 나중에 52c0e920 → 528f8228로 scheduler 등록을 요청한다. 화면 animation이 끝난 뒤에야 focus가 바뀐다는 구조는 아니다. [전환 준비 범위·해시]

두 번째 이벤트가 목록 이동 함수 52c0e948에 진입하면 기존 state2를 먼저 정리한다. 52c0e528은 scheduler 해제를 요청하고 저장된 scroll target을 적용한 뒤 current focus를 다시 setter에 전달하고 state를 0으로 바꾼다. e0→e0 검사에서 focus 0→1→0과 scheduler 등록 후 해제를 확인했다. 경계에 도달한 뒤 e0→e4와 df→e3의 두 번째 이벤트는 각각 5278daa0, 5278d9dc에서 목록 이동 함수에 진입하기 전에 반환한다. 두 사례 모두 focus와 state2를 유지했고 scheduler 해제 요청은 없었다. asynchronous tick, 시간 곡선, 실제 frame, state1 전환은 이번 범위 밖이다. [전환 정리 함수]

재현과 한계

검사 50개는 방향 이벤트 8개, 4행 이동 16개, 자격 검색 12개, 별도 상태 byte 4개, focus setter 5개, 연속 이벤트 3개, 실제 callback 등록 block→소비 2개로 구성된다. 이전 population/confirm 검사 횟수를 합산하지 않았다. 원본 geometry 복사·높이·누적위치, 검색·저장·전환 준비는 그대로 실행하고 rendering·scheduler·clock·heap과 supplied callback만 주소별로 stub 처리했다. [독립 수치 검사, 소스 검증]

python verify_colorspace_ui_input.py rtos.bin --output colorspace-ui-input-checks.json

입력은 SHA-256으로 검증한 RTOS 또는 decoded.bin이다. synthetic menu/list와 geometry를 사용하며 OS·렌즈·camera·media I/O는 없다. 첫 callback 등록 block은 부분 실행이며 전체 3개 action 등록이나 full window lifecycle은 아니다. zero-sized/all-ineligible list, 실제 hidden-row membership 재구성, 실제 color-row vtable 대상, 물리 입력 producer는 미확정이다. Cortex-A15 emulation을 카메라 fidelity로 간주하지 않는다. genuine angr C8개는 수정 없이 보존했고 predication·타입 오류가 있을 수 있으므로 ARM이 판단 기준이다.

50개 합성 CPU 검사다. 물리 입력·비동기 animation tick·완성 화면·전체 창 수명 주기는 검증하지 않았다. 화면 렌더링 검사는 생략하고 HTML 구조·링크를 확인했다.
