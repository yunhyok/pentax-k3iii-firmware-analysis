UI와 화면 자원 · 색공간 화면 2

색공간 화면에서 방향 입력이 포커스를 옮기는 과정

선택지 사이를 오가는 입력이 펌웨어 안에서 어떤 순서로 처리되는지 알아봤습니다. 포커스를 옮기는 일은 값을 확정하는 일과 별개의 단계이며, 화면을 옮겨 심으려면 두 단계의 경계를 정확히 알아야 합니다.

이 문서에서

  1. 배경: 포커스 이동은 확정과 별개의 단계입니다
  2. 방향 이벤트 네 가지와 목록 끝에서의 동작
  3. 옮겨 갈 수 있는 행은 자격 바이트가 정합니다
  4. 포커스가 바뀐 사실은 콜백으로 메뉴에 전달됩니다
  5. 전환 애니메이션을 예약해도 포커스는 먼저 바뀝니다
  6. 50가지 사례를 어떻게 실행했는가
  7. 한계와 남은 과제
  8. 재현 방법
  9. 근거 파일과 참고 자료

핵심 요약

  • 방향 이벤트는 네 가지입니다. 두 가지는 목록 끝에서 반대쪽 끝으로 돌아가고, 나머지 두 가지는 끝에서 멈춥니다. 어떤 버튼이나 다이얼이 이 이벤트를 만드는지는 확인하지 않았습니다.
  • 포커스 이동은 목록 객체의 포커스 번호 하나를 바꾸는 일입니다. 설정값은 건드리지 않습니다. 옮겨 갈 수 있는 행인지는 행마다 있는 자격 바이트가 정하며, 표시 여부나 확정 차단과는 다른 바이트입니다.
  • 포커스가 바뀌면 이전 행 알림 → 번호 기록 → 새 행 알림 → 메뉴 콜백 순서로 호출됩니다. 메뉴 콜백은 표시를 갱신하는 함수의 입구까지 이어집니다.
  • 전환 애니메이션을 예약하는 경우에도 포커스 번호는 예약보다 먼저 바뀝니다.
  • 원본 ARM 코드를 PC 에뮬레이터에서 50가지 합성 상황으로 실행했습니다. 그리기, 스케줄러, 시계는 호출만 기록하는 대체 함수였고 화면이 실제로 그려지는 과정은 실행하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 이벤트 네 가지의 이동 방향과 끝에서의 동작
  • 자격 없는 행을 건너뛰는 검색과 포커스 번호 기록
  • 콜백 호출 순서, 메뉴 콜백 등록과 호출
  • 전환 준비와 두 번째 이벤트의 정리 순서

정적 분석 코드를 읽어 판단

  • 표시 갱신 함수가 머리글 함수와 표시 여부 설정으로 이어지는 것
  • 행 객체의 기본 생성자가 넣는 초기값

모델 시험 조건으로 정한 것

  • 메뉴·목록·행 객체와 행 크기·스크롤 위치
  • 행의 알림 함수는 시험이 넣어 준 기록용 함수
  • 그리기 무효화, 스케줄러, 시계, 힙은 대체 함수
  • CPU는 Unicorn의 Cortex-A15 모델

미확인 확인하지 않은 것

  • 이벤트를 만드는 실제 버튼·다이얼·터치
  • 애니메이션의 시간 진행과 실제 화면 프레임
  • 실제 색공간 행 객체의 가상 함수 표
  • 빈 목록, 자격 있는 행이 하나도 없는 목록

배경: 포커스 이동은 확정과 별개의 단계입니다

색공간 선택 화면에는 sRGB와 AdobeRGB 두 행이 있습니다. 앞 문서에서 본 것처럼 화면에서 고르는 중인 값은 목록 객체의 포커스 번호(list+0x1ce)이고, 확정 이벤트가 와야 그 번호가 설정 함수로 넘어갑니다. 앞 문서의 시험은 이 번호를 직접 써 넣었습니다. 이 문서는 그 빈칸, 곧 방향 이벤트가 실제로 이 번호를 바꾸는 과정을 원본 코드로 실행한 기록입니다.

아래에서 M은 메뉴 controller 객체, L은 M의 +0x1c8이 가리키는 목록 객체입니다. 색공간 화면은 descriptor 72번(10진수, 주소 0x536453c0)을 씁니다. 그 밖의 주소와 offset은 모두 16진수입니다. 이벤트 번호는 펌웨어 안의 숫자일 뿐이며, 물리 버튼이나 다이얼의 이름을 붙이지 않았습니다.

방향 이벤트 네 가지와 목록 끝에서의 동작

이벤트 0xdf와 0xe0은 끝에서 반대쪽으로 돌아가고, 0xe3과 0xe4는 끝에서 멈춥니다. 색공간 화면처럼 행이 둘이면 앞의 둘은 항상 다른 행으로 넘어갑니다.

이벤트 처리 함수는 이벤트 번호에 따라 방향 wrapper 둘 중 하나를 부르고, 두 번째 인수로 ‘끝에서 멈출지’를 넘깁니다.

  • 번호가 늘어나는 쪽 wrapper는 descriptor의 개수 함수(0x5277620c)를 불러 선택지 수 2를 얻고 마지막 행인지 판단합니다.

옮겨 갈 수 있는 행은 자격 바이트가 정합니다

목록 이동 함수는 행의 바이트 +0x178이 0이 아닌 행만 이동 대상으로 셉니다. 표시 여부 바이트(+0x8a)나 확정 차단 바이트(+0x17a)는 이동에 영향을 주지 않았습니다.

목록 이동 함수(0x52c0e948)는 현재 번호의 앞이나 뒤를 차례로 살피고, 필요하면 반대쪽 끝으로 넘어가면서 자격 있는 행을 찾습니다. 포커스 설정 함수(0x52c0e25c)도 대상 행의 같은 바이트를 한 번 더 검사합니다. 대상에 자격이 없으면 번호를 쓰기 전에 돌아가고, 대상이 지금과 다를 때만 0x52c0e2cc의 16비트 저장으로 L+0x1ce를 바꿉니다.

포커스가 바뀐 사실은 콜백으로 메뉴에 전달됩니다

포커스 설정 함수는 이전 행에 알리고, 번호를 기록하고, 새 행에 알린 다음, 메뉴가 등록해 둔 콜백을 부릅니다. 색공간 화면에서 이 콜백은 표시 갱신 함수의 입구로 이어집니다.

  1. 이전 행에 알림 이전 행의 가상 함수 표 +0x70 칸을 부릅니다. 그 칸이 기본 함수(0x52c0d6c4)이면 생략합니다.
  2. 번호 기록 L+0x1ce에 새 행 번호를 씁니다.
  3. 새 행에 알림 L+0x1d0이 0이 아니면 새 행의 +0x6c 칸을 부릅니다. 기본 함수(0x52c0d6c0)이면 생략합니다.
  4. 메뉴 콜백 L+0x224가 0이 아니면 알림 함수(0x52c0e1c0)를 거쳐 L+0x220에 등록된 함수를 부릅니다. 인수는 L+0x214의 클로저와 새 포커스 번호입니다.

기록용 알림 함수를 넣은 시험에서 이전 행 알림은 바뀌기 전 번호를, 새 행 알림은 바뀐 뒤 번호를 읽었습니다. 순서가 위와 같다는 뜻입니다. 실제 색공간 행 객체가 어떤 알림 함수를 가지는지는 복원하지 않았습니다.

메뉴가 콜백을 등록하는 과정

알림 함수 안에서는 FocusChangeCallBack이라는 문자열과 소스 파일 이름 View/ScrollList/ScrollListView.cpp가 쓰입니다. 펌웨어에 남은 이 이름들로 이 필드가 ‘포커스 변경 콜백’임을 확인했습니다.

메뉴 쪽 코드의 첫 등록 구간(0x5278dcd0–0x5278dd54)은 메뉴 포인터를 담은 클로저, 클로저 관리 함수, 호출 함수를 만들어 목록의 설치 함수(0x52c0dfcc)에 넘깁니다. 설치 함수는 아래 네 필드를 채웁니다.

목록 객체에 설치되는 콜백 필드
필드설치되는 값
L+0x214메뉴 포인터를 담은 클로저의 사본

그 뒤 포커스가 바뀌면 0x5278ecd0 → 0x5278ec04가 불립니다. 색공간 descriptor의 +0x38과 +0x3c가 모두 0이라 행별 hook은 건너뛰고, 바이트 0의 값이 1이라 0x5278ecc4에서 표시 갱신 함수 0x5278e4ac로 들어갑니다.

사례 두 개에서 이 전체를 이어서 실행했습니다. 원본 등록 구간과 원본 클로저 관리 함수·설치 함수를 실행한 다음, 방향 이벤트를 넣어 원본 메뉴 콜백이 정확히 한 번 불리는 것을 확인했습니다. 이때 시험이 넣어 준 기록용 콜백은 불리지 않았습니다.

주의

표시 갱신 함수 0x5278e4ac는 이 시험에서 ‘지금 포커스 번호만 기록하는’ 대체 함수입니다. 명령을 읽어 보면 이 함수는 머리글 함수(0x52776a08)와 표시 여부 설정으로 이어지지만, 그 아래의 실제 그리기를 실행했다고 말할 수 없습니다. 등록 구간도 첫 번째 것만 실행했습니다. 같은 함수 안의 나머지 두 등록은 실행하지 않았습니다.

전환 애니메이션을 예약해도 포커스는 먼저 바뀝니다

끝을 넘지 않는 이동에서는 전환 상태를 기록하고 스케줄러에 등록을 요청합니다. 포커스 번호는 그 요청보다 먼저 바뀝니다. 끝을 넘어 순환할 때는 전환 없이 바로 옮깁니다.

시험 조건

스케줄러 등록·해제와 시계는 호출만 기록했습니다. 시간이 흘러 애니메이션이 한 단계씩 진행되는 호출은 한 번도 넣지 않았습니다. 시간 곡선, 실제 화면 프레임, 전환 상태 1은 이 시험의 범위 밖입니다.

조사 경과: 사례 수가 48개에서 50개가 된 이유

근거 JSON의 validation 항목은 처음 비공개로 점검한 48개 사례를 기록합니다. 그 뒤 ‘끝에서 멈춘 이벤트가 남은 전환을 건드리지 않는다’는 사례 두 개를 더했고, 공개 검증기와 결과 파일은 50개 기준입니다(public_replay 항목). 조정자가 독립적으로 다시 실행해 같은 결과를 얻었습니다.

한계와 남은 과제

  • 입력 — 이벤트 번호에 물리 버튼·다이얼·터치를 대응시키지 않았습니다. 이벤트를 만드는 하드웨어 쪽 코드는 추적하지 않았습니다.
  • 객체 — 메뉴·목록·행과 배치 값은 합성입니다. 행을 실제로 만들고 숨기는 코드, 실제 색공간 행의 가상 함수 표는 실행하지 않았습니다.
  • 실행하지 않은 분기 — 전환 상태 1, 행이 하나도 없는 목록, 자격 있는 행이 하나도 없는 목록.
  • 등록 — 콜백 등록은 첫 구간만 실행했습니다. 세 가지 동작 등록 전체나 창의 전체 수명은 아닙니다.
  • 그리기와 시간 — 그리기 무효화, 스케줄러, 시계는 경계에서 멈췄습니다. 완성된 화면과 애니메이션의 시간 진행은 확인하지 않았습니다.
  • 에뮬레이션 — Unicorn의 Cortex-A15 모델에서 실행했습니다. 카메라 CPU와 똑같이 동작한다는 보장으로 보지 않습니다.
  • 디컴파일 — angr가 만든 C 8개는 고치지 않고 보관했습니다. 조건부 명령이나 타입을 잘못 표현할 수 있어 ARM 명령과 실행 결과를 판단 기준으로 삼았습니다.

다음 과제는 물리 입력이 이 이벤트 번호로 바뀌는 경로를 찾는 것과, 표시 갱신 함수 아래의 글자·포커스 그리기를 잇는 것입니다. 세 기종의 같은 화면을 어떻게 맞출지는 UI 이식 설계에 정리했습니다.
