파일 시스템 인터페이스와 입력·출력 버퍼의 수명

업데이트 로더는 “파일을 열어 읽어라”는 요청을 어떤 객체에 보냅니다. 그 객체가 실제로 무엇이고 요청이 어디까지 내려가는지, 그리고 읽어 들인 파일과 풀어 낸 데이터가 메모리에 언제까지 함께 남는지를 확인했습니다.

이 문서에서

  1. 배경: 파일 요청이 내려가는 계층
  2. 파일 객체의 정체와 처리기 선택
  3. 압축된 입력과 풀린 출력이 함께 있는 구간
  4. 변환이나 체크섬이 실패했을 때 출력 버퍼의 처리
  5. 입력 버퍼의 정리와 해제 함수의 반환값
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 로더가 쓰는 파일 객체는 FileSystem 클래스의 객체입니다. 열기·닫기·읽기·정보 조회 요청은 경로의 첫 글자로 고른 volume에 따라 FAT, exFAT, Virtual 세 처리기 중 하나로 전달됩니다.
  • 처리기는 volume마다 붙은 설명 객체의 두 숫자로 고릅니다. 한 바이트가 4이면 Virtual, 아니면 32비트 값이 0x0403ffff보다 클 때 exFAT, 그 이하일 때 FAT입니다.
  • 압축된 입력 버퍼는 변환이 끝날 때까지 해제되지 않습니다. 그래서 입력과 출력이 같은 메모리 풀에 함께 잡혀 있는 구간이 있습니다. 원본 파일이면 그 시점의 요청 합계는 113,790,848바이트입니다.
  • 실패하는 위치에 따라 출력 버퍼의 처리가 다릅니다. 변환 실패나 길이 불일치는 출력 버퍼의 해제를 요청합니다. 안쪽 체크섬 실패는 출력 주소를 기록한 뒤에 일어나며, 그 함수 안에서는 해제하지 않습니다.
  • 파일 인터페이스 49건과 버퍼 수명 33건, 합계 82건을 원본 ARM 코드로 실행했습니다. 실제 파일·저장 장치·운영체제·변환 장치는 실행하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 객체 연결, 경로 첫 글자 검색, 처리기 선택 22건
  • 열기·읽기·정보 조회·닫기의 전달과 반환값 27건
  • 변환 실패 분기와 출력 인계 13건
  • 입력 정리와 풀 소속 검사 20건

정적 분석 코드를 읽어 판단

  • 클래스 이름(RTTI 문자열)과 가상 함수 표
  • 세 처리기의 하위 함수 연결
  • mount 경로가 처리기 배열을 채우고 지우는 위치
  • 입력 버퍼를 해제하는 호출이 변환 전에 없다는 점

모델 시험 조건으로 정한 것

  • volume 설명 객체의 숫자와 하위 파일 처리 함수
  • 변환 장치의 결과값과 작은 합성 출력
  • 할당·잠금·assert·운영체제 해제는 대체 함수
  • 바깥 체크섬은 생략 표식 0xffffffff로 통과

미확인 확인하지 않은 것

  • 실제로 어느 volume이 mount되어 있는지
  • FAT·exFAT 처리기 아래의 라이브러리와 드라이버
  • 풀린 출력 버퍼가 최종으로 해제되는 시점
  • 실패 뒤 검증이 반복 호출될 수 있는지

배경: 파일 요청이 내려가는 계층

입력 로더와 메모리 할당에서 로더는 “자원 관리 객체의 +0x38에 있는 객체”의 가상 함수를 불러 파일을 열고 읽었습니다. 그때는 이 객체의 정체를 몰랐습니다. 이 문서는 그 객체를 만든 코드를 찾아 클래스를 확인하고, 요청이 아래 계층으로 전달되는 조건을 따라갑니다.

이 문서에서 쓰는 말

volume
파일 시스템 하나가 차지하는 저장 영역입니다. 이 펌웨어는 C:, R:처럼 글자로 구분합니다. exFAT 규격은 volume을 “사용자 데이터를 저장하고 꺼내는 데 필요한 파일 시스템 구조와 데이터 공간 전체”로 정의합니다(Microsoft exFAT 규격).
FAT과 exFAT
메모리 카드에 널리 쓰이는 두 파일 시스템입니다. SD 규격은 2GB 초과 32GB 이하의 SDHC 카드에 FAT32를, 32GB를 넘는 SDXC 카드에 exFAT을 쓰도록 정합니다(SD Association의 용량 구분).
처리기(backend)
공통 창구 뒤에서 실제 일을 하는 객체입니다. 여기서는 FatFileSystem, ExFatFileSystem, VirtualFileSystem 세 가지입니다.
핸들
열린 파일 하나를 가리키는 값입니다. 읽기와 닫기는 이 값을 받아 동작합니다.
RTTI
C++ 컴파일러가 실행 파일에 남기는 클래스 이름 정보입니다. 가상 함수 표 바로 앞에 이름 문자열로 가는 포인터가 있습니다.

파일 객체의 정체와 처리기 선택

로더가 부르는 객체는 공장 객체가 만들어 연결한 FileSystem이고, 네 가지 요청은 volume마다 정해진 처리기로 전달됩니다.

객체가 만들어져 로더에 연결되는 과정

파일 시스템을 만드는 공장 객체(FileSystemFactory, 주소 0x54787088)의 초기화 함수가 0x30바이트짜리 객체를 할당해 FileSystem 생성자를 부르고, 그 주소를 공장 객체의 +0x14에 저장합니다. 자원 관리 객체는 이 값을 가져가 +0x38에 둡니다. 로더가 쓰던 바로 그 칸입니다.

클래스 이름은 진단 문자열로 짐작한 것이 아닙니다. 가상 함수 표 바로 앞의 포인터에서 RTTI, 이름 문자열로 따라가 확인했습니다. 시험에서는 가상 함수 표와 네 연결 칸을 일부러 틀린 값으로 채워 놓고 원본 코드가 올바른 값으로 덮어쓰는지 보았습니다. 공장 초기화 함수를 부르는 위쪽 호출자 한 단계는 파일 경로·volume·종료 처리에서 이었습니다.

처리기를 고르는 조건

  1. 경로의 첫 글자소문자는 대문자로 바꿔 비교
  2. volume 기록 찾기기록표의 글자와 비교해 번호와 설명 객체를 얻음. 없으면 −1
  3. 두 숫자로 선택바이트 +0x14, 32비트 값 +0x18
  4. 배열에 저장FileSystem +0x18의 해당 칸

글자 검색 함수 0x52f52554는 문자열이 비어 있지 않으면 첫 바이트만 읽습니다. volume 관리 객체가 가진 기록표에서 0x18바이트 간격의 기록마다 +4에 있는 글자와 비교합니다. 이 함수는 콜론이나 경로 전체의 문법을 보지 않으므로, 시험에 넣은 Cat도 C 기록과 일치했습니다.

주의

이 문서의 시험은 +0x14와 +0x18을 숫자 칸으로만 다뤘습니다. 용량의 단위, 매체의 종류, 실제 SD 카드와의 대응은 이 근거만으로 정하지 않았습니다. 클래스 이름이 아래쪽의 전송 방식이나 시스템 호출 구현을 증명하지도 않습니다.

참고: 경계값을 어떻게 읽을 수 있는가

매체 객체와 완료 통지는 SD 카드 쪽 설명 객체의 +0x18이 카드 정보에서 계산한 512바이트 sector 수임을 연결했습니다. 그 해석을 적용하면 경계 0x04040000 sector는 약 32.1GiB입니다. SD 규격이 FAT32를 쓰는 SDHC와 exFAT을 쓰는 SDXC를 나누는 32GB 부근입니다. 내장 저장소 쪽 설명 객체에서는 +0x18을 0이 아닌 값으로 만드는 코드를 찾지 못했으므로, 이 해석은 SD 경로에만 해당합니다.

핸들과 반환값이 전달되는 방식

  • 열기 — 처리기가 성공을 돌려주면 8바이트짜리 포장 구조체를 할당해 처리기의 핸들과 volume 번호를 적고, 그 구조체의 주소를 호출자에게 줍니다. 포장 구조체 할당이 실패하는 경우는 시험에서 실행하지 않았습니다.
  • 읽기·닫기 — 포장 구조체의 +4(volume 번호)로 처리기를 고르고 +0(처리기의 핸들)을 넘깁니다. 읽기는 버퍼와 크기를 그대로 전달합니다.
  • 잘못된 입력 — 핸들이 없거나, 번호가 음수이거나, 처리기가 없으면 아래로 내려가지 않고 반환값 0과 오류 번호 12를 냅니다. 정보 조회에서 경로가 맞지 않으면 반환값 0과 오류 번호 2입니다.
  • 닫기의 정리 — 처리기가 실패를 돌려줘도 포장 구조체를 해제하는 함수는 호출합니다.
  • 열린 파일 수 — 열기가 성공하면 늘리고 닫기가 성공하면 줄이는 계수도 이 계층에 있습니다.

열기와 닫기는 0이 아닌 값을 모두 1로 바꾸고, 읽기와 정보 조회는 32비트 값을 그대로 돌려줍니다. 이 차이는 합성 반환값 네 가지로 확인한 것이며, 처리기가 실제로 어떤 값을 돌려주는지는 실행하지 않았습니다. 정보 조회에서 합성 콜백이 파일 정보 구조체(FileInfo)의 +0x18에 쓴 크기는 호출자가 읽을 때까지 유지됐습니다.

이 계층의 읽기와 정보 조회는 안쪽 잠금 함수의 반환값을 분기 조건으로 쓰지 않습니다. 잠금 함수가 0을 돌려준 시험에서도 처리기 호출과 잠금 해제가 일어났습니다. 로더 쪽의 잠금 검사는 별개이며, 이 관찰을 실제 동시성 오류나 잠금 정책이 없다는 뜻으로 넓히지 않습니다.

시험 조건

파일 인터페이스 49건은 객체 연결 4건, 첫 글자 검색 10건, 처리기 분기 8건, 열기 반환값 4건과 잘못된 경로 1건, 읽기 7건과 잘못된 입력 3건, 정보 조회 7건과 잘못된 경로 1건, 닫기 4건입니다. 공장 초기화는 함수 전체가 아니라 0x52f51644–0x52f516d8 조각을 합성 레지스터와 스택으로 실행했습니다. 대체한 것은 처리기 콜백, 할당, 잠금, assert, 핸들 기록과 해제, 문자열 길이 함수, FileSystem 초기화 경계입니다. 수천만 바이트를 실제로 할당하거나 읽지 않았고, CPU는 Unicorn의 Cortex-A15 모델입니다.

압축된 입력과 풀린 출력이 함께 있는 구간

입력 버퍼는 검증과 변환이 진행되는 동안 계속 잡혀 있고, 그 사이에 출력 버퍼가 따로 할당됩니다. 두 버퍼는 같은 IMAGE1 풀에 함께 존재합니다.

종류 2의 검증 진입 함수 0x52fefb84는 상태 객체에 있던 입력 주소와 길이를 패키지 문맥으로 넘기고, 그 값은 다시 검증 객체로 전달됩니다. 검증 객체는 헤더·종류·바깥 체크섬을 확인한 뒤 변환 함수 0x52ff4f88에서 출력 버퍼를 따로 할당하고, 입력의 +0x80 주소(압축된 본문의 시작)를 변환 장치에 넘깁니다. 이 구간에는 입력 버퍼를 해제하는 호출이 없습니다.

  1. 입력 유지상태 +0x48 → 패키지 문맥 +0x1c → 검증 객체 +8
  2. 출력 할당같은 IMAGE1 풀, footer +0x10의 길이
  3. 검증 뒤 인계검증 객체 +0x10·+0x14 → 패키지 문맥 +0x24·+0x28 → CPU 문맥 +0x24·+0x28

입력 로더와 메모리 할당에서 구한 요청 합계를 이제 두 버퍼가 함께 있는 시점과 연결할 수 있습니다.

시험 조건

공개한 연결 시험은 바깥 체크섬 자리에 생략 표식 0xffffffff를 넣어 실제 합계 비교를 건너뜁니다. 실제 바깥 합계가 맞는 경우와 틀린 경우 2건은 공개 도구에 넣지 않은 별도 검토에서 확인했습니다. 변환 장치는 정해 준 결과값과 작은 합성 출력으로 대체했습니다.

변환이나 체크섬이 실패했을 때 출력 버퍼의 처리

변환 함수는 실패 위치에 따라 출력 버퍼를 해제하기도 하고 그대로 두기도 합니다. 반환값이 0이라는 것만으로 출력 버퍼가 회수됐다고 볼 수 없습니다.

실패했을 때 기존 값이 유지되는지는 필드에 표식 값을 넣어 두고 원본 코드를 실행해 확인했습니다. 안쪽 체크섬 실패는 출력 주소를 기록한 다음에 일어납니다. 그 뒤 전체 상태 전환이나 재부팅에서 회수되는지, 검증이 실제로 반복 호출될 수 있는지는 확인하지 못했습니다. 그래서 이것을 메모리 누수로 단정하지 않습니다.

성공 경로에서는 풀린 출력이 패키지 문맥과 CPU 문맥으로 전달됩니다. 그다음 하위 구획 7을 찾지 못하면 상위 함수는 0을 돌려주지만 이미 전달한 주소는 그대로 남습니다. 하위 구획을 검증하는 함수 두 개는 합성 반환값으로 대체했으며, 딸린 펌웨어나 장치의 실제 검증은 수행하지 않았습니다.

이 절의 13건은 변환 분기 7건(정상, 변환 실패, 길이 부족, 길이 초과, 체크섬 실패, 생략 표식 0과 0xffffffff), 할당 실패 1건, 종류 2 연결 5건(정상, 프로젝트 값 불일치, footer 종류 불일치, 구획 7 없음, 안쪽 체크섬 실패)입니다.

입력 정리 함수는 해제 요청 함수의 반환값에 따라 뒤따르는 초기화를 할지 정합니다. 그런데 그 반환값은 풀이 실제로 해제에 성공했는지가 아니라 잠금을 얻었는지를 나타냅니다.

IMAGE1 풀의 소속 검사와 해제

소속 검사 함수 0x530efb60은 부호 없는 수로 기준 ≤ 주소 < 기준 + 크기인지 봅니다. IMAGE1의 기준 0x6e500000과 크기 0x31affff0을 넣으면 끝 경계는 0x9ffffff0이고 그 주소 자체는 포함되지 않습니다. 풀 설정 영역의 끝 0xa0000000과는 다른 값입니다. 마지막 16바이트는 이 소프트웨어 검사의 범위 밖에 있습니다. 이 사실은 물리 DRAM의 배치나 실제 여유 공간을 알려 주지 않습니다.

해제 함수 0x530efee8은 정렬된 주소의 8바이트 앞에 적어 둔 값을 읽고, 그 값이 풀에 속하는지 확인한 뒤 그 칸을 0으로 지웁니다. 읽은 값에서 0x18을 빼 운영체제가 처음 준 주소를 되찾고, 운영체제의 해제 호출 0x525b75e0에 풀 번호와 함께 넘깁니다. 운영체제가 0을 돌려주면 해제 함수는 1을 돌려줍니다. 시험에서는 운영체제 호출을 대체 함수로 바꿨으므로 실제로 메모리가 반환됐다는 증명은 아닙니다.

지금까지 확인한 설정 함수와 정리 구간은 검증 객체의 출력 칸과 상위 문맥의 출력 칸을 지우지 않습니다. 풀린 출력 버퍼가 최종으로 회수되는 시점은 업데이트 종료 과정 전체를 따라가야 정할 수 있습니다.

한계와 남은 과제

  • 82건은 모두 합성 입력으로 원본 ARM 코드를 실행한 것입니다. 두 도구는 RTOS 단독 이미지와 통합 이미지에서 같은 결과를 냈습니다. 실제 장치·저장소·운영체제·변환 장치는 실행하지 않았습니다.
  • 공장 초기화를 부르는 가장 위쪽의 작업·시작 코드와 실제 mount 상태는 확인하지 못했습니다.
  • 설명 객체 두 숫자의 단위는 이 문서의 근거만으로 정하지 못했습니다. SD 경로의 +0x18은 매체 객체와 완료 통지에서, 업데이트 파일 이름이 어느 volume으로 이어지는지는 파일 경로·volume·종료 처리에서 이어서 다룹니다.
  • FAT·exFAT 처리기 아래의 드라이버, 풀린 출력의 최종 회수 시점, 검증이 반복 호출되는 조건이 남아 있습니다.
  • 디컴파일한 C 17개(파일 인터페이스 8개, 버퍼 수명 9개)와 원본 ARM 2,422개 단어의 주소·해시를 따로 보관했습니다. 디컴파일 결과는 자동 출력 그대로이며 조건과 주소는 ARM 명령을 기준으로 삼았습니다. 공개 자료에는 바이너리와 의사코드 본문 대신 분석과 검사 도구만 있습니다.
  • 이 결과는 파일 입력 경로와 메모리 수명의 범위를 좁혀 줍니다. 카메라가 수정 펌웨어를 받아들이거나 정상 실행한다는 근거로 쓸 수 없습니다.
