sRGB 글자가 화면 가장자리에 걸릴 때의 전송

글자 일부가 화면 밖으로 나가면 펌웨어가 어느 픽셀을 읽고 어디에 쓰는지 알아봤습니다. 다른 기종으로 화면을 옮길 때 가장자리에서 픽셀이 한 칸이라도 어긋나지 않게 하려면 이 규칙이 필요합니다.

  3. 일곱 위치 모두 독립 계산과 같았습니다
  4. Q7은 같은 왼쪽 위 입력에서 첫 행 여덟 픽셀을 건너뜁니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • K-3 III의 회전 없는 글자 전송은 먼저 글자 사각형과 그릴 수 있는 범위(viewport)의 겹치는 부분을 구하고 그 안의 칸만 읽고 씁니다.
  • 76×40 sRGB 비트맵을 일곱 위치에 놓고 원본 코드를 실행했습니다. 비트맵 읽기 순서, 4바이트 쓰기의 위치·값·순서, 256×144 프레임 전체가 일곱 경우 모두 독립 계산과 같았습니다.
  • 섞을 배경색은 겹친 영역 왼쪽 위의 표면 워드 하나입니다. 겹친 높이가 0인 경우에도 이 워드는 읽었습니다.
  • 기준 위치는 원본 코드가 만든 좌표이고 나머지 여섯 위치는 시험이 좌표를 바꿔 넣은 것입니다. 실제 메뉴가 이런 좌표를 만드는지, LCD에 어떻게 보이는지는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 부호 있는 사각형 교차와 읽기 시작점 계산
  • 일곱 위치의 읽기 순서, 쓰기, 프레임 전체
  • 최종 전송 구간에 모형 호출 0개

모델 시험 조건으로 정한 것

  • 여섯 위치의 텍스트 사각형과 viewport
  • 256×144 합성 RAM 프레임
  • 행·글꼴·팔레트 준비 단계의 모형 호출 72개

미확인 확인하지 않은 것

  • 실제 UI의 viewport 생산자와 음수 좌표 발생 여부
  • 회전 모드, 값 0xff인 칸의 단색 경로
  • LCD 출력과 화면 이식

배경: 화면 밖 픽셀은 쓰기 전에 잘라 냅니다

글자를 그릴 위치가 화면 가장자리에 걸리면 비트맵 일부는 표면 바깥을 가리킵니다. 그대로 쓰면 표면 앞뒤의 다른 메모리를 덮어씁니다. 그래서 그리기 코드는 쓰기 전에 그릴 범위를 잘라 냅니다. 이 처리를 클리핑이라고 합니다. 이 사이트의 용어집 ‘클리핑’은 값의 범위를 자르는 뜻이고 여기서는 사각형 영역을 자르는 뜻입니다.

K-3 III는 글자 사각형과 viewport 두 사각형을 교차시켜 겹친 사각형만 남깁니다. 겹친 사각형의 위치에서 두 가지 시작점이 정해집니다. 하나는 비트맵의 몇 번째 바이트부터 읽을지, 다른 하나는 표면의 몇 번째 워드부터 쓸지입니다. 비트맵 한 줄은 76바이트, 표면 한 줄은 256워드(stride)입니다.

교차 영역이 읽기와 쓰기의 시작점을 정합니다

원본 전송은 교차 → 시작점 계산 → 배경 워드 한 개 읽기 → 줄 단위 순회의 네 단계로 진행합니다.

  1. 사각형 교차 부호 있는 교차 함수가 시작 좌표는 큰 쪽, 끝 좌표는 작은 쪽을 고릅니다. 두 끝이 맞닿기만 해도 교차 상태는 1입니다.
  2. 시작점 계산 비트맵의 시작 바이트는 (clipY−textY)×76 + clipX−textX입니다. 이 시험의 추가 X 오프셋은 0입니다. 표면의 시작 워드는 clipY×256 + clipX로 계산합니다.
  3. 배경 워드 읽기 교차 영역의 첫 대상 워드 하나를 읽습니다. 부분 커버리지 칸은 모두 이 워드를 배경으로 섞고 칸마다 기존 색을 다시 읽지 않습니다.
  4. 줄 단위 순회 비트맵을 줄 순서로 읽고 0이 아닌 칸에만 4바이트 워드를 씁니다. 값 0xff인 칸의 단색 경로도 있지만 시험한 sRGB 비트맵에는 그런 칸이 없었습니다.

사각형 좌표는 원본 래스터가 끝난 뒤 호출자 스택에 있는 값을 바꿔서 공급했습니다. 대상 행 간격은 256워드, 소스 행 간격은 76바이트입니다.

일곱 위치 모두 독립 계산과 같았습니다

일곱 위치에서 읽기 순서, 쓰기 위치·값·순서, 최종 프레임 147,456바이트가 모두 독립 계산과 일치했습니다.

기준 위치는 원본 StringView가 만든 좌표와 뷰 클립을 그대로 썼습니다. 나머지 여섯 위치는 원본 비트맵이 만들어진 뒤 전송 진입 때 복사된 64바이트 설정에서 텍스트 사각형과 viewport만 바꿨습니다. 크기, 팔레트, 소스 X 오프셋, 나머지 설정 바이트, 원래 StringView 객체는 그대로 두었고 대상도 같은 256×144 합성 RAM 프레임입니다.

경계 접촉 사례의 교차 상태는 1입니다. 높이가 0이라 비트맵 읽기와 대상 쓰기는 없었습니다. 그래도 원본은 높이를 검사하기 전에 대상 시작 워드 하나를 읽고 혼합 캐시를 준비했고 프레임은 바뀌지 않았습니다. 이 결과는 시험용 viewport가 표면 안에 있는 조건에서만 성립합니다.

독립 스칼라 계산은 원본 비트맵의 3,040칸을 모두 방문하면서 각 대상점이 viewport 안인지 검사합니다. 부분 커버리지의 값은 원본 가중치와 배경 워드 한 개로 계산했습니다. 프레임 앞뒤 64바이트와 기존 할당 보호값도 그대로였습니다. 기준 사례의 전체 실행 해시는 기준 전송의 원본과 계산에 기록한 sRGB 재현과 같습니다.

Q7은 같은 왼쪽 위 입력에서 첫 행 여덟 픽셀을 건너뜁니다

K-3 III는 교차 영역만 계산하고 Q7은 글리프 행의 시작 주소를 먼저 검사합니다. 같은 (−9, −12) 입력에서 이 순서 차이가 첫 행에 드러납니다.

K-3 III의 비트맵에서는 Q7이 건너뛴 여덟 위치에 해당하는 칸이 원래 비어 있습니다. 그래서 두 결과가 보여 주는 차이는 첫 행을 처리하는 순서입니다. 두 기종의 텍스트 전송 기준은 기종 간 텍스트 전송의 기준에서 비교합니다.

각 사례의 행·글꼴·팔레트 준비에는 기존 모형 호출 72개가 들어 있습니다. 0x528c2560에서 재개한 최종 전송은 원본 assertion까지 실행했고 모형 호출은 0개입니다.

한계와 남은 과제

  • 여섯 위치의 좌표와 viewport는 시험이 넣은 값입니다. 두 사각형을 실제로 만드는 상위 경로는 텍스트 viewport의 생산 경로에서 원본 코드와 대조했습니다.
  • viewport가 표면 밖으로 나가는 경우는 시험하지 않았습니다.
  • 회전 모드, 값 0xff인 칸의 단색 경로, LCD 출력과 화면 이식은 확인하지 않았습니다.

재현 방법

실행 환경은 Python과 Unicorn 2.1.4, 입력은 고정된 decoded 파일입니다. 검증기는 보조 소스와 전체 공개 기록의 SHA-256을 확인한 뒤 실행합니다. 기본으로는 일곱 사례를 모두 비교합니다. --case를 주면 한 사례만 실행해 그 사례의 전체 실행 해시와 공통 메타데이터를 고정 기록과 비교합니다. 출력에는 새 파일 이름을 씁니다.

python -B tools/verify_colorspace_clip.py decoded.bin --output clip-all.json
python -B tools/verify_colorspace_clip.py decoded.bin --case upper_left --output clip-corner.json
python -B -m unittest discover -s tests -p test_colorspace_clip.py
