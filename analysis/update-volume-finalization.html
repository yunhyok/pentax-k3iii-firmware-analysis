펌웨어 업데이트 과정 · 파일 위치와 끝맺음

업데이트 파일의 경로, volume 기록, 종료 처리

업데이트의 맨 앞과 맨 뒤를 다룹니다. 카메라가 찾는 파일의 이름과 위치가 어떻게 정해지는지, 그리고 실행이 끝났을 때 입력 버퍼를 정리하고 완료를 알리는 순서를 확인했습니다.

이 문서에서

  1. 배경: 파일을 찾는 곳과 끝내는 곳
  2. 종류 2는 C: 쪽 파일 이름만 조회합니다
  3. 구성 요소 5의 입력 설정은 기존 값을 지우지 않을 수 있습니다
  4. 종료 함수의 해제 요청과 완료 통지
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 업데이트 파일 이름은 형식 문자열 C:\FWDC%ldB.BIN으로 만들어집니다. 본체 펌웨어를 뜻하는 종류 2는 이 C: 쪽 이름만 조회하며 R: 쪽 이름으로 바꿔 찾는 분기가 없습니다.
  • drive 글자는 volume 기록표에서 찾습니다. 기록표는 12칸이고 C, D, X, Y, A, B, E, F, G, H, R, W 순서로 등록됩니다. C는 0번 기록, R은 10번 기록입니다.
  • 종료 함수는 실행 결과와 관계없이 입력 버퍼의 해제를 요청하고 결과가 0이 아닐 때만 완료 메시지를 보냅니다. 해제 요청이 성공했는지는 통지를 보낼지 말지에 쓰이지 않습니다.
  • 정정: 구성 요소 5의 입력 설정 함수는 (0, 0)을 받으면 기존 값을 지우지 않습니다. “모든 구성 요소의 입력 정보를 0으로 만든다”는 이전 설명은 정확하지 않았습니다.
  • 파일 이름·volume 19건과 종료 처리 26건, 합계 45건을 원본 ARM 코드로 실행했습니다. 실제 파일 접근, 메모리 해제, 업데이트 실행은 하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 공장 초기화가 volume 12개를 등록하는 순서
  • 이름 버퍼에서 기록 번호·제공자 번호까지의 연결
  • 종료 함수와 실행 감싸기 함수의 호출 순서, 반환값
  • 구성 요소 5가 값을 유지하거나 바꾸는 조건

정적 분석 코드를 읽어 판단

  • 종류 0·1·3·4의 추가 준비 경로
  • CheckUpdateFirmware 수신부가 입력 정리를 부르는 분기
  • 공장 초기화를 부르는 BuildPackage의 간접 호출

모델 시험 조건으로 정한 것

  • 파일 이름에 들어가는 숫자(0, 9,067, 2,147,483,647)
  • 문자열 형식 함수, 할당, 공장의 조회·설정 함수는 대체
  • 해제 요청·업데이트 실행·통지는 값만 돌려주는 대체 함수

미확인 확인하지 않은 것

  • 카메라가 실행 중에 파일 이름에 넣는 실제 숫자
  • R: 쪽 이름을 고르는 다른 경로의 조건
  • 공장 초기화보다 위쪽의 작업·시작 코드
  • 풀린 출력 버퍼가 최종으로 회수되는 시점

배경: 파일을 찾는 곳과 끝내는 곳

Ricoh의 안내에 따르면 사용자는 펌웨어 파일을 SD 카드의 최상위 폴더에 복사해 슬롯 1에 넣고 업데이트를 시작합니다(Ricoh 공식 안내). 카메라 쪽에서는 “어느 drive의 어떤 이름을 찾을지”를 정하는 코드가 있어야 합니다. 이 문서의 앞 절반은 그 이름이 만들어져 volume으로 이어지는 과정을 다룹니다.

뒤 절반은 업데이트 실행이 끝난 직후를 다룹니다. 파일 인터페이스와 버퍼 수명에서 본 입력 버퍼 해제 요청이 실제로 어디서 불리는지, 완료를 알리는 메시지는 언제 나가는지입니다. 메시지를 받는 쪽은 매체 객체와 완료 통지로 이어집니다.

이 문서에서 쓰는 말

drive 글자 하나와 그 저장 영역을 설명하는 객체를 짝지어 둔 표의 한 칸입니다. 한 칸은 0x18바이트입니다.
설명 객체

종류 2는 C: 쪽 파일 이름만 조회합니다

이름 생성 함수는 C:와 R: 두 벌의 이름을 만들지만 종류 2 분기는 C: 쪽만 파일 크기 조회에 넘깁니다. 이름의 첫 글자가 volume 기록표에서 0번 기록을 고릅니다.

이름 버퍼 두 개

이름 생성 함수 0x52ff32ac는 숫자 하나를 읽어 형식 문자열 두 개에 넣습니다. 숫자는 함수 0x5310b748이 전역 포인터 0x547bb198이 가리키는 객체의 +0x18에서 읽습니다.

종류를 고르는 함수 0x52fef240의 종류 2 분기는 C: 쪽 조회 함수가 돌려준 이름을 파일 크기 조회에 넘깁니다. 크기가 0이 아니면 상태 객체에 종류·경로·길이를 적고 0이면 그 세 칸을 이전 값 그대로 둡니다. 이 분기에는 R: 쪽으로 바꿔 찾는 코드가 없습니다. R: 쪽 조회 함수를 고르는 다른 경로가 어떤 조건에서 쓰이는지는 정하지 않았습니다.

참고: 배포 파일 이름과의 관계

Ricoh가 배포하는 파일 이름 fwdc233b.bin은 이 형식에 숫자 233을 넣은 것과 대소문자만 다릅니다. 카메라가 실행 중에 이 칸에서 어떤 숫자를 읽는지, 파일 시스템이 이름의 대소문자를 어떻게 비교하는지는 확인하지 않았습니다. C:가 SD 슬롯 1이라는 대응도 이 문서의 근거로는 정하지 않았습니다. C: 뒤의 객체가 SD 카드 드라이버 클래스라는 점은 매체 객체와 완료 통지에서 확인했습니다.

시험 조건

문자열 형식 함수는 원본 라이브러리 대신 틀·길이 제한·숫자 인수를 받아 문자열을 만드는 대체 함수였습니다. 숫자는 0, 9,067, 2,147,483,647을 넣었고 만들어진 이름을 원본 경로 검색 함수에 넘겨 기록 번호를 확인했습니다. 크기 조회는 0과 35,136,788을 돌려주는 두 경우로 실행했습니다.

volume 기록표: 용량 12칸과 등록 순서

공장 초기화 함수는 volume 관리 객체를 만들 때 용량 12를 넘깁니다. 생성자 0x52f52334는 8 + 0x18 × 12바이트(296바이트)를 요청합니다. 그리고 배열 시작에서 8바이트 뒤의 주소를 관리 객체 +0x14에, 용량을 +0x20에 저장합니다. 따라서 +0x20은 등록된 기록의 수가 아니라 검색할 배열의 용량입니다.

등록 함수 0x52f524b8는 첫 칸(설명 객체 포인터)이 비어 있는 첫 기록을 찾아, 설명 객체를 기록 +0에, 넘겨받은 문자열의 첫 글자를 +4에 씁니다. 용량 값은 늘리지 않습니다. 빈 기록이 없으면 아무것도 쓰지 않고 0을 돌려줍니다.

구성 요소 5의 입력 설정은 기존 값을 지우지 않을 수 있습니다

구성 요소 5의 설정 함수는 주소와 길이가 둘 다 0이 아닐 때만 자기 칸을 바꿉니다. 입력 정리가 넘기는 (0, 0)으로는 기존 값이 그대로 남습니다.

정정

입력 정리 함수 0x52feec18은 0x52feecc0에서 이 설정 함수에 (0, 0)을 넘깁니다. 처음 상태의 슬롯 1 조건에서는 구성 요소 5의 기존 입력 칸이 그대로 남습니다. 따라서 “모든 구성 요소의 입력 정보를 0으로 만든다”는 이전 설명은 정확하지 않았습니다. 설정 함수를 부르는 것과 칸이 실제로 지워지는 것을 구분해야 합니다. 관련 근거 파일 startup-storage-evidence.json의 서술도 이에 맞게 고쳐져 있습니다.

설정 함수 0x52ff31c4는 리소스 슬롯 1(이름 M0A7CommunicationBuffer)의 기준 주소를 조회합니다. 조회 함수 0x52ff8de4는 기준 주소가 0xffffffff가 아니면 그 값을 그대로 돌려줍니다. 슬롯 1의 처음 값은 기준 0x509df000, 길이 0x100000입니다.

복사하는 분기에서 함수가 돌려주는 값은 복사 함수의 반환값입니다. 저장한 기준 주소와 항상 같다고 일반화할 수 없습니다. 실제 메모리 배치, 슬롯 값이 나중에 바뀌는 경우, 기준 주소가 0xffffffff일 때의 지연 할당은 이번 시험 범위 밖입니다.

슬롯 1의 처음 값이 놓인 위치

RTOS는 시작할 때 초기값 영역을 ROM에서 RAM으로 복사합니다. 복사 설명 0x52500450은 ROM 0x53ce7d40을 RAM 0x54500000으로 0x65a80바이트 대응시킵니다. 이 관계에서 슬롯 1의 ROM 기록 0x53d0d2c8은 RAM 0x54525588에 해당합니다. 기록의 네 단어는 이름 포인터 0x53912b84, 길이 0x100000, 기준 0x509df000, 표식 포인터 0입니다. 기록 16바이트의 SHA-256은 455b916505517d2a4b958dc73431a939b0d4dd7ebebb7dd8f96a1b407e91545f입니다.

종료 함수의 해제 요청과 완료 통지

종료 함수는 먼저 입력 버퍼의 해제를 요청하고 실행 결과가 0이 아니면 완료 메시지를 보냅니다. 해제 요청의 반환값은 통지 여부를 정하는 데 쓰이지 않습니다.

  • 종료 함수는 결과가 0이든 아니든 상태 +0x48의 값을 해제 요청 함수에 넘깁니다. 입력 주소가 없는 합성 사례에서도 호출을 생략하지 않았습니다.
  • 해제 요청 함수는 잠금 결과를 돌려주며 주소가 없으면 풀의 해제 호출을 건너뜁니다(입력 정리와 해제 함수의 반환값). 시험에 넣은 반환값 0xffffffff는 호출자가 그 값을 어떻게 전달하는지 보려는 것이며 실제 해제의 성공·실패 값으로 읽으면 안 됩니다.
  • 종료 함수 안에는 상태 +0x48(입력 주소)이나 +0x44(길이)를 지우는 명령이 없습니다.
  • 완료 통지 함수는 메시지 0x2640820b를 보내고 아래 경계에 0x20을 넘긴 뒤 마지막 호출로 넘어갑니다. 결과가 0이 아닐 때 종료 함수의 반환값은 이 마지막 통지 경계의 반환값입니다.

한계와 남은 과제

  • 파일 이름·volume 19건과 종료 처리 26건, 합계 45건이 RTOS 단독 이미지와 통합 이미지에서 같은 결과를 냈습니다. 종료 처리 26건에는 다른 검토자가 추가한 경계 사례 6건이 들어 있습니다. 이 6건을 합계에 따로 더하지 않았습니다.
  • 19건은 공장 등록 순서 1건, 이름에서 기록까지 6건, 종류 2의 크기 조건 2건, 이름에서 처리기 조건까지 8건, 등록 함수 2건(빈 칸 찾기, 가득 찬 표)입니다. 26건은 구성 요소 5의 5건과 반환값 1건, 종료 함수 4건과 주소 없는 경우 2건, 감싸기 함수 6건과 결과 2를 넣은 2건, 조회용 함수 5건과 반환값 전달 1건입니다.
  • 디컴파일한 C 12개와 원본 ARM 1,622개 단어의 주소·해시를 따로 보관했습니다. 구성 요소 5의 C에는 조건 코드 표현이 풀리지 않은 채 남아 있고 종료 함수의 C에는 성공 분기의 마지막 호출이 빠져 있습니다. C는 고치지 않고 두었으며 조건과 반환 관계는 원본 ARM 명령과 실행 결과로 판정했습니다.
  • 실제 파일 접근, 큰 메모리 할당, 운영체제의 해제, 업데이트 실행, 물리 매체, 카메라는 실행하지 않았습니다. 이 결과는 수정 펌웨어를 카메라가 받아들이거나 정상 실행한다는 것을 보여 주지 않습니다.
  • 이어지는 조사: 설명 객체를 만드는 코드와 크기의 단위, 완료 통지를 받는 쪽은 매체 객체와 완료 통지에서 다룹니다. mount와 처리기 초기화의 실행 시점, 풀린 출력 버퍼의 최종 회수 시점은 아직 남아 있습니다.
