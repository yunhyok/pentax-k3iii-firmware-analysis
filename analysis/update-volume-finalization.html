업데이트 파일 경로와 종료 처리

종류 2 업데이트가 사용하는 C 파일명 버퍼를 volume record까지 연결했다. 종료 함수가 입력 해제와 완료 통지를 처리하는 순서도 확인했다. component 5의 reset 호출은 기존 필드를 지우지 않는 조건이 있어 앞선 설명을 바로잡았다.

종류 2는 C 파일명 버퍼를 사용한다

생성자 0x52ff32ac는 0x5310b748이 읽은 값 [0x547bb198]→u32+0x18을 파일명 형식 문자열에 전달한다. 0x52ff3394의 대상은 0x54796104와 C:\FWDC%ldB.BIN, 0x52ff33b0의 대상은 0x54796140과 R:\FWDC%ldB.BIN이다. 두 formatting 호출의 길이 인자는 0x14다. 생성자·문자열·getter 근거

kind 2 분기는 C getter의 반환값을 크기 조회 함수 0x52ff7d10에 넘긴다. 크기가 비제로일 때 state의 종류·경로·길이를 기록하고 0이면 기존 세 필드를 유지한다. 이 분기에는 R fallback이 없다. R getter 0x52ff34d0를 선택하는 다른 경로의 정책은 이번 범위에서 확정하지 않았다. 숫자 getter의 카메라 런타임 값과 원본 libc formatting은 검사하지 않았으며 합성 숫자·formatting 결과를 원본 경로 검색기에 전달했다. 파일명·선택 검사

배열 용량과 record 생산자

factory는 생성자 0x52f52334에 용량 12를 전달한다. 생성자는 8 + 0x18×12바이트를 요청하고 배열 시작+8을 manager+0x14에, 용량을 +0x20에 저장한다. 따라서 +0x20은 등록된 record 수가 아니라 검색할 배열 용량이다. 등록 함수 0x52f524b8는 record+0의 descriptor 포인터가 NULL인 첫 자리를 찾아 descriptor를 record+0에, 입력 문자열의 첫 문자를 record+4에 쓴다. 용량은 증가시키지 않는다. 배열 생성·등록의 실제 쓰기 주소

등록 순서는 원본 factory의 진입점부터 backend 생성 직전까지 실행해 확인했다. 문자열 표에는 J도 있지만 이 루프는 J를 등록하지 않았다. provider getter 0x5327f710은 [provider+4+4×index]를 반환한다. 여기까지의 연결만으로 C/R을 물리 매체로 명명하지 않으며 descriptor 생성자와 후속 기록자는 별도 조사 대상이다. factory의 query/config helper를 합성 함수로 대체했으므로 record의 모든 필드가 실제 카메라와 같다는 뜻도 아니다. 여기서 record+4는 파일시스템 volume의 문자 필드이며 기존에 추적하던 FwPartition bank record+4와는 별개다.

상위 FileFactory::BuildPackage의 0x52f3f350은 singleton의 vslot+8을 호출한다. vptr 0x539014c0이 유지된 조건에서 ROM slot 0x539014c8의 대상은 factory 초기화 함수 0x52f510e8이다. 실제 호출 본문 한 단계를 추가로 연결했으며 그 위 task/startup 진입은 미확정이다. 조건부 간접 호출 연결

component 5의 reset은 필드를 지우지 않을 수 있다

0x52ff31c4는 리소스 슬롯 1을 조회한다. 초기 복사 descriptor 0x52500450은 ROM 0x53ce7d40에서 RAM 0x54500000으로 0x65a80바이트를 대응시킨다. 이 관계에서 slot 1의 ROM record 0x53d0d2c8은 RAM 0x54525588에 해당한다. 초기 길이는 0x100000, base는 0x509df000, 이름은 M0A7CommunicationBuffer다. 초기 record·주소 대응·해시

getter 0x52ff8de4는 base가 0xffffffff가 아니면 그대로 반환한다. component 5는 입력 포인터가 0이거나 길이가 0이면 기존 +0x0c/+0x10 필드를 유지한다. 둘 다 비제로일 때만 copy helper를 호출한 뒤 slot base와 길이를 저장한다. copy 분기의 반환값은 helper의 반환값이며 저장한 base와 항상 같다고 일반화할 수 없다. 실제 메모리 배치와 slot의 후속 변경, sentinel에서의 지연 할당은 이번 CPU 검사 범위 밖이다.

앞선 입력 정리 함수 0x52feec18은 0x52feecc0에서 이 setter에 (0, 0)을 전달한다. 초기 slot 1 조건에서는 component 5의 기존 입력 필드가 그대로 남는다. 따라서 “모든 component 입력 descriptor를 0으로 만든다”는 기존 설명은 정확하지 않다. setter 호출과 실제 필드 삭제를 구분하도록 기존 메시지·저장소 근거를 수정했다.

종료 함수의 해제 요청과 통지 순서

0x52feffa8(state, result)는 result가 0인지와 관계없이 state+0x48에 든 포인터를 0x52ff622c에 넘긴다. 입력이 null인 합성 사례에서도 호출은 생략되지 않았다. 앞선 wrapper 분석에서 0x52ff622c는 mutex 획득 결과를 r6에 보존하고 반환하며 입력이 null이면 하위 pool 해제 호출을 건너뛰는 것을 확인했다. 따라서 합성 반환값 0xffffffff는 호출자의 반환 전달 검사에만 쓰이며 실제 하위 해제의 성공·실패 값으로 해석하지 않는다. 이 종료 함수 자체에는 state+0x48이나 길이 +0x44를 지우는 명령이 없다. 종료 함수의 원본 명령 근거

비제로 분기는 해제 wrapper 0x52ff622c의 반환값을 분기 조건으로 쓰지 않는다. 통지 함수는 메시지 0x2640820b를 전달하고 하위 경계에 0x20을 넘긴 뒤 마지막 호출로 이동한다. 해제 요청 실패 여부와 통지 발생을 구분해야 한다. 합성 실행에서는 실제 큐·이벤트·저장소 동작을 대체했으며 이 통지가 물리적인 업데이트 완료를 보장한다는 뜻은 아니다. 해제 반환값·null 입력·비제로 결과 검사

상위 실행 wrapper와 조회 helper는 정리 경로가 다르다

0x52ff0044의 종류 2·6·7은 executor 0x52fefe98를 호출한 뒤 그 결과를 종료 함수에 전달한다. wrapper는 종료 함수의 반환값 대신 executor의 원래 32비트 값을 반환한다. 종류 5는 executor로 직접 tail call하며 이 wrapper의 종료 함수를 거치지 않는다. 범위 밖인 종류 8은 result=0으로 종료 함수를 호출하고 0을 반환한다. 종류 0·1·3·4의 추가 준비 경로는 정적으로만 확인했다.

별도 조회 helper 0x533031a0의 순서는 preflight → load → validation → postvalidation이다. 각 단계가 0을 반환하면 오류 byte에 차례로 0·3·1·3을 쓴다. 모두 비제로이면 호출자의 기존 오류 byte를 유지하고 마지막 postvalidation의 반환값을 그대로 전달한다. 이 helper 안에는 입력 해제 호출이 없다. 상위 호출자의 정리와 오류 보고를 더 따라가야 하며 이 사실만으로 누수나 중복 해제를 단정하지 않는다.

CheckUpdateFirmware 수신부는 종류 2 선택 후 load·validation·version 조회 결과를 0x533167a4 → 0x52feec18(state, 1)의 입력 정리 경로로 모은다. state+0x48이 NULL이면 0x52feec34에서 wrapper 호출을 건너뛰고 component 정리와 kind·파일명·길이 초기화를 진행한다. 포인터가 비제로일 때만 wrapper를 부르며, 반환값이 비제로여야 포인터를 지우고 나머지 정리를 진행한다. 이번에는 원본 receiver의 분기와 호출을 정적으로 대조했으며 전체 메시지 처리와 스케줄러를 실행하지 않았다. 수신부와 정리 호출 근거

검증 범위와 다음 조사

파일명·volume 19사례와 종료 처리 26사례, 합계 45사례가 원본 RTOS와 통합 decoded 이미지에서 같은 결과를 냈다. 종료 처리 26사례에는 독립 검토에서 추가한 6개 경계 사례가 포함돼 있다. 이 6개를 별도 합계로 중복 계산하지 않았다. 재분석한 범위를 포함해 C 출력 12개와 원본 ARM 1,622 words의 주소·해시를 로컬에 보존했다. 공개 자료에는 분석·검사 도구·메타데이터를 싣는다.

자동 복원 C의 한계도 확인했다. component 5의 C에는 조건 코드 표현이 남아 있고 종료 함수의 C에는 성공 분기의 tail call이 빠져 있다. C 원문은 그대로 보존하며 조건과 반환 관계는 원본 ARM과 CPU 실행으로 판정했다. 실제 파일 접근·큰 메모리 할당·OS 해제·업데이트 executor·물리 매체·카메라는 실행하지 않았다.

다음 조사 대상은 descriptor의 실제 생산자와 크기 단위, mount와 backend 초기화, 완료 통지의 수신 처리, decoded 출력의 최종 회수 시점이다. 현재 결과는 수정 펌웨어의 카메라 수용이나 정상 실행을 입증하지 않는다. 빌드·플래시는 이 분석에서 수행하지 않았다.
