UI와 화면 자원 · 색공간 화면 4

sRGB 글자를 비트맵으로 만들어 표면에 옮기는 과정

글자의 크기를 잰 다음 단계에서 펌웨어가 글자 픽셀을 어떻게 만들고 화면 버퍼에 어떻게 섞어 넣는지 알아봤습니다. 다른 기종으로 화면을 옮기려면 이 픽셀 규칙을 정확히 알아야 합니다.

이 문서에서

  1. 배경: 글자는 덮인 정도를 담은 비트맵으로 그립니다
  2. 원본 코드는 세 구간으로 나눠 실행했습니다
  3. 팔레트는 기본 항목까지만 만들어졌습니다
  4. 705개 픽셀 쓰기를 독립 계산과 대조했습니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 원본 코드가 sRGB 글자를 76×40 크기의 커버리지 비트맵으로 만들었습니다. 3,040칸 가운데 705칸이 글자 획에 걸린 칸입니다.
  • 획에 걸린 칸마다 전경색과 배경색을 float32 가중치로 섞은 4바이트 색을 계산해 표면에 썼습니다. 705개 쓰기의 위치·값·순서와 최종 표면 전체가 독립 계산과 같았습니다.
  • 배경색은 픽셀마다 다시 읽지 않습니다. 전송을 시작할 때 교차 영역 왼쪽 위의 표면 워드 하나를 읽어 모든 칸에 씁니다.
  • 표면은 256×144 합성 RAM이고 팔레트는 기본 항목만 채운 상태였습니다. 실제 LCD의 픽셀 해석, 시작 때의 팔레트 초기화, 메뉴 이벤트는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 텍스트 자식의 좌표와 클립 계산
  • 글꼴로 76×40 비트맵을 만드는 그리기
  • 혼합 캐시 생성과 705개 픽셀 전송
  • 전송 구간의 성공 단언 경로(별도 재생)

모델 시험 조건으로 정한 것

  • 256×144 표면, 현재 선택 0, 언어 0, 프로필 바이트 0
  • 팔레트·옵저버 준비 플래그 두 개
  • 글꼴 파일 읽기와 메모리 할당
  • 앞 단계의 성공 단언 일부

미확인 확인하지 않은 것

  • 확장 팔레트와 팔레트 생성자의 반환
  • 값 255(완전히 덮인 칸)를 쓰는 분기
  • LCD의 채널 배치와 실제 색
  • 메뉴 이벤트, 설정 저장, 다른 기종 이식

배경: 글자는 덮인 정도를 담은 비트맵으로 그립니다

화면 글자는 글꼴의 윤곽선을 픽셀 격자에 맞춰 칠해서 만듭니다. 이 결과물을 글리프 비트맵이라고 합니다. K-3 III의 비트맵은 칸마다 1바이트이며 그 칸이 글자 획에 얼마나 덮였는지를 담습니다. 0은 빈칸이고 값이 클수록 많이 덮인 칸입니다. 이런 값을 커버리지라고 부릅니다.

덮인 정도가 중간인 칸은 글자색과 바탕색을 섞어 칠합니다. 이 방식을 알파 혼합이라고 하며 일반적인 계산은 결과 = 전경 × a + 배경 × (1 − a)입니다(Porter·Duff, 1984). 펌웨어는 커버리지 값마다 전경 가중치와 배경 가중치를 ROM 표에 따로 적어 둡니다. 그 표로 색 16개를 미리 계산해 캐시에 담고 픽셀을 쓸 때는 캐시에서 고릅니다.

원본 코드는 세 구간으로 나눠 실행했습니다

팔레트 생성과 좌표 계산은 따로 진입했고 글자 그리기에서 픽셀 전송까지는 한 번에 이어서 실행했습니다.

  1. 팔레트 기본 항목기본 42개 항목을 채우고 UserData를 읽기 직전에 멈춥니다. 따로 진입했습니다.
  2. 좌표와 비트맵텍스트 자식의 좌표와 클립을 계산하고 같은 StringView가 원본 글꼴로 비트맵을 만듭니다.
  3. 픽셀 전송예상 결과를 계산하려고 잠시 멈춘 뒤 스택과 레지스터를 그대로 두고 이어서 실행했습니다.

하네스는 현재 선택 0, 언어 0, 프로필 바이트 0, 부모 사각형 [10,12,180,60]과 타입 5 표면을 공급했습니다. 표면은 한 줄이 256워드인 256×144 합성 RAM입니다. 이 표면에는 앞 문서의 원본 실행이 아이콘과 체크 표시로 이미 1,532개 픽셀을 써 두었고 글자 전송은 그 위에 이어서 씁니다. 두 Latin 글꼴은 decoded 파일에서 읽어 파일 모형이 요청된 버퍼에 넣었습니다.

원본 좌표 계산이 만든 텍스트 영역은 [110,22,76,40], 뷰 클립은 [110,22,80,40]입니다. 둘의 교차 영역은 76×40 비트맵 전체를 덮습니다.

팔레트는 기본 항목까지만 만들어졌습니다

팔레트 생성은 확장 항목을 만들기 전에 멈췄습니다. 글자 그리기는 이미 채워진 26번과 28번 항목만 읽었습니다.

원본 생성자가 옵저버 관리자를 만든 뒤 하네스가 준비 플래그를 켰습니다. 원본 팔레트 코드는 관리자를 통해 팔레트를 등록하고 프로필 0의 ROM 값과 같은 RGB 항목과 32비트 색 항목 42개를 채웠습니다. 확장 팔레트에 필요한 현재 UserData는 확보하지 못했습니다.

그리기 호출에는 팔레트 준비 플래그를 공급했습니다. 반환하지 않은 팔레트 생성 구간이 만든 값 가운데 26번과 28번만 읽도록 검사했고 두 항목은 프로필 0 생성자가 나중에 쓰는 로컬 쓰기 대상에 들어 있지 않습니다. 이후의 알림과 생성자 반환은 실행 범위 밖입니다.

705개 픽셀 쓰기를 독립 계산과 대조했습니다

원본 전송이 쓴 705워드와 최종 표면 147,456바이트가 Python으로 따로 계산한 값과 모두 같았습니다.

독립 계산은 원본 글리프 임시 버퍼에서 관찰한 바이트를 OR로 합쳐 3,040바이트 비트맵을 만드는 데서 시작합니다. 여기에 원본 가중치, 두 팔레트 워드, 기존 시험 표면을 넣습니다. 네 바이트마다 float32 곱셈과 덧셈을 한 뒤 정수로 잘라 16워드 캐시를 다시 만듭니다. 값 0인 칸은 기존 픽셀을 그대로 두고 부분 커버리지 칸은 캐시의 워드를 고릅니다. 이 대조는 글꼴 윤곽선을 따로 해석하는 실험과는 별개입니다.

한계와 남은 과제

  • 이 재현은 준비된 첫 행의 글자와 합성 RAM 전송까지입니다. 실제 LCD의 픽셀 해석과 색은 확인하지 않았습니다.
  • 팔레트는 기본 42개 항목까지만 원본으로 만들었습니다. 시작 때의 팔레트 초기화와 확장 팔레트는 따로 검증해야 합니다.
  • 값 255인 칸이 없어 단색 직접 쓰기 분기는 실행되지 않았습니다. 화면 가장자리에서 일어나는 일은 화면 경계에서의 sRGB 전송에서 다룹니다.
  • 메뉴 이벤트와 설정 저장, 다른 기종의 UI 이식은 별도 검증이 필요합니다(세 기종 이식 검증 조건).
정정

처음 공개한 JSON은 사례별 표면 높이를 글자 비트맵 높이인 40으로 잘못 적었습니다. 하네스 변수를 분리해 256×144로 고쳤습니다. 정정 전 기록에서 이 높이만 바꾼 해시와 원본 코드 재실행 결과를 대조했고 원본 명령·메모리 쓰기·최종 표면 해시는 그대로였습니다.

재현 방법

Python 3.12와 Unicorn 2.1.4에서 K-3 III 2.20의 decoded 파일(78,683,892바이트)을 읽습니다. 검증기는 도우미 소스를 모두 캡처해 SHA-256을 확인한 뒤 실행합니다. 같은 decoded 바이트에서 RTOS, ICONBIN, 글꼴 범위를 읽고 전체 관측 기록의 정규 JSON 해시 세 개를 검증한 다음 공개 JSON을 씁니다. 파일·메모리 할당·앞 단계 성공 단언의 모형은 단계별로 기록돼 있습니다.

python -B tools/verify_colorspace_text.py decoded.bin --output colorspace-text-replay.json
python -B -m unittest discover -s tests -p test_verify_colorspace_text.py
