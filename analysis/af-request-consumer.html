AF와 렌즈 제어 · 전달과 완료 단계

AF 요청이 큐에서 처리되고 완료 통지가 돌아오기까지

렌즈에 보낼 요청은 만든 자리에서 바로 전송되지 않고 대기 줄을 거칩니다. 누가 그 요청을 꺼내 처리하는지, 처리 뒤에 돌아오는 “완료” 통지가 렌즈의 실제 이동을 뜻하는지 확인했습니다.

이 문서에서

  1. 배경: 요청, 큐, task, 완료 통지
  2. 요청 하나가 지나가는 길
  3. 요청은 32칸 슬롯의 빈 칸에 복사됩니다
  4. 요청을 꺼내 실행하는 것은 AccessoryArbitrate task입니다
  5. 완료 통지는 전달을 건너뛰어도 옵니다
  6. 검사 18건의 범위와 재현 방법
  7. 한계와 남은 과제
  8. 근거 파일과 참고 자료

핵심 요약

  • 명령 0x8900 요청은 32칸짜리 슬롯의 빈 칸에 복사된 뒤 AccessoryArbitrate라는 task의 큐에 들어갑니다. task는 이벤트로 깨어나 요청을 꺼내 실행합니다. 요청 작성부터 완료 통지까지 원본 코드를 이어서 실행해 확인했습니다.
  • 요청을 실행하는 코드는 렌즈 쪽 교환 함수를 부르기 전에 세 가지 조건을 검사합니다. 어느 하나에 걸리면 교환을 건너뜁니다.
  • 완료 통지는 교환을 건너뛴 경우에도 똑같이 호출됐습니다. 그러므로 이 통지를 렌즈가 물리적으로 다 움직였다는 뜻으로 해석할 근거가 없습니다.
  • 교환 함수의 안쪽(패킷 송신·수신)과 그 아래의 통신, 모터 동작은 실행하지 않았습니다. 운영체제의 큐와 스케줄러도 시험용 대역입니다.

확인 원본 코드 실행으로 확인

  • 요청 작성 → 슬롯 복사 → 요청 기록 → 큐에 넣기 (6건)
  • task 진입 → 큐에서 꺼내기 → 실행 → 완료 통지 (5건)
  • 큐 꺼내기 함수의 성공·실패 (3건)
  • 슬롯 초기화, 슬롯 포화, 포인터 보존, 명령 불일치 (4건)

정적 분석 코드를 읽어 판단

  • task 등록과 시작 경로, vtable 연결
  • 교환 함수 안의 패킷 구성과 송신·수신 호출 위치

모델 시험 조건으로 정한 것

  • OS 큐: 넣기는 요청을 기록만 하고, 꺼내기는 합성 노드를 공급
  • 이벤트 대기: 첫 대기에 bit 0을 주고 둘째 대기에서 중단
  • 세 통과 조건의 상태 값과 교환 함수의 반환값
  • CPU는 Unicorn의 Cortex-A15 모델

미확인 확인하지 않은 것

  • 실제 전송과 모터 동작, 렌즈의 이동 완료
  • 통과 조건에 쓰이는 상태 값을 만드는 코드와 그 뜻
  • 다른 opcode, options가 0이 아닌 경로, 완료 뒤 호출되는 두 함수의 내부

배경: 요청, 큐, task, 완료 통지

앞 문서에서 InMotor 제어 객체가 구동 값을 명령 0x8900의 2바이트로 만드는 것을 확인했습니다. 이 문서는 그다음을 다룹니다. 만든 요청이 어디에 보관되고, 누가 꺼내고, 처리 뒤에 무엇이 돌아오는지입니다.

쉽게 말하면

민원 창구와 비슷합니다. 신청서(요청)를 접수함(큐)에 넣으면 담당자(task)가 차례대로 꺼내 처리하고, 끝나면 신청인에게 “처리 완료”라고 알려 줍니다(완료 통지). 이 알림은 서류 처리가 끝났다는 뜻입니다. 신청한 물건이 실제로 도착했다는 뜻은 아닙니다. 이 문서의 결론도 같습니다.

구동 방식이나 AF 알고리즘을 나중에 바꾼다면, 새 코드는 “요청이 접수됐다”, “렌즈 쪽으로 전달됐다”, “렌즈가 다 움직였다”를 서로 다른 사실로 다뤄야 합니다. 그래서 완료 통지가 정확히 어느 시점에, 어떤 조건에서 오는지를 확인했습니다.

요청 하나가 지나가는 길

요청은 슬롯에 복사되어 큐로 들어가고, task가 꺼내 실행한 뒤, 요청을 보관하던 객체로 완료 통지가 돌아옵니다. 교환 함수부터 오른쪽은 실행하지 않았습니다.

요청은 32칸 슬롯의 빈 칸에 복사됩니다

작성 함수가 스택에 만든 descriptor는 수명이 짧습니다. 그래서 AfLensControl 안의 슬롯으로 복사되고, 같은 슬롯 안에 큐로 넘길 요청 기록이 만들어집니다.

작성 함수 0x52efc7a0은 스택에 descriptor S를 만듭니다(0x52efc830..84c). 앞 8바이트는 02 00 00 89 00 00 00 00이고, S+8은 2바이트 데이터를 가리키는 포인터, S+c는 0입니다. 길이 2와 명령 번호 0x8900이 든 기록이며, 렌즈와 주고받는 통신 프레임 자체라고 부르지 않습니다. 요청 종류 번호(opcode) 0x1b는 0x52eff608이 따로 지정합니다.

token = ((descriptor_command << 16) + (options.word4 << 8) + i) mod 2^32
두 가지 조심할 점

token은 덧셈으로 만듭니다. options.word4의 범위를 가정한 OR 식으로 일반화하지 않습니다. 그리고 추가 포인터 D+c는 생성자가 32칸을 초기화할 때 0이 되지만, S+c가 0인 요청은 이 필드를 다시 쓰지 않습니다. 슬롯을 재사용하는 모든 경로에서 이 값이 0으로 유지되는지는 확인하지 않았습니다. 실제로 낡은 포인터가 남는 일을 관찰한 것도 아닙니다.

여섯 건 모두 함수는 슬롯 번호를 돌려주었고, 큐에 넣는 함수는 그 슬롯의 Req 주소를 받았습니다. 그 밖에 세 가지 경계를 확인했습니다.

  • 슬롯 초기화 — 생성자의 반복문 구간을 실행하니 32칸 모두에서 D+c가 0이 됐습니다.
  • 추가 포인터 보존 — D+c에 미리 0x11223344를 넣어 두고 요청을 만들었더니 값이 그대로 남았습니다.
  • 슬롯 포화 — 32칸을 모두 사용 중으로 만들면 함수는 0xff를 돌려주고 큐에 아무것도 넣지 않았습니다.

요청을 꺼내 실행하는 것은 AccessoryArbitrate task입니다

큐의 주인은 AccessoryArbitrate라는 task입니다. 이벤트 bit 0으로 깨어나 큐에서 요청을 꺼내고, 실행 함수를 직접 부릅니다.

AfLensControl은 초기화 때(0x52efe7b4..7f8) 싱글턴 0x52f16c10의 +4를 L+1d8에 저장해 둡니다. 이 객체가 A입니다. factory(0x52f16ae0..ae4)가 생성자 0x52f14814로 만들었고, 생성자는 A+74의 큐와 A+88의 이벤트를 초기화하고 A+4에 vtable 포인터 0x538f3c68을 설치합니다.

다섯 건 모두 완료 통지는 콜백 객체 L+1d4, 이벤트 0x0409001a, token 0x89004201로 호출됐습니다. 콜백 안에서 뒤처리 함수 두 개도 매번 호출됐습니다. 교환을 건너뛴 세 건과 교환한 두 건을 완료 통지의 인수만으로는 구별할 수 없습니다.

실행 함수가 하는 일

  1. descriptor 읽기 0x52f15e84..e9c가 D에서 명령 번호(+14, 16비트), 데이터 포인터(+8), 길이(+12, 1바이트), 추가 포인터(+c)를 꺼내 0x52f15100(A, 0x8900, payload, 2, extra)로 넘깁니다.
  2. 조건 검사 전달 함수 0x52f15100은 A의 byte +9b가 0이 아니면 바로 돌아옵니다. 중재 함수 0x52f14c9c(A, 4, 2)가 0을 돌려줘도 바로 돌아옵니다. 다시 시도하는 반복문이 아닙니다. 이어 부르는 0x52f18490은 통신 객체의 byte C+52f3이 0이 아니면 0x8900 전달을 막습니다. A+5c는 factory의 +8에 있는 reader 객체와 같은 포인터입니다.
  3. 명령 정보 조회와 교환 0x52f182d4가 실제 조회 함수로 0x8900의 정보를 얻습니다. type 3, index 0x49, 추가 바이트 2, required mask 0입니다. type 3 분기는 0x52f183fc에서 교환 함수 0x52f18128을 부릅니다.
  4. token 정리 전달 함수가 돌아오면 token의 하위 16비트는 그대로 두고 상위 16비트에 D의 명령 번호를 다시 넣습니다.
  5. 완료 통지 0x52f15ec0에서 Req+4가 가리키는 객체의 vtable +8 함수를 이벤트 0x0409001a와 token으로 부릅니다.

교환 함수 0x52f18128 안에는 패킷 번호 0x63과 명령 번호의 하위·상위 바이트를 놓는 코드, 송신 호출 0x52f3a74c와 수신 호출 0x52f3a754가 보입니다. 이번 검사는 이 함수의 입구에서 stub으로 바꿨습니다. 실제 전송이나 모터 동작은 실행하지도 검증하지도 않았습니다.

완료 통지를 받는 쪽

L+1d4의 vtable 포인터는 0x538f0568이고, 실제로 불리는 칸 0x538f0570의 값은 0x52eff43c입니다. 이 작은 연결 함수가 포인터를 L로 되돌려 0x52eff330을 부릅니다. 콜백은 token에 든 명령 번호와 슬롯에 저장해 둔 명령 번호를 비교합니다. 일치하는 이벤트 0x1a에서 데이터 처리 함수 0x52efde0c와 정리 함수 0x52eff2c8을 부릅니다. 두 함수의 안쪽은 이번 범위 밖입니다.

명령 번호가 다르면 어떻게 되는지도 한 건 확인했습니다. 검증 스크립트가 슬롯 0의 L+210에 0x8900을 써 두고 token에는 명령 번호 0x8901을 넣었더니, 콜백은 진단 출력 함수만 부르고 두 뒤처리 함수는 부르지 않았습니다.

주의

세 조건에 쓰이는 상태 바이트를 누가 언제 바꾸는지, 그 값이 무슨 뜻인지, 렌즈에 따라 어떻게 달라지는지는 확인하지 않았습니다. 검사에서 그 값을 바꿔 넣어 분기가 달라지는 것을 본 것이며, 특정 렌즈나 화면 조작이 그 값을 만든다는 증거는 아닙니다.

검사 18건은 모두 PC의 CPU 에뮬레이터에서 원본 ARM 코드를 실행한 것입니다. 운영체제, 통신, 완료 뒤 함수는 주소를 밝힌 stub으로 바꿨습니다.

한계와 남은 과제

  • 물리 동작 — 렌즈와의 실제 입출력, 드라이버 실행, 렌즈의 이동 완료, 시간, 기계적 조건은 확인하지 않았습니다. 2바이트 값의 단위와 방향의 뜻도 앞 문서에서 밝힌 대로 미해결입니다.
  • 검사한 경로 — 비동기 경로(options의 byte 0이 0)만 검사했습니다. 다른 요청 opcode, options가 0이 아닐 때의 대기·할당 분기, 특수 명령 1·2·3, 잘못된 descriptor의 일반적인 동작은 수치로 확인하지 않았습니다.
  • 슬롯 재사용 — 슬롯을 다시 쓰는 모든 과정과 초기화 경로를 따라가지 않았습니다.
  • 상태 값의 출처 — C+52f3, A+9b, 중재 상태를 만드는 코드는 이번 범위 밖입니다.
  • 완료 뒤 함수 — 콜백이 부르는 두 뒤처리 함수의 안쪽은 보지 않았습니다.
  • 실행하지 않은 것 — 카메라, 렌즈, RTOS 스케줄러, 실제 전송을 실행하지 않았습니다. 외부 장치 입출력, 펌웨어 수정·빌드·플래시도 하지 않았습니다.
