펌웨어 재구축 · 초기 메모리 증명

RMW 8바이트의 최종값은 초기 메모리와 무관한가

원본 할당기는 아직 아무도 쓰지 않은 메모리를 읽어 일부 비트만 고쳐 씁니다. 다시 만든 펌웨어가 켜질 때마다 같은 결과를 내려면 이런 곳의 최종값이 처음 RAM 내용에 기대지 않아야 합니다. 그중 8바이트를 수식 모형으로 증명했습니다.

핵심 요약

  • 할당기가 남은 빈 블록의 길이를 적는 8바이트(워드 두 개)를 다루는 원본 명령 15개를 분석자가 수식 모형으로 옮겼습니다.
  • Z3로 검사한 결과, 전제 아래에서 최종 두 워드는 처음 64비트가 무엇이든 count를 2비트 왼쪽으로 민 값에 1을 더한 값과 0이었습니다. 비트 지우기를 하나씩 뺀 대조 모형에서는 반례가 나왔습니다.
  • decoded 이미지 하나로 재현합니다. 도구는 이미지와 대상 60바이트의 해시, 15개 명령의 해독만 확인하고 원본 명령을 실행하지는 않습니다. 모형이 원본을 바르게 옮겼는지는 사람이 검토한 것입니다.
  • 중간에 쓰는 바이트는 초기값에 따라 달라지고 실제 읽기도 그대로 남습니다. 나머지 48바이트, 물리 RAM의 초기값 출처, 동시 접근, 전체 부팅은 이 증명 밖입니다.

확인 파일 바이트로 확인

  • decoded 이미지, RTOS, 대상 60바이트의 SHA-256
  • 대상 구간이 4바이트 A32 명령 15개로 해독됨

모델 모형과 전제

  • 15개 명령의 의미를 분석자가 손으로 옮긴 모형
  • signed count > 1, 일반 RAM 8바이트, 순차 정상 완료
  • Z3 결과는 이 모형과 전제 안에서만 성립

미확인 증명 범위 밖

  • 원본 명령의 실제 실행과 과거 실행 기록의 재검증
  • 나머지 48바이트, 물리 RAM 초기값의 생산자
  • 동시 접근, 인터럽트, 전체 부팅

배경: 읽기-수정-쓰기와 초기 메모리

RMW는 값을 통째로 덮어쓰지 않고 읽은 값의 일부 비트를 살려 다시 쓰는 방식입니다. 대상이 이미 초기화된 메모리라면 문제가 없습니다. 아직 아무도 쓰지 않은 메모리라면 살린 비트에 켜질 때 남아 있던 값이 섞입니다.

원본 할당기는 빈 페이지 목록을 만들면서 관리 칸 몇 곳을 이렇게 처리합니다. 이름 registry 재현에서는 이런 바이트 56개만 "쓰이기 전에 읽어도 되는 곳"으로 허용했습니다. 허용 목록을 줄이거나 다시 만든 코드에서 초기화를 생략하려면, 그 바이트의 최종값이 초기 내용과 무관하다는 근거가 있어야 합니다.

쉽게 말하면

칠판에 이미 무언가 적혀 있을 때, 글자 일부만 지우고 새로 써서 결국 같은 문장이 되는지 확인하는 일입니다. 모든 가능한 낙서(2의 64제곱 가지)를 직접 해 볼 수 없으니, 계산을 식으로 옮겨 solver에게 "결과가 달라지는 낙서가 있는가"를 물었습니다.

증명한 것: 두 워드의 최종값

전제가 지켜지면 첫 워드는 (count << 2) | 1, 둘째 워드는 0이 됩니다. 초기 64비트는 최종값에 영향을 주지 않습니다.

모형은 처음 두 워드를 아무 32비트 값으로 둡니다. 첫 워드의 하위 2비트를 01로 정하고 상위 30비트를 count로 바꿉니다. 둘째 워드에서는 하위 2비트와 상위 30비트를 모두 지웁니다. 최종값이 이 식과 달라지는 반례를 찾게 하자 Z3는 unsat을 돌려주었습니다. 32비트를 넘는 부분은 버립니다.

전제

  • signed 32비트 count > 1인 경로로 이 구간에 들어옵니다.
  • 대상은 쓰기 가능한 일반 RAM 8바이트이고 little-endian입니다.
  • 명령은 순서대로 정상 완료됩니다. 동시 접근, 비동기 접근, 같은 칸을 가리키는 다른 쓰기, fault는 없습니다.
  • 모형이 원본 15개 명령의 의미를 바르게 옮겼다고 봅니다. 해시와 명령 수 검사는 이 번역의 정확성을 자동으로 증명하지 않습니다.
대조 모형: 비트 지우기를 하나씩 뺐을 때
모형에서 뺀 연산결과Z3가 찾은 반례 (첫 워드, 둘째 워드, count)

과거 실행 기록과의 연결

registry 재현에서 처음 읽힌 8바이트가 이 구간의 대상입니다. 기록된 최종값이 모형의 계산과 같습니다.

이름 registry 할당과 조회 재현에서는 0x56493278..0x5649327f(관리 칸 0xbf번)를 남은 빈 블록의 길이 레코드로 처음 기록했습니다. 그 전의 원본 기록 0xba51 >> 2 = 0x2e94에서 1페이지를 할당하면 count는 0x2e93입니다. 최종 두 워드는 0xba4d, 0입니다.

기록초기 00초기 A5
첫 바이트 쓰기01A5

모형으로 계산한 네 쓰기 값도 표와 같습니다. 다만 이것은 모형의 예시이며 새로 원본을 실행해 얻은 관측이 아닙니다. 과거 기록은 출처 기록에 보존했습니다. 공개 CLI는 그 기록을 다시 검증하지 않습니다.

해석할 때 주의

registry 재현은 마지막에 허용한 56바이트 모두를 guest가 기록했는지 검사합니다. 나머지 48바이트도 초기화 과정에서 읽고 씁니다. 이 증명을 그 48바이트의 값이 보존된다는 뜻으로 읽으면 안 됩니다.

registry 재현에서 실제로 관측한 prologue 정지점은 0x525b5a54입니다. 그 뒤 정적 조사에서 찾은 MPIDR 후보 0x525d9f4c와 0x525d6f18은 이 관측 정지점과 구분합니다. 공개 도구는 어느 주소에서도 원본 CPU 명령을 실행하거나 값을 대신 넣지 않습니다.

과거 기록의 쓰기 위치

두 초기 패턴 모두 처음 쓴 명령은 0x525d85b0, 0x525d85b4, 최종 워드를 쓴 명령은 0x525d85c8, 0x525d85cc입니다. 그보다 앞서 이 8바이트에 쓴 명령은 없었습니다. 조사한 guest store는 4,473개입니다.

기본 검사와 실제 증명 검사

입력 없이 도는 기본 검사 18개와, decoded 이미지로 실제 증명까지 하는 검사 19개가 모두 통과했습니다.

원본 분석 스크립트의 출처 해시와 지금 실행하는 공개 helper의 해시는 다릅니다. helper와 source manifest는 읽어 들인 바이트의 해시를 확인한 뒤 씁니다. 원본 명령 바이트, 전체 disassembly, 비공개 7MB trace는 패키지에 넣지 않았습니다.

한계와 남은 과제

  • 증명한 것은 이 8바이트의 최종 두 워드입니다. 실제 읽기와 중간 바이트 쓰기는 남아 있고 그 값은 초기값에 따라 다릅니다.
  • 원본 명령을 새로 실행하지 않았고 과거 실행 기록도 다시 검증하지 않았습니다.
  • 다른 48바이트는 이 증명 범위 밖이며 기존 56바이트 RMW 허용 목록은 그대로입니다. 그 48바이트의 분류와 그중 4바이트 증명은 RMW 48바이트 분류에 있습니다.
  • 물리 RAM 초기값의 생산자, 동시성, 전체 부팅은 입증하지 않았습니다.

재현 방법

Python 3.12.3에서 확인했습니다. 설치한 배포판은 capstone 5.0.9와 z3-solver 5.3.1.0입니다. 실행 중 모듈은 각각 5.0.7과 5.3.1로 표시됩니다. 실제 증명용 의존성은 별도 환경에 설치할 수 있습니다. 기본 검사에는 필요 없습니다.

# 표준 라이브러리만 쓰는 기본 검사
python -S test_verify.py --work-dir /existing/temp-parent --output /path/to/new-guard-results.json

# decoded 이미지로 실제 모형 증명
python -m pip install -r requirements-proof.txt
python verify.py /path/to/decoded.bin --output /path/to/new-proof.json
python test_verify.py --work-dir /existing/temp-parent --decoded /path/to/decoded.bin --output /path/to/new-proof-tests.json

명령은 이 패키지 폴더에서 실행하는 예입니다. 스크립트의 절대 경로를 쓰면 다른 폴더에서도 됩니다. 입력은 업데이트 파일 자체가 아닌 정확한 decoded 이미지(78,683,892바이트)입니다. 해시는 source.json에 있습니다. 출력 파일은 새 경로여야 하며 --work-dir는 이미 있는 폴더여야 합니다.

기본 검사는 독립된 임시 폴더 안에서 합성 fixture를 만들고 지웁니다. 저장소 CI와 릴리스 검사가 기본 검사를 돌립니다. 실제 증명 검사는 사용자가 원본 입력을 가진 환경에서 골라 실행합니다.
