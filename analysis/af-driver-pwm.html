AF 모터 드라이버와 PWM 객체의 연결

AF 쪽 제어 객체가 만든 요청은 결국 하드웨어를 다루는 드라이버 객체에 닿습니다. 그 드라이버가 어떤 PWM 객체를 붙잡고 있는지, PWM 쪽에서 돌아오는 이벤트를 어떻게 처리하는지 원본 코드에서 확인했습니다.

이 문서에서

  1. 배경: PWM과 드라이버 객체
  2. 드라이버는 PWM 객체 두 개를 붙잡습니다
  3. 여러 객체가 같은 PafMotor를 가리킵니다
  4. 리셋 요청은 PWM 설정 레코드를 부분 갱신합니다
  5. 드라이버 콜백은 이벤트에 따라 플래그를 쓰거나 Joint로 넘깁니다
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • PafMotor는 AfMotorDriver라는 드라이버 객체 하나를 가리킵니다. 드라이버는 레지스트리에서 찾은 PWM 객체 두 개를 붙잡습니다. 이 연결은 원본 코드와 RTTI 이름을 읽어 확인했습니다.
  • 드라이버의 이벤트 콜백을 원본 그대로 실행했습니다. PWM 이벤트 두 가지는 드라이버의 플래그 바이트를 1로 만듭니다. 다른 네 가지는 Joint 쪽 리스너로 넘기는 호출 직전까지 갔습니다. 이벤트 값은 시험에서 직접 넣었습니다.
  • Joint와 디버그·렌즈 정보 객체 등 여러 곳이 같은 PafMotor를 가리킵니다. Joint가 그 포인터로 Motor의 값을 읽어 오는 두 사례를 실행해 확인했습니다.
  • 리셋 요청이 PWM 설정 레코드를 거쳐 레지스터 읽기에 닿는 경로는 코드를 읽어 따라간 결과입니다. 실제 PWM 출력, 인터럽트, 모터 동작은 실행하지 않았고 두 PWM 채널의 물리적 역할도 모릅니다.

확인 원본 코드 실행으로 확인

  • 드라이버 생성자 후반부의 필드 초기화
  • 이벤트 콜백 7가지의 쓰기와 정지 지점
  • factory 확인 호출, 바인더 호출, Joint의 Motor 포인터 저장과 값 복사

정적 분석 코드를 읽어 판단

  • 드라이버 singleton과 PWM 객체 두 개의 등록·조회 경로
  • 리셋 요청의 12바이트 레코드 병합과 16바이트 레코드 구성, 레지스터 읽기 위치
  • Motor 코드 구간의 저장 명령 328개 검사

모델 시험 조건으로 정한 것

  • 콜백에 넣은 이벤트 값 7가지, 플래그의 초기값 0
  • factory 슬롯과 Motor 상태 값(+0x3c, +0x44)
  • CPU는 Unicorn의 Cortex-A7·A15 모델

미확인 확인하지 않은 것

  • 실제 초기화 순서, 리스너 목록과 등록 성공 여부
  • PWM 인터럽트의 발생, 레지스터 응답, 리셋 성공
  • 두 PWM 채널이 각각 무엇을 움직이는지, 숫자의 물리 단위

배경: PWM과 드라이버 객체

PWM은 전원을 아주 빠르게 켜고 끄면서 켜져 있는 시간의 비율(duty cycle)로 평균 출력을 정하는 방식입니다. 모터 구동 칩은 이 비율을 바꿔 모터에 걸리는 평균 전압을 조절합니다. TI의 모터 드라이버 DRV8235 데이터시트는 평균 출력 전압이 목표보다 낮으면 브리지의 duty cycle을 높이고 높으면 낮춘다고 설명합니다.

쉽게 말하면

전등 스위치를 1초에 수천 번 켰다 껐다 하는 것과 비슷합니다. 켜 둔 시간이 길수록 평균적으로 더 밝아집니다. 카메라 바디 안의 작은 모터도 이런 방식으로 세기와 속도를 조절할 수 있습니다.

K-3 Mark III는 바디 안에 AF 모터를 두고 마운트의 AF 커플러로 렌즈를 돌립니다. 리코이미징의 구동 방식 정의에서는 이것을 “Body AF”라고 부릅니다. 펌웨어에 Pwm이라는 클래스가 있고 AF 드라이버가 그것을 붙잡는다는 사실은 바디 쪽 구동 하드웨어를 짐작하게 합니다. 그러나 이 문서가 확인한 것은 객체 연결과 레코드 처리까지입니다. 두 PWM 채널이 바디 AF 모터에 연결된다는 증거는 아직 없습니다.

드라이버는 PWM 객체 두 개를 붙잡습니다

요청은 PafMotor → 드라이버 → PWM 두 개로 내려갑니다. PWM 이벤트는 드라이버의 리스너로 올라옵니다. 드라이버는 그중 일부를 Joint로 넘깁니다.

여러 객체가 같은 PafMotor를 가리킵니다

Joint, 디버그 객체, 렌즈 정보 객체 등이 PafMotor 포인터를 따로 보관합니다. Joint가 이 포인터로 Motor의 값을 읽어 오는 동작을 실행해 확인했습니다.

AfMotorFactory의 +0xc는 PafMotor를, +0x10은 PafPulse를 가리킵니다. factory의 첫 확인 호출은 각 객체의 vtable +8을 읽습니다. 별도 바인더 호출은 vtable +0xc를 읽습니다. PafMotor 포인터를 따로 보관하는 곳은 아래 다섯 군데입니다.

저장 명령 검사의 범위

Motor 코드 구간(10,848바이트)의 STR·STRB·STRH 328개를 폭과 변위로 검사했습니다. +0x56·+0x68과 겹치는 고정 변위 저장 두 개는 생성자의 0 초기화였습니다. 인덱스를 쓰는 저장 두 개는 Pulse +0xa6a를, 주소를 함께 갱신하는 저장 하나는 스택을 가리킵니다. 외부 호출, 간접 포인터 쓰기, Thumb 코드까지 닫은 전수 분석은 아닙니다. 두 필드에 0이 아닌 값을 넣는 경로는 미확인입니다.

리셋 요청은 PWM 설정 레코드를 부분 갱신합니다

Joint의 리셋 호출은 드라이버를 거쳐 PWM 객체 두 개에 12바이트 입력을 넘깁니다. 이 입력은 기존 설정 가운데 일부만 바꿉니다. 그 결과는 16바이트 레코드로 바뀌어 레지스터 쪽 코드로 갑니다. 이 절은 모두 정적 분석입니다.

  1. Joint 리셋 호출0x52f08214
    → PafMotor
  2. 드라이버 리셋0x52f0b9a4에서 r1=0으로
    0x5317817c 진입
  3. 12바이트 병합0x5326ca24
    PWM 두 개에 각각
  4. 16바이트 레코드0x5326c7c4
    스택에 구성
  5. 레지스터 읽기0x53349644
    0x1e000000 기반 주소
  • 드라이버는 12바이트 입력을 만들고 바이트 +8에 0을 지정한 뒤 두 PWM 객체에 차례로 넘깁니다.
  • 병합 함수는 각 PWM 객체 +0x2c의 12바이트 레코드를 복사합니다. 입력에서 “유지”로 표시한 필드는 남기고 나머지만 바꿉니다. 두 반워드는 0, 대부분의 바이트는 0xff가 유지 표시입니다.
  • 레코드 구성 함수는 0x5326c7f8부터 네 워드를 지우고 변환한 필드와 표의 워드를 씁니다. 그다음 0x5326c8f4에서 PWM 번호와 레코드 포인터를 하위 함수에 넘깁니다. 하위 코드는 RAM을 갱신한 뒤 0x53349644에서 레지스터를 읽습니다.
  • 드라이버에 r1≠0으로 들어오는 경우에는 정지 경로의 첫 레지스터 읽기가 0x53349b9c입니다.

드라이버는 두 적용 호출 사이에서 반환값을 보고 분기하지 않습니다. 적용 함수 안의 하위 호출은 0x5326c8f8과 0x5326c96c에서 각각 반환값을 검사합니다. 주변장치의 응답이나 리셋 성공은 재현하지 않았습니다. 리셋이 아닌 일반 요청이 어떤 12바이트를 만드는지는 AF PWM 요청과 정수 변환에서 원본 코드를 실행해 확인했습니다.

드라이버 콜백은 이벤트에 따라 플래그를 쓰거나 Joint로 넘깁니다

PWM 이벤트 두 가지는 드라이버 플래그를 1로 만듭니다. 다른 이벤트 하나는 아무것도 바꾸지 않습니다. 나머지 네 가지는 리스너 전달 호출 직전까지 갑니다.

드라이버는 PWM 리스너에 자기 +4를 이벤트 0x12f·0x130의 수신자로 등록합니다. 콜백 0x53177928은 받은 주소에서 4를 빼 원래 드라이버를 찾습니다. Joint는 같은 드라이버의 리스너에 자기 +0xc0을 ID 네 개로 등록합니다. 이 경로의 Joint 콜백 0x52f07de4는 받은 주소에서 0xc0을 뺍니다. 그중 0x3d의 일부 분기는 Joint +0xdc로 PafMotor에 접근합니다(정적 분석).

시험 조건

드라이버 생성자의 후반부를 실행해 vptr 두 개와 플래그를 초기화한 뒤 ROM 슬롯이 가리키는 콜백을 사례마다 호출했습니다. 이벤트 값은 하네스가 직접 넣었고 플래그는 사례마다 0으로 되돌렸습니다. 반환은 하네스가 둔 주소 0x20000000에서 확인했습니다. 실제 리스너 목록과 등록 성공 상태는 넣지 않았습니다. 서비스 반환이나 레지스터 응답을 대신하는 훅도 쓰지 않았습니다.

세 CPU 조건은 Cortex-A7 기본, 초기 일반 레지스터와 NZCV를 바꾼 Cortex-A7과 Cortex-A15입니다. 전달이 멈춘 네 사례에서 레지스터는 r0 = 0x547bc25c(드라이버 +4), r1 = 이벤트 번호, r2 = 0, r3 = 전달 함수 0x52f13a18이었습니다. 실제 초기화 순서, PWM 인터럽트의 발생, 전달 뒤의 리스너 실행, 두 채널의 물리적 역할은 검증 범위 밖입니다.

한계와 남은 과제

  • 하드웨어: PWM 레지스터 접근, 인터럽트, 주변장치 응답은 실행하지 않았습니다. 레지스터 접근 위치는 코드를 읽어 찾았습니다.
  • 채널의 역할: 키 0xe0·0xe1의 두 PWM이 바디 AF 모터의 어느 신호에 해당하는지, 애초에 AF 모터를 움직이는지는 모릅니다.
  • 이벤트 출처: 이벤트 값은 시험에서 넣었습니다. 실제로 어떤 순간에 0x12f·0x130이 오는지, 플래그 +0x44·+0x45를 누가 읽는지는 추적하지 않았습니다.
  • 숫자의 뜻: 일반 요청의 정수 두 개(0x52f0bcf0, 0x52f0bea8에서 오는 값)가 0x531780b8에서 PWM 반워드로 바뀌는 과정은 다음 문서에서 다룹니다. 그 물리 단위는 확인하지 못했습니다.
  • 실행하지 않은 것: 카메라, 렌즈, 모터, RTOS 스케줄러를 실행하지 않았고 펌웨어를 수정하지 않았습니다.

재현 방법

저장소 루트에서 Python, Unicorn 2.1.4, Capstone 5.0.7로 실행합니다. 원본 decoded.bin 또는 잘라 낸 RTOS 파일을 넣고 출력은 아직 없는 새 경로로 지정합니다. 재현기는 입력의 길이와 SHA-256, 보조 코드 두 개의 SHA-256을 먼저 확인합니다. 두 전체 관측 기록의 SHA-256이 맞아야 공개 JSON을 씁니다. 이 JSON에는 원본 바이트나 전체 디스어셈블리 대신 주소·구간 해시와 실행 결과만 남깁니다.
