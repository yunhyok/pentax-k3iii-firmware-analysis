K-3 III DNG의 CFA 범위와 기본 크롭

변환 DNG에서 센서 값이 어느 영역까지 쓰이고, 밝은 쪽 끝에서 몇 개가 포화하는지 셌습니다. 공개 SDK가 첫 정규화 단계에서 이 값을 어떻게 바꾸는지도 수식으로 계산했습니다.

이 문서에서

  1. 배경: 블랙·화이트 레벨과 기본 크롭
  2. 기본 크롭에 WhiteLevel 초과 샘플 8,529개가 남습니다
  3. SDK 수식에서는 8,530개가 65,535에 이릅니다
  4. PEF에 기록된 값과 비교하면
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 변환 DNG 한 개의 CFA 샘플을 세 영역에서 셌습니다. 최종 이미지 범위인 기본 크롭에 WhiteLevel 16,315를 넘는 샘플이 8,529개 남아 있습니다.
  • BlackLevel 64 이하인 샘플은 모두 ActiveArea 바깥 여백에 있습니다.
  • 공개 Adobe DNG SDK의 Stage 2 정수 계산을 Python으로 옮겨 보면 경계값과 같은 1개를 더한 8,530개가 최댓값 65,535에 이릅니다. 이 문서에서는 SDK를 실행하지 않았습니다. 실제 실행 결과는 SDK Stage 2 실행에 있습니다.
  • 디모자이크 이후, SDK 렌더 단계, Lightroom의 처리는 다루지 않습니다.

확인 파일을 직접 읽어 집계

  • DNG RAW SubIFD의 태그(ActiveArea, DefaultCrop, BlackLevel, WhiteLevel)
  • 세 영역과 RGGB 위치별 샘플 개수

정적 분석 SDK 소스를 읽어 계산

  • SDK 1.7.1 Build 2768 소스의 Stage 2 정수 경로를 Python으로 옮긴 계산
  • 좌표계와 영역 순서(소스 줄 번호는 접이식 상자)

미확인 이 집계로 알 수 없는 것

  • Converter 18.7과 Lightroom 내부의 실제 처리
  • Adobe가 PEF를 열 때 쓰는 WhiteLevel
  • 디모자이크와 최종 렌더

배경: 블랙·화이트 레벨과 기본 크롭

RAW 샘플은 센서가 낸 정수 그대로입니다. 빛이 없을 때도 0이 아닌 값이 나옵니다. 그 바닥값이 BlackLevel입니다. 센서나 변환기가 포화하는 값은 WhiteLevel입니다. DNG 규격은 현상할 때 BlackLevel을 빼고 WhiteLevel−BlackLevel로 나눠 0~1 범위로 옮기도록 정합니다.

저장된 배열은 실제 이미지보다 큽니다. 둘레의 여백을 뺀 유효 화소 영역이 ActiveArea입니다. 그 안에서 최종 이미지로 남길 범위가 기본 크롭입니다. 크롭 바깥의 몇 줄은 디모자이크가 가장자리에서 이웃 화소를 쓸 수 있게 남겨 둔 것입니다.

Adobe DNG SDK는 RAW를 단계별 배열로 다룹니다. 파일에서 읽은 그대로가 Stage 1, 블랙을 빼고 정규화한 것이 Stage 2, 디모자이크한 카메라 RGB가 Stage 3입니다. 이 문서는 Stage 1 배열을 세고 Stage 2 값을 계산합니다.

기본 크롭에 WhiteLevel 초과 샘플 8,529개가 남습니다

WhiteLevel을 넘는 샘플 8,565개 가운데 36개만 여백에 있습니다. 나머지 8,529개는 ActiveArea와 기본 크롭 안에 모두 들어 있습니다.

ActiveArea의 네 값은 RAW 배열의 위·왼쪽·아래·오른쪽이며 아래와 오른쪽 경계는 포함하지 않습니다. 기본 크롭의 원점은 ActiveArea 안에서 가로 28, 세로 24만큼 들어간 점입니다. 저장 배열 좌표로 옮기면 행 58, 열 54에서 시작합니다. 아래 표는 저장 방향의 RAW 좌표입니다.

SDK 수식에서는 8,530개가 65,535에 이릅니다

SDK의 기본 Stage 2 정수 경로를 따라 계산하면 16,315 이상인 코드는 모두 uint16 최댓값 65,535가 됩니다. 0이 되는 값은 ActiveArea에 없습니다.

이 RAW SubIFD의 BitsPerSample은 16이고 SampleFormat(태그 339)은 없습니다. SDK 1.7.1 Build 2768은 이를 부호 없는 16비트(ttShort)로 읽습니다. 기본 Stage 2도 같은 형식을 쓰며 목적지 블랙은 0입니다. 2×2 BlackLevel은 모두 64, WhiteLevel은 16,315입니다. 선형화 LUT, 가로·세로 블랙 보정값, opcode list는 없습니다.

  1. 스케일 정규화 스케일은 1/(16315−64) = 1/16251입니다. 계산은 real64로 합니다.
  2. 두 항을 따로 반올림 원시 샘플 항과 블랙 항을 8비트 추가 정밀도로 각각 반올림합니다. 반복 열이 둘이어서 블랙값이 같아도 2차원 보정표가 생깁니다. 세로 보정값이 없으므로 1차원 보정항은 0입니다. LUT에는 스케일만 담고 블랙은 따로 뺍니다.
  3. 빼고 줄이기 두 항을 뺀 뒤 128을 더하고 8비트 오른쪽으로 밉니다.
  4. 제한 결과를 0~65,535로 자릅니다.

PEF에 기록된 값과 비교하면

PEF 쪽 기준값 16,378을 쓰면 기본 크롭의 초과 샘플은 8,479개로 줄어듭니다. 다만 Adobe가 PEF에서 이 값을 쓴다는 근거는 없습니다.

16,315보다 크고 16,378 이하인 샘플은 50개입니다. 이 구간은 두 파일에 적힌 숫자의 차이일 뿐입니다. 원본 PEF와 DNG의 메타데이터 비교는 원본 PEF와 첫 DNG의 CFA 및 메타데이터 대조에 있습니다.

한계와 남은 과제

  • 파일 하나: 보존한 변환 DNG 한 개에서 얻은 결과입니다. 변환기 버전과 이 DNG의 출처는 K-3 III PEF의 As Shot 중립값에 있습니다.
  • 집계와 계산을 구분: 영역별 개수는 저장 CFA를 디코딩해 직접 센 값입니다. Stage 2 값은 SDK 소스를 Python으로 옮겨 계산했습니다.
  • 제품 내부 미확인: Converter 18.7과 Lightroom의 내부 실행, 디모자이크, 최종 렌더는 확인하지 않았습니다.

재현 방법

첫 변환 K3IIIhSLI0000100NR0.dng, 원본 K3IIIhSLI0000100NR0.PEF, Adobe DNG SDK 1.7.1 Build 2768 ZIP을 지정합니다. PEF는 해시 확인에만 쓰입니다. 검증기는 세 입력의 크기와 SHA-256, ZIP 안 소스 파일 6개의 해시를 확인한 뒤 DNG의 RAW SubIFD 한 장을 디코딩합니다. 다시 변환해 해시가 달라진 DNG는 거부합니다. 결과 전체가 고정 SHA-256과 같을 때만 새 파일을 씁니다.

환경은 Python 3.12.3, NumPy 1.26.4, tifffile 2023.4.12, imagecodecs 2023.1.23입니다.

python -B tools/check_lightroom_cfa_range.py --self-test
python -B tools/check_lightroom_cfa_range.py --dng K3IIIhSLI0000100NR0.dng --pef K3IIIhSLI0000100NR0.PEF --sdk dng-sdk.zip --output cfa-range-new.json
python -B -m unittest discover -s tests -p test_lightroom_cfa_range.py

검증기는 센서 샘플을 파일로 쓰지 않습니다.
