AF PWM 요청의 분기와 정수 변환

PafMotor는 정수 두 개를 PWM 드라이버에 넘겨 설정을 바꿉니다. 어떤 조건에서 레코드를 한 개 또는 두 개 만드는지, 정수가 어떤 계산을 거쳐 16비트 값이 되는지 원본 코드를 실행해 확인했습니다.

이 문서에서

  1. 배경: PWM 설정을 바꾸는 요청
  2. 두 호출점은 같은 라우터에서 갈라집니다
  3. 정수는 843/1000 배율과 16비트 제한을 거칩니다
  4. 패커가 만드는 12바이트 레코드
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • PafMotor 안의 두 호출점이 같은 분배 코드(라우터)를 거칩니다. 스택에 둔 플래그 바이트에 따라 PWM 입력 레코드를 한 개 만드는 함수나 두 개 만드는 함수로 갑니다.
  • 정수 하나는 843을 곱하고 1000으로 나눈 뒤 1을 빼서 16비트로 자릅니다. 두 결과의 합이 65535를 넘으면 둘째 값을 줄입니다. 32비트 곱셈이 넘치는 경우까지 원본 코드로 확인했습니다.
  • 만든 12바이트 레코드는 기존 PWM 설정의 일부만 바꾸는 입력입니다. 바꾸지 않을 칸은 0xff나 0으로 표시합니다.
  • 검사는 모두 합성 입력으로 원본 코드 구간을 따로 실행한 것입니다. 서비스 호출과 레코드 적용 함수 앞에서 멈췄습니다. 레지스터 접근과 실제 PWM 출력은 실행하지 않았습니다. 숫자의 물리 단위는 모릅니다.

확인 원본 코드 실행으로 확인

  • 라우터의 선택값 계산과 세 갈래 분기 (6건)
  • 두 호출점이 라우터에 넘기는 값 (10건)
  • 한 레코드·두 레코드 패킹과 정수 변환 (15건)
  • 세 CPU 조건에서 같은 결과, 총 93회

정적 분석 코드를 읽어 판단

  • 서비스 호출 뒤 두 레코드 패커로 가는 분기
  • 적응형 함수 본문과 그 문턱 값
  • 레코드 병합과 16바이트 레코드 구성

모델 시험 조건으로 정한 것

  • Motor 필드 값, 스택 플래그, 정수 입력
  • 드라이버와 PWM 칸의 RAM 주소
  • CPU는 Unicorn의 Cortex-A7·A15 모델

미확인 확인하지 않은 것

  • 서비스 호출의 결과, 레코드 적용, 레지스터 접근, 인터럽트
  • 843/1000 변환의 물리 단위, 두 값의 실제 역할
  • Motor +0x56·+0x68에 0이 아닌 값을 넣는 코드

배경: PWM 설정을 바꾸는 요청

앞 문서에서 AfMotorDriver가 PWM 객체 두 개를 붙잡고 있고 리셋 요청이 12바이트 레코드로 PWM 설정을 부분 갱신하는 것을 보았습니다. 이 문서는 리셋이 아닌 일반 요청을 다룹니다. PafMotor의 어느 코드가 어떤 정수를 넘기는지, 드라이버가 그 정수를 레코드의 어느 칸에 어떤 값으로 넣는지입니다.

쉽게 말하면

설정표의 일부 칸만 고쳐 쓰는 양식과 비슷합니다. 고칠 칸에는 새 값을 적고 그대로 둘 칸에는 “변경 없음” 표시를 합니다. 드라이버는 이 양식을 받아 기존 설정표와 합칩니다.

PWM은 켜짐과 꺼짐의 시간 비율로 평균 출력을 조절하는 방식입니다(앞 문서의 배경). 이 문서의 16비트 값 두 개가 그런 시간 설정인지는 이름과 구조로 짐작할 뿐이며 확인하지 않았습니다.

기준 RTOS의 적재 주소는 0x52500000이고 주소와 오프셋은 16진수입니다. 표의 입력·출력 값은 10진수입니다.

두 호출점은 같은 라우터에서 갈라집니다

두 호출점 모두 라우터 0x52f0bbd4로 들어갑니다. 스택의 첫 바이트가 1이면 서비스 호출이 먼저 옵니다. 첫 바이트가 0이면 둘째 바이트에 따라 한 레코드 패커로 바로 가거나 서비스를 거칩니다.

f는 두 번째 스택 워드의 최하위 바이트입니다. 라우터는 두 스택 플래그를 바이트로 읽습니다. 첫 바이트가 0일 때 둘째 바이트가 0이 아니면 한 레코드 패커로 바로 갑니다(0x52f0bc34). 둘째 바이트도 0이면 서비스 뒤에 같은 패커가 옵니다. 호출점 A의 서비스 뒤에 오는 0x52f0bc7c는 두 레코드 패커로 분기합니다(정적 분석).

두 호출점이 넘기는 값

호출점 A는 라우터에 3과 래퍼 진입 r2를 넘깁니다. 이 r2는 0x52f0c060의 상수 20000에서 오거나 0x52f0c4e4의 상수·적응형 반환에서 옵니다. 래퍼는 Motor +0x42가 0인지를 라우터 r1로 보냅니다.

호출점 B는 초기 리셋 뒤의 상태에서 두 값을 고릅니다. 아래 표는 그 구간(0x52f0be3c부터)을 실행한 결과입니다.

적응형 함수 (정적 분석)

적응형 함수 0x52f0bd6c의 본문은 실행하지 않고 읽었습니다. 이 함수의 비교 문턱은 래퍼에 넘긴 상태 값과 별개로 Motor +0x43을 다시 읽어 고릅니다. +0x43 = 2이면 2배·4배 문턱이 2000·4000입니다. 3이면 4000·8000입니다. 비교하는 입력은 AF 적응형 문턱의 입력에서 다룹니다.

리셋 쪽 원본 경계는 드라이버 등록과 리셋에 있습니다.

정수는 843/1000 배율과 16비트 제한을 거칩니다

한 레코드 패커는 두 정수를 각각 843배 한 뒤 1000으로 나누고 1을 빼서 16비트로 자릅니다. 두 값의 합이 65535를 넘지 않도록 둘째 값을 줄입니다.

w(x) = s32(843 × x)
t(x) = u16(trunc0(w(x) / 1000) − 1)
a = t(r2)
b = min(t(r3), 65535 − a)
record[+0], record[+2] = a + b, b
  • s32는 곱의 하위 32비트를 부호 있는 값으로 읽는다는 뜻입니다. 곱셈은 32비트에서 넘칠 수 있습니다.
  • 나눗셈은 0 방향으로 자릅니다(trunc0). 원본은 상수 0x10624dd3을 곱하고 부호를 보정하는 방식으로 이 나눗셈을 계산합니다.
  • 1을 뺀 뒤 u16으로 자르므로 입력이 0이면 첫 단계 결과가 65535가 됩니다.
  • 레코드의 +0에는 두 값의 합이, +2에는 둘째 값이 들어갑니다.

입력 2547430과 2547431 사이에서 843 × x의 하위 32비트 부호가 바뀝니다. 다만 이 조합은 최종 합계 제한 때문에 출력만으로는 제한 없는 곱셈과 구별되지 않습니다. 최대·최소 signed 32비트 조합(2147483647, −2147483648)은 두 방식의 결과가 달라 구별됩니다. 위 식으로 11건의 출력을 다시 계산해 모두 일치하는 것을 확인했습니다.

패커가 만드는 12바이트 레코드

한 레코드 패커는 계산한 반워드 두 개를 앞에 쓰고 나머지를 0xff로 채웁니다. 두 레코드 패커는 첫 레코드를 0과 표시값 3으로, 둘째 레코드를 계산값과 표시값 1로 채웁니다.

  • 한 레코드 패커: 선택값이 1이면 드라이버 +0x2c, 그 밖에는 +0x30의 PWM을 고릅니다. 적용 호출 0x53178154 직전에서 멈췄습니다.
  • 두 레코드 패커: 선택값이 1이면 PWM 칸을 +0x30, +0x2c 순으로 넘기고 그 밖에는 반대 순서입니다. 적용 호출 0x53179224 직전에서 멈췄습니다.

이 레코드는 기존 PWM 설정을 부분 갱신하는 입력입니다. 다음 단계의 병합 함수 0x5326ca24에서는 반워드 0과 대부분의 0xff 바이트가 기존 필드를 유지하라는 뜻입니다. 병합한 12바이트를 바탕으로 별도의 16바이트 스택 레코드를 만듭니다. 이 병합 이후의 실행, PWM 레지스터 접근, 인터럽트 전달은 수행하지 않았습니다.

Motor +0x56·+0x68과의 관계

Motor +0x56·+0x68을 읽는 경로는 +0x5a의 문턱을 정합니다. 이 문턱은 상수 20000을 쓰는 분기에 관여합니다. 두 필드를 PWM 반워드로 직접 복사하는 경로와 0이 아닌 값을 넣는 코드는 미확인입니다(Motor 필드의 입력 범위).

한계와 남은 과제

  • 실행 범위: 모든 사례는 서비스 호출과 레코드 적용 호출 앞에서 멈췄습니다. 서비스의 성공이나 레지스터 응답은 넣지 않았습니다.
  • 숫자의 뜻: 843/1000 배율과 1을 빼는 계산의 물리 단위, 두 반워드가 PWM의 어떤 시간 값인지는 모릅니다.
  • 입력의 출처: 적응형 함수의 반환과 Motor 상태 값은 시험에서 정했습니다. 실제 동작 중의 값은 확인하지 않았습니다.
  • 실행하지 않은 것: 카메라, 렌즈, 모터, RTOS 스케줄러를 실행하지 않았습니다.

재현 방법

세 CPU 조건(Cortex-A7 기본, 레지스터·NZCV를 바꾼 Cortex-A7과 Cortex-A15)에서 드라이버와 PWM 칸의 RAM 주소도 바꿔 가며 실행했습니다. 조건마다 패킹 15건, 라우터 6건, 호출점 10건으로 모두 93건이 같은 관측값을 냈습니다.

저장소 루트에서 Python과 Unicorn 2.1.4를 씁니다. 재현기는 입력의 길이·SHA-256과 보조 코드 두 개의 SHA-256을 확인합니다. 원래 관측 전체의 형을 구분하는 해시와 직렬화 해시가 맞아야 공개 JSON을 만듭니다. 출력에는 새 경로를 지정하고 --compare에는 LF 또는 CRLF로 저장된 공개 JSON을 줍니다.

python -B verify_af_pwm_parameters.py decoded.bin --output af-pwm-decoded.json --compare analysis/af-pwm-parameter-checks.json
python -B verify_af_pwm_parameters.py rtos.bin --output af-pwm-rtos.json --compare analysis/af-pwm-parameter-checks.json
python -B -m unittest discover -s tests -p test_af_pwm_parameters.py
