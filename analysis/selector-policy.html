K-3 III · bank 선택 · III-SELECTOR-PUBLIC-21

리소스 선택값과 업데이트 헤더의 기록 조건

원본 생성자가 writer bank를 0으로 만들어도, 외부에서 읽어 온 리소스 선택값 1은 시험한 초기화 경로를 통과해 BOOT의 bank 1 선택으로 이어졌습니다. 별도 실험에서는 표·헤더 쓰기의 반환값이 다음 단계 진입을 결정하는 경로를 재현했습니다. 두 결과 모두 실제 카메라의 선택값 정책을 확정하지는 못합니다.

앞선 분석: RTOS가 쓰는 bank와 BOOT가 읽는 bank

이 문서에서

  1. 같은 bank라는 표현으로 묶으면 안 되는 네 필드
  2. 19: writer bank가 0이어도 입력 선택값 1은 유지된다
  3. 20: 표 기록 성공 뒤에 헤더를 쓰고, 두 단계 성공 뒤에 image 함수로 간다
  4. 헤더의 세 필드는 어느 명령에서 만들어지는가
  5. 오류 알림 이후와 완료 상태 객체는 아직 열린 경로다
  6. 확인하지 못한 부분
  7. 원본 입력으로 다시 검증하기

같은 bank라는 표현으로 묶으면 안 되는 네 필드

대상사용처현재 증거
FwPartition +0x10RTOS writer bank시험한 원본 생성자는 0을 저장
헤더 +0x40BOOT의 표 후보 순서20의 헤더 생성 경로에서 writer bank를 복사
헤더 +0x44 / +0x48표 후보의 LBA원본 함수가 0 / 0xffff를 반환
리소스 레코드 +4각 리소스의 bank 선택전달·소비 경로는 확인했지만 실제 값 결정자는 미확정

헤더 선택값이 writer bank에서 복사되는 관계는 확인했습니다. 그 복사로 각 리소스의 선택값까지 결정되지는 않습니다. 아래 두 실험은 독립된 합성 입력을 사용합니다. 20에서 만든 헤더가 19의 선택값 1을 만들었다는 연결은 없습니다.

근거: 공개 검증 결과 JSON의 evidence.III-SELECTOR-19, evidence.III-SELECTOR-POLICY-20, static_findings.header_policy.

19: writer bank가 0이어도 입력 선택값 1은 유지된다

  1. 합성 FIFO 입력리소스 6의 선택값 1과 구별 가능한 bank 설명자를 공급
  2. M0 원본 저장 명령3ffe6396에서 17,280개 워드를 표 RAM으로 전송
  3. BOOT 원본 초기화시험한 초기화 구간은 표를 지우지 않음
  4. 리소스 6 선택bank 1의 읽기 인수를 준비한 뒤 BL 전에 중단

원본 생성자 52ff52d4가 writer bank를 0으로 만든 상태에서, M0 FIFO helper의 원본 명령을 실행했습니다. 선택값 1은 3ffe6396의 CPU 저장으로 표의 50b733a4에 도달했습니다. BOOT 초기화와 리소스 6 선택 코드를 이어 실행하자 읽기 인수는 (LBA 0x456, 블록 수 2, 목적지 0x44000000)이 됐습니다.

이는 “생성자와 시험한 초기화가 입력 선택값을 반드시 0으로 바꾼다”는 주장에 대한 조건부 반례입니다. 실제 매체에서 1을 관찰한 결과는 아닙니다. FIFO 값과 컨트롤러 상태를 모형으로 공급했고, M0와 BOOT 단계가 같은 RAM을 보도록 연결했습니다. BOOT의 cold 경로에서 수행하는 표 재읽기와 앞선 리소스 처리는 생략했습니다. 이 연결로 실제 코어 간 주소 alias나 캐시 일관성이 입증되지는 않습니다.

원본 M0는 여기서 값을 전달하는 CPU 기록자입니다. 선택값을 처음 결정하는 정책 기록자는 아닙니다. 50b01090의 저장소 읽기 BL 전에 멈췄으므로 payload 읽기·부팅·인증 성공도 확인하지 않았습니다.

근거: JSON의 evidence.III-SELECTOR-19.selector_stores, phases, boot_arguments, native_clear_ranges. native 8개 구간과 추가 정적 3개 구간의 해시를 source_ranges.III-SELECTOR-19에 고정했습니다.

20: 표 기록 성공 뒤에 헤더를 쓰고, 두 단계 성공 뒤에 image 함수로 간다

  1. 표 단계 52ff2060반환값 0이면 52ff2af8에서 오류 진입점으로 분기
  2. 헤더 단계 52ff20d0반환값 0이면 52ff2b14에서 오류 진입점으로 분기
  3. image 함수 52ff21c8두 단계 성공 시 진입. 첫 명령 실행 전에 중단
모형 하위 쓰기 응답원본 호출자가 도달한 곳모형 저장소 상태
표 실패52ff2bf4, 오류 본문 전기록 없음. 헤더 할당·생성도 호출되지 않음
표 성공, 헤더 실패52ff2bf4, 오류 본문 전partition 0/LBA 0에 표만 존재
표·헤더 성공52ff21c8, image 본문 전partition 0/LBA 0의 표와 partition 1/LBA 0의 헤더

완료 호출자와 표·헤더·하위 전송 함수 본문은 원본 명령으로 실행했습니다. 단계 전체를 임의의 반환값으로 대체하지 않았습니다. 다만 allocator, 메모리 복사, 진단·진행률, lock, partition 선택과 최하위 드라이버 쓰기는 모형입니다. 표 쓰기는 0x87개 블록, 헤더 쓰기는 2개 블록을 전달했습니다.

실패 응답에서 매체를 보존하는 동작은 모형이 정한 규칙입니다. 표 성공·헤더 실패 후 표가 남았다는 관찰은 실제 장치의 부분 쓰기, 전원 차단 내성 또는 rollback 보장을 뜻하지 않습니다.

근거: JSON의 evidence.III-SELECTOR-POLICY-20.cases. 원본 실행 15개 구간과 정적 확인 5개 구간은 source_ranges.III-SELECTOR-POLICY-20으로 구분했습니다.

헤더의 세 필드는 어느 명령에서 만들어지는가

헤더 오프셋저장 명령값의 출처시험값
+0x4052ff2140FwPartition +0x10의 1바이트를 32비트로 저장0
+0x4452ff215452ff5304(object, 0)0
+0x4852ff216452ff5304(object, 1)0xffff
위치 함수 52ff5304: index == 0 이면 0, 그 밖에는 0xffff
성공 시 헤더 +40 / +44 / +48: 0 / 0 / 0xffff
BOOT 후보 순서: [1, 2]
첫 읽기 인수: (LBA 0, 0x87 블록, 목적지 0x50b70100)

성공 경로의 헤더를 모형 저장소에서 꺼내 BOOT RAM에 호스트 복사로 넘겼습니다. 원본 BOOT 후보 선택 코드는 첫 위치로 LBA 0을 골랐습니다. 50b00c64의 표 읽기 BL은 실행하지 않았습니다. 실제 재부팅·헤더 읽기·표 재적재가 검증된 것은 아닙니다.

원본 kind 3 처리 조각에는 레지스터를 직접 공급했습니다. 여기서 M0 레코드 길이 0x16804가 working BOOTPARA +0x0c에 반영됐지만, 전체 패키지 dispatch는 실행하지 않았습니다. 헤더 +0x14–+0x3f에는 allocator의 시험 패턴이 남습니다. 이 헤더를 카메라에 쓸 수 있는 완성된 산출물로 제시하지 않습니다.

구별 가능한 시험값을 넣은 32개 리소스 레코드의 +4와 표 전체는 세 실행에서 유지됐습니다. 관찰한 완료·표·헤더 경로에 기록자가 없었다는 뜻이며, 펌웨어 전체에 그런 기록자가 없다는 뜻은 아닙니다.

근거: JSON의 native_location_policy_calls, header_stores, boot_candidate, table_and_all_resource_selectors_unchanged.

오류 알림 이후와 완료 상태 객체는 아직 열린 경로다

다음 내용은 정적 분석입니다. 오류 진입점 52ff2bf4는 52ff29a8에 사유 3을 전달합니다. ctx+0x34가 2와 5 모두 아닐 때 플래그를 참으로 만들고, 52ff3a3c → 52ff399c에서 52ff382c를 통해 메시지 0x2640820d를 전달합니다. 이벤트 호출에는 마스크 0x08 / 0x10 / 0x20과 조건부 0x40이 나타납니다.

확인한 본문에는 표·헤더를 직접 다시 쓰는 보상 호출이 없습니다. 알림 수신자와 간접 호출 이후에 복구가 일어날 가능성은 남아 있습니다. 별도의 성공 후 함수 52ff2970에서는 파생 상태 객체의 +0xf0를 기록하고 +0x100을 증가시키지만, 실제 alias를 모두 해소하지 못했습니다. 두 저장 명령을 리소스 레코드 +4의 기록자로 볼 근거는 아직 없습니다.

BOOT1 wrapper는 쓰기 결과를 보관한 다음 partition 0 복귀를 요청하고, 복귀 반환값을 검사하지 않은 채 보관한 쓰기 결과를 돌려줍니다. 시험에서는 복귀 성공을 공급했습니다. 실제 복귀 실패 뒤 캐시 재동기화 경로를 확인한 결과는 아닙니다.

근거: JSON의 static_findings.error_static_boundary, finalizer_static_boundary와 코드 범위 error_entry / error_bridge / error_notification / finalizer / boot1_wrapper.

확인하지 못한 부분

  • 실제 매체의 리소스 선택값, 비제로 writer bank 생산자, 레코드 +4의 정책 기록자는 찾지 못했습니다.
  • M0와 BOOT의 실제 물리 주소 매핑·캐시 일관성·전체 reset 경로를 재현하지 않았습니다. Cortex-A7 에뮬레이터에서 호환 명령을 실행했으며, Cortex-M0 시스템·주변장치 모형은 아닙니다.
  • 실제 저장소의 부분 쓰기·원자성·rollback, Boot ROM 인증, 수정 펌웨어의 정상 부팅은 검증하지 않았습니다.
  • 19의 선택값 1과 20의 성공 헤더는 별도 시험 입력입니다. 두 증거를 하나의 실제 업데이트·부팅 기록으로 합치면 안 됩니다.

원본 입력으로 다시 검증하기

저장소 루트에서 원본 decoded carrier를 입력합니다. Python과 Unicorn 2.1.4 환경에서 검증했습니다. 새 검증기는 이미 공개된 verify_update_bank_selection.py만 프로젝트 helper로 사용합니다. 이 helper의 줄 끝을 LF로 통일한 뒤 고정 SHA-256과 비교하고, 검사한 그 바이트를 직접 실행합니다. helper를 import하거나 .pyc를 읽지 않습니다. Unicorn과 표준 라이브러리는 별도의 실행 환경이며 소스 해시 고정 대상이 아닙니다.

python verify_selector_policy.py decoded.bin --output selector-policy-result.json
python -m unittest discover -s tests -p test_selector_policy.py -v

전체 입력과 RTOS·BOOT·M0·파라미터 해시, 증거 범위 31개를 확인한 뒤 두 증거를 실행합니다. 출력 경로가 이미 존재하면 거부하며, Python -O도 허용하지 않습니다. 보호 시험은 잘못된 입력, 변경된 helper, CRLF, 오래된 unchecked bytecode, 기존 파일·입력 hardlink·helper 출력 alias, dangling symlink를 확인합니다.
