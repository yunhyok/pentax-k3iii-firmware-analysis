펌웨어 업데이트 과정 · bank 선택값의 두 실험

리소스 선택값의 전달 경로와 업데이트 헤더의 기록 조건

BOOT가 어느 bank에서 프로그램을 읽을지는 파티션 표의 선택값이 정합니다. 그 값이 어디서 와서 어떻게 전달되는지, 업데이트 코드는 표와 헤더를 어떤 조건에서 기록하는지 원본 코드로 두 실험을 했습니다.

이 문서에서

  1. 배경: 이름이 비슷한 네 가지 선택값
  2. M0가 받아 온 선택값 1은 BOOT까지 그대로 갑니다
  3. 표와 헤더를 모두 써야 다음 단계로 갑니다
  4. 헤더의 세 필드는 정해진 규칙으로 만들어집니다
  5. 오류 알림 뒤와 완료 상태 객체는 코드를 읽어서만 보았습니다
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • RTOS의 쓰기 객체가 bank 0을 쓰도록 만들어져 있어도, M0가 저장소 쪽에서 받아 온 선택값 1은 M0와 BOOT의 원본 초기화를 거치며 지워지지 않았습니다. BOOT는 그 값대로 bank 1의 설명자로 읽기 요청을 준비했습니다.
  • 이 실험은 “선택값은 반드시 0으로 초기화된다”는 가정의 반례입니다. 선택값 1은 시험용으로 넣은 값입니다. 실제 저장소에서 관측한 값이 아닙니다.
  • 업데이트 완료 코드는 파티션 표 쓰기와 부트 헤더 쓰기가 모두 성공해야 다음 단계로 갑니다. 하나라도 실패하면 오류 처리로 갑니다. 하위 저장 장치 쓰기의 성공·실패는 시험용으로 정한 값입니다.
  • 만들어진 헤더의 표 위치 필드는 늘 0과 0xffff였습니다. 헤더의 순서 필드는 쓰기 bank 값을 그대로 복사했습니다. 리소스 레코드의 선택값을 바꾸는 코드는 이 경로에 없었습니다.
  • 두 실험은 서로 다른 시험 입력을 씁니다. 카메라에서 실행한 것이 아니며 실제 선택값 정책, 부분 쓰기와 복구, 인증은 확인하지 못했습니다.

확인 원본 코드 실행으로 확인

  • M0 FIFO 읽기 코드가 선택값 1을 표 RAM에 저장
  • BOOT 초기화가 표를 지우지 않고 bank 1을 고름
  • 표·헤더 쓰기 결과에 따른 세 갈래
  • 헤더 세 필드를 만드는 명령과 값

정적 분석 코드를 읽어 판단

  • 오류 진입점 뒤의 알림 경로
  • 성공 뒤 상태 객체 갱신 함수
  • BOOT1 wrapper의 복귀 반환값 처리

모델 시험용으로 정한 값

  • FIFO로 들어오는 표 내용과 선택값 1
  • M0와 BOOT가 같은 RAM을 보게 한 연결
  • 하위 쓰기의 성공·실패와 저장소 모델
  • 메모리 할당·복사, 진단, lock, partition 선택

미확인 확인하지 않은 것

  • 실제 저장소의 선택값, 0이 아닌 쓰기 bank를 만드는 코드
  • M0와 BOOT의 실제 주소 대응과 캐시 일관성
  • 부분 쓰기·원자성·rollback, Boot ROM 인증
  • 수정한 펌웨어의 정상 부팅

배경: 이름이 비슷한 네 가지 선택값

내장 저장소의 파티션 표는 리소스(BOOT, RTOS, INITFS 등) 32개의 위치를 레코드로 적습니다. 레코드마다 설명자 자리가 두 개 있으며 레코드의 선택값이 그중 하나를 고릅니다. 이 자리를 bank라고 부릅니다. 업데이트 때 RTOS가 쓰는 bank와 다음 부팅에서 BOOT가 읽는 bank가 서로 다른 값으로 정해진다는 것은 쓰기 bank와 BOOT 선택 문서에서 확인했습니다.

쉽게 말하면

같은 프로그램을 넣을 칸이 두 개 있습니다. “어느 칸을 읽을지”를 적은 쪽지가 표 안에 있습니다. 이 문서는 그 쪽지의 값이 부팅 초기에 바뀌지 않고 그대로 전달되는지, 업데이트가 표와 헤더를 어떤 순서와 조건으로 다시 쓰는지 본 기록입니다.

같은 bank로 묶으면 안 되는 네 필드

헤더의 순서 필드가 쓰기 bank에서 복사된다는 것은 확인했습니다. 그렇다고 리소스마다의 선택값이 그 복사로 정해지지는 않습니다. 아래 두 실험은 서로 독립된 시험 입력을 씁니다. 두 번째 실험에서 만든 헤더가 첫 번째 실험의 선택값 1과 이어지지 않습니다.

근거: 검증 결과 JSON의 evidence.III-SELECTOR-19, evidence.III-SELECTOR-POLICY-20, static_findings.header_policy. JSON의 표식은 III-SELECTOR-PUBLIC-21입니다. 아래에서 첫 실험은 19, 두 번째 실험은 20으로 부릅니다.

M0가 받아 온 선택값 1은 BOOT까지 그대로 갑니다

쓰기 bank가 0이어도, M0가 읽어 들인 선택값 1은 원본 초기화를 거친 뒤 BOOT의 bank 1 선택으로 이어졌습니다.

원본 생성자가 쓰기 bank를 0으로 만든 상태에서 M0의 FIFO 읽기 코드를 실행했습니다. 이 코드는 17,280개 워드를 표 RAM에 옮겼습니다. 리소스 6의 선택값 1도 이 저장으로 표에 들어갔습니다. 이어 BOOT 초기화와 리소스 6 선택 코드를 실행하자 읽기 인수는 LBA 0x456, 블록 수 2, 목적지 0x44000000이 되었습니다. 시험 표에서 bank 1 설명자에 넣어 둔 값입니다.

시험 조건

FIFO 값과 컨트롤러 상태는 시험용으로 넣었습니다. M0와 BOOT 단계가 같은 RAM 주소를 보도록 재현 도구가 이었습니다. 이 연결이 실제 코어 사이의 주소 대응이나 캐시 일관성을 증명하지는 않습니다. BOOT의 cold 경로에서 하는 표 재읽기와 그보다 먼저 처리하는 리소스는 건너뛰었습니다. Cortex-A7 에뮬레이터에서 호환되는 M0 명령을 실행했을 뿐 Cortex-M0 시스템·주변장치 모델은 아닙니다.

M0 코드는 여기서 값을 옮기는 역할만 합니다. 선택값을 처음 정하는 코드는 아닙니다. BOOT의 저장소 읽기 호출 전에 멈췄으므로 payload 읽기, 부팅, 인증 성공도 확인하지 않았습니다.

표와 헤더를 모두 써야 다음 단계로 갑니다

업데이트 완료 코드는 파티션 표를 먼저 씁니다. 그 결과가 성공일 때만 부트 헤더를 씁니다. 두 쓰기가 모두 성공해야 이미지 단계로 넘어갑니다.

하위 쓰기 응답(모델)별로 원본 코드가 간 곳
하위 쓰기 응답원본 코드가 닿은 곳저장소 모델의 상태
표 실패오류 진입점 0x52ff2bf4, 본문 전기록 없음. 헤더 할당·생성도 호출되지 않음
표 성공, 헤더 실패오류 진입점 0x52ff2bf4, 본문 전partition 0 / LBA 0에 표만 있음
표·헤더 성공이미지 함수 0x52ff21c8, 본문 전partition 0 / LBA 0의 표와 partition 1 / LBA 0의 헤더

완료 호출자, 표·헤더 단계, 하위 전송 함수의 본문은 원본 명령으로 실행했습니다. 단계 전체를 임의의 반환값으로 바꾸지는 않았습니다. 대체한 것은 메모리 할당과 복사, 진단·진행률, lock, partition 선택, 맨 아래 드라이버의 쓰기입니다.

주의

실패 응답에서 저장소 내용을 그대로 두는 것은 모델이 정한 규칙입니다. “표 성공·헤더 실패 뒤 표가 남았다”는 관측을 실제 장치의 부분 쓰기, 전원 차단 내성, rollback 보장으로 읽으면 안 됩니다.

분기 명령과 코드 구간
  • 표 단계 0x52ff2060이 0을 돌려주면 0x52ff2af8에서 오류 진입점으로 분기합니다. 헤더 단계 0x52ff20d0이 0을 돌려주면 0x52ff2b14에서 분기합니다. 둘 다 0이 아니면 0x52ff2b28의 BL로 0x52ff21c8에 갑니다.
  • 쓰기 요청: 표 0x87블록(69,120바이트, 원본 주소 0x50b70100), 헤더 2블록(1,024바이트).
  • 명령 수(완료 경로): 표 실패 123, 헤더 실패 320, 둘 다 성공 317. 생성자 11, kind 3 준비 6, BOOT 후보 선택 36.
  • 해시를 고정한 구간 20개 중 15개는 원본으로 실행했고 5개는 읽어서만 확인했습니다(source_ranges.III-SELECTOR-POLICY-20, evidence.III-SELECTOR-POLICY-20.cases).

헤더의 세 필드는 정해진 규칙으로 만들어집니다

순서 필드는 쓰기 bank를 그대로 복사합니다. 두 위치 필드는 index에 따라 0 또는 0xffff로 정해집니다.

성공 경로에서 만든 헤더를 저장소 모델에서 꺼내 BOOT RAM에 복사해 넘겼습니다. 원본 BOOT 후보 선택 코드는 첫 위치로 LBA 0을 골랐습니다. 0x50b00c64의 표 읽기 BL은 실행하지 않았습니다. 실제 재부팅, 헤더 읽기, 표 다시 읽기는 검증 범위 밖입니다.

원본 kind 3 처리 조각에는 레지스터를 직접 넣어 주었습니다. 여기서 M0 레코드 길이 0x16804(92,164바이트)가 working BOOTPARA +0x0c에 반영됐지만 전체 패키지 처리는 실행하지 않았습니다. 헤더 +0x14–+0x3f에는 할당 모델의 시험 패턴이 남아 있으므로 이 헤더는 카메라에 쓸 수 있는 산출물이 아닙니다.

구별 가능한 시험값을 넣은 리소스 레코드 32개의 +4와 표 전체는 세 실행에서 그대로였습니다. 관찰한 완료·표·헤더 경로에 선택값을 바꾸는 코드가 없었다는 관측입니다. 펌웨어 전체에도 없다고 결론 내리지는 않습니다.

근거: JSON의 native_location_policy_calls, header_stores, boot_candidate, table_and_all_resource_selectors_unchanged.

오류 알림 뒤와 완료 상태 객체는 코드를 읽어서만 보았습니다

정적 분석 오류 진입점은 사유 3으로 알림을 보냅니다. 확인한 본문 안에는 표와 헤더를 다시 쓰는 보상 호출이 없었습니다.

  • 오류 진입점은 오류 브리지에 사유 3을 넘깁니다. 모드 값(ctx+0x34)이 2도 5도 아니면 알림 플래그를 켜고 메시지 0x2640820d를 보냅니다.
  • 알림 수신자와 간접 호출 뒤에 복구가 일어날 가능성은 남아 있습니다.
  • 성공 뒤 함수 0x52ff2970은 파생 상태 객체의 +0xf0에 쓰고 +0x100을 1 늘립니다. 객체의 다른 이름(alias)을 모두 풀지 못했습니다. 두 저장을 리소스 레코드 +4의 기록자로 볼 근거는 아직 없습니다.
  • BOOT1 wrapper는 쓰기 결과를 보관한 뒤 partition 0 복귀를 요청합니다. 복귀의 반환값은 검사하지 않고 보관한 쓰기 결과를 돌려줍니다. 시험에서는 복귀 성공을 넣었습니다. 실제 복귀가 실패한 뒤 캐시를 다시 맞추는 경로는 확인하지 않았습니다.
오류·알림 경로의 주소
  • 오류 진입점 52ff2bf4 → 52ff29a8(사유 3) → 52ff3a3c → 52ff399c → 52ff382c를 거쳐 메시지 0x2640820d 전달.
  • 이벤트 호출 마스크 0x08 / 0x10 / 0x20, 조건부 0x40.
  • JSON의 static_findings.error_static_boundary, finalizer_static_boundary와 코드 범위 error_entry / error_bridge / error_notification / finalizer / boot1_wrapper.

한계와 남은 과제

  • 실제 저장소의 리소스 선택값, 0이 아닌 쓰기 bank를 만드는 코드, 레코드 +4를 정하는 코드는 찾지 못했습니다.
  • M0와 BOOT의 실제 물리 주소 대응, 캐시 일관성, 전체 reset 경로는 재현하지 않았습니다.
  • 실제 저장소의 부분 쓰기·원자성·rollback, Boot ROM 인증, 수정 펌웨어의 정상 부팅은 검증하지 않았습니다.
  • 실험 19의 선택값 1과 실험 20의 성공 헤더는 서로 다른 시험 입력입니다. 두 결과를 하나의 실제 업데이트·부팅 기록으로 합치면 안 됩니다.

재현 방법

저장소 루트에서 원본 decoded 스트림을 넣습니다. Python과 Unicorn 2.1.4 환경에서 검증했습니다.

python verify_selector_policy.py decoded.bin --output selector-policy-result.json
python -m unittest discover -s tests -p test_selector_policy.py -v
  • 전체 입력과 RTOS·BOOT·M0·파라미터 해시, 근거 구간 31개를 확인한 뒤 두 실험을 실행합니다.
  • 프로젝트 안에서 다시 쓰는 코드는 공개된 verify_update_bank_selection.py 하나뿐입니다. 줄 끝을 LF로 맞춘 뒤 고정 SHA-256과 비교한 다음 검사한 그 바이트를 직접 실행합니다. import하거나 .pyc를 읽지 않습니다. Unicorn과 표준 라이브러리는 해시 고정 대상이 아닙니다.
  • 출력 경로가 이미 있으면 거부하고 Python -O 실행도 거부합니다. 보호 시험은 잘못된 입력, 바뀐 helper, CRLF, 검사하지 않은 오래된 bytecode, 기존 파일·입력 hardlink·helper 출력 alias, 대상이 없는 symlink를 확인합니다.
