펌웨어 재구축 안내

제조사의 소스 코드는 공개되어 있지 않습니다. 이 주제는 펌웨어의 일부를 직접 다시 만들어 원본과 똑같이 동작하는 코드로 바꿔 넣을 수 있는지 가장 작은 단위부터 시험하고, 다시 만든 펌웨어가 부팅하려면 지켜야 할 시작 과정의 조건을 원본 코드로 확인합니다.

핵심 요약

  • 이 주제는 두 갈래입니다. 한 갈래는 “원본과 같은 코드를 직접 만들 수 있는가 → 원래 자리에 넣어도 같은가 → 파일 크기를 원본에 가깝게 되돌릴 수 있는가”의 세 단계입니다.
  • 다른 갈래는 다시 만든 펌웨어가 부팅하려면 지켜야 할 시작 과정의 전제입니다. 원본 할당기가 task 표와 첫 task 스택, 이름 registry를 만드는 과정을 재현했습니다. 초기 메모리를 읽어 고쳐 쓰는(RMW) 칸 일부는 최종값이 초기 내용과 무관함을 수식 모형으로 증명했습니다.
  • 모든 확인은 PC에서 원본 기계어를 에뮬레이터로 실행하거나, 파일 바이트를 대조하거나, 분석자가 옮긴 모형을 solver로 검사한 것입니다. 카메라에서 실행한 것은 하나도 없습니다.
  • 함수 하나를 원래 자리에 넣고 패키지를 다시 만들어 원본과 같다는 것까지 확인했습니다. 시작 과정은 구간별로 끊어 재현했을 뿐입니다. 카메라 수용과 부팅은 아직 남은 과제입니다.

한눈에 보기

위 줄은 함수를 다시 만들어 넣는 세 단계, 아래 줄은 부팅에 필요한 시작 과정의 전제를 재현·증명한 네 문서입니다. 두 갈래가 만나는 카메라 통합은 아직 하지 않았습니다.

배경 지식

이 주제의 문서를 읽는 데 필요한 개념만 짧게 정리합니다.

leaf 함수
다른 함수를 부르지 않고 계산만 하는 말단 함수입니다. 입력과 출력이 분명해 원본과 새 코드를 나란히 실행해 비교하기 쉽습니다.
Q13 고정소수점
실수 1.0을 정수 8,192(2의 13제곱)로 나타내는 표기입니다. 색 변환 행렬 값이 이 형식이라 곱한 뒤 반올림하고 13비트만큼 내립니다.
SAD·SSD
두 신호의 차이를 재는 기본 연산입니다. 차이의 절댓값 합(SAD)과 제곱 합(SSD)으로, 위상차 AF의 상관 연산에 쓰입니다. 자세한 설명은 명령·셸 안내에 있습니다.
NEON
ARM의 SIMD 확장입니다. 여러 데이터를 한 명령으로 처리해 속도를 높입니다. 원본 SAD·SSD 함수가 이 명령을 씁니다. Arm NEON 소개
압축 블록과 저장(stored) 블록
펌웨어는 되돌아 참조하는 복사 명령으로 압축됩니다. “그대로 담은” 블록을 저장 블록이라 합니다. 바뀐 부분만 저장 블록으로 다시 넣으면 나머지 원본 압축을 보존할 수 있습니다.
체크섬
파일 바이트를 32비트로 더한 검사 값입니다. 내용이 바뀌면 다시 계산해 맞춰야 합니다. 암호학적 서명이 아닙니다.
메모리 할당기와 task 스택
RTOS는 켜질 때 넓은 RAM을 2,048바이트 페이지로 나누고 필요한 곳에 내줍니다. task마다 상태 레코드와 실행용 스택 버퍼가 필요해서, 시작 과정 초기에 이 할당이 일어납니다.
RMW와 초기 메모리
read-modify-write. 값을 읽어 일부 비트만 바꿔 다시 쓰는 동작입니다. 아직 아무도 쓰지 않은 메모리에 하면 켜질 때 남은 값이 섞일 수 있습니다. 다시 만든 펌웨어가 매번 같은 상태로 시작하려면 그런 칸의 최종값이 초기 내용과 무관해야 합니다.
수동 모형과 Z3
분석자가 원본 명령 몇 개의 의미를 수식으로 옮긴 것을 수동 모형이라 부릅니다. Z3 solver에게 “결과가 달라지는 초기값이 있는가”를 물어 unsat이 나오면 그 모형과 전제 안에서는 그런 값이 없습니다. 모형이 원본을 바르게 옮겼는지는 사람의 검토에 기댑니다.

읽는 순서

함수를 다시 만들어 넣는 세 단계를 먼저 읽습니다. 그다음 시작 과정의 재현 두 편을 읽은 뒤 마지막으로 초기 메모리 증명 두 편을 봅니다.

  • 1단계

    수치 함수 C 재구현

    직접 만든 코드가 원본과 똑같이 계산하는가?

    SAD·SSD와 Q13 행렬 곱 두 함수를 C로 작성해, 합성 입력 237개에서 원본 기계어와 출력이 모두 같았습니다.

  • 2단계

    함수 배치·재패키징

    그 함수를 원래 자리에 넣고 패키지를 다시 만들어도 같은가?

    원래 주소와 실제 색 행렬 준비 호출자에서 출력·레지스터가 같았습니다. 원본의 헤더·체크섬 검사도 통과했습니다.

  • 3단계

    압축 블록 보존 재패키징

    파일을 원본에 가까운 크기로 줄일 수 있는가?

    블록 3,202개 중 4개만 바꿔 35,136,788바이트로 만들었습니다. 독립 디코더로 다시 풀어도 결과가 같았습니다.

  • 시작 과정 1

    설정에서 첫 task 스택까지

    원본 할당기는 시작할 때 메모리를 어떻게 나눠 주는가?

    설정 300개에서 task 표 188페이지와 첫 스택 13페이지가 나왔습니다. 초기 메모리 네 패턴에서 결과가 같았습니다. 실행은 MPIDR 읽기 직전에서 멈춥니다.

  • 시작 과정 2

    이름 registry 할당과 조회

    할당된 포인터가 0 채우기와 이름 조회까지 그대로 전달되는가?

    원본 calloc이 내준 1,200바이트를 원본 코드가 0으로 채워 저장했습니다. InitTask 조회는 hash 300개를 읽고 일치 없이 끝났습니다.

  • 초기 메모리 1

    RMW 8바이트의 수동 모형 검증

    빈 블록 길이 칸의 최종값은 초기 RAM과 무관한가?

    원본 명령 15개의 모형에서 두 워드가 초기 64비트와 관계없이 (count<<2)|1과 0이 됨을 증명했습니다. 중간 쓰기와 실제 읽기는 남습니다.

  • 초기 메모리 2

    RMW 48바이트 분류와 4바이트 증명

    나머지 48바이트는 어떤 칸이며 어디까지 증명했는가?

    48바이트를 여섯 레코드로 분류했습니다. 할당 끝 칸 4바이트의 최종값이 초기 32비트와 무관함을 증명했습니다. 나머지 44바이트는 증명 밖입니다.
