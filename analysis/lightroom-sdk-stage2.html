K-3 III DNG의 Adobe SDK Stage 2 실행

공개 DNG SDK를 직접 실행해, 블랙·화이트 레벨로 센서 값을 정규화하는 첫 단계의 결과를 꺼냈습니다. 수식으로만 계산했던 값이 실제 SDK 코드에서도 그대로 나오는지 확인하는 실험입니다.

이 문서에서

  1. 배경: DNG SDK의 Stage
  2. SDK에서 읽은 두 배열
  3. 모든 Stage 2 값이 정수 계산과 같았습니다
  4. 호출 순서와 빌드 조건
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 공개 Adobe DNG SDK 1.7.1 Build 2768을 PC에서 빌드했습니다. 고정한 K-3 III 변환 DNG 한 개로 Stage 1과 Stage 2까지 실행했습니다.
  • SDK가 만든 Stage 2 값 25,891,840개가 정수 계산과 모두 일치했습니다. 그중 8,530개가 uint16 최댓값 65,535에 이르렀습니다.
  • 빈 폴더에서 오브젝트 276개를 새로 빌드해 다시 실행해도 두 배열과 실행 로그가 같았습니다.
  • 실행 범위는 Stage 2까지입니다. Stage 3 이후, SDK 렌더 단계, Lightroom과 Converter 내부, PEF를 직접 여는 경로는 다루지 않습니다.

확인 공개 SDK를 실행해 관측

  • SDK 1.7.1 Build 2768 원본 소스로 만든 하네스의 Stage 1·2 배열
  • Stage 2 전 샘플과 정수 계산의 일치(불일치 0)
  • 새 빌드와 처음 실행의 배열·로그 일치

모델 연구자가 정한 조건

  • XMP, baseline libjpeg, SDK AVX를 끈 Zig 0.15.2 빌드
  • 입력은 보존한 첫 변환 DNG 한 개

미확인 이 실행으로 알 수 없는 것

  • Converter 18.7과 Lightroom이 PEF에 쓰는 화이트 레벨
  • 디모자이크와 최종 렌더
  • 공식 Windows 예제 빌드에서의 결과

배경: DNG SDK의 Stage

Adobe는 DNG 파일을 읽고 쓰는 참조 구현을 DNG SDK로 공개합니다. SDK에 들어 있는 dng_validate 예제는 처리 중간의 배열을 Stage 1, 2, 3으로 나눠 꺼낼 수 있습니다.

SDK가 RAW를 다루는 단계
단계내용이 주제에서
Stage 1파일에 저장된 CFA를 압축만 풀어 읽은 배열이 문서에서 실행
Stage 2ActiveArea만 남기고 블랙을 뺀 뒤 0~65,535로 정규화한 배열이 문서에서 실행
Stage 3디모자이크한 카메라 R·G·B 세 평면SDK Stage 3에서 실행
렌더화이트밸런스, 색 프로파일, 톤, 출력 색공간 적용실행하지 않음

Stage 2의 계산식은 CFA 범위와 기본 크롭에서 SDK 소스를 읽어 Python으로 옮겨 두었습니다. 이 문서는 그 계산을 실제 SDK 실행 결과와 맞춰 봅니다.

SDK에서 읽은 두 배열

Stage 2 배열은 ActiveArea 크기인 4160×6224입니다. 값은 69부터 65,535까지이며 0은 없습니다.

65,535가 된 8,530개는 저장 배열에서 WhiteLevel을 넘은 활성 샘플 8,529개와 WhiteLevel과 같은 1개입니다. 이 개수는 수식 계산의 예측과 같습니다. 배열별 해시와 관측치는 observation.json에 기록했습니다.

호출 순서와 빌드 조건

SDK 원본 함수를 기본 설정으로 차례대로 불렀습니다. 빌드에서는 이 DNG를 읽는 데 쓰이지 않는 기능만 껐습니다.

  1. 파싱 기본 dng_host로 DNG를 파싱합니다.
  2. Stage 1 ReadStage1Image, ValidateRawImageDigest, SynchronizeMetadata를 부릅니다. RAW 타일 425개는 모두 JPEG SOF3(무손실)이며 SDK의 무손실 JPEG 디코더가 풉니다.
  3. Stage 2 BuildStage2Image 안의 DoBuildStage2가 ActiveArea 크기의 ttShort 배열을 만든 뒤 원본 Linearize를 실행합니다.
  4. 종료 Stage 3 호출 전에 멈춥니다. 기본 블랙 보존은 꺼져 있었으며 Stage 2 직후 Stage3BlackLevel()은 0이었습니다.

공식 Windows 예제 프로젝트는 이 환경에서 ClangCL이 없다는 오류(MSB8020)로 빌드되지 않았습니다. 그래서 Zig 0.15.2(clang 20.1.2)로 하네스를 빌드했습니다.

한계와 남은 과제

  • Stage 2까지: 이 실행이 확인한 범위는 변환 DNG 한 개의 디모자이크 전 처리입니다. 이 배열을 입력으로 한 보간은 SDK Stage 3의 Bayer 보간과 전체 카메라 채널 값에서 이어서 확인했습니다.
  • 제품 내부와 다름: Adobe Converter 18.7과 Lightroom이 네이티브 PEF에 쓰는 화이트 레벨, 디모자이크, 최종 렌더는 확인하지 않았습니다. 변환 DNG의 출처는 K-3 III PEF의 As Shot 중립값, 원본과의 대조는 원본 PEF와 DNG의 저장 CFA 대조에 있습니다.
  • 기능을 줄인 빌드: XMP 등을 끈 하네스로 실행했습니다. 공식 예제 빌드에서 같은 결과가 나오는지는 확인하지 못했습니다.

재현 방법

Windows x64에서 Python 3.12와 NumPy 1.26.4를 씁니다. 고정한 첫 변환 K3IIIhSLI0000100NR0.dng, Adobe SDK 1.7.1 Build 2768 ZIP, Zig 0.15.2 Windows x64 전체 배포판의 zig.exe를 직접 지정합니다. 다시 변환한 DNG처럼 해시가 다르면 검사가 멈춥니다. Zig는 배포판 안의 인접 라이브러리가 있어야 실행됩니다. 검사는 실행 파일 해시만 확인합니다.

python -B tools/check_lightroom_sdk_stage2.py --sdk dng-sdk.zip --dng K3IIIhSLI0000100NR0.dng --zig C:\path\to\zig.exe --work sdk-stage2-run
python -B -m unittest discover -s tests -p test_lightroom_sdk_stage2.py
  1. 입력 확인 이미 있는 작업 경로는 받지 않습니다. 입력의 크기와 SHA-256을 확인합니다.
  2. 빌드 새 작업 폴더에서만 SDK를 풀고 빌드합니다. 실행하는 동안 다른 프로세스에서 이 폴더의 파일을 바꾸지 마십시오.
  3. 대조와 기록 해시, 통계, 호출 로그, 정수 계산과의 전수 대조를 모두 통과하면 result.json을 씁니다. DNG 사본, 배열 덤프, SDK 소스, 빌드 캐시는 작업 폴더에 남습니다.

이 도구로 빈 작업 폴더에서 오브젝트 276개를 다시 빌드했습니다. 새 실행 파일의 SHA-256은 처음 실험과 달랐습니다. 그래도 두 배열과 실행 로그는 처음 실험과 같았습니다. 기록은 최초 관측 기록과 새 빌드와 재실행 기록에 있습니다.
