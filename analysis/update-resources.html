이번에 확인한 범위

업데이트 파일명 생성 이후에 프로젝트 식별값, 펌웨어 종류, 버전, 두 체크섬을 검사하는 경로를 찾았다. ICONBIN은 패키지의 kind 4 / index 4 레코드에서 저장소 인덱스 4로 전달되고 런타임 로더가 같은 인덱스를 리소스 슬롯 5의 버퍼로 읽는다. 이 연결은 원본 ARM 명령과 패키지 바이트로 검증했다. 실제 카메라에서 업데이트나 적재가 성공하는지는 실행하지 않았다. 판정식·호출 관계 · 원본 범위 해시와 전이

서명에 관한 근거는 구성 요소별로 구분한다. 이번 RTOS 업데이트 경로에서 확인한 무결성 검사는 32비트 덧셈 체크섬이다. LINUX 레코드의 Stubby에서는 공개 소스의 RSA 옵션 비활성 분기에 대응하는 출력 경로를 확인했다. 이 결과만으로 전체 업데이트나 다른 부트 단계에 인증 검사가 없다고 판단할 수 없다.

파일 선택과 프로젝트 검사

파일명 생성자 0x52ff32ac가 만든 경로는 getter 0x52ff3474에서 반환된다. 선택자 0x52fef240의 종류 값 2 분기는 이 getter를 사용한다. 파일 정보 조회가 성공하면 상태 객체의 +0x40에 경로, +0x44에 크기 값을 보관하고 0x52fee900이 0x52ff7160을 호출해 얻은 입력 버퍼를 +0x48에 저장한다. 하위 파일 로더와 파일 시스템 가상 함수의 실제 대상은 아직 연결하지 못했다. update.relationships

파일명에 쓰는 숫자와 패키지에서 검사하는 식별값은 서로 다른 필드다. 파일명 getter 0x5310b748은 객체 +0x18을 읽지만 검증용 getter 0x5310b7f0은 같은 객체의 +8을 읽는다. 후자는 진단 문자열에서 project number로 부른다. 원본 패키지의 프로젝트 값은 0x246이다. 이를 파일명의 233이나 특정 하드웨어 칩 번호와 동일시하지 않았다. getter·문자열 범위

아래 표에서 B는 입력 시작 주소, N은 입력 길이, F는 B+N−0x18이다. 종류 값 2 경로가 넘기는 기대 프로젝트 값은 검증 객체 +0x18, 기대 펌웨어 종류는 +0x1c에 저장된다. 0x52ff4d80은 다음 조건 중 하나라도 맞지 않으면 0을 반환한다.

체크섬과 하드웨어 변환

외부 체크섬 함수 0x52ff4d08은 little-endian 32비트 단어를 더해 하위 32비트가 0인지 검사한다. 단어 수는 ceil(N/4)이며 F의 +0x14가 0xffffffff이거나 N이 0이면 합계를 검사하지 않고 1을 반환한다. 4의 배수가 아닌 길이는 논리적 끝을 넘는 패딩 바이트까지 읽는다. 이 함수의 분기만 확인한 것이므로 상위 경로가 길이 0이나 불완전한 헤더를 허용한다고 해석하지 않는다.

내부 체크섬 함수 0x52ff4ee8은 출력의 마지막 4바이트를 먼저 읽는다. 이 값이 0 또는 0xffffffff이면 검사를 생략한다. 그 외에는 floor(N/4)개 단어의 합계가 0이어야 한다. 0xfffffffe는 생략 값이 아니다. 원본의 외부·내부 합계는 모두 0이고 마지막 체크섬 값은 각각 0xb00900ab, 0x6b7e72ff이므로 두 생략 조건에 해당하지 않는다. 원본 ARM 함수를 합성 메모리에서 실행한 114개 검사가 계산식과 일치했다. 검사 결과 · 검증 도구

변환 래퍼에서 하위 드라이버 0x5327f04c까지 연결했다. 설정 함수 0x53339b5c는 MMIO 0x1b030000의 +0x18에 입력 시작 주소, +0x1c에 입력 끝 주소, +0x20에 출력 주소를 쓴다. 선택한 호출자는 네 번째 값을 0으로 전달하며 이 값은 +0x24에 기록된다. 이 레지스터의 하드웨어 의미는 미확정이다. 시작 함수 0x533399d8은 +4의 bit 0을 설정하고 DSB를 실행한다. 오류 조회는 +0x38의 하위 16비트를 읽는다.

성공 시 0x53339e00이 RAM 0x547c304c의 결과 필드를 복사하고 호출자는 결과의 +0xc를 출력 길이로 전달한다. CPU의 설정·시작·결과 처리까지 확인했다. 내부 압축·변환 알고리즘이나 인증 동작은 아직 특정하지 못했다. hardware_transform

버전 비교와 파일 끝의 256바이트

버전 검사 함수 0x52feef34는 종류 값 2·3·4에서 헤더의 세 버전 쌍을 각각 (high<<16)|low로 합친다. 현재 버전 getter 0x52ed7a28, 0x52ed7a6c, 0x52ed7ab0의 반환값보다 하나라도 작으면 실패한다. 분기 0x52fef024, 0x52fef038, 0x52fef04c는 unsigned 비교이며 같은 값은 허용한다. 이번에 확인한 상위 컨트롤러는 종류 값 2일 때만 이 검사를 호출한다. 모든 업데이트 진입점에 공통된 하향 버전 방지 정책인지는 미확정이다. 버전 조건과 호출 범위

첫 버전 쌍을 읽는 0x52ff4b3c은 헤더 +0x3c의 개수를 사용한다. 개수가 0이면 헤더 +0x38부터 두 BE16 값을 읽는다. 개수가 있으면 B+N−0x18−개수×0x80에서 128바이트 레코드를 순회해 첫 단어의 selector가 일치하는 항목을 찾고 해당 항목 +8 / +0xa의 BE16 값을 읽는다.

저장소 인덱스 4에서 리소스 슬롯 5로

순회 함수 0x52ff29c8은 레코드 헤더 +8의 kind, +0xa의 index, +0xc의 길이를 읽고 +0x10을 payload로 사용한다. kind 4의 테이블 항목 0x52ff2a4c는 0x52ff2b68로 연결된다. 인덱스가 레이아웃 개수보다 작을 때 0x52ff225c를 거쳐 저장소 기록 함수 0x52ff586c에 전달된다. 원본 ICONBIN의 index는 4이며 리소스 슬롯 번호 5와 구별된다. iconbin.relations

저장소 설명자는 인덱스마다 0x870바이트, bank마다 0x434바이트 간격이다. 선택한 설명자의 +0x10은 시작 블록, +0x14는 기록한 바이트 수, +0x18은 블록 수로 쓰인다. PARTPARA의 kind 2 레코드는 0x52ff1ea8에서 최대 32개 항목으로 처리되며 용량을 블록 단위로 바꿔 누적 시작 위치를 계산한다. 저장소 객체의 설명자 포인터는 0x52ff528c가 리소스 슬롯 2의 기준 주소에서 얻는다. 부트 단계가 슬롯 2를 채우는 경로와 활성 bank 선택 생산자는 미확정이다.

런타임 로더 0x5330279c은 슬롯 5가 준비돼 있으면 읽기를 생략한다. 준비되지 않았으면 0x52ff8de4(5)에서 버퍼 주소를 얻고 설명자 4의 길이를 블록 단위로 올림한 뒤 0x52ff568c에 인덱스 4와 버퍼 주소를 넘긴다. 기준 주소가 초기값 0xffffffff이면 getter는 길이가 0x08000000 이하인지 확인하고 가상 할당 함수를 호출한다. 할당이 성공하면 슬롯의 기준 주소와 길이를 갱신한다.

읽기 결과를 받는 0x52ff8f04는 슬롯 +0xc의 포인터가 유효할 때, 결과가 0이 아니면 0xa55a5aa5, 0이면 0xffffffff을 기록한다. 슬롯 5의 초기 marker 포인터는 0x50adf00c다. 이는 포인터 초기값이며 그 주소의 초기 메모리 내용은 확인하지 않았다. 준비 표식, 읽기 크기 제한, 레코드 분기를 원본 ARM으로 실행한 39개 검사가 통과했다. 저장소 드라이버 호출 직전에 중단했으므로 실제 장치 I/O를 검증한 결과는 아니다. 검사 결과 · 검증 도구

Stubby에서 확인한 서명 관련 경계

패키지의 LINUX 레코드에는 Stubby 코드가 있다. payload 기준 Thumb 함수 0x894–0x8b4는 literal 0x8b8과 PC 상대 덧셈을 사용해 문자열 0x2b04를 참조하고 0x8b0에서 출력 함수 0xc84로 분기한다. 문자열은 , (No security)이다. 여기의 숫자는 LINUX payload 상대 오프셋이며 RTOS 주소나 관찰한 런타임 주소가 아니다. linux_stubby · 세 영역 해시·상대 주소 대조

Ricoh가 배포한 Stubby 1.60.1의 boot-sequence.c 72–87행에서 이 문자열은 CONFIG_RSA_SIGNATURE 비활성 분기에 있다. 바이너리의 출력 경로는 이 분기에 대응한다. 같은 소스의 load_image.c 151–207행에는 옵션 활성 시 서명 파일을 읽고 커널 등 이미지의 해시를 검증하는 조건부 코드가 있다. 다만 공개 소스의 정확한 빌드 동일성이나 해당 옵션이 카메라의 모든 부트 구성 요소에 적용되는지는 입증하지 않았다. Ricoh 공식 OSS 패키지

이 LINUX 내부 구성 요소와 별도 BOOT 레코드, RTOS 업데이트 검증기는 서로 구별해야 한다. 따라서 현재 결론은 “해당 Stubby 출력 경로가 RSA 옵션 비활성 소스 분기에 대응한다”까지다. 수정 패키지의 수락 여부와 전체 인증 정책은 아직 미확정이다.

재현과 다음 분석

추가 의사코드는 RTOS 함수 창 41개와 LINUX Stubby 함수 창 1개를 로컬에 저장했다. 의사코드는 angr가 복원한 해석 자료이며 원래 소스가 아니다. 핵심 판정은 전체 ARM/Thumb 목록과 원본 바이트로 대조했다. 업데이트·ICONBIN 작업을 나눠 조사한 뒤 독립 검토자가 체크섬 114개와 로더 39개 검사를 다시 실행했다. 공개 자료에는 분석 문장, 주소·해시, 검증 도구와 결과만 포함한다.

공개 검증 도구 실행 방법

Python 환경에서 원본 파일과 기존 절차로 추출한 decoded.bin을 준비한다. 두 수치 검증 도구는 Unicorn·Capstone을 사용한다. 전체 업데이트 실행이나 파일 기록 기능은 없다.

python verify_deep_analysis.py decoded.bin
python verify_update_checksums.py decoded.bin --output checksum-check.json
python verify_iconbin_loader.py decoded.bin --output iconbin-check.json
python verify_update_resources.py fwdc233b.bin decoded.bin --output resource-check.json
