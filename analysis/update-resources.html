업데이트 파일의 검사 항목과 ICONBIN 적재 경로

카메라는 SD 카드에서 찾은 펌웨어 파일을 설치하기 전에 기종과 종류, 버전, 체크섬을 확인합니다. 이 검사가 파일의 어느 값을 보는지, 그리고 파일 안의 아이콘 묶음이 저장소를 거쳐 화면 자원으로 올라오는 경로를 추적했습니다.

  3. 체크섬 두 개와 하드웨어 변환

핵심 요약

  • RTOS의 업데이트 검증기는 프로젝트 값, 펌웨어 종류, 체크섬 두 개, 변환 뒤의 길이를 차례로 확인합니다. 원본 파일의 실제 바이트가 이 조건을 모두 만족한다는 것을 파일에서 직접 읽어 대조했습니다.
  • 이 경로에서 찾은 무결성 검사는 32비트 덧셈 체크섬입니다. 체크섬 함수 두 개를 PC 에뮬레이터에서 114개 입력으로 실행했고 계산식과 모두 일치했습니다. 암호학적 서명 검사는 이 경로에서 찾지 못했지만, 다른 단계에 인증이 없다는 뜻은 아닙니다.
  • 버전 검사는 파일의 버전이 카메라의 현재 버전보다 낮으면 거부하고 같으면 허용합니다. 파일 끝 24바이트 앞의 256바이트는 이 검사가 읽는 버전 레코드 두 개입니다.
  • 아이콘 묶음 ICONBIN은 업데이트 때 저장소 인덱스 4에 기록되고, 실행 중에는 같은 인덱스에서 리소스 슬롯 5의 버퍼로 읽힙니다. 이 연결의 분기와 인수 계산을 39개 입력으로 실행해 확인했습니다. 실제 저장 장치는 읽거나 쓰지 않았습니다.
  • Linux 부트로더 Stubby에는 “(No security)” 문구를 출력하는 경로가 있습니다. 공개 소스에서 이 문구는 RSA 서명 옵션을 끈 분기에 있습니다. 카메라 전체의 인증 정책은 아직 확정하지 못했습니다.

배경: 업데이트 파일의 모양과 이 문서의 위치

사용자는 Ricoh가 배포한 fwdc233b.bin을 SD 카드 최상위 폴더에 복사하고, MENU 버튼을 누른 채 전원을 켜서 업데이트를 시작합니다(Ricoh 공식 안내). 이 문서는 카메라의 실시간 운영체제(RTOS) 쪽 코드가 그 파일을 읽은 직후에 수행하는 검사를 다룹니다. 파일을 찾고 읽는 과정은 입력 로더와 메모리 할당, 검사 뒤의 기록과 완료 처리는 업데이트 과정 안내의 뒤쪽 문서에서 이어집니다.

업데이트 파일은 네 부분으로 이루어져 있습니다. 검사 함수들은 주로 맨 앞의 헤더와 맨 뒤의 footer를 읽습니다.

쉽게 말하면

택배 상자에 비유하면 헤더와 footer는 상자 앞뒤에 붙은 송장입니다. 카메라는 두 송장의 내용이 서로 맞는지, 받는 기종이 맞는지 먼저 보고, 상자 전체의 무게(체크섬)를 잰 다음 내용물을 풀어 다시 한번 무게를 잽니다.

이 문서에서 쓰는 말

프로젝트 값
파일 헤더와 카메라가 각각 가진 기종 식별 숫자입니다. 진단 문자열은 이것을 project number라고 부릅니다. 원본 파일의 값은 0x246입니다.
종류 값(kind)
업데이트의 종류를 나타내는 숫자입니다. SD 카드의 본체 펌웨어 파일은 종류 2로 처리됩니다.
체크섬
데이터를 정해진 방식으로 더한 값입니다. 전송·저장 중의 우연한 손상을 찾는 데 쓰입니다. 계산 방법을 아는 사람은 값을 다시 맞출 수 있으므로 위조를 막지는 못합니다(RFC 4949의 checksum 항목).
레코드
풀린 본문 안에 들어 있는 이름 붙은 덩어리입니다. RTOS, LINUX, ICONBIN 등 15개가 있습니다(펌웨어 구조와 하드웨어).
리소스 슬롯
RTOS가 큰 데이터 영역을 번호로 관리하는 표의 한 칸입니다. 슬롯 2는 파티션 표, 슬롯 5는 아이콘 데이터입니다.
bank
저장소의 같은 자원을 두 벌로 둘 때 각 벌을 가리키는 말입니다. 어느 bank를 쓰는지는 쓰기 bank와 BOOT 선택에서 다룹니다.

파일을 고른 뒤 헤더와 footer에서 확인하는 값

검증기는 헤더와 footer의 프로젝트 값·고정 표식·펌웨어 종류가 기대값과 맞는지 확인하고, 하나라도 다르면 실패를 돌려줍니다.

파일 이름과 프로젝트 값은 서로 다른 숫자입니다

파일 이름을 만드는 함수와 프로젝트 값을 읽는 함수는 같은 객체의 서로 다른 칸을 읽습니다. 파일 이름에 들어가는 숫자(배포 파일의 233)를 헤더의 프로젝트 값 0x246이나 특정 칩 번호와 같은 것으로 보지 않았습니다.

버전 비교: 낮으면 거부, 같으면 허용

버전 검사 함수 0x52feef34는 종류 2·3·4에서 헤더의 버전 쌍 세 개를 각각 (high<<16)|low로 합칩니다. 카메라의 현재 버전을 돌려주는 함수 세 개의 값과 부호 없는 수로 비교해, 하나라도 작으면 실패합니다. 같은 값은 통과합니다.

이번에 확인한 상위 제어 코드는 종류 2일 때만 이 검사를 부릅니다. 모든 업데이트 진입점에 공통으로 걸리는 정책인지는 확인하지 못했습니다. Ricoh의 공식 안내도 2.20으로 올린 뒤에는 2.13 이하로 되돌릴 수 없다고 적고 있습니다. 그 제한이 이 비교 때문인지는 확인하지 않았습니다.

첫 번째 버전 쌍을 읽는 함수 0x52ff4b3c는 헤더 +0x3c의 개수를 봅니다. 개수가 0이면 헤더 +0x38에서 빅엔디언 16비트 값 두 개를 읽습니다. 개수가 있으면 B+N−0x18−개수×0x80에서 시작하는 128바이트 레코드를 차례로 보며, 첫 단어(selector)가 맞는 레코드의 +8, +0xa에서 값을 읽습니다.

주의

레코드의 나머지 필드는 해석하지 않았습니다. 숫자를 제품에 표시되는 버전으로 바꾸거나, selector 0x26e를 다른 카메라 이름에 대응시키지도 않았습니다. 크기가 256바이트라는 점만으로 이 영역을 RSA 서명으로 볼 근거는 없습니다.

체크섬 두 개와 하드웨어 변환

검증기는 파일 전체의 체크섬을 확인한 뒤 본문을 변환 장치에 맡기고, 돌려받은 데이터의 길이와 체크섬을 다시 확인합니다. 두 체크섬 모두 32비트 단어의 단순 합입니다.

  • 안쪽 체크섬은 마지막 4바이트를 먼저 읽습니다. 0xfffffffe는 생략 값이 아니며, 이 값이면 합을 계산합니다.
시험 조건

두 함수 전체를 Unicorn 에뮬레이터의 합성 메모리에서 실행했습니다. 길이는 바깥 0·1·3·4·5·7·8·12·31·32·64바이트, 안쪽 4·5·7·8·12·31·32·64바이트이고, 길이마다 난수·0·합이 0이 되게 맞춘 값·생략 표식 세 종류를 넣었습니다. 114건 모두 계산식과 같은 결과를 냈습니다. 이 결과는 함수 두 개의 분기를 확인한 것입니다. 상위 경로가 길이 0이나 불완전한 헤더를 받아들인다는 뜻으로 읽으면 안 됩니다.

변환 장치: 설정과 시작, 결과 처리까지 확인

본문 변환은 0x52ff4f88 → 0x530fa6b4 → 하위 드라이버 0x5327f04c로 내려갑니다. 드라이버는 MMIO 주소 0x1b030000의 레지스터에 입력과 출력 위치를 쓰고 시작 비트를 켭니다. footer가 알려 주는 입력 길이와 기대 출력 길이는 PC에서 같은 본문을 풀었을 때의 압축 길이·풀린 길이와 같습니다. 장치가 내부에서 어떤 알고리즘으로 변환하는지, 인증 동작이 있는지는 특정하지 못했습니다.

ICONBIN이 저장소 인덱스 4에서 리소스 슬롯 5로 가는 경로

업데이트 때 ICONBIN을 기록하는 쪽과 실행 중에 읽어 오는 쪽이 같은 저장소 인덱스 4와 같은 설명자 구조를 씁니다. 패키지 안의 index 4와 리소스 슬롯 번호 5는 서로 다른 번호입니다.

기록: 레코드 순회에서 저장소 기록 함수까지

순회 함수 0x52ff29c8은 레코드 헤더에서 kind, index, 길이를 읽고 그 뒤를 내용(payload)으로 씁니다. kind 4인 레코드는 index가 배치 항목 수보다 작을 때 기록 요청 함수 0x52ff225c를 거쳐 저장소 기록 함수 0x52ff586c에 전달됩니다. 원본 ICONBIN의 index는 4입니다.

저장소 설명자: 인덱스와 bank로 위치를 고릅니다

저장소 설명자는 인덱스마다 0x870바이트, 그 안에서 bank마다 0x434바이트 간격으로 놓입니다. 선택된 설명자의 +0x10은 시작 블록, +0x14는 기록한 바이트 수, +0x18은 블록 수입니다. 기록이 성공하면 뒤의 두 값이 갱신됩니다.

이 표의 배치는 패키지의 PARTPARA 레코드(kind 2)에서 나옵니다. 처리 함수 0x52ff1ea8은 항목을 최대 32개까지 받아 용량을 블록 단위로 바꾸고 시작 위치를 차례로 누적합니다. 표가 놓이는 메모리는 리소스 슬롯 2(이름 PartitionTable)이며, 저장소 객체는 0x52ff528c에서 그 주소를 받아 옵니다. 부팅 단계의 BOOT 코드가 슬롯 2를 채우는 경로는 M0 reset·SRAM remap·bank에서 확인했고, 표와 헤더를 기록하는 순서는 같은 문서의 기록 순서 절에 있습니다. 0이 아닌 bank 값을 만드는 코드는 찾지 못했습니다.

적재: 런타임 로더가 슬롯 5로 읽어 옵니다

  1. 준비 여부 확인 런타임 로더 0x5330279c는 슬롯 5가 이미 준비되어 있으면 읽기를 건너뜁니다.
  2. 버퍼 확보 준비되지 않았으면 0x52ff8de4(5)로 버퍼 주소를 얻습니다. 슬롯 5의 기준 주소는 처음에 0xffffffff입니다. 이 경우 길이가 0x08000000 이하인지 확인한 뒤 할당 함수를 부르고, 성공하면 슬롯에 주소와 길이를 적습니다.
  3. 읽기 요청 설명자 4의 길이를 블록 단위로 올림한 뒤 읽기 함수 0x52ff568c에 인덱스 4와 버퍼 주소를 넘깁니다. 읽기 함수는 요청 길이를 그 인덱스의 용량 이하로 제한합니다.
  4. 준비 표식 결과를 받은 0x52ff8f04는 슬롯 +0xc의 포인터가 유효할 때, 결과가 0이 아니면 0xa55a5aa5, 0이면 0xffffffff을 그 위치에 씁니다.

슬롯 5의 표식 포인터 초기값은 0x50adf00c입니다. 포인터의 초기값이며, 그 주소에 처음 무엇이 들어 있는지는 확인하지 않았습니다. 준비 표식은 적재 상태를 나타내는 값이고 암호학적 서명이 아닙니다.

시험 조건

준비 표식 함수 전체와, 읽기 인수 계산·kind 4 분기 조각을 Unicorn의 Cortex-A15 모델과 합성 RAM에서 실행했습니다. 39건은 표식 기록 4건, 표식 포인터가 없는 경우 1건, bank 0·1 × 인덱스 0·4·10 × 요청 크기 5종의 읽기 인수 30건, kind 4의 index 0·4·31 수락과 32 거부 4건입니다. 저장소 드라이버를 부르기 직전에 실행을 멈췄으므로 실제 장치 입출력을 검증한 결과가 아닙니다.

저장소 드라이버의 실제 대상은 내장 eMMC를 다루는 Emmc 클래스의 읽기·쓰기 함수로 연결했습니다(드라이버 연결). 아이콘 데이터 자체의 구조는 ICONBIN 아이콘 자원에서 다룹니다. 그 문서는 활성 descriptor 1,665개의 내용 분할, IconView에서 그리기 함수와 32비트 픽셀 복사로 이어지는 경로, 아이콘 한 개를 바꿨다가 되돌리는 편집을 검증했습니다.

Stubby의 “(No security)” 출력 경로

패키지의 LINUX 레코드에 든 부트로더 Stubby에는 “, (No security)” 문구를 출력하는 코드가 있고, 공개 소스에서 이 문구는 RSA 서명 옵션이 꺼진 분기에 있습니다. 여기서 말할 수 있는 것은 이 한 구성 요소의 출력 경로까지입니다.

LINUX 레코드 내용의 앞부분에는 Thumb 명령으로 된 정보 출력 함수가 있습니다. 이 함수는 PC 상대 주소 계산으로 문자열 , (No security)를 가리킨 뒤 출력 함수로 분기합니다. 아래 숫자는 모두 LINUX 레코드 내용의 시작을 0으로 한 상대 위치입니다. RTOS 주소나 실행 중에 관찰한 주소가 아닙니다.

  • 공개 소스와 카메라에 든 바이너리가 정확히 같은 빌드인지
  • 패키지 전체의 서명 정책, 다른 서명 검사 코드가 없다는 것

저장소와 부팅 초기화슬롯 2, bank 바이트, 저장소 드라이버슬롯 2를 채우는 코드와 드라이버 대상은 확인했습니다. 메시지 큐의 그룹 등록과 송수신 객체, 파티션 표 → 부트 헤더 → BOOT 이미지의 기록 순서도 연결했습니다. 0이 아닌 bank를 만드는 코드는 찾지 못했습니다. 미확인
변환 장치와 인증 범위MMIO 0x1b030000, 별도의 BOOT 레코드레지스터의 뜻과 변환 알고리즘, 다른 인증 경로는 각각 따로 확인해야 합니다. BOOT 쪽 검사는 SDHCI 호환 전송 상태 처리까지 추적했습니다. 전체 인증 정책은 정해지지 않았습니다. 미확인
화면 자원의 형식슬롯 5 버퍼, 아이콘 설명자와 그리기 함수픽셀 형식과 ID 대응은 ICONBIN 아이콘 자원에서 이어서 다룹니다.
  • 잘못 만들어진 파일에 대한 경계 검사가 충분한지는 증명하지 않았습니다. 헤더 접근은 입력이 충분히 길다고 가정합니다.
  • 디컴파일한 의사코드는 RTOS 함수 구간 41개와 Stubby 함수 구간 1개를 따로 보관했습니다. 의사코드는 angr가 복원한 해석 자료이며 원래 소스가 아닙니다. 판단은 ARM·Thumb 명령 목록과 원본 바이트를 기준으로 했습니다.
  • 체크섬 114건과 로더 39건은 조사한 사람과 다른 검토자가 한 번 더 실행했습니다.

재현 방법

원본 파일 fwdc233b.bin과, 추출 절차로 만든 decoded.bin이 필요합니다. 수치 검증 도구 두 개는 Unicorn과 Capstone을 씁니다. 네 도구 모두 파일을 읽기만 하며 업데이트를 실행하거나 장치에 쓰는 기능이 없습니다.

python verify_deep_analysis.py decoded.bin
python verify_update_checksums.py decoded.bin --output checksum-check.json
python verify_iconbin_loader.py decoded.bin --output iconbin-check.json
python verify_update_resources.py fwdc233b.bin decoded.bin --output resource-check.json
