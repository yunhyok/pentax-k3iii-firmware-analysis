Lightroom 색 프로파일 · 프로파일 지문

Lightroom이 TIFF에 적는 프로파일 지문을 DCP에서 직접 계산하기

Lightroom이 내보낸 파일에는 어떤 프로파일로 현상했는지를 나타내는 32자리 값이 남습니다. 이 값을 프로파일 파일에서 직접 계산할 수 있으면, 출력이 정말 그 프로파일로 만들어졌는지 파일만 보고 확인할 수 있습니다.

이 문서에서

  1. 배경: 프로파일 지문이 무엇이고 왜 직접 계산하는가
  2. 결과: 여섯 DCP의 계산값이 TIFF의 값과 모두 같았습니다
  3. 계산 방법: DCP 태그에서 MD5 입력을 만드는 순서
  4. 지문이 같아도 같은 파일이라는 뜻은 아닙니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • Lightroom Classic 15.6이 내보낸 TIFF의 XMP에는 CameraProfileDigest라는 16진수 32자리 값이 있습니다. Adobe DNG SDK 소스에 있는 “전체 프로파일 지문” 계산 절차를 따라 시험 DCP 여섯 개에서 이 값을 직접 계산했습니다. 여섯 개 모두 TIFF의 값과 같았습니다.
  • 이 지문은 DCP 파일 전체의 해시가 아닙니다. 광원, 정규화하고 반올림한 색 행렬, 프로파일 이름, 정책 값, 그리고 있으면 톤 곡선을 정해진 순서로 이어 붙인 바이트 열의 MD5입니다.
  • 그래서 지문이 같아도 파일은 다를 수 있습니다. 합성 DCP로 시험했을 때 모델 제한 문자열, 반올림에서 사라지는 작은 계수 차이, 행렬 전체에 곱한 배율, 파일의 바이트 순서는 지문을 바꾸지 않았습니다.
  • 확인한 대상은 색 행렬 두 개와 선택적 톤 곡선만 가진 DCP 여섯 개입니다. 지문은 프로파일을 구분하는 값일 뿐이며 파일이 진짜임을 보증하거나 색이 정확함을 뜻하지 않습니다.

확인 실제 파일로 확인한 것

  • DCP에서 계산한 지문 여섯 개가 Lightroom TIFF의 값 여섯 개와 일치
  • 같은 DCP의 파일 전체 MD5와 렌더 데이터 지문은 TIFF 값과 다름
  • DCP, TIFF, SDK ZIP과 그 안의 소스 15개를 SHA-256으로 고정

정적 분석 SDK 소스를 읽은 것

  • 색 행렬의 정규화·반올림과 직렬화 순서
  • 전체 지문, 렌더 데이터 지문, UniqueID에 각각 무엇이 들어가는지

모델 합성 입력으로 시험한 것

  • 합성 DCP를 한 군데씩 바꾼 변형 8가지
  • 정책 값 시험은 DCP 태그가 아니라 MD5 입력 값만 바꿈
  • 0인 행렬 원소의 표기 비교

미확인 확인하지 않은 것

  • 행렬 원소가 0일 때 Lightroom이 쓰는 표기
  • ForwardMatrix, HueSatMap, 명시된 정책 태그 등을 가진 DCP
  • Lightroom 내부 구현 자체

배경: 프로파일 지문이 무엇이고 왜 직접 계산하는가

이 주제의 실험은 직접 만든 DCP를 Lightroom에 넣고 TIFF를 내보내 비교합니다. 이때 “이 TIFF가 정말 그 DCP로 현상됐는가”를 확인할 수단이 필요합니다. Lightroom은 내보낸 파일의 XMP 메타데이터에 프로파일 이름(CameraProfile)과 함께 CameraProfileDigest라는 값을 적습니다. 프로파일 이름은 누구나 같은 이름을 붙일 수 있지만 이 값은 프로파일의 내용에서 계산됩니다.

계산 방법: DCP 태그에서 MD5 입력을 만드는 순서

DCP에서 읽은 값을 정규화하고 정해진 순서로 이어 붙여 MD5에 넣습니다. 파일의 바이트를 그대로 넣지 않습니다.

  1. DCP를 읽습니다 광원 두 개, 색 행렬 두 개, 프로파일 이름, 그리고 있으면 톤 곡선을 읽습니다. DCP 파일의 바이트 순서(little-endian 또는 big-endian)에 맞춰 값으로 해석합니다.
  2. 색 행렬을 정규화합니다 행렬에 D50 백색을 곱해 나온 세 값 가운데 최댓값을 구합니다. 그 값이 양수이고 0.99~1.01 범위를 벗어나면 행렬 전체를 그 값으로 나눕니다.
  3. 소수 넷째 자리로 반올림합니다 각 원소에 배정밀도 실수로 10,000을 곱합니다. 그다음 부호를 고려해 정수로 반올림합니다(양수는 0.5를 더하고 음수는 0.5를 빼고 소수부를 버림).
  4. 정해진 순서로 이어 붙입니다 아래 표의 순서대로 little-endian 바이트 열을 만듭니다.
  5. MD5를 계산합니다 결과 16바이트를 16진수 대문자 32자리로 적은 것이 전체 프로파일 지문입니다.

지문이 같아도 같은 파일이라는 뜻은 아닙니다

지문에는 프로파일 내용의 일부만, 그것도 정규화한 뒤에 들어갑니다. 지문에 들어가지 않는 부분이 달라도 지문은 그대로입니다.

SDK에는 프로파일을 식별하는 값이 세 가지 있습니다. 무엇이 들어가는지가 서로 다릅니다.

합성 DCP로 확인한 변형 8가지

단위 행렬 두 개와 점 세 개짜리 톤 곡선을 가진 합성 DCP를 기준으로 삼고 한 군데씩 바꿔 두 지문이 달라지는지 봤습니다. 여덟 변형 모두 DCP 파일의 SHA-256은 달라졌습니다.

  • 이름과 모델 제한: 이름만 바꾸면 전체 지문만 달라졌습니다. 모델 제한을 바꾸면 두 지문 모두 그대로였습니다.
  • 작은 계수와 배율: 넷째 자리 반올림에서 사라지는 작은 계수 변화, 정규화에서 상쇄되는 균일한 배율은 지문을 바꾸지 않았습니다. 유효 자릿수가 달라지는 행렬 수정, 광원 수정, 곡선 수정은 두 지문에 모두 반영됐습니다.
  • 파일의 바이트 순서: 합성 DCP를 big-endian 파일로 다시 담아도 읽은 값이 같으면 지문은 같았습니다. 반대로 MD5 입력 자체를 big-endian으로 직렬화하면 두 지문이 모두 달라졌습니다.
  • embed policy: MD5 입력의 정책 값을 0에서 1로 바꾸면 전체 지문만 달라졌습니다. 이 시험은 DCP의 태그는 그대로 두고 MD5 입력 값만 바꿨습니다. 정책 태그가 명시된 DCP는 검사기가 받지 않습니다.

행렬 원소가 0일 때의 표기는 정하지 못했습니다

확인한 SDK는 0인 행렬 원소를 분자 0, 분모 1(0/1)로 적습니다. 분모를 10,000으로 둔 0/10,000으로 바꿔 넣으면 두 지문이 모두 달라집니다. 그런데 실제 DCP 여섯 개에는 정규화한 뒤 0이 되는 행렬 원소가 하나도 없습니다. 따라서 이 여섯 출력만으로는 Lightroom이 0을 어떻게 적는지 판별할 수 없습니다.

한계와 남은 과제

  • 대상이 좁습니다. 색 행렬 두 개와 선택적 톤 곡선을 가진 DCP 여섯 개, Lightroom Classic 15.6 하나에서 확인했습니다. ForwardMatrix나 HueSatMap, 저작권 문자열, 명시된 정책 태그를 가진 DCP는 이 검사기의 범위 밖입니다.
  • 계산을 옮겨 적은 것입니다. SDK 소스를 읽고 Python으로 같은 계산을 구현했습니다. 결과 값이 같다는 것은 확인했습니다. Lightroom이 내부에서 SDK와 같은 코드를 쓰는지는 직접 보지 않았습니다.
  • 0의 표기: 행렬 원소가 0인 프로파일에서 Lightroom이 어떤 표기를 쓰는지는 확인하지 못했습니다.
  • 지문의 용도: 같은 지문이어도 DCP 파일의 바이트나 모델 제한은 다를 수 있습니다. 이 대조는 프로파일 지문의 재현에 한정되며 파일 인증이나 색 정확도는 다루지 않습니다.

재현 방법

Python 3.11 이상과 tifffile을 씁니다. --sdk에는 Adobe DNG SDK ZIP, --dcps에는 DCP 여섯 개가 든 폴더, --exports에는 TIFF의 하위 폴더를 모아 둔 경로를 줍니다. 파일 배치는 JSON의 input_layout에 있습니다. 검사기는 해시가 정확히 일치하는 파일만 받고 결과는 아직 없는 새 경로에만 씁니다.

python -B tools/check_lightroom_profile_fingerprints.py \
  --sdk fingerprint-fixtures/dng-sdk.zip --dcps fingerprint-fixtures/dcps \
  --exports fingerprint-fixtures/exports \
  --output fingerprint-fixtures/fingerprint-replay.json

검사기는 계산 결과가 공개 JSON과 다르면 실패합니다. 만들어진 fingerprint-replay.json의 SHA-256을 analysis/lightroom-profile-fingerprints.json과 비교해도 됩니다. 합성 대조만 다시 돌리려면 파일이 필요 없습니다.

python -m unittest discover -s tests -p test_lightroom_profile_fingerprints.py -v
공개 자료에 없는 것

SDK 소스와 TIFF, 시험 DCP 여섯 개의 파일은 저장소에 싣지 않았습니다. SDK ZIP은 Adobe 배포처에서 받습니다. K-3 II의 DCP 네 개는 톤 곡선 비교의 재현 방법으로 다시 만들 수 있습니다.

시험 DCP에 넣은 색 행렬은 카메라가 공개 RAW에 적어 둔 값이며 저장소에 실었습니다. K-3 II의 값은 lightroom-matrix-1376.json입니다. K-3 III와 Q7의 값은 lightroom-studio-baseline.json의 profile_recipes에 있고 같은 도구로 두 DCP도 다시 만듭니다. 펌웨어에서 추출한 계수와 Adobe 프로파일의 값은 싣지 않았습니다.
