K-3 III DNG의 Adobe SDK Stage 3

센서의 한 색 샘플을 화소마다 R·G·B 세 값으로 채우는 디모자이크 단계를 공개 SDK로 실행했습니다. SDK가 어떤 이웃 값을 어떻게 섞는지 따로 계산해 한 값씩 맞춰 봤습니다.

핵심 요약

  • 공개 Adobe DNG SDK 1.7.1 Build 2768이 고정한 K-3 III 변환 DNG의 CFA를 카메라 R·G·B 세 평면으로 보간했습니다.
  • 가장자리를 포함한 채널 값 77,675,520개가 별도로 계산한 Bayer 보간과 모두 일치했습니다. 센서가 직접 잰 색은 Stage 2 값 그대로였습니다.
  • 새로 빌드한 SDK와 기존 오브젝트를 재사용한 빌드가 같은 배열을 만들었습니다.
  • 결과는 디모자이크한 카메라 채널입니다. 그 뒤의 화이트밸런스, 프로파일, 톤, 출력 색공간(SDK 렌더 단계)과 Lightroom은 실행하지 않았습니다.

확인 공개 SDK를 실행해 관측

  • SDK 원본 소스로 만든 하네스의 Stage 3 배열과 평면별 통계
  • 독립 보간 12개 조합과의 전수 대조(불일치 0)
  • 센서 자리 값과 Stage 2의 일치

모델 연구자가 정한 조건

  • Stage 2와 같은 XMP·baseline libjpeg·SDK AVX 비활성 빌드
  • 미리보기와 크기 요청을 끈 BuildStage3Image 호출
  • 입력은 보존한 첫 변환 DNG 한 개

미확인 이 실행으로 알 수 없는 것

  • SDK 렌더 단계의 출력
  • Lightroom과 Adobe Converter의 내부 디모자이크

배경: 디모자이크와 Stage 3

Bayer 센서의 화소는 한 색만 잽니다. 디모자이크는 빈 두 색을 주변 화소의 같은 색 값으로 채워 화소마다 R·G·B를 만드는 계산입니다. DNG SDK에서는 그 결과가 Stage 3입니다. 값은 아직 카메라 고유의 RGB입니다. 화이트밸런스와 색 프로파일은 그다음 렌더 단계에서 적용됩니다.

입력은 SDK Stage 2 실행과 같은 DNG입니다. 하네스는 Stage 1과 Stage 2 배열을 다시 만들어, 모든 행이 그 실행과 같은지 확인한 뒤 Stage 3으로 넘어갑니다.

SDK는 ActiveArea 전체를 돌려줍니다. 기본 크롭 통계는 그 배열에서 메타데이터 좌표에 맞춰 따로 셌습니다. 배열은 행 우선 little-endian uint16이며 위치마다 R·G·B 순서로 저장했습니다. 평면별 통계와 배열 SHA-256은 채널별 통계와 배열 SHA-256에 있습니다.

원본 보간과 경계 처리

SDK는 자기 값을 그대로 두거나 같은 색 이웃 2개·4개를 평균합니다. 네 CFA 위상과 세 평면의 12개 조합을 따로 계산해 모두 맞췄습니다.

센서 자리에서는 자기 값 하나를 그대로 씁니다. 가로나 세로 이웃 두 개, 십자나 대각선 이웃 네 개를 쓰는 경우도 있습니다. 원본 uint16 루프는 Q8 가중치로 누산한 값에 128을 더하고 8비트 오른쪽으로 밉니다. 가장자리에서는 2×2 CFA 주기를 유지한 채 경계 값을 반복합니다.

12개 조합은 각각 6,472,960개이고 불일치는 모두 0이었습니다. 이 입력은 SDK의 모자이크 레이아웃 1(RGGB)입니다. SDK는 단일 CFA 평면이라 소스 평면 0을 씁니다. 다운스케일과 raw-to-full 배율은 모두 (1,1)입니다.

전체 보간 대조 · 하네스 · Adobe DNG SDK

실행은 렌더 전에 끝났습니다

이 배열은 디모자이크만 끝난 카메라 채널입니다. 사진으로 보이는 색이 되기 전 단계입니다.

Stage 3 직후 블랙은 0, 게인은 1이고 OpcodeList3는 비어 있습니다. 하네스는 BuildStage3Image(host, -1)를 미리보기와 크기 요청 없이 부릅니다. 그리고 SDK 렌더를 호출하기 전에 멈춥니다. 기본 크롭 [24,28,4152,6220)은 ActiveArea 기준 메타데이터로만 남아 있습니다.

주의

렌더의 화이트밸런스, 프로파일, 톤, 출력 색공간은 적용하기 전입니다. Lightroom과 Adobe Converter의 내부 경로도 실행하지 않았습니다. 이 값을 Lightroom 출력과 바로 비교할 수는 없습니다.

한계와 남은 과제

  • DNG 한 개: 보존한 첫 변환 DNG에서만 실행했습니다.
  • 렌더 미실행: Stage 3 뒤의 화이트밸런스, 프로파일, 톤을 각각 확인하는 일이 남아 있습니다.
  • 제품과 다른 경로: Lightroom과 Converter가 같은 보간을 쓰는지는 이 실행으로 알 수 없습니다.

재현 방법

Windows x64에서 Python 3.12와 NumPy 1.26.4를 씁니다. 고정한 첫 변환 DNG, Adobe SDK ZIP, Zig 0.15.2 전체 배포판의 zig.exe를 직접 지정합니다. 빌드 조건은 Stage 2와 같습니다. DNG IFD0에는 XMP가 있습니다. 파일과 도구 준비는 고정 파일과 도구 준비를 따릅니다.

python -B tools/check_lightroom_sdk_stage3.py --sdk dng-sdk.zip --dng K3IIIhSLI0000100NR0.dng --zig C:\path\to\zig.exe --work C:\sdk-s3
python -B -m unittest discover -s tests -p test_lightroom_sdk_stage3.py
  1. Stage 2 빌드 기존 Stage 2 도구로 컴파일하고 실행합니다. 새로 만든 Stage 2 오브젝트는 같은 실행 안에서 재사용합니다.
  2. Stage 3 하네스 새 Stage 3 하네스 하나만 컴파일하고 나머지 오브젝트 275개를 다시 씁니다.
  3. 대조 배열, 통계, SDK 로그, 전체 보간 대조로 결과를 비교합니다. 처음 실행과 새 실행의 EXE 해시는 따로 기록합니다.

작업 폴더는 기존 부모 폴더 아래에 새로 만듭니다. Windows 경로 길이를 고려해 짧은 경로를 쓰십시오. 실행하는 동안 다른 프로세스에서 이 폴더의 파일을 바꾸지 마십시오. SDK 소스, DNG 사본, 배열 덤프, 빌드 캐시가 이 폴더에 남습니다. 처음 Stage 2 작업 폴더를 보존해 두었고 영수증과 오브젝트 275개의 해시가 모두 맞는다면 --stage2-work로 재사용합니다.
