AF와 렌즈 제어 · 구동 요청을 만드는 단계

렌즈 응답에서 구동 방식 선택과 명령 작성까지

K 마운트에는 바디의 모터로 돌리는 렌즈와 렌즈 안의 모터로 움직이는 렌즈가 함께 있습니다. 펌웨어가 어느 쪽 제어 코드를 쓸지 어디에서 정하는지, 그 뒤 렌즈에 보낼 요청을 어떻게 만드는지 따라갔습니다.

이 문서에서

  1. 배경: 구동 방식을 고르는 코드를 찾는 이유
  2. 능력 바이트의 bit 6이 제어 객체를 고릅니다
  3. 능력 바이트는 두 경로로 기록됩니다
  4. 두 제어 객체는 서로 다른 이벤트를 처리합니다
  5. InMotor 쪽은 구동 값을 명령 0x8900의 2바이트로 만듭니다
  6. 검사 1,267건의 범위와 재현 방법
  7. 한계와 남은 과제
  8. 근거 파일과 참고 자료

핵심 요약

  • 렌즈와 통신하는 객체 안에 능력 바이트가 하나 있습니다. 이 바이트의 bit 6이 1이면 AfInMotorLensControl, 0이면 AfJointLensControl 객체가 AF 구동 명령을 받습니다. 256가지 값을 모두 넣어 원본 코드를 실행해 확인했습니다.
  • 능력 바이트를 기록하는 경로를 두 개 찾았습니다. 렌즈 정보를 받은 뒤 응답의 byte 6을 옮기는 경로와, 렌즈 명령 0x8205의 응답 첫 바이트를 옮기는 경로입니다. 둘 다 바이트 전체를 그대로 복사합니다.
  • InMotor 쪽은 구동 값을 명령 0x8900의 2바이트로 만듭니다. 하위 14비트가 값이고 최상위 비트가 방향 표시입니다. 값의 단위와 방향의 극성은 알지 못합니다.
  • 확인한 범위는 요청을 만드는 데까지입니다. 렌즈 응답은 모두 연구자가 넣은 합성 값이고, 실제 렌즈 통신과 모터 동작은 실행하지 않았습니다.
  • 나중의 변경에 대비해 기본 구조를 조사한 것이며, 렌즈별 패치나 실제 구동 적용은 하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 능력 바이트 256값에서 bit 6을 읽고 객체를 고르는 코드
  • 능력 바이트를 기록하는 두 경로의 복사
  • InMotor·Joint 이벤트 루프의 분기 순서
  • 명령 0x8900 요청의 2바이트 구성

정적 분석 코드를 읽어 판단

  • 객체 생성과 포인터 연결 (factory, 생성자, vtable)
  • InMotor의 이벤트 0x80 처리기가 요청 작성 함수를 부르는 관계
  • 요청 큐 진입 함수의 호출 순서

모델 시험 조건으로 정한 것

  • 렌즈 응답 바이트, 송신·수신·대기 함수의 반환값
  • 이벤트 플래그는 직접 주입, 하위 처리 함수는 stub
  • CPU는 Unicorn의 Cortex-A15 모델

미확인 확인하지 않은 것

  • bit 6의 제조사 명칭, SDM만 뜻하는지, 렌즈 ID와의 관계
  • 0x8900 값의 단위, 방향 극성, 유효 범위
  • 실제 렌즈 통신, 모터 동작, Joint 쪽 하위 구동

배경: 구동 방식을 고르는 코드를 찾는 이유

K-3 Mark III의 마운트는 AF 커플러(바디 모터의 회전을 렌즈에 전하는 기계 연결부)와 렌즈 정보 접점, 전원 접점을 갖춘 KAF2입니다. 그래서 바디 모터로 돌리는 렌즈와 렌즈 안 모터(SDM·DC·PLM)를 쓰는 렌즈를 모두 받습니다. 두 방식의 차이와 마운트 종류는 AF 안내 문서에 정리했습니다.

구형 SDM 렌즈를 바디 모터로 돌리는 것 같은 변경을 검토하려면, 펌웨어가 구동 방식을 정하는 지점을 먼저 알아야 합니다. 이 문서는 그 지점과 바로 뒤의 요청 작성까지를 다룹니다. 요청이 큐에 들어간 뒤의 일은 AF 요청 큐와 완료 통지에서 이어집니다.

등장하는 객체

이 부분의 펌웨어는 C++ 객체로 짜여 있습니다. 클래스 이름은 펌웨어에 남아 있는 RTTI 문자열과 소스 파일 이름 문자열에서 가져왔고, 생성자가 설치하는 vtable과 맞춰 보았습니다.

이름에서 알 수 있는 것과 없는 것

InMotor는 “렌즈 안 모터”, Joint는 “연결부”를 떠올리게 하는 이름입니다. K-3 II에서는 같은 자리의 비트가 켜지면 렌즈 명령, 꺼지면 바디 드라이버 쪽으로 갈렸습니다(K-3 II 렌즈 능력과 구동 분기). 그러나 K-3 Mark III에서 확인한 것은 클래스 이름과 선택 조건까지입니다. 각 객체가 실제로 어느 모터를 움직이는지, Paf·Caf로 시작하는 객체가 구동 방식과 어떤 관계인지는 확인하지 않았습니다.

이 문서의 주소와 필드 오프셋은 16진수입니다. facade의 명령 번호와 client 번호는 10진수입니다.

능력 바이트의 bit 6이 제어 객체를 고릅니다

AfDriveFacade는 명령을 받을 때마다 능력 바이트의 bit 6을 읽습니다. 1이면 InMotor 객체에, 0이면 Joint 객체에 일을 넘깁니다.

C        = LensFactory.field14 = AfLensControl.field58 = reader.field54
selected = (C.byte5272 & 0x40) ? facade.field0c : facade.field04
  1. 능력 바이트 읽기 facade의 선택 코드(0x52ef89f4)가 0x52eff628을 거쳐 0x52efda40을 부릅니다. 이 함수는 [C+0x5272]의 bit 6만 꺼내 0 또는 1을 돌려줍니다.
  2. 객체 고르기 facade는 Joint, AfLensControl, InMotor 객체의 포인터를 각각 +4, +8, +c에 갖고 있습니다. 반환값이 1이면 +c(InMotor)를, 아니면 +4(Joint)를 읽습니다. 이 선택은 0x52ef8a28과 0x52ef8a2c의 조건부 읽기 명령 두 개로 이뤄집니다.
  3. 명령 넘기기 고른 객체를 첫 인수로 삼아 명령 1~22번에 해당하는 함수를 부릅니다.

두 객체는 렌즈에 따라 하나만 만들어지지 않습니다. AfMotorFactory의 생성 경로(0x52f08be8)는 AfJointLensControl, CafJointLens, PafMotor, PafPulse를 모두 만듭니다. 렌즈 정보에 따라 하나만 만드는 분기는 이 경로에 없습니다. AfInMotorLensControl과 AfLensControl은 별도의 AfLensFactory가 만듭니다. 즉 선택은 객체를 만들 때가 아니라 명령을 처리할 때 일어납니다.

선택 뒤에 붙는 조건: client 검사와 명령 18

명령 18에는 능력 비트를 한 번 더 보는 처리가 있습니다. client가 2이고 bit 6이 1이면, 하위 함수 0x52ef8578에 넘기는 셋째 인수를 0으로 고정합니다. 그 밖에는 첫 가변 인자 word의 byte 1을 넘깁니다. 하위 함수는 전역 변수 0x5478442c의 값과 client가 같을 때만 다음 호출로 진행합니다. 이 숫자들이 정지나 회전 같은 물리 동작 가운데 무엇에 해당하는지는 풀지 않았습니다.

능력 바이트는 두 경로로 기록됩니다

능력 바이트에 값을 쓰는 코드를 두 곳 찾았습니다. 두 경로 모두 받은 바이트 전체를 그대로 옮기며, bit 6만 골라 켜거나 끄는 처리는 없습니다.

생성자는 0x5315c274에서 능력 바이트를 0으로 초기화합니다. 경로 A의 buffer[6]과 경로 B의 cache[0]은 서로 다른 입력 위치입니다. 같은 패킷이나 같은 값이라고 가정하지 않습니다. mode와 submode가 사용자 기능 가운데 무엇에 해당하는지, 통신이 유효한지를 가리는 조건 전체는 확인하지 않았습니다. C를 전역 공용 속성 객체라고 부르지도 않습니다.

명령 0x8205가 처리되는 순서

  1. 명령 정보 조회 함수 0x5315a8a0은 명령 0x8205에 index 0x26, type 2, required-mask 0을 돌려줍니다.
  2. 교환 처리기 0x52f182d4는 type 2 경로에서 교환 함수 0x52f18128을 부릅니다. 이 함수 안에 송신과 수신 호출이 있습니다.
  3. 캐시에 복사 반환값이 0이면 0x5315dc68이 32바이트를 캐시에 복사합니다. 위치는 C + 0x38 + index × 0x20, 곧 C+0x4f8입니다.
  4. 필드 갱신 0x5315dc9c가 캐시의 첫 바이트를 보조 객체의 +6과 능력 바이트에 씁니다.
통신 실패 때의 동작은 확정하지 못했습니다

type 2 경로는 교환 함수가 0이 아닌 값을 돌려주면 캐시 갱신을 건너뜁니다. 그런데 관찰한 교환 함수의 일반 반환부는 항상 0입니다. 이 함수는 대기 함수 WaitLensCpuControl(0x52f180a0)의 반환값을 뒤의 조건에 쓰지 않습니다. 대기 함수 안의 assertion이나 하위 전송이 실행을 멈출 수 있으므로, 실제 통신이 실패했을 때도 능력 바이트가 갱신된다고 단정할 수 없습니다. type 3 경로는 0x52f18410에서 캐시를 복사한 뒤에 상태를 검사하므로, 이 조건을 모든 type에 적용하지도 않습니다.

  • 버퍼 길이 — 교환 함수는 32바이트를 송신하고, 수신 뒤 호출자 버퍼에 min(requested_length, 32)바이트를 복사합니다. 그 뒤 캐시 함수가 다시 32바이트를 복사합니다. 호출자 버퍼의 용량과 초기화가 중요한 구조입니다. 다만 잘못된 호출자나 실제 메모리 침범을 관찰한 것은 아닙니다.
  • index 범위 — 캐시 함수의 범위 검사는 부호 있는 index가 0x86보다 클 때만 거부합니다. 합성 index −1은 C+18로 계산됐습니다. 실제 조회가 0x8205에 내놓은 index는 정상값 0x26입니다.
  • 전달을 막는 조건 — 상위 전달 함수 0x52f15100은 자기 객체의 byte +9b가 0일 때 0x52f18490을 부릅니다. 이 함수는 C+52f3이 0이 아니면 0x8205 전달을 막습니다. 두 상태 필드의 뜻과, 실제로 0x8205를 일으키는 화면 조작이나 이벤트는 확정하지 못했습니다.

InMotor 쪽은 구동 값을 명령 0x8900의 2바이트로 만듭니다

요청 작성 함수는 능력 비트를 다시 확인한 뒤, 입력 값의 하위 14비트와 방향 표시 1비트를 묶어 2바이트를 만듭니다.

InMotor의 이벤트 0x80 처리 함수에는 제어 모드에 따라 요청 작성 함수 0x52efc7a0을 부르는 경로가 있습니다. 이 함수는 통신 객체의 같은 bit 6을 한 번 더 검사합니다. 비트가 0이면 큐 쪽 함수를 부르지 않고 0xff를 돌려줍니다. 비트가 1이면 아래처럼 2바이트를 만듭니다.

value14 = inputValue & 0x3fff
word    = value14 | (directionArgument != 0 ? 0x8000 : 0)
payload = [word >> 8, word & 0xff]
descriptor.command = 0x8900
request.opcode     = 0x1b

주의

상위 facade의 선택만 바꾸면 구동 방식이 바뀐다고 볼 근거는 없습니다. 요청 작성 함수가 능력 비트를 다시 검사하고, 두 객체가 지원하는 이벤트가 다르며, 제어 모드별 처리와 렌즈의 기계적 조건도 따로 있습니다. 이들을 함께 검토해야 합니다.

요청 작성 검사의 구성과 주소

320건은 능력 바이트 0~255 전부(입력 값 0x2345, 방향 인자 1)에, 능력 바이트 0과 0x40 각각에서 입력 값 8가지(0, 1, 0x3fff, 0x4000, 0x7fff, 0x8000, 0xffff, 0x12345678)와 방향 인자 4가지(0, 1, 2, 0xffffffff)를 조합한 64건을 더한 것입니다. bit 6이 0인 160건은 모두 0xff를 돌려주고 요청을 만들지 않았으며 객체의 +88~+8d도 바뀌지 않았습니다. bit 6이 1인 160건은 모두 요청 하나를 만들었습니다. descriptor의 앞 8바이트는 02 00 00 89 00 00 00 00이었습니다.

실행한 구간은 작성 함수 0x52efc7a0–0x52efc858과 opcode 지정 함수 0x52eff608–0x52eff618입니다. 큐 진입 함수 0x52eff524는 stub으로 받아 인수와 바이트를 대조했습니다. 정적 분석으로는 0x52eff524가 0x52efeec0으로 요청 기록을 얻고 opcode를 요청의 +0c에 쓴 뒤 0x52f148fc를 부르는 것을 확인했습니다. 이벤트 0x80 처리 함수에서 작성 함수를 부르는 명령은 0x52ef94a4에 있습니다. 근거: af-command-evidence.json, af-command-checks.json.

디컴파일한 C는 참고용입니다

디컴파일러 angr가 만든 C 의사코드 23개(선택 경로 6개, 명령 경로 11개, 능력 기록 경로 6개)를 손대지 않고 로컬에 보관했습니다. 여기에는 중요한 복원 오류가 있습니다. facade의 C는 조건부 읽기 명령(LDREQ/LDRNE)을 잃어 항상 Joint를 고르는 것처럼 보입니다. 요청 작성 함수의 C도 일부 인자와 포인터를 정확히 복원하지 못합니다. 그래서 선택식과 바이트 변환은 원본 ARM 명령과 실행 결과를 근거로 썼습니다. 이 C를 컴파일할 수 있는 원본 소스로 다루지 않습니다.

한계와 남은 과제

  • 비트의 뜻 — bit 6이 어느 클래스를 고르는지만 확인했습니다. 제조사의 비트 이름, 값 전체의 인코딩, 렌즈가 물리적으로 구동 가능한지를 가리는 규칙은 복원하지 못했습니다.
  • 통신 — 응답 바이트를 옮기는 CPU 명령은 실행했지만, 수신 호출 0x52f3a754와 그 아래 전송 계층은 실행하지 않았습니다. 전기적 통신, 응답의 유효성, 모터의 움직임은 이 결과로 알 수 없습니다.
  • 부분 실행 — 복사 256건과 진입 조건 25건은 수신 함수의 일부 구간입니다. 생성자와 factory의 포인터 연결은 정적 분석이며, 시작 과정을 실행한 것이 아닙니다.
  • 다른 기록자 — 조사 범위를 정해 놓고 찾은 결과입니다. 능력 바이트를 쓰는 코드나 같은 필드를 가리키는 다른 포인터가 더 없다고 증명한 것은 아닙니다.
  • 값의 뜻 — 0x8900 값의 단위, 방향의 극성, 유효 이동 범위, 기계적 호환 조건은 미해결입니다.
  • 범위 밖 — AF 계산, 전원 순서, 하드웨어 드라이버 실행은 다루지 않았습니다. 펌웨어와 렌즈 EEPROM을 수정하지 않았고, 실제 모터·저장 매체·카메라를 실행하지 않았습니다.
  • 다른 기종 — K-3 Mark III의 현재 코드 구조를 분석한 것입니다. K-3 II와 Q7이 같은 내부 규약을 쓴다는 주장은 하지 않습니다.
