PENTAX K-3 MARK III · FIRMWARE 2.20 · 2026-11-08

렌즈 정보에서 AF 제어·명령까지

렌즈 응답 필드가 제어 객체 선택에 쓰이는 경로를 연결했다. 선택된 객체의 이벤트 처리와 명령 작성도 일부 확인했다. 현재 목적은 향후 변경에 필요한 기본 구조를 연구하는 것이며 렌즈별 패치나 실제 구동 적용은 진행하지 않는다.

연구 개요 · 상위 요청·AF 계산 · ICONBIN·GUI

factory 생성과 실행 중 선택

AfMotorFactory의 생성 경로 0x52f08be8은 AfJointLensControl, CafJointLens, PafMotor, PafPulse를 모두 만든다. 렌즈 정보에 따라 하나만 만드는 분기는 이 경로에 없다. AfInMotorLensControl과 AfLensControl은 별도 AfLensFactory가 만든다. 이름은 생성자의 vtable 설치와 RTTI를 함께 대조했다. 생성·alias·원본 해시

실제 선택은 AfDriveFacade의 0x52ef89f4에 있다. facade의 +4는 Joint, +8은 AfLensControl, +c는 InMotor 객체를 가리킨다. 주소와 필드 offset은 16진수이며 command·client 번호는 10진수다.

C = LensFactory.field14 = AfLensControl.field58 = reader.field54
selected = (C.byte5272 & 0x40) ? facade.field0c : facade.field04

생성자 0x5315c274는 C+5272를 0으로 초기화한다. 수신 함수 0x52f18638은 하위 호출 0x52f3a754 뒤 mode가 3이거나 mode가 0이고 submode가 3인 경로에서 응답 byte 6을 복사한다. mode·submode의 사용자 기능 이름과 통신 유효성 전체는 아직 확인하지 않았다. C는 전역 common-property 객체로 명명하지 않는다. 생산자·초기화·분기 근거

이 비트가 선택하는 클래스는 확인했지만 vendor의 비트 이름, SDM만을 뜻하는지 여부, 특정 렌즈 ID와의 관계는 미확정이다. 후속 조사에서 0x5315e078을 같은 필드의 두 번째 기록자로 확인했다. 0x531346e4는 별도 영상처리 출력 주소를 쓰므로 이 후보에서 제외했다.

command 0x8205가 갱신하는 같은 필드

명령 metadata 함수 0x5315a8a0은 command 0x8205에 index 0x26, type 2, required-mask 0을 반환한다. 처리기 0x52f182d4는 type 2 경로에서 교환 helper 0x52f18128을 호출한다. 반환값이 0이면 0x5315dc68로 32바이트를 캐시에 복사하고 0x5315dc9c로 필드를 갱신한다. lookup·분기·저장 주소 근거

이 경로는 캐시 첫 바이트 전체를 복사한다. bit 6만 설정하거나 지우는 정책은 확인되지 않았다. 앞선 수신 경로의 buffer[6]과 이 경로의 cache[0]는 서로 다른 입력 위치이며 같은 packet이나 같은 값으로 가정하지 않는다. 초기화 코드 0x5315c0b8..c0과 0x52f17ad8..ec에서 C+5260 = reader+4c = LensFactory+c alias를 확인했다. 두 경로는 같은 C 필드와 같은 보조 객체 byte 6을 갱신한다. 객체 alias와 기록자

교환 helper는 송신에 32바이트를 사용하고 수신 후 caller 버퍼에 min(requested_length, 32)바이트를 복사한다. 그 뒤 캐시 함수는 다시 32바이트를 복사한다. 따라서 caller 버퍼의 용량과 초기화가 중요하지만 이번 범위에서 잘못된 caller나 실제 메모리 침범을 관찰한 것은 아니다. 캐시 함수의 범위 검사는 signed index가 0x86보다 큰 경우만 거부한다. 합성 index −1은 C+18로 계산됐고 확인한 0x8205 lookup은 정상 index 0x26을 생산했다.

0x8205/type 2 처리 경로는 교환 helper의 nonzero 반환에서 캐시 갱신을 건너뛰지만 관찰한 helper의 일반 반환부는 항상 0이다. type 3 경로는 0x52f18410에서 캐시를 복사한 뒤 상태를 검사하므로 이 조건을 모든 type에 적용하지 않는다. helper는 WaitLensCpuControl 0x52f180a0의 반환값을 후속 조건에 사용하지 않는다. wait 내부의 assertion이나 하위 transport가 실행을 멈출 수 있으므로 실제 통신 실패 때도 capability가 갱신된다고 단정할 수 없다. 합성 wait·nonzero 입력의 검사 범위

상위 전달 함수 0x52f15100은 자체 byte +9b가 0일 때 0x52f18490을 호출한다. 이 wrapper는 C+52f3가 nonzero이면 0x8205 전달을 막는다. 두 상태 필드의 의미와 실제 0x8205를 발생시키는 UI/event는 미확정이다. 다른 MOVW 후보는 MOVT와 결합하면 0x26408205여서 16비트 명령과 구분했다.

제외한 후보 0x531346e4는 EdgeEnhancement packer 0x5313432c 안에 있다. 시작부가 r3 = output + 0x1000을 만들고 해당 store가 [r3+0x272]에 쓰므로 목적지는 output+1272다. 이 호출 경로의 주소식을 확인한 결과이며 다른 모든 alias가 없다는 전체 부재 증명은 아니다. 영상처리 caller와 주소 계산

InMotor 명령 작성에서 다시 만나는 capability

InMotor의 이벤트 0x80 처리기에는 제어 모드에 따라 0x52efc7a0을 호출하는 경로가 있다. 이 명령 작성 함수는 통신 객체의 같은 bit 6을 다시 검사한다. 비트가 0이면 queue를 호출하지 않고 0xff를 반환한다. 비트가 1이면 아래 값을 두 바이트로 작성한다. 원본 명령과 전이

value14 = inputValue & 0x3fff
word = value14 | (directionArgument != 0 ? 0x8000 : 0)
payload = [word >> 8, word & 0xff]
descriptor.command = 0x8900
request.opcode = 0x1b

directionArgument는 0 여부에 따라 bit 15를 만드는 인자를 구분하기 위한 분석용 이름이다. 회전 방향의 극성, 거리·펄스 단위, 유효 이동 범위는 확인하지 않았다. 입력 하위 14비트와 인자 원값은 객체의 +8c, +88에 각각 저장된다. 0x52eff608은 opcode 0x1b를 넣어 0x52eff524로 넘긴다. descriptor는 CPU 내부 요청 형식이며 실제 렌즈 버스 프레임으로 단정하지 않는다.

상위 facade만 바꾸는 것으로 구동 전환이 성립한다고 판단할 근거는 없다. 하위 capability 검사, 이벤트의 지원 범위, 제어 모드별 처리와 기계적 조건을 함께 검토해야 한다.

미래 변경을 위한 연구 범위

후속 조사에서는 capability의 다른 기록자, 재연결·오류 시 갱신, AF 계산 결과와 command 인자의 관계, queue 이후의 transport를 추적한다. 대상 렌즈나 실물이 없어도 이 기본 구조 연구는 진행할 수 있다. 실제 구동을 검토할 때는 타이밍, 위치 한계, 보정과 기계적 호환성을 별도로 검증해야 한다.

구형 smc DA★16–50 SDM 공식 설명에는 SDM 호환 여부에 따라 렌즈 내장 모터와 바디 모터를 사용하는 사례가 있다. 반면 K-3 III 공식 FAQ는 KAF3를 AF coupler가 없는 렌즈로 설명한다. 이 차이는 기계적 조건을 구분하는 근거이며 bit 6의 공식 이름이나 강제 전환 가능성을 입증하지 않는다.

펌웨어·렌즈 EEPROM을 수정하거나 실제 모터·저장매체·카메라를 실행하지 않았다. 이 보고서는 현재 K-3 Mark III 코드의 기본 구조 분석이며 K-3 II·Q7에서 같은 ABI를 사용한다는 주장은 포함하지 않는다.
