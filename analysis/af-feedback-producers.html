PafPulse 기준값은 어디에서 쓰이는가

요청 3의 피드백 계산은 PafPulse의 기준값을 빼서 잔여값을 구합니다. 그 기준값을 누가 쓰는지, 쓴 값이 실제로 같은 객체를 거쳐 소비자에게 닿는지 확인했습니다.

이 문서에서

  1. 배경: 왜 기준값의 출처를 찾는가
  2. 생산자와 소비자는 같은 PafPulse 객체를 씁니다
  3. 기준값을 쓰는 명령은 네 곳입니다
  4. 네 입력에서 새 기준값과 소비자의 판단
  5. PafMotor의 두 보정 필드는 아직 출처를 모릅니다
  6. 한계와 남은 과제
  7. 재현 조건과 실행 범위
  8. 근거 파일과 참고 자료

핵심 요약

  • PafMotor, PafPulse, PafControl은 원본 바인더가 연결한 같은 PafPulse 객체를 가리킵니다. 생성자와 바인더를 원본 코드로 실행해 확인했습니다.
  • 기준값 Pulse+0xa88을 쓰는 명령을 네 곳 찾았습니다. 그중 PafControl의 두 경로를 실행했고 나머지 두 곳은 코드를 읽어 확인했습니다.
  • 두 경로를 네 가지 입력으로 실행한 뒤 소비자 코드를 따로 시작했습니다. 소비자는 같은 객체에서 새 기준값을 읽어 잔여값을 계산했고 양수일 때만 요청 3 진입 직전까지 갔습니다.
  • PafMovableObject의 값, 분기 상태, 소비자 쪽 수치는 시험 입력입니다. PafMotor의 두 보정 필드를 0이 아닌 값으로 쓰는 코드는 아직 찾지 못했습니다.

확인 원본 코드 실행으로 확인

  • PafMotor·PafPulse 생성자와 두 바인더, PafControl의 포인터 저장
  • PafControl의 기준값 쓰기 두 경로 (4건)
  • 같은 객체를 읽는 소비자의 잔여값 계산

정적 분석 코드를 읽어 판단

  • PafDrive와 PafMovableObject의 기준값 쓰기 두 곳
  • 보정값 M+0x148을 만드는 계산
  • PafMotor +0x68 소비자의 분기

모델 시험 조건으로 정한 것

  • 할당 주소와 초기 factory 상태 (전체 초기화는 실행하지 않음)
  • PafMovableObject의 word, PafControl 분기값, 기존 Pulse 상태
  • 소비자 진입 때 r0에 넣은 수치

미확인 확인하지 않은 것

  • M+0x4c의 비영값과 설정 word의 원래 출처
  • PafMotor +0x56/+0x68의 비영값 생산자
  • 렌즈별 보정 레코드, 물리 단위, 연속 AF 동작

배경: 왜 기준값의 출처를 찾는가

모드 1 문서의 피드백 계산에서 로컬 호출자는 Pulse+0xa88에서 피드백 수치를 빼고 그 결과를 목표값 Pulse+0x2e와 비교해 요청 3을 부를지 정했습니다. 그때 +0xa88은 시험 값으로 넣었습니다. 이 문서는 그 값을 실제로 쓰는 코드를 찾습니다.

쉽게 말하면

계산기에 “기준점”이 하나 들어 있고 새 피드백이 올 때마다 기준점과의 차이를 봅니다. 앞 문서는 그 기준점을 손으로 넣어 계산만 확인했습니다. 이 문서는 기준점을 적어 넣는 쪽을 찾아, 적어 넣은 값이 같은 계산기로 들어가는지 확인했습니다.

생산자와 소비자는 같은 PafPulse 객체를 씁니다

원본 바인더가 PafMotor와 PafControl에 같은 PafPulse 주소를 씁니다. 그래서 PafControl이 쓴 기준값을 PafMotor 쪽 소비자가 읽습니다.

AfMotorFactory 초기화의 원본 코드는 PafMotor 0xec바이트를 factory +0xc에, PafPulse 0xab4바이트를 +0x10에 둡니다. 이 실행에서는 원본 생성자와 두 바인더를 실행했고 전체 초기화 대신 필요한 factory 슬롯만 준비했습니다.

원본 바인더 하나가 PafMotor +0x14에 Pulse를, 다른 하나가 Pulse +0x10에 PafMotor를 기록합니다. PafControl도 같은 factory 슬롯에서 Pulse를 읽어 자기 +0x34에 기록합니다.

객체 연결의 주소
항목주소
AfMotorFactory 초기화 (객체 배치)0x52f08c74
ROM vtable +0xc (PafMotor / PafPulse)0x52f0b380 / 0x52f0dde0
PafMotor +0x14 ← Pulse0x52f0b46c

PafControl +0x34 ← Pulse0x52cad944

근거: 실행 기록과 원본 구간 해시

기준값을 쓰는 명령은 네 곳입니다

네 곳 모두 보정값이나 기존 기준값을 바탕으로 Pulse+0xa88을 고칩니다. 두 곳은 실행했고 두 곳은 코드를 읽어 확인했습니다.

보정값 d는 원본 0x52cbeba4가 만듭니다. M +0x148의 signed word 절댓값에 M +0x3c의 부호를 붙이고 PafControl +0x74가 1이면 부호를 한 번 더 뒤집습니다. 아래 쓰기에서 기준값은 32비트, 변화량은 하위 16비트입니다.

기준값 P+0xa88을 쓰는 네 명령
쓰기 명령값과 대상확인 방식
0x52cb2c64PafControl +0x34의 P에 M[+0x4c] + d를 씁니다. P+0x5a에는 새 값에서 이전 기준값을 뺀 결과를 씁니다.확인 0x52cb2c24부터 따로 실행. 그 앞의 0x52cb9908의 비영 반환을 요구하는 분기는 정적 분석
0x52cb2e28같은 P에 M[+0x4c] + d − P[+0xe8]를 씁니다. P+0x5a에는 같은 방식으로 변화량을 씁니다.확인 0x52cb2ba8부터 실행. P+0x21이 0이 아닌 분기
0x52cb9e10PafDrive +0x28의 P에 씁니다. 한 경로는 M +0x44에서 값을 읽고, 다른 경로는 보정값과 기존 기준값을 씁니다.정적 분석 분기와 0x52cb8500의 객체 연결
0x52cbeb8cM +0x1c의 P에 스택에 준비한 값을 씁니다. 그 앞의 명령이 P +0x36과 기존 기준값의 하위 16비트 가운데 하나를 고릅니다.정적 분석 선택, 스택 저장, 0x52cbe5ec의 객체 연결

M +0x148을 쓰는 원본 0x52cbea90도 읽었습니다. M +0x20이 가리키는 설정 객체의 +0xf4 word와 Pulse +0x56을 곱합니다. 이어 부호 있는 값의 256 나눗셈과 그 앞 호출의 결과에 따른 부호 처리를 거칩니다. 실행에서는 이미 계산된 M의 값을 시험 조건으로 넣었습니다. M +0x4c의 비영값 출처와 설정 word의 원래 저장소는 확인하지 못했습니다.

PafMotor의 두 보정 필드는 아직 출처를 모릅니다

PafMotor +0x56/+0x68은 생성자가 0으로 만든 뒤 다시 쓰는 코드를 찾지 못했습니다.

PafMotor 생성자의 0x52f0b57c와 0x52f0b5a0이 +0x56/+0x68을 0으로 초기화합니다. 네 실행에서 이후 두 필드를 쓴 명령은 없었습니다. PafMotor 인접 코드 0x52f0b354–0x52f0ddb4를 정렬된 A32 직접 오프셋으로 검사해도 이 두 쓰기만 나왔습니다. 다른 모듈의 별칭, 블록 복사, 계산한 주소, Thumb 코드의 쓰기는 이 검사에 들어 있지 않습니다.

0x52f0e3f4의 +0x56 쓰기는 PafPulse가 대상입니다. 렌즈 관련 조건에 따라 값이 달라질 수 있으며 PafMotor의 같은 오프셋 필드에는 이 결과를 적용할 수 없습니다. 별도의 PafMotor 소비자 0x52f0cdd0은 +0x68이 0이 아니면 +0x5c에 ROM 기본값을, +0x5a에 +0x68의 값을 씁니다. 인수 r1이 0이 아니면 200을 더한 하위 16비트를 씁니다. 이 분기는 코드로만 읽었습니다.

한계와 남은 과제

  • 남은 생산자 M+0x4c의 비영값, 설정 word의 원래 저장소, PafMotor +0x56/+0x68의 비영값 생산자는 찾지 못했습니다. 이어지는 조사는 PafMotor와 PafPulse의 입력값 경로에 있습니다.
  • 실행하지 않은 쓰기 PafDrive와 M의 쓰기 두 곳은 정적 분석입니다.
  • 하드웨어와 물리 의미 레지스터 읽기를 실행하지 않았습니다. 렌즈별 저장 보정 레코드, 거리·각도·시간 단위, 모터의 물리적 종류, 연속 AF 동작은 확인하지 않았습니다.

재현 조건과 실행 범위

원본 RTOS 또는 그것을 담은 decoded 파일 하나로 네 실행을 재현합니다.

  • Unicorn 2.1.4의 Cortex-A7 기본 실행과, 호출자 저장 레지스터·NZCV를 바꾼 Cortex-A7·A15 대조가 일치했습니다. 두 입력의 결과 JSON도 바이트 단위로 같았습니다.
  • 각 실행은 실행 범위, 쓰기 주소·폭·값, 인접 필드의 카나리, RX 원본 영역 전체의 SHA-256을 확인합니다.
  • 메모리·서비스 설정의 일부는 모형으로 넣었습니다. 레지스터 읽기와 장치 반환값은 만들어 넣지 않았습니다.
python -B verify_af_feedback_producers.py rtos.bin --output af-producers-rtos.json
python -B verify_af_feedback_producers.py decoded.bin --output af-producers-decoded.json
python -B -m unittest discover -s tests -p test_af_feedback_producers.py

-O를 쓰지 않고 아직 없는 출력 경로를 지정합니다.
