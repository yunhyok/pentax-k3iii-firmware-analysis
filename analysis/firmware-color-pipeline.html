펌웨어에서 확정한 RAW→JPEG 색 처리 경로

카메라가 JPEG의 색을 정할 때 쓰는 설정 계산 코드를 실제 펌웨어 2.20에서 꺼내 PC에서 그대로 실행했습니다. 그렇게 만든 색을 카메라가 직접 저장한 JPEG 파일과 비교해 어디까지 맞는지 확인했습니다.

  2. 카메라의 설정 계산 전체를 PC에서 실행했습니다
  3. 처리 순서와 각 단계의 뜻

  7. Custom Image마다 달라지는 것
  8. 카메라 JPEG과의 대조
  9. 기존 검증기를 실제 펌웨어로 다시 돌렸습니다

핵심 요약

  • 카메라가 사진 한 장의 영상 처리 설정을 만드는 루틴 전체를 PC 에뮬레이터에서 실행했습니다. Custom Image 19개 모두 끝까지 돌았고 펌웨어의 자체 검사(assert)는 한 번도 걸리지 않았습니다.
  • 색 행렬의 출력은 선형 sRGB입니다. AdobeRGB를 고르면 덧붙는 행렬이 표준 “선형 sRGB → 선형 Adobe RGB” 행렬과 0.0003 안에서 같았습니다. 감마 곡선의 출력도 sRGB로 부호화된 값입니다.
  • 노출 기준은 펌웨어가 DNG의 BaselineExposure를 계산하는 식에서 얻었습니다. 기준 노출 이득에서 이 식의 배율은 1448/2048이고 0.5 EV에 해당합니다.
  • 색·톤 매개변수를 하나도 맞추지 않은 계산이 카메라 JPEG과 평탄 블록 평균 ΔE00 0.85(Natural)와 1.38(Bright)만큼 달랐습니다. 채도가 높은 평탄 블록에서는 0.42와 0.77이었습니다.
  • 한계: ISO 100 장면 두 장뿐이고 표본은 카메라 펌웨어 1.01·1.10으로 찍혔습니다. 카메라 JPEG과 대조한 모드는 Natural과 Bright 둘입니다. 다축 색 보정의 식, 화이트밸런스 단계, 무채색 영역의 밝기 차 원인은 모릅니다. Lightroom은 실행하지 않았습니다.

확인 원본 코드 실행과 계산으로 확인

  • 설정 루틴 Make 전체를 19개 모드에서 실행, 자체 검사 실패 0회
  • 색공간 행렬이 표준 sRGB→AdobeRGB 행렬과 최대 0.000277 차이
  • AdobeRGB 감마 표가 sRGB 복호 후 감마 2.2 재부호화와 10비트 0.947단계 안에서 일치
  • 카메라 JPEG 두 장과 PC에서 계산한 색차(맞춘 매개변수 0개)

정적 분석 코드를 읽어 판단

  • BaselineExposure 계산식과 그 상수(루틴은 실행하지 않음)
  • 메뉴 값이 들어가는 입력 필드의 위치와 뜻
  • DNG ColorMatrix1·2 표를 채널별 값으로 나누어 쓰는 경로

모델 연구자가 정한 조건

  • 운영체제 기능의 대역, 나열한 입력 밖의 값은 모두 0
  • 레지스터가 픽셀에 하는 일은 공개 헤더의 설명을 따름(회로는 실행하지 않음)
  • 톤 제어 표는 히스토그램 입력이 없어 항등, 화이트밸런스는 RAW 파일의 촬영 시 값

미확인 확인하지 않은 것

  • 다른 ISO·조명, Natural·Bright 밖 모드의 카메라 JPEG 대조
  • 다축 색 보정 블록의 하드웨어 식, 화이트밸런스 단계
  • 무채색 영역에서 카메라 JPEG이 한두 단계 밝은 원인
  • Lightroom에서의 결과

배경: 설정을 만드는 코드와 공개 레지스터 설명을 이었습니다

K-3 Mark III의 영상 처리 회로에는 RAW에서 얻은 RGB를 JPEG용 YCbCr로 바꾸는 블록이 있습니다. 공개 SDK 헤더는 이 블록을 R2Y라고 부릅니다. CPU는 픽셀을 직접 고치지 않고 이 블록의 레지스터에 넣을 값을 계산합니다.

펌웨어만 읽으면 어떤 값을 쓰는지까지만 압니다. 회로가 그 값으로 무엇을 하는지는 레지스터 설명이 있어야 압니다. 같은 SoC 계열의 공개 헤더 im_r2y.h와 __fr2y6a.h가 그 설명을 줍니다. 레지스터 묶음은 주소 순서로 아래와 같습니다. 펌웨어의 레지스터 덤프 문자열도 같은 이름(R2Y_Core.CCA0.CC0CTL, R2Y_Core.GAM.GMCTL, R2Y_Core.CSP.CSYCTL 등)을 씁니다.

  1. OFG오프셋·화이트밸런스 이득
  2. CCA0색 행렬 CC0
  3. MCC다축 색 보정
  4. BTC/TC톤 제어
  5. GAM감마
  6. CCA1 · YC두 번째 행렬 · YC 변환
  7. CSP채도 억제(YNR·윤곽 처리 뒤)

자매 기종 GR III의 공개 분석도 같은 계열 펌웨어를 다룹니다. 그 분석은 ImageTuning 15단계를 나열하고 설정 루틴 전체를 Unicorn에서 돌리는 방법을 보였습니다. 이 연구의 에뮬레이터 배치는 그 구성을 따랐습니다. 다만 GR III 분석은 CC0CTL의 비트 1이 휘도 혼합 단계를 켠다고 적었습니다. 공개 헤더에서 이 필드는 소수점 위치이므로 이 문서는 헤더를 따랐습니다.

쉽게 말하면

카메라 안의 계산 담당이 회로에 건네는 작업 지시서를 PC에서 그대로 다시 써 보았습니다. 지시서의 각 칸이 무슨 뜻인지는 회로 제조사가 공개한 설명서에서 찾았습니다. 그 지시대로 색을 계산해 카메라가 실제로 만든 JPEG과 나란히 놓았습니다.

관련 문서와 나눈 범위는 다음과 같습니다.

카메라의 설정 계산 전체를 PC에서 실행했습니다

설정 루틴 ImageTuningStill::Make가 15개 단계를 차례로 부르며 레지스터 이미지를 채웁니다. 이 루틴을 메뉴 수준의 입력만 넣고 19개 모드에서 끝까지 실행했습니다.

단계 이름은 펌웨어의 이름 그대로입니다. 색에 관여하는 다섯 단계는 출력 레지스터를 읽어 역할을 확인했습니다. 나머지 단계의 한국어 풀이는 이름으로 짐작한 것이고 출력을 따로 분석하지 않았습니다. 채도 억제(CSP) 묶음은 레지스터 이미지에서 읽었고 어느 단계가 썼는지는 나누어 보지 않았습니다.

에뮬레이터에는 카메라의 운영체제가 없습니다. 그래서 C++ new/delete, assert, 풀 할당기, 정적 초기화 보호, 잠금·해제, 기종 변형 표의 캐시된 행을 대역 함수로 바꿨습니다. 윤곽 강조 단계와 단계 뒤의 두 처리(0x531275d0, 0x53127888)는 건너뛰었습니다. 뒤의 것은 DNG 색 태그를 준비하는 루틴이며 노출 기준에서 읽은 내용을 다룹니다.

처리 순서와 각 단계의 뜻

RAW 값은 화이트밸런스 이득, 색 행렬, 감마, YC 변환, 채도 억제를 거쳐 JPEG이 됩니다. 각 단계의 값은 실행한 코드에서, 그 값의 뜻은 공개 헤더에서 얻었습니다.

두 번째 행렬 CC1은 모든 모드에서 꺼져 있어 그림에서 뺐습니다. 노이즈 감소와 윤곽 처리도 색 경로에서 다루지 않았습니다.

색 행렬의 출력은 선형 sRGB입니다

AdobeRGB를 고를 때만 곱해지는 행렬이 표준 “선형 sRGB → 선형 Adobe RGB (1998)” 행렬과 같았습니다. 그 앞까지의 행렬은 화이트밸런스를 마친 센서 RGB를 선형 sRGB로 바꿉니다.

색 행렬은 네 행렬을 곱해 만듭니다. 순서는 out = A·F·M·B·in이고 in은 화이트밸런스를 마친 센서 RGB입니다. 이 순서는 색 처리 알고리즘에서 이미 다뤘습니다.

B 공통 행렬
디스크립터 32개가 모두 같은 포인터를 씁니다. 각 행의 합은 정확히 1.0입니다.
M 모드 행렬
Custom Image마다 다릅니다. Natural은 단위 행렬입니다.
F 채도 행렬
채도 슬라이더 가운데(인덱스 4)에서 단위 행렬입니다.
A 색공간 행렬
색공간이 AdobeRGB일 때만 곱합니다.

A를 표준 행렬과 비교하니 가장 큰 차이가 0.000277이었습니다. 1/8192 단위로 두 단위쯤입니다. A가 선형 sRGB를 받으므로 그 앞의 F·M·B는 선형 sRGB를 내보냅니다. AdobeRGB 모드의 행렬도 sRGB 모드의 행렬에 A를 곱한 값과 0.005 안에서 같았습니다. 지금까지 경로 문서와 계산식 문서가 미확인으로 남긴 “행렬이 받는 RGB의 원색과 전달함수”는 이렇게 정해졌습니다.

레지스터 값도 이 해석과 맞습니다. 19개 모드 모두 소수점 위치가 1이고 각 행의 합이 정확히 256입니다. 256이 1.0이므로 회색은 회색으로 남습니다. 행렬은 화이트밸런스나 광원에 따라 바뀌지 않습니다. 모든 조건에서 공통 행렬 하나를 쓰고 화이트밸런스는 그 앞의 OFG 블록에서 채널 이득으로 처리합니다. 이 이득은 더 따라가지 않았습니다.

보완

색 처리 알고리즘은 대각 원소를 보정해 “행의 합이 2 × gain”이 되게 한다고 적었습니다. 식은 맞습니다. 여기서 gain은 행렬 전체의 배율입니다. 기본 gain 인덱스 8의 표 값 128과 실행 중 gain 0x100이 만나면 gain은 128이고 행의 합은 256이 됩니다. 정지 사진의 실행 중 gain은 SI+0x3e1b6에서 오며 0x100~0x200으로 제한됩니다.

감마 곡선과 노출 기준

감마 곡선의 출력은 sRGB로 부호화된 값입니다. 곡선 입력의 노출 기준은 펌웨어 자신의 BaselineExposure 식으로 정해지며 기준 이득에서 0.5 EV 차이가 납니다.

곡선에서 하드웨어 표로

Gamma 단계는 256점짜리 16비트 곡선을 계산합니다. 최댓값은 16384이고 12비트 입력 눈금에서 16마다 한 점입니다. 하드웨어 표는 이 곡선의 위쪽 10비트입니다. 기준값 256개와 기준값마다 4비트 증분 16개(64비트 워드 하나)로 구성됩니다. 곡선 하나를 쓰는 모든 모드에서 “기준값 = 곡선 >> 4”가 성립했습니다. 출력은 10비트입니다.

AdobeRGB 표가 알려 준 곡선의 뜻

AdobeRGB를 고르면 펌웨어 곡선은 그대로이고 하드웨어 표만 바뀝니다. 바뀐 표는 sRGB 표를 sRGB 함수로 풀고 Adobe RGB 감마(563/256, 약 2.2)로 다시 감은 값과 같았습니다. 가장 큰 차이는 10비트 한 단계의 0.947배였습니다. 펌웨어가 곡선 출력을 sRGB 부호화 값으로 다룬다는 증거입니다. 그래서 선형 톤 곡선은 감마 곡선을 sRGB로 복호한 것으로 정했습니다.

중간 회색 기준점

노출 이득이 N일 때 곡선의 꺾이는 점은 4096 가운데 입력 512·N/8192에 놓입니다. N = 8192이면 전체 눈금의 12.5%입니다. 이 점은 출력 전체의 약 0.47로 옮겨지며 sRGB 8비트 코드로 약 119입니다.

노출 이득과 BaselineExposure 식

카메라는 노출 이득 G를 제조사 태그 0x009d에 G/4로 저장합니다. DNG 색 태그를 준비하는 루틴 0x53127888은 이 이득으로 BaselineExposure를 계산합니다. 코드를 읽어 얻은 식은 다음과 같습니다.

BaselineExposure = log2( 1448 / ( c × (maxval / (white − black)) × (G / 8192) / d ) )

c      = 2048 (SI+0x2bc9 플래그가 켜지면 1024)
maxval = 2^bits − 1
G      = 노출 이득 (info+0x82d8)
d      = 1 (SI+0x2bcc가 켜지지 않았을 때)
저장할 때 분모 65536

식의 상수 2048.0, 1024.0, 1/8192, 1448.0, 65536.0은 펌웨어 이미지에서 직접 읽어 확인했습니다. 1448은 1024·√2에 가깝습니다. 기준 이득 G = 8192에서 화이트 레벨이 거의 꽉 차면 배율은 1448/2048이 되고 BaselineExposure는 약 −0.5 EV입니다.

YC 변환, 채도 억제, 다축 색 보정

YC 변환은 JFIF 표준 행렬 그대로입니다. 채도 억제는 아주 어두운 곳과 밝은 곳에서 색차를 줄입니다. 다축 색 보정은 기본 세트만 들어 있고 효과를 찾지 못했습니다.

YC 변환은 JFIF 행렬입니다

색상 슬라이더가 0이면 19개 모드 모두 YC 변환 계수가 JFIF(BT.601) 정수 행렬과 정확히 같았습니다. 256으로 나누는 값입니다.

채도 억제는 휘도에 따라 색차 이득을 바꿉니다

채도 억제(CSP)는 모든 모드에서 켜져 있고 휘도를 기준으로 씁니다(혼합비 8). 색차 이득은 10비트 휘도에 대한 구간 선형 함수입니다. 모양은 모든 모드에서 같습니다. Monochrome은 여기에 “색차 고정”을 더 켜서 Cb와 Cr을 0으로 둡니다.

이 단계를 빼면 결과가 나빠집니다. Imaging Resource 표본에서 채도 5~15의 평탄 블록은 단계를 빼면 1.81, 넣으면 1.09였습니다.

다축 색 보정은 모델에 넣지 않았습니다

다축 색 보정(MCC) 블록은 모든 모드가 같은 기본 세트를 씁니다. 영역 경계와 영역 번호가 모두 0이어서 모든 픽셀이 영역 0에 들어갑니다. 하드웨어가 이 값으로 무엇을 계산하는지는 공개되지 않았습니다. 두 가지 해석을 시험했고 둘 다 결과를 나쁘게 만들었습니다.

  • 기본 행렬을 밝은 영역의 채도 감소로 해석: 밝고 채도 높은 블록이 0.87에서 1.09로 나빠졌습니다.
  • 저장된 값을 그대로 행렬로 해석(1.0 = 1024): 무채색 블록이 1.4에서 2.2로 나빠졌습니다.

그래서 이 블록은 효과가 없는 것으로 두었습니다. 식을 모르는 상태이므로 미확인으로 남깁니다.

카메라 JPEG과의 대조

색·톤 매개변수를 하나도 맞추지 않고 계산한 색이 카메라 JPEG과 평탄 블록 평균 ΔE00 0.85(Natural)와 1.38(Bright)만큼 달랐습니다. 모드를 바꿔 넣으면 차이가 크게 벌어져 모드 행렬이 구별됩니다.

방법

  1. RAW 준비 2×2 센서 셀을 묶어 절반 크기 영상을 만들고 RAW의 촬영 시 화이트밸런스를 씁니다.
  2. 펌웨어 색 단계 적용 위에서 정한 행렬·감마·YC 변환·채도 억제를 그대로 계산합니다. 맞춘 색·톤 매개변수는 0개입니다.
  3. 위치 맞춤 카메라 JPEG에는 렌즈 보정과 잘라 내기가 들어 있어 아핀 정합(ECC)으로 기하만 맞춥니다.
  4. 비교 16×16 픽셀 블록 평균끼리 CIEDE2000(ΔE00)을 계산합니다. 카메라 JPEG은 자기 색공간으로 해석합니다. “평탄” 블록은 윤곽이 없는 블록입니다.

모두 카메라가 저장해 둔 파일을 PC에서 계산한 것입니다. 이 표의 값은 펌웨어 색 단계를 직접 계산한 “모델” 결과입니다. 같은 비교를 DCP 프로파일로 한 값은 펌웨어 값으로 만드는 색 프로파일에 있습니다.

남은 밝기 차

두 표본 모두 무채색 영역에서 카메라 JPEG이 모델보다 8비트 기준 한두 단계 밝습니다. 제조사 태그를 보면 두 장 모두 섀도 보정(Shadow Correction)이 Auto로 찍혔습니다. 에뮬레이션의 톤 제어 표는 항등이어서 이 보정이 빠졌을 가능성이 있습니다. 원인은 확정하지 못했습니다.

기존 검토는 펌웨어 파일 없이 이루어졌습니다. 펌웨어에 의존하는 검증기 101개를 실제 파일로 다시 돌렸고 모두 재현되었습니다.

펌웨어는 RICOH IMAGING의 공식 다운로드 페이지에서 받은 k3III_v220.zip의 fwdc233b.bin입니다. 파일과 복호 스트림의 SHA-256이 evidence.json과 같았습니다.

돌리지 못한 것은 세 가지입니다.

  • rmw-scope의 펌웨어 모드: accepted31.json이 필요합니다.
  • tools/verify_recompiled_kernels.py와 verify_recompiled_integration.py: 버전을 고정한 Zig Windows 실행 파일이 필요합니다.
  • tools/check_ui_render_chain.py: Q7 펌웨어가 필요합니다.

이식성 결함 하나를 찾아 고쳤습니다. verify_bank_writers.py가 Windows에만 있는 TEMP 환경 변수를 읽고 있었습니다.

한계와 남은 과제

  • 미확인 표본 범위: 장면 두 개, 둘 다 ISO 100입니다. 표본은 카메라 펌웨어 1.01과 1.10으로 찍혔고 분석한 펌웨어는 2.20입니다. 고감도와 다른 조명은 시험하지 않았습니다.
  • 미확인 모드 범위: 19개 모드를 모두 실행했지만 카메라 JPEG과 대조한 것은 Natural과 Bright뿐입니다.
  • 미확인 남은 밝기 차: 무채색 영역에서 카메라 JPEG이 한두 단계 밝습니다. 섀도 보정 Auto와 항등 톤 제어 표의 차이로 짐작하지만 확인하지 않았습니다.
  • 미확인 다축 색 보정과 화이트밸런스: 다축 색 보정은 식을 몰라 넣지 않았습니다. 화이트밸런스 이득과 그 앞 단계(블랙 레벨, 디모자이크)는 추적하지 않았고 RAW의 촬영 시 값을 썼습니다.
  • 모델 에뮬레이션 조건: 운영체제 기능은 대역이고 나열한 필드 밖의 입력은 0입니다. 카메라에서는 섀도·하이라이트 보정이 장면마다 톤 제어 표를 바꿀 수 있습니다. Auto Select의 곡선도 카메라에서는 장면에 따라 달라집니다.
  • 모델 하드웨어 해석: 회로 자체는 실행하지 않았습니다. 레지스터가 픽셀에 하는 일은 공개 헤더의 설명을 따랐습니다.
  • 미확인 Lightroom: 실행하지 않았습니다. PEF 파일에 Lightroom이 쓰는 BaselineExposure가 카메라가 DNG에 쓰는 값과 같은지도 확인하지 않았습니다. 프로파일 쪽 한계는 펌웨어 값으로 만드는 색 프로파일에 있습니다.

재현 방법

펌웨어는 사용자가 RICOH IMAGING에서 직접 받아야 합니다. 도구는 실행할 때 decoded.bin에서 값을 읽으며 저장소에는 펌웨어, 계수 표, 프로파일이 없습니다.

에뮬레이터·검사기
unicorn==2.1.4, numpy
카메라 JPEG 대조
위에 더해 rawpy, opencv-python-headless
python inspect_firmware.py fwdc233b.bin --output-dir .private/my-decode
python tools/check_firmware_color.py .private/my-decode/decoded.bin \
  --compare analysis/firmware-color-pipeline.json
python tools/compare_camera_jpeg.py IMGP0001.PEF --jpeg IMGP0001.JPG \
  --decoded .private/my-decode/decoded.bin

첫 명령은 펌웨어를 복호합니다. 둘째 명령은 19개 모드를 실행해 공개 JSON의 해시·구조와 비교합니다. 셋째 명령은 자기 RAW와 카메라 JPEG 한 쌍을 비교합니다(--jpeg를 빼면 RAW 안의 미리보기를 씁니다). 단위 시험 tests/test_firmware_color_model.py는 환경 변수 PENTAX_K3III_DECODED가 있으면 펌웨어 실행 시험까지 돌립니다.
