M0·BOOT 주소 매핑: 같은 오프셋, 미확정인 물리 연결

M0의 0x2000fffc와 BOOT의 0x0100fffc가 같은 물리 SRAM을 가리키는지는 아직 확인하지 못했다. M0 기록 주소와 BOOT 소비 주소는 각 기준 주소에서 +0xfffc에 놓인다. 이번에는 Ricoh가 배포한 다른 M0 바이너리도 살펴봤다. BOOT의 MMU 설정과 대조해 이 연결을 뒷받침하는 근거와 남은 경계를 구분했다. 주소·명령·비교 파일 근거

BOOT의 0x50b0003c..0x50b00050은 SCTLR을 읽고 bit 0, 즉 MMU 활성 비트를 지운 뒤 다시 기록한다. 제공된 BOOT 전체를 4바이트 경계의 ARM 명령으로 검사했을 때 SCTLR 기록은 이 지점 하나였다. 따라서 이 진입 경로를 일반적인 A7 페이지 테이블 변환으로 설명할 근거는 없다. 이 결과가 버스 alias나 선행 코드의 하드웨어 설정을 배제하지는 않는다. BOOT 원본 대조 결과

Ricoh 공식 OSS 묶음의 stubby-1.60.1/configs/config-sc2000-rtos.h 138–142행은 SRAM base를 0x01000000, 크기를 0x10000으로 정의한다. 같은 묶음의 이전 M0 RS_MILBCM0-ES3.bin에서도 0x3ffe4a24 / 0x3ffe4ee0이 0x2000fffc에 1·2를 기록한다. 파일 SHA와 해당 구간을 원본 archive에 대조했다. 반복되는 소프트웨어 규약을 확인한 것이며 현재 2.20 M0와 동일한 바이너리라는 뜻은 아니다. 비교 범위·해시·리터럴

HYPOXIC의 SC2000A/GP1 실측 연구는 다른 기기의 M0가 메모리를 준비한 뒤 A7을 시작하는 구조와 일부 주변장치 주소의 +0x30000000 대응을 설명한다. 그러나 이번 SRAM 두 주소의 차이는 0x1f000000이다. 주변장치의 주소 차이를 SRAM에 그대로 적용하거나 다른 기기의 인증 정책을 K-3 III에 대입하지 않았다.

BOOT의 RTOS 적재와 인증 검사 범위

BOOT는 파티션 표 index 1의 bank 값을 읽고 선택한 설명자에서 목적지·진입 주소·시작 블록·길이를 가져온다. 저장된 블록 수가 0이면 바이트 길이를 512로 나눠 올림한다. 읽기 실패는 표 사본 fallback으로 연결된다. 선택한 성공 경로에서는 진입 주소를 0x50b054c4와 0x4fffff20에 저장하고 공유 위치 0x50b810f0에 0xd1c3b5a7를 쓴 뒤 SEV를 실행한다. boot.relations

하위 읽기 함수 0x50b03f04는 0x50b042e0을 거쳐 명령 구성 함수 0x50b01f18로 연결된다. 이 읽기 경로의 방향 값 2에서는 한 블록이면 명령값 0x11, 여러 블록이면 0x12를 선택한다. 후속 조사에서 명령 제출 0x50b01558과 대기 0x50b01774를 전송 상태·응답 검사까지 확장했다. 하위 제어 경로

기록한 BOOT 범위에서는 저장소 반환 상태, 설명자 유무, 코어를 깨운 뒤의 진입 주소 조건을 확인했다. 암호학적 검증으로 분류할 연산은 이 범위에서 식별하지 못했다. 이는 BOOT 전체, 하위 드라이버, Boot ROM, 다른 단계나 하드웨어의 인증 기능이 없다는 증거가 아니다. 수정된 펌웨어가 수락된다는 결론도 내리지 않았다.

그룹 등록에서 동일 객체의 응답까지

표·부트 헤더·BOOT 이미지의 기록 순서

패키지 순회가 완료되는 분기에서 0x52ff2af0 → 0x52ff2060이 파티션 표를 기록하고 성공하면 0x52ff2b0c → 0x52ff20d0이 부트 헤더를 기록한다. 그다음 0x52ff2b28 → 0x52ff21c8이 BOOT 이미지를 기록한다. 어느 단계든 0을 반환하면 0x52ff2bf4의 실패 경로로 간다. 일반 리소스 payload의 기록 호출은 이 완료 분기보다 앞에 있다. 기록 순서·인수 근거

헤더 생성 함수는 FwPartition byte +0x10을 헤더 +0x40에 직렬화한다. 0x52ff5304에 0과 1을 전달해 얻은 값은 각각 +0x44 = 0, +0x48 = 0xffff에 저장된다. 앞서 확인한 BOOT의 사본 순서 selector와 사본 A/B 시작 블록 입력에 대응한다. 현재 확인된 기본값 0의 경로에서는 A가 블록 0이고 B가 생략 표식이다. 비제로 값을 새로 만드는 코드는 이 함수에 없다.

따라서 선택값은 네 범주로 구별해야 한다. FwPartition byte +0x10, BOOT가 읽는 각 리소스 레코드 +4, 부트 헤더의 표 사본 selector, eMMC의 partition 선택값이다. 객체 byte가 헤더 selector로 복사되는 관계는 확인했지만 리소스별 bank 필드와 항상 일치한다는 근거는 없다. 0x52ff1ea8의 레이아웃 생성과 0x52ff586c의 리소스 기록에서 레코드 +4를 바꾸는 쓰기는 확인하지 못했다. 다른 생산자·alias·넓은 store·복사 경로는 남아 있다.

boot1 쓰기 래퍼 0x52ff5ad0는 lock → partition 1 선택 → 쓰기 → partition 0 복귀 → unlock 순서다. 진단 문자열은 선택값 1을 boot1으로 명명한다. 이 값 1은 리소스의 bank 1을 뜻하지 않는다. 복귀 함수의 반환값은 검사하지 않고 원래 쓰기의 결과를 반환한다. 또한 헤더 생성 함수 자체는 할당 버퍼 +0x14–0x3f를 초기화하지 않는다. 할당기의 초기화 보장과 실패 후 상태 처리는 별도 추적이 필요하다.

원본 ARM을 사용한 19개 합성 검사에서 외부 호출은 명시적으로 대체했다. 검사에서는 헤더 필드, 표 읽기·쓰기 인수, boot1 선택·복귀 순서와 단계별 실패 분기를 확인했다. bank 1·255 입력은 직렬화 검증용 합성 값이며 실기에서 이 값을 생산한다는 증거가 아니다. 검사 조건·결과 · 재현 도구

M0의 0x3ffe47f0는 헤더의 +0x40 / +0x44 / +0x48로 테이블 사본 순서를 정한다. 0x3ffe48aa의 읽기 요청은 0x87블록과 목적지 0x50b70100을 전달하지만, CPU의 테이블 접근은 0x70b70100을 사용한다. 이 읽기 인수에서는 두 주소의 0x20000000 차이를 명령으로 확인했다. 전체 버스 주소 매핑까지 증명한 것은 아니다.

테이블 첫 레코드가 존재하면 +4의 하위 16비트로 bank를 선택하고 0x434×bank의 설명자를 사용한다. 이미지 읽기가 성공한 분기 0x3ffe492a..0x3ffe4938에서 설명자 +0xc를 0x3fffa800에 저장한다. 진입 주소가 실제 BOOT를 가리키는지는 매체의 레코드 값에 달려 있다. 이번 합성 검사의 BOOT 주소는 입력 예시이며 장치에서 얻은 값이 아니다.

적재 작업 0x3ffe4df4는 0x3ffe4974의 반환값이 0일 때 0x3ffe4db4를 호출한다. 이 함수는 진입 주소가 0이 아니면 0x20000000 = 0xe59ff018, 0x20000020 = 진입 주소, 0x2000fffc = 1을 순서대로 기록한다. DSB 뒤 0x4d021090 = 0xf3f를 쓴다. 값 2를 기록하는 별도 경로는 0x3fff00a0의 후반부이며 0x3fff01da의 모드 저장 뒤 같은 DSB·레지스터 기록이 있다. 이 순서는 A7 진입 준비 경로로 해석되지만 실제 코어 기동은 실행하지 않았다. 13개 Thumb 합성 검사

Ricoh 공개 Stubby의 configs/config-sc2000-rtos.h 138–142행은 SRAM 기준 주소 0x01000000과 크기 0x10000을 정의한다. BOOT의 0x0100fffc는 이 정의의 마지막 4바이트에 해당한다. 다만 M0의 0x2000fffc가 같은 SRAM을 보는 주소라는 매핑 근거는 찾지 못했다. 동일한 오프셋과 모드 값만으로 두 접근을 확정 연결하지 않았다. Ricoh 공식 OSS 패키지

이 M0 범위에서는 장치 선택, 메모리 준비, 읽기 반환값과 진입 주소 조건을 확인했다. 암호학적 인증으로 식별할 연산은 확정하지 못했다. 하위 드라이버·메모리 초기화의 미추적 부분과 M0 이전 단계는 남아 있으며, 이를 근거로 Boot ROM 인증이 없거나 변경한 펌웨어가 수락된다고 결론내릴 수 없다.
