이번 추적의 결론

CheckUpdateFirmware 요청 0x4642010c를 처리하는 분기와 응답 0x27408410의 소비자를 연결했다. 하위 저장소 가상 함수는 객체 생성·ID 등록·조회·캐스팅을 따라 Emmc의 읽기·쓰기 함수까지 특정했다. 별도 BOOT에서는 파티션 표를 리소스 슬롯 2의 주소로 읽고 준비 표식을 쓰는 생산 경로를 확인했다. 판정·주소·호출 근거

이번에는 레코드 +4를 포함한 테이블 전체 읽기와 partition 복귀 실패의 하위 캐시 경로를 연결했다. 쓰기가 성공하면 복귀 실패에도 상위 성공값을 반환하는 조건을 합성 실행으로 확인했다. RTOS 객체의 비제로 bank 생산자, 구체적인 리소스 bank 전환 정책과 선행 Boot ROM 인증은 미확정이다. 테이블 갱신 · 오류 전달 · 인증 경계

CheckUpdateFirmware의 요청과 응답

수신 dispatcher 0x533161e8은 0x53316230에서 요청 ID를 비교하고 0x53316304로 분기한다. 종류 2 선택 0x52fef240, 파일 읽기 0x52fee900, 검증·변환 0x52fefb84가 순서대로 성공하면 0x52fee9b4에서 버전 필드를 추출한다. 이 검증 호출은 앞서 조사한 프로젝트·종류·체크섬·변환 길이 검사에 연결된다. 이전 검사 경로 · receiver.confirmed_paths

처리기는 22바이트 응답을 만들고 byte 0과 0x02–0x14의 u16 필드 10개를 0으로 초기화한다. 버전 값은 선택·읽기·검증이 성공한 뒤 채워진다. 실패 분기에서는 버전 필드가 0인 응답을 사용한다. 응답 발행 0x53315494가 보내는 ID는 0x27408410이며 소비자 0x52c16240은 payload +2 / +4의 u16 값을 0x52c275f8에 전달한다.

두 값이 모두 0이 아니면 결과 생산자는 이벤트 마스크 0x4를 설정하고 하나라도 0이면 0x8을 설정한다. 호출자는 마스크 0xc로 기다린 뒤 0x4가 설정됐을 때 참을 반환한다. 이 참·거짓은 조회 응답에 유효한 두 버전 값이 있는지를 반영한다. 현재보다 새 버전인지 비교하는 판정과는 구분해야 한다. high·low 각각 0 / 1 / 0xffff를 넣은 9개 합성 실행 검사가 이 조건과 일치했다. 문자열·로그 보조 함수 4개는 stub으로 대체했고 이벤트 syscall 0x525b76dc 직전에 중단했다. 범위·stub·결과 · 검증 도구

현재 버전과 비교하는 0x52feef34는 별도 메시지 0x4c410101 경로에 있다. 분기 0x53318be0 이후 updater +0x9c가 UPDATE_WAITING_MESSAGE 상태를 가리키고 종류가 2일 때 0x533192c8에서 호출한다. 이번 결과는 이 조회·응답·버전 검사 상태까지의 분석이며 업데이트 상태 기계 전체를 복원한 것은 아니다.

별도 BOOT가 채우는 리소스 슬롯 2

이번에 조사한 BOOT payload는 21,696바이트다. 벡터의 PC 상대 LDR와 내부 절대 주소가 일치하는 기준 주소 0x50b00000으로 해석했다. 이 주소는 정적 분석 기준이며 실기에서 관찰한 적재 주소가 아니다. 이전에 조사한 LINUX 내부 Stubby와도 별도 구성 요소다. boot.base_evidence

BOOT 시작 경로는 0x50b00888 → 0x50b011c4로 연결된다. 부트 모드로 쓰는 메모리 0x0100fffc의 값이 2가 아니면 리소스 로더 0x50b00a48을 호출한다. 값 2의 warm 경로는 이 로더를 건너뛰고 보존된 진입 주소와 공유 상태를 사용한다. 아래 표 생산 경로는 로더를 호출하는 쪽에서 확인했다.

로더는 0x50adf000의 준비 값을 0으로 초기화한다. 장치의 시작 블록 0부터 2블록을 0x18004000으로 읽은 뒤, 헤더 +0x40의 selector와 +0x44 / +0x48의 사본 A/B 블록 번호를 사용한다. 선택한 블록 번호가 0xffff이거나 읽기·후속 적재가 실패하면 다음 사본을 시도한다. 두 사본 시도 뒤의 실패 분기는 오류 처리로 간다.

표 읽기는 0x50b00c64에서 0x50b03f04를 호출하며 목적지는 0x50b70100, 길이는 0x87블록이다. 읽기 반환값 0을 확인한 뒤 0x50b00c7c에서 0x50adf000 = 0xa55a5aa5를 쓴다. 읽는 양은 135×512 = 69,120바이트다. RTOS 슬롯 2의 예약 길이 69,376바이트와 구분해야 한다.

RTOS 0x52ff528c은 슬롯 2의 준비 상태를 반복 확인하며 준비되지 않았으면 yield한다. 준비되면 기준 주소 getter의 반환값을 0x52ff52c8에서 FwPartition +0x14에 저장한다. 슬롯 2의 초기 기준 주소와 marker 포인터가 각각 0x50b70100, 0x50adf000이므로 BOOT의 생산 위치와 맞는다. 준비 표식은 데이터 사용 가능 상태이며 암호학적 서명으로 해석하지 않는다.

BOOT의 RTOS 적재와 인증 검사 범위

BOOT는 파티션 표 index 1의 bank 값을 읽고 선택한 설명자에서 목적지·진입 주소·시작 블록·길이를 가져온다. 저장된 블록 수가 0이면 바이트 길이를 512로 나눠 올림한다. 읽기 실패는 표 사본 fallback으로 연결된다. 선택한 성공 경로에서는 진입 주소를 0x50b054c4와 0x4fffff20에 저장하고 공유 위치 0x50b810f0에 0xd1c3b5a7를 쓴 뒤 SEV를 실행한다. boot.relations

하위 읽기 함수 0x50b03f04는 0x50b042e0을 거쳐 명령 구성 함수 0x50b01f18로 연결된다. 이 읽기 경로의 방향 값 2에서는 한 블록이면 명령값 0x11, 여러 블록이면 0x12를 선택한다. 후속 조사에서 명령 제출 0x50b01558과 대기 0x50b01774를 전송 상태·응답 검사까지 확장했다. 하위 제어 경로

기록한 BOOT 범위에서는 저장소 반환 상태, 설명자 유무, 코어를 깨운 뒤의 진입 주소 조건을 확인했다. 암호학적 검증으로 분류할 연산은 이 범위에서 식별하지 못했다. 이는 BOOT 전체, 하위 드라이버, Boot ROM, 다른 단계나 하드웨어의 인증 기능이 없다는 증거가 아니다. 수정된 펌웨어가 수락된다는 결론도 내리지 않았다.

그룹 등록에서 동일 객체의 응답까지

이번에 확인한 등록은 메시지마다 수신자를 나열하는 구독 목록이 아니라 그룹 번호로 mailbox를 찾는 등록과 작업 객체의 연결이다. 생성 경로 0x533045dc / 0x5330463c → 0x53304c20이 그룹 1과 4를 등록한다. 송신·수신은 같은 map 0x547bffdc를 0x53304864에서 조회한다. 아래 연결은 할당·초기화·큐 연산이 성공하고 객체 포인터가 유지되는 조건의 정적 경로다. 등록·객체·호출 근거

그룹 1의 작업 루프 0x533044cc는 0x53304ae0 → 0x530edfa0으로 수신한다. 두 조사 메시지는 분류 함수 0x533042d8의 반환값 0 경로를 거친다. 이어 ID의 두 번째 바이트와 0x7f를 AND한 값으로 분기하므로 요청 0x4642010c는 마스크 1, 응답 0x27408410은 마스크 4를 사용한다. 요청은 0x53303c98을 거쳐 0x53315174로 전달된다.

updater factory는 객체를 +0x10에 보관한다. 시작 코드 0x532fe4b0–0x532fe4c0는 그 객체의 포인터를 DomainController +0x30에 넣는다. 이 객체의 secondary 부분은 원래 객체 +4다. 생성자에서 만든 mailbox와 0x530ef074 → 0x530edc60의 송신, 작업 루프 0x530eed94의 수신이 같은 secondary 객체의 mailbox 필드를 사용한다. 수신 뒤 vtable thunk 0x533196e4가 this를 4만큼 되돌려 기존 updater dispatcher로 연결한다.

HTControl은 domain 4를 가진 래퍼를 통해 수신한다. 활성 요청 호출자 0x5254042c–0x5254043c는 0x52c27260의 반환 객체 +4를 읽어 조회 함수를 호출한다. 응답 소비자 0x52c16240도 같은 getter와 +4를 사용한다. 따라서 이 호출 경로의 요청 객체와 결과 설정 객체를 정적으로 연결했다. 실행 중 singleton 교체나 수신 성공까지 관찰한 것은 아니다.

mailbox 송신은 0x525b7820, 수신은 0x525b73a0의 SVC 6 경계까지 추적했다. 이 단계에서는 동일 핸들과 객체를 사용하는 호출 관계를 확인했다. 커널 내부의 대기열 처리·스케줄링·실제 실행 순서는 추가 검증 대상이다.

표·부트 헤더·BOOT 이미지의 기록 순서

패키지 순회가 완료되는 분기에서 0x52ff2af0 → 0x52ff2060이 파티션 표를 기록하고 성공하면 0x52ff2b0c → 0x52ff20d0이 부트 헤더를 기록한다. 그다음 0x52ff2b28 → 0x52ff21c8이 BOOT 이미지를 기록한다. 어느 단계든 0을 반환하면 0x52ff2bf4의 실패 경로로 간다. 일반 리소스 payload의 기록 호출은 이 완료 분기보다 앞에 있다. 기록 순서·인수 근거

헤더 생성 함수는 FwPartition byte +0x10을 헤더 +0x40에 직렬화한다. 0x52ff5304에 0과 1을 전달해 얻은 값은 각각 +0x44 = 0, +0x48 = 0xffff에 저장된다. 앞서 확인한 BOOT의 사본 순서 selector와 사본 A/B 시작 블록 입력에 대응한다. 현재 확인된 기본값 0의 경로에서는 A가 블록 0이고 B가 생략 표식이다. 비제로 값을 새로 만드는 코드는 이 함수에 없다.

따라서 선택값은 네 범주로 구별해야 한다. FwPartition byte +0x10, BOOT가 읽는 각 리소스 레코드 +4, 부트 헤더의 표 사본 selector, eMMC의 partition 선택값이다. 객체 byte가 헤더 selector로 복사되는 관계는 확인했지만 리소스별 bank 필드와 항상 일치한다는 근거는 없다. 0x52ff1ea8의 레이아웃 생성과 0x52ff586c의 리소스 기록에서 레코드 +4를 바꾸는 쓰기는 확인하지 못했다. 다른 생산자·alias·넓은 store·복사 경로는 남아 있다.

boot1 쓰기 래퍼 0x52ff5ad0는 lock → partition 1 선택 → 쓰기 → partition 0 복귀 → unlock 순서다. 진단 문자열은 선택값 1을 boot1으로 명명한다. 이 값 1은 리소스의 bank 1을 뜻하지 않는다. 복귀 함수의 반환값은 검사하지 않고 원래 쓰기의 결과를 반환한다. 또한 헤더 생성 함수 자체는 할당 버퍼 +0x14–0x3f를 초기화하지 않는다. 할당기의 초기화 보장과 실패 후 상태 처리는 별도 추적이 필요하다.

원본 ARM을 사용한 19개 합성 검사에서 외부 호출은 명시적으로 대체했다. 검사에서는 헤더 필드, 표 읽기·쓰기 인수, boot1 선택·복귀 순서와 단계별 실패 분기를 확인했다. bank 1·255 입력은 직렬화 검증용 합성 값이며 실기에서 이 값을 생산한다는 증거가 아니다. 검사 조건·결과 · 재현 도구

하위 BOOT 검사는 전송 상태까지 연결

BOOT의 장치 초기화 0x50b03e68는 기준 주소 0x19120000을 넘긴다. 컨텍스트 초기화 0x50b02280은 여기에 0x200을 더해 host +0x410에 저장하므로 이 경로의 레지스터 기준 주소는 초기화가 성공할 때 0x19120200이다. 실제 MMIO를 읽거나 쓴 결과는 아니다. BOOT 원본 범위·호출·주소 근거

명령 제출 0x50b01558은 host +0x418에 진행 중인 요청을 저장하고 요청 byte +0x3b를 0xff로 설정한다. 대기 함수 0x50b01774는 이 byte가 바뀔 때까지 완료 처리 0x50b023f4 → 0x50b0306c를 호출한다. 상태 레지스터 +0x30의 0x8000은 오류 분기를 선택하고 상위 비트는 서로 다른 오류 코드로 변환된다. Linux 정의와 대조하면 명령·데이터 CRC, timeout, ADMA 등의 전송 오류에 대응한다.

응답 type 1에서는 첫 응답 레지스터에 0xfdfc8080을 AND한다. 결과가 0이 아니면 요청 status byte에 1을 저장한다. 입력은 저장장치 명령 응답이며 펌웨어 payload의 hash나 공개키가 아니다. 오류 우선순위 13건과 응답 마스크 4건, 총 17개 합성 검사가 원본 명령과 일치했다. DMA 마무리 함수 하나는 stub으로 대체했고 복구 분기는 상태 값으로 건너뛰었다. MMIO 동작과 실제 CRC 계산을 에뮬레이션한 결과는 아니다. 범위·stub·결과 · 검증 도구

이번에 추가한 명령 제출·DMA/PIO·완료 처리 범위에서는 암호학적 서명 검증 함수를 식별하지 못했다. Boot ROM, 다른 부트 단계, 하드웨어 정책과 영속 설정의 인증 여부는 여전히 미확정이다. 현재 자료만으로 수정 펌웨어가 수락된다고 판단할 수 없다.

리소스 레코드 +4를 바꾸는 전체 테이블 읽기

진단 handler 0x52575ce4에서 live 파티션 표 전체를 다시 읽는 경로를 찾았다. 기존 명령 목록에서 sys_fwtable(목록 순번 580)로 분류한 함수다. 0x52575cf0 → 0x52fee52c로 manager를 얻고 manager +8의 FwPartition을 0x52ff5638에 전달한다. 읽기 목적지는 객체 +0x14의 테이블 포인터이며 길이는 +0x18에서 가져온다. 호출·객체 연결 근거 · 원본 범위와 전이 해시

초기 길이 0x10e00은 512바이트 블록 135개이자 0x870바이트 레코드 32개다. 하위 읽기가 요청 전체를 채우면 각 레코드의 +4도 저장소에서 읽은 내용으로 교체된다. 따라서 외부 내용이 bank 필드에 들어오는 생산 경로는 연결했지만, 구체적인 비제로 값이나 자동 bank 전환 정책은 확인하지 못했다. 이 handler와 읽기 wrapper에는 partition 선택 호출이 없으므로 현재 eMMC 선택 상태를 사용한다.

읽기가 성공했을 때만 테이블 출력 함수 0x52ff5494를 호출한다. 진단 handler 자체는 성공·실패 양쪽에서 0을 반환하므로 명령 반환값만으로 읽기 성공을 판단할 수 없다. 실제 실패 때 목적지 일부가 바뀌는지, 동시 접근이 있는지는 미확정이다.

원본 ARM을 사용한 합성 검사 10개에서 생성자 초기화, 고정 slot2 반환, 진단 읽기의 인수와 성공 분기를 확인했다. 합성 sector 내용을 테이블로 복사한 것은 읽기 stub이다. 실패 stub에서는 목적지를 보존하도록 설정했다. 이 조건을 실제 저장장치의 실패 원자성으로 해석하지 않는다. 검사 범위·stub·결과 · 재현 도구

partition 0 복귀 실패가 상위 성공에 가려지는 조건

앞서 확인한 0x52ff5ad0의 복귀 반환값 누락을 하위 선택 캐시까지 추적했다. 0x53297bc0 → 0x533593a0은 선택 캐시 byte 0x520c25e0를 읽는다. 요청과 같으면 장치 전환 명령을 생략한다. 다르면 0x53360428 → 0x533601e8로 내려가 CMD6, CMD13, EXT_CSD shadow 갱신을 거친 뒤 선택 캐시를 바꾼다. 주소·오류 전달 근거

하위 선택은 EXT_CSD index 179(0xb3)에서 마스크 0x7에 해당하는 비트를 바꾼다. 이 필드와 CMD6·CMD13의 의미는 Linux upstream MMC 정의와 대응한다(2026-11-08 확인). 펌웨어가 boot1으로 부르는 선택값 1은 해당 Linux 정의에서 BOOT0로 명명한다. 명령 형식의 대응이며 이 카메라 드라이버의 출처를 뜻하지 않는다.

CMD6가 성공한 뒤 CMD13이 실패한 경우에도 shadow와 선택 캐시는 이전 값으로 남는다. 이때 실제 장치가 어느 partition을 선택했는지는 반환값만으로 확정할 수 없다. 상위 wrapper는 복귀 결과를 버리고 앞서 보관한 쓰기 결과를 반환하므로, 쓰기가 성공했다면 복귀 실패에도 1을 반환한다. 이어지는 BOOT 이미지 쓰기에서 다시 partition 1을 요청하면 캐시가 이미 1이라 CMD6를 건너뛸 수 있다.

일반 쓰기 경로 0x533598d8 → 0x5335908c는 현재 선택 캐시를 사용한 용량 검사와 쓰기로 내려간다. 이 경로에서 partition 0으로 되돌리는 호출은 확인되지 않았다. 새 update walker 0x52ff29c8는 처음에 0을 명시적으로 선택하고 실패하면 실패 처리기에 stage 인수 2를 전달한 뒤 0을 반환한다. 후단의 표·헤더·BOOT 이미지 쓰기가 0을 반환할 때는 stage 인수 3을 전달한다. 복귀 실패가 쓰기 성공값에 가려지면 이 후단 실패 분기도 실행되지 않는다.

원본 ARM으로 선택 wrapper와 하위 캐시·shadow 분기를 실행했다. 7개 합성 검사가 통과했다. 실제 CMD6·CMD13, media write, RTOS 호출은 stub으로 대체했다. 이 결과는 오류가 상위에 드러나지 않는 조건을 확인한 것이며 실제 카메라에서 오류나 오기록이 발생했다는 관측은 아니다. 명령 상태를 기다리는 loop와 일반 쓰기의 최대 3회 재시도도 구분했다. 검사 입력·호출 순서 · 재현 도구

배포 BOOT의 진입점과 Boot ROM 인증의 경계

조사한 BOOT 레코드는 배포 패키지에 포함돼 있다. vector의 0x50b00020 값은 초기 진입점 0x50b0003c를 가리킨다. 이 경로는 CP15·레지스터·코어별 stack을 설정하고 고정 literal을 통해 0x50b00888을 호출한다. 초기화 함수 6개의 의사코드와 전체 ARM 목록을 추가했다. 이 BOOT를 적재하거나 호출한 선행 코드와 인증 판정은 아직 연결하지 못했다. 진입점·초기화·분기 근거

주 코어는 0x50b054c0–0x50b06de8을 0으로 초기화한다. 이 범위에는 보조 코어 entry 슬롯 0x50b054c4와 주 코어 entry 슬롯 0x50b054c8이 들어간다. 초기 레지스터 동기화는 0x1d001000의 값 3을 사용한다. 이 값과 앞서 확인한 준비 marker를 서명 검증 성공값으로 해석할 근거는 없다.

주 코어 entry의 출처연결한 생산·소비 경로판정 범위
cold 경로리소스 index 5의 +4 하위 16비트로 bank 선택. 읽기 성공 후 선택 설명자의 +0xc entry를 0x50b00f54에서 주 코어 슬롯에 저장리소스 메타데이터가 제공하는 분기 주소. Boot ROM API로 특정되지 않음
mode 2 경로0x0100fffc == 2이면 유지된 0x4fffff20 / 0x4fffff1c 값을 보조·주 코어 entry 슬롯에 저장mode 값과 유지된 entry의 생산자·진위는 미확정. mode 주소를 하드웨어 인증 레지스터로 단정하지 않음
마지막 분기0x50b00224가 주 코어 슬롯을 읽고 0x50b0022c가 값이 0이 아닐 때 BXNE r1 실행. 0이면 대기nonzero 검사만 확인. 진입 대상의 명령과 선행 인증 여부는 별도 조사 대상

entry 복사 6개와 0·비제로 분기 3개를 추가해 BOOT 합성 검사는 기존 28개에서 37개가 됐다. 복사 검사는 앞선 저장소 읽기의 성공을 가정하고 분기 검사는 BXNE를 실행한 뒤 대상의 첫 명령 전에 중단한다. startup의 MMIO·CP15·코어 동기화는 실행하지 않았다. 37개 검사와 범위 · 재현 도구

Boot ROM의 인증 검사 함수, 공개키 정책, fuse 상태와 검증 성공·실패 분기는 식별하지 못했다. 다음 조사에는 먼저 mask-ROM 또는 선행 boot stage의 코드가 현재 자료 어디에 포함되는지 확인하고, BOOT 진입 이전의 호출자와 상태 전달을 연결할 근거가 필요하다. 배포 BOOT에서 인증 함수를 찾지 못했다는 사실만으로 인증이 없거나 꺼져 있다고 결론내릴 수 없다.

저장한 자료와 검증

이번 조사에서 C 의사코드 15개를 로컬에 추가했다. 테이블·객체 생성 4개, partition 복귀 5개, BOOT 초기화 6개다. 새 합성 검사 26개(10 + 7 + 9)를 추가했고 기존 BOOT 28개를 포함한 관련 54개가 통과했다. 원본 해시·전이·포인터를 대조하고 독립 검토를 거쳤다. RTOS 통합 근거는 1,100개 범위·7,021개 전이·479개 데이터 word·82개 조건부 연결이며, 디컴파일 범위 489개는 서로 다른 진입점 487개를 포함한다. BOOT는 별도 이미지로 검증한다.

앞선 후속 조사에서 의사코드 32개를 추가 저장했다. 메시지 큐 14개, bank·기록 경로 7개, BOOT 전송 제어 11개다. 원본 범위 해시·ARM 목록·호출 지점을 대조하고 작업별 독립 검토를 거쳤다. 당시 합성 검사는 기록 경로 19개와 전송 상태 17개로 36개다. 아래 앞선 결과와 합산하거나 실기 실행으로 해석하지 않도록 범위를 각각 기록했다.

앞선 조사에서 의사코드 26개를 로컬에 저장했다. RTOS의 메시지·저장소 함수 창 20개와 별도 BOOT 함수 창 6개다. angr 출력과 전체 ARM 목록을 함께 보관했으며 주소·분기·조건은 원본 바이트로 대조했다. 메시지·저장소 작업을 나눠 조사하고 별도 검토자가 BOOT와 주요 수신·드라이버 근거를 독립 검토했다.

앞선 합성 실행은 응답 마스크 9개와 BOOT 선택·적재 인수 28개로 총 37개 검사다. BOOT 검사는 표 사본 순서, 0xffff 후보 생략, 읽기 성공에 따른 슬롯 2 marker, bank별 읽기 인수와 길이 올림을 검증했다. 저장소 호출·fallback 본문·코어 진입 전에 중단했으므로 전체 BOOT 실행 검증은 아니다. 응답 검사 · BOOT 검사
