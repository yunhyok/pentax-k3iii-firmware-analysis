부팅 단계와 저장소 구조: M0에서 BOOT, RTOS까지

카메라가 켜지면 작은 초기 코드가 메모리를 준비하고, 저장소에서 다음 단계를 읽어 실행을 넘깁니다. 고친 펌웨어를 넣었을 때 어느 사본이 읽히고 어디에서 검사를 받는지 알기 위해 이 과정을 따라갔습니다.

핵심 요약

  • 펌웨어 패키지의 M0와 BOOT 두 레코드를 따라가 부팅 순서를 이었습니다. M0 단계는 메모리를 설정하고 저장소에서 다음 이미지를 읽어 진입 주소와 모드 값을 남깁니다. BOOT 단계는 파티션 표를 읽어 RTOS를 올리고 대기하던 코어를 깨웁니다.
  • 추적한 M0·BOOT 코드가 성공과 실패를 가르는 조건은 저장소 읽기 결과, 카드 응답 상태, 준비 표식, 진입 주소가 0인지 여부였습니다. 이미지의 해시나 서명을 비교하는 연산은 이 범위에서 찾지 못했습니다. 그 앞 단계(Boot ROM)는 자료가 없으므로 인증이 없다는 결론은 내리지 않습니다.
  • bank를 고르는 값은 서로 다른 네 곳에 있습니다. RTOS가 기록할 때 쓰는 값과 BOOT가 읽을 때 쓰는 값이 다른 필드이고 둘을 맞춰 주는 코드와 0이 아닌 값을 만드는 코드는 아직 찾지 못했습니다. 의심했던 기록 후보들은 모두 다른 객체에 쓰는 코드였습니다.
  • RTOS는 업데이트 마지막에 파티션 표 → 부트 헤더 → BOOT 이미지 순서로 기록합니다. 부트 영역에 쓴 뒤 일반 영역으로 되돌리는 호출이 실패해도 쓰기 성공으로 보고되는 조건을 확인했습니다.
  • 모든 결과는 PC에서 한 정적 분석과, 원본 코드를 조각 단위로 실행한 합성 검사 300건입니다. 카메라에서 실행한 것은 없습니다. M0가 모드 값을 쓰는 주소와 BOOT가 읽는 주소가 같은 메모리인지도 아직 확인하지 못했습니다.

확인 원본 코드 실행·바이트 대조

  • M0 136건, BOOT 54건, RTOS 110건의 합성 검사에서 분기·인수·기록 주소가 분석과 일치
  • 헤더 직렬화, 기록 순서, 영역 복귀 실패가 가려지는 조건, 캐시 분기
  • 배포 DTB의 해시와 root 속성, 공식 소스 파일 6개의 해시와 행 번호

정적 분석 코드를 읽어 이은 것

  • 단계 사이의 호출 순서, 객체의 생성·등록·형 변환 연결
  • 업데이트 확인 메시지가 지나는 그룹·mailbox 경로
  • SDHCI·MMC 공개 정의와 레지스터·명령 번호의 대응

모델 시험 조건으로 넣은 값

  • 레지스터(MMIO)는 일반 RAM으로 대체, 하드웨어 상태와 카드 응답은 넣어 준 값
  • 저장소 읽기·쓰기, 할당기, 커널 호출은 대체 함수(stub)
  • bank 1·255 같은 0이 아닌 값은 시험용 입력

미확인 남은 것

  • M0보다 앞선 단계(Boot ROM)의 적재와 인증, 전체 인증 정책
  • M0가 쓰는 SRAM 주소와 BOOT가 읽는 주소의 물리 연결
  • 0이 아닌 bank 값을 만드는 코드, 레코드 +4를 직접 쓰는 코드
  • 실제 매체의 내용, 전원 차단 때의 복구, 실기 부팅

배경: 부팅 단계와 저장소 용어

카메라의 메인 칩은 전원이 들어오면 작은 초기 코드부터 실행합니다. 이 코드가 메모리를 쓸 수 있게 만들고 저장소에서 더 큰 프로그램을 읽어 실행을 넘깁니다. 넘겨받은 프로그램이 다시 다음 프로그램을 읽는 식으로 단계가 이어집니다. K-3 Mark III의 펌웨어 패키지(fwdc233b.bin)에는 이런 초기 단계에 해당하는 레코드가 두 개 들어 있습니다.

M0라는 이름

M0는 패키지 안의 레코드 이름입니다. 펌웨어 근거가 직접 보여 주는 것은 이 이름과 Thumb 코드라는 사실까지입니다. 칩 제조사 Socionext의 개발자는 리눅스 커널에 SC2000(내부 이름 M10V) 지원을 올렸습니다. 그때 이 칩이 Cortex-A7 코어 네 개와 “전원 제어용 Cortex-M0”를 갖는다고 소개했습니다. 그래서 M0 레코드가 그 Cortex-M0에서 도는 프로그램이라고 추정할 수 있습니다. 이것은 공개된 칩 설명에서 끌어낸 추정입니다. 카메라에서 어느 코어가 이 코드를 실행하는지는 관측하지 않았습니다. M0 레코드는 패키지에 들어 있는 펌웨어입니다. 칩 안에 고정된 Boot ROM(mask ROM)의 덤프가 아닙니다.

읽는 데 필요한 용어

eMMC와 boot1
eMMC는 카메라 내장 플래시입니다. 일반 데이터 영역 외에 부트용 영역이 따로 있고 장치 설정 바이트(EXT_CSD 179번)의 하위 3비트로 접근할 영역을 바꿉니다. 이 펌웨어는 선택값 1을 진단 문자열에서 boot1이라고 부릅니다.
파티션 표
리소스(BOOT, RTOS, 조정 데이터, 로그 등)가 저장소의 어디에 있는지 적은 표입니다. 0x870바이트 레코드 32개, 합쳐서 0x10e00바이트(512바이트 블록 135개)입니다.
bank
레코드 하나에는 같은 리소스의 위치를 적은 설명자가 0x434바이트 간격으로 놓입니다. 그중 어느 설명자를 쓸지 고르는 번호가 bank입니다.
부트 헤더
boot1 영역의 블록 0에 기록하는 0x278바이트 구조입니다. 파티션 표 사본 A·B 가운데 무엇을 먼저 시도할지와 각 사본의 블록 번호가 들어 있습니다.
리소스 슬롯
BOOT와 RTOS가 함께 쓰는 RAM 영역에 붙인 번호입니다. 슬롯 2가 파티션 표, 슬롯 6이 CameraLog, 슬롯 7~10이 조정 데이터입니다. 파티션 표의 레코드 번호(index)와는 다른 번호 체계입니다.
FwPartition
RTOS 안에서 파티션 표를 읽고 쓰는 객체입니다. +8에 저장소 드라이버, +0x10에 bank byte, +0x14에 표의 주소, +0x18에 표의 길이를 둡니다.
합성 검사
원본 펌웨어의 기계어 일부를 PC의 CPU 에뮬레이터(Unicorn)에 올리고 연구자가 만든 입력을 넣어 실행한 시험입니다. 분기와 기록 주소는 확인할 수 있지만 실제 하드웨어의 반응은 알 수 없습니다.

M0 단계: 메모리를 준비하고 다음 이미지를 올린다

M0 레코드는 reset 뒤 초기 설정과 작업 등록을 마칩니다. 그다음 적재 작업 안에서 SDRAM 설정 → 표 읽기 → 이미지 읽기 → 진입 주소·모드 기록을 차례로 수행합니다. 이 경로에서 이미지의 해시나 서명을 검사하는 분기는 찾지 못했습니다.

보드 선택값

0x3ffe08dc는 보드 종류를 가리키는 값을 읽습니다. reset의 데이터 복사가 gate 변수에 1을 넣어 두며 gate가 1일 때만 입력을 샘플합니다. 샘플한 5비트 인덱스가 0–24이면 표를 거쳐 값을 얻고 25–31이면 27이 됩니다. 결과를 캐시에 넣고 gate를 0으로 바꾸므로 이후 호출은 캐시만 돌려줍니다. 0x3ffe3594가 이 값으로 보드별 호출을 고릅니다. 이 경로에서 이미지 서명 검사는 확인하지 못했습니다.

초기 레지스터 기록

0x3ffe0838은 0x4dffb208의 bit 5를 켭니다. 0x3ffe04a4는 0x4dfff0xx 범위의 레지스터들을 기록합니다. 입력 bit 7이 0이면 추가 설정을 한 뒤 0x4dfff00c의 bit 4가 켜지기를 기다립니다. 이 대기 반복문에는 자체 timeout이 없습니다. 레지스터의 하드웨어 정의를 확보하지 못했으므로 이 기록을 SRAM remap이나 인증 해제라고 부르지 않았습니다. 0x3ffe0838 뒤에 이어지는 직렬 출력 설정은 M0 진단 직렬 출력에서 다룹니다.

SDRAM 설정: 두 채널을 5단계로 확인한다

로더는 저장소에서 읽은 헤더의 값으로 클록 레지스터와 SDRAM 컨트롤러를 설정합니다. 채널마다 다섯 단계의 명령을 쓰고 상태 값을 기다리는 방식이며 이미지 서명 검사와는 이어지지 않았습니다.

로더는 헤더를 0x3ffe4798에 넘겨 레지스터를 설정하고 헤더 +0x58을 0x3ffe4754에 넘겨 SDRAM 설정을 진행합니다. 뒤의 함수는 첫 설정 블록을 0x58830000에 나눠 기록한 뒤 채널 0을 설정합니다. 성공하면 +0x110의 두 번째 블록을 0x58850000에 기록하고 채널 1을 설정합니다. 결과에 따라 SDRAM OK 또는 SDRAM NG 진단 문자열을 출력하는 호출이 이어지므로, 이 경로를 메모리 초기화로 분류했습니다.

디컴파일 출력의 차이

저장소 읽기: CMD17·CMD18과 카드 응답 검사

M0의 읽기 경로는 한 블록이면 CMD17, 여러 블록이면 CMD18을 보냅니다. 이 경로에 있는 검사는 카드 응답 상태와 호스트 오류 비트이며 읽은 내용의 해시나 서명을 보는 분기는 확인되지 않았습니다.

CMD17(READ_SINGLE_BLOCK)과 CMD18(READ_MULTIPLE_BLOCK)은 SD·MMC 규격의 블록 읽기 명령입니다. 콜드 로더의 읽기 호출은 0x3ffe6fa8 → 0x3ffe71d4 → 0x3ffe5fd8로 내려가 명령을 만듭니다. 그 뒤 호스트 제출 0x3ffe5930과 대기·상태 처리 0x3ffe5abc → 0x3ffe62f8 → 0x3ffe665c로 이어집니다. 읽기 연산(연산 번호 2)에서 블록이 하나면 CMD17, 그 밖에는 CMD18을 구성합니다. 명령 인수는 카드 필드에 따라 블록 번호(LBA) 그대로이거나 LBA << 9입니다.

공개 정의와 비교

마스크 0xfdfc8080이 고르는 비트 15개는 모두 Linux의 MMC 정의에서 카드 상태(R1)의 오류 비트로 이름이 붙은 위치입니다. 범위는 bit 31(OUT_OF_RANGE)부터 bit 7(SWITCH_ERROR)까지입니다. 카드가 잠겨 있음을 알리는 bit 25는 들어 있지 않습니다. 호스트 쪽의 상태 비트(0x20, 1, 2, 0x8000)와 오프셋(+0x20, +0x58)은 뒤의 BOOT 전송 제어에서 대조한 SDHCI 정의와 같은 값입니다. 두 비교는 값이 같은지만 본 것이며 드라이버의 출처를 말해 주지는 않습니다.

적재가 끝나면 진입 주소와 모드 값을 기록한다

M0는 표의 첫 레코드에서 고른 설명자로 이미지를 읽고 성공하면 그 진입 주소와 모드 값 1을 SRAM 주소에 쓴 뒤 제어 레지스터를 기록합니다. 다시 깨어나는 경로에서는 모드 값 2를 씁니다.

  1. 레코드 0 적재 성공0x434 × bank 위치의 설명자 +0xc가 진입 주소입니다.
  2. 진입 주소 보관0x3ffe4936이 그 값을 0x3fffa800에 둡니다.
  3. 진입 준비 기록벡터 명령, 진입 주소, 모드 값을 쓰고 DSB 뒤에 제어 레지스터를 씁니다.
  4. BOOT가 모드 값을 읽음BOOT는 0x0100fffc를 읽습니다. M0가 쓴 주소와 같은 메모리인지는 미확인입니다.

M0의 0x3ffe47f0은 BOOT와 마찬가지로 헤더의 +0x40·+0x44·+0x48로 파티션 표 사본의 순서를 정합니다. 표 읽기 요청 0x3ffe48aa는 0x87블록과 목적지 0x50b70100을 넘기지만 M0의 CPU가 표에 접근할 때는 0x70b70100을 씁니다. 이 읽기 인수에서는 두 주소의 차이 0x20000000을 명령으로 확인했습니다. 전체 버스 주소 대응은 증명하지 않았습니다.

표의 첫 레코드가 존재하면 +4의 하위 16비트로 bank를 고르고 0x434 × bank 위치의 설명자를 씁니다. 이미지 읽기가 성공한 분기 0x3ffe492a–0x3ffe4938에서 설명자 +0xc를 0x3fffa800에 저장합니다. 이 진입 주소가 실제로 BOOT를 가리키는지는 매체의 레코드 값에 달려 있습니다. 합성 검사에 넣은 BOOT 주소는 입력 예시이며 장치에서 얻은 값이 아닙니다.

BOOT 단계: 파티션 표를 읽고 RTOS를 올린다

BOOT 레코드는 모드 값이 2가 아니면 저장소에서 부트 헤더와 파티션 표를 읽어 공유 RAM에 올립니다. 이어서 표의 설명자로 RTOS 등을 읽은 뒤 코어별 진입 주소를 저장합니다. 진입 직전에 보는 조건은 그 주소가 0이 아닌지뿐이었습니다.

  • 0으로 초기화: 주 코어는 0x50b054c0–0x50b06de8을 0으로 채웁니다. 이 범위에 보조 코어 진입 슬롯 0x50b054c4와 주 코어 진입 슬롯 0x50b054c8이 들어 있습니다.

표 사본을 골라 리소스 슬롯 2에 올린다

BOOT는 부트 헤더가 정한 순서대로 파티션 표 사본을 시도하고 읽기에 성공하면 표를 리소스 슬롯 2의 주소에 올린 뒤 준비 표식을 씁니다. RTOS는 이 표식을 기다렸다가 같은 주소를 FwPartition에 넣습니다.

  1. 표 사본 선택장치 헤더 +0x40·+0x44·+0x48. 순서 선택과 실패 시 다음 사본
  2. 표 읽기와 준비 표식0x50b00c64 → 0x50b03f04. 0x50b70100에 읽고 표식 기록
  3. RTOS 슬롯 2 소비0x52ff528c. 준비를 기다린 뒤 기준 주소를 FwPartition에 저장

부트 모드로 쓰는 메모리 0x0100fffc의 값이 2가 아니면 BOOT는 리소스 로더 0x50b00a48을 호출합니다. 값이 2인 warm 경로는 로더를 건너뛰고 보존된 진입 주소와 공유 상태를 씁니다. 아래 내용은 로더를 호출하는 쪽에서 확인했습니다.

  1. 준비 값 초기화 로더는 0x50adf000의 준비 값을 0으로 만듭니다.
  2. 헤더 읽기 장치의 시작 블록 0부터 2블록을 0x18004000으로 읽습니다. 헤더 +0x40이 순서 선택값이고 +0x44·+0x48이 사본 A·B의 블록 번호입니다.
  3. 사본 시도 선택값이 0이면 A→B, 1이면 B→A 순서입니다. 다른 값이면 실패합니다. 고른 블록 번호가 0xffff이거나 읽기·이어지는 적재가 실패하면 다음 사본을 시도합니다. 두 사본을 모두 시도한 뒤의 실패 분기는 오류 처리로 갑니다.
  4. 표 읽기 0x50b00c64에서 0x50b03f04를 호출합니다. 목적지는 0x50b70100, 길이는 0x87블록입니다.
  5. 준비 표식 읽기 반환값이 0인 것을 확인한 뒤 0x50b00c7c에서 0x50adf000 = 0xa55a5aa5를 씁니다.

읽는 양은 135 × 512 = 69,120바이트입니다. RTOS가 슬롯 2에 예약해 둔 길이 69,376바이트와는 다른 값이므로 구분해야 합니다.

RTOS의 0x52ff528c는 슬롯 2의 준비 상태를 반복해서 확인하고 준비되지 않았으면 다른 작업에 실행을 양보합니다. 준비되면 기준 주소 getter의 반환값을 0x52ff52c8에서 FwPartition +0x14에 저장합니다. 슬롯 2의 초기 기준 주소와 표식 포인터가 각각 0x50b70100, 0x50adf000이므로 BOOT가 쓰는 위치와 맞습니다. BOOT와 RTOS의 원본 주소·준비 값·표 접근이 서로 대응한다는 뜻이며 실제 장치에 들어 있는 표와 실행 때의 선택값은 관측하지 않았습니다. 준비 표식은 “데이터를 써도 된다”는 표시이지 암호학적 서명이 아닙니다.

RTOS를 읽고 대기하던 코어를 깨운다

BOOT는 표의 레코드 index 1에서 고른 설명자로 RTOS를 읽고 성공하면 진입 주소와 공유 표식을 쓴 뒤 다른 코어를 깨웁니다. 기록한 범위에서 본 조건은 저장소 반환 상태, 설명자 유무, 진입 주소가 0이 아닌지였고 암호학적 검증으로 볼 연산은 찾지 못했습니다.

BOOT는 파티션 표 index 1의 bank 값을 읽고 고른 설명자에서 목적지·진입 주소·시작 블록·길이를 가져옵니다. 저장된 블록 수가 0이면 바이트 길이를 512로 나눠 올림합니다. 읽기가 실패하면 표 사본을 바꿔 다시 시도하는 경로로 갑니다. 성공한 경로에서는 진입 주소를 0x50b054c4와 0x4fffff20에 저장합니다. 그리고 공유 위치 0x50b810f0에 0xd1c3b5a7을 쓴 뒤 SEV(대기 중인 코어에 이벤트를 보내는 ARM 명령)를 실행합니다.

진입 주소가 0이 아닌지 보는 검사는 SEV 뒤에, 대기하던 코어 쪽에 있습니다. 진입 주소는 표의 데이터에서 얻은 값이므로 고정된 RTOS 진입점이라고 단정하지 않았습니다. 주 코어가 쓰는 index 5가 어떤 리소스인지도 이 문서의 근거에서는 이름을 확인하지 않았습니다.

하위 읽기 함수 0x50b03f04는 0x50b042e0을 거쳐 명령 구성 함수 0x50b01f18로 이어집니다. 읽기 방향(값 2)에서 한 블록이면 명령값 0x11(CMD17), 여러 블록이면 0x12(CMD18)를 고릅니다. 명령 제출 0x50b01558과 대기 0x50b01774는 아래 절에서 전송 상태와 응답 검사까지 따라갔습니다.

기록한 BOOT 범위에서 확인한 것은 저장소 반환 상태, 설명자 유무, 코어를 깨운 뒤의 진입 주소 조건입니다. 암호학적 검증으로 분류할 연산은 이 범위에서 식별하지 못했습니다. 이것은 BOOT 전체, 하위 드라이버, Boot ROM, 다른 단계나 하드웨어에 인증 기능이 없다는 증거가 아닙니다. 수정된 펌웨어가 수락된다는 결론도 내리지 않았습니다.

하위 전송 제어는 SDHCI 배치와 맞는다

BOOT의 저장소 제어 코드가 쓰는 레지스터 오프셋과 비트는 공개 규격인 SDHCI의 정의와 일치합니다. 이 계층의 검사는 전송 오류와 카드 응답 상태이며 서명 검증 함수는 이 범위에서 찾지 못했습니다.

BOOT의 장치 초기화 0x50b03e68은 기준 주소 0x19120000을 넘깁니다. 컨텍스트 초기화 0x50b02280이 여기에 0x200을 더해 host +0x410에 저장합니다. 그래서 초기화가 성공할 때 이 경로의 레지스터 기준 주소는 0x19120200입니다. 실제 MMIO를 읽거나 쓴 결과는 아닙니다.

  • 명령 제출과 대기: 명령 제출 0x50b01558은 host +0x418에 진행 중인 요청을 저장하고 요청의 byte +0x3b를 0xff로 둡니다. 대기 함수 0x50b01774는 이 byte가 바뀔 때까지 완료 처리 0x50b023f4 → 0x50b0306c를 호출합니다.
  • 전송 오류: 상태 레지스터 +0x30의 0x8000 비트가 오류 분기를 고르고 그 위의 비트들이 서로 다른 오류 코드로 바뀝니다. Linux 정의와 대조하면 명령·데이터 CRC, timeout, ADMA 등의 전송 오류에 해당합니다.
  • 응답 마스크: 응답 type 1에서는 첫 응답 레지스터에 0xfdfc8080을 AND합니다. 결과가 0이 아니면 요청의 상태 byte에 1을 저장합니다. 입력은 저장 장치의 명령 응답이며 펌웨어 payload의 hash나 공개키가 아닙니다. M0의 읽기 경로도 같은 마스크를 씁니다.

오류 우선순위 13건과 응답 마스크 4건, 모두 17건의 합성 검사가 원본 명령과 일치했습니다. DMA 마무리 함수 하나는 대체 함수로 바꿨고 복구 분기는 상태 값으로 건너뛰었습니다. MMIO 동작과 실제 CRC 계산을 에뮬레이션한 결과는 아닙니다. 명령 제출·DMA/PIO·완료 처리 범위에서 암호학적 서명 검증 함수는 식별하지 못했습니다. Boot ROM, 다른 부트 단계, 하드웨어 정책과 영속 설정의 인증 여부는 여전히 미확정이며 현재 자료만으로 수정 펌웨어가 수락된다고 판단할 수 없습니다.

RTOS가 저장소에 쓰는 순서와 오류 처리

RTOS는 Emmc 드라이버로 저장소에 접근합니다. 업데이트의 마지막에 파티션 표, 부트 헤더, BOOT 이미지를 차례로 기록하며 boot1 영역에 쓴 뒤 일반 영역으로 되돌리는 호출의 결과는 검사하지 않습니다.

FwPartition이 부르는 저장소 드라이버는 Emmc입니다

FwPartition은 저장소 함수를 주소로 직접 부르지 않고 객체의 가상 함수 표를 거쳐 호출합니다. 그 객체가 무엇인지를 생성·등록·조회 과정에서 확인했습니다. 0x5327f954가 0x48바이트 객체를 할당하고 생성자 0x53297454를 호출합니다. 생성자가 가상 함수 표 0x53cb1638을 설치한 뒤, 같은 객체를 ID 0x18d로 등록합니다. FwPartition 생성 경로 0x52ff51f8은 이 ID를 조회하고 Emmc의 형 정보(RTTI) 0x53cb16b8로 형 변환해 객체 +8에 저장합니다. 생성·등록·형 변환이 성공하고 가상 함수 표 포인터가 유지된다는 조건에서 아래 호출 대상을 이을 수 있습니다.

부트 헤더에 들어가는 값

헤더 생성 함수는 FwPartition의 byte +0x10을 헤더 +0x40에 그대로 적습니다. 0x52ff5304에 0과 1을 넘겨 얻은 값은 각각 +0x44 = 0, +0x48 = 0xffff에 저장됩니다. 이 세 필드는 BOOT가 읽는 사본 순서 선택값과 사본 A·B의 시작 블록에 대응합니다. 지금 확인된 기본값 0의 경로에서는 사본 A가 블록 0이고 사본 B는 “없음” 표식입니다. 0이 아닌 값을 새로 만드는 코드는 이 함수에 없습니다.

객체의 byte가 헤더의 선택값으로 복사되는 관계는 확인했지만 그 값이 리소스별 bank 필드(레코드 +4)와 항상 같다는 근거는 없습니다. 레이아웃을 만드는 0x52ff1ea8과 리소스를 기록하는 0x52ff586c에서 레코드 +4를 바꾸는 쓰기는 확인하지 못했습니다. 다른 생산자, alias, 넓은 단위의 저장, 복사 경로는 남아 있습니다.

헤더 생성 함수는 할당받은 버퍼의 +0x14–0x3f를 초기화하지 않습니다. 할당기가 버퍼를 지워 주는지와 실패 뒤의 상태 처리는 따로 추적해야 합니다.

일반 영역 복귀가 실패해도 쓰기 성공으로 보고됩니다

boot1에 쓰는 데 성공하면, 그 뒤 일반 영역(partition 0)으로 되돌리는 명령이 실패해도 래퍼는 성공값 1을 반환합니다. 소프트웨어가 기억하는 선택 캐시는 1로 남고 위쪽 코드의 실패 분기는 실행되지 않습니다.

  1. boot1 쓰기 성공partition 1을 선택하고 payload를 씁니다. 래퍼가 쓰기 결과를 보관합니다.
  2. partition 0 복귀 실패선택 캐시는 1로 남습니다. 래퍼는 쓰기 성공값 1을 반환합니다.
  3. 다음 요청다음 boot1 쓰기는 캐시가 같아 선택 1을 생략할 수 있습니다. 새 업데이트 순회는 0 선택부터 다시 시도합니다.

영역 선택은 0x53297bc0 → 0x533593a0으로 내려가 선택 캐시 byte 0x520c25e0을 읽습니다. 요청과 같으면 장치 전환 명령을 생략합니다. 다르면 0x53360428 → 0x533601e8로 내려가 CMD6, CMD13, EXT_CSD 사본 갱신을 거친 뒤 선택 캐시를 바꿉니다.

하위 선택은 EXT_CSD index 179(0xb3)에서 마스크 0x7에 해당하는 비트를 바꿉니다. 이 필드와 CMD6(SWITCH)·CMD13(SEND_STATUS)의 의미는 Linux upstream의 MMC 정의와 대응합니다(2026-11-08과 2026-11-10에 확인). 펌웨어가 boot1이라고 부르는 선택값 1을 이 Linux 정의는 BOOT0이라고 부릅니다. 대응하는 것은 명령 형식이며 이 카메라 드라이버의 출처는 말해 주지 않습니다.

  • CMD13만 실패한 경우: CMD6가 성공한 뒤 CMD13이 실패해도 EXT_CSD 사본과 선택 캐시는 이전 값으로 남습니다. 이때 실제 장치가 어느 partition을 선택하고 있는지는 반환값만으로 확정할 수 없습니다.
  • 성공값에 가려짐: 위쪽 래퍼는 복귀 결과를 버리고 앞서 보관한 쓰기 결과를 반환합니다. 쓰기가 성공했다면 복귀가 실패해도 1을 반환합니다. 이어지는 BOOT 이미지 쓰기에서 다시 partition 1을 요청하면 캐시가 이미 1이라 CMD6를 건너뛸 수 있습니다.
  • 일반 쓰기 경로: 0x533598d8 → 0x5335908c는 현재 선택 캐시로 용량을 검사하고 쓰기로 내려갑니다. 이 경로에서 partition 0으로 되돌리는 호출은 확인되지 않았습니다.
  • 업데이트 순회의 처리: 새 업데이트 순회 0x52ff29c8은 처음에 0을 명시적으로 선택하고 실패하면 실패 처리기에 단계 인수 2를 넘긴 뒤 0을 반환합니다. 뒤쪽의 표·헤더·BOOT 이미지 쓰기가 0을 반환할 때는 단계 인수 3을 넘깁니다. 복귀 실패가 쓰기 성공값에 가려지면 이 뒤쪽 실패 분기도 실행되지 않습니다.

장치를 다시 초기화해도 두 소프트웨어 값이 항상 맞춰지지는 않습니다

드라이버는 “지금 선택된 영역”을 두 군데에 기억합니다. 장치 설정의 사본(EXT_CSD 사본)과 따로 둔 선택 캐시입니다. 장치 초기화는 앞의 것만 새로 읽으며 캐시가 이미 0이면 전환 명령을 생략할 수 있습니다.

  1. 컨트롤러 RAM 초기화앞 0x400바이트를 지웁니다. EXT_CSD 사본은 포함되고 선택 캐시 +0x4e0은 빠집니다.
  2. CMD0과 CMD8장치 초기화 뒤 EXT_CSD 512바이트를 받아 사본 +0x200을 갱신합니다.
  3. partition 0 요청0x533593a0(0). 기존 캐시가 0이면 CMD6를 생략합니다.

이 순서는 별도의 장치 초기화 경로입니다. 일반 쓰기가 실패한 뒤 자동으로 호출되는지는 확인하지 못했습니다.

  • 초기화에 들어가는 조건: Emmc 초기화 0x532977ac는 준비 byte와 선행 부트 상태 검사 0x5310b888 → 0x532fb73c를 먼저 봅니다. 준비 byte가 0이면 u32[0x50800008] == 0x5aa5a55a인지 검사합니다. 값이 맞으면 보조 함수 세 개를 수행한 뒤 준비 byte를 다시 읽고 0이 아니면 초기화 반복문을 생략합니다. 값이 맞지 않거나 다시 읽은 준비 byte가 0이면 하위 초기화를 시도합니다. 그 세 번째 단계가 0x5331b968 → 0x5331ff68 → 0x533202f0 → 0x5335948c로 이어집니다.
  • 무엇이 지워지는가: 0x5335c770은 컨텍스트 0x520c2100의 앞 0x400바이트를 지웁니다. EXT_CSD의 partition 구성 사본 0x520c23b3은 이 범위 안에 있지만 선택 캐시 0x520c25e0은 밖에 있습니다.
  • 사본 갱신: 이어서 CMD0을 제출합니다. 카드 초기화 0x53359c84 → 0x5335d338 → 0x5335b778에서는 CMD8의 수신 목적지로 컨텍스트 +0x200을 넘깁니다. 명령은 512바이트 한 블록을 요청합니다.
  • 영역 0 요청: 장치 초기화가 성공하면 0x5331ffd4–0x5331ffd8에서 partition 0을 요청합니다. 캐시가 1이면 전환 절차가 성공했을 때만 0으로 갱신합니다. 이미 0이면 새 EXT_CSD 사본과 비교하지 않고 CMD6를 생략할 수 있습니다.

이 경로를 “두 소프트웨어 값을 무조건 다시 맞추는 절차”라고 설명할 수는 없습니다. CMD0 뒤에 실제 카드가 어떤 partition 상태를 유지하는지는 관측하지 않았습니다.

오류 복구는 이와 다른 경로입니다. CMD6·CMD13이나 일반 데이터 전송에서 특정 호스트 오류가 나면 0x5335e97c → 0x5335dd78에 도달할 수 있습니다. 여기서는 호스트 레지스터 +0x2c의 0x06000000 비트를 설정하고 그 비트가 지워지기를 기다립니다. 추적한 범위에서 이 복구는 선택 캐시와 EXT_CSD 사본을 갱신하지 않고 장치 초기화로 다시 들어가는 호출도 없습니다. 일반 쓰기의 세 번 시도가 모두 실패하면 0x532976d8에서 오류를 기록하고 0을 반환합니다. 비동기 복구나 위쪽의 재시작까지 배제한 결론은 아닙니다.

공개 정의와 비교

eMMC에서 CMD8은 SEND_EXT_CSD, CMD0은 GO_IDLE_STATE입니다. 호스트 레지스터 +0x2c에는 0x06000000을 32비트로 씁니다. SDHCI 배치라면 이 값은 +0x2f 소프트웨어 리셋 레지스터의 명령 선·데이터 선 리셋 비트(0x02, 0x04)에 해당하는 위치입니다. 근거 JSON도 이 함수를 명령·데이터 리셋으로 분류했습니다. RTOS 드라이버의 레지스터 배치 전체를 SDHCI와 대조하지는 않았습니다.

bank 값을 만드는 코드는 아직 찾지 못했다

파티션 표의 bank 필드(레코드 +4)가 바뀌는 경로로 확인한 것은 매체에서 표를 통째로 읽어 오는 경우뿐입니다. CPU가 값을 계산해 그 필드에 직접 쓰는 코드와, RTOS 객체에 0이 아닌 bank를 넣는 코드는 찾지 못했습니다. “+4에 쓰는 코드”로 보였던 후보들은 모두 다른 객체를 대상으로 했습니다.

확인된 경로: 표 전체를 매체에서 다시 읽기

진단 명령 하나가 사용 중인 파티션 표 전체를 저장소에서 다시 읽습니다. 읽기가 요청 전체를 채우면 각 레코드의 +4도 저장소의 내용으로 바뀝니다. 외부 내용이 bank 필드에 들어오는 길은 이었지만 구체적인 0이 아닌 값이나 자동 bank 전환 정책은 확인하지 못했습니다.

진단 handler 0x52575ce4가 그 경로입니다. RTOS 명령 목록에서 sys_fwtable(목록 순번 580)로 분류한 함수입니다. 0x52575cf0 → 0x52fee52c로 manager를 얻고 manager +8의 FwPartition을 0x52ff5638에 넘깁니다. 읽기 목적지는 객체 +0x14의 표 포인터이고 길이는 +0x18에서 가져옵니다.

  • 읽는 범위: 초기 길이 0x10e00은 512바이트 블록 135개이자 0x870바이트 레코드 32개입니다. 표 전체가 한 번에 바뀝니다.
  • 영역 선택 없음: 이 handler와 읽기 래퍼에는 partition 선택 호출이 없으므로 그때의 eMMC 선택 상태를 그대로 씁니다.

업데이트 파일 확인 요청이 오가는 경로

“카드에 업데이트 파일이 있는가”를 묻는 요청(CheckUpdateFirmware)은 메시지로 updater에 전달됩니다. updater는 파일을 골라 읽고 검사한 뒤 버전 두 값을 응답으로 돌려줍니다. 요청과 응답이 같은 객체에서 만나는 것까지 정적으로 이었고 실제 큐 동작은 실행하지 않았습니다.

이 절은 부팅이 끝난 뒤 RTOS 안에서 일어나는 일입니다. 저장소에 쓰기 전 단계이며 업데이트 과정 전체는 업데이트 과정 안내에서 이어집니다.

요청을 처리하고 버전 두 값으로 응답합니다

  1. 조회 요청0x52c28cc4. 요청 0x4642010c를 보내고 결과 마스크 0xc로 기다립니다.
  2. 선택·읽기·검증0x533161e8의 처리 분기. 종류 2 선택 → 파일 읽기 → 패키지 검사
  3. 버전 응답응답 0x27408410. 버전 두 값 → 이벤트 마스크 0x4/0x8

수신 dispatcher 0x533161e8은 0x53316230에서 요청 ID를 비교하고 0x53316304로 분기합니다. 종류 2 선택 0x52fef240, 파일 읽기 0x52fee900, 검증·변환 0x52fefb84가 차례로 성공하면 0x52fee9b4에서 버전 필드를 꺼냅니다. 이 검증 호출은 업데이트 검사에서 다룬 프로젝트·종류·체크섬·변환 길이 검사로 이어집니다.

  • 응답의 모양: 처리기는 22바이트 응답을 만들고 byte 0과 0x02–0x14의 16비트 필드 10개를 0으로 초기화합니다. 버전 값은 선택·읽기·검증이 성공한 뒤에 채웁니다. 실패 분기에서는 버전 필드가 0인 응답을 씁니다.
  • 응답의 전달: 응답 발행 0x53315494가 보내는 ID는 0x27408410입니다. 소비자 0x52c16240이 payload +2와 +4의 16비트 값을 0x52c275f8에 넘깁니다.

이 참·거짓이 뜻하는 것

참은 “응답에 유효한 버전 두 값이 들어 있다”는 뜻입니다. 현재보다 새 버전인지를 비교한 결과가 아닙니다. 현재 버전과 비교하는 0x52feef34는 별도 메시지 0x4c410101의 경로에 있습니다. 분기 0x53318be0 뒤에 updater +0x9c가 UPDATE_WAITING_MESSAGE 상태를 가리키고 종류가 2일 때 0x533192c8에서 호출합니다. 여기서 확인한 범위는 조회·응답·버전 검사 상태까지입니다. 업데이트 상태 기계 전체는 복원하지 않았습니다.

그룹 등록에서 같은 객체의 응답까지

여기서 확인한 등록은 “메시지마다 수신자를 나열한 구독 목록”이 아니라, 그룹 번호로 mailbox를 찾는 등록과 작업 객체의 연결입니다. 생성 경로 0x533045dc / 0x5330463c → 0x53304c20이 그룹 1과 4를 등록합니다. 보내는 쪽과 받는 쪽이 같은 map 0x547bffdc를 0x53304864에서 조회합니다.

요청이 updater에 닿는 길

  1. 조회 객체 → 그룹 1 0x52c28cc4가 요청 0x4642010c를 만들고 그룹 map을 조회해 mailbox에 보냅니다.
  2. DomainController 그룹 1의 작업 루프 0x533044cc가 0x53304ae0 → 0x530edfa0으로 수신합니다. 분류 함수 0x533042d8의 반환값 0 경로를 거친 뒤, ID의 두 번째 바이트와 0x7f를 AND한 값으로 분기합니다. 요청 0x4642010c는 마스크 1을 씁니다.
  3. updater 전용 mailbox 요청은 0x53303c98을 거쳐 0x53315174로 전달됩니다. DomainController가 보관해 둔 updater 포인터를 씁니다.
  4. SystemControl 작업 updater의 secondary 객체(원래 객체 +4)의 mailbox에서 메시지를 꺼냅니다. 그 뒤 thunk 0x533196e4가 this를 4만큼 되돌리고 dispatcher 0x533161e8로 이어집니다.

updater factory는 객체를 +0x10에 보관합니다. 시작 코드 0x532fe4b0–0x532fe4c0이 그 객체의 포인터를 DomainController +0x30에 넣습니다. 생성자에서 만든 mailbox, 0x530ef074 → 0x530edc60의 송신, 작업 루프 0x530eed94의 수신이 모두 같은 secondary 객체의 mailbox 필드를 씁니다.

응답이 조회 결과를 설정하는 길

  1. updater → 그룹 1 0x53315494가 응답 0x27408410을 보냅니다. DomainController에서 이 ID는 분류 마스크 4를 씁니다.
  2. 그룹 4 → HTControl 그룹 4로 다시 발행됩니다. HTControl은 domain 4를 가진 래퍼 0x5330ae60을 거쳐 공통 그룹 수신으로 받습니다.
  3. 같은 getter의 +4 객체 응답 소비자 0x52c16240이 0x52c27260의 반환 객체 +4를 읽습니다. 0x52c275f8은 결과 이벤트 0x4/0x8을 설정합니다.

활성 요청 호출자 0x5254042c–0x5254043c도 0x52c27260의 반환 객체 +4를 읽어 조회 함수를 호출합니다. 그래서 이 호출 경로에서 요청을 보낸 객체와 결과가 설정되는 객체를 정적으로 이었습니다. 실행 중에 이 singleton이 바뀌는지, 수신이 실제로 성공하는지는 관찰하지 않았습니다.

mailbox 송신은 0x525b7820, 수신은 0x525b73a0의 SVC 6 경계까지 따라갔습니다. 이 단계에서 확인한 것은 같은 핸들과 객체를 쓰는 호출 관계입니다. 커널 내부의 대기열 처리, 스케줄링, 실제 실행 순서는 추가 검증 대상입니다.
