Lightroom 색 프로파일 안내: DCP 만들기와 검증

Lightroom은 프로파일이라는 작은 파일로 RAW의 색을 정합니다. 이 주제는 그 프로파일을 직접 만들어 카메라가 낸 JPEG의 색에 다가가려는 연구이며, 프로파일의 구조를 조사하고 실제 Lightroom으로 효과를 측정한 기록입니다.

핵심 요약

  • 목표는 Lightroom에서 RAW를 열었을 때 카메라가 직접 만든 JPEG에 가까운 색이 나오게 하는 프로파일을 만드는 것입니다. 재료는 펌웨어 분석에서 찾은 색 처리 정보입니다. 그런 프로파일은 아직 없습니다.
  • 지금까지 한 일은 세 가지입니다. Lightroom에 설치된 Adobe 프로파일 13개의 구조를 조사했고, 프로파일 파일(DCP)을 직접 만드는 도구를 만들었고, 그 도구로 만든 시험 DCP 8개를 실제 Lightroom Classic 15.6에 넣어 TIFF 16개를 내보내 측정했습니다.
  • 직접 만든 DCP가 Lightroom에 그대로 적용되고, 프로파일의 톤 곡선이나 LookTable을 바꾸면 출력이 그에 따라 달라진다는 점을 확인했습니다.
  • K-3 II의 사진 한 장에서 카메라 JPEG와의 평균 색차(ΔE00)는 Adobe의 Camera Natural이 1.615, 행렬만 담은 시험 DCP가 3.073, Adobe Standard가 3.476였습니다. 앞으로 만들 프로파일이 넘어야 할 기준선입니다.
  • 모든 측정은 조작이 결과에 반영되는지를 확인한 것입니다. 카메라의 색 모드를 재현했다는 주장이 아닙니다. 색 비교는 장면 한 장뿐이고, 표본을 찍은 펌웨어는 분석한 펌웨어보다 앞선 버전입니다.

한눈에 보기: RAW에서 색 비교까지

공개 RAW에서 시험 프로파일을 만들고, 실제 Lightroom으로 현상한 결과를 네 가지 방법으로 조사했습니다. 펌웨어 분석과 프로파일을 잇는 마지막 고리는 아직 비어 있습니다.

이 주제의 실험은 모두 PC에 설치한 Adobe Lightroom Classic에서 실제 RAW 파일로 수행했습니다. 그래서 여기의 “확인”은 다른 주제와 달리 에뮬레이션 결과가 아니라 Lightroom이 실제로 낸 출력의 측정값입니다. 다만 측정 대상은 Lightroom이지 카메라가 아닙니다.

배경 지식: 프로파일이 색을 정하는 방식

RAW 파일에는 센서가 받은 빛의 양만 들어 있습니다. 이것을 눈에 보이는 색으로 바꾸려면 “이 카메라의 센서 값은 이런 색이다”라는 해석 규칙이 필요합니다. Lightroom에서는 그 규칙을 DCP(DNG Camera Profile) 파일이 담고 있습니다. 현상 화면의 “프로파일” 메뉴에서 고르는 항목이 이것입니다.

DCP 안의 태그와 적용 순서

DCP는 TIFF와 비슷한 구조의 작은 파일이고, 내용은 이름이 붙은 값(태그)의 모음입니다. Adobe의 DNG 규격이 각 태그의 뜻과 적용 순서를 정합니다. 색에 영향을 주는 태그는 아래 순서로 쓰입니다.

  1. 색 행렬ColorMatrix, ForwardMatrix로 센서 값을 표준 색 좌표(XYZ D50)로
  2. HueSatMap색상·채도·명도 표로 색을 보정
  3. LookTable노출 보정 뒤에, 같은 형식의 표로 “인상”을 입힘
  4. 톤 곡선ProfileToneCurve로 밝기 분포를 정함
DCP 태그와 Enhanced XMP 프로파일이 표현하는 변환
단계표현하는 변환
DCP 행렬ColorMatrix는 XYZ에서 기준 카메라 색공간으로 가는 변환이고, ForwardMatrix는 화이트밸런스를 적용한 카메라 색에서 XYZ D50으로 가는 변환입니다. 둘은 단순한 역행렬 관계가 아닙니다. 광원이 두 개이면 사용자가 고른 화이트밸런스에 따라 두 행렬 사이를 보간합니다.
DCP HSV 표ProfileHueSatMap은 XYZ D50으로 바꾼 값을 선형 ProPhoto RGB 원색 기준의 HSV(색상·채도·명도)로 옮겨 보정합니다. ProfileLookTable은 같은 형식이고 같은 색공간에서 적용하지만, 노출 보정 뒤이면서 톤 곡선 앞이라는 더 늦은 단계에 놓입니다. 표가 3차원(명도 축이 2칸 이상)일 때 인코딩 값 1은 명도 V에 sRGB 전달 함수를 적용한 뒤 표를 찾는 방식입니다.
DCP 톤 곡선ProfileToneCurve는 선형 값 기준의 (입력, 출력) 좌표 쌍 목록입니다. (0, 0)에서 시작해 (1, 1)로 끝나야 하고, 규격은 3차 스플라인으로 보간하도록 정합니다.
Enhanced XMPDCP와 다른 형식의 프로파일입니다. RAW에서는 기준이 되는 DCP를 이름으로 지정해 그 위에 적용할 수 있습니다. 별도의 HSV Look Table이나, 처리 후반에 적용되는 RGB→RGB 변환표를 담을 수 있습니다. Adobe가 2018년에 낸 프로파일 SDK는 Camera Raw에서 .cube 파일을 불러오는 절차와 32×32×32라는 크기 한도를 설명합니다.

근거: Adobe DNG 규격 1.7.1.0의 32~33쪽(ColorMatrix), 48~53쪽(프로파일 태그), 56~57쪽(LookTable), 62~64쪽(인코딩), 100~104쪽(색 처리 모델). Enhanced XMP는 Adobe Profile SDK의 Enhanced Profiles.pdf 1~3쪽과 8~9쪽.

읽는 순서

아래 순서대로 읽으면 재료, 측정 방법, 결과, 세부 확인의 차례가 됩니다. 결과만 보려면 4번부터 읽어도 됩니다.

  • 1 · 지금 이 문서

    DCP 생성·검증 개요

    Adobe의 프로파일은 어떻게 생겼고, 프로파일을 직접 만들 수 있는가?

    설치된 DCP 13개의 구조를 조사했고, 출처가 분명한 값으로 DCP를 만드는 도구를 만들었습니다.

  • 2 · 재료

    시험용 RAW 준비

    누구나 다시 해 볼 수 있는 시험 재료는 무엇인가?

    세 기종의 CC0 DNG와 그 안의 카메라 JPEG, 행렬만 담은 시험 DCP 세 개입니다.

  • 3 · 방법

    ColorChecker 비교 절차

    색 차이를 어디에서 어떻게 재는가?

    색상표 24개 패치의 측정 영역과 ΔE00 계산 순서를 정하고 표본에 끝값이 없음을 확인했습니다.

  • 4 · 결과

    실제 TIFF 6개 비교

    지금 있는 프로파일은 카메라 JPEG에 얼마나 가까운가?

    K-3 II 한 장에서 Camera Natural이 가장 가까웠습니다(평균 ΔE00 1.615).

  • 5 · 대조 실험

    톤 곡선 비교

    프로파일의 톤 곡선 태그를 바꾸면 Lightroom 출력이 어떻게 달라지는가?

    곡선을 생략한 출력은 Adobe SDK의 기본 곡선을 명시한 출력과 거의 같았습니다.

  • 6 · 다른 기종

    K-3 III·Q7 DCP 내보내기

    K-3 Mark III와 Q7에서도 직접 만든 DCP가 적용되는가?

    두 기종 모두 시험 DCP를 선택해 16비트 TIFF로 내보냈습니다.

  • 7 · 검증 수단

    프로파일 지문 재현

    TIFF에 적힌 프로파일 지문은 어떻게 계산되는가?

    시험 DCP 여섯 개의 지문을 Adobe SDK 방식으로 다시 계산해 TIFF의 값과 일치시켰습니다.

  • 8 · 대조 실험

    LookTable 대조 실험

    LookTable 태그를 넣으면 색이 의도대로 바뀌는가?

    채도를 0.8배로 줄이는 표가 24개 패치 모두의 채도를 낮췄습니다.

카메라 안에서 색이 만들어지는 과정은 색 처리 안내에서, 세 기종의 진행 상황은 세 기종 연구 본부에서 볼 수 있습니다.

설치된 Adobe 프로파일 13개의 구조

K-3 Mark III와 K-3 II에는 Adobe Standard와 카메라 모드 다섯 개의 프로파일이 있고, Q7에는 Adobe Standard뿐입니다. 카메라 모드 프로파일은 LookTable과 톤 곡선을 두 묶음으로 나눠 쓰고, 모드마다 다른 것은 ForwardMatrix입니다.

ProfileHueSatMap광원별로 90×30×1없음
ProfileLookTable36×8×1636×8×16, 인코딩 1
ProfileToneCurve없음좌표 64쌍
  • LookTable과 톤 곡선은 두 묶음뿐입니다. 두 K-3 기종 모두에서 Camera Bright와 Landscape가 같은 LookTable과 톤 곡선을 쓰고, Camera Natural·Portrait·Vibrant가 또 다른 같은 조합을 씁니다. 묶음은 기종이 달라도 같습니다.
  • 모드를 가르는 것은 ForwardMatrix입니다. 같은 묶음 안에서도 ForwardMatrix1과 ForwardMatrix2는 열 개 파일에서 모두 달랐습니다. 검사기가 읽는 태그 가운데 같은 묶음, 같은 기종의 두 모드 사이에서 다른 것은 프로파일 이름과 이 두 행렬뿐입니다.
  • ColorMatrix는 기종에 딸려 있습니다. 각 기종의 ColorMatrix1/2는 Adobe Standard와 다섯 Camera Matching 파일에서 같았습니다.
주의

LookTable과 톤 곡선의 바이트가 같다는 사실만으로 두 기종의 센서 변환이나 최종 색이 같다고 판정할 수 없습니다. 모드 이름이 같은 두 기종 사이에서도 마찬가지입니다. 이 조사는 태그의 종류, 개수, 크기, 해시만 기록했고 설치 파일의 계수나 표의 값은 복제하지 않았습니다.

DCP를 직접 만드는 도구

출처를 적은 JSON 하나를 넣으면 DCP 파일 하나가 나옵니다. 계수를 추정하는 도구가 아니라, 이미 가진 값을 올바른 파일 형식으로 적어 주는 도구입니다.

tools/profile_bridge.py는 Python 표준 라이브러리만 씁니다. 입력 JSON에는 데이터의 출처를 provenance로 적어야 하고, UniqueCameraModel은 RAW 파일에 적힌 값과 정확히 같아야 합니다. 아래는 가장 작은 입력 예시입니다. 숫자는 파일 형식 시험용이며 실제 PENTAX 기종에 쓸 값이 아닙니다.

{
  "provenance": "Synthetic serialization test only",
  "UniqueCameraModel": "TEST camera, not a real model",
  "ProfileName": "Bridge Format Test",
  "CalibrationIlluminant1": 17,
  "ColorMatrix1": [[0.85, -0.125, 0.0625], [0, 1, 0], [0, 0, 1]]
}

만든 파일을 검사한 방법

  • 두 프로그램으로 읽기 — 저장소의 검사기(inspect_adobe_profiles.py)로 태그를 확인했고, ExifTool 13.59이 합성 파일을 DCP 형식으로 읽어 Validate: 0 0 0을 돌려줬습니다.
  • 단위 테스트 5개 — 광원 두 개짜리 파일의 태그와 배열 값, 잘못된 입력의 거부, 기존 출력 파일의 보존을 검사합니다.
  • Adobe DNG SDK와의 호환 — SDK(1.7.1 Build 2768)는 행렬을 정규화하고 소수 넷째 자리로 반올림해서 씁니다. 도구는 그렇게 처리한 뒤에도 행렬이 유효한지 검사합니다. 톤 곡선은 SDK의 한도인 8,192점으로 제한합니다.
  • 실제 Lightroom — 이 도구로 만든 시험 DCP 8개를 Lightroom Classic 15.6이 프로파일 목록에 올렸고 현상에 적용했습니다. 결과는 읽는 순서의 2~8번 문서에 있습니다.
이 도구가 하지 않는 일

계수를 추정하지 않고, XMP 프로파일을 쓰지 않으며, Lightroom에 설치하지도 않습니다. 파일 구조가 맞는지 검사하는 일과 그 프로파일의 색이 맞는지 검증하는 일은 별개입니다.

만든 파일에는 ProfileEmbedPolicy 태그를 넣지 않으므로 DNG 규격의 기본값 0(“allow copying”)이 적용됩니다. 규격은 이 값의 프로파일을 DNG가 아닌 파일의 처리에 쓸 수 없다고 정합니다. 그래서 지금의 시험 대상은 DNG이고, PEF에서의 적용은 따로 검증해야 합니다.

카메라 색을 맞추려면 남은 확인

프로파일 파일을 만들어 넣는 길은 열렸습니다. 남은 것은 그 안에 무슨 값을 넣어야 카메라와 같은 색이 되는지를 알아내는 일입니다.

  1. 입력 좌표를 확정합니다. RAW의 검정·백색 레벨과 채널 배열, 노출 배율, 화이트밸런스 이득(B2r 단계)의 단위와 적용 전후의 좌표를 확인해야 합니다. 펌웨어에서 Q13 고정소수점으로 계산되는 행렬은 아직 DNG가 정의하는 방향의 행렬로 바꿀 수 없습니다. RGB와 YCbCr 각 구간의 원색, 백색점, 선형성, 행렬을 곱하는 순서가 필요합니다.
  2. 픽셀 처리 순서를 확정합니다. 색 모드·출력 형식·우회(bypass) 설정에 따른 분기, MultiAxial과 ColorReference의 실제 보간, M2P·R2y 단계의 포화와 감마·톤의 순서를 확인해야 합니다. 펌웨어에서 찾은 설정값과 계수 산술은 이 순서를 보여 주는 증거의 일부입니다. 하이라이트 클리핑, 히스토그램에 따라 달라지는 처리, 노이즈 감소와 샤프닝까지 전역 변환표 하나로 맞출 수는 없습니다. 근거는 색 처리 알고리즘과 JPEG·ISP와 색 재현 경로에 있습니다.
  3. 같은 RAW의 출력 쌍을 모읍니다. 기종별로 같은 RAW를 카메라 안에서 여러 Custom Image로 현상합니다. 두 K-3 기종은 TIFF나 JPEG로, Q7은 JPEG로 저장할 수 있습니다. 화이트밸런스, 노출, 출력 색공간, 모드 세부값, 자동 보정, 렌즈와 펌웨어 버전을 기록합니다. Auto Select는 실제로 선택된 모드를, Cross Processing은 고정 프리셋을, Monochrome은 필터와 토닝 값을 구분해 적습니다.
  4. 따로 찍은 장면으로 검증합니다. Lightroom에서 기준 DCP, Process Version, 화이트밸런스, 노출, 자동 보정을 고정합니다. 색상표와 회색 계조를 두 가지 조명과 여러 노출로 촬영하고, 값을 맞추는 데 쓰지 않은 피부·잎·고채도·하이라이트 장면을 따로 확보합니다. 같은 출력 색공간으로 바꾼 뒤 패치별 ΔE00 분포, 중성축, 계조, 채널별 클리핑을 비교합니다. 그 결과로 DCP의 HSV 표와 후반 RGB 변환표 가운데 어느 쪽이 목표 변환을 더 잘 표현하는지 판단할 수 있습니다.
  • Q7의 Smart Effect — Ricoh 사양에서 Smart Effect는 Custom Image와 별개의 기능입니다. 따로 다뤄야 합니다.
  • 이름이 같은 모드 — 다른 기종에서 이름이 같은 모드도 기종별로 따로 보정해야 합니다.

재현 방법

DCP 만들고 검사하기

위 예시 JSON을 저장소 안 .private/profile-input.json에 저장한 뒤 실행합니다. 출력 경로에 파일이 이미 있으면 작업을 멈춥니다. 입력과 출력의 SHA-256, 출처는 표준 출력에 기록됩니다.

python tools/profile_bridge.py .private/profile-input.json .private/profile-output.dcp
python inspect_adobe_profiles.py .private/profile-output.dcp
python -m unittest discover -s tests -p test_profile_bridge.py -v
exiftool -validate -Warning -Error -FileType .private/profile-output.dcp

설치된 Adobe 프로파일 검사하기

아래 명령은 폴더 아래에서 이름이 세 기종의 Adobe Standard 또는 Camera 프로파일인 DCP를 찾아 검사기에 넘깁니다. 마지막 인수를 Lightroom Classic 설치 폴더의 Resources/CameraProfiles로 바꾸면 내장 파일을 검사합니다.

python -c "import pathlib,re,subprocess,sys; \
pat=re.compile(r'PENTAX (K-3 Mark III|K-3 II|Q7) (Adobe Standard|Camera .+)\.dcp', re.I); \
files=sorted(str(p) for p in pathlib.Path(sys.argv[1]).rglob('*.dcp') if pat.fullmatch(p.name)); \
subprocess.run([sys.executable,'inspect_adobe_profiles.py',*files],check=True)" \
  "C:/ProgramData/Adobe/CameraRaw/CameraProfiles"

공개 기록에는 파일 크기, 태그의 형식과 개수, 표의 차원, SHA-256만 들어 있습니다. 검사기 자체는 python inspect_adobe_profiles.py --self-test로 점검할 수 있습니다. 기록일은 2026-11-08입니다.
