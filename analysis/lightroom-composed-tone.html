Lightroom 색 프로파일 · 실험 DCP 판정

합성 톤 DCP를 실제 Lightroom에서 내보낸 결과

PC에서 계산한 톤 보정을 프로파일 파일 하나에 담았을 때 Lightroom이 그 계산대로 출력하는지 확인했습니다. 미리 정한 판정 기준 가운데 하나를 넘지 못했습니다.

이 문서에서

  1. 배경: 오프라인 목표와 합성 곡선

  3. 오프라인 목표에 얼마나 가까워졌나
  4. 카메라 내장 JPEG와 비교한 색차
  5. 한계와 남은 과제
  6. 프로파일 생성과 측정 재현
  7. 근거 파일과 참고 자료

핵심 요약

  • 차트 #1376에서 정한 톤 곡선 G를 Adobe 기본 곡선의 대리값과 합성해 실험 DCP 하나에 넣었습니다. 이 DCP로 실제 Lightroom Classic 16.0에서 차트 #1376과 별도 장면 #1363을 내보냈습니다.
  • 판정: 미리 정한 기준을 모두 충족하지는 못했습니다. 상대 기준(기준 오차의 절반 미만)은 두 장면 모두 통과했습니다(5.28%, 2.90%). 차트 패치 기준 가운데 평균 0.1554는 허용값 0.25 이하로 통과했습니다. 그러나 최대는 7번 주황 패치 0.8918로 허용값 0.75를 넘었습니다.
  • 카메라 Natural 내장 JPEG와 비교하면 실제 후보는 기준 행렬보다 가까웠습니다. 영역 평균 ΔE00은 차트 3.1847 → 2.0653, 별도 장면 5.3743 → 4.0573입니다. 줄어든 영역은 각각 24곳 중 19곳과 24곳입니다.
  • RAW 두 장과 Lightroom 한 버전에서 얻은 결과입니다. 허용값은 연구용 판정선일 뿐 눈으로 같아 보인다는 기준은 아닙니다. 주황 패치 잔차의 원인도 이 측정으로 정하지 못했습니다.

확인 실제 Lightroom 출력에서 잰 값

  • Lightroom Classic 16.0(Camera Raw 19.0)에서 내보낸 TIFF의 프로파일 이름·지문, CRS 속성 115개와 중첩 설정 6개
  • 기준 TIFF·후보 TIFF와 오프라인 목표 사이의 색차, TIFF 쌍의 위치 맞춤
  • 두 장면의 내장 JPEG 대비 색차

모델 연구자가 정한 것

  • 오프라인 목표: 기준 TIFF에 고정 곡선 G를 PC에서 적용한 값
  • Lightroom 기본 곡선의 대리값으로 쓴 DNG SDK 1.7.1 Build 2768의 ACR3 표
  • 상대 기준과 차트 허용값(0.25, 0.75)

미확인 남은 것

  • Lightroom의 실제 내부 기본 곡선과 처리 순서
  • 7번 주황 패치 잔차의 원인(톤과 RGB 좌표에서 계속)
  • 다른 장면·조명·Lightroom 버전에서의 결과

배경: 오프라인 목표와 합성 곡선

톤 보정 뒤 남는 색차의 계산은 Lightroom이 이미 내보낸 TIFF에 곡선 G를 PC에서 덧씌운 것입니다. 실제로 쓰려면 같은 효과가 프로파일 안에 들어가 Lightroom이 직접 그렇게 출력해야 합니다. 이 문서는 그 전달이 얼마나 정확한지 잽니다.

오프라인 목표는 톤 곡선이 없는 기준 DCP로 내보낸 TIFF에 G를 PC에서 적용한 결과입니다. 후보 DCP로 내보낸 TIFF가 이 목표에 가까울수록 프로파일이 계산을 그대로 전달한 것입니다. 카메라 JPEG와 얼마나 가까운지는 별도로 쟀습니다.

이미 렌더된 톤을 프로파일 곡선으로 옮기는 조건

프로파일 곡선은 Lightroom의 기본 곡선을 대신하므로, G만 넣지 않고 "기본 곡선 다음에 G"를 합성한 곡선을 넣었습니다.

G는 행렬 DCP로 내보낸 #1376 TIFF에서 무채색 6칸의 밝기를 기준으로 정한 단조 PCHIP 곡선입니다(톤 잔차 실험). 이 실험은 그 곡선을 바꾸지 않고 씁니다.

Adobe 참조 SDK에서는 유효한 프로파일 곡선이 장면 기준 기본 곡선 B를 대체합니다. 곡선은 선형 ProPhoto RGB의 가장 높은 채널과 낮은 채널에 적용됩니다. 중간 채널은 두 채널 사이의 상대 위치를 유지합니다. B가 엄격히 증가하면 이 연산을 B, G 순서로 두 번 적용한 결과와 합성 곡선 G∘B를 한 번 적용한 결과가 같습니다. 같은 전단 상태를 쓰고 두 연산 사이에 채널 혼합이나 클리핑이 없을 때만 성립합니다. 공개 명세는 ProfileToneCurve(태그 50940)를 선형 감마의 FLOAT 점 쌍으로 정의합니다(Adobe DNG 규격 51쪽).

주의

ACR3 표는 Lightroom 기본 곡선의 대리값입니다. Lightroom의 실제 내부 기본 곡선과 처리 순서는 이 실험에서 따로 확인할 수 없습니다. 비교 대조군은 기존 항등·Lift·ACR3 대조에, SDK 소스 범위와 레시피 해시는 결과 JSON에 있습니다.

오프라인 목표에 얼마나 가까워졌나

두 장면 모두 오프라인 목표에 크게 다가갔지만 차트 7번 주황 패치가 최대 허용값을 넘어 전체 판정은 불합격입니다.

오프라인 목표 대비 ΔE00 · 영역마다 픽셀 중앙값을 구한 뒤 24개 영역을 같은 비중으로 평균
장면기준 행렬 TIFF실제 후보 TIFF후보 ÷ 기준상대 기준(50% 미만)
#1376 차트3.03720.16035.28%통과
#1363 별도 장면4.44800.12882.90%통과
판정

상대 기준은 두 장면 모두 충족했습니다. 차트 패치별 Lab 중앙값의 ΔE00 평균은 0.1554로 허용값 0.25 이하였습니다. 최댓값은 7번 주황 패치의 0.8918로 허용값 0.75를 넘었습니다. 같은 패치의 중앙 100×100픽셀에서도 0.8917이었습니다. 그래서 미리 정한 기준을 모두 충족하지는 못했습니다(delivery_tolerances_met = false).

같은 차트 지표에서 무채색 6칸 평균은 0.0102, 유채색 18칸 평균은 0.2038이었습니다. 오차가 유채색에 몰려 있습니다. 허용값은 두 장면을 판정하려고 정한 실험 기준입니다. 관측한 차이만으로 주황 패치 잔차의 원인을 정할 수는 없습니다.

현상 조건과 위치 맞춤
  • Lightroom Classic 16.0, Camera Raw 19.0, Process Version 15.4. 6,016×4,000 무압축 ProPhoto RGB 16비트 TIFF.
  • 두 장면에서 비교한 CRS 속성은 각각 115개이고 그중 프로파일 이름과 지문만 달랐습니다. 중첩 설정 6개는 모두 같았습니다.
  • As Shot 수치는 #1376에서 5200 K/+2, #1363에서 4650 K/+28이었고 노출은 두 장면 모두 0.00 EV였습니다.
  • TIFF 쌍의 최대 위치 이동은 #1376 0.0974픽셀, #1363 0.0154픽셀로 미리 정한 1픽셀 미만 조건을 충족했습니다.
  • 새 TIFF를 읽기 전에 #1376의 고정 정합 지점을 기존 homography로 TIFF 좌표에 옮기도록 방법을 고친 기록이 있습니다. 평가 영역과 허용값은 그대로였고 후보의 미세 이동은 보정하지 않았습니다.

한계와 남은 과제

  • K-3 II RAW 두 장, Lightroom Classic 16.0 한 버전에서 얻은 결과입니다. 이 사이트가 펌웨어를 분석하는 K-3 Mark III의 RAW는 쓰지 않았습니다.
  • 허용값 0.25·0.75와 50% 상대 기준은 연구용 판정선입니다. 눈으로 같아 보인다는 주장은 하지 않습니다.
  • Lightroom 내부 기본 곡선 대신 SDK의 ACR3 표를 썼으므로, 주황 패치 잔차가 대리값 탓인지 처리 순서 탓인지 알 수 없습니다. 같은 엔진에서 채널 순서를 비교한 분석은 Lightroom 톤과 RGB 좌표에 있습니다.

실험 프로파일 이름은 PENTAX K-3 II 1376 Composed Tone Offline v1입니다. 기존 #1376 DCP의 모델·행렬 두 개·광원 두 개는 그대로입니다.

실험 DCP 다운로드 · 파생 곡선의 출처와 Adobe 고지 · Adobe SDK 라이선스

다운로드 파일은 위 SHA-256과 일치하는 실험판입니다. 위 판정대로 기준을 모두 통과한 프로파일은 아닙니다. 같은 DCP를 다시 만들려면 직접 확보한 Adobe DNG SDK 1.7.1 Build 2768 ZIP이 필요합니다. Adobe 페이지의 배포 빌드는 바뀔 수 있으므로 ZIP SHA-256으로 확인합니다. Adobe SDK 소스와 원본 ACR3 표는 별도 ZIP에 있습니다(Adobe SDK 배포처, RAW 출처와 CC0 기록).

python tools/check_lightroom_composed_tone.py build --sdk dng-sdk-2768.zip --output candidate.dcp

Lightroom에 가져오기 전에 두 RAW를 각각 pentax-k3ii-1376.dng와 pentax-k3ii-1363.dng로 저장합니다. 검증기가 TIFF의 XMP에서 이 원본 이름을 확인합니다. 두 DNG에서 SubIFD1:PreviewImage를 꺼내 비교용 JPEG로 씁니다(#1376 RAW와 내장 JPEG, #1363 RAW와 현상·내보내기 설정).

exiftool -b -SubIFD1:PreviewImage -w %d%f-preview.jpg pentax-k3ii-1376.dng pentax-k3ii-1363.dng

직접 내보낸 TIFF를 넘기면 같은 실험 조건에서 새 결과를 계산합니다. 기록 당시 TIFF로 기준 결과를 검증하려면 --fresh-exports를 빼고 실행합니다. 필요한 도구는 Python의 NumPy·SciPy·OpenCV·Pillow·tifffile·scikit-image, ExifTool, LittleCMS tificc입니다.

python tools/check_lightroom_composed_tone.py replay --fresh-exports \
  --dcp candidate.dcp --raw-1376 pentax-k3ii-1376.dng --preview-1376 pentax-k3ii-1376-preview.jpg \
  --matrix-1376 chart-matrix.tif --candidate-1376 chart-candidate.tif \
  --raw-1363 pentax-k3ii-1363.dng --preview-1363 pentax-k3ii-1363-preview.jpg \
  --matrix-1363 scene-matrix.tif --candidate-1363 scene-candidate.tif \
  --natural-1363 scene-natural.tif --standard-1363 scene-standard.tif \
  --scratch work --output fresh-result.json

입력 경로는 실제 파일로 바꾸고 work는 이미 있는 디렉터리로 지정합니다. 실행 파일 경로는 --exiftool과 --tificc로 줍니다. 새 TIFF로 돌릴 때 검증기가 하는 일은 다음과 같습니다.

  • RAW·DCP·ICC 해시, 기록된 현상값과 중첩 설정 전체, TIFF 사이 위치 맞춤을 확인합니다.
  • 고정 차트 좌표를 지키기 위해 #1376 기준 행렬 TIFF는 파일 컨테이너가 달라도 디코딩한 RGB 픽셀이 기록 당시와 같아야 합니다.
  • #1363의 두 마스크는 선택된 픽셀까지 기존과 같아야 합니다. 픽셀이 다르면 마스크를 바꿔 끼우지 않고 오류를 냅니다.
  • 새 결과에는 실제 파일·픽셀·ICC·XMP 해시와 별도 실험 판정을 기록합니다.
