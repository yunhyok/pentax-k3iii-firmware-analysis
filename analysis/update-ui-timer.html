UI 타이머 슬롯에서 완료 화면 콜백까지

업데이트가 끝난 뒤 완료 화면 객체는 타이머를 하나 걸고, 시간이 지나면 콜백을 받아 다음 동작으로 넘어갑니다. 이 타이머가 UI 코드 안에서 어떻게 보관되고 어떤 길로 되돌아오는지 추적했습니다.

이 문서에서

  1. 배경: 완료 화면은 왜 타이머를 거는가
  2. 서비스는 예약을 슬롯에 보관합니다
  3. 예약, 취소, 만료 확인의 규칙
  4. 만료된 예약은 두 listener를 거쳐 콜백이 됩니다
  5. 39개 사례의 구성
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • UI 타이머 서비스는 예약 한 건을 슬롯 하나에 적어 둡니다. 슬롯에는 예약 번호(handle)와 콜백이 들어가고 실제로 시간을 재는 일은 커널의 알람 호출에 맡깁니다.
  • 예약, 취소, 만료 확인, 콜백 전달 코드를 PC 에뮬레이터에서 원본 기계어로 39개 사례 실행했습니다. 결과는 모두 예상한 값과 같았습니다.
  • 타이머가 울린 뒤 콜백은 event flag와 UI 작업 큐를 거쳐 UserFwUpdateController에 닿습니다. 이 길에 놓인 코드는 실행했지만 단계를 넘기는 순서는 시험이 직접 정했습니다.
  • 커널 호출이 실패하면 assertion이 먼저 불립니다. “실패해도 handle을 돌려주거나 슬롯을 지운다”는 결과는 assertion이 되돌아오는 조건에서만 성립합니다.
  • 예약에 넘긴 1000의 시간 단위, 실제 지연, 콜백 뒤의 재부팅 여부는 확인하지 못했습니다.

확인 원본 코드 실행으로 확인

  • handle 번호 규칙과 빈 슬롯 재사용
  • 취소, 상태 조회, 만료 확인(poll)의 분기
  • work 0x1bc만 통과시키는 수신 조건
  • UserFwUpdateController 콜백의 handle 비교

정적 분석 코드를 읽어서 판단

  • 서비스 생성자와 가상 함수 표의 연결
  • 타이머 객체를 커널에 등록하는 호출
  • 빈 슬롯이 없을 때 새로 만드는 경로

모델 시험 조건으로 정한 것

  • 커널 타이머 호출 세 개, event, lock, assertion은 대체 함수
  • 슬롯과 배열은 시험이 미리 채운 값
  • 단계 사이의 전달 순서는 시험이 지정
  • CPU는 Unicorn의 Cortex-A15 모델

미확인 확인하지 않은 것

  • 시간 단위와 실제 지연
  • 커널이 콜백을 전달하는 실제 과정
  • 원본 assertion이 되돌아오는지 여부
  • 콜백 뒤의 work 5 처리와 재부팅

배경: 완료 화면은 왜 타이머를 거는가

앞 단계인 완료 후 UI 작업에서, 업데이트 완료 통지를 받은 UserFwUpdateController는 모델 값이 3일 때 UI 타이머 서비스에 예약을 넣습니다. 넘기는 값은 지연 1000과 자기 자신의 일부(this+0x188)를 가리키는 콜백입니다. 돌려받은 handle은 객체 안에 저장해 둡니다.

이 문서는 그 예약이 서비스 안에서 어떻게 보관되고 만료된 뒤 어떤 경로로 콜백이 되어 돌아오는지 다룹니다. 시간을 실제로 재는 커널 쪽은 커널 호출과 예약 시각부터 이어지는 여섯 문서에서 따로 내려갑니다.

슬롯
예약 한 건을 담는 칸. 타이머 객체 포인터, ID(handle과 같은 값), 콜백 객체 포인터가 들어갑니다.
listener
“일이 생기면 불러 달라”고 등록해 두는 객체. 서비스는 listener 두 개를 겸합니다.
event flag
한 작업(task)이 다른 작업을 깨울 때 쓰는 커널의 신호 비트.

assertion
조건이 거짓이면 오류를 알리는 검사 코드. 알린 뒤 멈추는지 되돌아오는지는 구현에 달려 있습니다.

서비스는 예약을 슬롯에 보관합니다

서비스 객체가 슬롯 배열을 갖고 슬롯마다 타이머 객체가 하나씩 붙어 있습니다. 타이머 객체는 다시 서비스의 첫 번째 listener를 가리킵니다.

생성자는 서비스 안의 두 위치(listener 1과 listener 2)에 서로 다른 가상 함수 표 주소를 적습니다. 서비스 하나가 listener 두 개 노릇을 합니다. 슬롯을 만들 때는 listener 1의 주소를 타이머 객체 생성자에 넘기고 타이머 객체가 그 주소를 보관합니다.

생성자는 counter에 1을 적습니다. 그래서 이 값에서 출발하면 첫 예약의 handle은 2입니다. 생성과 등록 과정은 코드를 읽어 확인한 내용이고 실제 커널 등록은 실행하지 않았습니다.

예약, 취소, 만료 확인의 규칙

handle은 1씩 커지는 번호이고 슬롯은 ID가 0이거나 콜백이 비어 있으면 빈 것으로 봅니다. 만료 확인은 커널에 “아직 진행 중인가”를 물어 아니라고 할 때 콜백을 부릅니다.

펌웨어의 진단 문자열에는 시작, 정지, 상태 조회 wrapper의 이름이 StartAlarmTimer, StopAlarmTimer, HasAlarmTimerStarted로 남아 있습니다. 상태 조회의 이름대로, 반환값 1은 “알람이 아직 진행 중”이라는 뜻으로 읽을 수 있습니다. poll은 이 값이 0일 때, 곧 진행 중이 아닐 때 콜백을 부릅니다.

같은 번호가 이미 다른 슬롯에 쓰이고 있는지 확인하는 코드는 보이지 않았습니다. 같은 ID를 두 슬롯에 넣고 취소한 사례에서는 첫 슬롯만 지워졌습니다.

커널 호출이 실패했을 때

시작, 정지, 상태 조회 wrapper는 커널 반환 0을 성공으로 계산합니다. 0이 아니면 먼저 assertion(err==E_OK)을 부릅니다. 원본 assertion이 그 뒤에 멈추는지 되돌아오는지는 검사하지 않았기 때문에, 두 경우를 나누어 시험했습니다.

커널이 오류를 돌려준 사례의 결과

주의

“실패했는데도 handle을 돌려준다”, “실패했는데도 슬롯을 지운다”는 결과는 오른쪽 열, 곧 assertion이 되돌아온다고 가정한 경우에만 해당합니다. 원본 assertion의 실제 동작은 확인하지 않았습니다.

만료된 예약은 두 listener를 거쳐 콜백이 됩니다

타이머가 울리면 첫 번째 listener가 event flag를 세웁니다. 이어서 event task가 UI 작업 0x1bc를 큐에 넣고 두 번째 listener가 그 작업을 받아 poll을 돌립니다.

4. listener 20x528eb81cthis를 보정한 뒤 들어옵니다. 작업 번호가 0x1bc일 때만 다음 단계로 갑니다.

시험 조건

연결 시험은 등록 콜백, event task 한 바퀴, 기존 큐 넣기와 배분 코드를 차례로 직접 호출했습니다. event task는 두 번째 대기에 들어가는 순간 멈추게 했습니다. 커널이 실제로 이 순서로 전달한다는 증거는 아닙니다.

완료 화면 객체가 받는 콜백

콜백 대상이 완료 화면 객체이면 poll은 원본 가상 함수 표의 thunk를 거쳐 그 객체의 콜백 함수에 도달합니다. 이 함수는 전달받은 handle이 저장해 둔 값과 같을 때만 저장값을 지우고 “콜백을 받았다”는 바이트를 1로 씁니다. 이어서 두 바이트의 조건이 맞으면 후속 작업을 만드는 코드로 갑니다.

공개하지 않고 보관한 자료는 디컴파일 C 12개, 보조 구간 15개, ARM 명령 698 words입니다. 직접 분기 68개, 간접 분기 5개, 리소스 8개, 포인터 10개, 조건부 연결 4개의 주소와 해시를 대조했습니다. 디컴파일된 C에는 poll의 반복자 오류와 꼬리 호출 누락이 있어서 해석은 원본 ARM 명령과 실행 결과를 기준으로 했습니다. 검증 스크립트는 이 서비스를 AppTimerModel이라고 부릅니다.

한계와 남은 과제

  • 시간이 흐르는 시험이 아닙니다. 커널 타이머 호출, event, lock은 모두 대체 함수입니다. 실제 지연과 커널의 콜백 전달은 실행하지 않았습니다.
  • 1000의 단위는 모릅니다. 서비스는 이 값을 바꾸지 않고 커널 시작 호출의 두 번째 인수로 넘깁니다. 커널 쪽 단위는 타이머 설정과 64비트 카운터에서 정리한 대로 아직 가설 단계입니다.
  • poll은 콜백 뒤에 배열의 끝만 다시 읽고 현재 위치는 그대로 둡니다. 그래서 이 결과로 배열 재할당이나 배열이 줄어드는 경우의 안전성을 말할 수 없습니다. 이 코드를 옮겨 쓸 때는 순회 중 배열의 수명과 위치 관계를 따로 보장해야 합니다.
  • 콜백이 슬롯을 바꾼 사례는 시험이 만든 동작입니다. 실제 콜백이 다시 예약하는 경우나 여러 작업이 동시에 접근하는 경우를 입증하지 않습니다.
  • 이 문서 범위 밖: work 5의 처리, 재부팅, decoded 버퍼의 최종 회수, 0이 아닌 bank 값을 만드는 코드, 인증. 카메라와 저장 매체 입출력, 펌웨어 빌드와 기록은 하지 않았습니다. 화면 표시도 검사하지 않았습니다.
