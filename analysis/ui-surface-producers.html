StringView가 그릴 표면을 받는 경로

글자를 찍으려면 어느 메모리에 찍을지 알려 주는 표면 정보가 필요합니다. 이전 시험에서는 이 표면을 시험이 만들어 넣었습니다. 이 문서는 펌웨어가 등록된 Canvas에서 글자 객체까지 표면을 어떻게 넘기는지, 그 표면의 필드를 누가 채우는지 코드를 읽어 정리했습니다.

이 문서에서

  1. 배경: Canvas, 스냅샷, 표면
  2. 표면 포인터가 Canvas에서 StringView까지 가는 길
  3. 표면의 필드는 화면 입력 버퍼 기술자에서 옵니다
  4. 한계와 남은 과제
  5. 재현 방법
  6. 근거 파일과 참고 자료

핵심 요약

  • 등록된 Canvas가 가진 표면 포인터는 뷰 스냅샷을 거쳐 하위 객체들의 그리기 호출로 넘어갑니다. 받는 쪽이 StringView의 내부 객체이면 텍스트 설정의 첫 워드에 그 포인터를 저장합니다.
  • 이 길에는 조건이 네 번 걸립니다. 등록 갱신 검사, 표면의 16비트 필드, 내부 객체의 함수 표, 내부 객체의 플래그입니다. 조건이 맞지 않으면 중간에 돌아갑니다.
  • 표면의 RAM 시작 주소, 형식, 행 간격 같은 필드는 화면 입력 버퍼 기술자에서 복사됩니다. 조회가 성립하지 않으면 초기화된 상태가 남을 수 있습니다.
  • 모두 코드를 읽어 얻은 정적 분석입니다. 원본 코드를 실행하지 않았습니다. 실제 메뉴의 어떤 StringView가 이 길에 연결되는지, 버퍼의 주소·치수, LCD 출력은 확인하지 못했습니다.

정적 분석 코드를 읽어 판단

  • 등록 슬롯 → Canvas → 스냅샷 → 중첩 그리기로 이어지는 포인터 전달
  • StringView 내부 객체의 함수 표와 표면 저장 명령
  • 표면 기술자에서 표면 필드로 복사하는 명령
  • 타입 5 전송에서 행 간격을 워드 단위로 쓰는 것

모델 이전 시험에서 정한 값

  • 이전 시험의 256×144 RAM 표면(호스트가 공급)

미확인 확인하지 않은 것

  • 실제 메뉴의 StringView가 이 목록에 연결되는지
  • 입력 버퍼 기술자의 실제 값, 버퍼 할당 주소와 치수
  • 네 조건이 실제 실행에서 성립하는지, LCD 출력

배경: Canvas, 스냅샷, 표면

  • 표면은 그리기 대상 메모리를 설명하는 작은 구조체입니다. RAM 시작 주소, 픽셀 형식, 한 줄의 길이(스트라이드) 같은 값이 들어 있습니다.
  • Canvas는 화면 요소들을 묶어 그리는 최상위 객체입니다. 펌웨어 진단 문자열에 RegistCanvas와 6Canvas라는 이름이 남아 있어 이 이름을 씁니다.
  • 뷰 스냅샷은 그리기 전에 화면 요소들의 상태를 그리기용 필드로 옮겨 두는 단계입니다.
  • StringView는 글자 한 줄을 맡는 객체입니다. V+0x11c에 내부 객체 N을 둡니다. viewport와 텍스트 설정은 글자 viewport 문서에서 다룹니다.

객체가 어떤 함수를 부를지는 가상 함수 표의 칸으로 정해집니다. 아래의 “표 +0x14 슬롯”은 그 표의 여섯 번째 칸입니다.

표면 포인터가 Canvas에서 StringView까지 가는 길

활성 등록 슬롯의 표면은 Canvas의 보류 칸에 들어갔다가 스냅샷에서 그리기 칸으로 옮겨집니다. 그 뒤 하위 객체 목록을 따라 전달되어 StringView 내부 객체의 텍스트 설정에 저장됩니다.

  1. 등록 슬롯 0x526d9454는 +0x30이 활성인 0x34바이트 슬롯에서 표면을 조회합니다. 0x526d951c–0x526d9524가 슬롯의 Canvas 포인터와 슬롯+8을 0x52bea3f0에 넘겨 Canvas+0x1e0에 둡니다.
  2. 스냅샷 등록 갱신 함수는 0x526d9560의 검사 결과가 0이면 복귀합니다. 통과하면 같은 활성 슬롯의 Canvas에 뷰 스냅샷을 부릅니다. Canvas 표 0x5386f680의 +0x60 칸인 0x52bea084가 +0x1e0을 +0x1d8로 복사합니다.
  3. Canvas 그리기 별도 그리기 함수 0x52bea3f8은 +0x1d8을 읽습니다. 표면의 u16 +0x1c가 0이면 돌아갑니다. 선택된 분기는 내부 객체 +0x178과 같은 표면을 순회 함수에 넘깁니다.
  4. 중첩 순회 뷰 스냅샷의 0x52c02608은 하위 뷰 +0x114의 내부 객체 포인터를 가져옵니다. 0x52c02718의 가상 호출은 표 +0x14를 읽으며 들어온 표면 r1을 그대로 넘깁니다. 하위 호출 때도 저장해 둔 포인터를 다시 r1에 넣습니다.
  5. StringView에 저장 순회 대상이 StringView 내부 객체이면 표 슬롯이 0x52bedb40을 고릅니다. N+0x64가 0이 아니면 0x52bedb78이 표면을 N+0x6c(텍스트 설정의 첫 워드)에 씁니다.

내부 객체가 이 표를 갖게 되는 연결은 자동 대조 38개와 별도로 고정 RTOS에서 확인했습니다. 생성자의 0x52bee2f0이 리터럴 0x52bee414에서 표 주소 0x5386fec0을 읽습니다. 이어서 0x52bee2fc가 그 값을 V+0x11c에 씁니다. 0x52bee3fc → 0x52c0025c는 내부 객체의 주소를 V+0x114에 저장합니다. 실제 메뉴에서 특정 StringView가 이 목록에 연결되는지는 확인하지 못했습니다.

표면의 필드는 화면 입력 버퍼 기술자에서 옵니다

조회가 성립하면 0x53114538이 화면 입력 버퍼 기술자 D의 필드를 표면 S로 복사합니다. 성립하지 않으면 초기화한 값이 그대로 남을 여지가 있습니다.

슬롯에서 부르는 0x528f66a4 → 0x5310e4ec는 먼저 표면 헤더를 초기화합니다. 조회 모드 1·2에서 필요한 객체와 레코드가 있을 때만 복사가 일어납니다. 원본 진단 문자열의 파일 이름은 ScreenBuffer/ScreenInputBuffer.cpp입니다.

형식 5는 그리기 디스패처가 0x528c2e74에서 검사하는 값입니다. 타입 5 비회전 전송은 전역 너비를 32비트 워드 단위의 행 간격으로 씁니다. 0x528c265c에서 워드 위치를 4배 해 바이트 주소로 바꾸고 0x528c26c8에서 한 워드를 씁니다. 이전 시험의 256×144는 호스트가 정한 값입니다(합성 RAM 표면의 경계 시험).

진단 이름 GetWidth와 GetHeight는 자동 검사의 문자열 6개와 별도로 원본 0x53a73e18, 0x53a73dcc에서 확인했습니다.

한계와 남은 과제

  • 경로 전체가 정적 분석입니다. 네 조건이 실제 실행에서 성립하는지는 원본 코드를 실행해 확인해야 합니다.
  • 이 경로를 쓰는 실제 메뉴 객체, 입력 버퍼의 할당 주소와 치수, LCD 출력은 확인하지 못했습니다.
  • 다음 단계는 표면을 넘기는 원본 호출자와, 그 +8·+0x18을 채우는 실제 값을 찾는 일입니다(viewport 문서의 남은 과제와 같습니다).

재현 방법

고정 RTOS 파일을 Python과 Capstone 5.0.7로 읽어 원본 31구간, A32 명령 38개, 표 값 7개, 진단 문자열 6개를 다시 만듭니다. 원래 검증 기록 전체의 SHA-256이 맞으면 명령 텍스트를 해시로 바꿉니다. 공개 JSON 전체 해시까지 맞을 때만 새 파일을 씁니다. CPU나 MMIO는 실행하지 않습니다. 출력은 실행 중 다른 프로세스가 경로를 바꾸지 않는 디렉터리에 둡니다.

python -B tools/verify_ui_surface_producers.py rtos.bin --output surface-replay.json
python -B -m unittest discover -s tests -p test_ui_surface_producers.py
