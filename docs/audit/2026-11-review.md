# 2026년 11월 문서 검수 기록 — K-3 Mark III

v0.2.0에서 HTML 문서를 다시 쓰면서 페이지마다 내용을 검수했습니다. 이 문서는 그 결과입니다. 무엇을 어떻게 확인했는지, 무엇을 고쳤는지, 저장소 주인의 판단이 필요한 것은 무엇인지 적었습니다.

## 검수 방법과 한계

- 개편 전 HTML의 수치·주소·해시·사례 수를 그 페이지가 근거로 삼는 JSON(`analysis/*.json`, `evidence.json`)과 검증 스크립트(`verify_*.py`, `tools/*.py`)에 대조했습니다. 합계와 뺄셈, 계산 예는 다시 계산했습니다.
- 같은 값이 여러 문서에 나오는 경우 문서끼리도 맞는지 봤습니다.
- 규격 이름, 명령 번호, 제품 사양, 날짜, 소프트웨어 버전 같은 외부 사실은 1차 자료로 확인했습니다.
- 개편 전 문서에 있던 16진수·해시·큰 수·식별자가 새 문서에 남아 있는지 도구로 비교했습니다. 빠진 것은 이유를 확인했습니다.
- **하지 못한 것**: 이 작업 환경에는 원본 펌웨어가 없습니다. 그래서 검증 스크립트를 원본 펌웨어에 다시 돌리지 못했습니다. "근거 JSON과 일치한다"는 말은 공개된 JSON·스크립트와 맞는다는 뜻이며, 펌웨어 바이트를 다시 확인했다는 뜻이 아닙니다.
- Lightroom 쪽은 일부를 다시 계산했습니다. Adobe DNG SDK ZIP과 Profile SDK ZIP의 SHA-256, 시험 DCP 여섯 개의 재생성 해시와 프로파일 지문, 근거 JSON의 정규화 해시가 기록과 일치했습니다.

## 판단이 필요한 항목

근거가 부족해 고치지 않았거나, 이번에 새로 넣은 해석이라 빼도 되는 것들입니다.

**주소·이름이 개편 전 HTML에만 있고 근거 JSON에는 없는 것**

- `startup-storage.html`: `u32[0x50800008] == 0x5aa5a55a`(Emmc 초기화의 magic), 명령 이름 `sys_fwtable`.
- `colorspace-ui.html`: vtable 주소 `0x5364ad68` (JSON에는 블록 시작 `0x5364ad60`만 있음).
- `firmware-structure.html`: BIN 헤더의 빌드 시각 2024-10-08 15:31:16 JST (`evidence.json`에 없음).
- `pipeline-report.html`: "표 분기 검증 정상 4건·거부 5건"에 대응하는 공개 테스트를 찾지 못했습니다.

**이번 개편에서 새로 넣은 비교·해석** (모두 본문에 "확정한 것이 아님"이라고 한정했습니다. 원 연구 범위만 남기려면 해당 참고 상자를 지우면 됩니다.)

- 타이머 문서 일곱 개와 `update-memory.html`: 공개된 T-Kernel 2.0 소스와의 구조 비교. 펌웨어의 서비스 번호는 T-Kernel 2.0의 함수 번호보다 상위 16비트가 일정하게 6 작고 인수 개수는 같습니다. T-Kernel 1.x의 번호표를 구하지 못해 대응을 확정하지 않았습니다.
- `startup-storage.html`: R1 오류 비트 마스크, 호스트 상태 비트, 소프트웨어 리셋 비트를 Linux의 MMC·SDHCI 정의와 견준 것.
- `stubby-load-auth.html`: ROMFS 헤더 배치와의 관계.
- `update-file-lifetimes.html`, `update-media-completion.html`: 경계값 `0x04040000` sector(약 32.1GiB)와 SDHC/SDXC 경계의 관계. ExFat 경계가 SDXC 최소 용량보다 262,144 sector 큰 이유는 모릅니다.
- `guide-boot.html`, `m0-board-config.html`, `firmware-structure.html`: M0 레코드가 칩의 "전원 제어용 Cortex-M0"에서 돈다는 것은 Socionext가 리눅스 커널에 낸 SC2000(M10V) 설명에서 끌어낸 추정입니다.
- `update-timer-clock.html`: "틱 1ms, 하위 시간 ns"를 미확인 가설로 적었습니다. 리코 공개 소스의 클럭 트리로 계산하면 6,750카운트가 정확히 1ms가 되지만, RTOS가 고른 분주비를 확인하지 못했습니다.
- `update-subtick-arithmetic.html`: 32비트 곱의 넘침이 실제 결함일 가능성. 카운터 범위와 호출 조건을 몰라 "미확인"으로 두었습니다.

**해석의 수위**

- `af-drive-architecture.html`: InMotor = 렌즈 안 모터, Joint = 바디 구동이라는 물리적 의미는 확인된 적이 없습니다. 확인한 것은 이름과 선택 조건입니다. 진입 조건 "mode 0, submode 3"은 시험에서 `r8=0`을 입력으로 넣은 것이며 실제 값은 정적 판독에 의존합니다.
- `startup-storage.html`: BOOT가 주 코어 진입 주소를 얻는 "표 index 5"가 어느 레코드인지 확인된 곳이 없습니다. M0·BOOT가 부트 헤더와 표를 읽을 때 eMMC의 어느 영역이 선택되어 있는지도 분석되지 않았습니다.
- `color-lightroom.html`: Auto Select가 모드를 고르는 기준은 리코 자료에서 찾지 못했습니다.
- DNG 규격 1.7.1.0의 쪽 번호 표기가 문서마다 다릅니다. PDF를 내려받지 못한 작업에서는 1.6.0.0 본문과 SDK 헤더로 대신 확인했습니다.
- Adobe의 최소 지원 버전(Camera Raw 13.3 등), Lightroom Classic 15.6이라는 버전은 Adobe 도움말을 열지 못해 다시 확인하지 못했습니다. 기록된 값 그대로입니다.
- 리코의 펌웨어 사용 조건에는 수정·리버스 엔지니어링을 제한하는 조항이 있습니다. 공개 범위에 대한 판단은 저장소 주인의 몫입니다.

**다른 문서로 옮기지 못한 예전 첫 화면의 수치**

- "심층 분석 목록을 115개에서 162개 고유 디컴파일 진입점으로 확장" 가운데 162개.
- M2PCLIP 호출자 14곳을 분류할 때 "새 의사코드 10개를 로컬에 저장".

둘 다 조사 과정의 집계이고 결과에 영향이 없어 새 문서에 넣지 않았습니다. 예전 첫 화면은 v0.1.1 릴리스와 Git 이력에 남아 있습니다.

## 외부 자료로 확인한 사실 (요약)

- 펌웨어 2.20은 2024-10-30 배포, `k3III_v220.zip` → `fwdc233b.bin` (리코 다운로드 페이지).
